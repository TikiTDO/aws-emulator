# opensearch: field-level security never reaches a verdict — the domain data plane has no HTTP-basic authentication for the internal user database, no /_plugins/_security/api/internalusers route, and a role's fls clause is stored but never applied

> _Note: this issue was identified against the code base at commit `3e5df2e7a8c070265aefe0f482ffb5f6c8116a06`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ESHttpGet

## Description
Cause 1 of 1 — on a domain with fine-grained access control switched on, the published domain endpoint does not authenticate an HTTP-basic request, so every call the field-level-security behaviour is made of goes unanswered and the check is cut off at the harness budget; behind that barrier the internal-user API is unrouted and a role's `fls` clause is stored verbatim and never evaluated.

Failing check: opensearch.fgac-field-level-security-hides-field-from-hit-and-from-query.

NOTE ON OVERLAP: open issue 20261103T073642Z-opensearch-eight-more-divergences-the-fgac-security-plugin.md names this check in its Cause 7, but the replay suite does NOT report this failure as owned by it — its replay key for this check no longer matches, so this check is uncovered and is filed here. Treat this issue as the field-level-security cause specifically.

AWS: Smithy: CreateDomain.AdvancedSecurityOptions (AdvancedSecurityOptionsInput) carries Enabled, InternalUserDatabaseEnabled and MasterUserOptions{MasterUserName, MasterUserPassword}; MasterUserOptions$MasterUserName is documented as "a username and password for the master user" used when the internal user database is enabled, and the service requires EncryptionAtRest, NodeToNodeEncryption and EnforceHTTPS alongside it. On such a domain the endpoint DomainStatus$Endpoint publishes accepts HTTP Basic authentication for that master user and serves the security plugin's REST API (recorded behavior for the data plane, which is not a Smithy API): GET /_cluster/health as the master user answers HTTP 200; PUT /_plugins/_security/api/roles/<role> with index_permissions carrying allowed_actions [read, search] and fls ["~<field>"] answers 201; PUT /_plugins/_security/api/internalusers/<user> {"password": ...} answers 201; PUT /_plugins/_security/api/rolesmapping/<role> {"users": [<user>]} answers 201. Afterwards, for the mapped internal user, the excluded field is removed from every read of the document: POST /<index>/_search answers 200 with hits.total.value 1 whose _source carries the permitted fields and NOT the excluded one, a term query on the excluded field answers 200 with hits.total.value 0, a terms aggregation on it answers 200 with an empty buckets list, and GET /<index>/_doc/<id> answers 200 with found true and a _source without the field — while the master user reading the same document on the same index still sees the field and still matches it with a term query. Deleting the role mapping leaves that internal user with no grant at all, so its search is refused HTTP 403 with error.type security_exception (body carrying "no permissions for [indices:data/read/search]") and the refusal does not echo the restricted field's value.

Emulator: no answer is ever produced — the check exhausts the harness budget ("Check timed out after 60.0s") while polling the master user's own HTTP-basic GET /_cluster/health for a 200, the barrier the whole behaviour sits behind. The data plane resolves the calling principal only from a SigV4 credential: services/service-com-amazonaws-opensearch-amazonopensearchservice/src/service/domain_rest.rs is reached from Service::override_operation "for a request carrying a SigV4 credential" and the master-user test state::fgac::is_master matches domain.master_user_arn/master_user_name against that signed principal ARN; nothing in either file reads an Authorization: Basic credential or the internal user database, so a basic-auth request as the master user never becomes that principal and never gets the 200 the client waits for. Behind that barrier two further gaps keep the behaviour unserveable even once basic auth answers: (a) the router has arms for ["_plugins","_security","api","roles",name] and ["_plugins","_security","api","rolesmapping",name] but NO arm for .../api/internalusers/{user}, so creating the restricted internal user falls through to the no-handler answer (HTTP 400 "no handler found for uri [<uri>] and method [<method>]", fixed text "no handler found for uri [" and "] and method [", variable parts the request URI and method) instead of 201; (b) a role document is stored verbatim and its permissions are explicitly not evaluated (domain_rest.rs module docs: a role's index_permissions "are stored and reported back by the security API, and are not evaluated, so a principal any role mapping binds is permitted every action this surface names"; state/fgac.rs SecurityRole doc: "what the emulator reads out of it is nothing"), so an `fls` exclusion has no effect on a search hit, on a term query, on a terms aggregation or on a realtime GET.

Why: fine-grained access control is this service's authorization model, and field-level security is how a client keeps a sensitive field (a salary, a token, a PII column) out of a reader's results. A client that authenticates to its own domain with the master user's basic credentials — the credentials the create call just set — hangs with no response at all, so it cannot create a role, an internal user or a role mapping; and any code that would rely on the field being filtered gets either no answer or (once a role exists) a document that still carries the restricted field and a term query that still matches it, i.e. the data the policy was written to withhold. Nothing refuses it either, so the leak is silent.

Fix: the domain REST data plane of the opensearch service crate — services/service-com-amazonaws-opensearch-amazonopensearchservice/src/service/domain_rest.rs (request authentication: accept HTTP Basic against the domain's internal user database and resolve it to the master user / internal user as the request principal; add the /_plugins/_security/api/internalusers/{user} route; apply a mapped role's fls/dls clauses when projecting a search hit, a realtime GET source, a term/terms query and an aggregation) together with the authorization and security-record state in src/state/fgac.rs (an internal-user record with its password, and evaluation of a role's index_permissions/fls rather than storing them for reporting only).

Traces: opensearch.fgac-field-level-security-hides-field-from-hit-and-from-query (behavioral check, service heading `### opensearch`).

## Evidence
Expected (AWS): on a domain created with AdvancedSecurityOptions {Enabled:true, InternalUserDatabaseEnabled:true, MasterUserOptions:{MasterUserName,MasterUserPassword}} — GET /_cluster/health with HTTP basic auth as the master user -> HTTP 200; PUT /_plugins/_security/api/roles/<role> with index_permissions [{index_patterns:[<index>], fls:["~salary"], allowed_actions:[read, search]}] -> 201; PUT /_plugins/_security/api/internalusers/<user> -> 201; PUT /_plugins/_security/api/rolesmapping/<role> {users:[<user>]} -> 201; then as <user>: POST /<index>/_search -> 200, hits.total.value 1, _source WITHOUT the excluded field and the excluded value absent from the whole response body; term query on the excluded field -> 200 with hits.total.value 0; terms aggregation on it -> 200 with buckets []; GET /<index>/_doc/1 -> 200, found true, _source without the field; as the master user the same GET and term query still see/match the field; after DELETE of the role mapping, the user's search -> HTTP 403 security_exception ("no permissions for [indices:data/read/search]") with no occurrence of the restricted value.

Actual (emulator): nothing is answered at all — "Error: Check timed out after 60.0s" for check opensearch.fgac-field-level-security-hides-field-from-hit-and-from-query, raised while the bounded poll in _wait_admin_auth repeatedly asks GET /_cluster/health with the master user's HTTP basic credentials and never observes HTTP 200. Grounding in the checkout: src/service/domain_rest.rs is entered for "a request carrying a SigV4 credential" and contains no occurrence of a Basic/Authorization credential path (searched the whole 4671-line file); state/fgac.rs::is_master compares domain.master_user_arn/master_user_name to the signed principal ARN only; the router has no ["_plugins","_security","api","internalusers",name] arm (so that PUT yields HTTP 400 "no handler found for uri [...] and method [PUT]" rather than 201); and both domain_rest.rs (module docs, "are stored and reported back by the security API, and are not evaluated") and state/fgac.rs (SecurityRole, "the definition is kept VERBATIM ... what the emulator reads out of it is nothing") state that a role's permissions — hence its fls exclusion — are never applied.

## Steps to Reproduce
1. CreateDomain with EngineVersion OpenSearch_2.11, ClusterConfig {InstanceType t3.small.search, InstanceCount 1, DedicatedMasterEnabled false, ZoneAwarenessEnabled false}, EBSOptions {EBSEnabled true, gp3, 10}, EncryptionAtRestOptions{Enabled:true}, NodeToNodeEncryptionOptions{Enabled:true}, DomainEndpointOptions{EnforceHTTPS:true} and AdvancedSecurityOptions {Enabled:true, InternalUserDatabaseEnabled:true, MasterUserOptions:{MasterUserName:<admin>, MasterUserPassword:<password>}}.
2. Poll DescribeDomain until Processing=false and an Endpoint is published; take that endpoint as the data-plane host.
3. Send GET <endpoint>/_cluster/health with an HTTP `Authorization: Basic` header for <admin>/<password> (no SigV4). AWS answers HTTP 200; the emulator never answers 200, so a bounded poll for this barrier never clears (the check is cut off at 60 s).
4. Past that barrier the remaining calls are also unserved: PUT <endpoint>/_plugins/_security/api/internalusers/<user> {"password":"<p>"} -> HTTP 400 "no handler found for uri [...] and method [PUT]" instead of 201; and after PUT .../api/roles/<role> with index_permissions [{index_patterns:[<index>], fls:["~salary"], allowed_actions:["read","search"]}] plus PUT .../api/rolesmapping/<role> {"users":["<user>"]}, a search as <user> returns the document WITH the excluded field and a term query on that field still matches it, because the stored role is never evaluated.
