# ssm-quicksetup configuration-deployment responses diverge: minted ids, status-summary members, fabricated async executions, post-delete refusal class

> _Note: this issue was identified against the code base at commit `0b692cce1214b5f4b4750727075ba6ccae4ee506`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetConfigurationManager

## Description
Replaying the host-management deployment fixture shows the ssm-quicksetup emulator serving a configuration-deployment view that the recorded service never returns: identifiers in forms the service does not mint, status summaries missing the members AWS always carries, an asynchronous-execution lifecycle the service does not run for this configuration, and a post-delete read refused by the front door instead of reaching the modeled not-found branch. 6 causes; ALL must be closed before this issue is submitted.

Related open issue 20261106T174308Z-ssm-quicksetup-the-configurationmanager-managerarn-routes-turn-a-deleted-manager.md describes the same front-door stage as Cause 6 but is grounded only in the behavioral suite (simparity-behavioral-aws-v1 check ids); the wire replay marks this fixture step as owned by NO issue, so Cause 6 is filed here with its own wire replay key. Resolved issue 20261024T194720Z-ssm-quicksetup-getconfiguration-wrong-behavior.md added the AsyncExecutions summary that Cause 5 is about and does not cover any of these; a resolved issue covers nothing. The three other divergences in this corpus (ListQuickSetupTypes catalog, GetConfiguration rejection class, UpdateServiceSettings validation body) are already owned by open issue 20261029T200609Z-ssm-quicksetup-payload-defects-getconfiguration-rejection-class-updateservicesettings.md and are deliberately NOT re-filed here.

Cause 1 of 6: a configuration definition's Id is a store-wide decimal counter instead of a service-minted opaque token.
AWS: GetConfigurationManager (GET /configurationManager/{ManagerArn}) returns ConfigurationDefinitions[].Id and ListConfigurations (POST /listConfigurations) returns ConfigurationsList[].ConfigurationDefinitionId. Recorded behavior only for the token's form: the model declares ConfigurationDefinition$Id as a plain String with no pattern, and only constrains the id where it is accepted as input (Smithy: ListConfigurationsInput.ConfigurationDefinitionId @pattern ^[a-z0-9-]{1,20}$). The recording serves a short opaque lowercase-alphanumeric token (the recorded instance is the 5-character 'vsir7', which also appears as the middle segment of the configuration Id in Cause 2); the corpus asserts the token's SHAPE, not its characters, so the exact letters are a per-run filler and never a requirement.
Emulator: ConfigurationDefinitions[0].Id and ConfigurationsList[0].ConfigurationDefinitionId are both '1'. services/service-com-amazonaws-ssmquicksetup-quicksetup/src/state.rs mints the id in ComAmazonawsSsmquicksetupQuicksetupState::fresh_definition_id by incrementing the store-wide next_definition_id counter and stringifying it, so the Nth definition any manager in the store ever creates is named by that ordinal.
Why: the id is an opaque service identifier a client round-trips into ListConfigurations/UpdateConfigurationDefinition and persists. A decimal ordinal is guessable and shared across managers, so a client that caches a definition id, or that asserts the service's id form, is driven by values AWS does not mint; two managers created in either order swap ids, which no AWS-backed client expects.
Fix: definition-id minting in the ssm-quicksetup service crate's state (services/service-com-amazonaws-ssmquicksetup-quicksetup/src/state.rs, fresh_definition_id and its doc comment) — mint a short opaque lowercase-alphanumeric token per definition, as fresh_uuid already does for the resources whose ids are uuids.
Traces: ssm-quicksetup-host-management-configuration-deploys#task#6, ssm-quicksetup-host-management-configuration-deploys#task#7.

Cause 2 of 6: a deployed configuration's Id is a bare uuid instead of AWS's composite deployment identifier.
AWS: ListConfigurations returns ConfigurationsList[].Id, documented as 'A service generated identifier for the configuration' (Smithy: ConfigurationSummary$Id, plain String, no pattern — recorded behavior only for its structure). The recording's identifier is THREE colon-separated segments: the owning configuration manager's uuid, then the configuration-definition id, then the base64 of '<account-id>:<region>'. The recorded instance 'e6e9348a-149f-4abc-81a4-000000000001:vsir7:MTIzNDU2Nzg5MDEyOnVzLXdlc3QtMg' decodes its third segment to '123456789012:us-west-2'; the fixed part of the requirement is the three-segment '<manager-uuid>:<definitionId>:<base64(account:region)>' structure, and the particular uuid, definition token, account id and Region are values taken from the manager, the definition and the deployment target, never literals to copy.
Emulator: ConfigurationsList[0].Id is a bare uuid ('86ce654b-b6d0-46e9-8645-000000000002'), carrying none of the three segments. state.rs ComAmazonawsSsmquicksetupQuicksetupState::deploy_definition builds each per-target configuration with `let id = self.fresh_uuid();` and ConfigurationRecord::deployed stores that as the record's id and store key, and the fresh_uuid doc comment asserts that 'a configuration's Id takes the same shape' as a manager ARN's uuid, which the recording contradicts.
Why: the configuration id is the deployment's address — it is what GetConfiguration takes as its path label, and it is how a client correlates one configuration row back to the manager, the definition and the account/Region it was deployed into. A bare uuid loses that correlation entirely, so a client that parses the id (or that builds per-account/Region bookkeeping from it) reads nothing, and the id cannot be reconstructed from a ListConfigurations row the way AWS's can.
Fix: configuration-id minting in the ssm-quicksetup service crate's state (services/service-com-amazonaws-ssmquicksetup-quicksetup/src/state.rs: deploy_definition's call to fresh_uuid, ConfigurationRecord::deployed, and the fresh_uuid doc claim about a configuration Id's shape) — compose the id from the manager uuid, the definition id and the base64 of the target account and Region.
Traces: ssm-quicksetup-host-management-configuration-deploys#task#7.

Cause 3 of 6: members AWS carries as the empty string are dropped from the response instead of serialized.
AWS: GetConfigurationManager returns Description (optional String) and StatusSummaries[].StatusMessage (optional String, 'When applicable, returns an informational message relevant to the current status and status type'). Recorded behavior: for a manager created without a description, and for a status summary whose status is the whole of the report, the response carries those members PRESENT with the empty string '' — the member exists in the JSON body with an empty value rather than being omitted.
Emulator: both members are absent from the body (replay reports $.Description expected '' got None, and $.StatusSummaries[0].StatusMessage expected '' got None). In services/service-com-amazonaws-ssmquicksetup-quicksetup/src/state.rs, StatusSummaryRecord::to_status_summary passes status_message straight through, and state.rs's status_message(status_type, status) returns None for every pair it does not name (its `_ => return None` arm, with the comment that a terminal deployment status 'is the outcome itself'), so a terminal summary loses the member; the manager's description is likewise serialized as the stored Option, so an unset description emits nothing.
Why: present-and-empty and absent are different to a client. An SDK or template that reads the member unconditionally gets a null/KeyError where AWS gives it an empty string, and a client that distinguishes 'no message for this phase' (empty) from 'this field was not returned' cannot: a diff of two responses shows a member appearing and disappearing across phases.
Fix: the GetConfigurationManager output serialization in the ssm-quicksetup service crate — services/service-com-amazonaws-ssmquicksetup-quicksetup/src/state.rs (StatusSummaryRecord::to_status_summary and status_message) and src/ops/get_configuration_manager.rs where the manager's description is copied into the output: emit these members as the empty string rather than omitting them.
Traces: ssm-quicksetup-host-management-configuration-deploys#task#6.

Cause 4 of 6: StatusDetails is never populated, so every status summary omits the per-target counters.
AWS: StatusSummary$StatusDetails is the modeled StatusDetails map ('Details about the status'). Recorded behavior for a deployment: every summary carries StatusDetails present with the three string-valued counters 'failed', 'pending' and 'succeeded' — the keys are fixed text and the values are the counts of deployment targets in each state taken from the service's own state (the recording shows succeeded '1', failed '0', pending '0' for the single-target deployment summary, and all three '0' for a kind of work that has not run). The counts themselves come from the request's targets and the emulator's state; only the three key names are fixed.
Emulator: the member is absent from every summary. state.rs StatusSummaryRecord::walking initializes `status_details: BTreeMap::new()` and nothing ever inserts into it, and to_status_summary serializes the map only `(!self.status_details.is_empty()).then(...)` — so the map is always empty and the member is always dropped. The field's own doc comment states the rule the emulator follows ('a summary with no details to report carries the member absent'), which is the opposite of what the service records.
Why: StatusDetails is how a client reads deployment progress numerically — how many targets succeeded, failed or are still pending. With the member absent, a poller cannot tell a partially-failed deployment from a wholly successful one, and anything that sums these counters to drive a progress display or a failure branch sees nothing at all.
Fix: status-summary construction in the ssm-quicksetup service crate's state (services/service-com-amazonaws-ssmquicksetup-quicksetup/src/state.rs: StatusSummaryRecord::walking / settle / to_status_summary) — maintain and always serialize the failed/pending/succeeded counters for the summary's own targets.
Traces: ssm-quicksetup-host-management-configuration-deploys#task#6.

Cause 5 of 6: an asynchronous-execution lifecycle is fabricated — the AsyncExecutions summary is advanced to SUCCEEDED with an invented sentence, and one is attached to each listed configuration where the service reports none.
AWS: StatusType is the modeled two-value enum {Deployment, AsyncExecutions} and Status includes NONE, 'the status a kind of work that has not run reports'. Recorded behavior for this host-management deployment: after the deployment reaches its terminal status, the manager's AsyncExecutions summary still reports Status 'NONE' with zeroed StatusDetails counters and an empty StatusMessage — no asynchronous executions ran, so the summary never leaves NONE; and a ListConfigurations row for the deployed configuration carries ONLY the Deployment summary, with no AsyncExecutions entry at index 1 at all.
Emulator: the AsyncExecutions summary is walked to 'SUCCEEDED' on the clock and carries the locally invented sentence 'All asynchronous executions have succeeded.' (replay: $.StatusSummaries[1].Status expected 'NONE' got 'SUCCEEDED'; $.StatusSummaries[1].StatusMessage expected '' got that sentence), and ListConfigurations emits an extra $.ConfigurationsList[0].StatusSummaries[1] of StatusType AsyncExecutions. In services/service-com-amazonaws-ssmquicksetup-quicksetup/src/state.rs, ASYNC_EXECUTION_PHASES = [STATUS_NONE, STATUS_SUCCEEDED] makes NONE a transient phase the clock is obliged to leave, fresh_summaries attaches StatusSummaryRecord::async_executions to the manager AND to every configuration deployed from its definitions, and status_message hard-codes the two AsyncExecutions sentences.
Why: a client polling for completion reads the status summaries as the service's report of what work exists and how it went. The emulator asserts that asynchronous executions ran and succeeded when none ran, and invents a message in place of the empty one, so a client that waits for all summaries to be terminal, or that surfaces StatusMessage to an operator, is told about work the service never performed; the extra per-configuration summary also shifts the index of every entry a client reads positionally.
Fix: status-summary composition in the ssm-quicksetup service crate's state (services/service-com-amazonaws-ssmquicksetup-quicksetup/src/state.rs: ASYNC_EXECUTION_PHASES, fresh_summaries, StatusSummaryRecord::async_executions and the status_message table) and the ConfigurationRecord::to_summary path ListConfigurations serializes — NONE must be a resting status for work that did not run, and a listed configuration must carry only the summaries the service actually reports for it.
Traces: ssm-quicksetup-host-management-configuration-deploys#task#6, ssm-quicksetup-host-management-configuration-deploys#task#7.

Cause 6 of 6: reading the caller's OWN manager after deleting it is refused 401 UnauthorizedException instead of reaching the modeled 404 ResourceNotFoundException.
AWS: GetConfigurationManager binds ResourceNotFoundException with errorKind client and httpError 404 (Smithy: GetConfigurationManager errors = AccessDeniedException 403, ConflictException 409, InternalServerException 500, ResourceNotFoundException 404, ThrottlingException 429, ValidationException 400 — the model declares no 401 and no UnauthorizedException shape anywhere in this service). Recorded behavior: a caller that deletes a manager and then polls GET /configurationManager/{ManagerArn} on the SAME ARN — its own account, the endpoint's Region — is answered HTTP 404 with error code ResourceNotFoundException, which is what lets a teardown poll converge. Hypothesis for the discriminator: AWS's front door judges the ARN's account and Region against the caller and the endpoint, not whether a manager is currently stored, so a deleted manager of the caller's own account reaches the handler's not-found branch while a genuinely foreign ARN is still refused.
Emulator: the request never reaches the handler; the poll is answered HTTP 401 with __type / x-amzn-errortype 'UnauthorizedException' and body {"message": "Unauthorized"}, and the fixture's teardown poll therefore never converges (replay: 'error code UnauthorizedException not in [ResourceNotFoundException] after 19 attempt(s)', poll capped at 180s). services/service-com-amazonaws-ssmquicksetup-quicksetup/src/service.rs enrolls get_configuration_manager::GetConfigurationManager in target_authorization_table, and TargetAuthorization::serves is nothing but `store.settle(SystemTime::now()); store.manager_in(&region, arn).is_some()` — store presence is the whole authorization predicate — so an absent manager is refused by unauthorized() before src/ops/get_configuration_manager.rs can raise its ResourceNotFoundException. The handler's own module doc (lines 9-12) claims this route's ARN is resolved in the handler rather than by that stage, which is not what the stage does.
Why: 401 is a credentials fault and 404 is a resource-state fault. Every delete-then-verify and teardown loop branches on ResourceNotFoundException to decide a delete is done; a 401 is not in this operation's generated error union, so it surfaces as an unmatched generic client error, drives credential-refresh paths, and makes idempotent cleanup raise instead of completing. No client can ever observe this operation's not-found answer.
Fix: the request-authorization stage in the ssm-quicksetup service crate (services/service-com-amazonaws-ssmquicksetup-quicksetup/src/service.rs: TargetAuthorization::serves / refusal, target_authorization_table, the unauthorized() renderer and the module doc stating the rule) — its predicate must be the ARN's entitlement (the ARN's account and Region against the caller and the endpoint being served), not the presence of a row in the store, so an ARN the caller owns in this Region passes through to the handler that already carries the modeled 404 and its not-found sentence. A genuinely foreign ARN must keep answering 401, as the fixture ssm-quicksetup-not-found-error-paths records.
Traces: ssm-quicksetup-host-management-configuration-deploys#teardown#9.
