# ElastiCache data plane still unreachable and multi-wait flows never converge: a VPC-attached Lambda opens no connection, the advertised cache endpoint accepts no TCP, and status polls burn the whole budget (4 causes, 17 checks)

> _Note: this issue was identified against the code base at commit `dff6e291e5e6489707888b0049fa49b367909ca3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeCacheClusters

## Description
Four net-new root causes, grounded in the 17 failing elasticache checks the replay report binds to no open issue. Related open issues report the same families but own a different set of replay keys and none of the ids below: 20261108T152921Z-elasticache-in-vpc-data-plane-unverifiable-the-emulator.md (its keys are pinned to `_probe_call#NN` frames that no longer match — the probe now executes), 20261105T090541Z-elasticache-every-in-vpc-data-plane-check-is.md (symptom: os.register_at_fork missing) and 20261110T144301Z-elasticache-multi-step-lifecycle-flows-never-converge-every.md (same convergence mechanism, 4 other check ids). The earlier _ssl defect filed as 20261110T001859Z-elasticache-in-vpc-data-plane-still-unverifiable-the.md is now resolved: the probe package imports and runs (selftest returns ok:true with a verified proof digest), so what blocks these checks is the next barrier, not that refusal — Invoke itself answers 200 with no FunctionError.

Cause 1 of 4: a Lambda function created with VpcConfig has no network vantage point inside the VPC it named — every datagram socket it opens fails, so no in-VPC executor can be stood up.
AWS: recorded behavior only (no Smithy shape governs a runtime sandbox). CreateFunction with VpcConfig{SubnetIds, SecurityGroupIds} attaches ENIs in those subnets; the running function's outbound socket toward an in-VPC address reports getsockname()[0] inside the VPC's CIDR, and a DNS query to the VPC resolver at the VPC CIDR base + 2 is answered. Those two signals are the only way a client can prove it is inside the VPC, and both are answerable only from inside it.
Emulator: CreateFunction accepts the VpcConfig, Invoke returns 200 with no FunctionError and the handler's selftest payload verifies ({'ok': True, 'proof': <digest>}), but every socket operation fails with the emulator's own OSError: `[Errno 101] a Lambda function in this emulator opens no connection: the only address its datagrams reach is the X-Ray daemon named by AWS_XRAY_DAEMON_ADDRESS`. In the selftest digest src_ip is None with src_ip_error `OSError: errno=101 [Errno 101] a Lambda function in this emulator opens no connection: the only address its datagrams reach is the X-Ray daemon named by AWS_XRAY_DAEMON_ADDRESS`, and resolver_rcode/resolver_ancount are both None with the same errno-101 resolver_error. The fixed text of that message is entirely the emulator's own prose — AWS emits no such sentence; the only per-run values in the evidence are the resolver address (VPC CIDR base + 2), the CIDR itself, the function name and the subnet/security-group ids. The runtime also reports python '3.14.0.alpha' while advertising AWS_Lambda_python3.12.
Why: VPC attachment is the whole premise of private cache access. A client that creates a VPC-attached function, gets 200 from CreateFunction and 200 from Invoke, and then finds no socket works cannot distinguish 'my security group is wrong' or 'my cache is down' from 'this function has no networking'. Every ElastiCache behaviour that is only observable from inside the VPC — AUTH enforcement, Lua EVAL atomicity and the script cache, key expiry/TTL, security-group ingress revocation, stream XAUTOCLAIM min-idle selection, the SLOWLOG threshold parameter, and a transit-encryption endpoint refusing plaintext RESP — is unmeasurable, and the checks say so explicitly ('the in-VPC executor is unusable, so this run measured nothing').
Fix: the Lambda invoke/execution path's VPC attachment in the emulator — give a VpcConfig-attached function a network vantage point inside the named VPC with that VPC's resolver reachable, or refuse the VpcConfig rather than accepting it and running the function with no network.
Traces: elasticache.elasticache-auth-token-required-cluster-rejects-unauthenticated-command, elasticache.elasticache-lua-eval-atomicity-and-script-cache, elasticache.elasticache-redis-key-expiry-removes-value-and-reports-ttl, elasticache.elasticache-revoked-security-group-ingress-blocked-from-cache-data-plane, elasticache.elasticache-streams-xautoclaim-min-idle-threshold-selects-pending-entries, elasticache.slowlog-threshold-parameter-governs-what-the-engine-records, elasticache.transit-encryption-endpoint-refuses-plaintext-resp-in-vpc.

Cause 2 of 4: the cache endpoint the control plane advertises accepts no TCP connection from inside its own VPC, so ElastiCache has no data plane at all.
AWS: Smithy: Endpoint is documented 'Represents the information required for client programs to connect to a cache node', with Endpoint$Address 'The DNS hostname of the cache node' and Endpoint$Port 'The port number that the cache engine is listening on'. Recorded behaviour: once DescribeCacheClusters reports CacheClusterStatus 'available' and a CacheNodes[].Endpoint, a TCP connect to that Address:Port from inside the cluster's VPC succeeds and speaks RESP (SET returns +OK, GET returns the bulk string, a missing key returns a null bulk, TTL returns -1/-2, INCR on a string returns an -ERR reply, DEL returns 1 then 0).
Emulator: the stream-socket path fails with the emulator's own OSError `a Lambda function in this emulator has no host network to reach`, so the probe reports `connect: OSError: a Lambda function in this emulator has no host network to reach` and the checks assert `DATAPLANE_UNIMPLEMENTED: the cache endpoint <Endpoint.Address>:<Endpoint.Port> advertised in DescribeCacheClusters accepts no TCP connection from inside its own VPC ...; an endpoint that cannot be connected to is not a data plane` and `DATAPLANE_UNIMPLEMENTED: the RESP session to <Endpoint.Address>:<Endpoint.Port> broke after []`. The hostname, port and cluster id in those sentences are per-run values; the requirement is that whatever Address/Port the emulator publishes is one it listens on and serves RESP from inside that VPC. Hypothesis: the same absent Lambda host network as Cause 1 surfaces on the stream path with a second message, and nothing listens for the published cache address either; the replay cannot separate the two, because the connect never leaves the sandbox.
Why: a client that provisions a cache and reads its endpoint out of DescribeCacheClusters cannot store or read a single key. Snapshot/restore data persistence, which is only provable by writing a key, snapshotting, restoring and reading it back, is unverifiable.
Fix: the ElastiCache data plane — serve RESP on the address and port the cluster/serverless-cache projection publishes (and publish an address the emulator actually listens on), together with the Lambda network vantage point of Cause 1.
Traces: elasticache.cache-cluster-resp-protocol-round-trip-over-socket, elasticache.e2e-cluster-snapshot-restore-data-persists.

Cause 3 of 4: multi-wait flows that chain control-plane status waits with data-plane steps never finish — each is killed by the 60 s per-check budget inside a poll loop, with no assertion ever firing.
AWS: recorded behaviour per flow: CacheCluster$CacheClusterStatus goes creating -> available and ReplicationGroup$Status goes creating -> available; Snapshot$SnapshotStatus is documented 'creating | available | restoring | copying | deleting'; ServerlessCache$Status allowed values are documented 'CREATING, AVAILABLE, DELETING, CREATE-FAILED and MODIFYING' (recorded wire values lower case). Once a resource has settled, the FIRST client read reports the settled value; an auth-token ROTATE makes both the old and the new token authenticate until SET finalises it; a user-group membership change is reflected after the group returns to active.
Emulator: all seven flows end with the identical detail 'Check timed out after 60.0s' and no failing assertion. Mechanism in this checkout: services/service-com-amazonaws-elasticache-amazonelasticachev9/src/state.rs:403 `pub const CLUSTER_TRANSITION: Duration = Duration::from_millis(500);` and :413 SNAPSHOT_TRANSITION, documented 'deliberately NOT zero ... The due instant is stored on the record and materialised by whichever later call reads it'. A client's first poll therefore always observes the transient status and then sleeps its full 15-20 s interval; three to six such waits per flow exhaust the budget even though the emulator settled in half a second. Hypothesis for the remainder: these same flows also drive the in-VPC probe of Causes 1-2, whose connect attempts add wall clock before any assertion is reached; the replay cannot separate the two contributions, because no assertion in these checks fired.
Why: a client written against AWS polls a lifecycle status on an interval sized for AWS (tens of seconds). Against this emulator every wait costs the client that whole interval instead of returning immediately, so a flow that chains several waits takes minutes and is indistinguishable from a resource that never settles. SDK waiters and CI pipelines time out, and a client cannot tell 'still provisioning' from 'stuck'.
Fix: the status-settling path of the elasticache crate's state — a resource whose transition is already due must read back settled to the FIRST call that observes it (or the transient span must be short enough that a client's next request sees the settled value), while the create/modify/delete RESPONSE keeps reporting the transient status other checks assert.
Traces: elasticache.auth-token-dual-validity-window, elasticache.auth-token-special-characters-preserved, elasticache.e2e-cluster-scale-failover-data-consequence, elasticache.e2e-cluster-snapshot-restore-data-consistency, elasticache.e2e-serverless-snapshot-restore-flow, elasticache.e2e-user-group-auth-enforcement-flow, elasticache.elasticache-redis-set-get.

Cause 4 of 4: a purely control-plane serverless-cache create -> wait available -> modify -> wait applied -> delete -> wait gone flow never converges either, so the defect of Cause 3 is not confined to data-plane checks.
AWS: Smithy: CacheUsageLimits{DataStorage{Minimum,Maximum,Unit}, ECPUPerSecond{Minimum,Maximum}} are integers and round-trip through create -> modify -> describe with no rounding; ServerlessCache$Status settles at 'available'; after DeleteServerlessCache the name stops resolving and a ModifyServerlessCache on it is refused 404 ServerlessCacheNotFoundFault with the message 'Serverless cache with name <ServerlessCacheName> not found.' (fixed text 'Serverless cache with name ' + the requested name + ' not found.').
Emulator: 'Check timed out after 60.0s' with no assertion failing. The flow has three waits on DescribeServerlessCaches at interval 15 s (Status == 'available'; Status == 'available' AND CacheUsageLimits.DataStorage.Maximum == the modified value; then absence after delete), and the first poll of each never sees the settled value, so 45 s+ of sleeping is spent before the integer-precision and not-found assertions are ever reached. Related open issue 20261110T153512Z-elasticache-describeserverlesscaches-never-converges-the-serverless-cache-poll.md reports a DIFFERENT symptom for this surface (the poll answering 404 ServerlessCacheNotFoundFault for the whole window) and does not carry this check id; here Describe answers 200 and the status simply is not settled on first read.
Why: a client cannot confirm a serverless cache became available, cannot confirm a usage-limit modification applied, and cannot confirm a delete completed, without paying a full poll interval per step; the integer round-trip and the post-delete refusal are never observable at all.
Fix: the same status-settling path as Cause 3, applied to the ServerlessCache projection read by DescribeServerlessCaches.
Traces: elasticache.serverless-cache-usage-limits-numeric-precision-persists.
