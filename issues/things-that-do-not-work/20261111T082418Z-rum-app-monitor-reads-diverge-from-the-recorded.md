# RUM app-monitor reads diverge from the recorded corpus: GetAppMonitorData never reports ingested events, GetAppMonitor advertises an unrecorded vended CwLogGroup

> _Note: this issue was identified against the code base at commit `767c5fc850277081efd4126ee58e3d62591d7ee3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetAppMonitorData

## Description
TWO distinct net-new root causes in the RUM app-monitor read path, both found by replaying the wire corpus (simparity-wire-aws-v1, 3 mismatched steps of 283). BOTH must be closed before submitting; each is numbered below and carries its own fixture and step.

Cause 1 of 2: an event accepted by PutRumEvents is never reported by GetAppMonitorData, so the data plane is write-only.
AWS: recorded behavior only (the Smithy model documents neither the unit of TimeRange nor the shape of EventData: TimeRange$After/Before target QueryTimestamp, a plain `long` with @default(0), and EventData is an unconstrained string). The recording shows that after a successful PutRumEvents for an app monitor Id, a GetAppMonitorData(Name=<monitor>, TimeRange={After,Before}) over a window spanning the submission returns the delivered event in Events[] as a JSON document, and NextToken null on the last page. The recorded document is the SERVER-side enriched event, not the client structure that was submitted: its keys are userId, sessionId, application_id, application_version, application_name, event_id, event_timestamp, event_type, event_version, log_stream, batch_id, metadata (with metadata_keys / metadata_values projections), event_details, user_details, account_id and event_interaction. Its event_timestamp is an epoch instant in MILLISECONDS (the recorded value is a 13-digit epoch), which is the same unit the query window is expressed in. Those key names and that unit are the requirement; the particular ids, session/user ids, batch id, timestamps and account id in any one recording are per-run values that fill the template and are NOT requirements.
Emulator: GetAppMonitorData answers 200 with Events: [] for the whole polling window (the corpus poll was capped at 180s and never saw the event), while PutRumEvents had returned 200. The event IS written to state (services/service-com-amazonaws-rum-rum/src/ops/put_rum_events.rs calls record.record_events(...)), so the loss is on the read side: the window comparison runs in SECONDS. services/service-com-amazonaws-rum-rum/src/ops/get_app_monitor_data.rs builds `Window` straight from TimeRange$After/Before and documents them as "seconds since the epoch", defaults an omitted Before to now_seconds(), and tests each event with crate::state::event_instant_seconds. Hypothesis: a caller sending the millisecond bounds AWS takes therefore asks for a window roughly a thousand times beyond the stored instant, so `Window::covers` is false for every event and the page is always empty. Separately, the document the emulator would report is the one PutRumEvents stored — only {id, timestamp, type, metadata, details} (see event_json in put_rum_events.rs) — so even with the window fixed the reported event would not carry the enriched keys AWS reports (event_id / event_timestamp / event_type / event_details / user_details / application_* / batch_id / account_id / metadata_keys / metadata_values).
Why: a client cannot read back its own telemetry. Ingestion is unverifiable, dashboards and tests that poll GetAppMonitorData see an empty page rather than an error and hang until their own timeout, and a client that does get a page cannot find event_id or event_timestamp where AWS puts them.
Fix: the GetAppMonitorData reader's time-range filter and the PutRumEvents event-store projection must agree with AWS on both the unit of the window (epoch milliseconds) and the enriched event document the read reports. Components: the Window/now_seconds/event-instant codec in GetAppMonitorData's handler and the event_json projection in the PutRumEvents handler (plus the shared instant codec in the service state).
Related open issues that do NOT cover this: 20261028T204859Z-rum-getappmonitordata-pagination.md (resume-by-count page drift, a different cause on the same operation) and Cause 2 of 20261029T192752Z-rum-app-monitor-data-plane-resource-policy-tagging.md (same behavior seen from the behavioral suite, but it carries no wire replay key, so this fixture step is not gated by it).
Traces: rum-page-view-event-is-returned-by-get-app-monitor-data#task#3.

Cause 2 of 2: GetAppMonitor advertises a vended CloudWatch Logs group name that is not the one the recording binds for the monitor.
AWS: recorded behavior only (Smithy: CwLog$CwLogGroup is "The name of the log group where the copies are stored", an unconstrained String with no pattern or length; DataStorage.CwLog is reported inside AppMonitor by GetAppMonitor). The recording expects DataStorage.CwLog.CwLogGroup to equal the corpus binding for the monitor's vended log group (`{{cw_log_group}}`): the fixed text of such a name is the vended-logs prefix /aws/vendedlogs/RUMService_ followed by the app monitor's own name, and its variable part is the service-chosen suffix, which must be the SAME name as the log group RUM actually vended for that monitor and must stay stable across reads. The suffix of any one recording is a per-run value, not a requirement; what is required is that the advertised name resolves to the monitor's vended group as the recording binds it.
Emulator: GetAppMonitor answers 200 but DataStorage.CwLog.CwLogGroup does not satisfy that binding — the emulator draws the suffix from its own counter domain (ComAmazonawsRumRumState::mint_cw_log_group / cw_log_group_name in services/service-com-amazonaws-rum-rum/src/state.rs: CW_LOG_GROUP_PREFIX + the monitor name + CW_LOG_GROUP_SUFFIX_LEN = 12 lowercase hex characters, an emulator-chosen width stated as such in that file's own docs), so the name it advertises is unrelated to anything the recording can resolve for that monitor. Two fixtures diverge identically on this one JSON path, at different points of the monitor's lifecycle (right after a create with full configuration, and after a lifecycle update), so it is the name's derivation and not one step's state.
Why: a client that takes CwLogGroup from GetAppMonitor and then addresses CloudWatch Logs with it (to read, subscribe to or tag the vended group) is handed a name the rest of the environment does not recognise, and any correlation of "the group RUM vended" with "the group RUM advertises" fails.
Fix: the vended-log-group naming in the service state (mint_cw_log_group / cw_log_group_name) and the DataStorage.CwLog projection that GetAppMonitor's handler reports from the record — the advertised name must be the one the monitor's vended group is actually provisioned under and must be derivable the way AWS derives it, rather than from this emulator's own id counter.
Traces: rum-app-monitor-full-configuration#task#2, rum-basic-app-monitor-lifecycle#task#4.
