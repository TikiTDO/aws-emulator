# ecs__efs__logs: a Fargate container has no filesystem at all, so an efsVolumeConfiguration volume is never mounted — the shared write/read and the readOnly EROFS refusal are unobservable

> _Note: this issue was identified against the code base at commit `d9e20b4dbdf06191d17fc8b16aa8f32f57ea4689`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RunTask

## Description
One net-new root cause. This check is not marked ALREADY FILED and is not OWNED by any open issue in this replay. The open issue 20261111T030649Z-ecs-efs-logs-an-efs-volume-shared-by.md describes the same scenario, but it is keyed on a different failure (`_poll_until#5|Timeout` — the check was killed at its 60 s budget and no container output arrived at all) and therefore does not cover this one: the container now DOES run and DOES deliver output to the awslogs stream, and the surviving divergence is narrower and newly visible — the container's session has no filesystem, so the mounted EFS volume does not exist inside it. That issue is named here so a fixer can see the relationship; it is not a duplicate of it.

Cause 1 of 1: a task definition volume with an `efsVolumeConfiguration` is not mounted into the container at its `mountPoints[].containerPath`, because the emulator's container session provides no filesystem of any kind.

AWS: a Fargate task whose task definition declares `volumes[].efsVolumeConfiguration` (Smithy: EFSVolumeConfiguration.fileSystemId required; EFSVolumeConfiguration.transitEncryption; EFSAuthorizationConfig.accessPointId/iam) has that EFS file system mounted into every container that lists the volume in `containerDefinitions[].mountPoints` at `containerPath` (Smithy: MountPoint.sourceVolume, MountPoint.containerPath, MountPoint.readOnly — "If this value is true, the container has read-only access to the volume"). Inside the container that path is a real POSIX filesystem: a redirection into it creates a file, `wc -c` on that file reports the bytes written, `ls -l` reports a regular writable file (mode beginning `-rw`), a second task mounting the same file system reads back the first task's exact bytes after the first task has STOPPED, and a write through a mount point with `readOnly: true` is refused by the kernel with EROFS, whose message as busybox `sh` words it is the fixed text `Read-only file system`, while a read through the same mount still succeeds. The container's stdout is delivered to the configured `awslogs` group. The data-plane effects themselves are recorded behavior only; the Smithy model states the plumbing (the shapes above).

Emulator: the container's program is performed in-process by a session that deliberately holds no filesystem (`services/service-com-amazonaws-ecs-amazonec2containerservicev20141113/src/state/container_shell.rs`: "It has no process to start, no network to reach, no filesystem and no host environment"; `BUILT_IN_COMMANDS` is exactly `echo true false : exit export unset trap sleep wait`, and every other command, every redirection and every command substitution returns `EXIT_COMMAND_NOT_FOUND` = 127). The declared EFS volume and its mount points are therefore never materialised anywhere a command could reach. For the writing arm the entire program `set -e; echo "$MARKER" > /mnt/shared/payload; sync; echo "A-SIZE=$(wc -c < /mnt/shared/payload)"; echo "A-MODE=$(ls -l /mnt/shared/payload | cut -c1-10)"; echo A-DONE` delivered a single log line, `A-DONE`: the redirection into the mount, `sync`, and both command substitutions were each declined 127, so the file was never created, no size and no mode were ever reported, and nothing was left for the sibling tasks to read or be refused. The task nevertheless reports container `exitCode` 0 — the status of the one `echo` that did run — so a client cannot even tell from the exit code that nothing happened.

Why: a client relying on AWS's behavior gets two guarantees silently voided. An EFS volume shared between tasks is a correctness guarantee: data a task writes must be visible to a later task on the same file system, and here every write is dropped, so a pipeline that stages data in one task and consumes it in another reads an empty (in fact non-existent) path and either fails obscurely or processes nothing. `mountPoints[].readOnly` is a containment guarantee: a write through a read-only mount must be refused with EROFS, and here it is neither refused nor performed, so a workload whose confinement is being validated passes against the emulator and a test asserting the refusal can never observe it. Because the failing commands do not move the container's exit code, both failures present as a task that ran successfully.

Fix: the ECS container data plane — the task-execution path behind RunTask, i.e. `state::container_shell` together with `state::container_runtime` and `state::container_logs`. It must give a task's containers a filesystem, attach each task-definition volume (including an `efsVolumeConfiguration` volume, backed by the named EFS file system and access point so two tasks on the same file system share one namespace) at each container's `mountPoints[].containerPath`, enforce `mountPoints[].readOnly` by refusing writes with the kernel's EROFS and its `Read-only file system` message while still permitting reads, and support the file-touching command forms a container actually uses against such a mount (redirection into and out of a mounted path, and the utilities that report on it) so that the container's own output reflects what happened on the volume.

## Evidence
Cause 1 — Expected (real AWS): task A's `echo "$MARKER" > /mnt/shared/payload` creates the file on the mounted EFS volume, so A's log carries `A-SIZE=<len(marker)+1>` (the marker's bytes plus its newline, as the container's own `wc -c` reports) and `A-MODE=-rw...`; a second task B started only after A reached STOPPED reads `B-SAW=<marker>` back from the same path and appends to it; a third task C whose mount point is `readOnly: true` still reads the current content but has its append refused with the kernel's EROFS, whose message text is the fixed string `Read-only file system`, and never prints `C-WROTE`; a fourth task D confirms the refused write left no trace.

Actual (emulator): the writing task's whole log is `['A-DONE']` and the check fails at
  `AssertionError: the file A wrote must be exactly the 25 bytes of the marker plus its newline, as the container's own wc reports it; log=['A-DONE']`
The only variable part of that message is the marker's own length (25 here, a per-run value — the requirement is `len(marker)+1`, not 25). Every command that touched `/mnt/shared/payload` — the output redirection, `sync`, `wc -c < …` and `ls -l …` inside the two command substitutions — was declined with status 127 (`EXIT_COMMAND_NOT_FOUND`, `src/state/container_shell.rs`), so no `A-SIZE=`/`A-MODE=` line exists, and the arms that depend on A's bytes (B's read-back, C's EROFS refusal, D's no-trace confirmation) are never reached. The container still reports `exitCode` 0 because the final `echo A-DONE` succeeded.

Source of the behavior, for reference: `src/state/container_shell.rs` — module doc "It runs IN THIS PROCESS. It has no process to start, no network to reach, no filesystem and no host environment"; `BUILT_IN_COMMANDS = ["echo", "true", "false", ":", "exit", "export", "unset", "trap", "sleep", "wait"]`; `Command::Compound(compound, redirects)` returns `EXIT_COMMAND_NOT_FOUND` when `redirects.is_some()` ("A redirection names a file this container has no filesystem for, so a command carrying one did not run").

## Steps to Reproduce
1. Create an EFS file system, a mount target in the task subnet, and an access point rooted at /data, all polled `available`.
2. Register an awsvpc/FARGATE task definition with `volumes=[{name: shared, efsVolumeConfiguration: {fileSystemId: <fs>, transitEncryption: ENABLED, authorizationConfig: {accessPointId: <ap>, iam: ENABLED}}}]` and one busybox container whose `mountPoints` is `[{sourceVolume: shared, containerPath: /mnt/shared, readOnly: false}]`, logging via the `awslogs` driver to a log group. Register a second, identical definition with `readOnly: true`.
3. RunTask the read-write definition with the command override `sh -c 'set -e; echo "$MARKER" > /mnt/shared/payload; sync; echo "A-SIZE=$(wc -c < /mnt/shared/payload)"; echo "A-MODE=$(ls -l /mnt/shared/payload | cut -c1-10)"; echo A-DONE'` and `MARKER` set in `environment`; poll to STOPPED and read the container's awslogs stream.
   Observed: the stream contains only `A-DONE`; no `A-SIZE=` and no `A-MODE=` line, container `exitCode` 0.
   Expected: `A-SIZE=<len(MARKER)+1>` and `A-MODE=-rw...`.
4. RunTask the same definition again with `sh -c 'echo "B-SAW=$(cat /mnt/shared/payload)"; echo B-APPEND >> /mnt/shared/payload; echo B-DONE'` after the first task is STOPPED.
   Observed: no `B-SAW=` line — the file written by the first task does not exist.
5. RunTask the readOnly definition with an append to `/mnt/shared/payload` whose stderr is captured.
   Observed: no refusal is reported at all; expected the kernel's `Read-only file system` (EROFS) on the write while the read still succeeds.
