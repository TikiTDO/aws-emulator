# Transcribe transcription-job projection diverges on timestamp shape, withheld determined members and the transcript location it announces

> _Note: this issue was identified against the code base at commit `4280f890470fc3016a7f7b2f270013172addcc68`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartTranscriptionJob

## Description
2 causes. Both are in the one place a stored transcription-job record is projected onto the modelled `TranscriptionJob` shape, which StartTranscriptionJob and GetTranscriptionJob both answer with, so they are filed together; each must be closed separately.

Cause 1 of 2: the timestamp members of `TranscriptionJob` are serialized in a form AWS never emits. Fixture transcribe-polly-speech-transcribed-to-s3-transcript, step task#4 (StartTranscriptionJob); the same members diverge again on task#5 (GetTranscriptionJob).
AWS: Smithy: StartTranscriptionJob/GetTranscriptionJob -> output TranscriptionJob; TranscriptionJob$StartTime, $CreationTime and $CompletionTime all target com.amazonaws.transcribe#DateTime (type timestamp). The service protocol is awsJson1_1 (smithy_query service_info: protocols [awsJson1_1], sdkId Transcribe), so a timestamp travels as an epoch-seconds number. The member docs state the rule for their resolution: "Timestamps are in the format YYYY-MM-DD'T'HH:MM:SS.SSSSSS-UTC", with the examples 2022-05-04T12:32:58.761000-07:00 (CreationTime), 2022-05-04T12:32:58.789000-07:00 (StartTime) and 2022-05-04T12:33:13.922000-07:00 (CompletionTime) — i.e. the fractional part AWS actually populates is milliseconds. The recording asserts the SHAPE of these members and not their value (the comparator's expected value is '<shaped-not-asserted>'), because the instant itself is a per-run value.
Emulator: emits the raw floating-point instant at full precision — $.TranscriptionJob.CreationTime and $.TranscriptionJob.StartTime both 1794485710.3821714 on task#4, and on task#5 the same two plus $.TranscriptionJob.CompletionTime 1794485710.8821714 — seven fractional digits, which fails the shape assertion the recording carries for a DateTime member. Hypothesis: since the comparator asserts only the shape of these members, the only property that can diverge is the number's form, i.e. the fractional-digit precision of the epoch-seconds encoding. A second, independent oddity in the same projection: CreationTime and StartTime are bit-identical and CompletionTime is exactly CreationTime + 0.5 s. Hypothesis: the lifecycle derives the later instants from the creation instant by a fixed offset; on AWS the three are distinct instants separated by real queueing and processing time, and CompletionTime in particular is minutes, not half a second, after creation.
Why: a client that formats or diffs these members, or that round-trips them through a timestamp type with millisecond resolution, gets a value AWS would never return; a client that derives a job's processing duration from CompletionTime - CreationTime always reads the same synthetic half-second regardless of the job.
Fix: the timestamp serialization of the transcription-job projection — the DateTime encoder the `TranscriptionJob` projection uses, and the lifecycle clock that stamps the record's creation/start/completion instants.
Traces: transcribe-polly-speech-transcribed-to-s3-transcript#task#4 (StartTranscriptionJob), transcribe-polly-speech-transcribed-to-s3-transcript#task#5 (GetTranscriptionJob).

Cause 2 of 2: a COMPLETED transcription job withholds the two members AWS determines for it and announces a transcript location that names no host the emulator serves. Fixture transcribe-polly-speech-transcribed-to-s3-transcript, step task#5 (GetTranscriptionJob).
AWS: Smithy: TranscriptionJob$MediaSampleRateHertz targets MediaSampleRateHertz (integer, @range min 8000 max 48000), documented as "The sample rate, in hertz, of the audio track in your input media file" — the sample rate of the MEDIA, which the service determines from the audio it read, so a finished job reports it even when the request stated none (the recording carries 22050 for the fixture's Polly-synthesized mp3; 22050 is this run's media, the requirement is that the member is present and is the rate of the media the job processed). TranscriptionJob$Settings targets Settings, documented as "Provides information on any additional settings that were included in your request"; a finished job echoes the effective settings, and the recording shows them present with the Settings booleans at their defaults (ChannelIdentification false, ShowAlternatives false) for a request that carried no Settings at all. Transcript$TranscriptFileUri targets Uri (@length 1..2000, @pattern ^(s3://|http(s*)://).+$) and is documented as "The Amazon S3 location of your transcript. You can use this URI to access or download your transcript" — for a job that named OutputBucketName the recording shows it as an HTTP(S) URL of the form https://s3.<region>.amazonaws.com/<bucket>/<key>, i.e. a URL that is fetchable with an HTTP GET against the S3 endpoint; the host and bucket in the recording are environment values.
Emulator: $.TranscriptionJob.MediaSampleRateHertz missing (got None) and $.TranscriptionJob.Settings missing (got None) on a job reported COMPLETED, and $.TranscriptionJob.Transcript.TranscriptFileUri is an `s3://<bucket>/transcripts/<job-name>.json` URI — the comparator's verdict is host_not_own: the location the emulator announces names no host it is reachable on, so the URI the client is told to "use to access or download your transcript" cannot be fetched where the client reached the API. Note that the sibling member DownloadUri has the opposite flavour of the same defect (announced on the real AWS S3 host), which is why that cluster is already owned by the open issue "Transcribe StartTranscriptionJob refuses media uploaded to S3, breaking the job lifecycle, and GetVocabularyFilter DownloadUri names a host the emulat..."; the related open issue "Transcribe publishes service-managed DownloadUri / TranscriptFileUri on the real AWS S3 host" covers the service-managed branch. Neither covers this step: this is the customer-bucket branch of TranscriptFileUri on its own replay key, and neither carries it.
Why: a client that reads MediaSampleRateHertz off a finished job (to pick a decoder, to validate the media it submitted, or simply to display it) finds the member absent and cannot distinguish "not determined" from "job never ran"; a client that reads back Settings to learn which options the job actually ran with gets nothing; and a client that follows TranscriptFileUri over HTTP — the documented way to download a transcript — has no host to connect to, so the last step of the canonical start/poll/fetch workflow fails even though the object exists in this emulator's object store.
Fix: the transcription-job projection and its output-location builder in the transcribe state (the `TranscriptionJob` projection of the stored record, and the `output_uri` branch that formats the customer-bucket location, in services/service-com-amazonaws-transcribe-transcribe/src/state.rs — see that module's header, which documents the determined-vs-withheld rule this case falls on the wrong side of). On completion the record must carry the determined sample rate of the media it processed and the effective Settings, and the announced transcript location must be an HTTP(S) URL on the S3 endpoint this emulator serves.
Traces: transcribe-polly-speech-transcribed-to-s3-transcript#task#5.
