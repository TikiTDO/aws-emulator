# qconnect message-template version refusals diverge: DeactivateMessageTemplate accepts a never-activated version, and the qualified-id refusal carries a message AWS does not send (2 causes)

> _Note: this issue was identified against the code base at commit `9b0642efcbb416a2d848390c0f01f1a772175058`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeactivateMessageTemplate

## Description
The emulator's QConnect (wisdom) message-template version surface gets two refusals wrong: it accepts a DeactivateMessageTemplate that AWS refuses, and it refuses a qualified messageTemplateId with bespoke prose instead of AWS's validation-constraint message. This bundle carries 2 causes.

Cause 1 of 2: DeactivateMessageTemplate on a version that was never activated returns 200 instead of ValidationException. Failing check: qconnect.deactivate-inactive-template-version-rejected.
AWS: Smithy (com.amazonaws.qconnect) DeactivateMessageTemplate, POST /knowledgeBases/{knowledgeBaseId}/messageTemplates/{messageTemplateId}/deactivate, models ValidationException (HTTP 400, "The input fails to satisfy the constraints specified by a service") among its errors; the operation is documented as deactivating "a specific version ... in active status", the counterpart of ActivateMessageTemplate. Recorded behavior: deactivating a published version that was never activated is refused with HTTP 400, error code ValidationException and message `Version <versionNumber> is not an active version` — the fixed text is "Version " ... " is not an active version" and the only variable part is the request's own `versionNumber` value (it is NOT a literal 1; 1 is just what this run published). The template's version is left with isActive=false, and after a later ActivateMessageTemplate the same DeactivateMessageTemplate succeeds and flips isActive back to false.
Emulator: the call SUCCEEDS with HTTP 200 and a normal DeactivateMessageTemplateResponse body (messageTemplateArn / messageTemplateId / versionNumber for the version). No ValidationException is produced at all: the handler only distinguishes "this version exists" from "it does not" (`store.deactivate_message_template_version(...)` returning false -> ResourceNotFoundException) and never checks whether the version is the ACTIVE one.
Why: a client relying on AWS's behavior uses the refusal as the authoritative answer to "is this version the active one?" — e.g. idempotent teardown code that treats a 200 from deactivate as proof the version HAD been active, or a controller that activates/deactivates versions in a loop and counts on ValidationException to detect a lost activation. Against the emulator every deactivate succeeds, so that control flow never fires, the error branch is never exercised, and a bug that AWS surfaces as a 400 passes silently.
Fix: the DeactivateMessageTemplate handler's state check — the active-version predicate must be consulted before the write, so a version that is not the template's active version is refused with the modeled ValidationException and nothing is written; the state helper that performs the deactivation currently reports only presence/absence, so the "is active" distinction has to be made available to the handler.
Traces: qconnect.deactivate-inactive-template-version-rejected.

Cause 2 of 2: a messageTemplateId carrying a version qualifier is refused with the emulator's own prose instead of AWS's validation-constraint message. Failing check: qconnect.update-activated-message-template-version-rejected.
AWS: Smithy UpdateMessageTemplate, POST /knowledgeBases/{knowledgeBaseId}/messageTemplates/{messageTemplateId}, documents messageTemplateId as "The identifier of the message template. Can be either the ID or the ARN. It cannot contain any qualifier." and models ValidationException (HTTP 400). Recorded behavior: passing `<uuid>:<versionNumber>` is refused with HTTP 400, code ValidationException and AWS's standard constraint-violation message: `1 validation error detected: Value at 'messageTemplateId' failed to satisfy constraint: Member must satisfy regular expression pattern: [a-f0-9]{8}-[a-f0-9]{4}-[a-f0-9]{4}-[a-f0-9]{4}-[a-f0-9]{12}$|^arn:[a-z-]*?:wisdom:[a-z0-9-]*?:[0-9]{12}:[a-z-]*?/[a-f0-9]{8}-[a-f0-9]{4}-[a-f0-9]{4}-[a-f0-9]{4}-[a-f0-9]{12}(?:/[a-f0-9]{8}-[a-f0-9]{4}-[a-f0-9]{4}-[a-f0-9]{4}-[a-f0-9]{12}){0,2}`. In that message the fixed text is "1 validation error detected: Value at '<member>' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern>"; the variable parts are the member name taken from the request (`messageTemplateId`) and the pattern the service enforces for it — a pattern that admits NO qualifier group, i.e. stricter than the model's UuidOrArnOrEitherWithQualifier. Note the model's own pattern for this member DOES admit `(:[A-Z0-9_$]+){0,1}`, so this rule is service-enforced and the recorded message is the requirement.
Emulator: HTTP 400 with code ValidationException (correct) but message `The messageTemplateId cannot contain a qualifier.` — prose AWS never sends, produced by `crate::state::message_qualifier_not_accepted(MEMBER_MESSAGE_TEMPLATE_ID)` and raised from the handler body after the id is resolved, rather than as the member's pattern-constraint violation raised during input validation. The same helper backs the identical refusal in DeactivateMessageTemplate, so the divergence is shared by every message-template operation that rejects a qualifier.
Why: clients and test suites match on AWS's validation-error text (and on the "N validation error(s) detected" prefix produced for every constrained member) to tell a malformed-input refusal apart from a state refusal, and to report which member and which constraint failed. Against the emulator that parse finds no member name and no constraint, so input-validation error handling and any assertion on the message break even though the status and code look right.
Fix: the messageTemplateId validation for UpdateMessageTemplate (and the shared refusal helper in the service's state module that DeactivateMessageTemplate reuses) — refuse a qualifier as a pattern-constraint violation on the member and render AWS's standard "1 validation error detected: Value at '<member>' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern>" message, with the no-qualifier pattern the service enforces.
Traces: qconnect.update-activated-message-template-version-rejected.
