# Discovery reads answer 404 Registry not found for a control-plane registry, hiding list results, filter validation and batch partial results

> _Note: this issue was identified against the code base at commit `65ec34a1ebf10c9d79f156d89c102210b3c63d83`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListDiscoverableRegistryRecords

## Description
Three net-new wire divergences on service `agent-registry` (AgentRegistry, sdkId 'Agent Registry', protocol restJson1, authSchemes [sigv4]) share one fault: the discovery (data-plane) operations now REACH a handler, but the handler resolves the registry out of a store that no AgentRegistryControl write ever reaches, so every read against a registry the fixture just created through the control plane is refused with HTTP 404 ResourceNotFoundException, message "Registry not found: <registryId as supplied>" (fixed text "Registry not found: " plus the identifier echoed from the request; the 12-character ids in the replay output are that run's values, not part of the contract). That single refusal both replaces the modeled 200 bodies and PRE-EMPTS input validation, so a malformed filter is reported as a missing registry. All three causes must be closed and re-replayed: sharing the state is necessary but not sufficient — Cause 2 additionally requires that input validation run before (not after) registry resolution, and Cause 3 requires BatchGet's partial-success assembly.

--- Cause 1 of 3: ListDiscoverableRegistryRecords must answer 200 with the required registryRecords list for an existing registry, not 404 ResourceNotFoundException.
AWS: Smithy ListDiscoverableRegistryRecords — POST /registries/{registryId}/discoverable-records-list, http code 200, @readonly, @paginated(items=registryRecords, inputToken/outputToken=nextToken, pageSize=maxResults); input registryId @httpLabel required RegistryIdentifier @length 1..2048 @pattern ^(arn:aws(-[^:]+)?:agent-registry:[a-z0-9-]+:[0-9]{12}:registry/)?[a-zA-Z0-9]{12,16}$, maxResults @range 1..100, filters RegistryRecordFilterList @length max 10; output registryRecords REQUIRED (DiscoverableRegistryRecordSummaryList) + nextToken. Modeled error ResourceNotFoundException httpError 404, documented "The requested resource was not found" — per the model its only ground here is a registryId that names no registry in the account/region. Once CreateRegistry has returned a registryArn and the registry reads READY, a list against that id returns HTTP 200 with registryRecords present: the APPROVED, discoverable records (RegistryRecordStatus doc: a record is "APPROVED once it is approved and discoverable"; REJECTED and DEPRECATED records are not discoverable), and an EMPTY list — present, not absent — when nothing is discoverable yet.
Emulator: HTTP 404 with no registryRecords member at all ($.registryRecords expected [], got None). The sibling cluster in Cause 2 shows the refusal body for this class: x-amzn-errortype ResourceNotFoundException with message "Registry not found: <registryId>".
Why: the required output member is absent, so a generated client fails deserialization rather than seeing an empty page; worse, 404 is a terminal client error an SDK does not retry, so a caller that just created the registry and is told it does not exist aborts the publish-then-discover workflow. Pagination loops and the APPROVED-only projection are unreachable.
Fix: the service's state/seeding seam — agent-registry's registry+record state must be the same store AgentRegistryControl mutates — and then the ListDiscoverableRegistryRecords handler/serializer so an existing registry yields 200 with registryRecords always present (empty list when nothing is discoverable).
Traces: agent-registry-discoverable-record-filter-validation#task#3 (representative), agent-registry-discovery-serves-approved-and-withdraws-deprecated#task#10, agent-registry-discovery-serves-approved-and-withdraws-deprecated#task#13.

--- Cause 2 of 3: a malformed filter on ListDiscoverableRegistryRecords must be refused 400 ValidationException with the filter's own message, not 404 ResourceNotFoundException "Registry not found".
AWS: Smithy RegistryRecordFilter members name (REQUIRED, enum RegistryRecordFilterName values [recordType, descriptorType]) and values (REQUIRED, DiscoverableFilterValues @length 1..10); modeled error ValidationException httpError 400 with members message (required), reason (required, enum, default FieldValidationFailed) and fieldList. Recorded behavior for this rejection class: HTTP 400 with message "Filter recordType must specify exactly one value." — fixed text is "Filter " ... " must specify exactly one value." and the variable part is the filter name taken from the request (here recordType); the other steps of this cluster assert the sibling filter refusals of the same class. AWS validates the request body before resolving the path's registry, so the filter defect is what is reported.
Emulator: HTTP 404 instead of 400; $headers.x-amzn-errortype "ResourceNotFoundException" instead of the ValidationException shape; $.message "Registry not found: 4a737edb5ed4" instead of the filter message — fixed text "Registry not found: " with the registryId echoed from the request as its variable part.
Why: the client is told the resource does not exist when the actual defect is its own input, so it retries against a different registry or aborts instead of fixing the filter; error classifiers that branch on ValidationException vs ResourceNotFoundException take the wrong branch, and no fieldList/reason is ever produced. The ordering defect survives the state fix: with a real registry present the handler would still have to validate the filter.
Fix: the ListDiscoverableRegistryRecords input-validation path — run filter/shape validation before registry resolution and emit the modeled ValidationException (400, x-amzn-errortype ValidationException, required message/reason) for a filter whose values count violates the rule.
Traces: agent-registry-discoverable-record-filter-validation#task#4 (representative), agent-registry-discoverable-record-filter-validation#task#5, agent-registry-discoverable-record-filter-validation#task#6.

--- Cause 3 of 3: BatchGetDiscoverableRegistryRecord must answer 200 with both required members — the found record in registryRecords and a per-entry error for the one that is not discoverable — not 404.
AWS: Smithy BatchGetDiscoverableRegistryRecord — POST /discoverable-records-batch, http code 200; input entries REQUIRED (RegistryRecordsEntryList @length 1..1); output registryRecords REQUIRED (RegistryRecordSummaryList) and errors REQUIRED (BatchGetDiscoverableRegistryRecordErrorList). BatchGetDiscoverableRegistryRecordError members: registryId REQUIRED ("echoed from the request"), recordId REQUIRED ("echoed from the request in the same format that you supplied"), errorCode REQUIRED (enum BatchGetDiscoverableRegistryRecordErrorCode values [RESOURCE_NOT_FOUND, ACCESS_DENIED, INTERNAL_ERROR]), message optional ("Do not parse this value programmatically"). So a record that exists and is APPROVED comes back in registryRecords (recordId/recordArn/registryArn/name/recordType/status APPROVED/descriptors/createdAt/updatedAt), while a record that is not retrievable/discoverable is reported per-entry as errorCode RESOURCE_NOT_FOUND with its registryId and recordId echoed — the whole call still being HTTP 200. A batch-get is never a top-level 404 for a per-entry miss.
Emulator: HTTP 404; neither required member is present ($.registryRecords and $.errors both None), and the asserted status poll on $.registryRecords[0].status never observes APPROVED (not in ['APPROVED'] after 30 attempts, got None) because no body is served at all.
Why: the partial-success contract that distinguishes "this one record is gone" from "the whole call failed" is destroyed: a client sees a terminal 404 for a batch in which some entries resolved, both required members are missing so deserialization fails, and read-back by recordId after approval is impossible.
Fix: after the shared-state fix, the BatchGetDiscoverableRegistryRecord handler/serializer — resolve each entry independently against the shared store and always emit HTTP 200 with both required members, putting resolvable APPROVED records in registryRecords and one BatchGetDiscoverableRegistryRecordError (errorCode RESOURCE_NOT_FOUND, registryId/recordId echoed from the entry) per unresolvable entry, with each list serialized even when empty.
Traces: agent-registry-discovery-serves-approved-and-withdraws-deprecated#task#9.
