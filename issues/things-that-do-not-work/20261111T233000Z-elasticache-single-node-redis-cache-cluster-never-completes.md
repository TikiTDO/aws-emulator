# ElastiCache single-node Redis cache cluster never completes a data-plane SET/GET: the check burns its whole budget with no assertion (1 cause, 1 check)

> _Note: this issue was identified against the code base at commit `7be3c4c4f98e3bb4fe12b293a9b02ae8c9c46178`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeCacheClusters

## Description
One net-new root cause, grounded in the single elasticache failing check that the replay report binds to no open issue and does not mark ALREADY FILED. Related open issue 20261111T005655Z-elasticache-data-plane-still-unreachable-and-multi-wait.md reports the same family (control-plane status settling + an unreachable cache endpoint) and even lists this check id in its trace list, but its replay key for it (`elasticache.elasticache-redis-set-get|_redis_set_get#20|Timeout|time.sleep(2)`) no longer matches the current failure, so the report leaves this check unowned; it is re-filed here so it is not closed unrun.

Cause 1 of 1: a provisioned single-node Redis cache cluster is never usable end to end — a client that creates the cluster, waits for it to settle, reads its node endpoint and opens a RESP session to it from inside the cluster's own VPC never gets through, and the whole flow consumes the per-check wall-clock budget without a single assertion firing.
AWS: Smithy (services/service-com-amazonaws-elasticache-amazonelasticachev9/smithy-model/com-amazonaws-elasticache-amazonelasticachev9.json): CreateCacheCluster returns CacheCluster$CacheClusterStatus 'creating'; CacheNode$CacheNodeStatus is documented 'available | creating | rebooting | deleting'; CacheNode$Endpoint is 'The hostname for connecting to this cache node', with Endpoint documented 'Represents the information required for client programs to connect to a cache node', Endpoint$Address 'The DNS hostname of the cache node' and Endpoint$Port 'The port number that the cache engine is listening on'. Recorded behavior: DescribeCacheClusters reports CacheClusterStatus 'available' within the poll window, DescribeCacheClusters(ShowCacheNodeInfo=true) then returns a non-empty CacheNodes with an Endpoint whose Address/Port accept a TCP connection from inside the cluster's VPC and speak RESP2 — `SET <key> <value>` answers `+OK` and `GET <key>` answers the bulk string `$<value>`. The Address and Port are per-run values; the requirement is that whatever Address/Port the control plane publishes is one the emulator listens on and serves RESP from, and that a status poll issued after the transition is due reads back the settled status.
Emulator: the check ends with exactly `Error: Check timed out after 60.0s` and no failing assertion, so no SET/GET reply, no `+OK`, and no endpoint refusal was ever observed. The flow it never finishes is: CreateCacheSubnetGroup over two run subnets, AuthorizeSecurityGroupIngress on tcp/6379, CreateCacheCluster(Engine='redis', CacheNodeType='cache.t3.micro', NumCacheNodes=1), a DescribeCacheClusters poll for CacheClusterStatus=='available' at a 15 s interval, DescribeCacheClusters(ShowCacheNodeInfo=True) for CacheNodes[0].Endpoint, then a connect-retry loop (2 s between attempts, 120 s budget) carrying `SET sim2real:dp hello-sim2real` / `GET sim2real:dp` from a VPC-attached Lambda probe. Hypothesis: the time is consumed by the two known mechanisms the related issue describes — a status transition that is only materialised by a later read, so the first poll always observes the transient status and the client pays a full poll interval, plus a published cache endpoint that accepts no TCP from inside its VPC, so the connect loop retries until the budget is gone. The replay cannot separate the two contributions here, because no assertion in this check fired.
Why: this is the plainest possible ElastiCache use — provision a cache, read its endpoint, store a value, read it back. A client doing exactly that cannot store or read one key, and because the emulator answers 200 at every control-plane step while never converging, the client cannot distinguish 'still provisioning' from 'this cache has no data plane'. SDK waiters and CI pipelines hang instead of failing with a diagnosable error.
Fix: two components, both in the elasticache crate: (a) the status-settling path of its state, so that a cluster whose transition is already due reads back settled to the FIRST Describe that observes it while the create response still reports 'creating'; and (b) the ElastiCache data plane, so the address/port published in CacheNodes[].Endpoint is served with RESP from inside the cluster's VPC (together with the Lambda in-VPC network vantage point the related issue describes).
Traces: elasticache.elasticache-redis-set-get.
