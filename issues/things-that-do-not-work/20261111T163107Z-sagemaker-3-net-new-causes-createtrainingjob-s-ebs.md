# sagemaker: 3 net-new causes — CreateTrainingJob's EBS-quota refusal message is reworded with the wrong limit, a pipeline execution with an unresolvable RoleArn never reaches a terminal status, and CreatePresignedNotebookInstanceUrl publishes an unreachable host so its session-duration range is never validated

## Operation
CreateTrainingJob

## Description
Three net-new behavioral root causes on the SageMaker surface. None of the three failing checks below is marked ALREADY FILED or OWNED by the replay, so no open issue carries their replay keys; where an open issue touches the same area it is named in the cause.

Cause 1 of 3: CreateTrainingJob's ResourceLimitExceeded refusal for an out-of-range VolumeSizeInGB carries an emulator-authored sentence and the wrong quota value.
AWS: Smithy (services/service-com-amazonaws-sagemaker-sagemaker/smithy-model/com-amazonaws-sagemaker-sagemaker.json): CreateTrainingJob input ResourceConfig.VolumeSizeInGB -> OptionalVolumeSizeInGB (@range min 0, no modelled maximum), modelled errors ResourceInUse, ResourceLimitExceeded, ResourceNotFound (all client, HTTP 400); ResourceLimitExceeded.Message -> FailureReason (@length 0..1024). A VolumeSizeInGB above the account's EBS-volume-per-training-job quota is a quota violation, refused with ResourceLimitExceeded (NOT ValidationException) whose Message is the sentence: "The account-level service limit 'Size of EBS volume for a training job instance' is <limit> GBs, with total requested utilization of <requested> GBs. Please use AWS Service Quotas to request an increase for this quota. If AWS Service Quotas is not available, contact AWS support to request an increase for this quota." Fixed text: "The account-level service limit '", the quota name "Size of EBS volume for a training job instance", "' is ", " GBs, with total requested utilization of ", " GBs. Please use AWS Service Quotas to request an increase for this quota. If AWS Service Quotas is not available, contact AWS support to request an increase for this quota." Variable parts: <limit>, the account's quota for that named limit (the default is 1024), and <requested>, the VolumeSizeInGB the request asked for. Note the unit is spelled "GBs" in both slots, and the second slot is the TOTAL REQUESTED utilization — there is no "current utilization"/"request delta" pair in this message class.
Emulator: refuses with the right code (ResourceLimitExceeded) but a different sentence and a different limit: "The account-level service limit 'Size of EBS volume for a training job instance' is 16384 GB, with current utilization of 0 GB and a request delta of 999999999 GB. Please use AWS Service Quotas to request an increase for this quota. If AWS Service Quotas is not available, contact AWS support to request an increase for this quota." Three divergences: the quota value reported for that named limit, the unit spelling ("GB" instead of "GBs"), and the middle clause ("with current utilization of <used> GB and a request delta of <delta> GB" instead of "with total requested utilization of <requested> GBs").
Why: a client or operator that parses this refusal to learn which quota to raise and by how much reads a limit the account does not have and a clause shape that does not match, so automated quota-increase requests and log matchers keyed on this message class (shared by every SageMaker account-level limit refusal) break; the limit value also tells the client a 16384 GB volume would be accepted when AWS refuses anything over the real quota.
Fix: the CreateTrainingJob handler's ResourceConfig quota guard — the account-level-limit message template and the EBS-volume quota value it reads.
Traces: sagemaker.create-training-job-out-of-range-volume-size-rejected.

Cause 2 of 3: a pipeline execution whose RoleArn names no existing role never reaches a terminal status, so the step never fails naming the role.
AWS: Smithy: CreatePipeline and StartPipelineExecution both accept a syntactically valid RoleArn without resolving it (StartPipelineExecution's modelled errors are ConflictException, ResourceLimitExceeded, ResourceNotFound); the role is resolved when the step runs. DescribePipelineExecution then settles PipelineExecutionStatus at a terminal value (Failed), and ListPipelineExecutionSteps reports the sole step with StepStatus Failed and PipelineExecutionStep.FailureReason (@length 0..1024) naming the unresolvable role ARN as not existing — recorded behavior for the exact sentence; what is a requirement is that the execution and its step both settle Failed promptly and that FailureReason contains the requested RoleArn and states that it does not exist. The declared side effect (the step's SQS callback message) must not be produced.
Emulator: StartPipelineExecution is accepted and the execution then never settles: the check polls DescribePipelineExecution for a terminal PipelineExecutionStatus and exhausts the suite's 60 s budget ("Check timed out after 60.0s") without ever seeing one, so no StepStatus Failed and no FailureReason naming the role are ever produced.
Why: a client that starts a pipeline and waits for it to finish — the normal use of the API — hangs forever instead of being told, within seconds, that the execution failed because its RoleArn does not exist; waiters never return, CI jobs time out, and the role-misconfiguration diagnosis is never surfaced. The open issue 20261024T160943Z-sagemaker-runs-no-job-work-processing-pipeline-step.md covers pipeline steps performing no work for executions that DO settle; the replay reports this check as unowned, and the defect here is that the execution never reaches a terminal status at all on an unresolvable role.
Fix: the pipeline-execution state machine behind StartPipelineExecution/DescribePipelineExecution/ListPipelineExecutionSteps — it must resolve the pipeline's RoleArn when the step is dispatched, drive the execution and the step to Failed, and populate the step's FailureReason with the missing role ARN, rather than leaving the execution non-terminal.
Traces: sagemaker.create-pipeline-missing-role-not-found.

Cause 3 of 3: CreatePresignedNotebookInstanceUrl publishes an AuthorizedUrl on a host the emulator does not serve, and its SessionExpirationDurationInSeconds range refusal is therefore never exercised.
AWS: Smithy: CreatePresignedNotebookInstanceUrl input NotebookInstanceName (required) and SessionExpirationDurationInSeconds (@range 1800..43200); output AuthorizedUrl -> NotebookInstanceUrl; no modelled errors. The returned AuthorizedUrl is fetched by the caller and must yield an authenticated notebook session on a host that actually serves it. A SessionExpirationDurationInSeconds outside 1800..43200 (sent with client-side validation disabled) is refused with ValidationException and no URL, message "1 validation error detected: Value '<value>' at 'sessionExpirationDurationInSeconds' failed to satisfy constraint: Member must have value greater than or equal to 1800" (and "...less than or equal to 43200" for the upper bound) — fixed text apart from <value>, taken from the request.
Emulator: returns an AuthorizedUrl whose host is a real-AWS name it does not serve, of the form "https://<notebook-name>.notebook.<region>.sagemaker.aws/auth?authToken=<token>". The harness refuses to fetch it: "endpoint_url was given https://<nb>.notebook.<region>.sagemaker.aws/auth?authToken=<token> (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener". The emulator announced an address other than the one it is reached on, so the check aborts before reaching the out-of-range refusals and the range validation is unverified.
Why: a client that does what this operation exists for — fetch AuthorizedUrl to open a notebook session — is sent off the emulator entirely and gets a DNS/connection failure instead of an authenticated session; and because the call never gets past the URL, the documented 1800..43200 bound on SessionExpirationDurationInSeconds is not shown to be enforced server-side. The open issue 20261109T134927Z-sagemaker-5-net-new-causes-presigned-notebook-urls.md Cause 1 describes the same unreachable-host construction, but its replay keys are the two presigned-URL TTL checks; the replay reports THIS check as unowned, and it additionally requires the ValidationException range refusal.
Fix: the CreatePresignedNotebookInstanceUrl handler's URL construction must publish the emulator's own reachable host and port (the endpoint the request arrived on, or a per-resource listener it owns) with the notebook auth path and token, and the emulator must serve that path; the handler's input validation must refuse SessionExpirationDurationInSeconds outside 1800..43200 with ValidationException and the standard constraint sentence, returning no URL.
Traces: sagemaker.presigned-notebook-instance-url-session-duration-range-enforced.
