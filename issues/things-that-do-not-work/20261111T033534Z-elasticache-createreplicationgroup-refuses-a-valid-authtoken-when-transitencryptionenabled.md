# ElastiCache CreateReplicationGroup refuses a valid AuthToken when TransitEncryptionEnabled=true, and two cache flows still exhaust the per-check budget without reaching an assertion (2 causes, 3 checks)

> _Note: this issue was identified against the code base at commit `f6476a64244d41dc0fd9adea93cb75255e1386be`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateReplicationGroup

## Description
Two net-new root causes, grounded in the 3 failing elasticache checks the replay report binds to no open issue and does not mark ALREADY FILED. Cause 2's two check ids ARE named in the Issue-Trace-Ids of the open issue 20261111T005655Z-elasticache-data-plane-still-unreachable-and-multi-wait.md, but that issue's replay keys for them are pinned to frames that no longer match (`_tls_session#12|Timeout|time.sleep(2)` and `_redis_set_get#20|Timeout|time.sleep(2)`), so the report attributes neither to it; both now die at the bare per-check budget with no frame at all. Cause 1 is not reported by any open issue: the related elasticache auth-token issues (20261111T005655Z..., and the AUTH-enforcement entries of 20261108T152921Z-elasticache-accepts-input-aws-refuses-and-misreports-resource.md) are about the data plane AFTER a group exists, while here the CREATE itself is refused.

Cause 1 of 2: CreateReplicationGroup refuses an AuthToken that AWS accepts, so an encryption-in-transit replication group cannot be created at all.
AWS: Smithy (services/service-com-amazonaws-elasticache-amazonelasticachev9/smithy-model/com-amazonaws-elasticache-amazonelasticachev9.json) CreateReplicationGroupMessage$AuthToken: "The password used to access a password protected server. AuthToken can be specified only on replication groups where TransitEncryptionEnabled is true", with password constraints "Must be only printable ASCII characters", "Must be at least 16 characters and no more than 128 characters in length", "The only permitted printable special characters are !, &, #, $, ^, <, >, and -". Recorded behavior: the request that carries an AuthToken WITHOUT TransitEncryptionEnabled is refused 400 InvalidParameterValue with the message "The AUTH token is only supported when encryption-in-transit is enabled" (fixed text, no variable part) and creates nothing, and the IDENTICAL request with TransitEncryptionEnabled=true SUCCEEDS: the group then reports Status 'available', AuthTokenEnabled=true and TransitEncryptionEnabled=true. The token in the recording is a 32-character URL-safe base64 string over the alphabet [A-Za-z0-9-_] (secrets.token_urlsafe(24)) — printable ASCII, inside 16..128 — and AWS accepted it.
Emulator: the negative half is correct (InvalidParameterValue with exactly the AWS message), but the positive control is refused: `An error occurred (InvalidParameterValue) when calling the CreateReplicationGroup operation: Invalid AuthToken provided.` "Invalid AuthToken provided." is the emulator's own fixed text — it is not the wording AWS uses for a token-constraint refusal, it names neither the constraint that failed nor the member, and it is returned for a token AWS accepts. Hypothesis: the token-shape check behind it (the `crate::state::auth_token_refusal(token)` branch of CreateReplicationGroup::handle, services/service-com-amazonaws-elasticache-amazonelasticachev9/src/ops/create_replication_group.rs around line 500) enforces the documented special-character allow-list literally and so rejects the '_' that the URL-safe base64 alphabet contains; the replay cannot distinguish that from a stricter length/charset rule, because the refusal message states no reason.
Why: a client that generates its AUTH token the normal way (a random URL-safe/base64 secret) can never create a replication group with encryption in transit against this emulator, even though the same call works on AWS. Because the refusal is a flat 400 with no reason, the client cannot tell 'your token is malformed' from 'this parameter combination is unsupported', and every downstream behaviour that needs an auth-token-protected group (AUTH enforcement, token rotation) is unreachable.
Fix: the AuthToken validation in CreateReplicationGroup's handler — accept every token AWS accepts (printable ASCII, 16-128 characters, including the URL-safe base64 alphabet) and, when a token really is out of constraint, word the refusal as AWS words that error class instead of the emulator's own "Invalid AuthToken provided." sentence.
Traces: elasticache.create-replication-group-authtoken-without-transit-encryption-rejected (the first assertion pair passes; the failure is the positive control at check line 78).

Cause 2 of 2: a serverless snapshot/restore flow and a plain cluster SET/GET flow still spend the entire per-check budget inside status/connect polling and never reach an assertion.
AWS: recorded behavior only for the timings; Smithy: ServerlessCache$Status "The allowed values are CREATING, AVAILABLE, DELETING, CREATE-FAILED and MODIFYING", ServerlessCacheSnapshot$Status, CacheCluster$CacheClusterStatus, and Endpoint{Address "The DNS hostname of the cache node", Port "The port number that the cache engine is listening on"} documented as "the information required for client programs to connect to a cache node". Recorded: CreateServerlessCache -> DescribeServerlessCaches settles at 'available'; CreateServerlessCacheSnapshot settles 'available'; CreateServerlessCache(SnapshotArnsToRestore=[arn]) settles 'available' with the snapshot's data loaded; a TCP/TLS session to the published Endpoint Address:Port from inside the cache's VPC answers RESP (SET -> +OK, GET -> the stored bulk string), so the restored cache returns the pre-snapshot value.
Emulator: both checks end with exactly `Error: Check timed out after 60.0s` and no assertion ever fires, so neither the restore's data-persistence assertion nor the SET/GET assertion is ever evaluated. The flows poll DescribeServerlessCaches / DescribeCacheClusters every 2-15 s for 'available' and open a session to the advertised endpoint between the waits; with several such waits chained plus connect attempts to an endpoint that answers no TCP, the budget is gone before the first assertion. Mechanism in this checkout: services/service-com-amazonaws-elasticache-amazonelasticachev9/src/state.rs documents the status transition as "deliberately NOT zero ... materialised by whichever later call reads it", so a client's first poll after a create always observes the transient status and then sleeps its whole interval.
Why: a client cannot confirm that a serverless cache became available, that a snapshot completed, that a restore loaded its data, or that a key written to a cache can be read back; a flow that chains these waits is indistinguishable from resources that never settle, so SDK waiters and CI pipelines simply time out.
Fix: the status-settling path of the elasticache crate's state (a transition already due must read back settled to the FIRST call that observes it, while the create/modify/delete RESPONSE keeps reporting the transient status), together with the data plane actually listening on the Address:Port the ServerlessCache/CacheCluster projection publishes.
Traces: elasticache.e2e-serverless-snapshot-restore-flow, elasticache.elasticache-redis-set-get.
