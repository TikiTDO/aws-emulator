=== Cause 1 of 1: a TargetTrackingScaling policy with DisableScaleIn=true on a `custom-resource` target never drives the endpoint, and the scale-out never arrives inside the documented breach window ===
AWS: Smithy (com.amazonaws.applicationautoscaling#AnyScaleFrontendService) — PutScalingPolicy takes TargetTrackingScalingPolicyConfiguration {TargetValue (required, MetricScale), CustomizedMetricSpecification, ScaleOutCooldown, ScaleInCooldown, DisableScaleIn: "Indicates whether scale in by the target tracking scaling policy is disabled. If the value is true, scale in is disabled and the target tracking scaling policy won't remove capacity from the scalable target"} and returns Alarms (list of Alarm {AlarmName required, AlarmARN required}); errors ValidationException/ObjectNotFoundException/FailedResourceAccessException/LimitExceededException (client, httpError 400) and ConcurrentUpdateException/InternalServiceException (server, 500). DescribeScalingActivities returns ScalingActivity {Description required, Cause required, StartTime required, StatusCode required (ScalingActivityStatusCode = Pending|InProgress|Successful|Overridden|Unfulfilled|Failed), StatusMessage}. The custom-resource endpoint contract and the message wording are recorded behavior only: in the `custom-resource` namespace (ServiceNamespace value `custom-resource`, ScalableDimension `custom-resource:ResourceType:Property`) Application Auto Scaling reads and writes the caller's own endpoint, GET and PATCH on `/scalableTargetDimensions/{id}`. With DisableScaleIn=true the policy mints exactly ONE alarm, named `TargetTracking-<resource-id>-AlarmHigh-<uuid>` (the AlarmHigh kind only — no AlarmLow). While a customized metric is published far above TargetValue, that high alarm goes to ALARM and the service PATCHes the endpoint with a body of exactly `{"desiredCapacity": <N>}`, where <N> is the computed capacity clamped to the target's registered MaxCapacity, and records ONE activity that settles StatusCode `Successful` with Cause of fixed text `monitor alarm ` + the AlarmHigh name + ` in state ALARM triggered policy ` + the PolicyName, and Description `Setting desired capacity to <N>.` (fixed text `Setting desired capacity to `, the capacity, a period). The alarm name, the policy name and the capacity are the only variable parts; the enforcement completes well inside the documented target-tracking evaluation window (metric period 180 s).
Emulator: nothing ever reaches the endpoint. Registration, PutScalingPolicy and the AlarmHigh minting succeed (the alarm-kind leg of the check passes), but while the customized metric is published at ten times TargetValue the backing item stays at its pre-decision state — desiredCapacity 1.0, PATCH count 0, no recorded PATCH body (the previous run of this check reported `last saw (1.0, 0, None)` from the same probe) — and DescribeScalingActivities for the custom-resource target stays EMPTY, so no `monitor alarm ... in state ALARM triggered policy ...` activity with Description `Setting desired capacity to <N>.` is ever produced. In this run the breach never arrives for the entire 600 s window and the check is terminated by the harness: `Error: Check timed out after 600.0s`. Hypothesis: the custom-resource branch of the capacity-enforcement path is only wired into registration, so no policy execution emits the endpoint PATCH; the alarm may also never be evaluated against the published customized metric.
Why: a client that scales anything AWS does not model natively does so through the custom-resource contract. It configures target tracking, sees the policy and its AlarmHigh created, and then its resource is never moved and no activity records a decision — a scale-out that AWS delivers inside one metric period never happens, and scale-in-disabled semantics (only AlarmHigh exists, yet scale-out must still occur) cannot be observed at all. Because the enforcement never lands, the ceiling clamp (capacity capped at MaxCapacity) and the one-alarm-left invariant are also unverifiable.
Fix: the target-tracking policy-execution path of this service and its `custom-resource` namespace enforcement branch — evaluate the minted AlarmHigh against the published metric, issue the endpoint PATCH with a `{"desiredCapacity": <N>}` body clamped to the registered MaxCapacity, and record the Successful activity with AWS's Cause/Description templates through the activity recorder.
