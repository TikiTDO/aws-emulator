# ElastiCache RBAC user-group AUTH enforcement never observable: the attach/detach/reattach flow burns the whole per-check budget in replication-group status waits and RESP sessions to an endpoint that accepts no TCP

> _Note: this issue was identified against the code base at commit `0e97705e9904239bd55bed92c4be71546a783c93`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
One net-new root cause, grounded in the single failing elasticache check this replay binds to no open issue and does not mark ALREADY FILED.

Related open issues report the same family but do not cover this check. 20261111T005655Z-elasticache-data-plane-still-unreachable-and-multi-wait.md DOES name elasticache.e2e-user-group-auth-enforcement-flow in its Issue-Trace-Ids, but it keys that id to the frame `_resp#23|Timeout|assert session["error"] is None, (` — this replay produces no such frame at all (the check dies at the bare per-check budget with no frame), so the report attributes the check to no issue. 20261110T144301Z-elasticache-multi-step-lifecycle-flows-never-converge-every.md reports the same convergence mechanism for four other check ids and does not carry this one. 20261111T033534Z-elasticache-createreplicationgroup-refuses-a-valid-authtoken-when-transitencryptionenabled.md re-filed two sibling ids (e2e-serverless-snapshot-restore-flow, elasticache-redis-set-get) for exactly this reason and likewise does not carry this one. Filing it so the RBAC-enforcement path is not closed unrun.

Cause 1 of 1: a replication group with an RBAC user group attached never lets a client observe AUTH enforcement — the attach/detach/reattach flow spends its entire wall-clock budget inside DescribeReplicationGroups status polling and inside RESP sessions to the endpoint the control plane advertises, and not one assertion in the check ever fires.

AWS: Smithy (services/service-com-amazonaws-elasticache-amazonelasticachev9/smithy-model/com-amazonaws-elasticache-amazonelasticachev9.json) ReplicationGroup$Status is documented "The current state of this replication group - creating, available, modifying, deleting, create-failed, snapshotting"; ModifyReplicationGroup takes UserGroupIdsToAdd / UserGroupIdsToRemove (UserGroupIdList) with ApplyImmediately, and models InvalidReplicationGroupStateFault (400 InvalidReplicationGroupState), InvalidUserGroupStateFault (400 InvalidUserGroupState) and UserGroupNotFoundFault (404 UserGroupNotFound); Endpoint is documented "Represents the information required for client programs to connect to a cache node", with Endpoint$Address "The DNS hostname of the cache node" and Endpoint$Port "The port number that the cache engine is listening on". Recorded behavior for the rest: CreateReplicationGroup(TransitEncryptionEnabled=true) settles Status 'available'; ModifyReplicationGroup(UserGroupIdsToAdd=[g], ApplyImmediately=true) returns 200 and the group settles back to 'available'; a TLS RESP session to NodeGroups[0].PrimaryEndpoint.{Address,Port} from inside the group's VPC then refuses the RBAC user's wrong password with a reply whose fixed wire prefix is `-WRONGPASS` (or `-NOAUTH` when no AUTH has succeeded) and accepts the right one, after which `SET k v` answers `+OK` and `GET k` answers the stored bulk string; ModifyReplicationGroup(UserGroupIdsToRemove=[g], ApplyImmediately=true) restores unauthenticated default-user access (a bare SET answers `+OK`) and makes the same AUTH refuse with `-WRONGPASS`/`-NOAUTH`; reattaching the identical group makes the identical AUTH succeed again. The error-reply prefixes are the fixed text; the user name, password, key names and the endpoint host/port are per-run values from the request and the emulator's state.

Emulator: the check ends with exactly `Error: Check timed out after 60.0s` and NO assertion failure, so none of the five observations above is ever evaluated — not the wrong-password refusal, not the authenticated SET/GET round trip, not the post-detach default-user access, not the post-detach refusal, not the post-reattach restore. The flow issues four _wait_rg_available loops (DescribeReplicationGroups polled every 2 s: after create, after the attach, after the detach, after the reattach) and three _resp sessions, each of which retries a failed connect for up to 60 s with 5 s sleeps. Mechanism in this checkout: services/service-com-amazonaws-elasticache-amazonelasticachev9/src/state.rs line 404 `pub const CLUSTER_TRANSITION: Duration = Duration::from_millis(500);`, documented at lines 394-403 as "deliberately NOT zero ... The due instant is stored on the record and materialised by whichever later call reads it — nothing sleeps", so a client's first poll after each create/modify always observes the transient status and then sleeps its whole interval; chained four times that alone consumes the budget. Hypothesis: the RESP sessions add the rest, because the advertised PrimaryEndpoint accepts no TCP from inside the VPC (the sibling data-plane checks in this same replay report the emulator's own `OSError: a Lambda function in this emulator has no host network to reach` on that connect) and _resp therefore burns its full 60 s connect-retry window; the replay cannot separate the two contributions, because no assertion in this check fired.

Why: RBAC is the only way an ElastiCache client scopes access to a replication group, and a client cannot confirm any part of it against this emulator. It cannot tell that attaching a user group began enforcing the user's password, that a wrong password is refused rather than silently accepted, that detaching the group really revoked that user, or that reattaching restored it — a run that times out is indistinguishable from a group that never settled and from an engine that authenticates everyone. A client that polls ReplicationGroup$Status on an AWS-sized interval pays that whole interval per wait even though the emulator settled in 500 ms, so SDK waiters and CI pipelines time out; and because the published PrimaryEndpoint answers no TCP, the enforcement itself can never be exercised even if the waits were free.

Fix: two components, both already named by the related issues above and both required before this check can reach an assertion — (a) the status-settling path of the elasticache crate's state, so a transition whose due instant has passed reads back settled to the FIRST call that observes it while the create/modify RESPONSE keeps reporting the transient status other checks assert; and (b) the ElastiCache data plane for replication groups, so the emulator serves RESP on the Address:Port its NodeGroups[].PrimaryEndpoint projection publishes and enforces the attached user group's RBAC credentials there (wrong password -> `-WRONGPASS`, no successful AUTH -> `-NOAUTH`, detached user -> refused, default user unauthenticated when no group is attached).
