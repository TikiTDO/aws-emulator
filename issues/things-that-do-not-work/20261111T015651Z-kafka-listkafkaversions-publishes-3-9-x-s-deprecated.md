## Description

Cause 1 of 3: ListKafkaVersions reports 3.9.x as DEPRECATED when the catalog is folded by version, so no client can select the version MSK offers for standard provisioned brokers. AWS: Smithy: ListKafkaVersions, GET /v1/kafka-versions, HTTP 200 -> ListKafkaVersionsResponse.KafkaVersions (jsonName kafkaVersions) of KafkaVersion{Version (jsonName version), Status (jsonName status, enum KafkaVersionStatus = ACTIVE|DEPRECATED)}; the model enumerates no versions, so WHICH version carries WHICH status is recorded behavior only. The recorded behavior these checks encode is that 3.9.x is a version MSK currently offers for standard (non-Express) provisioned brokers: a client folds the catalog to a version->status map (the ordinary read: for each row, map version to status, so a version published more than once is read from its LAST row) and requires ACTIVE for 3.9.x before calling CreateCluster/CreateClusterV2 with KafkaVersion=3.9.x, which AWS accepts. The requirement is the rule, not the literal string: the status a client reads back for a version must be the status the service actually honours for that version.
Emulator: GET /v1/kafka-versions answers 200 with 37 rows and publishes 3.9.x TWICE — an ACTIVE row and, later in the same page, a DEPRECATED row (services/service-com-amazonaws-kafka-kafka/src/state.rs, KAFKA_VERSION_CATALOG: the ACTIVE 3.9.x row precedes 3.9.x.kraft, the DEPRECATED 3.9.x row follows it). Folded by version, 3.9.x therefore reads DEPRECATED. The emulator's own gates disagree with the catalog it serves: its offered-version predicate accepts a version that has ANY ACTIVE row, and CreateClusterV2 with Provisioned.KafkaVersion="3.9.x" is accepted and mints a CREATING cluster (observed in kafka.update-cluster-configuration-triggers-operation, which creates its cluster on 3.9.x without consulting the catalog). So the published catalog contradicts the behaviour the same service implements.
Why: a client that enumerates ListKafkaVersions to pick a version — which is what AWS documents the operation for, and what CDK/CloudFormation tooling and every version picker does — concludes that the only Apache Kafka version MSK still offers for standard brokers is deprecated, and either refuses to create a cluster or steers onto a version MSK would refuse. In this suite that single value is fatal: 29 checks across SCRAM, topics, configurations, cluster policy, replicators, VPC connections, tagging and the native data plane abort at setup and measure nothing about MSK at all.
Fix: the shared published version catalog in the service's state module (services/service-com-amazonaws-kafka-kafka/src/state.rs, KAFKA_VERSION_CATALOG) and the projection in the ListKafkaVersions handler (src/ops/list_kafka_versions.rs): a version the service still offers must not have DEPRECATED as the last status a reader of the page sees for it, and the catalog's rows must agree with the create/update gates about whether 3.9.x is offered. The now-fixed wire issue 20261030T072234Z-kafka-msk-version-catalog-is-stale-listkafkaversions-and-getcompatiblekafkaversions.md introduced the duplicate 3.9.x rows; that fixture (kafka-catalog-list-kafka-versions) must keep passing alongside this correction. Related open issues concern the refusal messages' valid-value lists, not the catalog's statuses, and do not cover this: 20261102T083811Z-kafka-createconfiguration-s-unsupported-kafkaversions-refusal-message-is-the.md, 20261103T090515Z-kafka-createconfiguration-s-unsupported-kafkaversion-refusal-renders-the-wrong.md, 20261107T230554Z-kafka-createclusterv2-s-unsupported-kafkaversion-refusal-offers-versions-msk.md.
Traces: the 29 checks listed above; each aborts in its `_pick_kafka_version` helper with `AssertionError: Kafka 3.9.x is not ACTIVE in ListKafkaVersions: [...]`.

Cause 2 of 3: UpdateClusterConfiguration refuses a cluster that is not ACTIVE with the emulator's own prose instead of MSK's fixed state-refusal text. Failing check: kafka.update-cluster-configuration-triggers-operation.
AWS: Smithy: UpdateClusterConfiguration, PUT /v1/clusters/{ClusterArn}/configuration, errors BadRequestException (400, members invalidParameter/message), NotFoundException (404), ForbiddenException (403). Recorded behavior for the wording: a cluster that is still CREATING is refused with HTTP 400 BadRequestException and the message `This operation is only valid for resources that are in one of the following states :[ACTIVE]`. The fixed text is `This operation is only valid for resources that are in one of the following states :[` + `]` (including AWS's space before the colon); the variable part is the comma-separated list of states the operation accepts, here ACTIVE. The refusal is on the cluster's STATE, not on the configuration reference the body carries, even when that reference does not resolve.
Emulator: answers 400 BadRequestException with the emulator-authored message `The cluster is in the CREATING state; it must be ACTIVE to be updated.` (invalidParameter `ClusterArn`) — same status and code, different wording, built from the cluster's current state rather than from the accepted-state list. The emulator already owns the correct template for the configuration family (state.rs `configuration_not_in_accepted_state`), so this handler re-words a message the service states correctly elsewhere.
Why: a client that matches on MSK's message (or a human reading it) sees text AWS never emits; tooling that keys retry/backoff on "only valid for resources that are in one of the following states" does not recognise the refusal and treats a transient provisioning state as a permanent input error.
Fix: the cluster-state gate in the operation's handler, services/service-com-amazonaws-kafka-kafka/src/ops/update_cluster_configuration.rs (the `cluster_state != CLUSTER_STATE_ACTIVE` branch), which must emit the shared accepted-state refusal from crate::state rather than its own sentence. The open issue 20261105T161551Z-kafka-msk-cluster-state-guard-on-updatebrokerstorage-updatemonitoring-updatesecurity.md reports the same prose for UpdateBrokerStorage/UpdateMonitoring/UpdateSecurity and does NOT cover UpdateClusterConfiguration.
Traces: kafka.update-cluster-configuration-triggers-operation (assertion at check line 155).

Cause 3 of 3: the emulator's Lambda python runtime exposes no `select` module, so a function package that vendors kafka-python cannot import it and no MSK native data-plane measurement is possible. Failing check: kafka.msk-transactional-abort-invisible-to-read-committed-visible-to-read-uncommitted.
AWS: recorded behavior only — the Smithy model for Invoke says nothing about a runtime's standard library. A managed python3.x runtime ships a complete CPython standard library, so `import select` (a built-in extension module, and a dependency of `socket`/`selectors` and therefore of kafka-python) succeeds; the executor's selftest invocation returns HTTP 200 with the handler's JSON payload reporting the vendored kafka-python version, and no FunctionError.
Emulator: the handler module itself now imports and runs (it answers the nonce-bound proof and the VPC DNS probe), but `import kafka` inside it fails and the payload reports `IMPORT FAILED: ModuleNotFoundError: No module named 'select'`. The stdlib shim backing the python runtimes is still partial — the gap has moved from `os.register_at_fork` to the `select` module.
Why: any function whose code or vendored dependency touches `select`, `socket` or `selectors` cannot run, and the developer is pointed at their own deployment package for a defect that lives entirely in the emulator's runtime. For this suite it means the MSK transactional read-committed/read-uncommitted behaviour is never exercised: the instrument the check carries into the VPC is unusable, so the run measures nothing.
Fix: the emulator's in-process Python Lambda runtime — the sandbox/stdlib shim that backs Invoke for the python runtimes. It must expose the real CPython standard library (including the `select` extension module) so a package vendoring kafka-python imports cleanly. The open issue 20261105T101629Z-kafka-every-native-msk-data-plane-check-is.md reports the earlier `os.register_at_fork` gap of the same shim for this check and does not carry this failure's key; this is the next missing piece of the same runtime.
Traces: kafka.msk-transactional-abort-invisible-to-read-committed-visible-to-read-uncommitted (`_prove_executor_in_vpc`, check line 1176).
