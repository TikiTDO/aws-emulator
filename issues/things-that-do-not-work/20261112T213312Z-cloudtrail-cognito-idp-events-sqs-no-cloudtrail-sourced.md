# cloudtrail__cognito-idp__events__sqs: no CloudTrail-sourced "AWS API Call via CloudTrail" event ever reaches an EventBridge rule, so cognito-idp AdminCreateUser/AdminDeleteUser (and the sqs TagQueue control write) are never delivered and the check blocks until the harness ceiling

> _Note: this issue was identified against the code base at commit `d6ad4ce57ed9bb499e6aab14c4da909be2b9b510`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AdminCreateUser

## Description
Cause 1 of 1: a trail that is logging management events feeds no events onto the default EventBridge bus, so an EventBridge rule matching detail-type "AWS API Call via CloudTrail" never fires for any eventSource. The check wires three rules (source aws.sqs / eventName TagQueue as a liveness control, source aws.cognito-idp / eventName AdminCreateUser as the subject, source aws.cognito-idp / eventName AdminDeleteUser as a near miss), each targeting its own SQS queue, then blocks polling those queues. Nothing arrives and the check is killed at the harness ceiling ("Check timed out after 60.0s") before any delivery assertion can run.

AWS: CloudTrail management events for a logging trail are published to EventBridge as events whose envelope carries detail-type "AWS API Call via CloudTrail", source "aws.<service>" (here "aws.sqs" for the control write and "aws.cognito-idp" for the pool calls), account = the caller's account and region = the call's region, with the CloudTrail record itself under `detail` (eventSource "cognito-idp.amazonaws.com", eventName "AdminCreateUser"/"AdminDeleteUser", readOnly false, eventCategory "Management", recipientAccountId = account, awsRegion = region) — https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudwatch-event-reference.html. Cognito's secret request members are redacted in that record rather than dropped: Smithy marks AdminCreateUser.Username and AdminCreateUser.TemporaryPassword @sensitive (pattern ^[\S]+$, length 0-256 for TemporaryPassword), and the delivered record keeps the members with the exact literal value HIDDEN_DUE_TO_SECURITY_REASONS — for detail.requestParameters.username, detail.requestParameters.temporaryPassword and detail.responseElements.user.username — while non-secret siblings of the same request are kept verbatim (detail.requestParameters.messageAction "SUPPRESS", detail.requestParameters.userPoolId = the pool id), and the user is named by detail.additionalEventData.sub (= the sub returned by the AdminCreateUser response). detail.responseElements.user.userStatus is "FORCE_CHANGE_PASSWORD" for a create carrying a TemporaryPassword. The literal HIDDEN_DUE_TO_SECURITY_REASONS and the additionalEventData.sub naming are recorded behavior only (the model states only the @sensitive classification). Rule matching is exact on these fields, so a rule naming eventName AdminDeleteUser must receive the delete and never the create, and vice versa.

Emulator: all control-plane setup succeeds (CreateUserPool, CreateBucket + bucket policy, CreateTrail, PutEventSelectors{ReadWriteType WriteOnly, IncludeManagementEvents true}, StartLogging with GetTrailStatus reporting IsLogging true, three PutRule/PutTargets, AdminCreateUser). The subsequent ReceiveMessage polling never yields a single envelope: the control leg (an sqs:TagQueue write, budget 900 s) and then the cognito legs (budget 180 s each) all sit in their wait loops, and the replay ends with "Error: Check timed out after 60.0s" — i.e. within the harness's 60 s ceiling not one CloudTrail-derived event was delivered to any of the three rules. Hypothesis: the emulator has no CloudTrail→EventBridge publication path at all, so neither the sqs control event nor the cognito-idp events exist to match; consequently the redaction and rule-scoping assertions (HIDDEN_DUE_TO_SECURITY_REASONS for username/temporaryPassword, additionalEventData.sub, no AdminCreateUser in the AdminDeleteUser sink) are never even reached.

Why: a client cannot build the standard audit-driven automation — react to a Cognito administrative write by rule, fan it out to a queue/Lambda, or alarm on AdminDeleteUser — because no CloudTrail-sourced event is ever emitted; every such rule stays silent forever instead of firing, and code that waits for the event hangs rather than failing. It also leaves the security contract unverifiable: on real AWS the delivered record provably carries no plaintext username or temporary password, and here there is no record at all, so an emulator that later starts delivering unredacted records would not be caught.

Note: open issue 20261024T114720Z-cloudtrail-event-history-is-empty-for-everything-but.md covers the event-history/S3-log-file gap and 20261111T002832Z-cloudtrail-cognito-idp-no-cognito-idp-amazonaws-com.md covers LookupEvents for cognito-idp AdminGetUser; neither carries this check's replay key nor the CloudTrail→EventBridge delivery path and its redaction contract, so it is filed here.

Fix: the CloudTrail trail pipeline must publish management events of a logging trail onto the EventBridge default bus as "AWS API Call via CloudTrail" events (envelope source/account/region + the CloudTrail record under detail), and the cognito-idp record builder must emit requestParameters/responseElements with the @sensitive members present and replaced by HIDDEN_DUE_TO_SECURITY_REASONS plus additionalEventData.sub; EventBridge's rule matcher then needs to scope those events to the pattern's eventSource/eventName so a near-miss rule receives nothing.

Traces: cloudtrail__cognito-idp__events__sqs.xsvc-cognito-idp-1-admin-create-user-routes-only-to-its-own-rule-without-password-material (verdict mismatch; timed out in the delivery wait).

## Evidence
Expected: after StartLogging on a trail with EventSelectors[{ReadWriteType: WriteOnly, IncludeManagementEvents: true}], (a) an sqs:TagQueue write is delivered to a rule matching {source: [aws.sqs], detail-type: ["AWS API Call via CloudTrail"], detail.eventName: [TagQueue]}; (b) AdminCreateUser is delivered to the rule matching {source: [aws.cognito-idp], detail.eventSource: [cognito-idp.amazonaws.com], detail.eventName: [AdminCreateUser]} with detail.requestParameters.userPoolId = the pool id, detail.requestParameters.username = "HIDDEN_DUE_TO_SECURITY_REASONS", detail.requestParameters.temporaryPassword = "HIDDEN_DUE_TO_SECURITY_REASONS", detail.requestParameters.messageAction = "SUPPRESS", detail.additionalEventData.sub = the created user's sub, detail.responseElements.user = {username: "HIDDEN_DUE_TO_SECURITY_REASONS", userStatus: "FORCE_CHANGE_PASSWORD"}, detail.readOnly = false, detail.eventCategory = "Management", and neither the plaintext username nor the temporary password anywhere in the body; (c) AdminDeleteUser is delivered only to the AdminDeleteUser rule, which holds no AdminCreateUser.

Actual: no message is ever received on any of the three queues. The replay reports: "[mismatch] cloudtrail__cognito-idp__events__sqs.xsvc-cognito-idp-1-admin-create-user-routes-only-to-its-own-rule-without-password-material — Error: Check timed out after 60.0s". The assertions the check would otherwise raise are "DATAPLANE_UNIMPLEMENTED: the CloudTrail->EventBridge channel never went live: none of N sqs:TagQueue control writes reached the control rule ... expected >=1, actual 0" and "DATAPLANE_UNIMPLEMENTED: the subject rule never delivered cognito-idp:AdminCreateUser for pool <poolId> ... expected 1, actual 0". GetTrailStatus reported IsLogging true, so the trail believes it is logging while nothing is published.

2. s3.create_bucket(<unique>) (+ LocationConstraint outside us-east-1) and put_bucket_policy allowing cloudtrail.amazonaws.com s3:GetBucketAcl on the bucket and s3:PutObject on AWSLogs/<account>/* with s3:x-amz-acl=bucket-owner-full-control.

4. Create three SQS queues with policies allowing events.amazonaws.com SendMessage, and three EventBridge rules targeting them: {source:[aws.sqs], detail-type:["AWS API Call via CloudTrail"], detail:{eventSource:[sqs.amazonaws.com], eventName:[TagQueue]}}, {source:[aws.cognito-idp], detail-type:["AWS API Call via CloudTrail"], detail:{eventSource:[cognito-idp.amazonaws.com], eventName:[AdminCreateUser]}}, and the same with eventName AdminDeleteUser.
5. sqs.tag_queue(QueueUrl=<control queue>, Tags={"sim2real-marker": <unique>}) and long-poll the control queue. Expected: an envelope with source "aws.sqs", detail-type "AWS API Call via CloudTrail" and detail.requestParameters containing the marker. Actual: nothing, indefinitely.
6. idp.create_user_pool(...); idp.admin_create_user(UserPoolId=<pool>, Username=<unique>, TemporaryPassword="Tp1!<token>", MessageAction="SUPPRESS") -> User.UserStatus FORCE_CHANGE_PASSWORD; long-poll the subject queue.
