# cloudformation__rds__secretsmanager: AWS::SecretsManager::SecretTargetAttachment is inert — Ref/GetAtt Id return a generated physical id instead of the secret ARN, and the target's connection details are never merged into the secret (2 causes)

> _Note: this issue was identified against the code base at commit `b5518325ad9936970d86f9a3541971c01b6fb226`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Two net-new root causes, both in the CloudFormation resource provider for AWS::SecretsManager::SecretTargetAttachment. Both are now reachable because the stack reaches CREATE_COMPLETE; the open issue 20261109T135215Z-cloudformation-rds-secretsmanager-an-aws-rds-dbinstance-whose.md (the {{resolve:secretsmanager:...}} MasterUsername/MasterUserPassword reference failing the DBInstance create) blocked everything downstream of the instance and listed these same two check ids, but its recorded failure was `assert status == "CREATE_COMPLETE"`; that assertion now passes and the two causes below are what the checks fail on instead. Neither cause is covered by any open issue (no issue mentions SecretTargetAttachment).

Cause 1 of 2: Ref and GetAtt .Id on AWS::SecretsManager::SecretTargetAttachment return a generated physical resource id, not the attached secret's ARN. Failing check: cloudformation__rds__secretsmanager.deploy-secret-target-attachment-rds-instance.
AWS: recorded behavior only for the physical-id composition (CloudFormation's resource contract is not in a Smithy model; the resource reference is documented at https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-secretsmanager-secrettargetattachment.html). A SecretTargetAttachment's physical resource id IS the ARN of the secret named in its SecretId property, so `Ref <attachment>` and `Fn::GetAtt <attachment>.Id` both resolve to that secret ARN — the same value `Ref` on the AWS::SecretsManager::Secret resource returns. The ARN's shape is arn:aws:secretsmanager:<region>:<account>:secret:<name>-<6-char suffix>; the region, account, name and suffix are per-environment values, the requirement is that the attachment's Ref equals the referenced secret's ARN.
Emulator: the attachment's Ref (and GetAtt .Id) is a CloudFormation-style generated physical id built from the stack name, the logical id and a random hex suffix — of the form '<stack-name>-SecretAttachment-<12 hex chars>' — which is not a secret ARN at all and names no Secrets Manager resource.
Why: the attachment's Ref is the canonical way a template hands a database secret's ARN to a consumer (a Lambda environment variable, an ECS task `secrets` entry, an IAM policy Resource, a stack Output) while also ordering that consumer after the attachment. A client that does so receives a string that is not an ARN, so every downstream GetSecretValue/DescribeSecret call made with it is refused and IAM policies written from it match nothing.
Fix: the AWS::SecretsManager::SecretTargetAttachment resource provider in the cloudformation service crate — it must return the resolved SecretId ARN as the resource's physical id (and expose that same value as the `Id` attribute) instead of minting a generated name.

Cause 2 of 2: a SecretTargetAttachment never writes the target's connection details into the secret's SecretString. Failing check: cloudformation__rds__secretsmanager.secret-target-attachment-update-nonexistent-target-rejected.
AWS: recorded behavior only (same resource reference). When the attachment is created, Secrets Manager adds the target's connection details to the referenced secret as a new AWSCURRENT version, merging them into the existing JSON object without disturbing the keys already there. For TargetType AWS::RDS::DBInstance those keys are `engine` (the instance's Engine, e.g. "mysql"), `host` (the instance endpoint Address), `port` (the endpoint Port, a JSON number) and `dbInstanceIdentifier` (the DBInstanceIdentifier) — so a secret created from GenerateSecretString with {"username": ...} plus a generated "password" reads back as exactly {username, password, engine, host, port, dbInstanceIdentifier}. Removing the attachment by a stack update reverts the secret to just the keys it held before ({username, password}). The host, port and identifier values come from the target instance and the username/password from the secret; only the key set and the sourcing rule are the requirement.
Emulator: the secret's SecretString keeps only the keys the Secret resource generated. GetSecretValue after CREATE_COMPLETE parses to host=None, port=None, engine=None, dbInstanceIdentifier=None, username='sim2realadmin' — i.e. the four connection keys are absent entirely; the attachment resource reports CREATE_COMPLETE while writing nothing.
Why: this resource exists precisely so an application can read one secret and get both the credentials and where to connect. A client that deploys the documented RDS+secret pattern gets a secret with no host/port/engine, so it cannot connect at all; and because the keys never appear, the inverse contract (a stack update that drops the attachment removing exactly those keys, and a rejected retargeting update leaving them untouched) is unobservable.
Fix: the AWS::SecretsManager::SecretTargetAttachment provider's create/update/delete handlers in the cloudformation service crate, plus the secretsmanager state write they must perform (put a new AWSCURRENT version of the referenced secret with the target's connection details merged in, and remove them again on delete).

Traces: cloudformation__rds__secretsmanager.deploy-secret-target-attachment-rds-instance (Cause 1), cloudformation__rds__secretsmanager.secret-target-attachment-update-nonexistent-target-rejected (Cause 2).

## Evidence
Cause 1 — check cloudformation__rds__secretsmanager.deploy-secret-target-attachment-rds-instance, replay detail verbatim:
  AssertionError: Ref(SecretAttachment) was 'sim2real-sta-stack-9c710a5fa92e-SecretAttachment-FDE03CA118AB', expected the secret ARN 'arn:aws:secretsmanager:us-west-2:000000000000:secret:sim2real-sta-secret-5513b0129e32-uafEp1'
Expected: Ref(SecretAttachment) == Ref(AppSecret) == the secret's ARN; GetAtt SecretAttachment.Id the same value. Actual: a '<stack>-<logical id>-<hex>' generated physical id. The stack name, secret name, account, region and ARN suffix shown are per-run values; the requirement is Ref(attachment) == the referenced secret's ARN.

Cause 2 — check cloudformation__rds__secretsmanager.secret-target-attachment-update-nonexistent-target-rejected, replay detail verbatim:
  AssertionError: positive control: the attached secret fields were {'host': None, 'port': None, 'engine': None, 'dbInstanceIdentifier': None, 'username': 'sim2realadmin'}, expected {'host': '127.0.0.1', 'port': 43181, 'engine': 'mysql', 'dbInstanceIdentifier': 'sim2real-stau-db-63c68bb3642a', 'username': 'sim2realadmin'}
Expected: after CREATE_COMPLETE, GetSecretValue(SecretId=<secret arn>).SecretString parses to a JSON object carrying engine/host/port/dbInstanceIdentifier taken from the attachment's RDS target alongside the username/password already in the secret. Actual: those four keys are absent. The specific host, port and instance identifier are per-run values from the target instance, not part of the requirement; `engine` is the target's Engine ("mysql" here) and the four key NAMES are fixed.
Both checks' template: an AWS::SecretsManager::Secret (GenerateSecretString with SecretStringTemplate '{"username":"sim2realadmin"}', GenerateStringKey "password"), an AWS::RDS::DBInstance (mysql, db.t3.micro), and an AWS::SecretsManager::SecretTargetAttachment with SecretId: !Ref AppSecret, TargetId: !Ref DbInstance, TargetType: AWS::RDS::DBInstance.

## Steps to Reproduce
1. CreateDBSubnetGroup over the account's subnets.
2. CreateStack with: AppSecret (AWS::SecretsManager::Secret, GenerateSecretString SecretStringTemplate '{"username":"sim2realadmin"}', GenerateStringKey "password", PasswordLength 20); DbInstance (AWS::RDS::DBInstance, Engine mysql, DBInstanceClass db.t3.micro, AllocatedStorage 20, MasterUsername/MasterUserPassword from {{resolve:secretsmanager:${AppSecret}:SecretString:username|password}}); SecretAttachment (AWS::SecretsManager::SecretTargetAttachment, SecretId: !Ref AppSecret, TargetId: !Ref DbInstance, TargetType: AWS::RDS::DBInstance); Outputs for !Ref AppSecret, !Ref SecretAttachment and !GetAtt SecretAttachment.Id.
3. Wait for CREATE_COMPLETE, then DescribeStacks and read the Outputs: Ref(SecretAttachment) and GetAtt SecretAttachment.Id are a generated '<stack>-SecretAttachment-<hex>' string instead of the AppSecret ARN (Cause 1).
4. GetSecretValue on the secret ARN and parse SecretString: it holds only username and password — engine, host, port and dbInstanceIdentifier are missing, although DescribeDBInstances reports the instance's Endpoint.Address/Port and Engine (Cause 2).
5. UpdateStack with the attachment removed and observe that nothing is removed from the secret either, since nothing was ever added.
