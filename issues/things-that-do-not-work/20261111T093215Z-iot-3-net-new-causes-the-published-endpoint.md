## Description
REOPENS 20261109T113725Z-iot-describeendpoint-publishes-a-real-aws-hostname-id.md: its fix left the call refused. That fix made DescribeEndpoint publish the emulator's own front door instead of an amazonaws.com host, but the front door still routes only by SigV4 credential scope / X-Amz-Target / Host, so the two certificate-authenticated (mTLS) planes that endpoint exists to serve are refused at the router, and the published value now carries no AWS endpoint-type structure at all.

Three net-new root causes in this service, none of them carrying these checks' replay keys today. Related open issues, named so they are not mistaken for cover: 20261110T222008Z-iot-the-published-data-plane-address-serves-no.md describes Cause 2 and Cause 3 for FOUR OTHER checks (iot.iot-mtls-publish-refused-when-policy-pins-sourcevpce-rejected, iot.iot-mtls-retained-publish-rejected-without-retainpublish-action, iot.iot-sigv4-publish-unaffected-by-certificate-policy-condition, iot.shadow-client-token-echoed-not-persisted) and carries none of the five keys below; 20261109T114414Z / 20261109T120740Z / 20261109T122953Z all describe the OLD real-AWS-hostname behavior, which is no longer what is served. Cause 1 (the credential provider) is described nowhere.

Cause 1 of 3: the published iot:CredentialProvider endpoint serves no certificate-authenticated credential exchange — GET /role-aliases/{roleAlias}/credentials answers 404 UnknownService instead of vending credentials.
AWS: recorded behavior only — the IoT credential provider is an endpoint-only API and is not an operation in the iot Smithy model (the model covers only the control-plane role-alias operations: CreateRoleAlias, DescribeRoleAlias GET /role-aliases/{roleAlias}, DeleteRoleAlias DELETE /role-aliases/{roleAlias}). AWS documents the exchange as a mutual-TLS HTTPS GET to /role-aliases/{roleAlias}/credentials on the account's iot:CredentialProvider endpoint, with a registered X.509 client certificate and NO SigV4 signature: the certificate is the principal, and its attached IoT policy must allow iot:AssumeRoleWithCertificate on the role alias ARN. The recording shows HTTP 200 with a JSON body containing a "credentials" object carrying "accessKeyId" (plus the session secret/token and expiry); the member names are fixed text, the key material and expiry are per-run values. After DeleteRoleAlias the very next request is refused immediately with 404 (alias gone) or 400 (role resolution races the delete) — never a 200, and never a cached-TTL grace period.
Emulator: every such request answers HTTP 404 with body {"__type":"UnknownService","message":"could not resolve a target service from the request (no SigV4 credential scope, X-Amz-Target, or Host header)"}. The 404, the error code "UnknownService" and that message are the fixed text of the divergence; "UnknownService" is an error code that exists in no IoT model. iot.delete-role-alias-succeeds-despite-active-credentials fails with 'credentials-provider never returned 200 within 45s: HTTP 404: {"__type":"UnknownService",...}'; iot.role-alias-delete-invalidates-credential-exchange polls the same URL and reaches no verdict at all, timing out at the 60 s harness cap.
Why: a device doing exactly what AWS prescribes — DescribeEndpoint(iot:CredentialProvider), then an mTLS GET of /role-aliases/<alias>/credentials — never obtains credentials, and a client cannot distinguish "this role alias was deleted" from "no such service". Because the positive exchange is unreachable, the post-delete refusal cannot be observed either: the no-grace-period guarantee and the ResourceNotFoundException-after-delete control-plane behavior both pass vacuously or never run.
Fix: the front door's service resolution plus a new iot credential-provider data-plane handler — the router must dispatch /role-aliases/{roleAlias}/credentials by path/listener when no SigV4 scope is present, and the handler must authenticate the TLS client certificate as the IoT certificate principal, evaluate its attached IoT policies for iot:AssumeRoleWithCertificate on the alias ARN, assume the alias's role and return the credentials body — refusing with 404/400 once the alias is deleted.
Traces: iot.delete-role-alias-succeeds-despite-active-credentials, iot.role-alias-delete-invalidates-credential-exchange. Published address: services/service-com-amazonaws-iot-awsiotservice/src/ops/describe_endpoint.rs lines 176-200 (published_endpoint_address -> emulator_endpoint_authority), whose own note states the front door "resolves a request to the service its SigV4 credential scope names".

Cause 2 of 3: the published iot:Data-ATS endpoint serves no certificate-authenticated publish — POST /topics/{topic} answers 404 UnknownService, so neither the allowed (200) nor the denied (403) half of certificate-principal authorization is reachable.
AWS: Smithy com.amazonaws.iotdataplane#Publish — POST /topics/{topic} with topic as @httpLabel, qos/retain/contentType/responseTopic/messageExpiry as @httpQuery, payload as @httpPayload, success code 200 with an empty body; modeled errors UnauthorizedException (401), InvalidRequestException (400), MethodNotAllowedException (405), ThrottlingException (429), InternalFailureException (500). On AWS the request is accepted over mutual TLS with a registered client certificate and no SigV4 signature; the attached IoT policy decides it. An allowed publish is 200. A publish the policy does not permit is HTTP 403 whose body is exactly {"message": null, "traceId": "<uuid>"} — the two member names and the null message are fixed text, the traceId is a per-request UUID and is not part of the requirement. An INACTIVE certificate is refused one layer earlier, at TLS: the session closes with no HTTP response at all, which is how a client tells a certificate-status refusal from an authorization refusal.
Emulator: every such request answers HTTP 404 with body {"__type":"UnknownService","message":"could not resolve a target service from the request (no SigV4 credential scope, X-Amz-Target, or Host header)"} — the status, the code and that message being the fixed text of the divergence. The front door rejects the request before any iot-data handler sees it, because a cert-authenticated data-plane request carries none of the three routing hints it resolves on.
Why: DetachPolicy/AttachPolicy revocation and restoration cannot be observed at the data plane, so a bookkeeping-only detach that changes nothing but ListAttachedPolicies is indistinguishable from a real one; and the ACTIVE-vs-INACTIVE certificate distinction (TLS-layer close vs HTTP 403) collapses, since both end as the same 404. Devices get an error code from no IoT model where AWS gives them 200 or 403.
Fix: the front door's service resolution plus the iot-data plane's authentication — route the modeled iot-data HTTP paths (POST /topics/{topic} and the /connections/* family) by path/listener when no SigV4 scope is present, and have the Publish handler authenticate the TLS client certificate as the IoT certificate principal, honour the certificate's ACTIVE/INACTIVE status at the TLS layer, and evaluate the attached IoT policies — 200 on allow, the modeled 403 body on deny.
Traces: iot.iot-detach-policy-revokes-mtls-publish-and-reattach-restores, iot.iot-mtls-inactive-certificate-rejected-before-authorization.

Cause 3 of 3: DescribeEndpoint publishes ONE bare host:port authority for EVERY endpointType, so the data endpoint and the credential-provider endpoint are indistinguishable and neither has the documented host-name form.
AWS: Smithy com.amazonaws.iot#DescribeEndpoint — GET /endpoint, input endpointType (@httpQuery, @length 0..128), output endpointAddress, modeled errors InternalFailureException (500), InvalidRequestException (400), ThrottlingException (400), UnauthorizedException (401). endpointAddress is documented as "The endpoint. The format of the endpoint is as follows: identifier.iot.region.amazonaws.com." — a dotted DNS host name, with no port component, whose labels identify the endpoint TYPE: the ATS data endpoint carries the "-ats.iot.<region>" labels and the credential provider carries a "credentials" label, so the two addresses necessarily differ. The identifier, region and DNS suffix are environment values; the per-type label structure and the fact that distinct endpoint types yield distinct addresses are the requirement.
Emulator: endpointAddress is the raw front-door authority — a host and a port with no host-name structure, containing no ".iot." labels and no "credentials" label, and the SAME value is returned for iot:Data, iot:Data-ATS, iot:CredentialProvider and iot:Jobs alike (describe_endpoint.rs lines 176-200 state outright that it "is therefore the address of EVERY endpoint type"). iot.describe-endpoint-types fails on the first of these assertions with 'AssertionError: 127.0.0.1:40601' (the specific host and port are per-run values and are not the defect; the absence of any type-bearing host-name form, and the two types not differing, are). Because the check stops there, the retired-iot:Jobs and unknown-endpointType refusals it also asserts are never reached.
Why: the documented discovery contract is "call DescribeEndpoint for an endpoint type, then address that plane at the host name returned". Code that derives anything from the published form — the ATS marker, the embedded region, the name used as the TLS/SNI host for an MQTT or HTTPS session — or that caches one address per endpoint type and expects them to differ, breaks against a single undifferentiated authority, even though it happens to be reachable. The two requirements compose: the published value must be a host name of the documented per-type form AND must resolve and route to the emulator's own listener.
Fix: the endpoint-address rendering in DescribeEndpoint's handler — publish, per endpointType, an own-host DNS name of the documented form (carrying the "-ats.iot.<region>" / "credentials.iot.<region>" labels) that the emulator also owns and routes, with a port only where the listener needs one, instead of returning the bare front-door authority for every type.
Traces: iot.describe-endpoint-types. Rendering site: services/service-com-amazonaws-iot-awsiotservice/src/ops/describe_endpoint.rs lines 176-200, with the per-type tokens at lines 157-165.
