# cloudwatch__ec2__elbv2__opensearch: a stack's AWS::ElasticLoadBalancingV2::Listener never leaves CREATE_IN_PROGRESS, so CloudFormation gives up and rolls the whole stack back to ROLLBACK_COMPLETE

> _Note: this issue was identified against the code base at commit `34aa023e13a037c836015cae341f7a7e68727fe7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateListener

## Description
One net-new root cause (Cause 1 of 1).

Cause 1 of 1: a native AWS::ElasticLoadBalancingV2::Listener resource in a CloudFormation stack is provisioned (an ELBv2 listener ARN is minted for it) but its CloudFormation resource status never advances from CREATE_IN_PROGRESS to CREATE_COMPLETE. CloudFormation's own wait for that resource expires, the resource is marked FAILED with the reason '<logical-id> <resource-type> <physical-id> was still CREATE_IN_PROGRESS when the wait for it to be created ran out', and the stack rolls back to ROLLBACK_COMPLETE instead of CREATE_COMPLETE.
Failing check ids: cloudwatch__ec2__elbv2__opensearch.e2e-diagnose-alb-opensearch-stale-targets-with-alarm-config

AWS: elbv2 CreateListener is a synchronous AWS Query operation — Smithy: CreateListener input {LoadBalancerArn (required), Protocol, Port (range 1-65535), DefaultActions (required), ...} -> output {Listeners: Listeners}; its modeled errors are all client 4xx refusals (IncompatibleProtocolsException/IncompatibleProtocols, InvalidLoadBalancerActionException/InvalidLoadBalancerAction, TargetGroupNotFoundException/TargetGroupNotFound, LoadBalancerNotFoundException/LoadBalancerNotFound, ...), and the Listener shape carries no pending/creating state member at all. There is therefore no asynchronous settling step for a listener: in real AWS an AWS::ElasticLoadBalancingV2::Listener resource reaches CREATE_COMPLETE as soon as CreateListener returns 200 with the listener, and the stack containing it reaches CREATE_COMPLETE. The template here asks for a plain HTTP:80 listener on an internal application load balancer whose single DefaultActions entry is {"Type":"forward","TargetGroupArn": <an ip-target HTTPS:443 target group in the same VPC>} — a configuration AWS accepts (no modeled error applies), so the only AWS-correct outcomes are CREATE_COMPLETE for the resource, or one of the 4xx refusals above surfaced as a CREATE_FAILED with that error code as the reason. Neither an indefinite CREATE_IN_PROGRESS nor a timeout is an AWS outcome.

Emulator: the listener's physical id is assigned (the failure reason quotes a well-formed listener ARN of the form arn:aws:elasticloadbalancing:<region>:<account>:listener/app/<alb-name>/<alb-id>/<listener-id>), so the create itself ran, yet the resource stays CREATE_IN_PROGRESS until CloudFormation's create wait expires. DescribeStacks then reports StackStatus 'ROLLBACK_COMPLETE', and DescribeStackEvents reports the listener's logical id ('HttpListener' in this template) with ResourceStatus ending in FAILED and ResourceStatusReason '<physical-id> was still CREATE_IN_PROGRESS when the wait for it to be created ran out'. In that reason the fixed text is 'was still CREATE_IN_PROGRESS when the wait for it to be created ran out'; the leading resource type and ARN are values taken from the request and the emulator's state, and the stack name, ALB name and listener/ALB id segments vary per run and are not part of the requirement. Because the stack rolls back, every downstream resource and output of the stack is torn down: the check's deploy phase never gets the stack Outputs (VpcId, DomainName, DomainEndpoint, AlbDnsName, AlbArn, DashboardsTgArn, ApiTgArn, AlarmName) and the remaining four phases (setup, solve, cleanup, destroy) never run.

Why: a client that deploys an ALB-fronted estate by CloudFormation — the normal way an ALB, its target groups, its listener and its CloudWatch alarm are created together — can never obtain a CREATE_COMPLETE stack if the template contains a single listener. The stack self-destructs, so the load balancer, target groups, alarm and OpenSearch domain the template created are all deleted again, every stack Output is unavailable, and the client sees a rollback with no actionable AWS error code. A template that AWS deploys successfully is unusable here, and the rollback is indistinguishable (to a client) from a genuine configuration defect in its own template.

Fix: the CloudFormation resource provisioner/stabilization path for the AWS::ElasticLoadBalancingV2::Listener resource type — the step that is supposed to mark the resource CREATE_COMPLETE once the underlying elbv2 CreateListener call returns. Either it never reports completion back to the stack's resource state machine, or it waits on a listener readiness condition that the elbv2 state never satisfies (the modeled Listener has no such state). The listener's create must settle synchronously, and any configuration the service rejects must surface as CREATE_FAILED carrying the modeled elbv2 error code rather than as a wait timeout.

## Evidence
Expected (AWS): CreateListener is synchronous (Smithy: CreateListener -> CreateListenerOutput{Listeners}; no state member on Listener; all modeled errors are client 4xx). The stack's AWS::ElasticLoadBalancingV2::Listener resource therefore reaches CREATE_COMPLETE and DescribeStacks reports StackStatus 'CREATE_COMPLETE', with the stack Outputs (VpcId, DomainName, DomainEndpoint, AlbDnsName, AlbArn, DashboardsTgArn, ApiTgArn, AlarmName) readable. If the configuration were refused, the resource would be CREATE_FAILED with a modeled elbv2 error code (e.g. IncompatibleProtocols, InvalidLoadBalancerAction, TargetGroupNotFound) as the reason.

Actual (emulator): the listener resource is assigned a listener ARN but stays CREATE_IN_PROGRESS; CloudFormation's create wait expires, the resource is marked FAILED with ResourceStatusReason '<type> <listener-arn> was still CREATE_IN_PROGRESS when the wait for it to be created ran out', and DescribeStacks reports StackStatus 'ROLLBACK_COMPLETE'. The stack never yields Outputs, so phases setup/solve/cleanup/destroy never execute.

## Steps to Reproduce
1. CreateStack with a template containing an AWS::EC2::VPC, two private subnets, an internal AWS::ElasticLoadBalancingV2::LoadBalancer (Type application, Scheme internal) over those subnets, two AWS::ElasticLoadBalancingV2::TargetGroup resources (TargetType ip, Protocol HTTPS, Port 443) and one AWS::ElasticLoadBalancingV2::Listener with Properties {LoadBalancerArn: Ref Alb, Port: 80, Protocol: HTTP, DefaultActions: [{Type: forward, TargetGroupArn: Ref DashboardsTg}]}.
2. Poll DescribeStacks(StackName=<stack>) until StackStatus is terminal.
3. Observe StackStatus 'ROLLBACK_COMPLETE' rather than 'CREATE_COMPLETE'.
4. Call DescribeStackEvents(StackName=<stack>) and observe the listener's logical id with a *_FAILED ResourceStatus and ResourceStatusReason ending 'was still CREATE_IN_PROGRESS when the wait for it to be created ran out', while the quoted physical id is an already-minted listener ARN.
5. Replay the behavioral check cloudwatch__ec2__elbv2__opensearch.e2e-diagnose-alb-opensearch-stale-targets-with-alarm-config to confirm.
