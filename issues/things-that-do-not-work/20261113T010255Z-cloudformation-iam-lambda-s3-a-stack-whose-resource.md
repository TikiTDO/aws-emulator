# cloudformation__iam__lambda__s3: a stack whose resource is a Lambda-backed Custom:: provider never reaches a terminal StackStatus — DescribeStacks stays *_IN_PROGRESS forever

> _Note: this issue was identified against the code base at commit `ab3e9411edd79c78c4763b290b74822ee89d0fde`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
One net-new root cause.

Cause 1 of 1: a CloudFormation stack whose only resource is a `Custom::<Name>` resource whose `ServiceToken` names an AWS Lambda FUNCTION never settles. Failing check ids: cloudformation__iam__lambda__s3.cfn-custom-resource-lambda-missing-s3-permission-negative, cloudformation__iam__lambda__s3.cfn-custom-resource-role-least-privilege-positive.

AWS: CloudFormation sends the custom resource's provider a `Create`/`Update`/`Delete` request and holds the resource — and the stack operation behind it — in its `*_IN_PROGRESS` status only until the provider answers at the request's pre-signed `ResponseURL`. A Lambda `ServiceToken` is invoked with that request as its event, the function RUNS, and its PUT to the `ResponseURL` releases the wait, so the stack reaches a terminal `StackStatus` within seconds-to-minutes: `CREATE_COMPLETE` on a `SUCCESS` answer, and `CREATE_FAILED` for the resource followed by `ROLLBACK_COMPLETE` for the stack on a `FAILED` answer, with the resource's `ResourceStatusReason` carrying the provider's own `Reason` text verbatim (here the provider reports the S3 refusal, whose code is `AccessDenied`). Smithy (cloudformation): `StackStatus` enum = CREATE_IN_PROGRESS | CREATE_FAILED | CREATE_COMPLETE | ROLLBACK_IN_PROGRESS | ROLLBACK_FAILED | ROLLBACK_COMPLETE | ... ; `ResourceStatus` enum = CREATE_IN_PROGRESS | CREATE_FAILED | CREATE_COMPLETE | ... ; `StackEvent$ResourceStatusReason`. Even when the provider answers NOTHING at all, AWS bounds the wait: the custom resource's own `ServiceTimeout` property ("the maximum time, in seconds, that can elapse before a custom resource operation times out", 1..14400, default one hour) ends it and the resource is failed with a reason, so the stack always reaches a terminal status. Recorded behavior only for the exact timeout reason text.

Emulator: the request IS sent — `services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioning/custom_resource.rs` resolves the `ServiceToken`'s SERVICE segment to `Provider::Function` and invokes it with `InvocationType=Event`, i.e. an asynchronous invoke whose 202 is only the queueing receipt — but the provider's answer never arrives at the `ResponseURL`, so the resource's barrier in `src/state/stabilising.rs` is never released and `DescribeStacks` reports a non-terminal `StackStatus` (`CREATE_IN_PROGRESS`) indefinitely. Both checks poll `DescribeStacks` for ANY terminal status and never observe one; they are killed by the harness's 60 s cap with `Check timed out after 60.0s`, having reached no assertion. Nothing in the emulator ends the wait either: no `ServiceTimeout` expiry fails the resource, and a provider invocation that cannot run is not turned into a `FAILED` answer, so the stack hangs rather than failing.

Why: a client that deploys a stack containing a Lambda-backed custom resource — which is how every CDK custom resource, every `AWS::CloudFormation::CustomResource` and every SAM/CDK bootstrap helper is built — blocks forever. `aws cloudformation wait stack-create-complete`, CDK `deploy` and any `describe_stacks` poll never terminate, and the stack can be neither finished nor rolled back. This is strictly worse than a wrong answer: there is no answer, and the failure is unattributable from the client side. The negative control is also lost: a client that relies on the custom resource's `CREATE_FAILED` `ResourceStatusReason` to learn WHY its provider failed (here an `AccessDenied` from S3 because the provider role lacks `s3:PutObject`) gets no event at all.

Fix: two components, both in the cloudformation crate's custom-resource path. (1) The provider-run path: an `Event` invoke of the provider function must actually deliver and RUN the package so the handler's PUT to the `ResponseURL` reaches `src/service/custom_resource_plane.rs`; the python3.12 providers these checks deploy import `boto3` and `urllib3`, so the in-process engine must serve those or the invocation must be reported as a failed delivery rather than silently dropped. (2) The WAIT must be bounded regardless: `custom_resource.rs` already parses `ServiceTimeout` (`SERVICE_TIMEOUT`, 1..14400) but nothing expires it — `src/state/stabilising.rs` / `src/state/provisioning` must fail the resource with a reason when the window closes, and a provider invocation its own service REFUSES must fail the resource immediately instead of leaving the barrier armed. Related open issues, neither of which carries these two replay keys: `20261104T160000Z-cloudformation-iam-lambda-s3-six-causes-awaiting-the-lambda-provisioner-and-an-in-process-runtime.md` (its cause 6 describes the same custom-resource path, but its recorded symptom is `GetObject` answering 404 `NoSuchKey` AFTER a stack that did reach `CREATE_COMPLETE` — the stack no longer reaches a terminal status at all, which is what this issue is about) and `20261025T180059Z-cloudformation-custom-resource-providers-and-hook-configuration.md` (which records the SNS-topic provider transport as working).

Traces: cloudformation__iam__lambda__s3.cfn-custom-resource-lambda-missing-s3-permission-negative (negative control: expects `ROLLBACK_COMPLETE` plus a `Writer` `CREATE_FAILED` event whose `ResourceStatusReason` contains `AccessDenied`, and `HeadObject` 404 on the unwritten key), cloudformation__iam__lambda__s3.cfn-custom-resource-role-least-privilege-positive (positive control: expects `CREATE_COMPLETE` then `UPDATE_COMPLETE` with the v1 and v2 objects written). `src/state/provisioning/custom_resource.rs` lines 128-135 (`LAMBDA_SIGNING_NAME`, `INVOCATION_TYPE_EVENT`) and 65-79 (`SERVICE_TIMEOUT`, `MIN_SERVICE_TIMEOUT`/`MAX_SERVICE_TIMEOUT`, `SERVICE_TIMEOUT_OUT_OF_RANGE`).

## Evidence
Both checks: `Error: Check timed out after 60.0s` — the harness kills them while they are still inside `_poll_until(lambda: cfn.describe_stacks(StackName=stack_name)["Stacks"][0]["StackStatus"], lambda s: s in {"CREATE_COMPLETE", "CREATE_FAILED", "ROLLBACK_COMPLETE", "ROLLBACK_FAILED"}, timeout_s=180)`, so no assertion is ever reached and no terminal status is ever observed.

Expected (AWS), positive control: `DescribeStacks` → `StackStatus=CREATE_COMPLETE`, then after `UpdateStack` → `StackStatus=UPDATE_COMPLETE`; `GetObject` on the v1 key returns body `least-privilege-write-v1` and on the v2 key `least-privilege-write-v2`.
Expected (AWS), negative control: `DescribeStacks` → `StackStatus=ROLLBACK_COMPLETE`; `DescribeStackEvents` carries an event with `LogicalResourceId=Writer`, `ResourceStatus=CREATE_FAILED` and a `ResourceStatusReason` containing the provider's reported error code `AccessDenied` (the provider's own `Reason` text, propagated verbatim — the fixed part is the S3 error code and message class, the variable parts are the bucket, key, role ARN and action named by the request and state); `HeadObject` on the unwritten key → HTTP 404.
Actual (emulator): `DescribeStacks` keeps answering a non-terminal `StackStatus` (`CREATE_IN_PROGRESS`) for the whole observation window; no `CREATE_FAILED` event is emitted for `Writer`, no `ROLLBACK_*` status is ever reached, and neither `UpdateStack` nor the stack delete the checks register for cleanup can settle either.

Grounding in the checkout: `services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioning/custom_resource.rs` documents and implements exactly this hold — "holds the resource — and the stack operation behind it — in its `*_IN_PROGRESS` status until the provider answers at the request's `ResponseURL`" — reaches a Lambda `ServiceToken` with `INVOCATION_TYPE_EVENT = "Event"` (an async invoke whose answer is only the queueing receipt), and parses `ServiceTimeout` without anything expiring it.

## Steps to Reproduce
1. Create an S3 bucket.
2. Create an IAM role trusting `lambda.amazonaws.com` with an inline policy granting only `logs:CreateLogGroup`/`CreateLogStream`/`PutLogEvents` on `*` (negative control), or that plus `s3:PutObject` on `arn:aws:s3:::<bucket>/*` (positive control).
3. `lambda:CreateFunction` a `python3.12` function from an inline zip whose handler does `boto3.client("s3").put_object(...)` with the event's `ResourceProperties`, then PUTs `{"Status": "SUCCESS"|"FAILED", "PhysicalResourceId": ..., "StackId": ..., "RequestId": ..., "LogicalResourceId": ..., "Reason": ...}` to `event["ResponseURL"]`; wait for `GetFunction` `State=Active`.
4. `cloudformation:CreateStack` with `{"AWSTemplateFormatVersion":"2010-09-09","Resources":{"Writer":{"Type":"Custom::S3Writer","Properties":{"ServiceToken":"<that function ARN>","BucketName":"<bucket>","ObjectKey":"cr-object.txt","Body":"least-privilege-write-v1"}}}}`.
5. Poll `cloudformation:DescribeStacks` for a terminal `StackStatus`. Observed: it never leaves `CREATE_IN_PROGRESS`. Expected: `CREATE_COMPLETE` (with `s3:PutObject` granted) or `ROLLBACK_COMPLETE` with a `Writer` `CREATE_FAILED` event whose `ResourceStatusReason` names `AccessDenied` (without it).
6. For the positive control, `UpdateStack` the same template with a new `ObjectKey`/`Body` and poll for `UPDATE_COMPLETE`; for the negative control, `s3:HeadObject` the unwritten key and expect 404.
