# endusermessaging brand profiles: 3 net-new causes — UpdateBrandProfile accepts a no-op request with 200 instead of ValidationException, the brand-profile identifier resolver never rejects a malformed BrandProfileIdOrArn (404 instead of 400 ValidationException), and the DeletionProtection ConflictException message is emulator-authored prose

> _Note: this issue was identified against the code base at commit `b35089c281a7e84768d928c8c72034d27eee1ae8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateBrandProfile

## Description
Three independent root causes in the endusermessaging brand-profile control surface. The service is bootstrapped and serving — every cause below is a response the emulator actually produced, not a stub. The only open endusermessaging issues are the scaffold-stub issues (CreateBrandProfileAttributes, UpdateBrandProfileAttribute, ListTagsForResource, CreateNotifyCodeConfiguration, DeleteBrandProfileAttribute, ListBrandProfileAttributes, ListJobs, TagResource, ValidateNotifyCodeVerification), which cover different, unimplemented operations, plus 20261104T173700Z-endusermessaging-brand-profiles-2-net-new-causes-createbrandprofile.md — see Cause 3 for its relation to this issue.

=== Cause 1 of 3: UpdateBrandProfile with neither brandProfileName nor deletionProtectionEnabled is accepted with 200 instead of being refused with ValidationException ===
AWS: Smithy com.amazonaws.endusermessaging#UpdateBrandProfile — PUT /v1/brand-profiles/{brandProfileId+}, input members brandProfileName (BrandProfileName, optional) and deletionProtectionEnabled (Boolean, optional), with only brandProfileId @required; ValidationException is modeled on the operation (HTTP 400, httpError defaulted). Because both updatable members are individually optional, the model alone does not state the rule; recorded behavior only: AWS refuses an update request that carries no updatable member at all with 400 ValidationException and the message `At least one field must be provided for update`. That message is entirely fixed text for this error class — it contains no value from the request or from state. The refusal must also be total: the profile's name, deletionProtectionEnabled and updatedAt are unchanged, and a subsequent GetBrandProfile still reports the pre-call record.
Emulator: the handler resolves the id and then applies only the members that are present — both `if let Some(..)` arms are skipped — so a request with no updatable member falls through to the success path. The replay recorded HTTP 200 with the full profile body (brandProfileId, brandProfileArn, brandProfileName, status ACTIVE, deletionProtectionEnabled false, createdAt, updatedAt) and the check failed at `_error(...)` with "expected the call to be refused, but it succeeded". Worse, the no-op path still bumps `profile.updated_at = SystemTime::now()`, so a call AWS rejects outright mutates the record's updatedAt in the emulator.
Why: a client that builds an update from a diff and sends it unconditionally gets a silent 200 from the emulator and concludes the write was meaningful; against AWS the same call is a 400 it must handle. Validation-shape tests and SDK error-handling paths for this operation therefore never fire, and the spurious updatedAt bump makes any optimistic-concurrency or change-detection logic keyed on updatedAt see a modification AWS never recorded.
Fix: UpdateBrandProfile's input validation (services/.../src/ops/update_brand_profile.rs `handle`) — reject the request before resolving or touching state when neither brandProfileName nor deletionProtectionEnabled is present, returning ValidationException with AWS's fixed message, and leave updatedAt untouched on every refused path.
Traces: endusermessaging.update-brand-profile-rejects-request-with-no-fields.

=== Cause 2 of 3: the shared brand-profile identifier resolution never validates the BrandProfileIdOrArn FORMAT, so a syntactically invalid identifier is answered 404 ResourceNotFoundException instead of 400 ValidationException ===
AWS: Smithy BrandProfileIdOrArn (length 1..256, pattern ^[A-Za-z0-9_:/-]+$), documented on GetBrandProfile/UpdateBrandProfile/DeleteBrandProfile as "You can specify either the bare ID or the full Amazon Resource Name (ARN)". The member's pattern admits many strings that are neither a bare brand-profile id nor a brand-profile ARN, and AWS separates the two failure classes: a WELL-FORMED identifier that names nothing is 404 ResourceNotFoundException, while an identifier that is not an id-or-ARN at all is a format failure refused with 400 ValidationException whose message is `invalid brand profile ID format: <value>` — `invalid brand profile ID format: ` is the fixed text and `<value>` is the identifier taken verbatim from the request's brandProfileId path label. Recorded behavior confirms this: passing a brand profile's NAME (which satisfies the member pattern but is not an identifier) is refused with ValidationException, not with not-found. Resolution by bare id and by full ARN must still both succeed and return the identical record.
Emulator: resolution is a pure lookup. `state.rs::resolve_brand_profile_id` tries the value as a map key, then tries `brand_profile_id_from_arn`, and returns None for anything else; every caller renders that None as `brand_profile_not_found(..)`, i.e. 404 ResourceNotFoundException. There is no format check anywhere on the path, so the emulator cannot distinguish "well-formed but absent" from "not an identifier". Replay: GetBrandProfile called with the profile's name returned `ResourceNotFoundException: 'Brand profile <name> was not found.'` where AWS returns `ValidationException: invalid brand profile ID format: <name>`; the check failed at `assert code == "ValidationException"`. (ARN-vs-id resolution itself passed — the two reads agreed — so only the format-rejection half diverges.)
Why: the two classes mean opposite things to a client. A 404 says "this resource is gone" and drives retry-after-create, reconcile or treat-as-deleted logic; a 400 says "your identifier is malformed" and must never be retried. A caller that mistakenly passes a name (a very common SDK slip, since the name is the human-facing handle) is told by the emulator that the profile does not exist and may go on to re-create a profile that already exists, whereas AWS tells it the argument is wrong. Any client that keys on error code to decide retryability inverts its decision here.
Fix: the shared brand-profile identifier handling — `crate::state::resolve_brand_profile_id` / its callers in get_brand_profile.rs, update_brand_profile.rs and delete_brand_profile.rs — must classify the identifier before looking it up: a value that is neither a bare brand-profile id nor a well-formed brand-profile ARN is a ValidationException carrying AWS's message template with the request's value interpolated; only a well-formed identifier that resolves to nothing becomes ResourceNotFoundException. Apply it uniformly to every operation taking a BrandProfileIdOrArn so the classification does not depend on which operation was called.
Traces: endusermessaging.get-brand-profile-accepts-arn-and-rejects-name-as-identifier.

=== Cause 3 of 3: DeleteBrandProfile's deletion-protection ConflictException carries an emulator-authored sentence instead of AWS's message template ===
AWS: Smithy declares ConflictException (HTTP 409; members message @required, resourceId, resourceType) on DeleteBrandProfile. The status and error code the emulator returns are right; the message is not. AWS words this refusal with fixed text only: `Conflict occurred - Reason="DELETION_PROTECTION_ENABLED" ResourceType="brand-profile"`. Every part is fixed for this error class — `Conflict occurred - Reason=` and `ResourceType=`, the reason token DELETION_PROTECTION_ENABLED naming the state that caused the conflict, and the resource type `brand-profile` in AWS's hyphenated vocabulary. No request-supplied value appears in it; in particular the brandProfileId does NOT. The same wording is this service's convention across resources, with only the type token changing (the notify-code-configuration checks assert ResourceType="notify-code-configuration"), and the rule holds regardless of how the profile became protected — including a profile created protected and then RENAMED, which must keep its protection and keep refusing the delete with the same message.
Emulator: DeleteBrandProfile's protected branch answers 409 ConflictException with its own sentence `Brand profile <id> cannot be deleted while deletion protection is enabled.` — different fixed text, and it interpolates the brand profile id AWS's conflict message does not contain. Replay, reached through the rename path (UpdateBrandProfile renamed a protected profile, Get and List correctly showed the new name and deletionProtectionEnabled stayed true): the delete was refused with `ConflictException: 'Brand profile <id> cannot be deleted while deletion protection is enabled.'` and the check failed at `assert message == ...`. The bp-… value in the replay output is this run's minted id and is not part of any requirement; the divergence is the whole template plus the presence of an id at all. The error struct also reports resourceType as the uppercase `BRAND_PROFILE` (state.rs BRAND_PROFILE_RESOURCE_TYPE) while AWS's own message for this service spells it `brand-profile`.
RELATION TO AN EXISTING OPEN ISSUE: 20261104T173700Z-endusermessaging-brand-profiles-2-net-new-causes-createbrandprofile.md describes this same message defect as its Cause 2, grounded in endusermessaging.brand-profile-deletion-protection-blocks-then-allows-delete. That issue does not carry the replay key for the check below, so the rename-under-protection check is reported here; a fixer that has already corrected the brand-profile refusal templates for that issue should re-replay this check to confirm the rename path is covered too, and close this cause without a second edit if it is.
Why: operators, support tooling, runbooks and test suites match on refusal text, and a client that reads `Reason="..."` out of the conflict message to tell deletion protection apart from other 409 conflicts finds no Reason token at all and cannot classify the conflict. The uppercase resourceType means a client switching on that member against AWS's vocabulary never matches.
Fix: DeleteBrandProfile's deletion-protection refusal construction and the service's shared brand-profile error constructors (delete_brand_profile.rs conflict branch; state.rs BRAND_PROFILE_RESOURCE_TYPE and brand_profile_not_found) must emit AWS's templates, with the resource-type token — and, for not-found, the request's identifier — as the only variable parts, and must report resourceType in the same hyphenated vocabulary the message uses.
Traces: endusermessaging.rename-brand-profile-under-deletion-protection-keeps-protection.

## Steps to Reproduce
Cause 1 (UpdateBrandProfile no-op accepted):
1. POST /v1/brand-profiles with {"brandProfileName": "<any name matching ^[A-Za-z0-9_ -]*[A-Za-z0-9_-][A-Za-z0-9_ -]*$"}; note brandProfileId.
2. PUT /v1/brand-profiles/{brandProfileId} with an empty JSON body (SDK: update_brand_profile(brandProfileId=bpid) and nothing else).
3. Emulator answers 200 with the full profile record; AWS answers 400 ValidationException with Error.Message `At least one field must be provided for update`.
4. GET /v1/brand-profiles/{brandProfileId} and compare updatedAt with the value from step 1 — the emulator advanced updatedAt on the call AWS refused.
5. Positive control (must keep working): PUT with {"brandProfileName": "<new name>"} applies the rename.

Cause 2 (malformed identifier misclassified):
1. POST /v1/brand-profiles with {"brandProfileName": "<name with no spaces, e.g. eum-ident-test>"}; note brandProfileId and brandProfileArn.
2. GET /v1/brand-profiles/{brandProfileId} and GET /v1/brand-profiles/{brandProfileArn} — both return the same record (this already works).
3. GET /v1/brand-profiles/{the brandProfileName from step 1}. The emulator answers 404 ResourceNotFoundException `Brand profile <name> was not found.`; AWS answers 400 ValidationException `invalid brand profile ID format: <name>`.
4. The same misclassification is reachable through UpdateBrandProfile and DeleteBrandProfile with the same identifier, since all three share resolve_brand_profile_id.

Cause 3 (conflict message text):
1. POST /v1/brand-profiles with {"brandProfileName": "<any valid name>", "deletionProtectionEnabled": true}; note brandProfileId.
2. PUT /v1/brand-profiles/{brandProfileId} with {"brandProfileName": "<a different valid name>"} — the rename applies and deletionProtectionEnabled stays true (correct).
3. DELETE /v1/brand-profiles/{brandProfileId}. The response is 409 ConflictException (correct) but Error.Message is `Brand profile <id> cannot be deleted while deletion protection is enabled.` instead of AWS's `Conflict occurred - Reason="DELETION_PROTECTION_ENABLED" ResourceType="brand-profile"`, and Error.resourceType is `BRAND_PROFILE` instead of `brand-profile`.
4. PUT {"deletionProtectionEnabled": false}, DELETE (succeeds), then GET /v1/brand-profiles/{brandProfileId}: 404 ResourceNotFoundException (correct) with message `Brand profile <id> was not found.` instead of `Resource not found - ResourceType="brand-profile" ResourceId="<id>"` — the same shared constructor.
