# cloudformation__kinesis: an in-place property update of AWS::Kinesis::Stream is refused with emulator-authored NotImplemented prose, so the stack rolls back to UPDATE_ROLLBACK_COMPLETE

> _Note: this issue was identified against the code base at commit `94350cf775acbc496950503935930c48964de18f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateStack

## Description
One net-new root cause in the CloudFormation resource provider for AWS::Kinesis::Stream. It is grounded in the only failing check the replay report lists under `### cloudformation__kinesis` that is marked NEITHER "ALREADY FILED" nor "OWNED by"; every other failure under that heading is owned by 20261109T214127Z-cloudformation-kinesis-4-net-new-causes-aws-kinesis.md, which carries none of this check's ids and reports a different class of gap (unregistered Channel/ResourcePolicy types, missing VALIDATION_ERROR diagnostics, Outputs with no OutputValue), so it does not cover this. Open issues 20261111T003921Z-cloudformation-ecr-an-in-place-update-of-aws.md (AWS::ECR::Repository), 20261110T214424Z-apigateway-cloudformation-an-in-place-update-of-aws.md (AWS::ApiGateway::RestApi) and 20261111T003921Z-cloudformation-iam-sts-reopens-the-aws-iam-role.md (AWS::IAM::Role) report the same CLASS of refusal for other resource types and carry none of this check's ids; this one is the AWS::Kinesis::Stream provider.

=== Cause 1 of 1: UpdateStack changing an updatable (no-interruption) property of AWS::Kinesis::Stream fails the resource with a NotImplemented reason instead of performing the update ===
AWS: recorded behavior only for the CloudFormation resource schema (CloudFormation's resource-type registry is not in the Smithy model). AWS::Kinesis::Stream's RetentionPeriodHours, ShardCount, StreamModeDetails, StreamEncryption and Tags are all update-without-interruption properties; only Name is create-only and forces a replacement. An UpdateStack whose template changes only RetentionPeriodHours (24 -> 48) on an existing stream is therefore applied IN PLACE: the stack settles in UPDATE_COMPLETE, the resource's events for that logical id are exactly UPDATE_IN_PROGRESS then UPDATE_COMPLETE with no replacement announcement, the PhysicalResourceId on the final event is unchanged (it is still the stream's Name), and the stream itself is mutated rather than recreated — DescribeStreamSummary reports the new RetentionPeriodHours with StreamStatus ACTIVE, the same StreamARN, the same OpenShardCount and EncryptionType, and every record put before the update is still readable from the shard. The Kinesis API that backs this is modeled: Smithy IncreaseStreamRetentionPeriod(StreamName/StreamARN, RetentionPeriodHours required) and DecreaseStreamRetentionPeriod, with errors AccessDeniedException / InvalidArgumentException / LimitExceededException / ResourceInUseException / ResourceNotFoundException — so the capability the stack update needs exists in the service surface.
Emulator: the UpdateStack is accepted, but the resource update fails. The stack settles in `UPDATE_ROLLBACK_COMPLETE` with StackStatusReason `The following resource(s) failed to update: [Stream]. `, and the logical resource emits an `UPDATE_FAILED` event whose ResourceStatusReason is the emulator-authored sentence `NotImplemented: this emulator does not change the properties of an existing AWS::Kinesis::Stream in place; the resource was left as it is.` No AWS error class, status or message uses that wording — it is invented prose, not a refusal AWS can produce for this update, and it names the emulator in client-visible stack output. In this reason only the bracketed logical id list in the stack reason (`[Stream]`) is a value from the request; the whole NotImplemented sentence is fixed emulator text that must not exist at all.
Why: a client cannot evolve a template-managed Kinesis stream at all. Any `cloudformation update-stack` / `cdk deploy` / `sam deploy` that tweaks RetentionPeriodHours, ShardCount, StreamModeDetails, encryption or Tags on an already-deployed stream rolls the whole stack back, so unrelated resources in the same stack are reverted too; a client reading the failure reason is told its deploy is impossible rather than that the retention change is supported. Because the update fails at step 2, the rest of the documented lifecycle is left entirely ungraded by this check: the Name-change replacement under `UpdateReplacePolicy: Retain` (which must announce `Requested update requires the creation of a new physical resource; hence creating one.`, complete on the NEW stream name as PhysicalResourceId, emit exactly `DELETE_SKIPPED` for the old name, re-resolve `Fn::GetAtt Stream.Arn` to the new stream's ARN, and leave the old stream ACTIVE and still holding its pre-replacement record), and the post-DeleteStack refusal where DescribeStreamSummary on the stack's stream must answer `ResourceNotFoundException` with `Stream <name> under account <account> not found.` (fixed text with the stream name and the caller's account id substituted). Those paths may hold further divergences that cannot be observed until the in-place update works.
Fix: the CloudFormation service crate's resource provider for AWS::Kinesis::Stream — its update path. Implement the no-interruption update for the updatable properties by diffing the old and new property sets and calling the corresponding Kinesis handlers (IncreaseStreamRetentionPeriod / DecreaseStreamRetentionPeriod for RetentionPeriodHours, UpdateShardCount for ShardCount, UpdateStreamMode for StreamModeDetails, Start/StopStreamEncryption, the tagging handlers for Tags), keep the PhysicalResourceId, and emit UPDATE_IN_PROGRESS/UPDATE_COMPLETE for the resource; treat only Name as create-only and route it through the replacement path. Remove the NotImplemented sentence from the provider's event-reason text entirely rather than rewording it.
Traces: cloudformation__kinesis.cfn-kinesis-stream-in-place-update-retained-replacement-then-not-found.
