# MSK retention/TTL data-plane checks are blocked by non-own bootstrap hosts, and the CREATING-state replicator guard and the UpdateTopic/RebootBroker sequence reach no verdict (3 causes)

> _Note: this issue was identified against the code base at commit `62c10db90cd2a20a5f435ff8fb900c0be39c8c7e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetBootstrapBrokers

## Description
THREE distinct root causes in the kafka service, all grounded in failing behavioral checks that the suite marked neither ALREADY FILED nor OWNED. Each must be closed separately before this issue is submitted.

Cause 1 of 3: the bootstrap endpoints the emulator publishes for a provisioned MSK cluster are real, public AWS broker DNS names the emulator does not serve, so the topic-retention / TTL data-plane family can never open a connection. (4 failing checks: kafka.topic-retention-config-echoed-over-scram-message-readable, kafka.topic-retention-ms-config-echoed-with-broker-sweep-interval, kafka.topic-retention-ms-expires-old-messages, kafka.topic-retention-ttl-expiry-hides-old-messages.)
AWS: Smithy GetBootstrapBrokers (GET /v1/clusters/{ClusterArn}/bootstrap-brokers, code 200; output members BootstrapBrokerString, ...Tls, ...SaslScram, ...SaslIam and their Public*/VpcConnectivity*/Ipv6 siblings, each a comma-separated list of host:port pairs; errors BadRequestException 400, ConflictException 409, ForbiddenException 403, UnauthorizedException 401, InternalServerErrorException 500). The contract of those strings is that each announced host:port is an address the service itself accepts a Kafka wire-protocol connection on: a client takes the string verbatim, connects, completes the SASL handshake, then reads topic configuration with DescribeConfigs and produces/fetches records, so that retention.ms / segment.ms / cleanup.policy applied through CreateTopic+UpdateTopic (Smithy: DescribeTopic.Configs and UpdateTopic.Configs are Base64 topic configuration strings; TopicState enum CREATING|UPDATING|DELETING|ACTIVE) can be observed on the broker and the retention sweep can be seen to drop expired records. The DNS shape of AWS's own names is an implementation detail; what is required is that the published address is the one the caller can reach the broker on. (Model contributes the member shapes; the data-plane consequence is recorded behavior.)
Emulator: the broker strings are synthesised as public AWS-domain names that belong to AWS and that this emulator neither owns nor answers on, of the form `b-<n>.<cluster-name>-<id>.<suffix>.c<n>.kafka.<region>.amazonaws.com:<port>`. Every one of these four checks is refused before a byte leaves the runner, with `simparity.published.PublishedUrlRejected: endpoint_host was given <published host>:<port> (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs an own host[:port]: the endpoint host, a documented own host or, for a loopback endpoint, a loopback address`. The cluster names, 12-hex ids, suffixes and the port in any single replay are per-run values and are not the requirement — the defect is that the announced host is not an address of the emulator at all. This is the emulator's own egress gap: it announced an address other than the one it is reached on.
Why: a client configured from GetBootstrapBrokers points its admin client, producer and consumer at a name that resolves to AWS or to nothing instead of to the emulator, so topic-level retention configuration cannot be read back over the native protocol, a freshly produced record cannot be read from the earliest offset, and retention expiry (the broker's log.retention.check.interval.ms sweep hiding records past retention.ms) cannot be observed at all. MSK's time-to-live semantics are unverifiable beyond the control plane.
Fix: the kafka service's endpoint publication — the GetBootstrapBrokers handler's broker-string assembly must emit a host:port the emulator itself answers on, and the broker listener behind it (per-scheme SASL authentication, topic config, record log and retention sweep) must accept connections there.
Traces: kafka.topic-retention-config-echoed-over-scram-message-readable, kafka.topic-retention-ms-config-echoed-with-broker-sweep-interval, kafka.topic-retention-ms-expires-old-messages, kafka.topic-retention-ttl-expiry-hides-old-messages. The open issue 20261109T211434Z-kafka-msk-bootstrap-endpoints-are-published-as-real-aws.md describes the same publication defect but carries 22 OTHER check ids and none of these four replay keys (the suite reports all four unowned); the neighbouring open issues 20261104T171616Z-kafka-no-kafka-broker-answers-on-the-advertised-bootstrap.md and 20261107T210159Z-kafka-three-more-msk-data-plane-checks-reach-no.md likewise do not carry them. 20261104T171616Z-kafka-getbootstrapbrokers-serves-every-broker-string-variant-regardless-of.md is a different defect (WHICH members are populated, not what host they name).

Cause 2 of 3: the CREATING-state guard sequence for UpdateStorage/UpdateRebalancing plus the replicator's CREATING -> RUNNING transition never reaches a verdict. (1 failing check: kafka.cluster-replicator-updates-blocked-while-creating-rejected.)
AWS: Smithy UpdateStorage (PUT /v1/clusters/{ClusterArn}/storage, required currentVersion, VolumeSizeGB; errors BadRequestException 400, NotFoundException 404) and UpdateRebalancing (PUT /v1/clusters/{ClusterArn}/rebalancing, required currentVersion and rebalancing; same error set) are refused on a cluster that is not ACTIVE with HTTP 400 BadRequestException and the message `This operation is only valid for resources that are in one of the following states :[ACTIVE]` — entirely fixed text, with only the state list taken from the operation's allowed states; the cluster's CurrentVersion is unchanged. Once DescribeClusterV2 reports State ACTIVE (Smithy ClusterState enum ACTIVE|CREATING|DELETING|FAILED|HEALING|MAINTENANCE|REBOOTING_BROKER|UPDATING) the same two calls are accepted and return a ClusterOperationArn whose DescribeClusterOperationV2 progresses to UPDATE_COMPLETE. CreateReplicator returns ReplicatorState CREATING (Smithy ReplicatorState enum RUNNING|CREATING|UPDATING|DELETING|FAILED) and DescribeReplicator settles to RUNNING; UpdateReplicationInfo (PUT /replication/v1/replicators/{ReplicatorArn}/replication-info, required currentVersion) on a replicator that is not RUNNING is refused 400 BadRequestException `Invalid parameter replicatorArn: This operation is only valid for resources that are in one of the following states: [RUNNING]` (fixed text apart from the member name and the state list), and on a RUNNING replicator it is accepted and bumps CurrentVersion.
Emulator: the check produces no verdict at all — the only detail is `Error: Check timed out after 60.0s`, with no HTTP status, no error code and no traceback frame, so neither refusal message nor either positive control was ever evaluated. The sequence it walks is: two CreateCluster calls, the two CREATING-state refusals, then _wait_for_clusters_active (DescribeClusterV2 at 20 s), UpdateStorage on the ACTIVE cluster, _wait_for_operation (DescribeClusterOperationV2 at 20 s until UPDATE_COMPLETE), CreateReplicator, the CREATING refusal, then _wait_for_replicator_state until RUNNING (20 s). Hypothesis (not stated by the replay output): one of the cluster's CREATING -> ACTIVE transition, the UPDATE_STORAGE operation's progress to UPDATE_COMPLETE, or the replicator's CREATING -> RUNNING transition never reaches its terminal value, so each poll runs to its deadline instead of paying one interval.
Why: a client that provisions a cluster, grows its storage and then builds a replicator hangs on its own waiter; both the ACTIVE-only guard on UpdateStorage/UpdateRebalancing and the RUNNING-only guard on UpdateReplicationInfo, together with the positive controls that prove those refusals were state guards and not malformed requests, are unverifiable.
Fix: the kafka service's state layer — the cluster, cluster-operation and replicator state machines behind CreateCluster / UpdateStorage / UpdateRebalancing / DescribeClusterOperationV2 / CreateReplicator / DescribeReplicator / UpdateReplicationInfo must settle to ACTIVE, UPDATE_COMPLETE and RUNNING on a cadence a first or second probe observes.
Traces: kafka.cluster-replicator-updates-blocked-while-creating-rejected. The open issue 20261110T144707Z-kafka-five-msk-lifecycle-families-still-reach-no-verdict.md describes the replicator-never-RUNNING family for five OTHER check ids and does not carry this check's replay key (the suite reports it unowned); 20261105T161551Z-kafka-two-more-msk-checks-never-reach-a-verdict.md and 20261105T161551Z-kafka-msk-cluster-state-guard-on-updatebrokerstorage-updatemonitoring-updatesecurity.md likewise cover other ids.

Cause 3 of 3: the UpdateTopic -> RebootBroker -> UpdateTopic sequence reaches no verdict, because the topic never becomes observably ACTIVE (and/or the reboot operation never settles). (1 failing check: kafka.update-topic-controller-moved-exception.)
AWS: Smithy CreateTopic/DescribeTopic (GET /v1/clusters/{ClusterArn}/topics/{TopicName}; output Status is TopicState CREATING|UPDATING|DELETING|ACTIVE) report a new topic as CREATING and then ACTIVE — MSK documents the topic APIs as reflecting data that updates approximately every minute. UpdateTopic (PUT /v1/clusters/{ClusterArn}/topics/{TopicName}, Configs a Base64 topic-configuration string; errors include BadRequestException 400, ControllerMovedException 409, NotControllerException 409, KafkaTimeoutException 409, UnknownTopicOrPartitionException 404) on an ACTIVE topic of a healthy cluster persists the new config, which DescribeTopic then echoes. RebootBroker (PUT /v1/clusters/{ClusterArn}/reboot-broker, required brokerIds) returns a ClusterOperationArn that progresses to UPDATE_COMPLETE with the cluster passing through REBOOTING_BROKER back to ACTIVE, and afterwards UpdateTopic still succeeds and the newly set retention.ms is readable from DescribeTopic.
Emulator: the check produces no verdict at all — the only detail is `Error: Check timed out after 60.0s`, with no status, error code or frame; the first assertion is never reached. It polls _topic_status(DescribeTopic) at 10 s for ACTIVE before the first UpdateTopic. Hypothesis (not stated by the replay output): the created topic never leaves CREATING on the emulator's read path (and/or the RebootBroker cluster operation never reaches UPDATE_COMPLETE with the cluster returning to ACTIVE), so the poll runs out rather than settling.
Why: a client that creates a topic and waits for it to be usable before configuring it never gets a terminal status, so topic-config persistence across a broker reboot — and the whole UpdateTopic-after-reboot contract — cannot be exercised.
Fix: the kafka service's topic and cluster-operation state in the CreateTopic / DescribeTopic / UpdateTopic / RebootBroker handlers must settle topic Status CREATING -> ACTIVE and the reboot operation to UPDATE_COMPLETE with the cluster back to ACTIVE.
Traces: kafka.update-topic-controller-moved-exception. The open issue 20261111T191205Z-kafka-updatetopic-is-accepted-while-a-broker-is.md covers a different UpdateTopic-during-reboot defect (a missing replication-factor-vs-available-brokers refusal) for another check id and does not carry this check's replay key; 20261029T175822Z-kafka-updatetopic-stub.md is a stub issue for the operation itself.
