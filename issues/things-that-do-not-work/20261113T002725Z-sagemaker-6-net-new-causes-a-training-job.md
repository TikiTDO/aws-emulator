# sagemaker: 6 net-new causes — a training job reports Completed no matter what its container did (non-zero exit ignored, MaxRuntimeInSeconds not enforced, SecondaryStatus skips every active-container phase), and InvokeEndpoint scores an unsupported ContentType and mis-frames a batched CSV response

## Description

Cause 1 of 6 — a training job whose algorithm container exits non-zero is reported Completed with no FailureReason.
AWS: Smithy: DescribeTrainingJob.TrainingJobStatus is enum com.amazonaws.sagemaker#TrainingJobStatus = InProgress|Completed|Failed|Stopping|Stopped|Deleting, and SecondaryStatus is enum com.amazonaws.sagemaker#SecondaryStatus which includes the terminal value Failed. When the algorithm container exits with a non-zero status (entrypoint overridden to /bin/false, or a container that exits 7), SageMaker ends the job with TrainingJobStatus=Failed, SecondaryStatus=Failed and a FailureReason of the form "AlgorithmError: <tail of the container's stderr>, exit code: <the container's exit status>" — the fixed text is "AlgorithmError: " and ", exit code: "; the stderr tail and the exit code are values taken from the run, never literals.
Emulator: both jobs end TrainingJobStatus='Completed', SecondaryStatus='Completed', FailureReason=None (absent). The container's exit status is not consulted at all: a job that cannot possibly have produced a model is reported as a success.
Why: a client that polls to Completed and then publishes/deploys ModelArtifacts cannot distinguish a real training run from a container that failed immediately; every failure-handling branch (retry, alarm, pipeline abort) is dead code against this emulator, and nothing ever populates FailureReason for a client that parses the AlgorithmError form.
Fix: the training-job execution/state component behind DescribeTrainingJob (the job state machine driven from the CreateTrainingJob handler) must propagate the container's exit status into TrainingJobStatus=Failed and render FailureReason in AWS's AlgorithmError form rather than settling every job Completed.
Traces: sagemaker.training-job-server-managed-status-progression, sagemaker.secondary-status-transitions-follow-canonical-phase-order-and-attribute-failure.

Cause 2 of 6 — SecondaryStatus never visits any active-container phase; the first DescribeTrainingJob after CreateTrainingJob is already terminal.
AWS: Smithy: SecondaryStatus enumerates the non-terminal phases Starting, LaunchingMLInstances, PreparingTrainingStack, Downloading, DownloadingTrainingImage, Training, Uploading before the terminal Completed, and DescribeTrainingJob.SecondaryStatusTransitions records each phase actually visited, in that relative order, each at most once. A job polled from creation is observable in at least one active-container phase (Starting/Downloading/Training/Uploading) while TrainingJobStatus=InProgress.
Emulator: a poller that starts immediately after CreateTrainingJob never observes an active phase — the job leaves InProgress already terminal (status=Completed, secondary=Completed), so no phase is ever reported.
Why: any client that keys work off a phase (waiting for Training before attaching a metric stream, or asserting an artifact upload happened during Uploading) sees that phase never occur; the lifecycle looks instantaneous and unobservable, which no AWS training job is. 20261108T214320Z-s3-sagemaker-a-training-job-is-already-past.md reports the same symptom from the s3__sagemaker suite but does not own this check's key.
Fix: the training-job state machine behind DescribeTrainingJob must publish the intermediate SecondaryStatus values and their SecondaryStatusTransitions entries while the job is InProgress, instead of jumping straight to a terminal pair.
Traces: sagemaker.algorithm-delete-allowed-while-referenced.

Cause 3 of 6 — StoppingCondition.MaxRuntimeInSeconds is not enforced.
AWS: Smithy: StoppingCondition.MaxRuntimeInSeconds (range min 1) is documented as "if the job does not complete during this time, SageMaker ends the job", with a 120 s SIGTERM grace for artifact saving; SecondaryStatus carries the dedicated terminal value MaxRuntimeExceeded. A job whose container asks for far more runtime than the cap is ENDED by SageMaker: TrainingJobStatus is Stopped (or Failed), the cap is attributed via SecondaryStatus=MaxRuntimeExceeded, the SecondaryStatusTransitions trail or FailureReason, the job is granted its allotted runtime first (TrainingEndTime - CreationTime >= the cap) and is cut off after it (TrainingEndTime - TrainingStartTime <= cap + grace); a twin job well inside the same cap reaches Completed with no MaxRuntimeExceeded attribution anywhere, and ListTrainingJobs agrees with DescribeTrainingJob for both.
Emulator: the job that asks for 1800 s of container work under a 300 s cap reports TrainingJobStatus='Completed', SecondaryStatus='Completed' — identical to its inside-the-cap twin. The cap is never applied and MaxRuntimeExceeded is never produced.
Why: MaxRuntimeInSeconds is a cost-control guardrail; a client that relies on it to bound a runaway job gets no enforcement and no distinguishable terminal state, and a client that detects runaway jobs by looking for MaxRuntimeExceeded never sees it.
Fix: the training-job state machine behind DescribeTrainingJob must honour StoppingCondition.MaxRuntimeInSeconds, ending an over-running job in Stopped/Failed with MaxRuntimeExceeded attribution and timestamps bounded by the cap (the handler that stores StoppingCondition, plus the component that settles the job).
Traces: sagemaker.max-runtime-in-seconds-stops-the-job-and-a-twin-inside-the-limit-completes.

Cause 4 of 6 — InvokeEndpoint accepts a ContentType the model container does not support and scores the payload anyway.
AWS: an InvokeEndpoint whose ContentType is not among the container's supported media types is refused BY THE CONTAINER and passed through by SageMaker as error code ModelError at HTTP 424 Failed Dependency, with the container's own status and text preserved: OriginalStatusCode=415, OriginalMessage = "Content-type <the requested content type> not supported. Supported content-type is <the container's supported list>" and Message = "Received client error (<the container's status>) from model with message \"<OriginalMessage>\". See https://<region>.console.aws.amazon.com/cloudwatch/home?region=<region>#logEventViewer:group=/aws/sagemaker/Endpoints/<EndpointName> in account <account id> for more information." — the fixed text is "Received client error (", ") from model with message \"", "\". See ", "#logEventViewer:group=/aws/sagemaker/Endpoints/", " in account " and " for more information."; the status, the container text, the region, the endpoint name and the account id are values from the request, the container and the environment. Message and OriginalMessage are necessarily different (one wraps the other). The endpoint is unaffected: it stays InService with no FailureReason and serves the identical prediction for the identical valid request afterwards.
Emulator: the same call SUCCEEDS with HTTP 200 and an inference body (a scored value), so no error code, status or message exists at all for the class.
Why: a client that probes content-type support, or that surfaces 424/ModelError to a caller as 'your payload was the wrong media type', gets a plausible-looking prediction computed from bytes the real container would never have parsed — silent wrong output instead of a classifiable refusal.
Fix: the InvokeEndpoint data-plane handler / the emulated model container must validate the request ContentType against the serving container's supported media types and refuse with 424 ModelError, populating OriginalStatusCode and OriginalMessage and wrapping the container text as above.
Traces: sagemaker.sagemaker-invoke-with-an-unsupported-content-type-rejected-by-the-model-container.

Cause 5 of 6 — a multi-row CSV InvokeEndpoint response is framed one prediction per LINE instead of one comma-separated line.
AWS: recorded behavior only (the framing is the built-in container's, not the Smithy model's): a text/csv InvokeEndpoint body carrying N rows returns ONE line containing N comma-separated predictions, in input row order, each equal to the prediction the same row returns when sent alone — there is no newline in the response body.
Emulator: the two-row request "0.5000,0.5000\n9.5000,9.5000" returns '2.5\n47.5' — newline-separated, one field per line.
Why: a client that splits a batched response on ',' (the AWS framing) reads a single malformed field and either crashes on float parsing or mis-pairs predictions to input rows; batch scoring silently produces one value where N were expected.
Fix: the InvokeEndpoint data-plane response serialization for the CSV accept/content type (the emulated container's response framing), which must join per-row predictions with ',' rather than '\n'.
Traces: sagemaker.sagemaker-endpoint-prediction-is-deterministic-and-ordered-in-its-input.

Cause 6 of 6 — the Inference-Recommender flow does not settle, so GetScalingConfigurationRecommendation is unreachable within the replay budget.
AWS: Smithy: DescribeInferenceRecommendationsJob.Status reaches a terminal COMPLETED for a Default job that benchmarked a caller-owned endpoint; that job then lists the endpoint under EndpointPerformances[].EndpointInfo.EndpointName, and GetScalingConfigurationRecommendation(InferenceRecommendationsJobName, EndpointName) echoes both and returns a DynamicScalingConfiguration with MinCapacity >= 1 and MaxCapacity >= MinCapacity.
Emulator: the check never gets an answer — it is cut off by the replay budget ("Check timed out after 60.0s") while polling this train -> model -> endpoint -> InvokeEndpoint -> CreateInferenceRecommendationsJob -> DescribeInferenceRecommendationsJob sequence, so no terminal Status, no EndpointPerformances entry and no recommendation is ever observed. Hypothesis: one of the polled resources in that chain (most likely the inference-recommendations job) is left non-terminal, so each poll interval is paid without the condition ever becoming true; the sibling check sagemaker.scaling-configuration-recommendation-for-existing-endpoint (owned by 20261030T171442Z) shows the same operation pair failing to produce a completed job.
Why: an autoscaling consumer that benchmarks an existing endpoint and then asks for a scaling recommendation hangs instead of receiving one; the operation pair is effectively unusable.
Fix: the CreateInferenceRecommendationsJob handler and its job state component must drive the job to a terminal Status (recording the caller-supplied endpoint under EndpointPerformances), and GetScalingConfigurationRecommendation must answer from that completed job.
Traces: sagemaker.get-scaling-configuration-recommendation-references-endpoint.
