=== Cause 1 of 2: FinalBakeTimeInMinutes does not pace the bake window — every non-zero bake lasts one flat 3-second span, so a declared 1-minute bake costs ~3s of real time ===
AWS: Smithy (appconfig) CreateDeploymentStrategy.FinalBakeTimeInMinutes -> MinutesBetween0And24Hours, range 0..1440, default 0; GetDeployment/Deployment project FinalBakeTimeInMinutes, State (DeploymentState enum incl. BAKING, COMPLETE), PercentageComplete (Percentage 1..100), StartedAt/CompletedAt (Iso8601DateTime) and EventLog (DeploymentEvents). The bake is the time AppConfig monitors the configuration AFTER it has reached 100% of targets and BEFORE the deployment is COMPLETE, so the window is bounded BELOW by the declared minutes: a deployment that entered BAKING with FinalBakeTimeInMinutes=N stays non-terminal for at least N minutes, and AppConfig's own timestamps say the same thing (CompletedAt minus the BAKE_TIME_STARTED event's OccurredAt >= N minutes). The model documents no scheduling granularity, so only the lower bound is a requirement; the declared minutes themselves are the requirement, not any emulator-chosen span. No error or message is involved in this cause.
Emulator: with FinalBakeTimeInMinutes=1 the deployment does enter BAKING at PercentageComplete=100.0 and logs BAKE_TIME_STARTED once, but it reaches COMPLETE after ~3 seconds: the check measured 4.9s between first observing BAKING and observing COMPLETE against a required >= 60s (its only slack is one 3.0s poll interval + 1.0s). This is by construction in the checkout: services/service-com-amazonaws-appconfig-amazonappconfig/src/state.rs defines `pub const STAGE_DURATION: Duration = Duration::from_secs(3)` (line 1032, documented at lines 1011-1031 as 'the EMULATOR's span, not a documented one') and `stage_duration(minutes)` (lines 1039-1045) returns that SAME 3-second span for ANY minutes > 0 and ZERO otherwise. `Deployment::bake_duration` (line 2833) is `stage_duration(self.final_bake_time_in_minutes)`, and `completion_due` = rollout_end + bake_duration (line 2844), so FinalBakeTimeInMinutes is used only as a zero/non-zero flag: 1 minute, 30 minutes and 1440 minutes all bake for 3 seconds. The declared value is still echoed back verbatim in the strategy and the deployment, which is why the divergence is invisible to a reader of the record.
Why: a client that sets a bake time to buy itself an abort/verification window gets ~3 seconds of it. Post-deploy verification that runs during BAKING races the completion; a CloudWatch-alarm or extension-driven rollback has essentially no window to fire in; a client that computes a deadline from FinalBakeTimeInMinutes sees the deployment terminal long before it should be; and CompletedAt - BAKE_TIME_STARTED.OccurredAt understates the declared window by orders of magnitude, so any audit of how long a configuration was monitored is wrong.
Fix: the deployment state machine's clock in the appconfig state crate — the stage-pacing helper and the bake span derived from it (stage_duration / Deployment::bake_duration / rollout_duration / completion_due), which must derive the window from the strategy's declared minutes rather than from a single flat constant. GetDeployment's materialize path then reports BAKING for the whole declared window and COMPLETE only once it has elapsed.
Traces: appconfig.final-bake-time-window-holds-the-deployment-non-terminal.

=== Cause 2 of 2: deleting a deployed environment never withdraws it from the appconfigdata data plane — a token minted before the deletion polls 200 indefinitely instead of being refused ===
AWS: AppConfigData sessions are over LIVE control-plane state. Once the environment a session polls is deleted (appconfig DeleteEnvironment; afterwards GetEnvironment answers ResourceNotFoundException and the environment is absent from ListEnvironments), the data plane withdraws it: GetLatestConfiguration presented with a token minted BEFORE the deletion is refused with ResourceNotFoundException, HTTP 404. Smithy (appconfigdata): GetLatestConfiguration is GET /configuration (200), input ConfigurationToken (@httpQuery configuration_token, @required, pattern ^\S{1,8192}$), errors BadRequestException 400, InternalServerException 500, ResourceNotFoundException 404, ThrottlingException 429; ResourceNotFoundException carries Message, ResourceType (enum Application | ConfigurationProfile | Deployment | Environment | Configuration) and ReferencedBy (StringMap, 'a map indicating which parameters in the request reference the resource that was not found'). For a deleted environment the refusal carries ResourceType 'Environment' and ReferencedBy naming the session/request member that referenced it. The message's fixed text is the service's own not-found sentence; its variable parts are the identifier values taken from the session/request — never one run's literal ids. That the withdrawal is not instantaneous is recorded behavior only (the check polls for the refusal with a 300s budget rather than assuming it is immediate).
Emulator: the refusal never arrives on the poll path, so the bounded poll never converges and the check is killed by the harness — reported verdict 'Error: Check timed out after 60.0s'. Verified in the checkout: services/service-com-amazonaws-appconfigdata-appconfigdata/src/ops/get_latest_configuration.rs STEP 2 (module comment at lines 379-402, code at lines 403-438) re-reads the control plane only to pick up a NEWER deployment, and on Err(unresolved) returns `Arc::clone(bound)` whenever session.bound_configuration is Some(..), raising the modeled ResourceNotFoundException only when it is None; every poll re-binds the successor token to what it just served, so the chain never degrades to None and the deleted environment's bytes are served with HTTP 200 forever. StartConfigurationSession DOES resolve the triple and refuse, so the divergence is confined to the poll path.
Why: a long-polling client is served a deleted resource's configuration indefinitely and never learns its environment was removed, so withdrawn configuration keeps being applied; a configuration token becomes a permanent grant on deleted state, a capability AWS revokes. Because the divergence is a never-terminating poll rather than a wrong value, it also costs the rest of the check: the positive controls after it (the sibling environment still serving its exact bytes, proving the refusal is scoped to the deleted environment and not an endpoint outage) are never reached.
Fix: the appconfigdata data plane's session resolution — GetLatestConfiguration's handler (STEP 2) and the state helper it calls (served_configuration / the deployed-triple resolution): when the control plane no longer resolves the session's application, environment or configuration profile, the poll must be refused with the modeled ResourceNotFoundException (404) carrying ResourceType for the level that is gone and ReferencedBy naming the referencing member, instead of falling back to Session::bound_configuration. The bound-configuration fallback belongs only to a control-plane store that cannot be READ (the InternalServerException path), not to a resource that has been deleted.
Traces: appconfig.session-against-deleted-environment-rejected.
