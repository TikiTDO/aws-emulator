# Elastic Beanstalk publishes CNAMEs that are not DNS names, CloudFormation-launched environments never leave Launching, and nothing serves the deployed application at the published address (4 causes)

> _Note: this issue was identified against the code base at commit `bbe224ee8535eddb09d8153d70c72e25d751373e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CheckDNSAvailability

## Description
FOUR distinct root causes in the elasticbeanstalk emulator, all in the same service, each grounded in failing behavioral checks of this suite that the replay marked neither ALREADY FILED nor OWNED. FOUR causes must be closed before submitting.

Adjacent OPEN issues describe neighbouring ground but do NOT carry these checks (the replay marked none of these failures OWNED, so their recorded replay keys no longer match): 20261109T144630Z-elasticbeanstalk-elastic-beanstalk-publishes-environment-cname-endpointurl-and-log.md (its Cause 1 read 'the emulator publishes <env>.<region>.elasticbeanstalk.com, a host it does not serve' — in THIS replay the published value has changed shape again, to a host:port/path string that is not a DNS name at all, which is what Causes 1 and 2 below are grounded in; its Cause 3 is CheckDNSAvailability's post-swap registry, not the FORM of FullyQualifiedCNAME) and 20261107T192913Z-elasticbeanstalk-elastic-beanstalk-environments-have-no-data-plane-endpointurl.md (its Cause 1 'EndpointURL is never published' no longer reproduces — an EndpointURL IS published now — and its Cause 2/3 checks are owned with different keys than the three checks of Cause 4 below).

Cause 1 of 4: CheckDNSAvailability.FullyQualifiedCNAME is not a DNS name — it is a host:port plus a URL path, so no client can use it as a CNAME.
AWS: Smithy: CheckDNSAvailability(CNAMEPrefix required, target DNSCnamePrefix @length 4..63) -> CheckDNSAvailabilityResultMessage{Available: boolean, FullyQualifiedCNAME target DNSCname @length 1..255}, documented 'The fully qualified CNAME to reserve when CreateEnvironment is called with the provided prefix'; no modelled operation errors. Recorded behavior: for an available prefix the answer is Available=true plus a dot-separated DNS name whose FIRST label is exactly the requested prefix and whose SECOND label is the region, followed by the service's own domain (on AWS, '<prefix>.<region>.elasticbeanstalk.com'); the domain part contains at least one further dot and repeats neither the prefix nor the region label. The value is a pure query answer: repeated calls for the same prefix return the SAME Available and the SAME FullyQualifiedCNAME and reserve nothing. The prefix and region labels are the requirement; the trailing service domain is the target's own, so only its form (a domain with a dot) is pinned.
Emulator: CheckDNSAvailability answers HTTP 200 with Available=true but FullyQualifiedCNAME is an endpoint URL fragment of the form '<host>:<port>/_aws/elasticbeanstalk/<region>/<prefix>' — the prefix is the LAST path segment, the region is a path segment, and the string carries ':' and '/' which a DNS name cannot. Both checks fail on the form assertion before they reach their later legality/purity assertions, so the prefix-legality part of this operation (leading/trailing hyphen and underscore must not be reported Available=true, a 64-character prefix must be refused) is still ungraded.
Why: FullyQualifiedCNAME exists so a client can predict and then use the hostname its environment will answer on — it is written into DNS records, health-check configuration and smoke tests. A value containing a port and a path is not a name any resolver or HTTP Host header can take, so every client that composes a URL or a DNS record from it builds an invalid address, and clients that parse the prefix back out of it (split on '.') read garbage.
Fix: the FullyQualifiedCNAME construction in the CheckDNSAvailability handler (services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/ops/check_dns_availability.rs) and whatever shared environment-address helper it uses: it must mint a dot-separated name whose first label is the request's CNAMEPrefix and whose second label is the region, on a domain the emulator itself answers on, and return the identical value on repeated calls.
Traces: elasticbeanstalk.check-dns-availability-semantics, elasticbeanstalk.check-dns-availability-prefix-legality-and-purity.

Cause 2 of 4: EnvironmentDescription.CNAME is published in the same host:port/path form, so a client cannot recover the environment's CNAME prefix from it (and the derived CheckDNSAvailability call is rejected client-side).
AWS: Smithy: DescribeEnvironments -> EnvironmentDescriptionsMessage/EnvironmentDescription, member CNAME documented 'The URL to the CNAME for this environment'; CheckDNSAvailability's CNAMEPrefix is @length 4..63. Recorded behavior: a launched environment's CNAME is the fully qualified name the prefix minted — its first dot-label IS the environment's CNAME prefix (a legal prefix, hence at least 4 characters), and SwapEnvironmentCNAMEs exchanges exactly these values between the two environments.
Emulator: DescribeEnvironments reports CNAME as '<host>:<port>/_aws/elasticbeanstalk/<region>/<env-name>'. Taking the first dot-separated label of that value — the documented way to get back to the prefix — yields the first component of the host literal (3 characters in the recorded run), and the follow-up CheckDNSAvailability(CNAMEPrefix=<that label>) is rejected before it leaves the client with botocore.exceptions.ParamValidationError 'Invalid length for parameter CNAMEPrefix, value: 3, valid min length: 4'. The host and port are per-run values; the defect is that the published CNAME carries no prefix label and no region label.
Why: the CNAME is the environment's public identity. A client that wants to know which prefix an environment holds, re-check that prefix's availability after a swap, or point a DNS alias at the environment, has only this string to work from; in this shape it is neither a name nor parseable, so swap/DNS workflows break at the first step and, as here, the derived API call is not even well-formed.
Fix: the environment CNAME the CreateEnvironment / UpdateEnvironment / SwapEnvironmentCNAMEs handlers record and the EnvironmentDescription serializer emits (services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/ops/ plus the service's environment state module): it must be the same dot-separated '<prefix>.<region>.<service domain>' name Cause 1 describes, on a host the emulator answers on, with the port and any path kept OUT of the CNAME value.
Traces: elasticbeanstalk.e2e-swap-cname-then-verify-dns-and-traffic-consequence.

Cause 3 of 4: an environment created by a CloudFormation stack is still Status='Launching' when the stack reports CREATE_COMPLETE, and it never reaches Ready.
AWS: Smithy: EnvironmentDescription.Status documents 'Launching: Environment is in the process of initial deployment' and 'Ready: Environment is available to have an action performed on it, such as update or terminate'. Recorded behavior: AWS::ElasticBeanstalk::Environment is not CREATE_COMPLETE until the environment has finished launching, so the moment the stack reports CREATE_COMPLETE an independent DescribeEnvironments of that environment reports Status='Ready' (and its CNAME prefix is then held, so CheckDNSAvailability on that prefix answers Available=false).
Emulator: the stack reaches CREATE_COMPLETE, and the immediately following eb.describe_environments(EnvironmentNames=[env]) reports Status='Launching' — AssertionError "environment status is 'Launching', expected Ready". The environment does not settle later either: the companion check that re-reads it after the stack completed sees 'Launching' too. Hypothesis: the CloudFormation resource provisioner calls CreateEnvironment and reports the resource complete without driving (or waiting on) the environment state machine's Launching->Ready transition, which the direct-API path does perform.
Why: CREATE_COMPLETE is the signal every deployment pipeline waits on. A client that sees it and then operates on the environment (deploy a version, update settings, terminate, probe it) is working against an environment that the service itself says is mid-launch, so those calls are refused by the state guards or hang; the stack's success is not a usable guarantee.
Fix: the AWS::ElasticBeanstalk::Environment resource provisioner must treat the environment as complete only once the environment state machine reports Ready, and that state machine must advance for CFN-created environments as it does for API-created ones — the CloudFormation Beanstalk resource handler plus the environment state module behind CreateEnvironment (services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/ops/create_environment.rs and the service's environment state module).
Traces: elasticbeanstalk.deploy-environment-via-cloudformation-then-active-and-reachable.

Cause 4 of 4: nothing serves the deployed application version at the address the environment publishes, so every data-plane check runs to its cap without an answer.
AWS: recorded behavior only — once a Processed application version is deployed and the environment reports Ready, an HTTP GET of the published CNAME (and of the EndpointURL) returns 200 carrying exactly the content baked into that version's source bundle; the same address keeps answering across a saved-configuration-template launch, and SwapEnvironmentCNAMEs makes each address answer with the OTHER environment's application.
Emulator: the emulator now publishes a CNAME and an EndpointURL on its own host, but polling that address for the deployed bundle's content never succeeds: all three checks are killed by the harness with 'Error: Check timed out after 60.0s' while in that poll loop, with no assertion frame — the same symptom the sibling checks of the open data-plane issue carry. Hypothesis: the environment is modelled as control-plane state only and the published address has no responder bound to the deployed version's bundle (for the template-launched case, the environment the template produces is likewise never reachable).
Why: running an application is the whole point of an Elastic Beanstalk environment. A client gets a Ready environment with an address that answers nothing, so no deployment consequence — content served, a swap moving which application answers, a saved configuration template reproducing its option setting in a new environment — is observable, and smoke tests that gate a deploy on fetching the new content never pass.
Fix: the environment data plane — the HTTP responder the emulator must bind to the environment's published CNAME/EndpointURL serving the deployed application version's bundle, driven from the CreateEnvironment / UpdateEnvironment / SwapEnvironmentCNAMEs / TerminateEnvironment handlers and the environment state module. These three checks are the weakest-grounded part of this issue (a bare harness timeout, no assertion frame): re-replay them first, and if one then fails on an assertion instead, treat that assertion as its own cause.
Traces: elasticbeanstalk.eb-deployed-application-serves-its-own-content-over-http, elasticbeanstalk.eb-swap-environment-cnames-swaps-which-application-answers, elasticbeanstalk.eb-saved-configuration-template-reproduces-its-option-in-a-new-environment.
