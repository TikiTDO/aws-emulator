# agent-registry-control: 3 net-new causes — CreateRegistryRecord validates neither descriptor payloads nor customMetadata against the registry schema, and record reads omit customMetadataSchemaComplianceStatus

> _Note: this issue was identified against the code base at commit `ce0a33dd83459f56e544c6d97982c4df2e00c51d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateRegistryRecord

## Description
The emulator's registry-record write path performs no content validation and its record reads drop the schema-compliance verdict. This bundle has THREE causes; all three must be fixed and re-replayed before it is closed.

Related (does NOT cover these checks): the open issue 20261110T223112Z-agent-registry-control-registry-configuration-blocks-dropped-custom-metadata-schema-never.md describes the same two defects from the WIRE corpus (its Cause 1 and Cause 4); these behavioral checks are not carried by it and cause 1 below (descriptor payload validation) is net-new to it.

Cause 1 of 3: CreateRegistryRecord accepts a descriptor payload the real service rejects.
AWS: Smithy: CreateRegistryRecord POST /registries/{registryId}/records, success code 202; input member `descriptors` -> Descriptors (required), "the typed set of descriptors for a registry record. Exactly one descriptor field is populated based on the record type", with members custom -> CustomDescriptor and mcpServer -> McpServerDescriptor; McpServerDescriptor is documented as "Descriptor that defines the content of an MCP (Model Context Protocol) server registry record ... The content is validated against the MCP protocol schema"; `data` -> DescriptorData (@length 1..102400, @sensitive). Modeled error ValidationException (errorKind client, httpError 400, required member `message`, required member `reason` -> ValidationExceptionReason default FieldValidationFailed). The descriptor payload is parsed and schema-checked before the record is written, and a payload that fails is refused with HTTP 400 / x-amzn-errortype: ValidationException and NO record is created. Message templates, as recorded: for a CUSTOM descriptor whose `data` is not parseable JSON, the fixed text "data is not valid JSON: " followed by the parser's diagnosis — recorded as "Unrecognized token '<token>': was expecting (JSON String, Number, Array, Object or token 'null', 'true' or 'false')", where <token> is the offending token taken from the request's payload and the parenthesised list is fixed text; for an mcpServer descriptor whose JSON matches no MCP server schema version, the whole message is the fixed text "mcp.server data does not match any supported version".
Emulator: both calls return HTTP 202 with a body {recordArn, status: "CREATING"} and the record is persisted — no 400, no message, no x-amzn-errortype.
Why: a client is told a malformed MCP/CUSTOM descriptor was accepted, so unparseable payloads enter the registry and the client's correction path (catch ValidationException, fix the descriptor) is never taken; on real AWS the same code would fail later at a point the client does not handle.
Fix: CreateRegistryRecord's input validation (the operation's handler, before the record is written) — parse `descriptors.custom.data` / `descriptors.mcpServer.data` and validate the MCP payload against the supported MCP server schema versions, raising ValidationException.
Traces: agent-registry-control.invalid-descriptor-rejected-without-creating-record.

Cause 2 of 3: CreateRegistryRecord ignores the registry's customMetadataSchemaConfiguration.
AWS: Smithy: input member `customMetadata` -> CustomMetadataDocument (document, @sensitive); the owning registry carries customMetadataSchemaConfiguration -> CustomMetadataSchemaConfiguration { defaultSchema ("a JSON Schema with the common attributes: fields that records of every record type can carry"), recordTypeSchemaOverrides }; modeled error ValidationException (400). customMetadata is validated against the schema that applies to the request's recordType (defaultSchema plus that record type's override) before the record is created, and a violation is refused HTTP 400 / x-amzn-errortype: ValidationException, creating nothing. Message template, as recorded: the fixed prefix "Custom metadata validation failed for record type <recordType>: " followed by the JSON-Schema failure, where <recordType> is the recordType from the request and the failure carries the JSON pointer of the offending member from the request plus the constraint text from the registry's stored schema — recorded forms: "<prefix><pointer>: does not have a value in the enumeration [<the schema's enum members>]" for a value outside an enum, "<prefix>: required property '<member>' not found" for an omitted required field, and "<prefix>: property '<member>' is not defined in the schema and the schema does not allow additional properties" for an undeclared field.
Emulator: each of the three violating creates returns HTTP 202 {recordArn, status: "CREATING"} and the record is persisted.
Why: invalid metadata is accepted and occupies the record's name, so a client's schema contract is silently unenforced; code that relies on the registry refusing off-schema metadata writes records real AWS would never hold, and the subsequent retry under the same name then collides.
Fix: CreateRegistryRecord's validation — evaluate customMetadata against the owning registry's customMetadataSchemaConfiguration before the name-uniqueness check and before the record is written.
Traces: agent-registry-control.custom-metadata-violations-rejected-at-create.

Cause 3 of 3: GetRegistryRecord never emits customMetadataSchemaComplianceStatus.
AWS: Smithy: GetRegistryRecord GET /registries/{registryId}/records/{recordId}, 200; output member `customMetadataSchemaComplianceStatus` -> enum CustomMetadataSchemaComplianceStatus with values COMPLIANT, NON_COMPLIANT, documented "Indicates whether a registry record's custom metadata conforms to the registry's current schema. COMPLIANT means all required fields are present and all values match their declared types. NON_COMPLIANT means the metadata does not satisfy the current schema, for example because the schema was updated after the record was last modified." A record whose metadata satisfies the registry's current schema reads COMPLIANT; one missing a required field (including after an additive schema change made a new field required) reads NON_COMPLIANT.
Emulator: the member is absent from every 200 record body, so a client reading it raises KeyError: 'customMetadataSchemaComplianceStatus'.
Why: a client cannot tell whether a record conforms to the registry's current schema; remediation tooling that lists or filters NON_COMPLIANT records finds none and silently does nothing, and a client branching on COMPLIANT takes the wrong branch.
Fix: GetRegistryRecord's serializer plus record state — compute the verdict against the registry's current schema when the record is written and when the registry's schema changes, and emit the member (ListRegistryRecords summaries carry the same member).
Traces: agent-registry-control.custom-metadata-schema-evolution-additive-only, agent-registry-control.submit-rejects-record-noncompliant-with-metadata-schema.
