# AppSync: 2 net-new causes — StartSchemaCreation refuses an unresolvable apiId as NotFoundException instead of BadRequestException "Invalid API ID <apiId>", and the EvaluateCode/EvaluateMappingTemplate sandbox never completes its grant→deny→re-grant cycle

> _Note: this issue was identified against the code base at commit `f601992755cd0f47cfe5dce56d2a72c97091404c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartSchemaCreation

## Description
Two distinct net-new root causes in the AppSync control plane, both grounded in failing behavioral checks that no open issue carries the replay key for. 2 causes in this issue; BOTH must be closed before submitting. For each cause the adjacent open issue is named — none of them re-runs these checks.

=== Cause 1 of 2: StartSchemaCreation classifies an apiId that resolves to no API as a missing resource instead of a bad request ===
AWS: Smithy (appsync) StartSchemaCreation — POST /v1/apis/{apiId}/schemacreation, required apiId (String, @httpLabel, no pattern constraint) and definition (Blob); modeled errors BadRequestException|400, ConcurrentModificationException|409, InternalFailureException|500, NotFoundException|404, UnauthorizedException|401. AWS deliberately classifies an apiId it cannot resolve on this operation as a BAD REQUEST: 400 BadRequestException, x-amzn-errortype BadRequestException, with the message template "Invalid API ID <apiId>" — the fixed text is "Invalid API ID " and the single variable part is the apiId taken verbatim from the request's URI label. (Recorded behavior pins the sentence; the model documents BadRequestException as "The request is not well formed. For example, a value is invalid …".) The happy path of the same operation is 200 with status in PROCESSING/SUCCESS/ACTIVE, settling to SUCCESS/ACTIVE, and the created SDL readable back through GetIntrospectionSchema.
Emulator: the same call is answered 404 NotFoundException with the constant sentence "API not found." — wrong status, wrong error code, and the rejected apiId is not echoed. The handler does have a malformed-shape branch that produces BadRequestException with an "Invalid API ID …" message, but an id that merely does not exist (well-shaped, e.g. a lowercase alphanumeric/underscore token) passes that branch and falls through to the shared api-lookup not-found path. Open issue 20261109T022338Z-appsync-schema-creation-plane-diverges-success-detail-text.md describes this same classification defect as its Cause 2, but it is a WIRE issue whose keys are appsync|StartSchemaCreation|4xx->4xx|status/$.message/$headers.x-amzn-errortype; it carries no behavioral replay key, so it will not re-run this check.
Why: typed-error dispatch is driven by the error code, so a client that catches BadRequestException on StartSchemaCreation (the class AWS models for an unusable apiId) does not catch the emulator's NotFoundException and the failure escapes as an unhandled 404; retry/backoff layers that treat 404 as "the resource may still appear" loop where AWS fails fast. The caller also loses the echoed apiId and so cannot tell which id was rejected.
Fix: the apiId resolution step of the StartSchemaCreation handler — raise the modeled BadRequestException (400) with AWS's "Invalid API ID <apiId>" template for an apiId that resolves to no API, instead of routing through the shared not-found path the other api-scoped handlers use. Note the shaped-vs-existing distinction the handler currently draws does not exist on this operation in AWS: both cases are the same 400.
Traces: appsync.op-contract-startSchemaCreation — AssertionError: expected BadRequestException, got NotFoundException (check_appsync_op_contract_startSchemaCreation.py line 40, after start_schema_creation(apiId=<nonexistent id>, definition=<SDL>)); the check's next assertion requires message == "Invalid API ID <that id>". Handler: services/service-com-amazonaws-appsync-awsdeepdishcontrolplaneservice/src/ops/start_schema_creation.rs (malformed-id branch lines 154-164; the not-found branch that is taken, lines 186-193, uses crate::state::API_NOT_FOUND_MESSAGE).

=== Cause 2 of 2: the EvaluateCode/EvaluateMappingTemplate sandbox never completes the grant → deny → re-grant cycle, so the check cannot finish at all ===
AWS: Smithy (appsync) EvaluateCode — POST /v1/dataplane-evaluatecode, required runtime (AppSyncRuntime), code (@length 1-32768) and context (@length 2-28000, @pattern ^[\s\S]*$), optional function; output evaluationResult/error/logs/stash/outErrors; modeled errors AccessDeniedException|403, BadRequestException|400, InternalFailureException|500. EvaluateMappingTemplate — POST /v1/dataplane-evaluatetemplate, required template (@length 2-65536) and context (@length 2-28000), same three modeled errors. A principal whose identity policy Allows appsync:EvaluateCode / appsync:EvaluateMappingTemplate on Resource "*" gets 200 with an evaluationResult for a well-formed APPSYNC_JS module (request/response exports) and for the template "$util.toJson($context)". Once that grant is deleted the identical calls are refused 403 AccessDeniedException with the IAM implicit-deny message "User: <user arn> is not authorized to perform: appsync:<EvaluateCode|EvaluateMappingTemplate> on resource: arn:aws:appsync:<region>:<account>:* because no identity-based policy allows the appsync:<action> action" — fixed text "User: ", " is not authorized to perform: appsync:", " on resource: ", " because no identity-based policy allows the appsync:", " action"; variable parts are the caller's IAM user ARN, the action name, and the resource ARN derived from the request. Re-attaching the identical grant restores the 200.
Emulator: the cycle never reaches any of those states — the check exhausts its whole 60s budget polling (reported as "Check timed out after 60.0s") without ever observing the state AWS produces, so neither the granted 200 nor the 403 implicit-deny refusal is served. Two emulator behaviors keep it stalled: (a) there is no identity-based authorization gate in front of either sandbox operation, so removing the grant changes nothing about the answer (the same gap this suite shows for the rest of the AppSync surface), and (b) the sandbox itself is not serving AWS's answers — EvaluateMappingTemplate is still an unimplemented scaffold stub answering the unmodeled error code NotImplemented (open issue 20261029T174359Z-appsync-evaluatemappingtemplate-stub.md), and EvaluateCode refuses well-formed APPSYNC_JS code with 400 BadRequestException "Invalid code given." (observed on appsync.op-contract-evaluateCode, which is owned by 20261110T215409Z-appsync-10-net-new-causes-graphql-realtime-endpoints.md). Hypothesis: the budget is consumed by the first positive-control poll (the granted EvaluateCode/EvaluateMappingTemplate call must return 200 within 90s) rather than by the later deny poll; the report gives only the timeout, so which poll stalls is not pinned by the evidence. Open issue 20261107T183746Z-appsync-authorization-gaps-domain-name-and-flushapicache-calls.md recorded this check's earlier failure (Cause 3, when EvaluateCode was still a NotImplemented stub); its replay key for this check is an AssertionError at _poll#17, and the check now dies on a harness timeout, so that key is no longer this failure's and that issue will not re-run it.
Why: resolver-development tooling (the console sandbox, `aws appsync evaluate-code`, CI jobs that lint resolver code or mapping templates) cannot use the sandbox at all, and no test of WHO may use it can run: an unprivileged principal is not refused, so a least-privilege or guardrail test passes against the emulator while real AWS answers 403, and conversely a client cannot distinguish "you may not call this" from "your code is invalid".
Fix: (i) the request authorization layer must evaluate identity-based policy for appsync:EvaluateCode and appsync:EvaluateMappingTemplate and answer 403 AccessDeniedException with the implicit-deny message BEFORE either handler inspects the payload; (ii) both sandbox handlers must serve AWS's 200 evaluationResult for a well-formed module/template — the EvaluateMappingTemplate handler is still the scaffold stub and EvaluateCode's code-acceptance check refuses valid input.
Traces: appsync.access-denied-sandbox-eval — "Error: Check timed out after 60.0s" on a check that calls EvaluateCode(runtime={name:APPSYNC_JS,runtimeVersion:1.0.0}, code=<request/response exports>, context="{}", function="response") and EvaluateMappingTemplate(template="$util.toJson($context)", context="{}") under an Allow grant, then after DeleteUserPolicy, then under a re-attached identical grant. Handlers: services/service-com-amazonaws-appsync-awsdeepdishcontrolplaneservice/src/ops/evaluate_code.rs and .../src/ops/evaluate_mapping_template.rs.
