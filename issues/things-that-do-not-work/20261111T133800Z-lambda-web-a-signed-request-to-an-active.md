# lambda-web: a signed request to an Active web function endpoint's domainName is answered 501, so the revision's handler response is never served (1 cause)

> _Note: this issue was identified against the code base at commit `53bfbc08a5ec2983a62510ba6bf3546a998019d9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetWebFunctionEndpoint

## Description
Cause 1 of 1: the data plane a web function endpoint publishes never serves the deployed revision's own HTTP response. An authorized (SigV4-presenting) request to the address the endpoint reports as its `domainName` is answered HTTP 501 with a fixed sentence saying no web function code ran, instead of the status, headers and body the revision's handler produced. Failing check: lambda-web.signed-https-get-on-web-function-endpoint-serves-handler-response.

AWS: a web function endpoint IS an HTTP data plane. Smithy (services/service-com-amazonaws-lambdaweb-lambdaweb/smithy-model/com-amazonaws-lambdaweb-lambdaweb.json): GetWebFunctionEndpointResponse$domainName is required, DomainName @length min 4 max 256, @pattern ^([a-z0-9-]+\.)+[a-z]+$ — "The domain name assigned to the endpoint"; GetWebFunctionEndpointResponse$state (enum EndpointState) and $revisionWeights (RevisionWeightList, @length min 1 max 2, uniqueItems) say which revision(s) that address serves; GetWebFunctionEndpointResponse$authType (enum AuthType: ApplicationManaged | IamAuth) says how a request to it is authorized. The revision names its code as a .zip deployment package in S3 (CreateWebFunction revisionConfig.buildConfig.codeConfig.s3Object) for the runtime revisionConfig.buildConfig.runtimeConfig.runtime names (a Node.js runtime identifier in the recording). The hop itself is plain HTTP and is NOT modelled — there is no operation shape, no restJson1 error envelope and no status on it — so for what comes back this is recorded behavior only: once the endpoint's `state` is `Active`, a SigV4-signed HTTPS GET to `domainName` is answered with exactly what the deployed revision's handler returned — in the recording HTTP 200 with the handler's literal body. The status, the body and any headers are entirely the handler's; nothing fixed belongs to this hop, so there is no AWS-worded message here at all and no error code.

Emulator: `serve_request` in services/service-com-amazonaws-lambdaweb-lambdaweb/src/state/endpoint_plane.rs resolves the endpoint, applies the `IamAuth` no-credential refusal, and then unconditionally returns `plain(head, 501, NO_WEB_FUNCTION_HANDLER)` — HTTP 501, content-type `text/plain; charset=utf-8`, body the module constant "This web function endpoint is not implemented: the emulator runs no web function code, so the handler's own response cannot be served.\n". That is the terminal arm for EVERY authorized request, on every endpoint, for every revision and every path and method, because no execution engine is mounted in the crate: the revision's deployment package is read and judged as an archive (src/state/code_package.rs) but never run. The control plane meanwhile reports the endpoint `Active` with a `domainName` the emulator does answer on, so the gap appears only at the last hop. The check polls the signed GET for a 200 and never gets one, so it is reported as "Check timed out after 60.0s" rather than as a 501 assertion.

Why: every behaviour that depends on what a web function ANSWERS is unreachable for a client. A client that reads `domainName` off an `Active` endpoint and issues its request there gets 501 for a function AWS reports as healthy and serving — so a web function cannot be exercised end to end, a handler's status/headers/body cannot be asserted, routing between two revisions by `revisionWeights` can never be observed (both weights resolve to the same 501), and `authType: ApplicationManaged` ("Your application handles authorization") has no observable effect at all since the only thing past the auth gate is the 501. A client treating 501 as a transient server fault retries forever, which is exactly what the check's poll does.

Fix: the endpoint data plane's authorized-request arm — the final arm of `serve_request` in the lambda-web service crate's endpoint-plane state module — must bridge the buffered request to the deployed revision's code and return that handler's own response, instead of a fixed 501 constant. That requires an execution layer for the revision's deployment package in this crate (containment and bounds first, then the request/response bridge); the emulated Lambda service's existing execution state is the closest reference, and anything shared belongs in a shared crate rather than a second copy. Which revision to dispatch to comes from the endpoint's `revisionWeights`.

Related, already filed, named here rather than re-filed: issues/things-that-do-not-work/20261110T090000Z-lambda-web-endpoint-serves-no-handler-response.md describes this same 501 and lists this check in its Issue-Trace-Ids, but it carries no replay key, so the suite did not report this check as OWNED and it is still failing at the recorded commit; treat the two as one work item. issues/things-that-do-not-work/20261111T072317Z-lambda-web-iamauth-endpoint-s-unsigned-request-refusal.md covers the sibling endpoint-invocation check's 403 body/header divergence and does NOT cover this 200-path cause.

## Evidence
Check lambda-web.signed-https-get-on-web-function-endpoint-serves-handler-response (GROUP endpoint-invocation) creates an execution role, a versioned S3 bucket holding a Node.js .zip deployment package, and one web function via CreateWebFunction with endpointConfig {endpointName: "ep", endpointType: "HomeRegion", authType: "IamAuth"}; polls GetWebFunctionEndpoint until state == "Active" (asserting Active is reached); reads domainName; then issues a SigV4-signed GET (service "lambda", X-Amz-Content-SHA256 of the empty body) to that address inside `_poll_until(..., lambda r: r[0] == 200)` and asserts `status == 200` and `text == "sim2real-probe ok"` (the handler's literal output).

Reported verdict: [mismatch] — "Error: Check timed out after 60.0s". The poll never observes a 200 because the emulator answers every authorized request to the published address with HTTP 501, content-type text/plain; charset=utf-8, body "This web function endpoint is not implemented: the emulator runs no web function code, so the handler's own response cannot be served.\n" — the `NO_WEB_FUNCTION_HANDLER` constant returned by the terminal `plain(head, 501, NO_WEB_FUNCTION_HANDLER)` arm of `serve_request` (services/service-com-amazonaws-lambdaweb-lambdaweb/src/state/endpoint_plane.rs: constant declared ~line 88, returned ~line 432). That status and that body are fixed for every authorized request, carrying nothing from the request or from the revision.

Expected per the recording: the handler's own response — HTTP 200 and the body the deployment package's handler returns (its status, headers and body are the handler's; the probe's literal body string is that run's handler output filling the template, not a fixed part of the requirement). The emulator's 501 and its sentence are not AWS behaviour on this hop at all: AWS serves no fixed document there.

## Steps to Reproduce
1. CreateRole with a lambda.amazonaws.com trust policy; CreateBucket with versioning enabled and a bucket policy letting lambda.amazonaws.com GetObject; PutObject a valid Node.js .zip deployment package whose handler returns a known literal body.
2. CreateWebFunction with revisionConfig.buildConfig.codeConfig.s3Object pointing at that object, runtimeConfig.runtime "nodejs24.x", serviceConfig.executionRoleArn the role, and endpointConfig {endpointName: "ep", endpointType: "HomeRegion", authType: "IamAuth"}.
3. Poll GetWebFunctionEndpoint(functionName, endpointName="ep") until state == "Active"; read domainName off the response.
4. Issue an HTTPS GET to that address SigV4-signed for service "lambda" in the region, carrying X-Amz-Content-SHA256 for the empty body.
5. Observed: HTTP 501, content-type text/plain; charset=utf-8, body "This web function endpoint is not implemented: the emulator runs no web function code, so the handler's own response cannot be served.\n" — on every retry, so a client polling for 200 never terminates. Expected: the deployed revision's handler response — HTTP 200 and that handler's own body.
