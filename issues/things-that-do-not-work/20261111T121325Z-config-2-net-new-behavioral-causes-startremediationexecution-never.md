# config: 2 net-new behavioral causes — StartRemediationExecution never runs the target SSM Automation document (no execution, no side effect), and the conformance-pack deploy/compliance path never converges

> _Note: this issue was identified against the code base at commit `c6eb6cb9b89be924e67ca1ea4b242861bd98eea1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartRemediationExecution

## Description
Two distinct net-new root causes on the AWS Config surface. Both were reached by checks the suite lists under `### config`, and the replay report marked NEITHER of their checks ALREADY FILED nor OWNED by an open issue. They are bundled because they share the service, not because they share a fix: a fixer must close BOTH causes before submitting.

=== Cause 1 of 2: StartRemediationExecution accepts the call and drives Config's own execution record to a terminal state, but no SSM Automation execution of the remediation target is ever created and the document's effects never happen ===
Failing checks: config.concurrent-start-remediation-execution-dedup, config.e2e-remediation-execution-resolves-noncompliant-resource

AWS: Smithy (com.amazonaws.configservice#StarlingDoveService) documents StartRemediationExecution as "Runs an on-demand remediation for the specified Config rules against the last known remediation configuration. It runs an execution against the current state of your resources. Remediation execution is asynchronous." Input is ConfigRuleName (@required) + ResourceKeys (@required, 1..100); output is FailureMessage/FailedItems; modeled errors are InsufficientPermissionsException, InvalidParameterValueException and NoSuchRemediationConfigurationException (all client, HTTP 400). A remediation configuration whose TargetType is SSM_DOCUMENT therefore has a real consequence: for each accepted resource key Config starts an SSM Automation execution of the TargetId document, assuming the role passed in the AutomationAssumeRole parameter, and that execution is visible through SSM (DescribeAutomationExecutions filtered on DocumentNamePrefix) and runs to AutomationExecutionStatus `Success`; its steps then actually mutate the targeted state (in the recordings, an aws:executeAwsApi step that calls SSM PutParameter so the parameter's value becomes "true", and an aws:executeAwsApi SNS Publish step). Config's own bookkeeping is separate and coarser: DescribeRemediationExecutionStatus reports exactly ONE RemediationExecutionStatuses record per resource key even when two accepted racing calls each ran their own automation (which is what the dedup check asserts), and a second concurrent StartRemediationExecution for a key whose execution has not completed may be refused by returning that key in FailedItems — at most one of two racing calls is rejected. The requirement here is the SIDE EFFECT, not a particular execution id or status timestamp (those are per-run values).
Emulator: the Config-facing surface answers plausibly — StartRemediationExecution returns 200 with FailedItems=[] and DescribeRemediationExecutionStatus progresses to a terminal State (in the e2e check it reports SUCCEEDED) — yet nothing downstream of it happens. (a) No SSM Automation execution of the remediation document is ever created: the dedup check polls SSM for the automation executions of its document for the whole 180 s budget and finds none, failing with `TimeoutError: 1 settled automation execution(s) of '<doc name>': the run budget ended first; not graded`. (b) Because the document never runs, its effect never lands: in the e2e check the automation's job is to flip the SSM parameter the evaluator Lambda reads from "false" to "true", so after Config reports the remediation SUCCEEDED, StartConfigRulesEvaluation + GetComplianceDetailsByConfigRule still report NON_COMPLIANT for the whole 180 s budget and the check fails with `TimeoutError: compliance 'COMPLIANT' for account <account id>: the run budget ended first; not graded`. The earlier legs of that same check PASS (the Lambda rule is invoked and lands a NON_COMPLIANT PutEvaluations verdict with its own Annotation, PutRemediationConfigurations is accepted, StartRemediationExecution is accepted with no FailedItems, and the tracked execution reaches SUCCEEDED), which isolates the defect to the step that should hand the remediation off to SSM Automation: the status is synthesized rather than reflecting a real execution.
Why: a client that remediates through Config is told the remediation SUCCEEDED while the non-compliant resource was never changed. Nothing distinguishes a real fix from a fabricated success: re-evaluating the rule still reports NON_COMPLIANT, and the only way to notice is to go look in SSM, where the execution does not exist. Auto-remediation pipelines, compliance-gate logic and runbooks that assert on the automation (DescribeAutomationExecutions, the document's own output, the SNS notification its step publishes) all read as if remediation is working when it has no effect at all; a SUCCEEDED record that corresponds to nothing is worse than a refusal, which a caller could handle.
Fix: Config's remediation execution path — the StartRemediationExecution handler and the asynchronous executor behind it must resolve the rule's stored remediation configuration, render its Parameters (StaticValue/ResourceValue, including AutomationAssumeRole) and actually invoke SSM StartAutomationExecution for a SSM_DOCUMENT TargetId, then derive the RemediationExecutionStatuses record's State and step timestamps from that execution's real status instead of synthesizing a terminal state. The dedup behavior must be preserved on top of real executions: one tracked record per resource key regardless of how many accepted calls ran, and at most one of two racing calls rejected via FailedItems. Note the adjacent pre-check already filed: open issue 20261110T200127Z-config-4-net-new-behavioral-root-causes-remediation.md (its cause 2) covers PutRemediationConfigurations refusing AWS-OWNED `AWS-*` SSM documents as missing targets; these two checks use CUSTOMER-created documents, PutRemediationConfigurations accepts them, and no open issue carries either check's replay key — fixing the target-lookup gate will not make an execution appear.

=== Cause 2 of 2: the conformance-pack deploy-and-evaluate path never converges, so the check that reads a deployed pack's compliance summary never completes ===
Failing check: config.conformance-pack-deploy-compliance-summary

AWS: Smithy models PutConformancePack, DescribeConformancePackStatus and GetConformancePackComplianceSummary (input ConformancePackNames @required 1..5; output ConformancePackComplianceSummaryList 1..5; errors InvalidLimitException, InvalidNextTokenException, NoSuchConformancePackException — all client/400). Recorded behavior: with a running recorder, a newly created S3 bucket is discovered so ListDiscoveredResources(resourceType="AWS::S3::Bucket", resourceIds=[<bucket>]) resolves exactly one resourceIdentifier; a pack whose template declares an AWS::Config::ConfigRule (Source.Owner=AWS, SourceIdentifier=S3_BUCKET_VERSIONING_ENABLED, Scope scoped to that bucket) reaches ConformancePackState CREATE_COMPLETE; and the pack's member rule is then really evaluated, so GetConformancePackComplianceSummary's ConformancePackComplianceStatus settles on NON_COMPLIANT for a versionless bucket (COMPLIANT/NON_COMPLIANT are the only terminal values the check accepts). Every one of those reads answers promptly; none of them is expected to hang.
Emulator: the check does not finish at all — replay reports `Error: Check timed out after 60.0s`, so no assertion in it is ever reached and no step's value is observable. The check's only unbounded work is its three convergence polls, in order: (1) ListDiscoveredResources for the bucket it just created, (2) DescribeConformancePackStatus until CREATE_COMPLETE/CREATE_FAILED, (3) GetConformancePackComplianceSummary until the status is COMPLIANT or NON_COMPLIANT. Hypothesis: the pack's member rule is never evaluated, so poll (3) spins forever on an unresolved summary; a second candidate on the same path is poll (1), since a running recorder not discovering a just-created resource is already filed. Either way the emulator answers 200 with a projection that never resolves rather than refusing, and the whole check is unreachable.
Why: a client that deploys a conformance pack is told the pack is CREATE_COMPLETE and can then never learn whether it passes — an unresolved summary is indistinguishable from a clean account, so compliance reporting silently reads "no findings" forever and any loop waiting for a terminal pack status hangs.
Fix: the conformance-pack deployment and evaluation path — PutConformancePack must materialize each template-declared AWS::Config::ConfigRule (honouring ConformancePackInputParameters substitution into Scope/Properties) as a real config rule, run it through the managed-rule evaluation engine, and have GetConformancePackComplianceSummary / DescribeConformancePackCompliance project those evaluation results so the status reaches a terminal value; whichever read on this path blocks must answer within a normal request budget. Related but NOT covering: open issue 20261107T193246Z-config-4-net-new-causes-custom-lambda-and.md (its cause 2) describes pack member rules never being evaluated, but carries only the replay keys of config.aggregate-conformance-pack-compliance-summary-reflects-pack-status and config.conformance-pack-compliance-details-and-summary-consistent — not this check, which is why the report did not mark this failure owned; and 20261104T093105Z-config-a-running-recorder-never-discovers-an-ec2.md covers recorder discovery for EC2 instances only. This check must be replayed to confirm any fix.

Traces: config.concurrent-start-remediation-execution-dedup and config.e2e-remediation-execution-resolves-noncompliant-resource (cause 1); config.conformance-pack-deploy-compliance-summary (cause 2).
