# cloudfront__events: 3 net-new causes — CreateInvalidation performs no IAM authorization (and loses AccessDenied precedence over NoSuchDistribution), a cron() rule fires ~2 min before its cron minute, and a read-only GetInvalidation call is emitted as a CloudTrail-derived event

> _Note: this issue was identified against the code base at commit `4561d0722e5c03ef656b5ed57b40071717cb7fdd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateInvalidation

## Description
Three distinct net-new root causes, all grounded in cloudfront__events checks that the replay report does NOT mark OWNED or ALREADY FILED. Several open issues cover the same area but none carries these checks' replay keys, so none of them covers these failures: 20261107T192835Z-cloudfront-events-3-net-new-causes-a-matched.md (its cause 1 'target produces no effect' no longer reproduces for these checks — the pipeline now runs and the divergence has moved to authorization/timing; its cause 3 is the same read-only classification defect as Cause 3 here but is keyed to a different check), 20261023T140640Z-cloudfront-iam-sts-cloudfront-performs-no-iam-authorization-an-assumed-role.md (same authorization gap, filed under the cloudfront__iam__sts heading and keyed to its checks), 20261109T171600Z-cloudfront-2-net-new-causes-eventbridge-cron-rate.md (cron/rate schedules never fired at all; the symptom is now the opposite — they fire too early), 20261110T105638Z-cloudfront-events-the-s3-objectcreated-eventbridge-lambda-createinvalidation.md.

=== Cause 1 of 3: CreateInvalidation is not authorized — any caller succeeds, and AccessDenied no longer precedes NoSuchDistribution ===
AWS: CreateInvalidation (Smithy: POST /2020-05-31/distribution/{DistributionId}/invalidation, success 201; modeled errors AccessDenied httpError 403, NoSuchDistribution httpError 404, InvalidArgument 400, BatchTooLarge 413, MissingBody 400, InconsistentQuantities 400, TooManyInvalidationsInProgress 400) is an IAM-authorized call. A request signed with credentials (here a Lambda execution role assumed via sts:AssumeRole) whose identity policy does not allow cloudfront:CreateInvalidation on the target distribution's ARN — either because the action is absent entirely, or because the statement's Resource names a DIFFERENT distribution ARN — is refused with HTTP 403 and error code AccessDenied before any invalidation is created. The refusal message is IAM's standard implicit-deny text: the fixed text is "User: " / " is not authorized to perform: " / " on resource: " / " because no identity-based policy allows the " / " action", and its variable parts are the caller's own ARN taken from the signing credentials (the assumed-role ARN of the invoking role), the action name cloudfront:CreateInvalidation, and the distribution ARN from the request. Authorization is evaluated BEFORE resource resolution, so a caller that is not allowed the action and names a distribution that does not exist gets 403 AccessDenied, not 404 NoSuchDistribution (Smithy doc for AccessDenied: "Access denied."; for NoSuchDistribution: "The specified distribution does not exist."). The checks assert only the HTTP class / error code, not the message text.
Emulator: no authorization is evaluated at all. A Lambda whose execution role carries no cloudfront:CreateInvalidation statement creates the invalidation and returns 201 (the handler reports {'ok': True, 'invalidationId': ...} and {'role': 'negative', 'ok': True}); a role scoped to distribution A's ARN successfully invalidates distribution B ({'outcome': 'success', 'invalidationId': ...}); and an unauthorized call naming a nonexistent distribution id falls straight through to the existence check and is refused with code 'NoSuchDistribution' where AWS answers 'AccessDenied'.
Why: a client relying on CloudFront's IAM boundary gets none of it — a least-privilege execution role is indistinguishable from an administrative one, an invalidation policy scoped to one distribution silently grants every distribution in the account, and any test or control that proves a permission boundary (or that reads the error code to distinguish 'not allowed' from 'does not exist') passes against an emulator that enforces nothing.
Fix: the authorization step in front of CloudFront's CreateInvalidation handler — identity-policy evaluation of cloudfront:CreateInvalidation against the request's distribution ARN, ordered before the distribution lookup, and the AccessDenied (403) serializer for the refusal.
Traces: cloudfront__events.eventbridge-target-missing-cloudfront-invalidation-permission-not-invoked, cloudfront__events.eventbridge-target-role-scoped-to-wrong-distribution-denied, cloudfront__events.lambda-role-missing-cloudfront-permission-denied, cloudfront__events.lambda-role-missing-cloudfront-permission-denied-invalidation.

=== Cause 2 of 3: an EventBridge rule with a cron() ScheduleExpression fires its target immediately instead of at its cron minute ===
AWS: PutRule with ScheduleExpression "cron(Minutes Hours Day-of-month Month Day-of-week Year)" (the same field syntax a daily schedule uses, evaluated in UTC) fires the rule's targets at the start of each minute that MATCHES the cron fields, and never before it; dispatch may lag the matched minute by up to about a minute, but it cannot precede it. Recorded behavior only — the schedule semantics are not expressed in the Smithy model; the recording shows the first invalidation appearing at or after the targeted minute.
Emulator: the target runs essentially at registration time. With a rule created at ~17:29:0x carrying cron(31 17 * * ? *) — i.e. a target minute of 17:31:00Z — the Lambda target had already created an invalidation whose CreateTime was 17:29:11Z, roughly 110 s BEFORE the cron minute and far outside the check's 20 s early slack. The cron fields are therefore not being matched: the schedule is fired once on put_targets/put_rule (or on a coarse poll that ignores the fields).
Why: every cron-scheduled automation runs at the wrong time — a nightly cache invalidation, report or cleanup fires the instant it is deployed, the cron fields carry no meaning, and a client cannot build or test anything that depends on when a schedule fires (including proving that a schedule has NOT yet fired).
Fix: the EventBridge rule scheduler — cron-expression parsing/next-occurrence computation for ScheduleExpression in PutRule and the dispatcher that decides when a scheduled rule's targets are invoked.
Traces: cloudfront__events.eventbridge-cron-rule-triggers-cloudfront-invalidation-daily.

=== Cause 3 of 3: a read-only CloudFront management call (GetInvalidation) is emitted as an "AWS API Call via CloudTrail" event ===
AWS: for the lifecycle of one invalidation, the only aws.cloudfront CloudTrail-derived event that carries the invalidation's id is the API-call record of the mutating call that created it, detail-type "AWS API Call via CloudTrail" with detail.eventName "CreateInvalidation". The read-only polling calls made while waiting for the invalidation to reach Completed (GetInvalidation) produce no delivered event, and the invalidation's completion is not an event either. Recorded behavior only — event emission/selection is not expressed in the Smithy model (GetInvalidation is Smithy: GET /2020-05-31/distribution/{DistributionId}/invalidation/{Id}, 200, a pure read).
Emulator: the sink that collects every aws.cloudfront event receives a second API-call record for the same invalidation — the check observes [('AWS API Call via CloudTrail', 'CreateInvalidation'), ('AWS API Call via CloudTrail', 'GetInvalidation')] where AWS yields only the CreateInvalidation pair, held 30 s past the readiness barrier. Read-only CloudFront management calls are being classified and emitted as CloudTrail-derived events.
Why: a client that routes CloudFront API-call events to an automation or audit pipeline is flooded with its own read traffic — every console refresh or status poll re-triggers the automation and pollutes the audit stream, which on AWS it never would; and a rule written to see only the mutating calls about a resource cannot be built.
Fix: the CloudTrail-derived management-event emitter's read-only/write classification for CloudFront operations (the step that decides which operations produce an "AWS API Call via CloudTrail" event at all).
Traces: cloudfront__events.xsvc-cloudfront-1-s3-object-created-lambda-invalidation-refreshes-edge.

## Steps to Reproduce
Cause 1 (three shapes of the same gap):
1. Create a minimal CloudFront distribution. Create an IAM role trusted by lambda.amazonaws.com whose inline policy grants ONLY logs:* (no cloudfront:CreateInvalidation), and a Lambda using it that calls cloudfront:CreateInvalidation on that distribution and reports the outcome. Invoke it (directly, or as an EventBridge rule target). Expected: the SDK call fails with HTTP 403 / code AccessDenied and no invalidation exists. Actual: 201 and an invalidation id.
2. Same setup, but grant cloudfront:CreateInvalidation with Resource = distribution A's ARN, then have the Lambda invalidate distribution B. Expected: 403 AccessDenied for B while A still succeeds. Actual: B succeeds.
3. Same denied role, but call CreateInvalidation with DistributionId of a distribution that does not exist (e.g. a well-formed but unknown id). Expected: 403 AccessDenied (authorization before resource resolution). Actual: 404 NoSuchDistribution.

Cause 2: PutRule with ScheduleExpression "cron(<M> <H> * * ? *)" where <M>/<H> name a UTC minute ~2 minutes in the future, State=ENABLED; add a Lambda target that calls CreateInvalidation, grant events.amazonaws.com lambda:InvokeFunction, then poll ListInvalidations. Expected: nothing until the target minute (± dispatch lag), then one invalidation. Actual: an invalidation appears within seconds of creating the rule/target, ~110 s before the cron minute.

Cause 3: create an ENABLED rule matching {"source": ["aws.cloudfront"]} with an SQS sink, create an invalidation, then poll GetInvalidation until it reports Completed and drain the sink. Expected: exactly one event carrying the invalidation id, detail.eventName = CreateInvalidation. Actual: an additional "AWS API Call via CloudTrail" event with detail.eventName = GetInvalidation.
