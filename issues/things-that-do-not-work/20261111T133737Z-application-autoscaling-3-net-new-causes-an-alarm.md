# application-autoscaling: 3 net-new causes — an alarm-invoked step policy, a firing scheduled action's ceiling, and a DynamoDB target-tracking policy all never move the target's capacity

> _Note: this issue was identified against the code base at commit `768db93f7ee9a823eb9c7336f7c11f317ed4b425`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutScalingPolicy

## Description
Three distinct causes, all in Application Auto Scaling's scaling engine: a registered scalable target never has its capacity actually driven, even though the control-plane calls that configure it all succeed.

Cause 1 of 3: a CloudWatch alarm in ALARM whose AlarmActions names a StepScaling policy ARN never invokes that policy on a custom-resource target.
AWS: PutScalingPolicy with PolicyType='StepScaling' returns a PolicyARN, and that ARN is a valid CloudWatch alarm action (Smithy: PutScalingPolicy input PolicyType=ScalingPolicyType{StepScaling,TargetTrackingScaling,PredictiveScaling}, StepScalingPolicyConfiguration{AdjustmentType, StepAdjustments, Cooldown, MetricAggregationType}; output PolicyARN required). When the alarm transitions to ALARM, Application Auto Scaling evaluates the step whose MetricIntervalLowerBound the breach falls into, applies the ScalingAdjustment clamped to the target's MaxCapacity, issues the namespace's capacity change (for ServiceNamespace='custom-resource' a PATCH {"desiredCapacity": <new>} to the registered endpoint) and records a ScalingActivity whose Cause begins with the fixed text 'monitor alarm <AlarmName> in state ALARM triggered policy <PolicyName>' — the alarm name and policy name are values from the request, the rest is fixed — with StatusCode='Successful' (Smithy: ScalingActivityStatusCode = Pending|InProgress|Successful|Overridden|Unfulfilled|Failed).
Emulator: the endpoint is never PATCHed and no activity is recorded. Replay: `AssertionError: the alarm-invoked policy moving the endpoint off 1 not observed within 420s; last saw (1.0, 0, None)` — desired still 1.0, PATCH count 0, last PATCH body None, for 420s of a continuously breaching metric. A +3 ChangeInCapacity step from 1 under MaxCapacity=3 should have left the endpoint at exactly 3.
Why: a client that wires an alarm to a step policy — the documented way to do step scaling — gets an autoscaler that is configured and silent. Capacity never changes and DescribeScalingActivities stays empty, so the client cannot even tell the policy was not run.
Fix: the alarm-action dispatch path into the application-autoscaling crate's step-scaling executor (invocation of a policy by its PolicyARN as a CloudWatch alarm action), and the custom-resource capacity writer it calls.
Traces: application-autoscaling.custom-resource-step-policy-alarm-patches-the-endpoint-up-to-the-ceiling. (The open issue 20261111T025030Z-application-autoscaling-a-scale-in-disabled-target-tracking.md describes a custom-resource endpoint that is never PATCHed for a TARGET-TRACKING policy; it does not carry this step-scaling replay key. The open issue 20261109T144605Z-application-autoscaling-ecs-2-net-new-causes-an.md covers alarm STATE instability under ECS, not alarm-action dispatch.)

Cause 2 of 3: a scheduled action that lowers MaxCapacity below the target's current capacity rewrites the bound but never enforces it — the resulting scale-in activity and capacity change are missing.
AWS: PutScheduledAction with ScalableTargetAction{MaxCapacity: N} (Smithy: ScalableTargetAction.MaxCapacity doc — 'Although you can specify a large maximum capacity...'; ScalableTargetAction.MinCapacity doc — 'When the scheduled action runs, the resource will have at least this much capacity') applies the new bound when the schedule fires AND brings the resource inside it. Firing therefore produces TWO activities: the dispatch record, Cause 'scheduled action name <ScheduledActionName> was triggered' / Description 'Setting max capacity to <N>', and the enforcement record, Cause 'maximum capacity was set to <N>' / Description 'Setting desired capacity to <N>.' — the fixed text is everything but <ScheduledActionName> and <N>, which come from the request. Both reach StatusCode='Successful', and the custom-resource endpoint is PATCHed to {"desiredCapacity": <N>}.
Emulator: only the dispatch activity exists. Replay: `AssertionError: the action firing at <time> and the scale-in it causes, both Successful not observed within 300s; last saw [{... 'Description': 'Setting max capacity to 2', 'Cause': 'scheduled action name <action> was triggered', 'StatusCode': 'Successful', 'StatusMessage': 'Successfully set max capacity to 2'}]` — one activity instead of two, and the endpoint stays at its old capacity (5) above the new ceiling (2).
Why: the target's own DescribeScalableTargets reports MaxCapacity=2 while the underlying resource is still at 5. A client that schedules a nightly ceiling to cut cost or cap load sees the bound tighten and nothing happen, and the resource runs permanently out of bounds with no activity explaining it.
Fix: the scheduled-action firing path in the application-autoscaling crate — after writing the new bound it must clamp the target's current capacity into [MinCapacity, MaxCapacity], emit the enforcement ScalingActivity, and call the namespace's capacity writer.
Traces: application-autoscaling.custom-resource-scheduled-action-patches-the-endpoint-when-it-fires.

Cause 3 of 3: a TargetTrackingScaling policy on a DynamoDB table capacity dimension never scales out under sustained real load — no capacity change and no scaling activity at all.
AWS: a TargetTrackingScaling policy on ScalableDimension 'dynamodb:table:ReadCapacityUnits' or 'dynamodb:table:WriteCapacityUnits' (Smithy: ScalableDimension enum documents both; TargetTrackingScalingPolicyConfiguration{TargetValue required, PredefinedMetricSpecification, ScaleOutCooldown, ...}) creates the managed AlarmHigh/AlarmLow pair; when consumed capacity drives the utilization metric above TargetValue and AlarmHigh breaches, Application Auto Scaling raises the table's provisioned capacity toward the target and records a ScalingActivity for ResourceId 'table/<TableName>'.
Emulator: no activity and no capacity change. Replay: `AssertionError: a scaling activity for 'table/<table>' driven by the target-tracking AlarmHigh breaching on real read load not observed within 240s; last saw []` and `AssertionError: WriteCapacityUnits never increased past 5 after several minutes of sustained write load well above the policy's target utilization`. Both dimensions are inert.
Why: DynamoDB auto scaling is the canonical Application Auto Scaling use case. A client that provisions a table with a target-tracking policy gets a table that throttles under load forever: capacity never rises and DescribeScalingActivities offers no explanation (not even an Unfulfilled or Failed activity).
Fix: the target-tracking controller in the application-autoscaling crate — the managed-alarm evaluation that feeds it, and the dynamodb capacity writer it must call to apply the new ProvisionedThroughput.
Traces: application-autoscaling.target-tracking-policy-scales-out-table-capacity, application-autoscaling.target-tracking-alarm-breach-triggers-scaling-activity.

## Evidence
Cause 1 — Expected: after the alarm named in AlarmActions enters ALARM, the custom-resource endpoint holds desiredCapacity 3.0, the last PATCH body is {"desiredCapacity": 3.0}, and DescribeScalingActivities has an activity with Cause starting 'monitor alarm <alarm> in state ALARM triggered policy <policy>' and StatusCode='Successful'. Actual: `AssertionError: the alarm-invoked policy moving the endpoint off 1 not observed within 420s; last saw (1.0, 0, None)` — (desired, patch count, last body) = (1.0, 0, None).

Cause 2 — Expected: two activities, [('maximum capacity was set to 2', 'Setting desired capacity to 2.'), ('scheduled action name <action> was triggered', 'Setting max capacity to 2')], both Successful, endpoint PATCHed to {"desiredCapacity": 2.0}, bounds reading back (1, 2). Actual: `AssertionError: the action firing at <t> and the scale-in it causes, both Successful not observed within 300s; last saw [{'Description': 'Setting max capacity to 2', 'Cause': 'scheduled action name <action> was triggered', 'StatusCode': 'Successful', 'StatusMessage': 'Successfully set max capacity to 2', ...}]` — the enforcement activity is absent and capacity stays at 5.

Cause 3 — Expected: DescribeScalingActivities returns at least one activity for ResourceId 'table/<table>' attributable to the target-tracking AlarmHigh, and the table's provisioned capacity rises above its starting value. Actual: `AssertionError: a scaling activity for 'table/<table>' driven by the target-tracking AlarmHigh breaching on real read load not observed within 240s; last saw []`; and `AssertionError: WriteCapacityUnits never increased past 5 after several minutes of sustained write load well above the policy's target utilization`.

## Steps to Reproduce
Cause 1: stand up a custom-resource endpoint at desiredCapacity 1; application-autoscaling RegisterScalableTarget(ServiceNamespace='custom-resource', ScalableDimension='custom-resource:ResourceType:Property', MinCapacity=1, MaxCapacity=3); PutScalingPolicy(PolicyType='StepScaling', StepScalingPolicyConfiguration={AdjustmentType:'ChangeInCapacity', Cooldown:600, MetricAggregationType:'Maximum', StepAdjustments:[{MetricIntervalLowerBound:0.0, ScalingAdjustment:3}]}); cloudwatch PutMetricAlarm(Threshold=10.0, ComparisonOperator='GreaterThanThreshold', EvaluationPeriods=1, Period=60, AlarmActions=[<PolicyARN>]); feed breaching PutMetricData continuously. Poll the endpoint: desiredCapacity stays 1 and no activity is recorded.

Cause 2: stand up a custom-resource endpoint at desiredCapacity 5; RegisterScalableTarget(MinCapacity=1, MaxCapacity=8); PutScheduledAction(Schedule='at(<next whole UTC minute>)', ScalableTargetAction={'MaxCapacity': 2}); after it fires, DescribeScalingActivities returns only the 'scheduled action ... was triggered' record and the endpoint still reads desiredCapacity 5.

Cause 3: create a provisioned DynamoDB table; RegisterScalableTarget(ServiceNamespace='dynamodb', ScalableDimension='dynamodb:table:ReadCapacityUnits' / 'dynamodb:table:WriteCapacityUnits'); PutScalingPolicy(PolicyType='TargetTrackingScaling', TargetTrackingScalingPolicyConfiguration={TargetValue:<low>, PredefinedMetricSpecification:{PredefinedMetricType:'DynamoDBReadCapacityUtilization'/'DynamoDBWriteCapacityUtilization'}}); drive sustained real read/write load. Capacity never rises and DescribeScalingActivities stays empty.
