## Description

IMPORTANT for the fixer, Cause 1: open WIRE issue 20261109T061652Z-cloudformation-continueupdaterollback-s-wrong-state-refusal-names-rollbackupdatedstack-and.md asks for the OPPOSITE wording of the same refusal ('ContinueUpdateRollback cannot be called from stack with <StackStatus> status.'), which is EXACTLY what the emulator emits today. Reconcile the two before changing the handler, do not simply flip it back and forth.

Cause 1 of 2: ContinueUpdateRollback called from a status it is not valid from is refused with the right status and error code but the wrong message text.
Failing check ids for this cause: cloudformation.continue-update-rollback-on-stable-stack-fails, cloudformation.continue-update-rollback-wrong-state-rejected, cloudformation.rollback-cancel-continue-flow.
AWS: Smithy (services/service-com-amazonaws-cloudformation-cloudformation/smithy-model/com-amazonaws-cloudformation-cloudformation.json): ContinueUpdateRollback(StackName: StackNameOrId, required) models ONLY TokenAlreadyExistsException (client, HTTP 400, awsQueryError code TokenAlreadyExistsException), so a wrong-state refusal is CloudFormation's service-common ValidationError at HTTP 400; its documentation scopes the operation to one state — "Continues rolling back a stack from UPDATE_ROLLBACK_FAILED to UPDATE_ROLLBACK_COMPLETE state". Recorded behavior: from any other status the call is refused with Error.Code `ValidationError` and Error.Message exactly `RollbackUpdatedStack cannot be called from current stack status` — the whole sentence is FIXED text with NO variable part: AWS names its internal operation `RollbackUpdatedStack` (not the invoked public name), uses the constant phrase `current stack status` instead of interpolating the stack's StackStatus, and ends WITHOUT a period. The refused call leaves the stack's StackStatus untouched. The same checks' sibling assertions on the neighbouring guards PASS and are the family's reference wording: CancelUpdateStack from an invalid status answers `CancelUpdateStack cannot be called from current stack status`, and RollbackStack on a stable stack answers `RollbackStack can only be called on any of the [UPDATE_FAILED, CREATE_FAILED] statuses.`
Emulator: HTTP 400 and `ValidationError` are correct; the message is `ContinueUpdateRollback cannot be called from stack with <StackStatus> status.` — it substitutes the invoked public operation name for AWS's internal verb, interpolates the stack's current status into text AWS keeps invariant, and appends a trailing period. Observed as `... from stack with CREATE_COMPLETE status.` on a CREATE_COMPLETE stack and `... from stack with UPDATE_ROLLBACK_COMPLETE status.` on an UPDATE_ROLLBACK_COMPLETE stack; those two status words are this run's state values filling the emulator's own template, not part of any requirement.
Why: this message is the only thing that distinguishes "this stack is not stuck, there is nothing to continue" from every other ValidationError on the stack-recovery path. A client or deploy wrapper that matches CloudFormation's sentence to pick between ContinueUpdateRollback, RollbackStack and UpdateStack --disable-rollback never recognizes the refusal; and because the emulator's text varies with the stack's status where AWS's is constant, no exact match is possible at all.
Fix: the stack-status pre-condition of the ContinueUpdateRollback handler and the shared message builder it calls — emit the invariant sentence and leave CancelUpdateStack's and RollbackStack's wordings alone (file/line: services/service-com-amazonaws-cloudformation-cloudformation/src/ops/continue_update_rollback.rs lines 232-236, which calls crate::state::cannot_continue_update_rollback(&previous.status); the builder formats the status into the text and must stop doing so).
Traces: cloudformation.continue-update-rollback-on-stable-stack-fails, cloudformation.continue-update-rollback-wrong-state-rejected, cloudformation.rollback-cancel-continue-flow.

Cause 2 of 2: the full UPDATE_ROLLBACK_FAILED recovery lifecycle over an SNS-backed Custom:: resource never reaches a terminal state inside the replay window, so ContinueUpdateRollback's success path is unobservable.
Failing check ids for this cause: cloudformation.stack-continue-update-rollback-lifecycle.
AWS: recorded behavior only — the custom-resource provider protocol is not in the Smithy model. The recording shows a stack whose Custom:: resource provider answers FAILED on the update and FAILED again on the automatic rollback lands in UPDATE_ROLLBACK_FAILED; ContinueUpdateRollback is then accepted (200, empty output), one more provider Update request is published to the resource's SNS ServiceToken topic, and once answered SUCCESS the stack reaches UPDATE_ROLLBACK_COMPLETE; ContinueUpdateRollback on the stack after it is deleted is refused with ValidationError. Every one of those transitions is terminal within the window the suite allows.
Emulator: the check produces no verdict at all — it is killed at the harness ceiling with `Check timed out after 60.0s`, so no stack status transition on this path completes in time. Hypothesis (the replay output does not say which stage stalls): the SNS-backed custom-resource round trip and/or the update-rollback workflow that must drive UPDATE_ROLLBACK_IN_PROGRESS to UPDATE_ROLLBACK_FAILED and then to UPDATE_ROLLBACK_COMPLETE does not settle, since the sibling check in Cause 1 does now receive its provider Create request (it fails later, on the message assertion).
Why: a stack stranded in UPDATE_ROLLBACK_FAILED is exactly what ContinueUpdateRollback exists to recover; a client driving that documented recovery can observe neither the resume nor the final UPDATE_ROLLBACK_COMPLETE, so stuck stacks cannot be recovered or even diagnosed against the emulator.
Fix: the update-rollback workflow plus the custom-resource provisioner it waits on in the cloudformation service (the stage that must settle UPDATE_ROLLBACK_IN_PROGRESS to a terminal UPDATE_ROLLBACK_FAILED / UPDATE_ROLLBACK_COMPLETE rather than leaving the stack in flight), not the ContinueUpdateRollback request handler, which accepts the call. Related and NOT covering this failure: open 20261107T184737Z-cloudformation-4-net-new-causes-activatetype-refuses-aws.md carries this check only under the replay key `_next_request#25|AssertionError|no custom-resource request arrived within {timeout_s}s`, which no longer reproduces (the failure is now a whole-check timeout), and the replay report did not list it as this failure's owner; fixed 20261026T235900Z-cloudformation-update-rollback-failed-recovery-never-converges-the.md described the same non-convergence class for a DIFFERENT check (deep-cloudformation-1-cfn-enforce-continue-update-rollback-requires-resource-skip) and a resolved issue does not cover this one.
Traces: cloudformation.stack-continue-update-rollback-lifecycle.

Then confirm DescribeStacks still reports CREATE_COMPLETE (the refusal must not perturb the stack). Repeat from UPDATE_ROLLBACK_COMPLETE (update the stack to a wait-condition template, CancelUpdateStack, wait UPDATE_ROLLBACK_COMPLETE, then ContinueUpdateRollback): the message must be the same invariant sentence. Compare with CancelUpdateStack and RollbackStack from invalid statuses, whose messages are already correct.

Cause 2: create an SNS topic with an SQS subscription (queue policy allowing sns.amazonaws.com SendMessage from that topic). Call ContinueUpdateRollback, answer the resumed Update request SUCCESS, and poll for UPDATE_ROLLBACK_COMPLETE.
