# cloudfront: 6 net-new resource-policy causes — a policy-free VPC origin reads/deletes as 404 EntityNotFound, PutResourcePolicy validates no policy document, and the stored document is never canonicalized

> _Note: this issue was identified against the code base at commit `87482cc5c5e409200c9575bf7c958860b805c188`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetResourcePolicy

## Description
Six net-new root causes (6 causes) in the CloudFront resource-policy surface, all observed against a VPC origin that EXISTS in the emulator's state (created with CreateVpcOrigin and settled to Deployed). They are distinct from the two open issues in this family, neither of which carries any of these replay keys: 20261111T001225Z-cloudfront-resource-policy-operations-skip-resourcearn-argument-validation.md covers a MALFORMED or wrong-type ResourceArn answered 404 instead of 400 InvalidArgument, and 20261111T194302Z-cloudfront-resource-policy-operations-ignore-resource-existence-and.md covers a ResourceArn whose RESOURCE is absent from state being answered 200 instead of 404 EntityNotFound. The causes below are about a resource that is present and whose policy is absent, and about the content of the policy document — adding those two issues' ARN-validation and existence checks does not produce any of the behaviours required here.

Cause 1 of 6: GetResourcePolicy on an existing VPC origin that has no policy attached is refused 404 EntityNotFound instead of answering 200 with the empty document.
AWS: Smithy (services/service-com-amazonaws-cloudfront-cloudfront2020-05-31/smithy-model/com-amazonaws-cloudfront-cloudfront2020-05-31.json): GetResourcePolicy input ResourceArn @required; output members ResourceArn and PolicyDocument; http {POST /2020-05-31/get-resource-policy, code 200}; modeled errors AccessDenied (403), EntityNotFound (404), InvalidArgument (400), UnsupportedOperation (400). Recorded behavior: for a VPC origin that exists and has never had a policy attached, the read succeeds with HTTP 200, ResourceArn echoing the ResourceArn from the request and PolicyDocument carrying the empty JSON document "{}"; EntityNotFound is not used for "the resource exists but carries no policy". After PutResourcePolicy the same read returns that policy, and after DeleteResourcePolicy it returns "{}" again.
Emulator: answers HTTP 404 with Error.Code 'EntityNotFound' and Message "The specified resource policy does not exist." (that message is entirely emulator-authored: it names a resource POLICY, where AWS's 404 wording for this surface is about the resource).
Why: a client cannot distinguish "this resource takes no policy / the resource is gone" from "this resource has no policy yet". Every get-then-put flow (read the current policy, add a statement, write it back) fails on its first read instead of starting from the empty document, and any teardown or audit that reads a policy back after deleting it is handed an error where AWS reports the empty document. In this suite the failure is terminal: the check aborts on the uncaught EntityNotFound before it ever reaches its Put.
Fix: GetResourcePolicy's handler (services/service-com-amazonaws-cloudfront-cloudfront2020-05-31/src/ops/get_resource_policy.rs) — once the ResourceArn resolves to a resource the store holds, a missing policy entry must produce the 200 success shape with PolicyDocument "{}" and the echoed ResourceArn, not crate::state::resource_policy_not_found().
Traces: cloudfront.get-resource-policy-nonexistent-entity-not-found, cloudfront.get-resource-policy-invalid-argument-rejected, cloudfront.op-contract-getResourcePolicy, cloudfront.e2e-resource-policy-grants-and-revokes-cross-account-access, cloudfront.resource-policy-lifecycle, cloudfront.resource-policy-put-get-delete-lifecycle.

Cause 2 of 6: DeleteResourcePolicy on an existing VPC origin that has no policy attached is refused 404 EntityNotFound instead of succeeding as a no-op.
AWS: Smithy: DeleteResourcePolicy input ResourceArn @required, output Unit; http {POST /2020-05-31/delete-resource-policy, code 200}; modeled errors AccessDenied (403), EntityNotFound (404), IllegalDelete (400), InvalidArgument (400), PreconditionFailed (412), UnsupportedOperation (400). Recorded behavior: deleting the policy of a resource that exists and carries no policy succeeds (HTTP 200, empty output) — the delete is idempotent over an absent policy on a present resource; the subsequent read reports the empty document.
Emulator: answers HTTP 404 with Error.Code 'EntityNotFound' and Message "The specified resource policy does not exist."
Why: idempotent cleanup is impossible. A teardown that deletes a policy it may or may not have attached raises instead of completing, and a caller that must tolerate the absent case has to swallow a 404 that in AWS means something else entirely (a resource that is not there).
Fix: DeleteResourcePolicy's handler (src/ops/delete_resource_policy.rs) — after the ResourceArn resolves to a held resource, a store.delete_resource_policy() that removed nothing must still return the 200 success output; reserve EntityNotFound for an ARN whose RESOURCE the store does not hold.
Traces: cloudfront.resource-policy-delete-nonexistent-rejected, cloudfront.resource-policy-server-side-round-trip-enforcement.

Cause 3 of 6: PutResourcePolicy performs no policy-document FORMAT validation — malformed JSON and an empty Statement list are both stored and answered 200.
AWS: Smithy: PutResourcePolicy input ResourceArn (@required) and PolicyDocument (@required); http {POST /2020-05-31/put-resource-policy, code 200}; modeled errors include InvalidArgument (400). Recorded behavior: a PolicyDocument that is not parseable JSON, and a syntactically valid document whose Statement array is empty, are both refused with HTTP 400, Error.Code 'InvalidArgument' and Message "The specified policy format isn't valid. Verify that the format is valid JSON and try again." That message is fixed text in full — no name, ARN, id or member name from the request or from state appears in it. Nothing is persisted by the refused call, so the following read reports the empty document.
Emulator: answers HTTP 200 with the PutResourcePolicy success shape (ResourceArn echoed) and stores the document verbatim; src/ops/put_resource_policy.rs validates only the ResourceArn and a store-size bound, never the document.
Why: a caller that submits a corrupt or empty policy is told the grant is in place. Permissions the policy was supposed to express are not in effect, and the next read hands back a document the service would never have accepted, so a negative test for the malformed case passes vacuously and a real misconfiguration stays invisible until a cross-account call is unexpectedly denied.
Fix: PutResourcePolicy's validation (src/ops/put_resource_policy.rs) — parse and shape-check PolicyDocument before any store write: reject unparseable JSON and a document carrying no statements with InvalidArgument (400) and AWS's "policy format isn't valid" wording, leaving the store untouched.
Traces: cloudfront.put-resource-policy-malformed-document-illegal-update-rejected, cloudfront.resource-policy-invalid-document-rejected.

Cause 4 of 6: PutResourcePolicy accepts a document whose statement Resource names a different resource than the request's ResourceArn.
AWS: Smithy: as Cause 3; InvalidArgument (400) is modeled on PutResourcePolicy. Recorded behavior: when a statement's Resource element names a VPC origin ARN other than the ResourceArn parameter (a sibling origin, or a well-formed but never-created VPC origin ARN), the call is refused with HTTP 400, Error.Code 'InvalidArgument' and Message "The specified policy isn't valid (InvalidPolicy). Verify that it's both valid JSON, and that the ARN specified in the policy is the same ARN in the ResourceARN parameter" — fixed text in full (it names no ARN from the request; note AWS's own spelling 'ResourceARN' inside the sentence and the absence of a trailing period). Nothing is attached by the refused call.
Emulator: answers HTTP 200 and stores the mismatched document against the ResourceArn from the request.
Why: a policy is attached under one resource while granting access over another, which is precisely the cross-resource confusion the check exists to prevent. The caller believes it has scoped a grant to origin A while the stored document speaks about origin B; any later authorization decision taken from the stored document applies to the wrong resource, and the mistake is never reported.
Fix: PutResourcePolicy's validation — after parsing the document, require every statement's Resource to be the same ARN as the request's ResourceArn, and refuse a mismatch with InvalidArgument (400) and AWS's InvalidPolicy wording before the store write.
Traces: cloudfront.resource-policy-illegal-update-blocked, cloudfront.resource-policy-put-illegal-update-rejected.

Cause 5 of 6: PutResourcePolicy accepts a statement granting a mutating CloudFront action on a VPC origin.
AWS: Smithy: as Cause 3. Recorded behavior: a statement whose Action grants a mutating VPC-origin action (for example cloudfront:DeleteVpcOrigin) is refused with HTTP 400, Error.Code 'InvalidArgument' and the same fixed Message "The specified policy isn't valid (InvalidPolicy). Verify that it's both valid JSON, and that the ARN specified in the policy is the same ARN in the ResourceARN parameter"; the identical statement with a read-only action (cloudfront:GetVpcOrigin) on the same principal and resource is accepted and stored. Nothing is persisted by the refused call.
Emulator: answers HTTP 200 and stores the document, so the disallowed grant becomes readable.
Why: the resource-policy surface is the only thing standing between a shared VPC origin and a cross-account principal that can delete it. Accepting a mutating grant lets a caller publish a policy AWS would refuse, so the emulator's state models a trust relationship that cannot exist, and a negative test for the disallowed action class passes vacuously.
Fix: PutResourcePolicy's validation — check each statement's Action against the actions this surface permits on a VPC origin and refuse a disallowed action with InvalidArgument (400) and AWS's InvalidPolicy wording; this is the same validation step as Cause 4 and must run before the store write.
Traces: cloudfront.put-resource-policy-illegal-update-rejected.

Cause 6 of 6: the stored policy document is never canonicalized — a single-element Action array is read back as an array where AWS reads it back as a bare string.
AWS: Smithy: GetResourcePolicy output PolicyDocument (string). Recorded behavior: the service parses and re-renders the submitted document, collapsing a one-element Action list to the scalar form, so a document submitted with "Action": ["cloudfront:GetVpcOrigin"] is read back with "Action": "cloudfront:GetVpcOrigin" (and the document otherwise preserved: Version, Sid, Effect, Principal, Resource unchanged). The action value itself is taken from the request; only the scalar-vs-array shape is the service's canonical form.
Emulator: stores and returns the document byte-for-byte as submitted (src/ops/put_resource_policy.rs stores input.policy_document unchanged), so the read-back keeps the one-element array.
Why: a client that round-trips a policy — read it, add a statement, write it back — and compares against what it submitted sees a document that never converges, and any equality or diff check on the canonical form reports a permanent difference. Code that reads statement["Action"] expecting the service's canonical scalar gets a list and mis-handles it.
Fix: the resource-policy state/serializer path (src/ops/put_resource_policy.rs together with src/ops/get_resource_policy.rs and the store's resource-policy representation in src/state.rs) — parse the document on write and render the service's canonical form on read, collapsing single-element Action (and the other list-valued statement members AWS collapses) to the scalar form while preserving every other member.
Traces: cloudfront.resource-policy-json-document-byte-equality, cloudfront.resource-policy-json-document-round-trip.
