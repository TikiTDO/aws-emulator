# Route 53 CIDR collection read paths diverge: listing rows carry an account-stamped Arn, an emptied location is refused 404, and MaxResults is unvalidated

> _Note: this issue was identified against the code base at commit `d1185311883c3d926af6a235180686b5555f406c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListCidrCollections

## Description
FIVE net-new causes on the Route 53 CIDR-collection read surface, all on the same service (route53). Causes 1-3 are the same defect observed on three separate fixtures; causes 4 and 5 are distinct. All five must be closed before this issue is submitted.

Cause 1 of 5 — ListCidrCollections does not report the account's collections in a form that identifies them (fixture route53-cidr-collection-basic-lifecycle, step task#3, ListCidrCollections, status 200 vs 200; the same cluster also covers task#4 of that fixture).
AWS: recorded behavior only for the row layout. Smithy: route53 ListCidrCollections (GET /2013-04-01/cidrcollection) returns CidrCollections -> CollectionSummaries, whose CollectionSummary carries Arn (target ARN, @length 20..2048, pattern \S), Id (UUID, pattern ^[0-9a-f]{8}-(?:[0-9a-f]{4}-){3}[0-9a-f]{12}$), Name and Version; the only modeled error is InvalidInput (HTTP 400). The recording shows the account's collections reported one CollectionSummary each, with Arn in Route 53's global-service layout: fixed text 'arn:aws:route53:::cidrcollection/' (empty region AND empty account field) followed by that collection's own Id, Name as created, Version the collection's current counter. Route 53 is a global service, so the account field of every one of its resource ARNs is empty.
Emulator: every collection the fixture created is absent from the response when the reported rows are matched to the recorded ones by Arn. Replay detail for this step: '$.ListCidrCollectionsResponse.CidrCollections.member[Arn="arn:aws:route53:::cidrcollection/e446b774-9071-41c7-d8ad-ef4228313284"]: missing (expected {...Name: sim2real-probe-route53-cidrcol1-..., Version: 1}, got None)' and the same for the second collection of the same step (ids/names above are per-run fixture values, not requirements). The listing projection builds each row's Arn through the shared helper state::cidr_collection_arn, which renders the ARN through ::engine::emulator_arn with the emulator's account id populated, so a reported row reads 'arn:aws:route53::<account>:cidrcollection/<id>' and matches no collection ARN a client holds.
Why: a client that enumerates CIDR collections and keys them by ARN (to look a collection up, to compare against an ARN returned by another Route 53 response or written into an IAM policy Resource element, or to reconcile a listing against ARNs it stored earlier) finds no row for a collection that exists, so account-wide enumeration and ARN-equality reconciliation both fail even though the collection is there.
Fix: the ListCidrCollections response projection and the shared CIDR-collection ARN rendering it uses (the CollectionSummary construction in the operation's handler and the shared projection helper in the service's state module) — Route 53 resource ARNs must render both the region and the account fields empty. Hypothesis: the ARN layout is the whole of this divergence, because the collections are demonstrably in state (the same fixtures' later per-collection calls succeed). If, after the ARN layout is corrected, the rows are still absent, the deeper defect is in the listing's read of collection state and must be fixed there too — do not close this cause on the ARN edit alone without re-replaying the three fixtures named below.
Traces: route53-cidr-collection-basic-lifecycle#task#3 (representative; cluster also covers task#4).

Cause 4 of 5 — ListCidrBlocks refuses with HTTP 404 a collection/location the fixture has just emptied, where AWS answers 200 with an empty block list (fixture route53-cidr-collection-change-and-delete, step task#5, ListCidrBlocks; the same cluster also covers route53-cidr-collection-management#task#6).
AWS: recorded behavior only. Smithy: ListCidrBlocks (GET /2013-04-01/cidrcollection/{CollectionId}/cidrblocks, success 200) returns CidrBlocks -> CidrBlockSummaries plus NextToken, and models InvalidInput (400), NoSuchCidrCollectionException (404, 'The CIDR collection you specified, doesn't exist.') and NoSuchCidrLocationException (404, "The CIDR collection location doesn't match any locations in your account."). The recording shows that after the collection's blocks have been removed by a change, the enumeration is still a SUCCESS: HTTP 200 carrying a ListCidrBlocksResponse whose CidrBlocks container is present and empty. The requirement is therefore that an existing collection whose blocks have been removed enumerates as an empty result set, not as a not-found refusal; a 404 is reserved for a collection id the account does not hold.
Emulator: the step is answered HTTP 404 and no ListCidrBlocksResponse is produced at all. Replay detail: 'status: expected 200, got 404' and '$.ListCidrBlocksResponse: missing (expected {CidrBlocks: ""}, got None)'. Hypothesis: the refusal comes from the handler's emptied-location guard — the operation treats a location the collection holds no block for as absent and returns NoSuchCidrLocationException with the model's own documentation sentence as its Message; the alternative source is the collection lookup immediately above it returning NoSuchCidrCollectionException. Whichever branch fires, AWS answers 200 with an empty list for this request.
Why: a client that lists a collection's blocks to confirm a removal, or that polls the collection's contents during a change, gets a hard not-found error instead of an empty page. SDK paginators raise rather than yield zero items, idempotent 'remove then verify empty' flows fail, and the 404 is indistinguishable from 'the collection was deleted' — so a caller concludes the resource is gone while it still exists.
Fix: the ListCidrBlocks handler's refusal logic (services/service-com-amazonaws-route53-awsdnsv20130401/src/ops/list_cidr_blocks.rs, the NoSuchCidrLocationException guard around lines 209-222 and the collection lookup at lines 202-204): an existing collection must enumerate to an empty CidrBlocks container when it holds no matching block, reserving 404 for a collection id the account does not hold.
Traces: route53-cidr-collection-change-and-delete#task#5; same cluster at route53-cidr-collection-management#task#6.

Cause 5 of 5 — ListCidrCollections accepts a non-positive MaxResults and answers 200 where AWS refuses the request with 400 InvalidInput (fixture route53-cidr-collection-error-paths, step task#3, ListCidrCollections).
AWS: Smithy: ListCidrCollections input MaxResults (target Integer, httpQuery 'maxresults') is the @paginated pageSize member, and the operation's only modeled error is InvalidInput, errorKind client, HTTP 400, documented 'The input is not valid.' The recording shows a request whose page size is not a positive integer refused with HTTP 400 and the restXml error envelope ErrorResponse/Error with Type 'Sender', Code 'InvalidInput' and Message 'Max items must be a positive integer.' — that Message is entirely fixed text for this error class (it names no request value, no id and no limit), so it must be reproduced verbatim; the RequestId element beside it is a per-run value and is not part of the requirement.
Emulator: the request is answered HTTP 200 with a normal ListCidrCollectionsResponse. Replay detail: 'status: expected 400, got 200' and '$.ErrorResponse: missing (expected {Error: {Type: Sender, Code: InvalidInput, Message: "Max items must be a positive integer."}, ...}, got None)'. The handler applies no validation to the member: it reads input.max_results, substitutes the service default when absent and then clamps the caller's value into 1..=page-size maximum, so a zero or negative page size is silently turned into a valid one instead of being refused.
Why: a client sending a bad page size (a mis-propagated 0, a negative value from an unvalidated config) is told its request succeeded and is served a full first page. The bug that AWS surfaces immediately as InvalidInput is hidden, and error-handling paths that exist to catch it are never exercised; a client that relies on the refusal to validate user input accepts values AWS rejects.
Fix: the ListCidrCollections handler's input validation (services/service-com-amazonaws-route53-awsdnsv20130401/src/ops/list_cidr_collections.rs, the max_results handling around lines 172-175, which must refuse rather than clamp), returning the operation's modeled InvalidInput (HTTP 400) with the Message above.
Traces: route53-cidr-collection-error-paths#task#3.
