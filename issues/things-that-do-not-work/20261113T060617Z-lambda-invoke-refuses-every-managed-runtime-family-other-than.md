# Invoke refuses every managed runtime family other than Python and Node.js with 502 InvalidRuntimeException, so provided.al2023, Java, Ruby and .NET functions can never run

> _Note: this issue was identified against the code base at commit `65a54ca45d4af5e17b89290ffb091f639a3756dd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
ONE root cause. Cause 1 of 1: the Invoke data plane has a runtime-support gate that admits only the python* and nodejs* identifiers and refuses every other identifier, even though CreateFunction accepted that identifier and reported the function Active.

AWS: Smithy (services/service-com-amazonaws-lambda-awsgirapiservice): Invoke -> errors include InvalidRuntimeException (errorKind server, httpError 502, documented as "The runtime or runtime version specified is not supported."); InvokeWithResponseStream models the same error. AWS raises it only for an identifier Lambda does not support. provided.al2023, provided.al2, java8.al2, java17, java21, ruby3.3, ruby3.4, dotnet8 and dotnet10 are all supported Lambda runtime identifiers, so Invoke on a function created with one of them answers 200 with the handler's payload (or a 200 carrying X-Amz-Function-Error for a handler error), never 502 InvalidRuntimeException. The emulator itself proves AWS accepts these identifiers: CreateFunction with each of them succeeded and the function reached Active, so the control-plane half already treats them as supported.

Emulator: every Invoke (and InvokeWithResponseStream) of such a function is refused with 502 InvalidRuntimeException and the emulator-authored message "The runtime <runtime> is not supported by this emulator, which runs the Python and node runtimes." The fixed text of that sentence is the emulator's own invention — it is not AWS wording at all — and <runtime> is the function's configured Runtime taken from state. Observed for the identifiers provided.al2023, java8.al2, java17, java21, ruby3.3, ruby3.4, ruby4.0 and dotnet10 across the checks listed below. The botocore retry layer retries it (it is modeled as a server-kind 502), so each call burns the full retry budget before surfacing ("reached max retries: 3").

Why: a client that deploys a Java, Ruby, .NET, Go or custom (provided.*) function against the emulator can create it, see it Active, and then never invoke it. Nothing about these runtime families is observable: the Runtime API contract on provided.al2023 (/runtime/invocation/next, /response, /error, init-error, request-id echo, trace-id and invoked-arn headers), the Java handler resolution/JVM lifecycle, the Ruby interpreter selection and error typing, and the .NET serializer/handler-string behaviour are all unreachable. A client also cannot distinguish "this runtime is genuinely unsupported by Lambda" (a real 502 InvalidRuntimeException) from "this emulator did not implement it", because the emulator reuses the modeled error for both.

Fix: the Invoke / InvokeWithResponseStream handler's runtime dispatch in the lambda service crate (the execution-environment/runtime-selection component behind Invoke, not its request validation): either run the configured runtime family, or stop reusing InvalidRuntimeException for runtimes AWS supports. Any refusal that survives must not carry emulator-authored prose in the AWS error message. Note: the open issue 20261111T081112Z-lambda-managed-runtimes-are-stub-interpreters-10-node covers the *Node.js/Python* interpreters being stubs — it does not cover a runtime family being refused outright at Invoke, which is this cause.

Traces: the 63 failing checks in trace_ids. Representative detail, verbatim: "botocore.errorfactory.InvalidRuntimeException: An error occurred (InvalidRuntimeException) when calling the Invoke operation (reached max retries: 3): The runtime provided.al2023 is not supported by this emulator, which runs the Python and node runtimes." Families covered: provided.al2023 custom runtime + Runtime API contract (15 custom-runtime checks, plus execution-environment-contract-provided-al2023, provided-al2023-bootstrap-serves-the-runtime-api, provided-al2023-application-log-level-fatal..., runtime-api-poll-loop-shell-bootstrap, layer-custom-runtime-bootstrap..., native-elf-arch-execution..., and both go-bootstrap checks), java8.al2/java17/java21 (15 checks), ruby3.3/ruby3.4/ruby4.0 (13 checks), dotnet10 (12 checks).

## Evidence
Expected (AWS): Invoke on a function whose Runtime is provided.al2023 / java21 / ruby3.4 / dotnet10 returns HTTP 200 with the handler's response payload (or 200 + X-Amz-Function-Error for a handler error). InvalidRuntimeException (502) is reserved for identifiers Lambda does not support.

Actual (emulator): HTTP 502 InvalidRuntimeException, message "The runtime <runtime> is not supported by this emulator, which runs the Python and node runtimes." — fixed text is emulator-authored and not AWS's; the only variable part is <runtime>, read from the function's configuration. Same for InvokeWithResponseStream (seen on lambda.custom-runtime-streaming-response-mode..., which is separately owned).

1. CreateFunction with Runtime="provided.al2023" (or java21, ruby3.4, dotnet10), a valid Role and a Code ZipFile; wait for State=Active — all of this succeeds.
2. Call Invoke on that function with any Payload.
3. Observe HTTP 502 InvalidRuntimeException "The runtime provided.al2023 is not supported by this emulator, which runs the Python and node runtimes." instead of a 200 carrying the handler's response.
4. Repeat with InvokeWithResponseStream for the same refusal.
