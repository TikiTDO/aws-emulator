# RDS data-source introspection diagnoses the wrong failure and authors its own refusal text (2 causes)

> _Note: this issue was identified against the code base at commit `f7067607673c78bda9a2a88ab2c9b41127d89615`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetDataSourceIntrospection

## Description
One shared fault, two net-new divergence clusters (both service=appsync, both reported with owned_by [] and stub_path "" in this replay): the diagnostic text of the RDS data-source introspection plane is emulator-authored rather than AWS's. Both the asynchronous failure detail that GetDataSourceIntrospection serves and the BadRequestException message that StartDataSourceIntrospection returns for a config-less request state a different condition, in different words, from AWS. Both causes must be closed before this issue is submitted.

Related open issues that do NOT own these clusters: 20261111T092526Z-appsync-getintrospectionschema-returns-a-non-canonical-sdl-the.md and 20261109T053905Z-appsync-createresolver-kind-pipelineconfig-datasourcename-validation-refusals-and.md concern GetIntrospectionSchema (the GraphQL schema endpoint), not the Start/GetDataSourceIntrospection RDS plane; 20261029T200818Z-appsync-validation-refusals-are-emulator-authored-wrong-message.md covers the same class of emulator-authored refusal text for CreateDataSource/CreateResolver but the replay reports owned_by [] for the cluster below, so it does not exercise it.

Cause 1 of 2 - GetDataSourceIntrospection reports "HttpEndpoint is not enabled" for an RDS cluster that does not exist (fixture appsync-datasource-introspection, step task#2).
AWS: recorded behavior only for the detail text. Smithy: GetDataSourceIntrospection = GET /v1/datasources/introspections/{introspectionId}, code 200; output GetDataSourceIntrospectionResponse {introspectionId, introspectionStatus: enum DataSourceIntrospectionStatus (PROCESSING|FAILED|SUCCESS), introspectionStatusDetail: String, introspectionResult}. StartDataSourceIntrospection's RdsDataApiConfig requires resourceArn (@length 20..2048, @pattern ^arn:[a-z-]*:rds:[a-z0-9-]*:\\d{12}:cluster:[0-9A-Za-z_/-]*$), secretArn and databaseName. When the introspection is started against a well-formed resourceArn that names no existing cluster, AWS settles the job and serves the fixed detail sentence 'RDS cluster was not found for supplied resource arn.' - the whole string is fixed text, with no value interpolated from the request.
Emulator: 200 with the same introspectionId/status but a detail that diagnoses an entirely different condition and interpolates the arn - expected 'RDS cluster was not found for supplied resource arn.', got 'HttpEndpoint is not enabled for resource <resourceArn>.' (recorded instance: 'HttpEndpoint is not enabled for resource arn:aws:rds:us-east-1:000000000000:cluster:non-existent-cluster-appsync-probe.'; the arn is a request value, the 'HttpEndpoint is not enabled for resource ' / '.' wrapper is the emulator's own fixed text). Hypothesis: the handler checks the Data API (HTTP endpoint) flag before it checks that the cluster resolves at all, so a missing cluster is reported as a disabled Data API.
Why: the detail string is how a client distinguishes a typo/wrong-account ARN (retry with a corrected ARN) from a real cluster whose Data API is switched off (enable it and retry). Against the emulator every unresolvable ARN is reported as the latter, so automation that branches on the detail - or asserts it in a test - takes the wrong remediation path and a condition AWS never reports becomes the default answer.
Fix: the StartDataSourceIntrospection/GetDataSourceIntrospection job handler and the state it records - resolve the cluster named by rdsDataApiConfig.resourceArn first and record the not-found detail for a cluster that does not exist, keeping the HttpEndpoint detail for a cluster that exists with the Data API disabled.

Cause 2 of 2 - StartDataSourceIntrospection's config-less refusal message is emulator-authored (fixture appsync-start-introspection-config-validation-errors, step task#1).
AWS: recorded behavior only for the wording. Smithy: StartDataSourceIntrospection = POST /v1/datasources/introspections, code 200; input StartDataSourceIntrospectionRequest has the single optional member rdsDataApiConfig: RdsDataApiConfig, so a request that omits it is structurally valid and must be refused by the handler, not by the serializer; modeled errors BadRequestException(400), UnauthorizedException(401), NotFoundException(404), InternalFailureException(500). A request carrying no usable data-source config is refused with HTTP 400 and the fixed message 'No data source config defined.' - the whole sentence is fixed text, with no request value in it.
Emulator: the status and error class match (400), but the message is its own - expected 'No data source config defined.', got 'Missing RDS Data API config' (also emulator-authored: no terminating period, names the RDS Data API config specifically rather than the general absence of a config).
Why: the message is a requirement of the error class, so a client or test that matches on AWS's sentence does not recognise the emulator's refusal; and because it names only the RDS Data API config, it reads as "that one config is missing" rather than "no config was given at all", which misdirects a caller that supplied some other config shape.
Fix: the StartDataSourceIntrospection input validation - emit BadRequestException with AWS's fixed sentence for a request with no data source config.
Traces: appsync-start-introspection-config-validation-errors#task#1 (same cluster: appsync-start-introspection-missing-config-error#task#1, appsync-start-introspection-missing-rds-config-error#task#1).
