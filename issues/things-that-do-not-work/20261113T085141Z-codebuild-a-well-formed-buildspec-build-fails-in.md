# CodeBuild: a well-formed buildspec build FAILS in its BUILD phase and exports nothing, and a build with the project's S3 artifacts FAILS where the same build with NO_ARTIFACTS succeeds (2 causes)

## Operation

## Description
TWO net-new root causes in the codebuild crate (services/service-com-amazonaws-codebuild-codebuild-20161006), both on the StartBuild/build-execution seam. BOTH must be closed before this issue is resolved.

Relationship to existing open issues (neither carries a replay key for the two checks below, so neither covers them): 20261109T181128Z-codebuild-buildspec-commands-are-not-run-through-a.md describes buildspec commands not being run through a shell and owns a DIFFERENT assertion of the first check (its YAML-parse-context key, `run#17` / 'cannot start any token'); on this checkout that check now gets PAST the parse-context assertion and fails later, on its positive control. 20261109T181128Z-codebuild-s3-buildspec-commands-run-without-a-shell.md is filed against the service heading codebuild__s3, not codebuild, and carries no key for the second check. 20261108T000000Z-codebuild-a-build-still-faults-at-provisioning-the-nodejs-runtime-checks-remain-open.md describes a FAULT at PROVISIONING; in both cases below PROVISIONING and DOWNLOAD_SOURCE report SUCCEEDED, so these builds reach a real BUILD verdict and that issue does not describe them.

Cause 1 of 2: a build whose buildspec is well-formed and whose only build command is an `export` of a shell-expanded value ends with buildStatus FAILED, its BUILD phase phaseStatus FAILED, and no exported environment variable.
AWS: Smithy StartBuild -> {build: Build}; Build.buildStatus is a StatusType enum (SUCCEEDED/FAILED/FAULT/IN_PROGRESS/STOPPED/TIMED_OUT), Build.phases is a list of BuildPhase{phaseType (BuildPhaseType enum ... DOWNLOAD_SOURCE, INSTALL, PRE_BUILD, BUILD, POST_BUILD, UPLOAD_ARTIFACTS, FINALIZING, COMPLETED), phaseStatus, contexts: PhaseContext{statusCode, message}}, and Build.exportedEnvironmentVariables is a list of ExportedEnvironmentVariable{name, value}. The execution mechanism itself is recorded behavior only: AWS runs each entry of a phase's `commands` list through a POSIX shell in the build container, so parameter expansion and arithmetic expansion are evaluated, a command named in `env/exported-variables` is picked up after the build phase, and a command that exits zero leaves the phase SUCCEEDED. For a NO_SOURCE / NO_ARTIFACTS project whose buildspec declares `env: exported-variables: [X]` and whose build phase runs `export X="$(( SEED * 7 + 3 ))"` with SEED supplied via environmentVariablesOverride, the recording shows buildStatus SUCCEEDED, every phase SUCCEEDED, and exportedEnvironmentVariables containing X with the arithmetic result of the seed the request supplied.
Emulator: that same build ends buildStatus FAILED with phases [(SUBMITTED, SUCCEEDED), (QUEUED, SUCCEEDED), (PROVISIONING, SUCCEEDED), (DOWNLOAD_SOURCE, SUCCEEDED), (BUILD, FAILED), (COMPLETED, null)] — the BUILD phase itself fails on a command that must exit zero, and no exported variable is produced. Hypothesis: the command string is handed to an executable lookup rather than to a shell, so `export`/`$(( ))` is never evaluated and the command reports a non-zero status; that is the mechanism described in the open shell issue above, but no filed issue carries this check's key, and the observable divergence here is the build's FAILED verdict and the missing exportedEnvironmentVariables entry, not a phase-context message.
Why: a client cannot run any realistic buildspec. The documented exported-variables contract (ExportedEnvironmentVariable, the mechanism CodePipeline uses to pass values between stages) never yields a value, and a build a caller expects to SUCCEED is reported FAILED, so any gate keyed on buildStatus takes the wrong branch and any downstream stage reading an exported variable sees nothing.
Fix: the buildspec command runner and the exported-variable collection step in the codebuild build-execution component — execute each command through a shell with the build's environment exported, honour the resulting wait status when setting the phase's phaseStatus, and populate Build.exportedEnvironmentVariables from the names declared in `env/exported-variables` after the build phase.
Traces: codebuild.codebuild-invalid-buildspec-yaml-rejected-before-the-build-phase-runs (its positive control: AssertionError "the control build must SUCCEED on the same project, got 'FAILED'; phases=[('SUBMITTED', 'SUCCEEDED'), ('QUEUED', 'SUCCEEDED'), ('PROVISIONING', 'SUCCEEDED'), ('DOWNLOAD_SOURCE', 'SUCCEEDED'), ('BUILD', 'FAILED'), ('COMPLETED', None)]").

Cause 2 of 2: on one project, a build that uses the project's configured S3 artifacts ends FAILED, while the SAME build started with artifactsOverride {type: NO_ARTIFACTS} ends SUCCEEDED — so the artifact-producing/uploading path, not the command phase, fails the build.
AWS: Smithy StartBuild.artifactsOverride: ProjectArtifacts; Build.artifacts: BuildArtifacts{location, sha256sum, md5sum, artifactIdentifier, ...}. Recorded behavior: for a project whose artifacts are {type: S3, location: <bucket>, name: <artifact-name>, packaging: NONE} and whose buildspec declares `artifacts: files: [result.txt]`, a build with no override ends buildStatus SUCCEEDED, reports artifacts.location of the form `arn:aws:s3:::<bucket>/<build-uuid>/<artifact-name>` (build-uuid being the part of Build.id after the colon, artifact-name the project's artifacts name — both values from the request/state, not fixed text), and leaves exactly one object in the bucket at key `<build-uuid>/<artifact-name>/result.txt` whose bytes are the file the build phase wrote. The NO_ARTIFACTS override build also ends SUCCEEDED, reports no artifacts.location, and uploads nothing.
Emulator: the NO_ARTIFACTS build ends SUCCEEDED and correctly uploads nothing, and the two StartBuild refusals this check also exercises (InvalidInputException 'Invalid artifacts: location is required' and 'Bucket <name> does not exist') behave correctly — but the subsequent default build on the same project, with the same buildspec, ends buildStatus FAILED. The failure therefore appears only on the artifacts path. Hypothesis: the declared file is never created (so UPLOAD_ARTIFACTS has nothing matching `artifacts/files`) or the upload to the project's S3 location itself errors; the recording and the replay only establish that the identical build succeeds with NO_ARTIFACTS and fails with the project's S3 artifacts.
Why: a client cannot retrieve any build output. Every S3-artifacts project reports its builds as FAILED even though the build work itself completed, so the artifact object, the BuildArtifacts.location a caller resolves, and the checksum fields are all unavailable, and a deploy step gated on buildStatus never runs.
Fix: the UPLOAD_ARTIFACTS stage of the codebuild build-execution component together with the artifact-upload state/serializer — collect the files matched by the buildspec's `artifacts/files` from the build workspace, upload them under `<build-uuid>/<artifact-name>/` in the project's artifacts bucket, set Build.artifacts.location to the `arn:aws:s3:::<bucket>/<build-uuid>/<artifact-name>` form, and only fail the build when an artifact declared in the buildspec genuinely has no match.
Traces: codebuild.start-build-artifacts-override-rejected-without-a-location-and-no-artifacts-uploads-nothing (AssertionError "the default build ended 'FAILED'", reached after the NO_ARTIFACTS build on the same project asserted SUCCEEDED and uploaded nothing).
