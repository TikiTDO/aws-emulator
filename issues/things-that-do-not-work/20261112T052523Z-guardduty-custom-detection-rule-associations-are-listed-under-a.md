# Custom detection rule associations are listed under a re-minted identity rather than the association's established id

> _Note: this issue was identified against the code base at commit `03f875ec5891a5d63db09920b5ca7a9cbf214550`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
This issue bundles 4 distinct net-new replay clusters. All four are in the guardduty service, all are on ListCustomDetectionRuleAssociations, and all are on the `associationId` member of an AssociationSummary entry the replay locates by that entry's own `arn`. Fix ALL FOUR causes and re-replay every fixture#step named under Traces (the representative in Issue-Trace/Issue-Step plus the three in Issue-Trace-Ids) before submitting; closing fewer than four leaves this issue's remaining causes unexercised. None of the four clusters is blocked by a stub (stub_path="") and none is marked owned by an open issue (owned_by=[]).

SHARED FAULT: an association is listed under an identity the emulator minted for itself at create time, not under the identity the scenario (and therefore the client) already holds for that association. In every one of the four clusters the HTTP status is correct (200), the entry is present and selectable by its ARN, and every other member of the summary matches; only `associationId` is reported as a value_mismatch.

READ THE REPORT CAREFULLY — the rendering is misleading. The comparator renders expected and actual with the SAME visible 32-hex digits, which earlier issues on this family read as "the id prints the same, so the difference must be JSON type / case / whitespace". Code reading says otherwise and a fixer should not spend time on a serialization hypothesis: services/service-com-amazonaws-guardduty-guarddutyapiservice/src/ops/list_custom_detection_rule_associations.rs lines 248-264 (`fn summary`) take `association_id` from `record.association_id` (line 250) and derive `arn` from that SAME field via `crate::state::custom_detection_rule_association_arn` (lines 251-255), so the id member and its own ARN suffix are structurally incapable of disagreeing. The selector the replay uses is built from the ARN the emulator actually served, so the resolved selector and the actual id are necessarily the same characters — that is why both sides print identically. The value that diverges is the one the RECORD carries: services/service-com-amazonaws-guardduty-guarddutyapiservice/src/ops/create_custom_detection_rule_association.rs line 245 writes `state.mint_id()` onto the new DetectionRuleAssociationRecord on every non-ClientToken-replay create path (the only reuse path is the ClientToken lookup at lines 185-191; the duplicate check at lines 203-223 refuses with ConflictException instead of resolving the stored identity). So the listing faithfully reports a self-consistent pair whose identity is simply not the association's. Hypothesis for the rendering: the replay resolves the fixture's bound id variable out of the live response before printing, so the printed "expected" is the emulator's own id while the compared expected is the recorded identity.
