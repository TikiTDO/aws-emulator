# apigateway: 3 net-new causes — non-proxy HTTP integrations and VTL-templated MOCK integrations never produce a response at a deployed stage (6 checks hang to the 60 s cap), and the payload-size 413 body is 'Request Too Long' instead of AWS's 'HTTP content length exceeded 10485760 bytes.'

> _Note: this issue was identified against the code base at commit `458648e5d077c2a050f91416b837fc3012b6ecb7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke (execute-api data plane)

## Description
Three distinct net-new root causes in the API Gateway REST data plane, all grounded in failing behavioral checks of this suite. None of the seven checks below is marked ALREADY FILED, and none is marked OWNED by an open issue.

RELATED BUT NOT COVERING: open issue 20261107T191316Z-apigateway-4-net-new-causes-non-proxy-http.md describes a non-proxy-HTTP-integration 500 and a VTL-evaluation 500 for the same feature areas, but it does not carry the replay keys these checks now fail on — in that issue every one of these checks failed inside the check's own `_poll_http`/`_poll` deadline (150 s / 120 s) with a last observation of `(500, '{"message":"Internal server error"}')`, whereas in this run all six produce NO observation at all: the check is killed by the harness at `Check timed out after 60.0s` before its poll deadline is ever reached. The symptom this run records is therefore "the stage never produces the asserted response inside the check's wall clock", not "the stage answers 500". Causes 1 and 2 below are written from that evidence only. A fixer should treat this issue as the live replay list for those checks.

=== Cause 1 of 3: a deployed stage never serves a request routed through a non-proxy (type=HTTP) integration ===
AWS: Smithy: PutIntegration.type -> IntegrationType enum (HTTP, AWS, MOCK, HTTP_PROXY, AWS_PROXY) with `integrationHttpMethod`, `uri`, `requestTemplates`, `requestParameters`, `passthroughBehavior`; PutIntegrationResponse.selectionPattern/responseTemplates select and shape the method response. For type=HTTP, API Gateway renders the matching request template, calls `uri` with `integrationHttpMethod`, picks an integration response by selectionPattern, renders its response template and serves the mapped method-response status. Where `passthroughBehavior=NEVER` and the request Content-Type matches no `requestTemplates` key, AWS refuses the request itself with HTTP 415 and the UNSUPPORTED_MEDIA_TYPE gateway response (so a PutGatewayResponse customisation for that responseType, with `$context.error.responseType` substituted, is what the client receives) and the integration is never called; with `passthroughBehavior=WHEN_NO_MATCH` the same body is forwarded and served. Where the `uri` contains `${stageVariables.<name>}`, the value is substituted per request from the invoking stage's `variables`, so two stages created from ONE deployment reach different backends and a `variables` edit re-points a stage with no redeploy. Recorded behavior only for the marker bodies and 415/200 statuses the checks assert.
Emulator: every check whose claim requires a request to traverse a type=HTTP integration on a deployed stage produces no asserted observation at all — the check is terminated at the harness cap (`Check timed out after 60.0s`) while its bounded poll of the stage invoke URL is still re-issuing. The 415 refusal leg, the per-stage `${stageVariables.*}` URI substitution leg and the request/response template round trip through a real backend are therefore all unobservable. The same runs serve plain MOCK methods whose only template is a literal `{"statusCode": 200}`, and the control-plane calls that configure these integrations (PutIntegration, PutIntegrationResponse, PutGatewayResponse, CreateDeployment, CreateStage) all succeed, so the defect is in the data-plane integration dispatcher, not in the control plane.
Why: a client modelling the canonical "REST API in front of an existing HTTP backend" shape gets no response at all for every call. Request/response transformation, per-stage backend selection through stage variables, and strict-passthrough media-type refusal cannot be exercised, and a negative test that expects 415 hangs instead of being refused.
Fix: the execute-api data-plane integration dispatcher for IntegrationType HTTP in the apigateway service crate — the outbound integration client (it must complete or fail fast rather than leaving the request unanswered), its `${stageVariables.*}` URI substitution, and the passthroughBehavior gate that must emit the 415 UNSUPPORTED_MEDIA_TYPE gateway response before the integration is called.
Traces: apigateway.apigw-strict-passthrough-rejects-an-unmapped-content-type-with-415, apigateway.apigw-stage-variable-selects-a-different-backend-per-stage-from-one-deployment, apigateway.apigw-vtl-request-and-response-templates-transform-a-real-body (this last one wires an HTTP front onto a MOCK backend, so it also exercises Cause 2).

=== Cause 2 of 3: a deployed stage never serves a MOCK method whose mapping template uses anything beyond a literal body ===
AWS: Smithy: PutIntegration.requestTemplates and PutIntegrationResponse.responseTemplates are MapOfStringToString of VTL templates. API Gateway's template language binds `$input.params(<name>)`, `$input.params().header.get(<name>)`, `$input.path('$.<member>')`, `$util.escapeJavaScript(...)`, `$stageVariables.<name>` and `$context.*` (including `$context.requestId`), supports the `#if`/`#set` directives, and supports the response sinks `#set($context.responseOverride.status = <int>)` and `#set($context.responseOverride.header.<Name> = ...)`. A numeric literal assigned to `$context.responseOverride.status` replaces the declared method-response status (200 -> 201); the quoted STRING "201" does NOT, while a `responseOverride.header` assignment still takes effect on that same request. CreateDeployment.canarySettings (DeploymentCanarySettings: percentTraffic, stageVariableOverrides, useStageCache) makes a 100%-traffic canary serve the canary snapshot with its `stageVariableOverrides` applied to the templates, 0% serve the base snapshot again, and a copy patch from /canarySettings/deploymentId promote the canary. Recorded behavior only for the specific rendered bodies and the 201/200 pair the checks assert.
Emulator: every check whose claim requires evaluating one of those constructs on a deployed MOCK method produces no asserted observation at all — terminated at `Check timed out after 60.0s` while polling the stage invoke URL. Constructs involved: `$input.params('id')` + `$input.params().header.get('X-Req')` + `$context.requestId` (12 simultaneous invocations, each of which must get back its own query/header values and a distinct `x-amzn-RequestId` matching `$context.requestId`); `#set($context.responseOverride.status = 201)` with `#set($context.responseOverride.header.X-Overridden = ...)`; `$util.escapeJavaScript($stageVariables.release)` under base/canary stage-variable overrides. Plain MOCK methods whose only template is the literal `{"statusCode": 200}` are served in the same runs, so the failure is in template evaluation and the `$context.responseOverride` sink, not in MOCK dispatch.
Why: mapping templates are the primary way a REST API shapes requests and responses. A client gets no response instead of the rendered body, and cannot observe per-request `$context` identity under concurrency, status/header overrides, stage-variable substitution, or canary traffic shift and promotion at all. Because the concurrency check never completes, there is also no evidence that concurrent invocations of one stage are isolated from each other.
Fix: the VTL mapping-template evaluator used by the execute-api data plane (the `$input` / `$util` / `$stageVariables` / `$context` bindings and `#if`/`#set` directive handling) and the `$context.responseOverride` status/header sink that feeds the response serializer; plus the canary-snapshot selection path that applies `canarySettings.stageVariableOverrides` to those bindings.
Traces: apigateway.apigw-concurrent-invocations-through-one-stage-keep-per-request-identity, apigateway.apigw-response-override-status-requires-numeric-value, apigateway.canary-deployment-traffic-shift-and-promotion.

=== Cause 3 of 3: the payload-size 413 carries the wrong message text ===
AWS: recorded behavior only (this is the fixed, non-adjustable "API Payload Size — 10 Megabytes — Adjustable: No" REST API quota, not a modelled member). A body over 10485760 bytes is refused at the front door with HTTP 413, Content-Type `text; charset=utf-8`, and a PLAIN-TEXT body that names the limit: `HTTP content length exceeded 10485760 bytes.` The whole sentence is fixed text except the byte count, which is the limit in force (10485760 for a REST API). The refusal happens before the gateway-response substitution pipeline, so a REQUEST_TOO_LARGE PutGatewayResponse customisation configured on the same method is NOT served, and the integration is never reached. A body just under the limit is accepted and reaches the integration.
Emulator: the status (413), the absence of the REQUEST_TOO_LARGE customisation, the absence of the integration marker and the `text; charset=utf-8` content type are all correct, but the body is the single phrase `Request Too Long` — it never names the limit. `Request Too Long` is the wording of the REQUEST_TOO_LARGE gateway response's default `message` field, not the front-door payload-size body, so the handler appears to be reusing the gateway-response default phrase in place of the fixed sentence.
Why: a client (or an SDK/test harness) that distinguishes a payload-size refusal from other 413s by the message, or that parses the enforced limit out of it, reads the wrong thing; the limit the service enforced is not reported anywhere in the response.
Fix: the execute-api front-door payload-size guard in the apigateway service crate — the body it writes for the over-limit 413 must be the fixed sentence with the enforced byte limit interpolated, not the REQUEST_TOO_LARGE gateway-response default message.
Traces: apigateway.apigw-payload-over-the-ten-megabyte-limit-rejected-with-413.

## Evidence
Cause 1 — expected: the deployed stage serves the type=HTTP integration's mapped response (200 plus the backend's marker body), and the `passthroughBehavior=NEVER` resource refuses an unmapped Content-Type with 413... correction: with HTTP 415 carrying the customised UNSUPPORTED_MEDIA_TYPE gateway response, while its WHEN_NO_MATCH twin serves the same body 200. Actual: no HTTP observation is ever recorded — the three checks are killed by the harness with `Error: Check timed out after 60.0s` while `_poll_http` (deadline 150.0 s, interval 3.0 s) is still re-issuing the request against `ctx.rest_api_url(apiId, stage)`. The checks' own poll deadline (150 s) is longer than the harness cap (60 s), so the stage had 60 s of repeated requests and never once satisfied the predicate `status == 200` / `status == 415`.

Cause 2 — expected: 200 with the rendered template body (12 distinct `$input.params('id')`/header echoes and 12 distinct `$context.requestId` values under concurrency); 201 for `#set($context.responseOverride.status = 201)` and 200 for `#set($context.responseOverride.status = "201")`, both with the `X-Overridden` responseOverride header; `{"snapshot":"v1","release":"base"}` then the canary's `release=canary` override. Actual: `Error: Check timed out after 60.0s` for all three, with no HTTP observation recorded — the polls (`_poll` deadline 150.0 s, `_poll_http` deadline 120.0 s, interval 3.0 s) never satisfied their predicates inside the 60 s the harness allowed.

Cause 3 — expected body for a 10551296-byte POST (64 KiB over the 10485760-byte limit): the exact text `HTTP content length exceeded 10485760 bytes.` Actual, from apigateway.apigw-payload-over-the-ten-megabyte-limit-rejected-with-413: `AssertionError: expected AWS's fixed built-in 413 body naming the documented 10485760-byte limit ('HTTP content length exceeded 10485760 bytes.'), got 'Request Too Long'`. The preceding assertions in the same check passed, so status 413, `content-type: text; charset=utf-8`, absence of the integration marker and absence of the REQUEST_TOO_LARGE customisation marker are all already correct; only the message text diverges. Fixed text of the requirement: `HTTP content length exceeded ` ... ` bytes.`; variable part: the enforced byte limit (10485760 for a REST API). `Request Too Long` is not AWS's wording for this refusal.
