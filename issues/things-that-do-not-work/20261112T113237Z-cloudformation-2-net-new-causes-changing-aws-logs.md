# cloudformation: 2 net-new causes — changing AWS::Logs::LogStream's LogGroupName is applied in place instead of replacing the stream (no DELETE_COMPLETE event), and the CancelUpdateStack → UPDATE_ROLLBACK_FAILED → ContinueUpdateRollback flow never settles

> _Note: this issue was identified against the code base at commit `03f4a594008c5934f1cb0fdb48e463418aa26203`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateStack

## Description
Two net-new root causes in the CloudFormation update/rollback engine, found by replaying the two failing checks listed in trace_ids. Both are reached through UpdateStack on a stack the emulator itself created, so both are the emulator's own behaviour. Neither is covered by an existing open issue (the nearest ones are named per cause below).

Cause 1 of 2: an UpdateStack that changes AWS::Logs::LogStream's LogGroupName is executed as an in-place update, so the logical resource is never replaced and CloudFormation emits no DELETE event for the superseded stream. Failing check: cloudformation.logstream-replacement-orphans-old-stream-in-former-group.
AWS:      LogGroupName and LogStreamName are create-only properties of AWS::Logs::LogStream, so changing LogGroupName forces a replacement. CloudFormation then reports the replacement on the logical resource and, as part of it, a DELETE pair for the replaced resource: ResourceStatus DELETE_IN_PROGRESS with ResourceStatusReason "Requested update requires the replacement of the existing resource; deleting existing resource, then creating a new one." and DELETE_COMPLETE with reason "Resource <old-physical-id> delete complete", alongside CREATE_IN_PROGRESS/CREATE_COMPLETE for the new resource and UPDATE_IN_PROGRESS/UPDATE_COMPLETE for the logical id; the stack passes through UPDATE_COMPLETE_CLEANUP_IN_PROGRESS before UPDATE_COMPLETE. Smithy (cloudformation): DescribeStackEvents' ResourceStatus enum declares DELETE_IN_PROGRESS/DELETE_COMPLETE and StackStatus declares UPDATE_COMPLETE_CLEANUP_IN_PROGRESS, so these are modelled states of this path. Recorded behavior for the data plane: the replaced stream is in fact left behind (orphaned) in the former log group with its pre-move events, even though CloudFormation announced DELETE_COMPLETE for it; the fixed text above is the requirement, with the old physical id taken from the request/state.
Emulator: the whole update is reported as an in-place property change. DescribeStackEvents for the move update returns only ('Stream','UPDATE_IN_PROGRESS'), ('<stack>','UPDATE_IN_PROGRESS'), ('Stream','UPDATE_COMPLETE'), ('<stack>','UPDATE_COMPLETE') — there is no CREATE pair for the new stream, no DELETE_IN_PROGRESS/DELETE_COMPLETE for the replaced one, no replacement reason text and no cleanup stack status. The create-only nature of LogGroupName is not honoured at all.
Why:      a client that watches stack events to learn that a resource was replaced (and which physical resource was superseded, so it can reconcile or clean up the orphan AWS leaves in the former group) sees an ordinary in-place update and never learns a replacement happened; automation keyed on the documented DELETE reason strings never fires, and a drift/cleanup pass over the old log group is never triggered.
Fix:      the CloudFormation update engine's change-classification for AWS::Logs::LogStream (its resource schema's create-only properties) plus the replacement path that emits the logical resource's CREATE/DELETE/UPDATE event pairs and the stack's cleanup status. The open issue 20261111T111216Z-cloudformation-logs-a-replacing-update-of-cloudwatch-logs-resources-is.md covers a replacement that IS detected but mis-ordered/mis-reported for the cloudformation__logs checks; it does not cover a LogGroupName change being classified as in-place and carries neither replay key of this issue.
Traces:   cloudformation.logstream-replacement-orphans-old-stream-in-former-group (assertion at run() line 81: "no Stream DELETE_COMPLETE event for the replaced resource").

Cause 2 of 2: the CancelUpdateStack → UPDATE_ROLLBACK_FAILED → ContinueUpdateRollback state machine driven by a Custom:: resource never settles, so the check cannot complete. Failing check: cloudformation.stack-update-cancel-then-continue-rollback.
AWS:      recorded behavior only (the sequence is a CloudFormation state machine, not a single modelled call). CancelUpdateStack on a stack that is UPDATE_IN_PROGRESS abandons the pending forward request and issues a revert request to the custom resource's ServiceToken topic; a FAILED response to that revert leaves the stack in UPDATE_ROLLBACK_FAILED; ContinueUpdateRollback re-issues the same revert request and a SUCCESS response takes the stack to UPDATE_ROLLBACK_COMPLETE; a further ContinueUpdateRollback on the now-stable stack is refused with error code ValidationError and the message "RollbackUpdatedStack cannot be called from current stack status" (fixed text; no variable part). Smithy (cloudformation): StackStatus declares UPDATE_ROLLBACK_IN_PROGRESS, UPDATE_ROLLBACK_FAILED, UPDATE_ROLLBACK_COMPLETE_CLEANUP_IN_PROGRESS and UPDATE_ROLLBACK_COMPLETE, so every state this flow must pass through is modelled.
Emulator: the check never reaches any of its assertions — the replay records only "Error: Check timed out after 60.0s". No step of the flow produced an observable transition in time: the stack/custom-resource exchange (create, forward update request over SNS→SQS, cancel, revert request, failed revert, continue, retry request) does not progress. Hypothesis: the emulator never delivers the custom resource's Update request to the ServiceToken topic (or never leaves UPDATE_IN_PROGRESS after CancelUpdateStack), so every wait in the flow hangs; the recorded detail states only the timeout.
Why:      a client that cancels an in-flight update and then repairs it with ContinueUpdateRollback — the standard recovery for a wedged update — can never complete the recovery: the stack never reaches UPDATE_ROLLBACK_FAILED and never reaches UPDATE_ROLLBACK_COMPLETE, so the stack stays unusable and the refusal wording for the stable-stack case is unreachable.
Fix:      the CloudFormation update/rollback state machine — CancelUpdateStack's abandonment of the pending forward request, the custom-resource request dispatch for the revert, the UPDATE_ROLLBACK_FAILED landing on a FAILED response, and ContinueUpdateRollback's re-dispatch. Related open issues name neighbouring causes but not this replay key: 20261104T112602Z-cloudformation-5-net-new-root-causes-in-the.md (CancelUpdateStack rollback path), 20261104T173700Z-cloudformation-cancelupdatestack-refusals-and-liststacks-summaries-diverge-from.md (CancelUpdateStack refusals) and 20261112T002904Z-cloudformation-2-net-new-causes-continueupdaterollback-s-wrong.md (ContinueUpdateRollback wrong state).
Traces:   cloudformation.stack-update-cancel-then-continue-rollback (harness timeout, 60.0 s, before the first assertion).

Fixed text of the two DELETE reasons: "Requested update requires the replacement of the existing resource; deleting existing resource, then creating a new one." and "Resource <old-physical-id> delete complete" — the physical id is the value from the request/state (here the LogStreamName), not part of the template. The stack name shown above is a per-run generated name and is not a requirement.
Template replayed: one AWS::Logs::LogStream with LogStreamName fixed and LogGroupName taken from a stack parameter; UpdateStack changes only that parameter from the first log group to the second.

Cause 2 — check cloudformation.stack-update-cancel-then-continue-rollback [mismatch]:
  Error: Check timed out after 60.0s
No assertion was reached; the first in-check wait (the custom resource's Create request, then the stack reaching CREATE_COMPLETE) already has a 90 s budget, so the emulator produced no progress in the flow. Expected (AWS): the stack reaches CREATE_COMPLETE, UPDATE_IN_PROGRESS stays pending while the forward request is unanswered, CancelUpdateStack issues the v1 revert request, a FAILED revert lands the stack in UPDATE_ROLLBACK_FAILED, ContinueUpdateRollback re-issues the revert, a SUCCESS response lands UPDATE_ROLLBACK_COMPLETE, and a further ContinueUpdateRollback is refused with ValidationError / "RollbackUpdatedStack cannot be called from current stack status".

## Steps to Reproduce
Cause 1:
1. Create two CloudWatch Logs log groups, each with an unrelated log stream.
2. CreateStack with a template declaring a single AWS::Logs::LogStream whose LogStreamName is fixed and whose LogGroupName comes from a template parameter set to the first group; wait for CREATE_COMPLETE and write an event to the stream.
3. UpdateStack with UsePreviousTemplate=true, changing only the parameter to the second group (LogGroupName is create-only, so this forces replacement); wait for UPDATE_COMPLETE.
4. DescribeStackEvents for the stack: there is no DELETE_IN_PROGRESS/DELETE_COMPLETE (and no CREATE) event for the logical id 'Stream' — only UPDATE_IN_PROGRESS/UPDATE_COMPLETE, i.e. the change was applied in place and no replacement was reported.

Cause 2:
1. Create an SQS queue, an SNS topic, and subscribe the queue to the topic.
2. CreateStack with a template declaring one Custom::Sim2RealProbe whose ServiceToken is the topic ARN and Properties.Marker = "v1"; read the Create request from the queue and answer SUCCESS; wait for CREATE_COMPLETE.
3. UpdateStack with Marker = "v2" and leave the forward Update request unanswered, so the stack stays UPDATE_IN_PROGRESS.
4. CancelUpdateStack, then read the revert (Marker = "v1") request from the queue and answer FAILED.
5. Poll DescribeStacks: the stack never reaches UPDATE_ROLLBACK_FAILED; call ContinueUpdateRollback and observe that no retry request is delivered and the stack never reaches UPDATE_ROLLBACK_COMPLETE. The flow hangs and the check times out.
