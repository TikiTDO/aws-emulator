## Description
This bundle has 4 net-new root causes of service `pipes`; ALL FOUR must be closed before submitting. Each is grounded in failing behavioral checks of this run that the replay report did NOT mark ALREADY FILED or OWNED by an open issue.

Related open issues that do NOT cover these causes (they carry different replay keys and describe different divergences): 20261110T093426Z-pipes-cloudformation-updatestack-switching-an-aws-pipes-pipe.md (its cause is the stack update ending UPDATE_COMPLETE instead of rolling back — the stack now DOES reach UPDATE_ROLLBACK_COMPLETE and the surviving divergence is the reason TEXT, Cause 3 below); 20261107T175408Z-pipes-3-net-new-causes-a-running-pipe.md (named for Cause 4); 20261109T000313Z-pipes-caller-driven-pipe-transitions-leave-statereason-unwritten.md and the ListPipes StateReason-projection issues (those are about StateReason being ABSENT from ListPipes summaries; Causes 1 and 2 here are about the WORDING of a StateReason that IS written on DescribePipe).

Cause 1 of 4: the StateReason a pipe carries when its execution role may not read the source is emulator-authored prose instead of the AWS text.
AWS:      Smithy (com.amazonaws.pipes) models DescribePipe/UpdatePipe output members CurrentState (PipeState, whose values include CREATE_FAILED, START_FAILED, UPDATE_FAILED) and StateReason (PipeStateReason, @length 0..512, pattern ^.*$). The model does not spell the text, so the sentence is recorded behavior: for a pipe whose role cannot call the source-read action, the pipe settles in CREATE_FAILED and StateReason is exactly `Input parameter is invalid from the request due to : The provided customer role does not have permissions to call ReceiveMessage on SQS`. That whole sentence is FIXED text for this error class — it has NO variable parts: no ARN, no role name, no queue name is interpolated. Its only class-dependent portion is the action/service pair named at the end (`ReceiveMessage on SQS` for an SQS source), which follows the configured source type, not the request's identifiers.
Emulator: DescribePipe does reach CurrentState=CREATE_FAILED (that part is right) but returns its own sentence, e.g. `Pipes cannot poll the source arn:aws:sqs:<region>:<account>:<source-queue>: its execution role arn:aws:iam::<account>:role/<role> may not perform sqs:ReceiveMessage on arn:aws:sqs:<region>:<account>:<source-queue>: no identity-based policy allows it.` — i.e. a diagnostic that interpolates the source ARN and the role ARN and uses wording that appears nowhere in AWS.
Why:      StateReason is the only machine-visible explanation of a failed pipe. Clients, CDK/CFN tooling and runbooks match on this sentence (and CloudFormation embeds it verbatim — see Cause 3), so an emulator-authored string makes every permission failure unrecognisable: a client cannot tell a role denial from any other provisioning failure, and anything that greps for `The provided customer role does not have permissions to call` sees nothing.
Emulator: see above. Fix: the pipes create/start/update validation path that writes StateReason when the role's source-read grant check fails (the pipe state machine's failure-reason authoring, not its state transitions, which are already correct).
Traces:   pipes.start-pipe-without-execution-role-permission-denied (asserts the StateReason directly), pipes.deploy-cfn-pipe-whose-role-cannot-read-its-source-fails-the-stack-and-rolls-back and pipes.deploy-cfn-pipe-update-to-a-role-without-source-read-fails-and-rolls-back-to-the-working-pipe (both see the same wrong sentence surfaced through CloudFormation).

Cause 2 of 4: the StateReason a pipe carries when its source queue does not exist is emulator-authored prose instead of the AWS text.
AWS:      Same modeled members as Cause 1 (CurrentState/StateReason). Recorded behavior: CreatePipe naming a well-formed SQS queue ARN in the caller's account/region for a queue that does not exist is ACCEPTED (200, CurrentState CREATING) and refuses asynchronously — the pipe settles in CREATE_FAILED with StateReason exactly `Input parameter is invalid from the request due to : Error occurs while ReceiveMessage on SQS`. This is the whole fixed text of the class; nothing from the request is interpolated, and AWS deliberately does NOT distinguish 'absent queue' in the wording — it reports the failed ReceiveMessage attempt.
Emulator: the pipe reaches CREATE_FAILED but StateReason is `Pipes cannot poll the source arn:aws:sqs:<region>:<account>:<ghost-queue>: it does not exist.` — a different sentence that additionally interpolates the source ARN.
Why:      a client that distinguishes failure classes by StateReason (retry on a transient poll error, re-create the queue, alert) is handed an unknown string; the AWS text it switches on never appears.
Fix:      the same pipes asynchronous create-time source-resolution path as Cause 1 — when the source cannot be polled because it does not resolve, write the modeled AWS sentence.
Traces:   pipes.create-pipe-missing-source-queue-rejected (its CurrentState=CREATE_FAILED assertion passes; only the StateReason assertion fires).

Cause 3 of 4: a CloudFormation AWS::Pipes::Pipe that cannot stabilize reports the raw pipes StateReason as the resource event reason instead of the CloudFormation resource-handler wrapper.
AWS:      Recorded behavior only (the CloudFormation resource provider is not in any Smithy model; the pipes model only supplies the terminal PipeState values and StateReason the provider reads). When the declared pipe cannot stabilize, the stack emits one CREATE_FAILED (create path) or UPDATE_FAILED (update path) StackEvent for that logical resource whose ResourceStatusReason is `Resource handler returned message: "Resource of type 'AWS::Pipes::Pipe' with identifier '<pipe-name>' did not stabilize. Status Reason is <pipe StateReason>" (RequestToken: <token>)`. Everything outside the angle brackets is fixed text of this class and required verbatim, including the nested quoting and the `did not stabilize. Status Reason is ` join. The variable parts come from the request and from state: <pipe-name> is the Name property of the template's pipe, <pipe StateReason> is the pipe's own StateReason (per Cause 1, `Input parameter is invalid from the request due to : The provided customer role does not have permissions to call ReceiveMessage on SQS`), and <token> is a per-run request token that is NOT part of the requirement.
Emulator: the event's ResourceStatusReason is the bare pipes diagnostic — `Pipes cannot poll the source <source-arn>: its execution role <role-arn> may not perform sqs:ReceiveMessage on <source-arn>: no identity-based policy allows it.` The `Resource handler returned message: "..."` envelope, the `Resource of type 'AWS::Pipes::Pipe' with identifier '<name>' did not stabilize. Status Reason is ` prefix and the trailing request-token suffix are all absent.
Why:      the resource-handler wrapper is how a client attributes a stack failure to a resource TYPE and identifier; CI that parses `Resource of type '...' with identifier '...' did not stabilize` to point an operator at the failing resource, and tooling that lifts the inner Status Reason out of the envelope, both fail on these stacks even though the stack status and rollback are now correct.
Fix:      the CloudFormation AWS::Pipes::Pipe resource provider's stabilization-failure reporting (create and update paths) — format the resource event reason with the handler envelope around the pipe's StateReason instead of passing the pipe's reason through.
Traces:   pipes.deploy-cfn-pipe-whose-role-cannot-read-its-source-fails-the-stack-and-rolls-back (create path; the stack does reach ROLLBACK_COMPLETE and the CREATE_FAILED event is emitted — only the reason text diverges), pipes.deploy-cfn-pipe-update-to-a-role-without-source-read-fails-and-rolls-back-to-the-working-pipe (update path; the stack now reaches UPDATE_ROLLBACK_COMPLETE, so the surviving divergence is the reason text).

Cause 4 of 4: a RUNNING pipe whose Target is an EventBridge event bus never publishes the record, so nothing reaches a rule forwarding off that bus.
AWS:      Smithy (com.amazonaws.pipes) models PipeTargetParameters.EventBridgeEventBusParameters with DetailType and Source (plus EndpointId/Resources/Time), which exist because the service PUTS an event on the target bus for each source record. Recorded behavior for the data plane: each polled SQS record is published to the target bus as one event whose `source` is EventBridgeEventBusParameters.Source, whose `detail-type` is EventBridgeEventBusParameters.DetailType, whose `account`/`region` are the pipe's own, and whose `detail` is the SQS record object (with `body`, `messageId` equal to the id SendMessage returned, and `eventSourceARN` equal to the source queue ARN); a bus rule matching that source then forwards it to its own target.
Emulator: nothing is ever published. The check creates the bus, an ENABLED rule on {"source": [...]}, an SQS sink target with the events.amazonaws.com queue policy, a role granting events:PutEvents on the bus, and a RUNNING pipe, sends one message, then polls the sink; the check exhausts the harness budget with no event (`Error: Check timed out after 60.0s`). The control plane accepted and echoed the target parameters, so only the delivery is missing.
Why:      the EventBridge-bus target — the fan-out pattern Pipes exists for — moves nothing, and because the publish never happens the event envelope (source, detail-type, account, region, detail projection) cannot be observed at all. A client wiring queue -> pipe -> bus -> rules sees a pipe reporting RUNNING that drops every record.
Fix:      the pipes data-plane target stage for an EventBridge event-bus target in the pipes service — publish each record of the polled batch to the target bus using the stored EventBridgeEventBusParameters, with the record as the event detail.
Traces:   pipes.event-bus-target-publishes-record-with-detail-type-and-source.
