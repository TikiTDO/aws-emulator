## Description
TWO independent, net-new root causes in the Directory Service (ds) control plane, grounded in the only two failing checks the suite lists under `### ds` that are marked neither "ALREADY FILED" (stub-blocked) nor "OWNED by" an open issue. Both belong to the one service, so they are bundled here; a fixer must close BOTH before submitting. Cause 1 of 2: the @pattern constraint refusal for RegisterEventTopic's TopicName prints the regular expression WITH its leading `^` and trailing `$`, where AWS publishes that member's pattern unanchored — so the ValidationException sentence diverges from AWS's.
AWS: recorded behavior only for the message text (the model states the constraint, not the sentence). RegisterEventTopic(TopicName='<a value containing a dot>') is refused HTTP 400 with error code ValidationException and the message `<n> validation error detected: Value '<value>' at '<memberPath>' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern>`. Fixed text is everything outside the four variable slots: `<n>` the number of detected errors, `<value>` the rejected value taken from the request, `<memberPath>` the lowercase-initial input-member path (`topicName` here), and `<pattern>` the regular expression AWS publishes for that member — for TopicName the recorded refusal publishes `[a-zA-Z0-9_-]+`, with NO `^` and NO `$`. Smithy (services/service-com-amazonaws-directoryservice-directoryservice-20150416/smithy-model/com-amazonaws-directoryservice-directoryservice-20150416.json): TopicName is a string, @length 1..256, @pattern "^[a-zA-Z0-9_-]+$"; RegisterEventTopicRequest$TopicName is @required and carries that pattern; RegisterEventTopic models ClientException / EntityDoesNotExistException / InvalidParameterException / ServiceException, so ValidationException is the front-door constraint error raised before the handler runs. The recorded ordering is also a requirement and is already met: the constraint refusal wins over the not-found refusal, i.e. an illegal TopicName gets ValidationException even when the DirectoryId names no directory (the same check's absent-directory legs — EntityDoesNotExistException `Directory: '<directory id>' does not exist. : RequestId: <rid>` on RegisterEventTopic, DescribeEventTopics and DeregisterEventTopic — all passed).
Emulator: same status, same code, same `<n>`, same `<value>`, same member path, but the trailing regex is the Smithy @pattern verbatim: `… Member must satisfy regular expression pattern: ^[a-zA-Z0-9_-]+$` where AWS sends `… Member must satisfy regular expression pattern: [a-zA-Z0-9_-]+`.
Why: the status, the error code and the message are all requirements of this error class. A client, SDK test or CLI user that asserts on AWS's sentence never matches; and anything that regenerates a client-side pre-validator or a user-facing hint from the published regex gets a STRICTER expression than AWS advertises for this member.
Fix: this crate's shared request-constraint validation layer — the validate step that feeds `crate::scaffolded::Scaffolded::validation` and the pattern-rendering helper it calls. The rule is per-member: the refusal must publish the pattern AWS publishes for that member, so the renderer cannot apply one global anchor policy. Note the tension a fixer must resolve rather than paper over: open issue 20261109T135909Z-ds-3-net-new-causes-every-pattern-validationexception.md (Cause 1) and 20261109T072650Z-ds-validationexception-message-omits-regex-anchors-for-directoryid-pattern.md / 20261109T072650Z-ds-validationexception-message-omits-regex-anchors-for-certificateid-and.md report the OPPOSITE direction for CidrIp, DirectoryName, DirectoryId, TagValue, certificateId and assessmentId (anchors dropped where AWS keeps them). None of those three issues mentions TopicName or carries this check's replay key, so none covers this failure; landing them together means making the renderer reproduce AWS per member instead of flipping one global switch.
Traces: ds.register-event-topic-absent-directory-rejected (the earlier not-found and effect-absence legs of the same check pass; only the TopicName pattern sentence diverges).

Cause 2 of 2: the trust create/verify/delete flow reaches NO verdict — it is killed at the suite's 60 s per-check budget while polling clock-owed transitions, so none of the trust state machine's refusal texts or state assertions is ever graded.
AWS: recorded behavior only. This is a poll-and-wait flow: on AWS a Managed Microsoft AD stays Requested/Creating for 20–45 minutes and the trust transitions (Creating → Created/Failed, delete → gone) take minutes, so a client polls at human intervals — 30 s for the directory stage and 15 s for the trust polls in this flow — and eventually reads the settled value. The contract the flow grades is: CreateTrust to an unresolvable remote domain settles TrustState=Failed with TrustStateReason "An internal service error has been encountered while creating the trust. Please retry the operation." (fixed text, no variable parts); VerifyTrust on it is refused 400 InvalidParameterException "Cannot verify trust in state: Failed : RequestId: <rid>" (fixed text "Cannot verify trust in state: Failed : RequestId: " plus the call's own request id); after DeleteTrust both DescribeTrusts and a second DeleteTrust are refused 400 EntityDoesNotExistException "Trust: <trust id> does not exist : RequestId: <rid>" (fixed text "Trust: " / " does not exist : RequestId: ", with the trust id from the request and the request id from the call).
Emulator: every transient value is held for a span and the settled one is materialised only by a LATER call, so a client that probes immediately after the call that starts a transition always reads the transient value and learns the settled one a full poll interval later — one interval paid per transition. src/state.rs:119 TRANSITION_SPAN = 500 ms (documented as falling due 250–750 ms after the call that starts it, explicitly so an immediate caller still sees the transient state), :146 DIRECTORY_BUILD_SPAN = 3 s for Creating, :156 directory_active_at = create + TRANSITION_SPAN + DIRECTORY_BUILD_SPAN; the teardown is the same kind of chain, src/state/directory_deletion.rs:58-111 (Deleting → Deleted → record forgotten, one span per step), and advance_clock materialises the trust transitions the same way. The flow's fixed sleeps alone — 30 s waiting for Stage=Active, 15 s for the trust to settle, 15 s for the post-DeleteTrust DescribeTrusts refusal — reach the 60 s ceiling before any assertion is reached, and the report shows exactly "Check timed out after 60.0s" with no exception frame and no response divergence.
Why: the entire ds trust state machine is ungraded by this suite — the Failed settlement and its TrustStateReason, VerifyTrust's terminal-state refusal class and text, the post-delete 404 text, and DeleteTrust's second-call refusal. A regression in any of them is invisible, and a real client polling at these intervals reads a transient value where AWS would have settled.
Fix: this crate's clock-owed transition spans and the chains built on them (src/state.rs:119 TRANSITION_SPAN, :146 DIRECTORY_BUILD_SPAN, :156 directory_active_at, the trust transitions advance_clock materialises, and src/state/directory_deletion.rs's teardown chain) — a settled value must be reachable by a client polling at the intervals this flow uses, within the per-check budget; alternatively this is the transition-span-contract decision already escalated and it has to be settled rather than left failing. Related open issues that do NOT own this failure: 20261111T020957Z-ds-3-net-new-causes-the-password-pattern.md Cause 3 names the identical mechanism and lists this check id, but under the replay key `ds.trust-lifecycle-create-verify-delete|_wait_for_trust_state#11|Timeout|…`; in this run the budget is exhausted at a different poll, so the suite does not report the check as owned and it is ungraded again. 20261108T155909Z-ds-2-net-new-causes-describedirectories-omits-vpcsettings.md covers the trust-state cause this flow would reach next, and 20261102T012359Z-ds-the-trust-state-machine-never-reaches-failed.md is the resolved issue for the settlement itself — neither covers the budget exhaustion.
