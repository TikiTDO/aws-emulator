# bedrock-runtime generation stage serves a constant emulator-notice string instead of any prompt-responsive text, and fills toolUse.input with the schema property names

> _Note: this issue was identified against the code base at commit `3945994041ceeb2d9433bf9ac91cf7eef00f38b4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Converse

## Description
TWO CAUSES on the bedrock-runtime generation stage shared by Converse, ConverseStream, InvokeModel and InvokeModelWithResponseStream. Both are about the CONTENT the emulator puts into the response it serves (the emulator answers 200 on all of these calls, so the service is up and answering wrongly). Smithy model read for both: services/service-com-amazonaws-bedrockruntime-amazonbedrockfrontendservice/smithy-model/com-amazonaws-bedrockruntime-amazonbedrockfrontendservice.json.

NOTE ON SCOPE: the already-open issue 20261023T232022Z-bedrock-runtime-synchronous-inference-guardrailconfig-and-toolconfig-silently.md covers guardrailConfig being ignored, toolChoice never producing stopReason='tool_use', the single-frame response stream, the missing authorization gate, the not-found class and the embedding path. It explicitly states 'none of them is an assertion on generated content'. Neither cause below is described there: these checks now run PAST the assertions that issue keys on and fail on the generated content itself.

Cause 1 of 2 — every text block on every inference entry point carries a constant emulator-notice sentence instead of a response to the request.
AWS: Smithy Converse returns 200 with required `output` -> ConverseOutput (union, member `message` documented 'The message that the model generates'), required `stopReason` (StopReason enum) and required `usage`; Message.content is a required ContentBlocks list and ContentBlock.text is 'Text to include in the message'. InvokeModel -> POST /model/{modelId}/invoke returns 200 with the required `body` blob holding the model's native response (for Nova: output.message.content / stopReason / usage). ConverseStream delivers the same text through contentBlockDelta frames, and InvokeModelWithResponseStream through `chunk` deltas. The model does not word the generated text (recorded behavior only for its content), so the requirement is the RULE the recordings show: the text is responsive to the request's `messages` — an instruction prompt 'Reply with exactly the single word PONG and nothing else.' comes back containing PONG; a verbatim-echo prompt comes back containing the exact marker it supplied, multi-byte unicode (CJK, non-BMP emoji, accents) included; a 'confirm my number N' prompt comes back containing N; a 'print the integers 1..20 comma-separated' prompt comes back as those integers; and the unary and streamed forms of the same request carry the same answer.
Emulator: on all four operations the sole text block is the fixed string 'No language model runs in this emulator. <modelId> generated no text for this request.' — optionally followed by the fixed clause ' The request carried <n> message(s) and <m> input token(s).' Its FIXED text is those two sentences; the only variable parts are the modelId echoed from the request and the two counts taken from the request. stopReason is 'end_turn' and the status is 200, so the reply is presented as a successful, complete generation. Nothing the request asked for ever appears: not the forced token, not the echoed unicode marker, not the caller's own number, not the requested digit sequence.
Why: the entire text data plane is unusable. A client cannot validate prompt construction, cannot test instruction following, cannot test unicode round-tripping, cannot distinguish its own request-isolation bug from the emulator's constant reply (every concurrent response is byte-identical apart from the model id, so cross-talk is undetectable), and cannot exercise any tool/guardrail/streaming flow that depends on the answer. Several negative-path checks are also blocked: their positive control cannot distinguish a validation rule under test from a model that generates nothing.
Fix: the shared generation stage the Converse / ConverseStream / InvokeModel / InvokeModelWithResponseStream handlers call to produce response content (the component that fills ContentBlock.text and the native Nova body's output.message.content, and the deltas the two streaming serializers fragment). It must derive the text from the request's `messages` rather than emit a constant notice, and the unary and streamed paths must derive it the same way.
Traces: bedrock-runtime.bedrock-runtime-bare-model-id-needing-inference-profile-rejected, bedrock-runtime.bedrock-runtime-converse-stream-content-block-index-bookkeeping, bedrock-runtime.bedrock-runtime-converse-tool-result-with-an-unknown-tool-use-id-rejected, bedrock-runtime.bedrock-runtime-invoke-model-stream-invocation-metrics-match-nonstreaming-usage, bedrock-runtime.converse-additional-model-request-fields-validated-by-the-provider, bedrock-runtime.converse-and-invoke-model-agree-on-the-invocation-envelope, bedrock-runtime.converse-concurrent-requests-isolated, bedrock-runtime.converse-performance-config-must-not-silently-degrade-to-standard, bedrock-runtime.converse-stream-reassembles-exactly-what-converse-returns, bedrock-runtime.converse-stream-reassembly-matches-stop-reason, bedrock-runtime.invoke-model-nova-native-body-roundtrip, bedrock-runtime.invoke-model-response-stream-byte-ordering, bedrock-runtime.invoke-model-response-stream-frames-verify-their-own-crc32, bedrock-runtime.invoke-model-with-response-stream-nova-roundtrip, bedrock-runtime.managed-quota-throttling-enforced-uniformly, bedrock-runtime.unicode-text-round-trip-preserved, and the bedrock-runtime leg of the three multi-service checks bedrock-runtime__cloudwatch.refused-invocation-counted-as-client-error-never-as-an-invocation, bedrock-runtime__iam__sts.bedrock-runtime-model-arn-scoped-session-denied-for-second-model and bedrock__bedrock-runtime.bedrock-runtime-converse-with-a-deleted-guardrail-rejected (each fails on its bedrock-runtime positive control returning the same constant notice, so the cause is this one and not cloudwatch/iam/sts/bedrock).

Cause 2 of 2 — a toolUse block's `input` document is filled with the input-schema PROPERTY NAMES, so no request content reaches the tool call.
AWS: Smithy ToolUseBlock has required `toolUseId`, required `name` and required `input` -> Document, documented 'The input to pass to the tool'. The model populates that document against the toolSpec's inputSchema with values extracted from the conversation (recorded behavior only for the extracted values): a prompt that names Paris yields input {"location": "Paris"}; a prompt stating the reporter is in Reykjavik plus a long verbatim report yields {"city": "Reykjavik", "description": "<that report text>"}. On ConverseStream the same JSON arrives only as fragments in contentBlockDelta toolUse.input deltas that the client accumulates.
Emulator: each property's value is literally its own key name — input["location"] == "location" and input["city"] == "city". The schema is walked and echoed back as a self-referential stub; nothing from the request's messages is ever extracted.
Why: every agent / tool-calling client receives a tool invocation whose arguments are placeholders, so the tool it dispatches to is called with meaningless input and the tool-result round trip that follows is grounded in nothing. A caller debugging extraction cannot tell a prompt problem from the emulator never reading the prompt.
Fix: the toolUse-block construction inside the same Converse/ConverseStream generation stage — populate ToolUseBlock.input from the request's messages against the tool's inputSchema, and fragment that document across contentBlockDelta frames on the streaming path.
Traces: bedrock-runtime.converse-tool-use-full-cycle, bedrock-runtime.bedrock-runtime-converse-stream-tool-use-input-arrives-only-in-deltas.
