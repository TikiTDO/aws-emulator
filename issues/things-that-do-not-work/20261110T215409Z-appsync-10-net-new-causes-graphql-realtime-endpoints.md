# AppSync: 10 net-new causes — GraphQL/realtime endpoints published on real-AWS hosts (whole data plane unreachable), EvaluateCode sandbox has no ctx.args/util and raises on compile errors, dependency/existence refusals missing on DeleteDataSource/DeleteFunction/CreateResolver/ListResolversByFunction, GetFunction/GetResolver ungated

> _Note: this issue was identified against the code base at commit `790c5c5e1c0f240249b840d64996fdcf530cd42d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateGraphqlApi

## Description
Ten net-new root causes in the appsync emulator, all grounded in failing behavioral checks of this suite. Each is numbered and carries its own failing check ids; all ten must be closed before this issue is submitted.

=== Cause 1 of 10: CreateGraphqlApi publishes GraphqlApi$uris/$dns on real-AWS hostnames, so the emulator's own GraphQL and realtime data plane is unaddressable ===
AWS: Smithy: CreateGraphqlApi/GetGraphqlApi return GraphqlApi$uris (map key GRAPHQL and REALTIME) and GraphqlApi$dns. On AWS those URIs are the endpoint the caller then posts GraphQL documents to and opens the realtime WebSocket against; they are the only published address of the API's data plane. An emulator must publish an address it itself serves.
Emulator: the create/get projection emits uris.GRAPHQL = https://<token>.appsync-api.<region>.amazonaws.com/graphql and uris.REALTIME = wss://<token>.appsync-realtime-api.<region>.amazonaws.com/graphql (and the same hostnames in dns.GRAPHQL/dns.REALTIME). The replay harness refuses the egress: "its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener" (raised in the harness's endpoint_route, and asserted explicitly in appsync.appsync-graphql-query-end-to-end as DATAPLANE_UNIMPLEMENTED). No data-plane check can execute a single query, mutation, subscription, cache flush effect or auth-mode denial.
Why: a client that does what AWS documents — create an API, read uris.GRAPHQL, post its query there — is sent to a hostname outside the emulator. Every GraphQL request, realtime subscription, resolver execution, field-level authorization decision and api-cache behaviour is unreachable, so the emulator looks like it has no data plane at all.
Fix: the GraphqlApi projection (uris/dns construction) in the CreateGraphqlApi / UpdateGraphqlApi / GetGraphqlApi / ListGraphqlApis handlers, plus the data-plane listener those URIs must name; the Event API equivalent publishes host:port already (dns={'HTTP': '127.0.0.1:...','REALTIME':'127.0.0.1:...'}), so the GraphQL projection is the outlier. NOTE: open issues 20261110T055930Z-appsync-graphql-api-endpoints-publish-aws-hostnames-the.md and 20261109T150433Z-appsync-4-net-new-causes-apicache-creating-state.md describe the same published-URI defect for other checks; the suite did not mark these 33 checks as owned by them, so they are filed here and may be closed by the same fix.
Traces: the 33 check ids listed first in trace_ids, from appsync.appsync-deleted-api-key-subscription-rejected through appsync.update-resolver-changes-query-behavior.

=== Cause 2 of 10: EvaluateCode answers BadRequestException "Invalid code given." for code that fails to compile, instead of HTTP 200 with a structured error ===
AWS: Smithy: EvaluateCode (POST /v1/dataplane-evaluatecode, http code 200) returns EvaluateCodeResponse{evaluationResult, error: EvaluateCodeErrorDetail{message, codeErrors: list<CodeError{errorType, value, location: CodeErrorLocation{line, column, span}}>}, logs, stash, outErrors}. Recorded behavior: code that cannot compile is NOT an API-level refusal — AWS answers 200 with evaluationResult absent and error.codeErrors populated, one entry per diagnostic, errorType naming the class (PARSE_ERROR for unbalanced braces/dangling operator; MISSING_MAPPING_EXPORT for a module that omits the response() export) and location.line/location.column >= 1 pointing at the offending source position.
Emulator: every non-compiling code string is refused with HTTP 400 BadRequestException and the message "Invalid code given." — a constant with no variable part, no codeErrors list and no location. The response-shape contract (200 + error object) never happens, and a module missing response() is accepted silently instead of producing a MISSING_MAPPING_EXPORT codeError.
Why: a client that submits a resolver's JS to EvaluateCode to lint it before CreateResolver gets an exception instead of the diagnostics it is asking for; it cannot report the line/column of the error to its user, and cannot distinguish "your code has a parse error" from "the service rejected the request".
Fix: the EvaluateCode handler's error path — compile failures must serialize into EvaluateCodeResponse$error (message + codeErrors[].errorType/value/location) with a 200 status rather than raising BadRequestException.
Traces: appsync.evaluate-code-invalid-syntax-error-detail (got BadRequestException: Invalid code given.), appsync.op-contract-evaluateCode (same), appsync.evaluate-code-transforms-context (no codeErrors for a dangling-operator syntax error, no MISSING_MAPPING_EXPORT for a module without response()).

=== Cause 3 of 10: the APPSYNC_JS sandbox does not expose ctx.args, so handlers reading it see undefined ===
AWS: recorded behavior (AppSync APPSYNC_JS context contract): the evaluation context supplied in EvaluateCode$context under the key "arguments" is reachable from the handler as BOTH ctx.arguments and its alias ctx.args. request(ctx) returning {payload: ctx.args} for context {"arguments":{"name":"world"}} evaluates to {"payload":{"name":"world"}}, and ctx.args.value * 2 for {"arguments":{"value":21}} evaluates to 42.
Emulator: ctx.arguments is populated (the same module reading ctx.arguments.id evaluates correctly) but ctx.args is undefined: {payload: ctx.args} evaluates to {} (member dropped), and ctx.args.value raises the runtime error "cannot read property 'value' of undefined" returned in error.message.
Why: ctx.args is the form used throughout AppSync's JS resolver documentation and in most real resolver code, so a correct resolver evaluates to an empty payload or a runtime error under the emulator — the evaluator silently reports the author's code as broken.
Fix: the EvaluateCode handler's context binding for the APPSYNC_JS runtime (bind args as an alias of arguments alongside stash/result/source/identity/info/request).
Traces: appsync.evaluate-code-js-request-response (expected request() to map ctx.args into payload, got {}), appsync.evaluate-code-transforms-context (error {'message': "cannot read property 'value' of undefined"} where 42 was expected).

=== Cause 4 of 10: the APPSYNC_JS sandbox does not define the `util` global ===
AWS: recorded behavior: the APPSYNC_JS runtime provides the `util` helper module as a global. util.error("<message>") in a request() handler aborts the handler and surfaces that message in EvaluateCodeResponse$error.message, with no evaluationResult.
Emulator: the same handler returns 200 with error.message = "util is not defined" — the author's message (the string passed to util.error) never appears; the identifier itself is unresolved. The response() export of the same module evaluates fine, so the module compiles: only the global is missing.
Why: util.error / util.appendError / util.toJson are the standard way resolver code raises and shapes errors; code relying on them is reported as referencing an undefined identifier, and the error text a client expects to show its user is replaced by a sandbox diagnostic.
Fix: the EvaluateCode handler's APPSYNC_JS runtime globals (define `util`, and route util.error's message into EvaluateCodeResponse$error.message with evaluationResult absent).
Traces: appsync.evaluate-code-js-runtime-error (error {'message': 'util is not defined'}; expected the message to contain the handler's own "bad-request-boom").

=== Cause 5 of 10: EvaluateCode refuses an unknown runtime name with ValidationException instead of BadRequestException ===
AWS: Smithy: EvaluateCode's modeled errors are AccessDeniedException(403), BadRequestException(400), InternalFailureException(500) — ValidationException is not among them; AppSyncRuntime$name targets enum RuntimeName with the single value APPSYNC_JS. Recorded behavior: runtime={"name":"NOT_A_RUNTIME",...} is refused with BadRequestException and the message "1 validation error detected: Value at 'runtime.name' failed to satisfy constraint: Member must satisfy enum value set: [APPSYNC_JS]" (fixed text; no request value is interpolated — AWS omits the offending value here).
Emulator: the call is refused with error code ValidationException.
Why: a client catching BadRequestException (the only client-input error this operation models) does not catch the emulator's ValidationException, so the refusal escapes as an unmodeled error.
Fix: the EvaluateCode handler's input validation / error classification for runtime.name.
Traces: appsync.evaluate-code-unsupported-runtime-rejected (unexpected code ValidationException).

=== Cause 6 of 10: DeleteDataSource succeeds while a resolver still references the data source ===
AWS: Smithy: DeleteDataSource models BadRequestException(400) alongside NotFoundException(404). Recorded behavior: deleting a data source that a resolver is wired to is refused with BadRequestException/HTTP 400 and the message "Resolver for type <typeName> and field <fieldName> associated with data source" — fixed text with the referencing resolver's type and field names taken from state (e.g. "...for type Query and field getWidget..."); the data source is left intact and the identical delete succeeds once the resolver is removed.
Emulator: DeleteDataSource answers HTTP 200 with an empty body and removes the data source even while a resolver references it; no refusal is produced at all.
Why: a client's teardown or re-point sequence silently destroys a data source that live resolvers depend on, and the error AWS uses to tell it which resolver blocks the delete never arrives, so it cannot repair the reference.
Fix: the DeleteDataSource handler's dependency (referential-integrity) check against the API's resolvers and functions, before the state removal. NOTE: open issue 20261029T200818Z-appsync-resolver-function-data-source-plane-dependency-refusals.md describes missing dependency refusals on this plane for other checks; these checks were not marked owned by it and may be closed by the same fix.
Traces: appsync.delete-data-source-in-use-blocked (expected BadRequestException/400, call SUCCEEDED 200), appsync.delete-data-source-referenced-by-resolver-rejected (same), appsync.op-contract-deleteDataSource (same).

=== Cause 7 of 10: DeleteFunction succeeds while a PIPELINE resolver still references the function ===
AWS: Smithy: DeleteFunction models BadRequestException(400). Recorded behavior: deleting a function listed in a PIPELINE resolver's pipelineConfig.functions is refused with BadRequestException and the message "Cannot delete a function which is currently used by a resolver. Resolver type: <typeName>, field: <fieldName>" — fixed text with the referencing resolver's type and field from state (e.g. "... Resolver type: Query, field: echo"); the function stays readable via GetFunction and the identical delete succeeds after the resolver is deleted.
Emulator: DeleteFunction answers HTTP 200 with an empty body and removes the function while the pipeline resolver still names it, leaving the resolver pointing at a functionId that no longer exists.
Why: a client can silently break every pipeline resolver that chains the function, and it never learns which resolver holds the reference.
Fix: the DeleteFunction handler's dependency check against the API's resolvers' pipelineConfig.functions.
Traces: appsync.delete-function-referenced-by-pipeline-resolver-fails (expected BadRequestException, call succeeded 200), appsync.op-contract-delete-function (same).

=== Cause 8 of 10: CreateResolver accepts a dataSourceName that exists only on a DIFFERENT API ===
AWS: Smithy: CreateResolver models NotFoundException(404); dataSourceName targets ResourceName and names a data source of the API in the path label apiId. Recorded behavior: creating a resolver on API B whose dataSourceName exists only on API A is refused with NotFoundException and the message "No data source found named <dataSourceName>" (fixed text + the requested name), and no resolver is registered on API B.
Emulator: the call returns HTTP 200 with the resolver projected (dataSourceName echoed, resolverArn under API B), so a resolver on API B is bound to a data source API B does not own; ListResolvers on API B then shows the phantom field.
Why: data-source isolation between APIs is lost — a client can wire a resolver to another API's backend and only discovers it at query time, and tenancy boundaries that AWS enforces at create time do not hold.
Fix: the CreateResolver handler's dataSourceName existence check, scoped to the apiId in the request. NOTE: open issue 20261109T053905Z-appsync-createresolver-kind-pipelineconfig-datasourcename-validation-refusals-and.md covers CreateResolver dataSourceName validation for other checks and may close this one too.
Traces: appsync.cross-api-resolver-datasource-isolation-rejected (expected ('NotFoundException','No data source found named <ds>'), call SUCCEEDED 200).

=== Cause 9 of 10: ListResolversByFunction answers 200 with an empty list for an unknown functionId ===
AWS: Smithy: ListResolversByFunction (GET /v1/apis/{apiId}/functions/{functionId}/resolvers) models NotFoundException(404). Recorded behavior: a functionId that does not exist on the API is refused with NotFoundException and the message "Function not found." (fixed text, no interpolation); the empty list is reserved for a function that exists and has no referencing resolver.
Emulator: the request answers HTTP 200 with {"resolvers": []} for a well-formed but never-issued functionId (the filtering for real functionIds is correct — only the existence check is missing).
Why: "no such function" and "function with no resolvers" become indistinguishable, so a client that polls references before deleting a function reads an absent function as safely unreferenced.
Fix: the ListResolversByFunction handler's function-existence lookup before projecting the resolver list.
Traces: appsync.op-contract-list-resolvers-by-function (expected NotFoundException "Function not found.", call SUCCEEDED 200 with resolvers: []).

=== Cause 10 of 10: GetFunction and GetResolver are not gated by identity-based IAM ===
AWS: Smithy: GetFunction models UnauthorizedException(401)/NotFoundException(404); recorded behavior is that the service refuses a principal with no identity-based policy with AccessDeniedException and the message "User: <caller arn> is not authorized to perform: appsync:GetFunction on resource: <api arn prefix>:/v1/apis/<apiId>/functions/<functionId> because no identity-based policy allows the appsync:GetFunction action" — fixed text with the caller ARN, the resource path and the action name taken from the request; GetResolver refuses identically with appsync:GetResolver and the resource path .../apis/<apiId>/types/<typeName>/resolvers/<fieldName>.
Emulator: a freshly created IAM user with zero attached policies gets HTTP 200 and the full functionConfiguration (functionId, functionArn, dataSourceName, both mapping templates) — the request is served as if the caller were the owner; the same holds for GetResolver.
Why: authorization is not enforced on these reads, so an emulator user cannot test least-privilege policies: a deny-by-default principal reads resolver and function internals (including mapping templates) it must not see, and code that handles AccessDeniedException is never exercised.
Fix: the identity-based authorization gate in front of the GetFunction / GetResolver handlers (the same gate missing on other appsync reads).
Traces: appsync.unauthorized-function-resolver (GetFunction for a zero-policy principal succeeded with 200 and the functionConfiguration, where AccessDeniedException was expected).
