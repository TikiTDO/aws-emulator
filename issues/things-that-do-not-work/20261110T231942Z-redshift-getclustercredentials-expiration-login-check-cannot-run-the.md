# redshift: GetClusterCredentials expiration/login check cannot run — the cluster's published Endpoint.Address is an *.redshift.amazonaws.com host the emulator does not serve

> _Note: this issue was identified against the code base at commit `13cbee553af2e776db8b2ebed42254e169329488`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeClusters

## Description
One net-new root cause on the Redshift surface, grounded in a failing behavioral check of this replay.

Cause 1 of 1 — a cluster that DescribeClusters reports as 'available' publishes Cluster.Endpoint.Address on AWS's own DNS domain, so no client of the emulator can open the PostgreSQL session the API just invited it to, and the temporary-credential lifetime contract of GetClusterCredentials is therefore unverifiable.

AWS: Smithy: DescribeClusters/CreateCluster output Cluster.Endpoint -> Endpoint{Address: String ("The DNS address of the Cluster"), Port: Integer ("The port that the database engine is listening on"), VpcEndpoints}. GetClusterCredentials(ClusterIdentifier, DbUser, DbName, AutoCreate, DurationSeconds) -> ClusterCredentials{DbUser, DbPassword (sensitive), Expiration: timestamp}; modeled errors ClusterNotFoundFault (404, awsQueryError ClusterNotFound) and UnsupportedOperationFault (400). The wire data plane itself is not modeled — recorded behavior only: the Address:Port a cluster publishes once ClusterStatus is 'available' accepts a PostgreSQL (Redshift) session, and the DbUser/DbPassword pair GetClusterCredentials returns authenticates on it until Expiration (issuance + DurationSeconds, range 900–3600 s; DurationSeconds outside that range is refused with code InvalidParameterValue and the fixed message 'Token duration must be between 900 and 3600 seconds', which has no variable part).

Emulator: Endpoint.Address is published in the real-AWS form <cluster-identifier>.<hex-label>.<region>.redshift.amazonaws.com with Port 5439 — a name that resolves (if at all) to AWS, never to the address the emulator is reached on. The published target is therefore refused before any socket is opened: 'simparity.published.PublishedUrlRejected: endpoint_host was given <host>:5439 (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs an own host[:port]: the endpoint host, a documented own host or, for a loopback endpoint, a loopback address'. Fixed part of that diagnosis is the rejection class and its reason (the announced host is not one of the emulator's own hosts); the cluster identifier, the hex label and the region in the host are values generated by this run and are not part of the requirement.

Why: a client that creates a cluster, waits for 'available', mints temporary credentials with GetClusterCredentials and connects to the endpoint the control plane handed it is pointed at AWS's production domain instead of the emulator. It gets a DNS/connect failure (or, worse, leaks a connection attempt off-emulator) while the control plane claims a usable warehouse. Everything behind that address is unreachable: the credential TTL (Expiration == issuance + DurationSeconds) can never be observed against a real login, and the DurationSeconds-below-900 refusal leg of the same contract is never reached because the check dies at the connect step.

Fix: the cluster projection/state that builds Cluster.Endpoint — the DescribeClusters/CreateCluster response serializer plus the cluster state that stores the endpoint — must publish an address on a host the emulator actually serves, and the Redshift PostgreSQL-wire listener must answer there; the endpoint must not be advertised before it answers.

Traces: redshift.get-cluster-credentials-expiration-is-issuance-plus-duration-seconds.

Related, not covering: open issue 20261109T125831Z-redshift-6-net-new-behavioral-causes-cluster-endpoint.md describes the same unreachable-endpoint cause for ten other checks, and open issue 20261104T045922Z-redshift-publishes-a-cluster-endpoint-but-serves-no.md records an earlier run where the endpoint was a loopback address with nothing listening. Neither carries this check's replay key, so this failure is not covered by them; closing them without this check re-replayed would leave the GetClusterCredentials TTL/login contract unexercised.
