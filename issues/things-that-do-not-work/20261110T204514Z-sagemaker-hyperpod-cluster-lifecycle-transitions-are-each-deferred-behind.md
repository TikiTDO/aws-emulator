# HyperPod cluster lifecycle transitions are each deferred behind a 300 ms wall-clock span, so a polling client pays a full interval per transition and the Slurm controller-delete and post-delete refusals are never reached

> _Note: this issue was identified against the code base at commit `41bd6c476a5fe40a474aadc7e47c434277d677d7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeCluster

## Description
Cause 1 of 1 — a HyperPod cluster's create/node-add/delete lifecycle cannot be driven to its end by a client that polls, because every transition in it is materialised only by a read that happens AFTER a stored wall-clock instant, and nothing makes the transition observable to the first read that follows the mutation. Failing check: sagemaker.cluster-node-add-and-cluster-delete-lifecycle.

AWS: recorded behavior only for the timing. The model states the lifecycle this check walks: DescribeCluster.ClusterStatus (Creating | Deleting | Failed | InService | RollingBack | SystemUpdating | Updating, required) and DescribeCluster's only modeled error ResourceNotFound (HTTP 400); BatchDeleteClusterNodes refuses a request none of whose ids names a removable node with ValidationException and the fixed sentence "All provided nodes failed validation. Please ensure the nodes exist, are not part of the controller group for the Slurm cluster, and are in a removable state." (Smithy: BatchDeleteClusterNodes$NodeIds — "you cannot remove instances that are configured as Slurm controller nodes"), and a cluster addressed after its deletion answers ResourceNotFound with "Cluster with name <identifier> not found", where "Cluster with name" / "not found" is fixed text and <identifier> is the ClusterNameOrArn form the request carried. In the recording the whole sequence — CreateCluster → InService, BatchAddClusterNodes → the added worker reaches Running with an InstanceId, BatchDeleteClusterNodes refused for the Slurm controller node and accepted for the worker, DeleteCluster → the cluster gone — is observed to completion.

Emulator: each step of that sequence is answered correctly, but ONLY after a wall-clock span that the first read following the mutation always misses: CLUSTER_IN_SERVICE_AFTER = 300 ms for Creating → InService (and the nodes a group declares are minted only at that instant), the same 300 ms for an added node's Pending → Running and its InstanceId, and CLUSTER_RELEASED_AFTER = 300 ms for Deleting → gone. Because the transition is materialised by whichever read first runs at or after the stored instant, a client that polls — this check, and `aws sagemaker wait`-style loops generally — reads the transient value, then sleeps its own full interval (20–30 s here) before seeing the settled one. Three such waits in one lifecycle exceed the check's budget: the replay ends with "Error: Check timed out after 60.0s" and no verdict is ever reached for the assertions past the second wait — the BatchDeleteClusterNodes Slurm-controller ValidationException text, the worker's removal from ListClusterNodes, the post-DeleteCluster ResourceNotFound code and its "Cluster with name <name> not found" message, and the ResourceNotFound refusal of BatchAddClusterNodes against the deleted cluster. The same deferral pattern is already filed against another service as 20261107T094955Z-pcs-lifecycle-transitions-are-deferred-behind-a-fixed.md; this is the SageMaker HyperPod instance of it and that issue does not cover this service.

Why: a client that drives HyperPod with the documented poll-until-settled pattern pays one whole polling interval per transition instead of observing it on the next read, so a multi-step cluster workflow (provision, scale a group, scale it back, tear down) takes several polling intervals of pure waiting and a workflow with a bounded budget never completes. Everything the emulator would answer correctly after those waits — the controller-node delete refusal, the node inventory after a delete, and both post-delete ResourceNotFound refusals — is unreachable in practice, so a client cannot verify any of that behavior against the emulator.

Fix: the HyperPod cluster slice's clock-owed transitions and the readers that materialise them — the spans in services/service-com-amazonaws-sagemaker-sagemaker/src/state/cluster.rs (CLUSTER_IN_SERVICE_AFTER, CLUSTER_RELEASED_AFTER, Cluster::settle_status / Cluster::begin_deletion / Cluster::is_released / provision_group_instances), ClusterNode::settle_status in services/service-com-amazonaws-sagemaker-sagemaker/src/state.rs, and the reporting handlers that call them (src/ops/describe_cluster.rs, describe_cluster_node.rs, list_cluster_nodes.rs). The transient status must stay observable without costing a client a full polling interval: settle on the first read that follows the one which observed the transient value, rather than on a read that happens to fall after a fixed wall-clock instant.

Traces: sagemaker.cluster-node-add-and-cluster-delete-lifecycle (mismatch, timed out after 60.0 s with the lifecycle only partly walked).

## Evidence
Suite report, ### sagemaker: "#### [mismatch] sagemaker.cluster-node-add-and-cluster-delete-lifecycle / Error: Check timed out after 60.0s". The check creates a Slurm HyperPod cluster, polls DescribeCluster until ClusterStatus=InService (interval 30 s), calls BatchAddClusterNodes and polls DescribeClusterNode until NodeDetails.InstanceId is present and InstanceStatus.Status=Running (interval 20 s), then asserts the controller-node BatchDeleteClusterNodes refusal (ValidationException, "All provided nodes failed validation. Please ensure the nodes exist, are not part of the controller group for the Slurm cluster, and are in a removable state."), deletes the worker, and after DeleteCluster polls until DescribeCluster answers ResourceNotFound with "Cluster with name <name> not found" (interval 20 s).

Expected: the lifecycle completes and each refusal above is exercised.
Actual: each transition is answered only after a 300 ms stored instant (services/service-com-amazonaws-sagemaker-sagemaker/src/state/cluster.rs: `pub const CLUSTER_IN_SERVICE_AFTER: Duration = Duration::from_millis(300);`, `pub const CLUSTER_RELEASED_AFTER: Duration = CLUSTER_IN_SERVICE_AFTER;`, `Cluster::settle_status` materialising Creating → InService and minting the groups' instances only then; `ClusterNode::settle_status` in src/state.rs doing the same for Pending → Running and the InstanceId), so the first read after every mutation returns the transient value and the client sleeps a full interval. Three such waits overrun the 60 s budget and the run ends with no verdict for anything after the node-add wait.

## Steps to Reproduce
1. CreateCluster for a Slurm cluster with a controller group (InstanceCount 1, SlurmConfig.NodeType=Controller) and a compute group (InstanceCount 0), Orchestrator={"Slurm":{}}.
2. Immediately call DescribeCluster: ClusterStatus is Creating and both groups report CurrentCount 0. Poll on any interval of a few seconds or more — the first poll after the create always sees Creating, and InService is only materialised by a later read.
3. Once InService, call BatchAddClusterNodes with NodesToAdd=[{InstanceGroupName: <compute group>, IncrementTargetCountBy: 1}] and immediately DescribeClusterNode on the returned NodeLogicalId: InstanceStatus.Status is Pending and NodeDetails has no InstanceId; the Running/InstanceId pair appears only on a read taken later.
4. Call DeleteCluster and immediately DescribeCluster: the cluster is still describable in Deleting; the ResourceNotFound "Cluster with name <name> not found" refusal appears only on a read taken later.
5. Each of steps 2–4 therefore costs a polling client one full polling interval; running them in one scripted lifecycle with 20–30 s polls does not finish inside a 60 s budget, so the BatchDeleteClusterNodes controller-node refusal and the post-delete refusals are never reached.
