=== Cause 1 of 1: an SNS-target occurrence denied by its Target.RoleArn produces no dead-letter event (and the refusal is never observable) ===
Failing check: scheduler__sns.scheduler-sns-target-delivers-the-notification-envelope-and-a-denied-role-withholds-it

AWS: Smithy (com.amazonaws.scheduler) — Target.RoleArn is @required, @length 1..1600, @pattern ^arn:aws(-[a-z]+)?:iam::\d{12}:role\/[\w+=,.@\/-]+$, documented as "The Amazon Resource Name (ARN) of the IAM role that EventBridge Scheduler will use for this target when the schedule is invoked." Target.DeadLetterConfig -> DeadLetterConfig, member Arn @pattern ^arn:aws(-[a-z]+)?:sqs:[a-z0-9\-]+:\d{12}:[a-zA-Z0-9\-_]+$, @length 1..1600, documented as "An object that contains information about an Amazon SQS queue that EventBridge Scheduler uses as a dead-letter queue for your schedule. If specified, EventBridge Scheduler delivers failed events that could not be successfully delivered to a target to the queue." Target.RetryPolicy bounds the retries (MaximumRetryAttempts @range 0..185, MaximumEventAgeInSeconds @range 60..86400) before the event is dead-lettered. So each occurrence of a schedule whose Target.Arn is an SNS topic is published AS the assumed Target.RoleArn: when that role's policy does not permit sns:Publish on the topic, SNS refuses the publish with AuthorizationError, the topic's subscribers receive nothing, and Scheduler delivers the failed event to Target.DeadLetterConfig.Arn. Recorded behavior (the shape the check asserts on, no modelled contract for the event body): the dead-letter SQS message carries the failed occurrence's payload in its Body and message attributes naming the occurrence, including ERROR_CODE = the target service's error code (here the fixed string AuthorizationError, the code SNS returns for a Publish it refuses), SCHEDULE_ARN = the ARN of the schedule that failed (a value taken from state, so the two schedules' events are never crossed), and ERROR_MESSAGE naming the assumed-role session. Once sns:Publish is granted on the topic and nothing else changes, the previously withheld occurrences start delivering.
Emulator: the permitted arm works — a Notification envelope with the right Type/TopicArn/MessageId, the substituted <aws.scheduler.scheduled-time> context attribute and a Timestamp inside the allowed window arrived at the subscriber. The DENIED arm produces NOTHING observable: after 240 s of polling with WaitTimeSeconds=20 and MessageAttributeNames=['All'], the schedule's DeadLetterConfig queue is completely empty ("Other events seen and discarded: []"), so the occurrence of the schedule whose role carries only sqs:SendMessage on the DLQ and no sns:Publish was never recorded as having failed. Either the dispatcher published successfully without evaluating Target.RoleArn, or it failed and dropped the failure silently; in both cases the configured dead-letter queue never receives the failed event.
Why: for a schedule, the dead-letter queue is the ONLY channel through which a client learns an occurrence failed — CreateSchedule has already returned 200, there is no caller at occurrence time, and the control plane keeps reporting State=ENABLED. With the DLQ silent, a schedule whose SNS publishes are all being refused for lack of permission is indistinguishable from a healthy one: alarms on DLQ depth never fire, least-privilege role tests that assert "no delivery without sns:Publish, and a dead-letter event proving the refusal" cannot pass, and a negative test can never attribute an absence at the subscriber to the missing permission. A client that validates its Scheduler role policies against the emulator ships a configuration whose failures are invisible here and loud in AWS.
Fix: the scheduler crate's occurrence/dispatch component (services/service-com-amazonaws-scheduler-awschronosservice/src/, the target-invocation path shared by the templated targets) must, for an SNS topic target, issue the Publish under the assumed Target.RoleArn and evaluate that role's policy first; an authorization refusal must be classified as a delivery failure, retried per Target.RetryPolicy, and then SendMessage'd once to Target.DeadLetterConfig.Arn with the occurrence's payload and the ERROR_CODE / ERROR_MESSAGE / SCHEDULE_ARN attributes populated from the refusing service's error and the failing schedule's own ARN.
Traces: scheduler__sns.scheduler-sns-target-delivers-the-notification-envelope-and-a-denied-role-withholds-it (assertion raised in _await_dlq_event, reached from run line 144).

## Steps to Reproduce
All calls via boto3 against the emulator, as the check does.

1. sns.create_topic(Name=<topic>) -> topic_arn.
2. sqs.create_queue twice: an `inbox` subscriber queue and a `dlq`. For each, get_queue_attributes(AttributeNames=['QueueArn']).
3. sqs.set_queue_attributes on `inbox` with a Policy allowing Principal {"Service": "sns.amazonaws.com"} sqs:SendMessage on the queue ARN with Condition ArnEquals aws:SourceArn = topic_arn, then sns.subscribe(TopicArn=topic_arn, Protocol='sqs', Endpoint=<inbox arn>) (RawMessageDelivery left off).
4. iam.create_role twice, both trusting {"Service": "scheduler.amazonaws.com"} for sts:AssumeRole:
   - ALLOWED role: inline policy Allow sns:Publish on topic_arn + Allow sqs:SendMessage on <dlq arn>.
   - DENIED role: inline policy Allow sqs:SendMessage on <dlq arn> ONLY (no sns:Publish anywhere).
5. scheduler.create_schedule twice (retrying ValidationException while IAM propagates), both with ScheduleExpression='rate(1 minute)', ScheduleExpressionTimezone='UTC', FlexibleTimeWindow={'Mode':'OFF'}, State='ENABLED' and Target={'Arn': topic_arn, 'RoleArn': <that arm's role>, 'Input': json.dumps({'marker': <per-arm marker>, 'at': '<aws.scheduler.scheduled-time>'}), 'DeadLetterConfig': {'Arn': <dlq arn>}}.
6. Poll sqs.receive_message(QueueUrl=<inbox url>, MaxNumberOfMessages=10, WaitTimeSeconds=5) until the permitted marker appears (<=240 s). It does — this is the positive control.
7. Poll sqs.receive_message(QueueUrl=<dlq url>, MaxNumberOfMessages=10, WaitTimeSeconds=20, MessageAttributeNames=['All']) for 240 s looking for the DENIED arm's marker. On AWS a dead-letter event carrying that marker arrives, with MessageAttributes ERROR_CODE='AuthorizationError' and SCHEDULE_ARN equal to the denied schedule's ARN. On the emulator the queue stays empty for the whole window — this is the divergence.
8. (Blocked downstream by step 7, on AWS they hold:) watch `inbox` for a further 60 s and observe the denied marker never arrives while the permitted one keeps arriving; then iam.put_role_policy on the denied role adding Allow sns:Publish on topic_arn and observe the denied marker start arriving at `inbox` within 240 s.
