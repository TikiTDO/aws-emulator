# CodePipeline publishes webhook URLs on a webhooks.aws host the emulator does not serve

> _Note: this issue was identified against the code base at commit `d0a04fabcd83cf2b721ac740047fd92b0e777ff8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutWebhook

## Description
Both webhook surfaces publish a trigger URL whose host is an AWS-shaped name (<region>.webhooks.aws) rather than the address the emulator is actually reached on, so the URL the service hands a client is undeliverable. The replay verdict is host_not_own on both. 2 causes, one per surface that publishes the URL.

Cause 1 of 2 - PutWebhook's returned url (fixture codepipeline-webhook-lifecycle, step task#1).
AWS: Smithy PutWebhook input.webhook (WebhookDefinition, @required), output.webhook is a ListWebhookItem; ListWebhookItem.url is @required of type WebhookUrl (string, @length 1..1000) documented as 'A unique URL generated by CodePipeline. When a POST request is made to this URL, the defined pipeline is started as long as the body of the post request satisfies the defined authentication and filtering.' The URL is therefore the data-plane endpoint a provider POSTs to, and on AWS it resolves to a host the service answers on. The requirement an emulator inherits is that the published host and port are ones the emulator itself serves, and that the trigger path is served there; the uuid in the query string and the concrete host:port are per-run values, not requirements.
Emulator: PutWebhook returns webhook.url = 'https://<region>.webhooks.aws/trigger?t=<uuid>&v=1' - a host synthesized from the region that the emulator does not serve. The replay flags it host_not_own before any POST is attempted.
Why: a client that does exactly what the API documents - POST the provider payload and its signature to the URL the service handed it - never reaches the emulator. The request leaves for a name the emulator does not answer, so no execution is ever started through a webhook and the whole authentication path (accept a correct GITHUB_HMAC signature, ack-but-ignore a wrong secret) is unreachable. Any CI integration driven by a CodePipeline webhook is dead on arrival.
Fix: the URL construction in the PutWebhook handler - build the URL from the emulator's own published endpoint host and port (the same resolution the other per-resource listeners use) and serve the webhook trigger path on it. The host must never be synthesized from the region as a *.webhooks.aws name.
Traces: codepipeline-webhook-lifecycle#task#1, codepipeline-webhook-lifecycle#task#3, codepipeline-webhook-put-list-deregister-delete-lifecycle#task#2.

Cause 2 of 2 - ListWebhooks reads the same off-host URL back (fixture codepipeline-webhook-lifecycle, step task#2).
AWS: Smithy ListWebhooks output.webhooks is a WebhookList of ListWebhookItem, so webhooks[].url carries the same @required WebhookUrl with the same documented POST semantics as the PutWebhook result. A client that discovers an existing webhook rather than creating one must get an equally reachable URL.
Emulator: ListWebhooks returns webhooks[0].url with the same '<region>.webhooks.aws/trigger?...' host, flagged host_not_own. This is a second, separately reachable publication point - storing a correct URL at PutWebhook time is not sufficient if the list projection re-synthesizes it, and serving the trigger path is required for either to work.
Why: a client that enumerates webhooks (for example to re-register a provider hook after a restart, or to recover the URL it did not persist) is handed the same undeliverable address, so webhook-driven execution stays unreachable even when the webhook itself exists.
Fix: the ListWebhooks projection (and the stored webhook state it reads) must carry the emulator-served URL produced by the fixed construction in Cause 1, not re-derive an AWS host.

Related open issue: 20261109T175016Z-codepipeline-the-webhook-url-published-by-putwebhook-listwebhooks.md reports the same off-host URL, but it is a BEHAVIORAL issue from simparity-behavioral-aws-v1 and carries no wire replay key (no Issue-Trace/Issue-Step), which is why the replay reports these two clusters as unowned. This issue supplies the wire fixture/step bindings so the fix is re-replayed against the recorded corpus.
