# appsync__dynamodb: 2 net-new causes — the GraphQL API's published uris are real-AWS hostnames, and a DynamoDB UNIT-resolver API-key read never completes

> _Note: this issue was identified against the code base at commit `f456950adb04cb9e7696776dd0db02907fd8875a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateGraphqlApi

## Description
Two net-new root causes grounded in the failing behavioral checks of this service pairing; each carries its own failing check ids and both must be closed before this issue is submitted.

=== Cause 1 of 2: CreateGraphqlApi publishes GraphqlApi$uris/$dns on hostnames the emulator does not serve, so no DynamoDB-backed resolver can be driven ===
AWS: Smithy (appsync): CreateGraphqlApi returns GraphqlApi with `uris` and `dns` (MapOfStringToString, keys GRAPHQL and REALTIME). uris.GRAPHQL is the endpoint the client POSTs GraphQL documents to and uris.REALTIME the WebSocket it subscribes on; they are the only address the service publishes for the API's data plane, so an emulator must publish an address it itself serves.
Emulator: uris.GRAPHQL is emitted as https://<26-char token>.appsync-api.<region>.amazonaws.com/graphql (uris.REALTIME the matching wss://<token>.appsync-realtime-api...). Every data-plane step is refused before any request is sent: simparity.published.PublishedUrlRejected: "endpoint_url was given https://<token>.appsync-api.us-west-2.amazonaws.com/graphql (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener". Tokens, hosts and ports vary per run and are not part of the requirement.
Why: the DynamoDB-integration behaviors a client depends on are all unobservable — optimistic-concurrency conflict responses that must carry the server's version and data, AUTO_MERGE conflict resolution across concurrent stale writers, stale-delete rejection without a tombstone, disjoint-write merging, and Sync delta queries returning only post-lastSync changes with tombstones. A client reading uris.GRAPHQL as AWS documents is sent off the emulator.
Fix: the GraphqlApi projection (uris/dns construction) in the CreateGraphqlApi / UpdateGraphqlApi / GetGraphqlApi handlers of the appsync service, plus the GraphQL/realtime data-plane listener those URIs must name. NOTE: open issues 20261110T155738Z-appsync-dynamodb-creategraphqlapi-publishes-a-real-appsync-api.md and 20261109T150433Z-appsync-dynamodb-appsync-graphql-data-plane-unreachable-the-published-uris.md report this defect for other checks of this pairing; the five checks below were not marked owned by them and may be closed by the same fix.

=== Cause 2 of 2: a VTL UNIT resolver on an AMAZON_DYNAMODB data source queried with an API key never completes — the check exhausts its whole budget ===
AWS: Smithy: StartSchemaCreation is asynchronous and GetSchemaCreationStatus (GET /v1/apis/{apiId}/schemacreation, code 200) returns SchemaStatus, whose values are PROCESSING, ACTIVE, DELETING, FAILED, SUCCESS, NOT_APPLICABLE. The contract AWS honours is that a submitted schema reaches a TERMINAL status (SUCCESS/ACTIVE, or FAILED) in bounded time, after which CreateDataSource(type=AMAZON_DYNAMODB)+CreateResolver(kind=UNIT) with a GetItem request template and $util.toJson($ctx.result) response template serves the seeded item, with the DynamoDB {"N":"7"} attribute projected as a GraphQL Int 7 rather than a {"N":...} map.
Emulator: recorded behavior only — the check makes no progress and is killed at its deadline: "Error: Check timed out after 60.0s". No status, error code or body is produced to diagnose. Hypothesis: the only bounded wait before the data-plane step is the GetSchemaCreationStatus poll, so the emulator most likely never advances the schema past a non-terminal status (the poll's predicate is status in SUCCESS/ACTIVE/FAILED); if instead the schema does settle, the hang is in the data-plane GET/POST that follows, which Cause 1 shows is addressed at a hostname the emulator does not serve.
Why: a client that submits a schema and polls GetSchemaCreationStatus as AWS documents never observes a terminal status, so it waits forever instead of proceeding (or failing) — an operation that merely hangs is worse than a refusal, because no error path is reachable.
Fix: the StartSchemaCreation / GetSchemaCreationStatus handlers and the schema-creation state machine (a submitted definition must settle on a terminal SchemaStatus promptly, and GetSchemaCreationStatus must report it), together with the DynamoDB-data-source resolver execution path that follows. This cause may be closed by the same change as Cause 1 if the hang proves to be the unreachable data-plane endpoint.
Traces: appsync__dynamodb.appsync-unit-resolver-reads-dynamodb-via-api-key.

## Evidence
Cause 1 — expected: graphqlApi['uris']['GRAPHQL'] (and ['REALTIME']) name a host:port the emulator serves, so mutations/queries against a DynamoDB data source are executable. Actual: e.g. https://pr7qcq7nei7lgpj6mwahzvqjg6.appsync-api.us-west-2.amazonaws.com/graphql, refused with simparity.published.PublishedUrlRejected "...its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener" in all five listed checks (host/port/token are per-run values).

Cause 2 — expected: after put_item seeds {"id":{"S":<id>},"name":{"S":<name>},"count":{"N":"7"}}, StartSchemaCreation settles on SchemaStatus SUCCESS/ACTIVE, then the API-key GraphQL query { getWidget(id: <id>) { id name count } } returns count as the Int 7. Actual: the check never gets that far — "Error: Check timed out after 60.0s" with no response, status or error code recorded.

## Steps to Reproduce
Cause 1: dynamodb.create_table + put_item; iam.create_role trusting appsync.amazonaws.com with dynamodb permissions; appsync.create_graphql_api(...); start_schema_creation; create_data_source(type='AMAZON_DYNAMODB', dynamodbConfig={...}); create_resolver(kind='UNIT'); then read graphqlApi['uris']['GRAPHQL'] and POST the mutation/query there. The published URI is a *.appsync-api.<region>.amazonaws.com host instead of the emulator's own host:port.

Cause 2: as above with a GetItem request template and $util.toJson($ctx.result) response template, then poll appsync.get_schema_creation_status(apiId=api_id) until status is in (SUCCESS, ACTIVE, FAILED) and query the field with an API key. The sequence never completes within the check's 60s budget; no terminal status or data-plane response is observed.
