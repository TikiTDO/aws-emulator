# ECS task data plane: container commands never execute (exit 127), dependsOn/essential ignored, no exec agent, no task-credentials endpoint, no ephemeral storage, wrong stopCode for unpullable images (7 causes)

> _Note: this issue was identified against the code base at commit `d77a58d64fb70ca743013b1e12d44799c7a2b26f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RunTask

## Description
SEVEN net-new root causes in the ECS task data plane. All seven are grounded in failing behavioral checks listed under `### ecs`. Related open issues exist but do NOT cover these: `20261104T062603Z-ecs-containers-never-execute-no-in-container-behaviour.md` carries replay keys in which every such check ended in a 60s poll Timeout with containers stuck at lastStatus=PENDING; the emulator now *does* advance containers to STOPPED and reports exitCode, so the failures below are a different, observable set of divergences and the suite did not mark them as owned. `20261104T062603Z-ecs-exec-the-executecommandagent-managed-agent-never-reaches.md` is likewise about the managed agent never reaching RUNNING, not about the task stopping before exec is possible. Both should be read alongside Cause 1 and Cause 2.

Cause 1 of 7: the container's configured command/entryPoint is never executed; the container is reported STOPPED with exitCode 127 (shell 'command not found'), so the task immediately stops with stopCode EssentialContainerExited and no in-container behaviour exists.
AWS: Smithy com.amazonaws.ecs#Container.exitCode is documented as "The exit code returned from the container" — i.e. the exit status of the task definition's command as actually run. The task-definition runtime settings workingDirectory, user and ulimits (ContainerDefinition) take effect inside that process. A task whose container runs to a clean exit reports exitCode 0; a long-lived command (e.g. `sleep`) keeps the task at lastStatus RUNNING until it is stopped. stopCode EssentialContainerExited (Smithy TaskStopCode) is reserved for an essential container that actually ran and exited.
Emulator: every container comes back `lastStatus='STOPPED', exitCode=127, healthStatus='UNKNOWN', managedAgents=[]` with `stopCode='EssentialContainerExited'` and `stoppedReason='Essential container in task exited'`, regardless of the command. A probe that encodes four applied settings as exit 40 exits 127 instead; a probe expected to exit 0 exits 127; a task under health-status observation stops instead of staying RUNNING.
Why: a client that launches a task to do work and reads containers[].exitCode to decide success sees 127 for every workload, i.e. a uniform false failure, and no task definition runtime setting (workingDirectory, user, ulimits) can be validated. Nothing that requires a task to stay running can be tested at all.
Fix: the ECS task runtime behind RunTask/StartTask and the service scheduler — the container-materialisation path must actually execute the container's entryPoint/command (with the definition's workingDirectory/user/ulimits applied) and record the real exit status, rather than synthesising a 127 exit and an immediate essential-exit stop.
Traces: ecs.capprov-cluster-default-strategy-governs-a-task-that-names-no-provider, ecs.capprov-zero-capacity-provider-rejects-task-and-no-container-runs, ecs.container-workdir-user-and-ulimit-apply-inside-the-running-container, ecs.health-check-start-period-suppresses-unhealthy-then-expires.

Cause 2 of 7: no ECS Exec session can ever be established, because every exec-enabled task stops before it becomes execable.
AWS: a task launched with enableExecuteCommand=true stays RUNNING and its container reports a managedAgents entry named ExecuteCommandAgent that reaches lastStatus RUNNING (Smithy Container.managedAgents / ManagedAgent); ExecuteCommand then opens a streaming session against the named container, a second session sees the first session's filesystem writes, a resize propagates to the pty, and a task launched without the flag is refused.
Emulator: every one of these checks aborts while waiting for the agent with `AssertionError: task stopped before it was execable: 'Essential container in task exited'` (or "task stopped before becoming ready for exec"); containers are returned with `managedAgents: []`.
Why: ECS Exec is unusable. A client cannot open, stream, target, resize or correctly have refused a session, so no interactive-debugging workflow can be emulated, and the negative case (exec against a task launched without the flag) cannot be exercised either.
Fix: the ECS task runtime plus the ExecuteCommand/ExecuteCommandAgent path — keep an exec-enabled task's container running and publish the ExecuteCommandAgent managed agent so the session endpoints have a live target.
Traces: ecs.exec-disabled-task-session-rejected-while-enabled-streams, ecs.exec-file-write-visible-to-second-session, ecs.exec-interactive-stdout-round-trip, ecs.exec-session-resize-propagates-to-pty, ecs.exec-targets-the-named-container-not-a-sibling, ecs.execute-command-session-credentials-round-trip, ecs.execute-command-succeeds-when-enabled-at-runtime.

Cause 3 of 7: ContainerDefinition.dependsOn is not enforced — a dependent container starts and runs even when its dependency condition was never met.
AWS: Smithy com.amazonaws.ecs#ContainerDependency.condition documents the four conditions: START (dependency started), COMPLETE (dependency ran to completion/exited), SUCCESS ("the same as COMPLETE, but it also requires that the container exits with a zero status"), HEALTHY ("the dependent container passes its Docker health check before permitting other containers to start"). A container gated on SUCCESS whose dependency exits non-zero never starts, so DescribeTasks reports it with NO exitCode. A container gated on HEALTHY starts only after the dependency's health check passes, so the dependency must still be running when the gate opens.
Emulator: the gated container runs anyway. With a dependency that exits 1, the SUCCESS-gated `app` came back `exitCode=42` (the check's own payload) — i.e. SUCCESS was treated as COMPLETE — and in a second case `exitCode=5`. For the HEALTHY case the dependency `db` was reported `lastStatus='STOPPED', exitCode=143` and never produced its readiness artefact, so the dependency never stayed up to become healthy.
Why: dependsOn is the ECS mechanism for init containers and ordered sidecar start-up. A client that relies on it to guarantee a migration/bootstrap step succeeded before the app starts gets the app started unconditionally, which in a real deployment is a data-corrupting ordering bug the emulator will never surface. SUCCESS and COMPLETE also become indistinguishable, hiding the stricter contract.
Fix: the ECS task runtime's container start-ordering logic — evaluate each ContainerDependency's condition (START/COMPLETE/SUCCESS/HEALTHY) against the dependency's real state before starting the dependent container, and leave a never-started container with no exitCode.
Traces: ecs.container-depends-on-success-gates-dependent-start, ecs.container-depends-on-complete-admits-nonzero-exit-unlike-success, ecs.container-depends-on-healthy-waits-for-the-health-check-to-pass.

Cause 4 of 7: `essential: false` is not honoured — a non-essential container exiting stops the whole task.
AWS: Smithy ContainerDefinition.essential documents it exactly: "If the essential parameter of a container is marked as true, and that container fails or stops for any reason, all other containers that are part of the task are stopped. If the essential parameter of a container is marked as false, its failure doesn't affect the rest of the containers in a task." So when a non-essential sidecar exits, the task stays at lastStatus RUNNING and carries no stopCode/stoppedReason; EssentialContainerExited is only correct for an essential container's exit.
Emulator: after the non-essential container exits, the task is reported `lastStatus='STOPPED'` with `stopCode='EssentialContainerExited'` and `stoppedReason='Essential container in task exited'`. The fixed text 'Essential container in task exited' is AWS's wording for the essential case; what diverges is that it is applied to a container whose `essential` is false.
Why: every multi-container task is mis-modelled. A client that runs a log shipper, a one-shot init, or any short-lived sidecar beside its application sees the application killed as soon as the sidecar exits, and cannot distinguish a genuine essential-exit stop from this spurious one.
Fix: the ECS task runtime's task-stop decision — consult each container definition's `essential` flag (defaulting to true when omitted) before stopping the task, and only then set stopCode EssentialContainerExited.
Traces: ecs.essential-container-exit-stops-task-and-sidecar.

Cause 5 of 7: there is no task credential plane — the container-credentials endpoint is not served, so neither the task definition's taskRoleArn nor a RunTask overrides.taskRoleArn is observable to the process.
AWS: a task with a taskRoleArn gets AWS_CONTAINER_CREDENTIALS_RELATIVE_URI set in every container's environment, and 169.254.170.2 serves temporary credentials for that role; the SDK inside the container then acts as the task role. RunTask's overrides.taskRoleArn replaces the task definition's taskRoleArn for that task only (recorded behavior only for the endpoint itself — it is not in the Smithy model; the model only carries TaskOverride.taskRoleArn and TaskDefinition.taskRoleArn).
Emulator: the probe exits 9, meaning AWS_CONTAINER_CREDENTIALS_RELATIVE_URI was unset or 169.254.170.2 served nothing: "there is no task credential plane". Because the control leg cannot read the task-definition role either, the override-vs-definition distinction is unobservable.
Why: this is how every real containerised AWS workload authenticates. A client whose container calls S3/DynamoDB/SSM under its task role gets an unauthenticated container, and an override of the task role — the standard way to run one task definition under different permissions — has no observable effect, so least-privilege regressions pass silently.
Fix: the ECS task runtime — inject AWS_CONTAINER_CREDENTIALS_RELATIVE_URI into the container environment and serve the task-role credentials at 169.254.170.2, resolving the effective role as overrides.taskRoleArn when present and the task definition's taskRoleArn otherwise.
Traces: ecs.task-role-credentials-endpoint-serves-task-role, ecs.run-task-task-role-override-replaces-task-definition-role.

Cause 6 of 7: a task whose image cannot be pulled is reported as an essential-container exit instead of a start failure.
AWS: Smithy com.amazonaws.ecs#TaskStopCode enumerates TaskFailedToStart alongside EssentialContainerExited. A task naming an image tag that does not exist never starts a container, so it stops with stopCode TaskFailedToStart and a stoppedReason/container reason describing the pull failure and naming the image reference that could not be pulled (the reason's variable part is the image/tag from the request; the fixed part is AWS's pull-failure wording, e.g. a CannotPullContainerError describing that the image reference was not found).
Emulator: `expected ('TaskFailedToStart', True), got ('EssentialContainerExited', False) with stoppedReason 'Essential container in task exited'` — the wrong stopCode, and a reason that does not mention the image or tag at all.
Why: stopCode is the field clients branch on to tell "my image/registry/permissions are wrong" from "my program exited". Collapsing a pull failure into EssentialContainerExited sends every CI pipeline, deployment gate and alarm down the wrong diagnosis path, and the absent image name removes the only clue.
Fix: the ECS task runtime's image-pull and task-stop path — classify a failed pull as stopCode TaskFailedToStart and set stoppedReason/container.reason to the pull-failure message naming the requested image reference.
Traces: ecs.run-task-with-an-unpullable-image-reports-failed-to-start-not-running.

Cause 7 of 7: requested ephemeral storage is not provisioned, and the container has no measurable filesystem.
AWS: Smithy com.amazonaws.ecs#EphemeralStorage.sizeInGiB is documented as "The total amount, in GiB, of ephemeral storage to set for the task. The minimum supported value is 21 GiB and the maximum supported value is 200 GiB", and it expands the storage actually available to a Fargate task. A container therefore sees a writable filesystem whose size reflects the default (when ephemeralStorage is omitted) or the requested size, measurable from inside the container.
Emulator: even the control leg (no ephemeralStorage requested) cannot be measured — `the control (no ephemeralStorage) probe could not measure its filesystem (df/awk failed inside the container), so no size was observed: reason=None`. No size is observable, so neither the default nor a requested expansion can be verified.
Why: a client sizing a task for a download, a build cache or a data-processing scratch area gets no feedback that its ephemeralStorage request had any effect, and an application that would run out of disk in production runs "fine" against the emulator.
Fix: the ECS task runtime's volume/filesystem provisioning for Fargate tasks — give the container a real writable root/scratch filesystem whose reported size follows the task's ephemeralStorage.sizeInGiB (and the Fargate default when the member is omitted).
Traces: ecs.ephemeral-storage-request-is-provisioned-inside-the-container.
