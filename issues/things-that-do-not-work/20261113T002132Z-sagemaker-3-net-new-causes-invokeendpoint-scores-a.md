# sagemaker: 3 net-new causes — InvokeEndpoint scores a payload under an unsupported ContentType instead of refusing with ModelError/424, a multi-row CSV inference answer is newline-framed instead of one comma-separated line, and each clock-owed lifecycle transition costs a polling client a whole poll interval

> _Note: this issue was identified against the code base at commit `8b6f252f498885fe00e1ce0c1177e315b4527506`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
InvokeEndpoint

## Description
Three independent root causes found in the behavioral sweep, all in the sagemaker service's own inference-serving and lifecycle-settling state. All three are net-new: no failing check listed below was marked ALREADY FILED or OWNED by an open issue.

=== Cause 1 of 3: an unsupported ContentType is scored anyway instead of being refused by the model container ===
AWS: InvokeEndpoint hands the request body AND its ContentType to the model container. A built-in SageMaker algorithm container that does not accept the offered media type refuses the request, and SageMaker passes that refusal through as the operation's modelled ModelError — HTTP 424 (Failed Dependency, i.e. the failure was the dependency's, not the caller's), with the container's own HTTP status and text carried unwrapped in OriginalStatusCode / OriginalMessage. Smithy: sagemaker-runtime InvokeEndpoint errors include ModelError, whose members are Message, OriginalStatusCode, OriginalMessage, LogStreamArn; the Smithy model documents ModelError as "Model (owned by the customer in the container) returned 4xx or 5xx error code" and says nothing about content-type negotiation itself, so the message shape below is recorded behavior. For the built-in XGBoost container the refusal is HTTP 415 and its own sentence is fixed text `Content-type ` + <the ContentType the request sent> + ` not supported. Supported content-type is text/csv, text/libsvm`. SageMaker's wrapping of it is fixed text `Received client error (` + <the container's status> + `) from model with message "` + <the container's sentence> + `". See https://` + <region> + `.console.aws.amazon.com/cloudwatch/home?region=` + <region> + `#logEventViewer:group=/aws/sagemaker/Endpoints/` + <endpoint name> + ` in account ` + <account id> + ` for more information.` — only region, endpoint name, account id and the offered content type come from the request/state; everything else is fixed. OriginalStatusCode is the CONTAINER's status (415), distinct from the 424 SageMaker wraps it in, and OriginalMessage is the container's sentence alone (so Message != OriginalMessage).
Emulator: the same InvokeEndpoint, against the same InService endpoint and the same valid body, with only the ContentType header changed to an unsupported media type, returns HTTP 200 and a scored prediction body. The request's ContentType is never consulted: crate::state::model_serving::serve_inference takes only the body and the Accept header, decides JSON-vs-CSV purely from Accept, and parses the body as CSV/JSON regardless of what ContentType claims — there is no ServingRefusal variant for an unacceptable request media type at all.
Why: a client that relies on SageMaker to reject input its container cannot parse gets a silent, wrong-but-plausible prediction from the emulator where AWS gives it a 424 ModelError it can catch, log and retry. Worse, a negative-path test suite that asserts the refusal passes against AWS and cannot pass here, and code that mis-sets ContentType ships undetected.
Fix: the content-type negotiation belongs in the sagemaker serving state (services/service-com-amazonaws-sagemaker-sagemaker/src/state/model_serving.rs — serve_inference and the ServingRefusal enum must learn the request's ContentType and a new "media type not supported" refusal), with the sagemaker-runtime InvokeEndpoint handler rendering it as ModelError/424 carrying OriginalStatusCode 415 and the unwrapped OriginalMessage.
Traces: sagemaker.sagemaker-invoke-with-an-unsupported-content-type-rejected-by-the-model-container (assertion: "InvokeEndpoint with ContentType='application/x-unsupported-by-xgboost' SUCCEEDED and returned b'23'").

=== Cause 2 of 3: a multi-row text/csv inference answer is newline-framed instead of one comma-separated line ===
AWS: recorded behavior only (no Smithy member governs the body framing — InvokeEndpoint's Body is a blob). A built-in SageMaker algorithm container answering a multi-record text/csv payload returns ONE line of comma-separated predictions, one field per input record in input order, not one line per record. The per-record values are identical to what the same records score when sent one at a time.
Emulator: a two-row payload is answered with the predictions joined by a newline. Observed body: a two-field answer where the separator is '\n' instead of ','. Source: services/service-com-amazonaws-sagemaker-sagemaker/src/state/model_serving.rs, serve_inference — the CSV rendering path does `predictions.iter().map(f64::to_string).collect::<Vec<_>>().join("\n")`, and the comment above it asserts this is "the form SageMaker's built-in algorithms answer a text/csv payload in".
Why: a client that batches records into one invocation and splits the answer on ',' (the documented and recorded framing) reads the whole response as a single malformed field, or parses one prediction where it sent N. Row-to-prediction alignment — the entire point of batching — is lost.
Fix: the CSV rendering in the sagemaker serving state (model_serving.rs, serve_inference's text/csv branch) must join the per-record predictions with ',' into a single line; the JSON branch (Accept: application/json) is unaffected.
Traces: sagemaker.sagemaker-endpoint-prediction-is-deterministic-and-ordered-in-its-input (assertion: "a batched response is a single comma-separated line, so a newline here means the container's response framing changed: '2.5\n47.5'").

=== Cause 3 of 3: every clock-owed lifecycle transition costs a polling client a full poll interval, so a multi-resource scenario never reaches its last call ===
AWS: recorded behavior only. A scenario that trains a model, deploys an endpoint and then benchmarks it with an Inference Recommender job polls each resource until it reports a terminal status, then calls GetScalingConfigurationRecommendation (Smithy: input InferenceRecommendationsJobName required + EndpointName; output echoes both and carries DynamicScalingConfiguration with MinCapacity/MaxCapacity) and asserts the recommendation names the benchmarked endpoint. Every one of those statuses has to be reachable by a polling client inside the replay.
Emulator: the check never gets as far as GetScalingConfigurationRecommendation — it is cut off with "Check timed out after 60.0s" having answered every call, with no refusal recorded. The emulator settles each transient status behind a stored, deliberately non-zero wall-clock span (crate::state::ENDPOINT_IN_SERVICE_AFTER, TRAINING_JOB_ENDS_AFTER, the Inference-Recommender job's own settle span — all in services/service-com-amazonaws-sagemaker-sagemaker/src/state.rs and its sub-slices), and each is due AFTER the describe that immediately follows the create. Hypothesis: a client therefore pays its whole poll interval for every transition it waits on — the training job (20 s), then the endpoint (20 s), then the recommendations job (30 s) — and the three of them exhaust the replay budget before the last call is ever made, so this scenario is unreachable rather than wrong.
Why: a client (or waiter) that polls at a realistic interval sees each resource stuck in its transient status on the describe that follows its create, and a scenario chaining several resources pays that penalty once per resource. Any multi-resource flow becomes unobservably slow even though the emulator holds the terminal state almost immediately.
Fix: the settling spans in the sagemaker state (services/service-com-amazonaws-sagemaker-sagemaker/src/state.rs and the Inference-Recommender slice behind crate::state::InferenceRecommendationsJob::settle_status) should let a resource be observable in its transient status without charging a polling caller a full interval per transition. The same root cause is already described for a different resource family in open issue 20261110T204514Z-sagemaker-hyperpod-cluster-lifecycle-transitions-are-each-deferred-behind.md — that issue does not cover this check and does not carry its replay key, hence this cause.
Traces: sagemaker.get-scaling-configuration-recommendation-references-endpoint ("Check timed out after 60.0s").

## Evidence
Cause 1 — sagemaker.sagemaker-invoke-with-an-unsupported-content-type-rejected-by-the-model-container
  Expected (AWS): the second InvokeEndpoint is refused. HTTP 424; Error.Code 'ModelError'; Error.Message = 'Received client error (415) from model with message "Content-type <offered-content-type> not supported. Supported content-type is text/csv, text/libsvm". See https://<region>.console.aws.amazon.com/cloudwatch/home?region=<region>#logEventViewer:group=/aws/sagemaker/Endpoints/<endpoint-name> in account <account-id> for more information.'; OriginalStatusCode = 415; OriginalMessage = 'Content-type <offered-content-type> not supported. Supported content-type is text/csv, text/libsvm' (and OriginalMessage != Message). Fixed text: everything outside the angle brackets. Request/state values: the offered content type, the region, the endpoint name, the account id.
  Actual (emulator): HTTP 200 with a scored body — AssertionError: "InvokeEndpoint with ContentType='application/x-unsupported-by-xgboost' SUCCEEDED and returned b'23'; the model container must refuse a content type it does not support rather than scoring the payload anyway". The preceding baseline invocation with ContentType=text/csv on the identical bytes succeeded, so the endpoint was InService and the body valid: the only thing changed was the ContentType header.
  Source: services/service-com-amazonaws-sagemaker-sagemaker/src/state/model_serving.rs — serve_inference(model, body, accept) has no ContentType parameter; ServingRefusal has no unsupported-media-type variant.

Cause 2 — sagemaker.sagemaker-endpoint-prediction-is-deterministic-and-ordered-in-its-input
  Expected (AWS): a two-record text/csv payload returns a single line, '<prediction-for-row-1>,<prediction-for-row-2>', with no newline, each field equal to that row's prediction when invoked alone.
  Actual (emulator): the fields are newline-separated — AssertionError: "a batched response is a single comma-separated line, so a newline here means the container's response framing changed: '2.5\n47.5'".
  Source: services/service-com-amazonaws-sagemaker-sagemaker/src/state/model_serving.rs, serve_inference: `.map(f64::to_string).collect::<Vec<_>>().join("\n")`.

Cause 3 — sagemaker.get-scaling-configuration-recommendation-references-endpoint
  Expected (AWS): after the training job reports Completed, the endpoint InService and the Inference Recommender job COMPLETED, GetScalingConfigurationRecommendation(InferenceRecommendationsJobName, EndpointName) echoes both names and returns a DynamicScalingConfiguration with 1 <= MinCapacity <= MaxCapacity.
  Actual (emulator): "Check timed out after 60.0s" — the scenario is cut off before GetScalingConfigurationRecommendation is reached. No call was refused; the emulator answered every request, but each create-then-describe pair reports the transient status (training job InProgress, endpoint Creating, recommendations job PENDING) because the transition instant is stored to fall due after that first describe, so each waited-on transition costs the caller one whole poll interval (20 s + 20 s + 30 s against a 60 s budget).
  Source: the stored non-zero settle instants in services/service-com-amazonaws-sagemaker-sagemaker/src/state.rs (ENDPOINT_IN_SERVICE_AFTER and siblings) and crate::state::InferenceRecommendationsJob::settle_status, materialised only by the reporting operations.

## Steps to Reproduce
Common setup (all three causes): create an S3 bucket and a SageMaker execution role that trusts sagemaker.amazonaws.com, put a numeric label,f1,f2 training CSV in the bucket, CreateTrainingJob against it with a built-in XGBoost TrainingImage, wait for the job to report Completed, CreateModel on the resulting S3ModelArtifacts, CreateEndpointConfig with one variant and CreateEndpoint, and wait for EndpointStatus InService.

Cause 1: InvokeEndpoint(EndpointName=<endpoint>, ContentType='text/csv', Body='4.0,5.0') and keep the body — it returns 200 with a prediction. Now repeat the identical call changing ONLY ContentType to a media type the container does not accept, e.g. 'application/x-unsupported-by-xgboost'. Expect a ClientError: HTTP 424, Code 'ModelError', OriginalStatusCode 415, OriginalMessage naming the offered content type and the supported ones, and Message wrapping that text with the endpoint's CloudWatch log-group URL. Observed: HTTP 200 with the scored body. Then DescribeEndpoint — the endpoint must still be InService with no FailureReason, and a repeat of the text/csv call must return the byte-identical prediction.

Cause 2: InvokeEndpoint with ContentType='text/csv' and Body='0.5000,0.5000' alone, then with Body='9.5000,9.5000' alone, then with the two rows in ONE payload separated by a newline. Read the batched body: it must be a single line with no '\n', splitting on ',' into exactly two fields equal to the two single-row predictions in input order. Observed: the two predictions joined by '\n'.

Cause 3: after the endpoint is InService, upload a .tar.gz sample-payload object, call CreateInferenceRecommendationsJob(JobType='Default', InputConfig naming the existing endpoint under Endpoints[] plus ModelName and a ContainerConfig), then poll DescribeInferenceRecommendationsJob until Status is terminal, and finally call GetScalingConfigurationRecommendation(InferenceRecommendationsJobName=<job>, EndpointName=<endpoint>). Poll each resource (training job, endpoint, recommendations job) at a realistic interval (20-30 s) as a waiter would: each create-then-describe reports the transient status and the next probe is a full interval later, so the scenario exceeds a 60 s budget and GetScalingConfigurationRecommendation is never reached.
