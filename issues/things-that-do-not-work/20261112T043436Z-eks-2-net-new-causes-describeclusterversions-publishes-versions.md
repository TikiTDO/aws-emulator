# eks: 2 net-new causes — DescribeClusterVersions publishes versions past end of extended support in the default listing, and DescribeAddonConfiguration's schema has no top-level properties (no useFIPS)

> _Note: this issue was identified against the code base at commit `b92c95c734c83d384ee4236e8b1b66139a04e909`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeClusterVersions

## Description
TWO net-new root causes in the EKS read-only reference catalogs, both reached over HTTP 200 responses (no status or error code is at issue — the payload content is). Both must be closed before this issue is resubmitted.

Related OPEN issue that does NOT own these checks (the replay reports them owned by nothing; it is named only so a fixer sees the family): '20261111T150633Z-eks-add-on-cluster-version-and-configuration-schema.md' — its cause 3 reports the cluster-version catalog's VALUES diverging and its cause 5 reports the EFS CSI driver schema being a draft-06 $ref document rather than AWS's published one, both grounded in the WIRE corpus. Cause 2 below is the behavioral consequence of that same shape (a client reading the schema's top-level `properties` finds none) and cause 1 is about WHICH rows the default listing contains, not their values. A similar-looking open issue does not cover these replay units.

Cause 1 of 2: the unfiltered DescribeClusterVersions listing contains Kubernetes versions whose extended support has already ended, so the listing is not covered by its own STANDARD_SUPPORT/EXTENDED_SUPPORT filters and a caller that takes the oldest listed version gets one CreateCluster refuses.
  AWS: Smithy (services/service-com-amazonaws-eks-awswesleyfrontend/smithy-model/com-amazonaws-eks-awswesleyfrontend.json) DescribeClusterVersions GET /cluster-versions, 200, output clusterVersions -> ClusterVersionList + nextToken; httpQuery filters clusterType, clusterVersions, defaultOnly, `includeAll` ("Include all available versions in the response"), `status` (deprecated, ClusterVersionStatus: unsupported|standard-support|extended-support) and `versionStatus` (VersionStatus: UNSUPPORTED|STANDARD_SUPPORT|EXTENDED_SUPPORT). The model declares an UNSUPPORTED state and a separate `includeAll` flag but does not state which rows the default listing carries; recorded behavior only: the replayed checks establish that the DEFAULT listing (no `includeAll`, no status filter) is exactly the union of the two status-filtered listings — i.e. every row it carries is in standard or extended support — and that no row whose `endOfExtendedSupportDate` is in the past appears in it. The rule, in general terms: a version that has aged out of extended support is reachable only when the caller asks for it (`includeAll`, or `versionStatus=UNSUPPORTED`/`status=unsupported`), never in the default listing; the versions the default listing names are the versions a caller may still create a cluster at.
  Emulator: the default listing returns every row of the seeded calendar, including rows whose extended support ended before now. Replay reports the default listing as ['1.23','1.24','1.25','1.26','1.27','1.28','1.29','1.30','1.31','1.32','1.33','1.34','1.35','1.36','1.37'] while versionStatus=STANDARD_SUPPORT plus versionStatus=EXTENDED_SUPPORT together cover only ['1.31'...'1.37'] (the 1.23-1.30 rows derive UNSUPPORTED), and separately reports "1.30 is past extended support but still listed". The handler reads `includeAll` and deliberately discards it (services/service-com-amazonaws-eks-awswesleyfrontend/src/ops/describe_cluster_versions.rs:197-205, `let _ = input.include_all;`), and every released calendar row is reported (same file, lines 243-259); the calendar seed is crate::state's VERSION_CALENDAR (services/.../src/state.rs:4158-4174), whose oldest eight rows have already aged out at the current clock.
  Why: a client that enumerates the catalogue to pick an installable version, or to fold the catalogue by support status, reads versions AWS no longer offers as offered. Taking the oldest listed row and creating a cluster at it then fails: replay shows CreateCluster answering InvalidParameterException "unsupported Kubernetes version 1.23" for a version the service's own listing had just published, so the catalogue and the create path contradict each other and an upgrade planner that walks the listing plans from a floor that does not exist.
  Fix: the DescribeClusterVersions handler's row selection (services/service-com-amazonaws-eks-awswesleyfrontend/src/ops/describe_cluster_versions.rs) together with the calendar in crate::state — the default listing must exclude rows whose derived support status is UNSUPPORTED and admit them only on `includeAll` or an explicit unsupported status filter. Not the serializer: the envelope, paging and per-row fields are already well formed.
  Traces: eks.describe-cluster-versions-version-and-status-filters-partition-the-listing (the two status filters cover fewer versions than the listing), eks.ekscc-cluster-versions-support-status-agrees-with-support-dates (a row past end of extended support is still listed), eks.cluster-update-serialization (the oldest listed version is then refused by CreateCluster).

Cause 2 of 2: DescribeAddonConfiguration publishes the add-on configuration schema as a bare root `$ref` into its own `definitions`, so the document declares no top-level `properties` and the add-on's own options (for aws-efs-csi-driver, `useFIPS`) cannot be found where AWS declares them.
  AWS: Smithy DescribeAddonConfiguration GET /addons/configuration-schemas, 200, required httpQuery addonName + addonVersion, output addonName, addonVersion, configurationSchema (String), podIdentityConfiguration; errors InvalidParameterException 400, ResourceNotFoundException 404, ServerException 500. The model does not describe the schema document's shape; recorded behavior only: the replayed checks read `json.loads(configurationSchema)["properties"]["useFIPS"]["type"]` for aws-efs-csi-driver and require it to be "boolean", i.e. AWS publishes a document whose ROOT object declares the add-on's configurable keys under `properties` (the EFS CSI driver's `useFIPS` boolean among them — the key the User Guide's FIPS install sets). The requirement is the shape: the keys an add-on takes are declared at the document root, not only behind a reference.
  Emulator: the root document is `{"$schema": <dialect>, "$ref": "#/definitions/<Addon>", "definitions": {...}}` with the property set moved inside the referenced definition (services/service-com-amazonaws-eks-awswesleyfrontend/src/state/addon_catalog.rs:1372-1465, `configuration_schema_value`), so a reader of the root finds `properties` absent. Replay reports "useFIPS is not a boolean property of the schema: None" and "aws-efs-csi-driver v3.2.0-eksbuild.1 must declare useFIPS as a boolean; its properties are []". The catalog seed itself does carry ("useFIPS", "boolean") for that add-on (same file, line 427), so the data is present and only the published document's shape loses it.
  Why: a client that loads the published schema to decide whether an option exists, to build a form over the add-on's knobs, or to validate `configurationValues` before CreateAddon/UpdateAddon, sees an add-on with no configurable properties at all; the FIPS switch and every other per-add-on option become undiscoverable, and validation written against AWS's document resolves nothing against the emulator's.
  Fix: the published configuration-schema document in the add-on catalog state (services/service-com-amazonaws-eks-awswesleyfrontend/src/state/addon_catalog.rs, `AddonCatalogRecord::configuration_schema_value`, which both DescribeAddonConfiguration and CreateAddon's validation read) — the root object must declare the add-on's keys under `properties`, as AWS publishes them.
  Traces: eks.create-addon-on-missing-cluster-rejected-before-schema-validation, eks.efs-csi-driver-configuration-lookup-with-another-addons-version-not-found.

Note on values: the concrete version strings (1.23-1.37, 1.30), the add-on build string (v3.2.0-eksbuild.1) and the key name useFIPS are the replay's EXAMPLES of the two requirements (the default version listing carries only versions still in support; an add-on's published schema declares its own keys at the document root). They are reference data, not literals to pin.
