# cloudfront__pricing-plan-manager__wafv2: 4 net-new root causes — CreateSubscription ignores clientToken parameter conflicts and resource-already-subscribed, CancelSubscription answers the wrong class for a stale If-Match, and CloudFront lets a subscribed distribution drop its web ACL

> _Note: this issue was identified against the code base at commit `c6516c5463abfac6c10762734949ce363897af5e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateSubscription, CancelSubscription, UpdateDistribution

## Description
Four independent root causes in the pricing-plan-manager subscription surface and its CloudFront side-effect gate. All four are refusals AWS issues and the emulator does not (or issues under the wrong class), so a client reading the emulator's answer believes a call was accepted or mis-classifies the retry it must do. None of these is covered by the open issues 20261109T121305Z-cloudfront-pricing-plan-manager-wafv2-createsubscription-does-not.md (resource eligibility: distribution has no web ACL attached) or 20261109T121305Z-pricing-plan-manager-2-net-new-root-causes.md (unrecognized planFamily; 404 on subscription-ARN ops) — those describe different gates on the same operations.

Cause 1 of 4: CreateSubscription treats ANY clientToken replay as an idempotent hit and never compares the replayed request's parameters, so a reused token carrying DIFFERENT parameters is answered 200 instead of being refused as a conflict.
AWS: Smithy (services/service-com-amazonaws-pricingplanmanager-awspricingplanmanager/smithy-model/com-amazonaws-pricingplanmanager-awspricingplanmanager.json): CreateSubscription.clientToken targets IdempotencyToken with @idempotencyToken, @length 1..64; the operation models ConflictException (httpError 409, required members message + resourceId, doc "The request conflicts with the current state of the resource"). Recorded behavior: a replay with the SAME token and the SAME parameters returns the first subscription's arn (the emulator already does this, and the check's earlier assertion passed); a replay with the same token and a DIFFERENT planTier is refused HTTP 409, Error.Code "ConflictException", Error.Message "The clientToken matches a previous request but the request parameters differ. Reuse a clientToken only for an identical request." That whole sentence is fixed text — it carries no value from the request or from state — so it must be reproduced verbatim. The refusal must change nothing: the account still holds exactly the one subscription for the distribution and its planTier is still the originally created one.
Emulator: CreateSubscription(planFamily="CloudFront", planTier="PRO", resourceArns=[<dist-arn>, <webacl-arn>], clientToken=<token already used for a FREE subscription>) answers HTTP 200 with the stored FREE subscription. services/service-com-amazonaws-pricingplanmanager-awspricingplanmanager/src/ops/create_subscription.rs lines 227-240 look the token up in store.idempotency and return existing.to_subscription() unconditionally; the record's own plan_family/plan_tier/usage_level/resource_arns are never compared with the incoming input, and SubscriptionRecord.client_token (line 285) is stored but never used as a conflict key.
Why: clientToken is the client's safe-retry mechanism. A client that retries with a token after EDITING the request (a different tier, a different resource set) is told 200 and reads back a subscription that silently does not match what it asked for — it believes it bought PRO and is on FREE, with no error to surface. AWS makes that programming mistake loud; the emulator makes it invisible.
Fix: CreateSubscription's handler/validation in services/service-com-amazonaws-pricingplanmanager-awspricingplanmanager/src/ops/create_subscription.rs — the idempotency branch must compare the request's identity-bearing members (planFamily, planTier, usageLevel, resourceArns, approvalMode) against the record the token points at, return the existing subscription only when they are identical, and otherwise return the modeled ConflictException (409) with the sentence above and resourceId naming the existing subscription's ARN, mutating nothing.
Traces: cloudfront__pricing-plan-manager__wafv2.create-subscription-client-token-replay-returns-same-subscription.

Cause 2 of 4: CreateSubscription does not check whether a named resource is already covered by another subscription, so a second subscription over the same CloudFront distribution is minted instead of refused.
AWS: Smithy: CreateSubscription.resourceArns @required ResourceArns @length(1,10); ValidationException (httpError 400, member message + optional resourceId) is documented as "The request failed a business rule validation. For example, the specified resource might already be associated with another subscription" — this exact rule. Recorded behavior: with one ACTIVE subscription already covering the distribution, a second CreateSubscription naming it is refused HTTP 400, Error.Code "ValidationException", Error.Message "Cannot create subscription with <resource-arn>: resource must belong to your account and not be used in another subscription." The fixed text is "Cannot create subscription with ", the ": resource must belong to your account and not be used in another subscription." tail; the variable part is the offending resource ARN taken from the request (here the distribution ARN). The refusal creates nothing: ListSubscriptions over all pages still finds exactly the first subscription for that resource, still ACTIVE, still naming the same resourceArns.
Emulator: the second CreateSubscription(planFamily="CloudFront", planTier="FREE", resourceArns=[<dist-arn>, <webacl-arn>]) answers HTTP 200 and mints a second ACTIVE subscription with a new ARN over the same distribution. In create_subscription.rs, between the capacity check (lines 242-256) and insert_subscription (line 293), resource_arns is moved into the record (line 281) without any scan of store.subscriptions for an existing subscription holding any of those ARNs.
Why: a resource can be on at most one pricing plan. A client that double-subscribes gets 200 and an account whose billing state is ambiguous — two ACTIVE subscriptions naming one distribution — a state real AWS can never reach, so recovery code (and any de-dup logic keyed on "one subscription per resource") is never exercised and reconciliation against real AWS diverges.
Fix: CreateSubscription's handler/validation in services/service-com-amazonaws-pricingplanmanager-awspricingplanmanager/src/ops/create_subscription.rs — before minting, reject with the modeled ValidationException (400) and the message above when any entry of resourceArns is already present in the resourceArns of a non-terminated subscription in state, naming the first such ARN; no state mutation on the refusal path.
Traces: cloudfront__pricing-plan-manager__wafv2.subscribed-distribution-rejected-for-second-subscription.

Cause 3 of 4: CancelSubscription refuses a stale If-Match ETag under the wrong error class and the wrong message — ConflictException/409 instead of ValidationException/400.
AWS: Smithy: CancelSubscription.ifMatch is @required and bound to the If-Match HTTP header; the operation models both ValidationException (httpError 400) and ConflictException (httpError 409, whose doc does mention the If-Match case generically). Recorded behavior for an ETag that is not the current one: HTTP 400, Error.Code "ValidationException", Error.Message "Invalid or outdated ETag '<etag>': retrieve current ETag and retry." The fixed text is "Invalid or outdated ETag '" and "': retrieve current ETag and retry."; the variable part is the ETag value echoed from the request's If-Match header. Hypothesis for the split against the ConflictException doc: a value that is not a currently-issued ETag is a validation failure, while ConflictException is reserved for a state conflict — the recording is what fixes the class here. The refusal must be inert: GetSubscription still reports status ACTIVE, carries NO scheduledChange, and returns the SAME eTag as before the refused call.
Emulator: CancelSubscription(arn=<sub-arn>, ifMatch=<stale>) answers Error.Code "ConflictException" with Error.Message "the If-Match header does not match the current version of the subscription; retrieve the latest version and retry" — wrong class, wrong HTTP status (409 vs 400), and a message that is neither AWS's wording nor echoes the offending ETag. services/service-com-amazonaws-pricingplanmanager-awspricingplanmanager/src/ops/cancel_subscription.rs lines 192-200 map state::PreconditionFailure::ETagMismatch onto ConflictException with state::IF_MATCH_CONFLICT_MESSAGE.
Why: the class drives client behavior. A 409 ConflictException reads as a retryable optimistic-concurrency collision (botocore and hand-written retry wrappers treat conflict differently from validation), while AWS reports a 400 ValidationException the client must fix by re-reading the ETag. A client written against AWS either loops on the 409 or fails to match on the error code it was told to expect, and the message it logs does not name the ETag it sent.
Fix: CancelSubscription's refusal mapping in services/service-com-amazonaws-pricingplanmanager-awspricingplanmanager/src/ops/cancel_subscription.rs (the ETagMismatch arm), and the shared message constant in src/state.rs it uses — return the modeled ValidationException (400) with the sentence above, interpolating the If-Match value from the request, and keep the record and its ETag untouched. Apply the same mapping to the other If-Match-bearing subscription mutators so the class is consistent.
Traces: cloudfront__pricing-plan-manager__wafv2.stale-etag-cancel-rejected-subscription-stays-active. (Not reached in this run, so stated only as a follow-on hypothesis for the fixer re-replaying this check: the same check then cancels with the CURRENT ETag and polls GetSubscription for ResourceNotFoundException, while cancel_subscription.rs lines 215-224 only attach a scheduled cancellation to an ACTIVE record; that assertion is downstream of this fix, not a separate claim here.)

Cause 4 of 4: CloudFront UpdateDistribution lets a distribution covered by an ACTIVE flat-rate pricing-plan subscription drop its web ACL, instead of refusing the update.
AWS: Smithy (services/service-com-amazonaws-cloudfront-cloudfront2020-05-31/smithy-model/com-amazonaws-cloudfront-cloudfront2020-05-31.json): UpdateDistribution models InvalidArgument (httpError 400, member Message) and takes the whole DistributionConfig as its @httpPayload. The subscription-held-web-ACL rule itself is recorded behavior only: a PUT of the current config with WebACLId set to "" while a pricing-plan subscription covers the distribution is refused HTTP 400, Error.Code "InvalidArgument", Error.Message "You can't remove or replace the web ACL for your distribution. Distributions with a pricing plan subscription must have a web ACL resource." Both sentences are fixed text naming no value from the request or state. The refusal leaves the config untouched: GetDistributionConfig still reports WebACLId equal to the subscribed web ACL ARN. Once the subscription is cancelled, the identical update must succeed and WebACLId must become "" (the check's positive control).
Emulator: with an ACTIVE FREE CloudFront-family subscription naming the distribution and its CLOUDFRONT-scope web ACL, GetDistributionConfig + UpdateDistribution with WebACLId="" returns success (the check's _error helper reports "expected the call to be rejected, but it succeeded: None"), and the web ACL comes off. services/service-com-amazonaws-cloudfront-cloudfront2020-05-31/src/ops/update_distribution.rs runs its validation chain (through the missing-price-class check at lines 586-593) and then calls store.apply_config(...) at line 595; nothing in that chain consults pricing-plan-manager subscription state, and no WebACLId-removal gate exists.
Why: the whole point of the flat-rate CloudFront plan is that the protected distribution keeps a web ACL. A client (or an IaC drift-correction run) that PUTs a config without WebACLId is told the removal succeeded, so it believes the distribution is unprotected-but-consistent, while real AWS would have refused and kept the ACL. Teardown ordering is also inverted: against AWS you must cancel the subscription first, and the emulator rewards the wrong order with success.
Fix: UpdateDistribution's validation in services/service-com-amazonaws-cloudfront-cloudfront2020-05-31/src/ops/update_distribution.rs — before apply_config, when the stored distribution's WebACLId is non-empty and the submitted DistributionConfig would clear or change it, consult pricing-plan-manager subscription state for a non-terminated subscription whose resourceArns name this distribution and return the modeled InvalidArgument (400) with the sentence above; admit the same update once no such subscription exists. This needs the cross-service state read, which is the component the gate belongs in.
Traces: cloudfront__pricing-plan-manager__wafv2.subscribed-distribution-web-acl-cannot-be-removed.
