# autoscaling: PutNotificationConfiguration accepts a malformed TopicARN instead of refusing it, and a launch lifecycle hook never parks the instance in Pending:Wait (2 causes)

> _Note: this issue was identified against the code base at commit `7011ad447146056dadde7fecb62590edf9d79855`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutNotificationConfiguration

## Description
Two net-new root causes in the Auto Scaling notification/lifecycle-hook surface. A fixer must close BOTH before submitting.

Cause 1 of 2: PutNotificationConfiguration accepts a TopicARN that is not ARN-shaped and answers 200, instead of refusing the call. Failing check ids: autoscaling.put-notification-configuration-invalid-topic-arn-rejected, autoscaling.notification-config-create-delete-lifecycle.
AWS: the Smithy model (services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/smithy-model/com-amazonaws-autoscaling-autoscaling-2011-01-01.json) types PutNotificationConfigurationType$TopicARN as XmlStringMaxLen255 (@length 1..255, pattern ^[\u0020-\uD7FF\uE000-\uFFFD\uD800\uDC00-\uDBFF\uDFFF\r\n\t]*$) and documents it as "The Amazon Resource Name (ARN) of the Amazon SNS topic"; the model carries no ARN-shape constraint and no message text, so for the refusal itself this is recorded behavior only. The recording shows the call refused with HTTP 400, error code ValidationError, and the message "Invalid TopicARN: <TopicARN>" — the fixed text is "Invalid TopicARN: " and the only variable part is the TopicARN value taken verbatim from the request (the recording's value happened to be the literal not-an-arn; that value is not part of the requirement). Because the request is refused, no notification configuration is created for the group, and an already-stored configuration for another topic is left untouched.
Emulator: the call SUCCEEDS. Replay shows HTTP 200 with an empty PutNotificationConfigurationResult body (content-type text/xml, content-length 303) and no error at all, so the harness reports "expected the call to be rejected, but it SUCCEEDED". The handler's only input rules are the NotificationTypes catalog check and the 10-topics-per-group ceiling; nothing inspects whether TopicARN names an SNS topic. The non-ARN value is then stored as a notification configuration key and later silently skipped at publish time (the publisher drops any topic whose ARN yields no Region), so the group appears configured to notify a destination that can never receive anything.
Why: a client that mistypes or mis-templates a topic ARN (a bare topic name, a truncated ARN, an ARN of the wrong service) gets a 200 from the emulator and believes its notification wiring is in place. On AWS the same call fails fast with ValidationError and the client corrects it. Against the emulator the error surfaces much later as silently missing notifications, and any code path that tests its own error handling by submitting a bad ARN never sees the refusal.
Fix: the input validation of the PutNotificationConfiguration handler (services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/ops/put_notification_configuration.rs), before the store write in services/.../src/state/notification_configurations.rs::StoredGroup::put_notification_configuration — TopicARN must be validated as an SNS topic ARN and refused with ValidationError carrying AWS's fixed text plus the request's value, leaving the group's existing configurations unchanged.
Traces: autoscaling.put-notification-configuration-invalid-topic-arn-rejected (the rejection check), autoscaling.notification-config-create-delete-lifecycle (the same refusal asserted mid-lifecycle, after a good configuration was stored).

Cause 2 of 2: a group carrying an autoscaling:EC2_INSTANCE_LAUNCHING lifecycle hook never reports a launching instance in Pending:Wait, so the hook-plus-notification end-to-end flow never reaches a verdict. Failing check id: autoscaling.e2e-lifecycle-hook-notification-flow.
AWS: the model's hook contract (LifecycleHook$LifecycleTransition "Valid values: autoscaling:EC2_INSTANCE_LAUNCHING | autoscaling:EC2_INSTANCE_TERMINATING"; LifecycleHook$HeartbeatTimeout "the maximum time, in seconds, that can elapse before the lifecycle hook times out. If the lifecycle hook times out, Amazon EC2 Auto Scaling performs the action that you specified in the DefaultResult property"; CompleteLifecycleAction with a @required LifecycleActionResult) requires a wait state to exist: after SetDesiredCapacity raises capacity, DescribeAutoScalingGroups(...).AutoScalingGroups[0].Instances[].LifecycleState reports the new instance as 'Pending:Wait', DescribeAutoScalingInstances independently reports the same state for that InstanceId, and the instance leaves that state only on CompleteLifecycleAction (LifecycleActionResult=CONTINUE advances it to InService) or on HeartbeatTimeout expiry (then DefaultResult applies).
Emulator: no instance is ever reported in Pending:Wait. The check stores the hook and the notification configuration successfully (DescribeNotificationConfigurations echoes the topic and all four notification types), then polls DescribeAutoScalingGroups for an instance in 'Pending:Wait' and never sees one; the check is killed by the harness with "Check timed out after 60.0s" having produced no verdict, so CompleteLifecycleAction and the subsequent InService transition are never exercised.
Why: any deployment that gates admission of a new instance on a launch hook — warm-up, config bootstrap, registration with an external system — degrades to no hook at all: the instance is admitted without the client ever being given the chance to complete or abandon the action, and a client that waits for Pending:Wait before publishing its action token waits forever.
Fix: the instance lifecycle state machine in the autoscaling service state (the reconciliation that advances Pending -> Pending:Wait -> Pending:Proceed -> InService) must consult the group's lifecycle-hook collection and hold the instance until CompleteLifecycleAction or HeartbeatTimeout. Open issue 20261111T132217Z-autoscaling-lifecycle-hooks-are-stored-but-never-executed.md describes the same state-machine gap, but the replay does not report this check as owned by it and this check id is not among its trace ids, so it does not cover this failure; the fix for that issue should also close this check.
Traces: autoscaling.e2e-lifecycle-hook-notification-flow.

## Evidence
Cause 1 — Expected (AWS): autoscaling:PutNotificationConfiguration(AutoScalingGroupName=<existing group>, TopicARN=<not ARN-shaped>, NotificationTypes=[autoscaling:EC2_INSTANCE_LAUNCH]) -> HTTP 400, Error.Code = "ValidationError", Error.Message = "Invalid TopicARN: <the TopicARN from the request>" (fixed text "Invalid TopicARN: " + the request value); DescribeNotificationConfigurations(AutoScalingGroupNames=[group]) afterwards returns NotificationConfigurations == [] for a group that had none, and returns exactly the previously stored configuration unchanged for a group that had one.
Actual (emulator): HTTP 200 with an empty result body — ResponseMetadata {'HTTPStatusCode': 200, 'HTTPHeaders': {'content-type': 'text/xml', 'content-length': '303'}} and no Error member. Harness details: autoscaling.put-notification-configuration-invalid-topic-arn-rejected -> AssertionError "expected the call to be rejected, but it SUCCEEDED and returned {...'HTTPStatusCode': 200...}"; autoscaling.notification-config-create-delete-lifecycle -> AssertionError "real AWS rejects this call, but it SUCCEEDED and returned {...'HTTPStatusCode': 200...}". The malformed value is accepted into the group's notification_configurations map keyed by topic.

Cause 2 — Expected (AWS): with PutLifecycleHook(LifecycleTransition=autoscaling:EC2_INSTANCE_LAUNCHING, HeartbeatTimeout=300, DefaultResult=ABANDON) on the group, SetDesiredCapacity(DesiredCapacity=1, HonorCooldown=false) makes DescribeAutoScalingGroups report Instances[].LifecycleState == 'Pending:Wait' within seconds, DescribeAutoScalingInstances(InstanceIds=[that id]) confirms 'Pending:Wait', and CompleteLifecycleAction(LifecycleActionResult='CONTINUE') then drives it to 'InService'.
Actual (emulator): no instance ever reports 'Pending:Wait'; the poll never satisfies its predicate and the check ends as "Error: Check timed out after 60.0s" with no response recorded for CompleteLifecycleAction. The notification configuration stored alongside the hook does round-trip correctly, so the divergence is confined to the wait state.
