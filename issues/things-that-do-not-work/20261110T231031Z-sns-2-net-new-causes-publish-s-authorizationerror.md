# sns: 2 net-new causes — Publish's AuthorizationError names the resource-based policy instead of the identity-based one, and topic-policy grants carrying sns:Endpoint / aws:PrincipalArn conditions never admit the matching principal

> _Note: this issue was identified against the code base at commit `cd6d73564e5f4cf53934bca1327f08de31f2ee5f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Publish

## Description
Two net-new root causes in SNS's topic-policy authorization. Each is listed with its own failing check ids; both must be closed.

Cause 1 of 2: the AuthorizationError message SNS returns when it refuses a Publish names the wrong policy type. Failing checks: sns.deploy-cfn-removing-a-topic-inline-policy-restores-the-default-policy, sns.deploy-cfn-topic-policy-authorizes-only-the-named-role-and-follows-updates, sns.topic-policy-subscribe-only-grant-refuses-the-roles-publish.
AWS: Smithy (sns 2010-03-31) Publish declares AuthorizationErrorException, awsQueryError code `AuthorizationError`, HTTP 403. For a principal that holds no identity-based grant for sns:Publish — whether the topic policy never named it, named only another role, named it for SNS:Subscribe only, or stopped naming it because an AWS::SNS::TopicInlinePolicy/TopicPolicy was removed and the default policy came back — the message is "User: <caller ARN> is not authorized to perform: SNS:Publish on resource: <topic ARN> because no identity-based policy allows the SNS:Publish action". Fixed text (the requirement): "User: ", " is not authorized to perform: ", " on resource: ", " because no identity-based policy allows the ", " action". Variable parts come from the request and state: the caller's ARN (here arn:aws:sts::<account>:assumed-role/<role-name>/<session-name>), the topic ARN, and the action name (SNS:Publish). The emulator's code and HTTP status are already right.
Emulator: the identical message is returned with "because no resource-based policy allows the SNS:Publish action" — every byte before that clause matches, only 'resource-based' stands where AWS writes 'identity-based'.
Why: the refusal sends the caller to the wrong policy. An operator or automated remediation edits the topic's resource policy when AWS is reporting that the principal has no identity-based permission at all, and any client asserting on or classifying this text disagrees with real AWS. Note: open issue 20261110T210703Z-lambda-sns-sqs-sns-subscribe-s-authorizationerror-message.md reports the same clause for Subscribe under another service heading and does not carry these checks' replay keys; a single fix in the shared message builder may close all of them.
Fix: the SNS authorization path's error-message construction for Publish (and the shared builder behind it) — pick the 'no identity-based policy allows the <action> action' clause when the caller holds no identity-based grant.

Cause 2 of 2: a topic-policy statement whose grant depends on a condition key is never honoured for the principal it does admit, so even the positive control is refused and the check cannot finish. Failing checks: sns.topic-policy-endpoint-condition-limits-which-queue-a-role-may-subscribe, sns.topic-policy-principal-arn-pattern-admits-only-matching-roles.
AWS: a topic policy statement Allowing SNS:Subscribe to a role under Condition StringEquals {"sns:Endpoint": [<queue arn>]} admits a Subscribe of exactly that endpoint and refuses any other endpoint with AuthorizationError, creating nothing; widening the condition to name a second endpoint makes the identical Subscribe succeed. A statement Allowing SNS:Publish to Principal "*" under Condition ArnLike {"aws:PrincipalArn": "arn:<partition>:iam::<account>:role/<prefix>-pub-*"} admits a role whose ARN matches the pattern — its messages are published and delivered — and refuses a non-matching role with AuthorizationError. Recorded behavior only for the condition-key evaluation (IAM condition keys are not Smithy shapes); the operations are Smithy sns 2010-03-31 Subscribe and Publish, both declaring AuthorizationErrorException (code AuthorizationError, HTTP 403).
Emulator: neither check ever reaches an assertion — each is killed by the harness at its 60 s ceiling. In both, the only waiting the check does is a bounded retry that re-issues the call while it is answered AuthorizationError, waiting for the just-written grant to take effect; the condition-free siblings of these checks complete well inside the same ceiling. Hypothesis: the topic-policy evaluator does not implement the sns:Endpoint and aws:PrincipalArn condition keys (or the ArnLike operator / Principal "*" + condition form), so the conditioned statement never admits anybody and the matching principal's Subscribe/Publish is refused forever.
Why: condition keys are how a topic policy is scoped — pinning a subscriber to one endpoint, or granting a whole family of roles by ARN pattern. If a conditioned grant never admits its principal, every such policy reads as a total denial: legitimate subscribers and publishers are locked out, and the client cannot tell a mis-scoped condition from an unsupported one.
Fix: the SNS topic-policy evaluator's condition handling — evaluate the request context keys SNS supplies (sns:Endpoint, sns:Protocol) and the global ones (aws:PrincipalArn) with their operators (StringEquals, ArnLike) including the Principal "*" + condition form, so a matching principal is admitted and only a non-matching one is refused.

Traces: the five failing check ids above.

## Evidence
Cause 1 — Expected: ('AuthorizationError', 'User: arn:aws:sts::<account>:assumed-role/<role>/<session> is not authorized to perform: SNS:Publish on resource: <topic arn> because no identity-based policy allows the SNS:Publish action'). Actual: the same string ending '... because no resource-based policy allows the SNS:Publish action', reproduced in all three checks (role/session/topic names in the recorded runs are per-run values that fill the template; the policy-type clause is the defect).
Cause 2 — Expected: for the sns:Endpoint check, the role's Subscribe of the named endpoint returns a subscription ARN under the topic, the other endpoint is refused with AuthorizationError 'User: <assumed role arn> is not authorized to perform: SNS:Subscribe on resource: <topic arn> because no identity-based policy allows the SNS:Subscribe action', and ListSubscriptionsByTopic lists only the allowed endpoint; for the aws:PrincipalArn check, the pattern-matching role's publishes are delivered to the subscribed queue and the non-matching role is refused with the equivalent SNS:Publish message. Actual: `Error: Check timed out after 60.0s` in both — no verdict is ever reached, the only retry in each check being the bounded wait on AuthorizationError for the grant to become effective.

## Steps to Reproduce
Cause 1: (a) CreateTopic; create a bare IAM role the account root may assume (no identity policy) and assume it; SetTopicAttributes Policy = default + a statement allowing only SNS:Subscribe to that role; Publish as the role. (b) Deploy a stack with AWS::SNS::Topic + two AWS::IAM::Role + an AWS::SNS::TopicPolicy naming only RoleA, assume RoleB and Publish. (c) Deploy a stack with AWS::SNS::TopicInlinePolicy granting the role Publish, then update the stack removing it so the default policy returns, and Publish as the role. In each case compare the AuthorizationError message's final clause ('identity-based' in AWS, 'resource-based' in the emulator).
Cause 2: (a) CreateTopic; create a bare role and assume it; SetTopicAttributes Policy = default + {Effect Allow, Principal the role ARN, Action SNS:Subscribe, Resource the topic, Condition StringEquals sns:Endpoint = [<queue-A arn>]}; Subscribe as the role with Endpoint=<queue-A arn> — AWS returns a subscription ARN, the emulator keeps answering AuthorizationError. (b) CreateTopic with an SQS subscriber; create two bare roles named <family>-pub-a and <family>-ops-a; SetTopicAttributes Policy = default + {Effect Allow, Principal "*", Action SNS:Publish, Resource the topic, Condition ArnLike aws:PrincipalArn = arn:aws:iam::<account>:role/<family>-pub-*}; Publish as the -pub-a role — AWS accepts and delivers, the emulator keeps answering AuthorizationError.
