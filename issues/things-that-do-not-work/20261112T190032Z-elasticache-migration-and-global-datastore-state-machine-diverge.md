# ElastiCache migration and Global-datastore state machine diverge from AWS, and a CFN CacheCluster stack rolls back (5 causes)

> _Note: this issue was identified against the code base at commit `9f30cc5f50e7736550fc9d928f8a80b554132b0d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CompleteMigration

## Description
Five net-new root causes in the elasticache emulator, none of them marked ALREADY FILED or OWNED by the replay report. Each must be closed separately before this issue is submitted.

Cause 1 of 5: TestMigration is refused while the replication group carries a migration the emulator never retires.
  AWS: Smithy TestMigration takes ReplicationGroupId + CustomerNodeEndpointList, returns TestMigrationResponse{ReplicationGroup}, and models ReplicationGroupAlreadyUnderMigrationFault (awsQueryError code ReplicationGroupAlreadyUnderMigrationFault, HTTP 400) among its errors. Recorded behavior: after StartMigration against an unreachable customer endpoint (an address in TEST-NET-3), the group settles back to Status 'available' and TestMigration is then accepted — HTTP 200 with a ReplicationGroup member in the body; AWS does not raise the already-under-migration fault for this state.
  Emulator: TestMigration answers HTTP 400 ReplicationGroupAlreadyUnderMigrationFault with Message 'Replication group <replication-group-id> is already under migration.' ('Replication group ' + ' is already under migration.' fixed, the id taken from the request), even though DescribeReplicationGroups reports the group 'available'. Hypothesis: StartMigration sets an under-migration flag that is never cleared when the source is unreachable, so the group is permanently 'under migration'.
  Why: a client cannot probe connectivity to its source before cutting over, and the group is wedged — every migration-gated call after the first StartMigration is refused for the life of the group.
  Fix: the TestMigration handler's migration-state gate and the replication-group migration state it reads (the elasticache crate's migration state projection). Note the stale open issue 20261109T151249Z-elasticache-testmigration-stub.md still describes TestMigration as an unimplemented stub; it is implemented now and answers this fault instead.
  Traces: elasticache.migration-state-transitions.

Cause 2 of 5: CompleteMigration(Force=True) is ACCEPTED on a group that is not in migrating state.
  AWS: Smithy CompleteMigration takes ReplicationGroupId and Force and models InvalidParameterValueException (awsQueryError InvalidParameterValue, HTTP 400) and ReplicationGroupNotUnderMigrationFault. Recorded behavior: once the migration to an unreachable source has been abandoned and the group is back at 'available', both CompleteMigration(ReplicationGroupId=...) and CompleteMigration(..., Force=True) are refused with HTTP 400 InvalidParameterValue and Message 'The replication group must be in migrating state to complete the migration. Please retry later.' (the whole sentence is fixed text, no variable part), and the group stays 'available'. The same emulator answers that refusal correctly for the no-migration-ever-started case in this very check, so only the post-StartMigration path diverges.
  Emulator: CompleteMigration(Force=True) returns HTTP 200 with a ReplicationGroup whose Status is 'modifying' — the forbidden effect happens.
  Why: a client is told a migration completed that never ran; Force silently cuts a group over to a source that was never reachable, and the Start->Complete ordering contract is unenforced.
  Fix: the CompleteMigration handler's state gate (it must require an in-flight 'migrating' migration for both the Force and non-Force paths) and the abandonment of a migration whose customer endpoint never becomes reachable, in the elasticache crate's migration state.
  Traces: elasticache.online-migration-lifecycle.

Cause 3 of 5: the DisassociateGlobalReplicationGroup refusal for the PRIMARY member carries emulator prose.
  AWS: Smithy DisassociateGlobalReplicationGroup models InvalidParameterValueException (awsQueryError InvalidParameterValue, HTTP 400). Recorded behavior: disassociating the PRIMARY member of a Global datastore is refused 400 InvalidParameterValue with Message 'Cannot disassociate primary replication group. Primary Replication Group will be disassociated when you delete the Global Replication Group.' — the entire message is fixed text with NO variable part, and the member list is unchanged.
  Emulator: the code is right (InvalidParameterValue) but the message is 'Invalid value <replication-group-id> for ReplicationGroupId: the primary of Global Replication Group <global-replication-group-id> cannot be disassociated.' — the emulator's own sentence, echoing the request's ReplicationGroupId and the group id.
  Why: AWS's sentence tells a client the remedy (delete the global group); a client surfacing or matching AWS's text sees invented prose instead.
  Fix: the DisassociateGlobalReplicationGroup handler's primary-member check must emit AWS's fixed sentence instead of the shared 'Invalid value <v> for <member>' template.
  Traces: elasticache.global-replication-group-lifecycle-full-transition.

Cause 4 of 5: the DeleteGlobalReplicationGroup state-gate refusal carries emulator prose.
  AWS: Smithy DeleteGlobalReplicationGroup models InvalidGlobalReplicationGroupStateFault (awsQueryError InvalidGlobalReplicationGroupState, HTTP 400). Recorded behavior: deleting a global datastore that still has an associated secondary is refused 400 InvalidGlobalReplicationGroupState with Message 'Cannot delete a global replication group in <state> state' — fixed text 'Cannot delete a global replication group in ' + ' state', the single variable part being the datastore's current Status ('creating' or 'modifying' while the association settles); no trailing period. The group is left undeleted with both members.
  Emulator: right code, wrong message: 'Global Replication Group <global-replication-group-id> is in modifying state, not available or primary-only.' — a different sentence that names the id AWS does not name and states the allowed states AWS does not state.
  Why: a client keying retry on AWS's sentence (which names only the transitional state) does not match, so a transient 'still associating' refusal is indistinguishable from a permanent one.
  Fix: the DeleteGlobalReplicationGroup handler's state gate must emit AWS's per-operation sentence rather than the shared global-replication-group state-gate message. Related open issue 20261109T151249Z-elasticache-state-gate-and-limit-refusals-answer-one.md covers the same shape of defect on TestFailover/StartMigration/reshard/serverless paths but does not carry this check or this operation.
  Traces: elasticache.global-replication-group-secondary-lifecycle.

Cause 5 of 5: a CloudFormation stack carrying AWS::ElastiCache::CacheCluster rolls back instead of reaching CREATE_COMPLETE.
  AWS: recorded behavior — a stack whose resources are an AWS::EC2::SecurityGroup, an AWS::ElastiCache::SubnetGroup (SubnetIds only, name generated by CloudFormation) and an AWS::ElastiCache::CacheCluster (Engine redis, cache.t3.micro, NumCacheNodes 1, VpcSecurityGroupIds=[GetAtt CacheSG.GroupId], CacheSubnetGroupName={Ref SubnetGroup}) reaches CREATE_COMPLETE, and Fn::GetAtt Cluster.RedisEndpoint.Address/.Port resolve to the cluster's reachable endpoint.
  Emulator: the stack reaches terminal ROLLBACK_COMPLETE (the StackCreateComplete waiter matched ROLLBACK_COMPLETE), so no Outputs and no cluster exist and the deploy can never be driven. Hypothesis: the CacheCluster resource provider's create fails — most likely on CacheSubnetGroupName={Ref SubnetGroup} resolving to a subnet group the elasticache store never materialized, or on the RedisEndpoint.* GetAtt — but the failing resource's ResourceStatusReason is not in the replay output, so the provider's create path must be traced.
  Why: every CloudFormation-driven cache deployment fails outright; a client gets a rolled-back stack where AWS gives it a working cluster and endpoint outputs.
  Fix: the AWS::ElastiCache::CacheCluster resource provider in the cloudformation crate (its create must call the elasticache CreateCacheCluster path, resolve Ref to the stack's SubnetGroup, and expose the RedisEndpoint attributes). This is the successor state of Cause 7 of the resolved issue 20261108T152921Z-elasticache-migration-reshard-global-secondary-serverless-and-pending.md, which reported the same provider reaching CREATE_COMPLETE without materializing the cluster; related open issue 20261104T091523Z-elasticache-via-cloudformation-endpoint-outputs-are-returned-with.md owns the ReplicationGroup/ServerlessCache providers, not this one.
  Traces: elasticache.deploy-cachecluster-cfn-behavioral.
