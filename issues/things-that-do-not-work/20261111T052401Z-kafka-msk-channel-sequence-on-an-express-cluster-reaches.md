# MSK channel sequence on an Express cluster reaches no verdict: channel-update-unicode-fields-round-trip times out (60 s) because the channel never settles ACTIVE and the UpdateChannel mutation never becomes observable, so unicode name/tag/prefix round-tripping is unverifiable

> _Note: this issue was identified against the code base at commit `6e999892356890ba3b5e9cb330af8509250d0db3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateChannel

## Description
One kafka behavioral check survives every ALREADY-FILED / OWNED filter in this replay and is the sole net-new cause here.

Cause 1 of 1: the CreateClusterV2(Express) -> CreateTopic -> CreateChannel -> wait ACTIVE -> DescribeChannel -> UpdateChannel -> wait cluster operation -> wait ACTIVE -> DescribeChannel sequence never reaches a terminal, observable state, so the check runs to its wall-clock ceiling and reports only 'Error: Check timed out after 60.0s' — no HTTP status, no error code, no traceback frame, nothing asserted. The behavior under test is a representation one: a channel's UNICODE channel name, UNICODE tag value and UNICODE S3 output prefix must survive an unrelated UpdateChannel byte-for-byte, and the updated DataFreshnessInSeconds must become visible.

AWS: Smithy (com.amazonaws.kafka#Kafka). CreateChannel POST /v1/clusters/{ClusterArn}/channels, 200, idempotent; required input ChannelName, ClusterArn, TopicConfigurationList, optional Tags (map of string->string) and S3DestinationConfiguration; output requires channelArn and may carry clusterOperationArn — it echoes no channel state, so the channel's progress is observable ONLY through DescribeChannel/ListChannels. DescribeChannel GET /v1/clusters/{ClusterArn}/channels/{ChannelArn}, 200, REQUIRES channelArn, channelName, status, destinationType, creationTime, topicConfigurationList and may carry s3DestinationConfiguration, tags, stateInfo, clusterOperationArn; Status is the ChannelStatus enum CREATING|ACTIVE|UPDATING|DELETING|FAILED|SUSPENDING|SUSPENDED, so a freshly created channel settles CREATING -> ACTIVE. S3DestinationConfiguration.DataFreshnessInSeconds is documented 'Allowed range: 300 to 900. Default: 600.' UpdateChannel PUT /v1/clusters/{ClusterArn}/channels/{ChannelArn}, 200, idempotent; S3DestinationUpdate carries REQUIRED DataFreshnessInSeconds (same 300..900 range) and the modeled output is only {channelArn (required), clusterOperationArn} — again no destination field echoed, so AWS's contract is that the new value becomes visible via an independent DescribeChannel once the channel returns from UPDATING to ACTIVE, and the returned cluster operation settles to a completed OperationState observable through DescribeClusterOperationV2. Nothing in the model or the recording permits an update to alter the channel's name, its tags or its storage OutputPrefix: the stored strings must come back identical, including non-ASCII code points (the check uses a tag value of Japanese + accented Latin + Chinese text and an accented-Latin S3 OutputPrefix), and tags must be returned as the same map that was submitted. The modeled refusals for all three ops are BadRequestException 400, ForbiddenException 403, NotFoundException 404, UnauthorizedException 401, TooManyRequestsException 429, InternalServerErrorException 500, ServiceUnavailableException 503 — the emulator produced none of them here.

Emulator: the sequence never yields any response the check can assert on. It creates an Express provisioned cluster (InstanceType 'express.m7g.large', 3 AZ-distinct client subnets, NumberOfBrokerNodes 3, probing ListKafkaVersions candidates through CreateClusterV2), polls DescribeClusterV2 at 20 s for State ACTIVE; creates a topic (PartitionCount 1, ReplicationFactor 2) and polls DescribeTopic at 10 s for Status ACTIVE; creates the channel with Tags={'sim2real-unicode': '<Japanese>/<accented Latin>/<Chinese>'} and Storage.OutputPrefix 'logger/donnees-zhongwen/' and DataFreshnessInSeconds 300, polls DescribeChannel at 15 s for Status ACTIVE, then calls UpdateChannel with S3DestinationUpdate.DataFreshnessInSeconds=600, polls DescribeClusterOperationV2 at 15 s for OperationState in {UPDATE_COMPLETE, COMPLETED} and DescribeChannel again for ACTIVE. The replay detail is the bare frameless 'Error: Check timed out after 60.0s'. Hypothesis (neither the model nor the replay output names the broken link): one of (a) the Express cluster's CREATING -> ACTIVE, (b) the topic's CREATING -> ACTIVE, (c) the channel's CREATING -> ACTIVE, (d) the UpdateChannel cluster operation reaching a completed OperationState, or (e) the channel's UPDATING -> ACTIVE with the new DataFreshnessInSeconds applied, never reaches its terminal value, so every poll burns its whole deadline instead of paying one interval. A 501 or any modeled refusal would at least be a response the check could report; it gets none, so settling these states is a requirement beyond any unimplemented-stub issue.

Why: a client that creates an MSK data-delivery channel and waits for it to become usable, or that changes its S3 buffering and waits for the change to take effect, hangs until its own timeout. Because CreateChannel and UpdateChannel echo no channel state, DescribeChannel/ListChannels are the only confirmation path, so with neither converging a caller cannot distinguish 'applied' from 'silently dropped'. The representation guarantee is lost with it: nothing proves the emulator stores and returns non-ASCII channel names, tag values and S3 prefixes unchanged across an unrelated update, which is exactly where a lossy encode/normalise would corrupt a client's object layout and tag-based inventory.

Fix: the channel state machine in the kafka service's state layer plus the CreateChannel / DescribeChannel / UpdateChannel handlers and the cluster-operation settling they depend on (and the Express-cluster and topic settling in front of them): CreateChannel's channel must settle CREATING -> ACTIVE, UpdateChannel must write S3DestinationUpdate.DataFreshnessInSeconds into the stored channel's S3DestinationConfiguration, settle its cluster operation to a completed OperationState and return the channel UPDATING -> ACTIVE, and DescribeChannel must project ChannelName, Tags and S3DestinationConfiguration.Storage.OutputPrefix as the exact strings submitted while reporting the new DataFreshnessInSeconds — all within one or two probes at an AWS-sized cadence.
