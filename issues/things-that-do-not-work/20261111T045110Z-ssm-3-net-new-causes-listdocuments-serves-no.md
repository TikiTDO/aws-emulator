# ssm: 3 net-new causes — ListDocuments serves no Amazon-owned document catalog, its unknown-filter refusal is misclassified, and UpdateOpsItem's not-found message is emulator-authored

> _Note: this issue was identified against the code base at commit `950d97075a2dc28c97155d1939158688cbb186aa`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListDocuments

## Description
Three distinct net-new causes, all in service `ssm`, all on the document-catalog / refusal-shaping path. Replay reported stub_path empty and owned_by empty for all three clusters, so none is covered by an existing issue.

Cause 1 of 3: ListDocuments does not serve the AWS-published (Owner `Amazon`) document catalog (fixture ssm-catalog-list-documents, step task#1).
AWS: Smithy: ListDocuments -> ListDocumentsResult.DocumentIdentifiers (list of DocumentIdentifier with members Name, Owner, CreatedDate, DocumentType, DocumentFormat, DocumentVersion, SchemaVersion, PlatformTypes, TargetType, Tags); the operation is @paginated (MaxResults @range 1..50, NextToken). The set of Amazon-owned documents is not in the model, so for the catalog itself this is recorded behavior only: an unfiltered ListDocuments in a fresh account enumerates several hundred AWS-published documents — the AWS-* family (AWS-RunShellScript, AWS-RunPowerShellScript, AWS-ApplyPatchBaseline, AWS-ASGEnterStandby, AWS-ConfigureAWSPackage, ...), the AWSConfigRemediation-* family, the AWSConformancePacks-* family, AWSCodeDeployAgent, AWSApp2Container-* and so on — each with Owner 'Amazon', its own DocumentType (Command/Automation/Policy/Package), DocumentFormat, SchemaVersion, PlatformTypes, an empty Tags list and, where applicable, Categories and TargetType (for example TargetType '/AWS::EC2::Instance').
Emulator: almost every Amazon-owned document is absent from DocumentIdentifiers (reported as `missing ... got None` for AWS-ASGEnterStandby, AWS-ASGExitStandby, AWS-ApplyAnsiblePlaybooks, AWS-ApplyPatchBaseline, the whole AWSConfigRemediation-* and AWSConformancePacks-* families, and hundreds more). The handful it does seed are mis-projected: for AWS-ConfigureS3BucketVersioning, AWS-DisableS3BucketPublicReadWrite, AWS-EnableS3BucketEncryption and AWS-PublishSNSNotification the Categories, CreatedDate, DocumentFormat, PlatformTypes[0..2], Tags and TargetType members all diverge, and for AWS-RunShellScript / AWS-RunPowerShellScript / AWS-UpdateSSMAgent the Categories, CreatedDate, SchemaVersion, PlatformTypes and Tags members diverge.
Why: the public document catalog is the entry point for Run Command, Automation, patching and Config remediation. A client that discovers a document by listing (or filters the listing by Owner=Amazon / DocumentType / TargetType, as consoles and CDK/CFN tooling do) finds nothing to run, and the few documents that are listed advertise the wrong platform support, schema version and target type, so a caller selects a document that cannot be used as advertised.
Fix: the seeded public-document catalog behind the SSM document store, plus the DocumentIdentifier projection in the ListDocuments handler (every seeded Amazon-owned document must carry Owner, CreatedDate, DocumentType, DocumentFormat, SchemaVersion, PlatformTypes, Tags (empty list, never omitted), Categories and TargetType).
Traces: ssm-catalog-list-documents#task#1.

Cause 2 of 3: an unknown ListDocuments filter key is refused with the wrong error class and with no message at all (fixture ssm-parameter-labels-and-policy-validation, step task#8).
AWS: Smithy: ListDocuments binds errors InternalServerError, InvalidFilterKey and InvalidNextToken; DocumentKeyValuesFilter.Key is @length 1..128 and its documentation enumerates the Amazon-provided keys (DocumentType, Owner, PlatformTypes, Name, SearchText, TargetType, ...). Recorded behavior for a key outside that set: status 400 with __type 'ValidationException' and message '<Key> is not a known filter key.' — fixed text ' is not a known filter key.', with the leading value taken verbatim from the request's filter Key (the recording used the probe key 'BogusFilterKey').
Emulator: status 400, but __type is 'InvalidFilterKey' and the body carries no message member at all (expected message missing, got None). Note that the modeled InvalidFilterKey shape has no Message member, so picking that class structurally guarantees a message-less refusal.
Why: the refusal cannot be identified or explained — SDK/CLI callers match on the error code ValidationException and surface the message to say which filter key was wrong; they instead see a bare InvalidFilterKey with an empty message, so the mistyped key is never reported back to the caller.
Fix: the ListDocuments input validation / error serializer — classify an unrecognised filter key as ValidationException and render the message from the submitted Key.
Traces: ssm-parameter-labels-and-policy-validation#task#8.

Cause 3 of 3: UpdateOpsItem's OpsItemNotFoundException message is the model's documentation sentence rather than AWS's refusal text (fixture ssm-ops-item-not-found-errors, step task#2).
AWS: Smithy: UpdateOpsItem binds OpsItemNotFoundException (client error, HTTP 400, member Message); OpsItemId is required with pattern ^(oi)-[0-9a-f]{12}$. Recorded response for a well-formed but nonexistent OpsItemId: status 400, Message of the form 'OpsItem not found. (Service: AmazonSSM; Status Code: 400; Error Code: OpsItemNotFoundException; Request ID: <request id>; Proxy: null)'. Fixed text: 'OpsItem not found.' followed by the parenthesised 'Service: AmazonSSM; Status Code: 400; Error Code: OpsItemNotFoundException; ...; Proxy: null' suffix; the only variable part is the Request ID, which is per-request and is not itself a requirement.
Emulator: status 400 is right, but Message is "The specified OpsItem ID doesn't exist. Verify the ID and try again." — the Smithy documentation string of the OpsItemNotFoundException shape, not the message AWS sends.
Why: callers and test suites that match the refusal text, or that parse the trailing Error Code / Status Code fields the AWS SDKs emit in this envelope, do not recognise the refusal and treat a missing OpsItem as an unknown failure.
Fix: the UpdateOpsItem handler's error construction / the OpsItemNotFoundException message in the SSM error serializer. The same wording defect on the GetOpsItem path is already filed as 20261104T073124Z-ssm-opscenter-mutations-are-never-applied-to-stored (Cause 4 of 7, fixture ssm-ops-item-not-found-errors#task#1); this cluster is the UpdateOpsItem one (step task#2), which that issue does not carry and replay reports as unowned.
Traces: ssm-ops-item-not-found-errors#task#2.

Related open issues that do NOT cover the above: 20261103T173026Z-ssm-document-payloads-and-document-store-error-paths (CreateDocument response payloads — it owns the CreateDocument cluster in this same replay), 20261103T215115Z-ssm-validationexception-constraint-text-documentalreadyexists-wording (constraint text and the public /aws/service parameter hierarchy), 20261104T073124Z-ssm-run-command-validation-diverges-aws-managed-documents (SendCommand's rejection of AWS-managed documents, not the ListDocuments catalog projection).
