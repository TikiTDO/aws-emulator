=== Cause 1 of 1: a permanent (AccessDenied-family) target failure produces no dead-letter event carrying ERROR_CODE and RETRY_ATTEMPTS, and the reported attempt count does not stay pinned at 0 across an UpdateSchedule that raises MaximumRetryAttempts ===
Failing check: scheduler.scheduler-updated-retry-attempt-count-governs-the-next-occurrence

AWS: Smithy (com.amazonaws.scheduler) — Target.DeadLetterConfig -> DeadLetterConfig, member Arn @pattern ^arn:aws(-[a-z]+)?:sqs:[a-z0-9\-]+:\d{12}:[a-zA-Z0-9\-_]+$ @length 1..1600, documented "An object that contains information about an Amazon SQS queue that EventBridge Scheduler uses as a dead-letter queue for your schedule. If specified, EventBridge Scheduler delivers failed events that could not be successfully delivered to a target to the queue." Target.RetryPolicy -> RetryPolicy with MaximumRetryAttempts @range 0..185 ("The maximum number of retry attempts to make before the request fails. Retry attempts with exponential backoff continue until either the maximum number of attempts is made or until the duration of the MaximumEventAgeInSeconds is reached.") and MaximumEventAgeInSeconds @range 60..86400. Target.RoleArn is required (@pattern ^arn:aws(-[a-z]+)?:iam::\d{12}:role\/[\w+=,.@\/-]+$): every occurrence is delivered as that role. Recorded behavior (the model does not describe the dead-letter envelope): the dead-letter message Scheduler sends to Target.DeadLetterConfig.Arn carries SQS message attributes describing the failed occurrence, among them ERROR_CODE (an AccessDenied-family code when the target call was refused for the execution role) and RETRY_ATTEMPTS (the number of retry attempts actually made before the event was dead-lettered). An authorization refusal is a PERMANENT failure, so it is not retried at all: RETRY_ATTEMPTS is 0 regardless of the configured MaximumRetryAttempts. This is the behavior under test: with MaximumRetryAttempts=0 the first occurrence dead-letters with RETRY_ATTEMPTS=0, and after UpdateSchedule replaces the target with MaximumRetryAttempts=3 (GetSchedule then reporting 3 — the CONFIGURATION does change) the next occurrence still dead-letters with RETRY_ATTEMPTS=0, because the configured cap is an upper bound on retries and not a count to echo. MaximumEventAgeInSeconds is held at the model maximum (86400) in both generations, so the age bound can never be the binding bound and the cap is the only variable.

Emulator: no dead-letter event is produced at all, so neither attribute exists to be read. The check polls the configured DLQ for 240 s for the first occurrence (MaximumRetryAttempts=0) and receives nothing: "AssertionError: no dead-letter event for the first occurrence of <schedule-name> with MaximumRetryAttempts=0 arrived within 240s. Events from other generations seen and discarded: []". The run therefore never reaches the second generation, so the emulator is also unobserved on the invariant that the reported attempt count must be UNCHANGED (0 -> 0) while the configured cap changes (0 -> 3); an implementation that echoes the currently-configured cap into RETRY_ATTEMPTS would report 0 then 3 and diverge there too. Note the schedule names, generation markers and queue names quoted here are one run's values, not requirements.

Why: the dead-letter envelope's attributes are the only machine-readable account a client ever gets of WHY a scheduled occurrence failed and HOW HARD Scheduler tried. ERROR_CODE is what distinguishes a misconfigured execution role (permanent, fix the policy) from a throttled or erroring target (transient, retry-worthy), and RETRY_ATTEMPTS is what a client's dashboards and retry-exhaustion alarms count. With no dead-letter event emitted, a schedule whose every occurrence is refused by its own Target.RoleArn is indistinguishable from a healthy one (CreateSchedule returned 200 and the control plane keeps reporting State=ENABLED), so operational runbooks keyed on these attributes never fire. Worse, a client tuning MaximumRetryAttempts against the emulator can never learn that raising the cap does not change the outcome for a permanent failure, and will mis-size retry budgets and alarm thresholds for AWS.

Fix: the occurrence/dispatch component of the scheduler crate — the delivery-failure path that builds the dead-letter message for Target.DeadLetterConfig.Arn. It must classify a target refusal under Target.RoleArn as a PERMANENT failure (no retries, independent of Target.RetryPolicy.MaximumRetryAttempts), then SendMessage the failed event to the dead-letter queue exactly once with the failed occurrence's Target.Input as the body and message attributes including ERROR_CODE set to the AccessDenied-family code of the refusal and RETRY_ATTEMPTS set to the attempts ACTUALLY made (0 for a permanent failure), not to the configured cap. UpdateSchedule must keep storing the new cap (GetSchedule reporting it) without that stored value feeding the reported attempt count.

Traces: scheduler.scheduler-updated-retry-attempt-count-governs-the-next-occurrence (the only failing scheduler check in this replay that no open issue owns).
