# ec2 Describe read paths return stale and incomplete static attribute data

> _Note: this issue was identified against the code base at commit `ab3e9411edd79c78c4763b290b74822ee89d0fde`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceTypes

## Description
Two net-new causes, both in ec2 read paths that serve static (non-state) attribute data. Both are reported by the wire replay with HTTP 200 on both sides: the status and the envelope are right, the per-member values are not. Cause 1 is by far the larger: it is the single root cause behind 150+ divergence clusters in this replay, every one of them a DescribeInstanceTypes step of an ec2-catalog-describe-instance-types-* fixture. No open issue mentions instance types or the instance-type catalog (checked with the issue listing), so neither cause is owned.

Cause 1 of 2: DescribeInstanceTypes serves an instance-type catalog whose per-type attributes diverge from AWS, and which omits members the service always returns.
AWS: DescribeInstanceTypes returns, per instance type, a fully populated InstanceTypeInfo. Smithy (services/service-com-amazonaws-ec2-amazonec2 model): InstanceTypeInfo carries cpuBurstModel, ebsInfo (EbsInfo.attachmentLimitType, maximumEbsAttachments, ebsOptimizedInfo), networkInfo, processorInfo, vCpuInfo and supportedBootModes; EbsOptimizedInfo members BaselineBandwidthInMbps/BaselineIops/BaselineThroughputInMBps/MaximumBandwidthInMbps/MaximumIops/MaximumThroughputInMBps (xmlName baselineBandwidthInMbps, ...) are the per-type EBS-optimized performance figures; NetworkCardInfo members networkPerformance, baselineBandwidthInGbps, peakBandwidthInGbps, maximumNetworkInterfaces, additionalFlexibleNetworkInterfaces, defaultEnaQueueCountPerInterface, maximumEnaQueueCount, maximumEnaQueueCountPerInterface, interfaceTypeSet are the per-network-card figures. The model does not pin the VALUES for a given instance type -- for the values this is recorded behavior only: the fixtures record what AWS returns for each instance type, and that recording is the requirement. The requirement is per instance type: every member AWS returns must be present, and its value must be the value AWS returns for THAT instance type (the figures are a property of the instance type, not of the account, region or run, so nothing here is a per-run value).
Emulator: for most instance types in the corpus the emulator answers 200 with an InstanceTypeInfo whose figures are wrong and whose newer members are absent. The recorded clusters show, as examples: cpuBurstModel absent where AWS returns 'none'; ebsInfo.ebsOptimizedInfo figures taken from a different type (for c5ad.8xlarge AWS returns baselineBandwidthInMbps 3170 / baselineIops 13300 / baselineThroughputInMBps 396.25 and the emulator returns 6800 / 30000 / 850.0); ebsInfo.maximumEbsAttachments off (25 vs 26 for c5ad.8xlarge, 32 vs 27 for c8in.12xlarge); ebsInfo.attachmentLimitType 'shared' where AWS returns 'dedicated'; capability booleans inverted (dedicatedHostsSupported and hibernationSupported true where AWS returns false for c5ad.8xlarge; efaSupported, phcSupport, secondaryNetworkSupported, enaSrdSupported wrong on c8in/m6idn); instanceStorageInfo.disks.item.count and sizeInGB wrong (2x600 vs 1x800 for c5ad.8xlarge); networkInfo values wrong or absent (networkPerformance '50 Gigabit' where AWS returns '100 Gigabit' for m6idn.16xlarge, networkCards.item.baselineBandwidthInGbps/peakBandwidthInGbps 50.0 vs 100.0, flexibleEnaQueuesSupport 'unsupported' vs 'supported', trafficMirroringSupport / ipv4AddressesPerSecondaryInterface / additionalFlexibleNetworkInterfaces / defaultEnaQueueCountPerInterface / maximumEnaQueueCount / maximumEnaQueueCountPerInterface absent, connectionTrackingConfiguration.defaultTcpEstablishedTimeout 432000 where AWS returns 350, ipv4AddressesPerInterface/ipv6AddressesPerInterface/maximumNetworkInterfaces wrong on c8in); processorInfo.sustainedClockSpeedInGhz wrong; vCpuInfo.validCores truncated, so the list stops short of the type's core count; and for multi-card types (m6idn.32xlarge, m6idn.metal) networkCards is a single collapsed item where AWS returns one item per card.
Why: a client uses DescribeInstanceTypes to choose an instance type and to size what it then builds on it. Wrong EBS-optimized and network figures make it pick a type that cannot carry its workload, or compute wrong IOPS/bandwidth budgets; wrong dedicatedHostsSupported / hibernationSupported / efaSupported / attachmentLimitType make it offer or refuse a capability the type does not or does have; a truncated validCores list makes a valid CpuOptions core count look invalid; absent members (cpuBurstModel, the ENA queue counts, trafficMirroringSupport) are read as 'not supported' or crash a consumer that treats a modeled member as always present; and a collapsed networkCards list hides the second card of a multi-card type.
Fix: the ec2 instance-type catalog data the DescribeInstanceTypes handler serves (the static per-instance-type table behind services/service-com-amazonaws-ec2-amazonec2/src/ops/describe_instance_types.rs and the catalog data module it reads), not the serializer: the response shape and the 200 status are already right, the per-type rows are wrong and lack the newer members. The catalog must carry one row per instance type with every member AWS returns, including one networkCards entry per network card.
Traces: ec2-catalog-describe-instance-types-a1-c9g#task#7 (c5ad family), ec2-catalog-describe-instance-types-a1-c9g#task#32 (c8in family). The same cause produces 150+ further clusters across the ec2-catalog-describe-instance-types-* fixtures (m6i-r4 and the other generation ranges); re-replaying the two keys above exercises both the 'wrong value' and the 'missing member' shapes of it, and the remaining catalog fixtures should be re-replayed once the table is rebuilt.

Cause 2 of 2: DescribeImages omits blockDeviceMapping ebs.encrypted and reports freeTierEligible for every self-owned image as false.
AWS: DescribeImages returns, per image, blockDeviceMapping items whose ebs member is an EbsBlockDevice. Smithy: EbsBlockDevice.Encrypted (xmlName 'encrypted', boolean) 'Indicates whether the encryption state of an EBS volume is changed while being restored from a backing snapshot'; AWS returns it on the DescribeImages block device mapping, and for an image registered from an unencrypted snapshot it is false -- not absent. freeTierEligible is returned per image and reflects whether the image is free-tier eligible; the recording shows AWS returning true for these self-registered images (recorded behavior only for the value).
Emulator: answers 200 but leaves blockDeviceMapping.item.ebs.encrypted out of every mapping entirely, and returns freeTierEligible 'false' for every image where the recording has 'true'. In the replayed step this happens for all eight images the fixture registers, so it is the stored image's serialization, not one image's data.
Why: a client auditing image encryption cannot distinguish 'unencrypted' from 'not reported' and so either treats an unencrypted image as encrypted or fails on a missing member; a client filtering on free-tier eligibility sees no eligible image at all.
Fix: the DescribeImages response projection in the ec2 service -- the image/block-device serializer must emit the modeled encrypted member (defaulting to false for an unencrypted mapping) and freeTierEligible must be derived rather than hard-coded false.
Traces: ec2-describe-images-self-owned-pagination-and-params#task#15.
