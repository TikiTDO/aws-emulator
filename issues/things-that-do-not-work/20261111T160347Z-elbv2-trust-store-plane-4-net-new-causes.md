# elbv2 trust-store plane: 4 net-new causes — DescribeTrustStoreAssociations reports the listener ARN instead of the load balancer ARN, the TrustStoreInUse refusal is reworded, GetResourcePolicy refuses an existing trust store, and a CFN TrustStore Ref yields the name

> _Note: this issue was identified against the code base at commit `0e97705e9904239bd55bed92c4be71546a783c93`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeTrustStoreAssociations, DeleteTrustStore, GetResourcePolicy, CreateStack (AWS::ElasticLoadBalancingV2::TrustStore)

## Description
Four net-new root causes in the ELBv2 mutual-TLS trust-store plane. Every cause below must be closed before this issue is submitted.

=== Cause 1 of 4: DescribeTrustStoreAssociations reports the ASSOCIATED LISTENER's ARN where AWS reports the LOAD BALANCER's ARN ===
Failing checks: elbv2.trust-store-association-lifecycle, elbv2.trust-store-association-and-shared-deletion-rejected, elbv2.deploy-trust-store-deletion-rejected-while-in-use, elbv2.trust-store-association-created-and-removed, elbv2.trust-store-association-lifecycle-via-mtls-listener, elbv2.delete-trust-store-in-use-rejected, elbv2.delete-trust-store-in-use-by-listener-fails, elbv2.delete-shared-trust-store-association-same-account-fails, elbv2.describe-trust-store-associations-for-shared-listener, elbv2.e2e-mtls-trust-store-listener-flow, elbv2.e2e-trust-store-mtls-association-and-revocation-flow.

AWS: Smithy (com.amazonaws.elasticloadbalancingv2) DescribeTrustStoreAssociations takes required TrustStoreArn plus Marker/PageSize (@range 1..400) and answers DescribeTrustStoreAssociationsOutput{TrustStoreAssociations: list<TrustStoreAssociation>, NextMarker}; TrustStoreAssociation has a single member ResourceArn, documented only as "The Amazon Resource Name (ARN) of the resource." The sole modeled error is TrustStoreNotFoundException (client, awsQueryError code TrustStoreNotFound, httpError 400). The model does not state WHICH resource ARN is reported, so this is recorded behavior only: when an HTTPS listener enables MutualAuthentication Mode=verify against a trust store, AWS reports the association against the LOAD BALANCER that owns that listener — ResourceArn is an arn:<partition>:elasticloadbalancing:<region>:<account>:loadbalancer/app/<lb-name>/<lb-id> value, not the listener's arn:...:listener/app/<lb-name>/<lb-id>/<listener-id>. The checks encode exactly that requirement: they poll DescribeTrustStoreAssociations for the load balancer ARN they created the mTLS listener on.

Emulator: the handler derives the association set from the listeners that carry MutualAuthenticationAttributes$TrustStoreArn and emits the LISTENER ARN as TrustStoreAssociation.ResourceArn. Replay evidence (elbv2.trust-store-association-lifecycle): "load balancer associated with trust store not met within 30s. Last result: [{'ResourceArn': 'arn:aws:elasticloadbalancing:<region>:<account>:listener/app/<lb-name>/<lb-id>/<listener-id>'}]" — a listener ARN where the load balancer ARN is required. The same shape is asserted directly by elbv2.deploy-trust-store-deletion-rejected-while-in-use: "expected association with 'arn:...:loadbalancer/app/<lb-name>/<lb-id>', got {'arn:...:listener/app/<lb-name>/<lb-id>/<listener-id>'}". The remaining checks in this cause never get a verdict at all: their association-wait helpers ("resource <arn> never appeared in trust store associations") never see the load balancer ARN and burn the whole 60 s check budget ("Check timed out after 60.0s"). The ARN values quoted here are per-run generated names/ids filling a template; the requirement is the ARN's RESOURCE TYPE segment — loadbalancer/app/... rather than listener/app/....

Why: a client uses DescribeTrustStoreAssociations to answer "what is still using this trust store" before deleting or re-sharing it, and to join the trust store back to the load balancers it protects. Against the emulator every such join fails: the returned ARN names a listener, so a caller filtering or matching on load-balancer ARNs sees an EMPTY association set for a trust store that is in use (and a caller that passes the returned ARN on to DescribeLoadBalancers gets a not-found). Deletion-safety logic and cross-account sharing flows built on this read are unusable.

Fix: the DescribeTrustStoreAssociations handler and the state it reads — services/service-com-amazonaws-elasticloadbalancingv2-elasticloadbalancing-v10/src/ops/describe_trust_store_associations.rs together with crate::state's trust_store_associations derivation, which must map a listener that enables mutual TLS against the trust store to its OWNING load balancer's ARN before paginating. DeleteSharedTrustStoreAssociation / DeleteTrustStore read the same derivation, so correcting it must keep their in-use decision unchanged.

=== Cause 2 of 4: the DeleteTrustStore TrustStoreInUse refusal message is emulator-authored prose ===
Failing checks: elbv2.delete-trust-store-in-use-fails, elbv2.trust-store-in-use-delete-fails.

AWS: Smithy DeleteTrustStore takes required TrustStoreArn and models TrustStoreInUseException (client, awsQueryError code TrustStoreInUse, httpError 400, documented "The specified trust store is currently in use") and TrustStoreNotFoundException. The recorded refusal for deleting a trust store an mTLS listener still authenticates against is HTTP 400, Error.Code TrustStoreInUse, with the message template: fixed text "Trust store with ARN '" + "' is currently associated", whose single variable part is the TrustStoreArn echoed verbatim from the request.

Emulator: status 400 and the error code are right, but the message is rewritten to "Trust store '<TrustStoreArn>' is associated with one or more resources" — it drops "with ARN" after "Trust store" and substitutes "is associated with one or more resources" for AWS's "is currently associated". Replay evidence: expected message "Trust store with ARN 'arn:aws:elasticloadbalancing:<region>:<account>:truststore/<name>/<id>' is currently associated", got "Trust store 'arn:aws:elasticloadbalancing:<region>:<account>:truststore/<name>/<id>' is associated with one or more resources". The ARN is a per-run value that fills the template; the divergence is purely the fixed text.

Why: the error message is part of the contract. SDK error-mapping layers, operator runbooks and test suites that match AWS's sentence to distinguish the in-use refusal from TrustStoreNotFound stop matching, so a correctly-classified refusal reads as an unknown failure.

Fix: the DeleteTrustStore refusal path — crate::state::trust_store_in_use_message, as constructed at services/service-com-amazonaws-elasticloadbalancingv2-elasticloadbalancing-v10/src/ops/delete_trust_store.rs (the TrustStoreInUseException arm). The template must be AWS's fixed text with the request's TrustStoreArn interpolated.

=== Cause 3 of 4: GetResourcePolicy answers 400 ResourceNotFound for a trust store that exists ===
Failing checks: elbv2.get-resource-policy-no-policy-rejected, elbv2.get-resource-policy-nonexistent-fails, elbv2.get-resource-policy-returns-attached-json-policy, elbv2.get-resource-policy-returns-matching-policy-document, elbv2.resource-policy-not-found.

AWS: Smithy GetResourcePolicy takes required ResourceArn and answers GetResourcePolicyOutput{Policy (@length min 1)}; the ONLY modeled error is ResourceNotFoundException (client, awsQueryError code ResourceNotFound, httpError 400). That single refusal class is therefore reserved for an ARN that names no stored resource: an ARN naming a trust store the account created and that DescribeTrustStores reports ACTIVE is a 200, and the absence of an attached policy is represented in the body (recorded behavior: Policy is the empty JSON document '{}'), never as an error.

Emulator: every GetResourcePolicy call against a freshly created, ACTIVE trust store is refused with HTTP 400, code ResourceNotFound and the message "Trust store ARN '<ResourceArn>' not found" — including the POSITIVE control in elbv2.get-resource-policy-no-policy-rejected, which calls GetResourcePolicy on the trust store it has just waited to ACTIVE and only afterwards deletes it to exercise the genuine not-found. Hypothesis: the read resolves ResourceArn against a resource-policy store that only holds an entry once a policy has been PUT, so "no policy attached" is conflated with "resource not found".

Why: read-then-modify is the only safe way to edit a resource policy, so a client reads the policy before attaching, merging or replacing it. Against the emulator that read fails for exactly the case where the client is about to attach the first policy; the client concludes the trust store does not exist and aborts, making cross-account trust-store sharing unreachable.

Note: this is the same root cause as the already-open WIRE issue 20261111T142624Z-elasticloadbalancing-elbv2-trust-store-plane-diverges-getresourcepolicy-refuses-an.md (Cause 1 there). That issue carries only wire replay keys, not these five behavioral check ids, so the ids are recorded here; closing one closes both, and the fixer should re-replay the checks listed above.

Fix: the GetResourcePolicy handler and the trust-store/resource-policy state it reads — services/service-com-amazonaws-elasticloadbalancingv2-elasticloadbalancing-v10/src/ops/get_resource_policy.rs. Resolving ResourceArn must succeed whenever the ARN names a stored ELBv2 resource, an absent policy must serialize as the empty policy document in the 200 body, and ResourceNotFoundException must be reserved for an ARN that names nothing.

=== Cause 4 of 4: a CloudFormation AWS::ElasticLoadBalancingV2::TrustStore Ref resolves to the trust store NAME instead of its ARN ===
Failing check: elbv2.deploy-trust-store-cfn-association-enforced.

AWS: for AWS::ElasticLoadBalancingV2::TrustStore, Ref returns the trust store's ARN (the same arn:<partition>:elasticloadbalancing:<region>:<account>:truststore/<name>/<id> value CreateTrustStore returns as TrustStores[0].TrustStoreArn), which is why a template can write MutualAuthentication: {Mode: verify, TrustStoreArn: {"Ref": "TS"}} on a Listener and why that value can be handed straight to DescribeTrustStores / DescribeTrustStoreAssociations. Smithy: TrustStoreArn is the required input of DescribeTrustStoreAssociations and DescribeTrustStores, whose only modeled refusal is TrustStoreNotFoundException (TrustStoreNotFound, 400) — reserved for an ARN naming no trust store.

Emulator: the stack's TrustStore resource resolves to the plain trust-store NAME, so passing it to the ELBv2 control plane is refused: "TrustStoreNotFoundException: An error occurred (TrustStoreNotFound) when calling the DescribeTrustStoreAssociations operation: Trust store ARN 'sim2real-ts-<suffix>' not found" — note the value in the quotes is a bare name, not an ARN. The sibling check elbv2.deploy-trust-store-cfn-associates-with-listener shows the identical symptom on DescribeTrustStores and is OWNED by 20261023T205437Z-cloudformation-reports-create-complete-for-resources-it-never.md; that issue is about resources CloudFormation never creates and does not carry this physical-id/Ref defect or this check id.

Why: every template that wires a trust store to an mTLS listener, and every client that reads a stack's TrustStore Ref or Outputs to drive the ELBv2 API, gets a value the service rejects. An mTLS topology cannot be deployed by CloudFormation at all, and the failure surfaces as "trust store does not exist" for a resource the stack reports as created.

Fix: the CloudFormation resource handler for AWS::ElasticLoadBalancingV2::TrustStore — its physical resource id (and therefore its Ref/GetAtt projection) must be the ARN returned by CreateTrustStore, not the Name property.

Traces: the failing behavioral check ids listed under each cause above; all are in the elbv2 group of suite simparity-behavioral-aws-v1.
