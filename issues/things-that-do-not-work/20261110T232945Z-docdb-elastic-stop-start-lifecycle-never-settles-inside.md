# DocDB Elastic stop/start lifecycle never settles inside a client's poll: every transition withholds its settled status past the first read, so the stop/start flow and the STOPPED/ACTIVE state refusals can never be observed to complete

> _Note: this issue was identified against the code base at commit `b1b0bc7f12f2b32e092da76cddcf605dbbe6d9ca`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StopCluster

## Description
Cause 1 of 1: every cluster status transition (CREATING, STOPPING, STARTING, UPDATING) is pinned to a fixed wall-clock window measured from the mutating call, so the FIRST GetCluster a polling client issues after that call is always still answered the transient status. Each transition therefore costs a polling client one whole poll interval, and any flow that chains three or more transitions can never be observed to finish inside a check's wall-clock budget. Failing checks: docdb-elastic.cluster-stop-start-lifecycle, docdb-elastic.start-cluster-when-active-rejected, docdb-elastic.delete-cluster-while-stopped-rejected, docdb-elastic.update-cluster-while-stopped-rejected.

AWS: Smithy: StopCluster POST /cluster/{clusterArn}/stop, StartCluster POST /cluster/{clusterArn}/start, both @idempotent, both returning the required Cluster with its `status`; StopCluster is documented as "Stops the running elastic cluster that is specified by clusterArn. The elastic cluster must be in the available state." and StartCluster as "Restarts the stopped elastic cluster that is specified by clusterARN." Cluster$status targets the Status enum, whose values include CREATING, ACTIVE, STOPPING, STOPPED, STARTING, UPDATING. The model states nothing about timing. Recorded behavior only for the pacing: the mutating call's OWN response carries the transient status (STOPPING for a stop, STARTING for a start, CREATING for a create), and a subsequent GetCluster/ListClusters converges on the settled status (STOPPED, then ACTIVE) with the shard topology, shardCapacity and shardCount unchanged. The state refusals these checks exercise are the recorded ones and do NOT diverge here: StartCluster on an ACTIVE cluster is refused 400 ValidationException "Can't start the cluster as it's currently in state unavailable for starting." (fixed sentence, no interpolated values), DeleteCluster on a STOPPED cluster is refused 400 ValidationException "Can't delete the cluster because it is in <STATUS> state." where only <STATUS> comes from the cluster's own stored status, and UpdateCluster on a STOPPED cluster is refused 409 ConflictException. Nothing in the model or the recordings makes the transient status survive a client's later reads.

Emulator: every mutating path arms a 500 ms due instant and the status only completes when a later reader finds that instant already past, so a read issued milliseconds after the call is inside the window and is answered the transient status. The four checks poll at 20 s: cluster-stop-start-lifecycle chains CreateCluster -> wait ACTIVE, StopCluster -> wait STOPPED, StartCluster -> wait ACTIVE (3 x 20 s) and is cut off at exactly "Check timed out after 60.0s"; start-cluster-when-active-rejected chains the same three waits around its (correct) refusal; delete-cluster-while-stopped-rejected and update-cluster-while-stopped-rejected chain four or more waits (create -> ACTIVE, stop -> STOPPED, start -> ACTIVE, then delete-to-absent / update-to-applied) and are cut off identically. None of the four reaches an assertion about the refusal's code or message — they all die on the clock — so the pacing is the only divergence they expose; the refusal wording they pass through is already correct.

Why: a client doing the documented stop/start lifecycle — stop a cluster and wait for STOPPED, start it and wait for ACTIVE — stalls one full poll interval per transition and, for flows chaining three or more transitions, never sees the settled resource at all. That makes StopCluster/StartCluster's end state (status STOPPED then ACTIVE, consistent between GetCluster and ListClusters, with shardCapacity/shardCount/shards unchanged) unverifiable, and makes the state-gated refusals' positive controls (restart then delete; restart then re-apply the update) unreachable, so any workflow gated on a settled status stalls proportionally to its poll interval.

Fix: the settle pacing in this service's state and the mint/transition paths that arm it — a cluster should already be settled by the time of the first subsequent read, with the transient status carried by the mutating call's own response (which the handlers already return), rather than withheld for a wall-clock window that outlives that read. The transient-status refusals that depend on an in-flight window (ensure_available for StopCluster, ensure_startable for StartCluster, the DeleteCluster/UpdateCluster state gates) must keep working off the record's own status, so the window cannot simply be deleted where those refusals read it. Open issue 20261110T154150Z-docdb-elastic-lifecycle-transitions-settle-on-a-wall.md describes the same pacing for the snapshot-copy and restore happy paths, but it carries only the copy-cluster-snapshot-success and restore-cluster-from-snapshot-success replay keys; the four checks here are the cluster stop/start and state-refusal flows and are not covered by it.

Traces: docdb-elastic.cluster-stop-start-lifecycle, docdb-elastic.start-cluster-when-active-rejected, docdb-elastic.delete-cluster-while-stopped-rejected, docdb-elastic.update-cluster-while-stopped-rejected — all four [mismatch] "Check timed out after 60.0s". Code: services/service-com-amazonaws-docdbelastic-chimeradblionfishservicelambda/src/state.rs line 26 (`const SETTLE_AFTER: Duration = Duration::from_millis(500)`, commented "The span is deliberately non-zero, so a caller acting straight after CreateCluster still observes CREATING"), lines 222-250 (ClusterRecord::begin_transition / settle_due, which only completes the move once `Instant::now() >= due`); src/ops/stop_cluster.rs lines 162-176; src/ops/start_cluster.rs lines 160-173.

## Evidence
Expected (AWS / recorded behavior):
- StopCluster on an ACTIVE cluster returns 200 with status STOPPING; GetCluster and ListClusters then both converge on STOPPED for that clusterArn.
- StartCluster on that STOPPED cluster returns 200 with status STARTING; GetCluster and ListClusters then both converge on ACTIVE, with shardCapacity and shardCount unchanged across the stop/start.
- StartCluster on an ACTIVE cluster: 400 ValidationException, message exactly "Can't start the cluster as it's currently in state unavailable for starting." (whole sentence fixed), cluster still ACTIVE; after a stop, the same StartCluster succeeds and reaches ACTIVE.
- DeleteCluster on a STOPPED cluster: 400 ValidationException, message "Can't delete the cluster because it is in STOPPED state." — fixed text "Can't delete the cluster because it is in " + the cluster's own stored status + " state."; cluster stays STOPPED; after StartCluster to ACTIVE, the same DeleteCluster succeeds and GetCluster eventually answers ResourceNotFoundException.
- UpdateCluster on a STOPPED cluster: 409 ConflictException, shardInstanceCount unchanged; after StartCluster to ACTIVE, the identical UpdateCluster succeeds and shardInstanceCount converges on the requested value.

Actual (emulator):
- docdb-elastic.cluster-stop-start-lifecycle — [mismatch] "Error: Check timed out after 60.0s". Flow is CreateCluster(authType=PLAIN_TEXT, shardCapacity=2, shardCount=1) -> poll GetCluster every 20 s to ACTIVE, StopCluster -> poll to STOPPED, StartCluster -> poll to ACTIVE. The first poll of each wait is answered the transient status (CREATING, STOPPING, STARTING) because the record's due instant is 500 ms in the future when that poll arrives, so each wait needs two polls and the third wait is still pending at the 60 s cut-off.
- docdb-elastic.start-cluster-when-active-rejected — [mismatch] "Error: Check timed out after 60.0s". Same arithmetic: create -> ACTIVE (one wasted poll), refusal asserted and passed, stop -> STOPPED, start -> ACTIVE.
- docdb-elastic.delete-cluster-while-stopped-rejected — [mismatch] "Error: Check timed out after 60.0s". create -> ACTIVE, stop -> STOPPED, refusal, start -> ACTIVE, delete -> wait-for-absent: four or more 20 s polls.
- docdb-elastic.update-cluster-while-stopped-rejected — [mismatch] "Error: Check timed out after 60.0s". create -> ACTIVE, stop -> STOPPED, ConflictException, start -> ACTIVE, update -> wait for shardInstanceCount=2.
- All four checks' individual HTTP calls succeed (200) or produce the correct 400/409 refusal; no wrong status code, error code or message is observed. The resources are simply never reported settled before the budget is gone.

Source evidence: state.rs SETTLE_AFTER = 500 ms; ClusterRecord::settle_due completes the transition only when a reader arrives after the due instant; stop_cluster.rs and start_cluster.rs each call begin_transition(STATUS_STOPPING / STATUS_STARTING) and return the transient status.

## Steps to Reproduce
1. Boot the emulator and point a docdb-elastic client at it.
2. CreateCluster(clusterName=<new>, authType=PLAIN_TEXT, adminUserName=..., adminUserPassword=..., shardCapacity=2, shardCount=1).
3. Immediately GetCluster(clusterArn): status is CREATING, and stays transient for any read issued within 500 ms of the create — so a client polling on any interval >= that window burns a whole interval on this transition.
4. Poll GetCluster every 20 s until ACTIVE (takes two polls). StopCluster(clusterArn); poll every 20 s until STOPPED (two polls). StartCluster(clusterArn); poll every 20 s until ACTIVE (two polls). Observe the flow needs more than 60 s of wall clock, so the stop/start lifecycle check is cut off at 60 s before ACTIVE is ever seen.
5. Refusal flows: with the cluster STOPPED, call DeleteCluster (expect 400 ValidationException "Can't delete the cluster because it is in STOPPED state.") and UpdateCluster(shardInstanceCount=2) (expect 409 ConflictException); with it ACTIVE, call StartCluster (expect 400 ValidationException "Can't start the cluster as it's currently in state unavailable for starting."). Each refusal itself is correct, but the positive control that follows it (restart then delete, restart then re-apply the update) adds two more full poll intervals, so the check never reaches it.
6. Minimal reproduction of the cause: StopCluster, then GetCluster immediately — STOPPING; the settled STOPPED only appears to a read issued more than 500 ms after the call.
