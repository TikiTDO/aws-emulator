# autoscaling__ec2__elbv2: 2 net-new causes — TerminateInstanceInAutoScalingGroup's non-member refusal carries emulator-authored text naming 'Auto Scaling group null', and a stack's security-group ingress rules are absent from DescribeSecurityGroups

> _Note: this issue was identified against the code base at commit `f456950adb04cb9e7696776dd0db02907fd8875a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TerminateInstanceInAutoScalingGroup

## Description
Two independent net-new root causes in the Auto Scaling / EC2 / ELBv2 surface. Each must be closed before submitting.

Cause 1 of 2: TerminateInstanceInAutoScalingGroup now refuses an instance that belongs to no Auto Scaling group with the right error code but the wrong message — it renders a group name it does not have as the literal `null`. Failing check id: autoscaling__ec2__elbv2.asg-terminate-instance-outside-group-rejected.
  AWS: TerminateInstanceInAutoScalingGroup takes InstanceId (XmlStringMaxLen19) and required ShouldDecrementDesiredCapacity and returns an Activity; Smithy models only ScalingActivityInProgressFault and ResourceContentionFault, so the membership failure is the service-common awsQuery `ValidationError` at HTTP 400. For an EC2 instance that is in no Auto Scaling group the recorded message is `Instance Id not found - No managed instance found for instance ID: <instance-id>` — fixed text `Instance Id not found - No managed instance found for instance ID: ` with the instance id taken from the request. Note the request carries NO group name (the operation does not identify a group), so no group name appears in the message. Recorded behavior for the wording. The positive control is unaffected: the same call for a genuine member succeeds, terminates it, and decrements DesiredCapacity.
  Emulator: the code is `ValidationError` (correct) but the message is `Instance i-... is not part of Auto Scaling group null.` — emulator-authored text, and its variable slot for the group name is filled with the literal string `null` because the request has no group to name.
  Why: a client that matches on the refusal text to tell "this instance is not managed by Auto Scaling" from other validation failures matches nothing, and the leaked `null` advertises a group that does not exist, sending operators looking for a group named null. This is also a message regression against the fix direction recorded in open issue 20261104T042502Z-autoscaling-ec2-elbv2-4-net-new-root-causes.md, whose Cause 2 (the operation answering 501 NotImplemented) no longer reproduces but whose stated message template `Instance <id> is not part of Auto Scaling group <group>.` is not what the recording shows for a non-member; that issue does not carry this message divergence.
  Fix: the TerminateInstanceInAutoScalingGroup handler's validation (services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/ops/terminate_instance_in_auto_scaling_group.rs) — when the instance resolves to no group, refuse with ValidationError and the not-found sentence above, and never interpolate an absent group name.

Cause 2 of 2: the ingress permissions a CloudFormation stack declares on an EC2 security group do not exist in the EC2 read after the stack reports CREATE_COMPLETE — DescribeSecurityGroups answers with an empty IpPermissions list. Failing check id: autoscaling__ec2__elbv2.e2e-asghc-asg-instance-health-check-failure-lifecycle.
  AWS: after a stack that declares a security group together with its ingress rules reaches CREATE_COMPLETE, ec2:DescribeSecurityGroups(GroupIds=[<sg>]) returns one IpPermissions entry per declared rule, each with IpProtocol and FromPort/ToPort (IpProtocol='-1' for an all-traffic rule) and, for a group-sourced rule, UserIdGroupPairs naming the source group id. For the stack under replay that is three permissions — tcp 988, tcp 1018-1023 and all traffic — all sourced from the group itself, and no address-based (IpRanges/Ipv6Ranges/PrefixListIds) rule admitting the NLB health-check port. Smithy (ec2): SecurityGroup.ipPermissions -> IpPermissionList{IpProtocol, FromPort, ToPort, IpRanges, Ipv6Ranges, PrefixListIds, UserIdGroupPairs}; the specific rule set is recorded behavior of the deployed template.
  Emulator: the same read reports no permissions at all: the diagnosis derives `'ingress': (), 'sources': ()` where the deployed stack has `'ingress': ('TCP 1018-1023', 'TCP 988', 'all traffic'), 'sources': ('sg-...',)` — every other derived field (group id, target-group name, health-check protocol/port/path, load-balancer ARN and kind, HealthCheckType/grace) matches, so the divergence is isolated to the security group's rules.
  Why: the group's effective network policy is invisible. A client diagnosing a failing ELB health check reads IpPermissions to decide whether anything admits the probe; an empty list makes a correctly-restricted group indistinguishable from a wide-open one, and any flow that adds, audits or asserts ingress against a stack-deployed group reads the wrong security posture.
  Fix: the provisioning of EC2 security-group ingress by the CloudFormation resource handler (the stack's security group and its ingress rules must land in EC2's security-group state) and/or the DescribeSecurityGroups projection that serializes IpPermissions/UserIdGroupPairs. Hypothesis (not asserted by the model or the recording): one of the two is empty — the state never records the stack-created rules, or the serializer drops them; the replay cannot tell which, so both components are named.
  Traces: autoscaling__ec2__elbv2.asg-terminate-instance-outside-group-rejected (cause 1), autoscaling__ec2__elbv2.e2e-asghc-asg-instance-health-check-failure-lifecycle (cause 2)
