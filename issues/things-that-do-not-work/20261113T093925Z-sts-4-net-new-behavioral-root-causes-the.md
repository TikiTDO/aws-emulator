# sts: 4 net-new behavioral root causes — the invalid-MFA AccessDenied message drops AWS's trailing space, aws:userid is never matched for an assumed-role session policy, a GetFederationToken session policy's object-key wildcard Allow grants nothing, and the aws:RequestedRegion session-policy leg never reaches a verdict

## Operation
AssumeRole

## Description
Four distinct net-new root causes in the STS session/authorization path, each grounded in a failing check of the `sts` suite group that no open issue carries the replay key of. They are bundled because they share one service; each must be closed separately before this issue is submitted.

=== Cause 1 of 4: the invalid-MFA GetSessionToken refusal message omits AWS's trailing space ===
AWS: Smithy (com.amazonaws.sts#GetSessionToken) models SerialNumber (serialNumberType, @length 9..256, @pattern ^[\w+=/:,.@-]*$) and TokenCode (tokenCodeType, @length 6..6, @pattern ^[\d]*$) and documents "An incorrect MFA code causes the API to return an access denied error"; the model declares only RegionDisabledException, so the refusal itself is the service-common AccessDenied and its text is recorded behavior only. Recorded: HTTP 403, Error.Code `AccessDenied`, Error.Message exactly `MultiFactorAuthentication failed with invalid MFA one time pass code. ` — the whole string is FIXED text and it ENDS IN A SINGLE SPACE; there is no variable part taken from the request or state (no serial number, user name or code appears in it).
Emulator: status and code are right (AccessDenied, no credentials issued — those legs pass), but the message is `MultiFactorAuthentication failed with invalid MFA one time pass code.` — the trailing space is missing. Replay: `AssertionError: expected the refusal message 'MultiFactorAuthentication failed with invalid MFA one time pass code. ', got 'MultiFactorAuthentication failed with invalid MFA one time pass code.'`
Why: the message is part of the refusal contract. A client, test suite or log scraper that compares the AWS message byte-for-byte (the standard way to distinguish an MFA-code rejection from every other AccessDenied on GetSessionToken, which carries no distinguishing code) does not match, and reports an unclassified authorization failure instead of "wrong MFA code".
Fix: the message construction of the MFA-challenge refusal — `crate::state::mfa_challenge_failure` in the sts crate's state module, as consumed by services/service-com-amazonaws-sts-awssecuritytokenservicev20110615/src/ops/get_session_token.rs (see its `@op` doc header, which names that function as the MFA authentication seam).
Traces: sts.get-session-token-invalid-mfa-code-rejected.

=== Cause 2 of 4: aws:userid is not matched for an assumed-role session, so a session policy that allows exactly its own documented userid denies the request ===
AWS: for a role session, `aws:userid` is the `<RoleId>:<RoleSessionName>` composite, and it is the same value GetCallerIdentity returns as UserId (AWS IAM User Guide, global condition keys / "Specifying a principal" unique-id forms). A session policy is a scope-down, so AssumeRole must succeed and the REQUEST is judged later (Smithy: AssumeRoleRequest$Policy targets unrestrictedSessionPolicyDocumentType, @pattern ^[\u0009\u000A\u000D\u0020-\u00FF]+$ — the model constrains the document only; the condition-key semantics are AWS-documented behavior). With the role's own identity policy allowing s3:GetObject on the object unconditionally, a session policy whose only statement is Allow s3:GetObject on that object ARN with Condition StringEquals {"aws:userid": "<RoleId>:<RoleSessionName>"} must permit the read (HTTP 200, the object's bytes), as must StringLike {"aws:userid": "<RoleId>:*"}; the bare RoleId, the bare session name and another session's composite must each be refused 403 AccessDenied with `User: arn:aws:sts::<account>:assumed-role/<RoleName>/<RoleSessionName> is not authorized to perform: s3:GetObject on resource: "<object ARN>" because no session policy allows the s3:GetObject action` (fixed text: `User: `, ` is not authorized to perform: `, ` on resource: `, ` because no session policy allows the `, ` action`; variable parts: the assumed-role ARN of the calling session, the attempted action and the quoted resource ARN the request names).
Emulator: the positive control passes — the same session with NO session policy reads the object, and GetCallerIdentity reports exactly the `<RoleId>:<RoleSessionName>` composite, so the identity value itself is correct — but the very first conditioned leg is refused: `AssertionError: the session was refused by a policy that allows exactly its own documented aws:userid '<RoleId>:<RoleSessionName>': expected the read to succeed, got error code 'AccessDenied'`. The authorization decision therefore does not see aws:userid (or sees a different value) for a minted role session, so the condition can never be satisfied and the check cannot go on to grade the four negative legs or the composite's exactness.
Why: every request a userid-conditioned policy is supposed to permit is refused, and the converse — a policy that should NOT match (bare RoleId, another session's composite) — is indistinguishable, because the key is simply absent from the decision. A least-privilege design that pins access to one named session (the standard way to scope a break-glass or per-job session) breaks outright against the emulator, and its negative half cannot be validated at all.
Fix: the condition-key publication for a minted session (the `aws:userid` value derived from the role's RoleId and the request's RoleSessionName) in the sts crate's session registry — `mint_session` / `assume_role_published_condition_keys` in services/service-com-amazonaws-sts-awssecuritytokenservicev20110615/src/state.rs — together with the `aws:userid` lookup in the called service's request-authorization path (S3 GetObject is the enforcement site this check exercises).
Traces: sts.userid-condition-matches-the-role-id-and-session-name-composite.

=== Cause 3 of 4: a GetFederationToken session policy's Allow on an object-key wildcard ARN grants nothing — only its Deny takes effect ===
AWS: the permissions of a GetFederationToken session are the intersection of the IAM user's identity policies and the inline session policy (Smithy: GetFederationTokenRequest$Policy, sessionPolicyDocumentType, @length 1..2048, @pattern ^[\u0009\u000A\u000D\u0020-\u00FF]+$, documented as an inline session policy that cannot grant more than the user's permissions policy). With the user's identity policy allowing s3:GetObject on "*" and a session policy of two statements — Allow s3:GetObject on `arn:aws:s3:::<bucket>/*` and Deny s3:GetObject on one exact key ARN whose object-key segment contains non-ASCII characters (accented Latin and CJK) — AWS refuses GetObject on that exact key with 403 AccessDenied and the explicit-deny-in-a-session-policy message, and SERVES (HTTP 200) GetObject on any sibling key under the same bucket, e.g. `plain/other.txt`.
Emulator: the Deny leg is correct and its assertion passes (the unicode Resource ARN does reach the decision and matches exactly). The sibling ASCII key is then REFUSED instead of served, and the check errors out on it: `botocore.errorfactory.AccessDenied: An error occurred (AccessDenied) when calling the GetObject operation: User: arn:aws:sts::<account>:federated-user/<Name> is not authorized to perform: s3:GetObject on resource: "arn:aws:s3:::<bucket>/plain/other.txt" because no identity-based policy allows the s3:GetObject action` (the account id, federated-user name and bucket name are per-run values filling the template). So the session policy's Allow never grants, and the implicit deny reported is the no-match one, not an explicit deny. Hypothesis: a session-policy statement whose Resource ends in the object-key wildcard `/*` is not matched by the resource matcher, so the document contributes only its exact-ARN Deny; a sibling hypothesis is that statement evaluation stops once the document carries a non-ASCII Resource, but that is contradicted by the Deny leg having matched.
Why: a client that scopes a federation session to a key prefix and carves out a single object loses the entire prefix. The failure is silent and total: every key the session is supposed to read is refused with a message naming the wrong policy type, so an operator widens the IAM user's identity policy (which changes nothing, since that policy already allows the action).
Fix: resource matching for session-policy statements in the request-authorization path (object-key wildcard ARNs under a bucket), fed by the session scope the GetFederationToken handler records — services/service-com-amazonaws-sts-awssecuritytokenservicev20110615/src/ops/get_federation_token.rs and the session registry in that crate's src/state.rs. Related but NOT covering this: open issue 20261113T073604Z-sts-a-getfederationtoken-session-policy-refusal-is-attributed.md owns the `no identity-based policy` vs `no session policy` attribution clause for two OTHER checks; the net-new defect here is the missing GRANT (a request AWS serves 200 is refused), not the clause wording.
Traces: sts.get-federation-token-policy-document-unicode-round-trip.

=== Cause 4 of 4: the aws:RequestedRegion session-policy leg never reaches a verdict — the check exhausts the 60 s harness cap ===
AWS: a session policy whose only Allow carries Condition StringEquals {"aws:RequestedRegion": "<home region>"} permits s3:PutObject against a bucket in the home region (and the bytes round-trip) and refuses the SAME session's s3:PutObject against a bucket in a second region (us-east-2) with 403 AccessDenied, leaving no object behind (the bucket owner's HeadObject answers 404); a control session minted from the same role with NO session policy reaches both regions. The role's own inline policy allows s3:* on both buckets, so nothing but the condition can decide the outcome. Model: AssumeRoleRequest$Policy as in Cause 2 — aws:RequestedRegion is an AWS-documented global condition key, not modelled.
Emulator: no comparison is produced at all — `Error: Check timed out after 60.0s`. The check's only unbounded waits are bounded polls: `_poll_allowed` on the home-region PutObject (240 s), `_poll_denied` on the away-region PutObject waiting for exactly `AccessDenied` (180 s), `_poll_allowed` on the control session's away-region PutObject (240 s), plus `_wait_assumable`/`_wait_creds_active`; a poll whose condition never arrives spins to the cap. Hypothesis: `aws:RequestedRegion` is not published for / evaluated against a minted session, so the cross-region PutObject keeps being SERVED and the poll for AccessDenied never terminates. The analogous check in the iam__s3__sts group (assumed-role-permissions-policy-requestedregion-condition-gates-put-object-by-region) is owned by open issue 20261106T072814Z-iam-s3-sts-2-root-causes-an-aws.md, which does not carry this check's replay key.
Why: overly permissive. A session policy pinned to one Region is the standard guard against data landing outside a jurisdiction; against the emulator the out-of-Region write is served, so the guard is validated as working while it enforces nothing — and the whole contract is unobservable because the check cannot finish.
Fix: publish `aws:RequestedRegion` for the request being authorized and evaluate it against session-policy conditions — the condition-key set recorded on the minted session (services/service-com-amazonaws-sts-awssecuritytokenservicev20110615/src/state.rs, `mint_session`/`assume_role_published_condition_keys`) and the condition evaluation in S3's request-authorization path.
Traces: sts.session-policy-region-condition-rejected-in-one-region-and-permitted-in-another.
