# Neptune DescribeDBEngineVersions serves RDS-shaped release metadata and skips the engine-name refusal

> _Note: this issue was identified against the code base at commit `f40a11b031083e7917f727d0c5a7c9d7eef99d5d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeDBEngineVersions

## Description
The Neptune front door now answers DescribeDBEngineVersions for the graph engine instead of refusing it (the previously filed 20261103T175309Z-neptune-parameter-and-engine-version-catalogs-serve-rds.md, now RESOLVED, covered that refusal), but the release element it serves is still assembled from RDS-wide engine metadata rather than the graph engine's, and the engine-name validation that the same operation must still apply to a value the front door does not serve has been dropped altogether: that query now succeeds with a catalog body where the service refuses it. Both clusters are reported by replay with owned_by=[] and stub_path="", so no open issue carries their replay keys; the open 20261110T174431Z-neptune-catalog-reads-still-serve-non-neptune-engine.md covers only the UNFILTERED catalog-content clusters under the neptune-catalog-* fixtures, not the filtered single-release read or the refusal below. THIS ISSUE HAS 2 CAUSES — both must be closed before submitting.

Cause 1 of 2: the DBEngineVersion element served for a filtered Neptune engine-version query carries RDS-wide certificate/binlog metadata and the wrong engine and release descriptions. AWS: DescribeDBEngineVersions models NO errors and returns com.amazonaws.neptune#DBEngineVersionMessage.DBEngineVersions, a list of com.amazonaws.neptune#DBEngineVersion; that shape models DBEngineDescription ('The description of the database engine') and DBEngineVersionDescription ('The description of the database engine version') and does NOT model SupportedCACertificateIdentifiers, SupportsCertificateRotationWithoutRestart, SupportsChangeDataCaptureStreams or SupportsEnhancedBinlog (Smithy: DescribeDBEngineVersions errors=[], input Engine/EngineVersion/DBParameterGroupFamily/DefaultOnly/ListSupportedCharacterSets/ListSupportedTimezones, output DBEngineVersionMessage; shape com.amazonaws.neptune#DBEngineVersion). Recorded behavior only for the values, because the model documents neither the description text nor the RDS-shared wire members: for a query naming the graph engine and one published release the service reports DBEngineDescription as the engine NAME itself (the recorded value is 'neptune', not a product title), DBEngineVersionDescription as the product name plus the full release build identifier (recorded 'Neptune 1.4.8.0.R1' — i.e. the release's build suffix is part of the string, not just the version triple), an EMPTY SupportedCACertificateIdentifiers element, SupportsCertificateRotationWithoutRestart 'false', and the extra flags SupportsChangeDataCaptureStreams 'false' and SupportsEnhancedBinlog 'false' that the RDS-shared wire shape emits for this engine. Emulator: the 200 body reports DBEngineDescription 'Amazon Neptune' where the service reports the engine name, DBEngineVersionDescription without the release build suffix ('Neptune 1.4.8.0'), a populated SupportedCACertificateIdentifiers list of RDS certificate authority identifiers (recorded run: rds-ca-rsa4096-g1, rds-ca-rsa2048-g1) where the service emits an empty element, SupportsCertificateRotationWithoutRestart inverted to 'true', and no SupportsChangeDataCaptureStreams or SupportsEnhancedBinlog member at all. Why: this is the discovery call a client makes before CreateDBCluster/CreateDBInstance and the element an upgrade or certificate-rotation planner reads; it is told the release supports rotating its certificate without a restart when the service says it does not, it is offered RDS CA identifiers that are not selectable on this engine (and will be refused when passed to a modify call), and a client keying on the release description (a catalog cache diff, a console listing, a pinned test) sees a string the service never emits. Fix: the engine-version reference catalog read by the DescribeDBEngineVersions handler and that handler's projection of DBEngineVersion for the Neptune front door — engine/release descriptions and the certificate and capability flags must come from the graph engine's catalog, not the RDS-wide one. Traces: neptune-npt-traj-engine-version-catalog-to-create#task#1.

Cause 2 of 2: DescribeDBEngineVersions no longer refuses the engine-name value the front door does not serve — it answers 200 with a catalog body where the service answers 400 InvalidParameterValue. AWS: the operation models no errors, so the refusal travels as the awsQuery protocol error envelope — HTTP 400 with ErrorResponse/Error carrying Type 'Sender', Code 'InvalidParameterValue' and Message 'Unrecognized engine name: <engine>', where 'Unrecognized engine name: ' is fixed text and the trailing value is the offending engine name taken verbatim from the request (the recorded run's value is 'neptune'); RequestId is per-run and not a requirement (Smithy: DescribeDBEngineVersions errors=[], input member Engine; recorded response for the refusal). Hypothesis: the same step was previously refused by the emulator with the wrong code and message (resolved issue 20261103T175309Z cause 9), and widening the engine catalog so the graph engine resolves for cause 1's query removed the validation path entirely rather than correcting its classification — this step's engine/parameter combination is one the service still rejects. Emulator: HTTP 200 with a DescribeDBEngineVersionsResponse body and no ErrorResponse element at all. Why: a client that probes an engine value before CreateDBCluster/CreateDBInstance is told the value is valid and goes on to create against it, so the error surfaces at the create (or never) instead of at the call that was wrong; a refusal-path test or an error-classification branch keyed on InvalidParameterValue never fires. Fix: the DescribeDBEngineVersions handler's engine-name validation — the engine value must be resolved against the published engine catalog and an unresolved one must raise the 400 Sender/InvalidParameterValue refusal naming the offending engine, instead of falling through to a catalog response. Traces: neptune-npt-traj-engine-version-catalog-to-create#task#2.
