# config: the StartRemediationExecution refusal/positive-control check never completes — the rule-without-remediation refusal contract is unreachable because the remediation path never converges

> _Note: this issue was identified against the code base at commit `681ba8e3ce79605e692c1fa7f993944edfaadaa9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartRemediationExecution

## Description
One net-new root cause on the AWS Config surface, grounded in the single `### config` failure of this run that the replay report marked neither ALREADY FILED nor OWNED by an open issue.

=== Cause 1 of 1: the Config remediation path never converges inside a normal request/poll budget, so the whole StartRemediationExecution refusal check is unreachable — the NoSuchRemediationConfigurationException contract for a rule with no remediation configuration is never exercised and the accepted sibling rule never produces an observable terminal execution in time ===
Failing check: config.start-remediation-execution-missing-configuration-rejected (verdict [mismatch], `Error: Check timed out after 60.0s`).

AWS: Smithy (com.amazonaws.configservice#StarlingDoveService) models StartRemediationExecution with input ConfigRuleName (@required, @length 1..128, @pattern \S) + ResourceKeys (@required, @length 1..100) and output FailureMessage/FailedItems; its modeled errors are InsufficientPermissionsException, InvalidParameterValueException and NoSuchRemediationConfigurationException (all errorKind client, HTTP 400). NoSuchRemediationConfigurationException is documented "You specified an Config rule without a remediation configuration." DescribeRemediationExecutionStatus models the same NoSuchRemediationConfigurationException plus InvalidNextTokenException/InvalidParameterValueException, and returns RemediationExecutionStatuses entries of {ResourceKey, State (RemediationExecutionState enum), StepDetails, InvocationTime, LastUpdatedTime}. Recorded behavior for the two refusals, with the fixed text and the variable part named explicitly:
  * StartRemediationExecution against a config rule that has NO remediation configuration -> HTTP 400, code `NoSuchRemediationConfigurationException`, message fixed text `There is no applicable RemediationConfiguration setup for AWS Config rule ` followed by the rule name taken verbatim from the request's ConfigRuleName, and NO trailing period.
  * DescribeRemediationExecutionStatus for that same rule -> HTTP 400, code `NoSuchRemediationConfigurationException`, message fixed text `There is no RemediationConfiguration setup for AWS Config rule ` followed by the request's ConfigRuleName, and a trailing `.` (the two messages differ in wording and in the trailing period; both are requirements). The refusal also has no side effect: no execution record is created for a rule that has no remediation configuration.
  * For the sibling rule that DOES have a remediation configuration (TargetType=SSM_DOCUMENT, TargetId=<a customer-created Automation document>, Parameters.AutomationAssumeRole StaticValue=<role arn>, Automatic=false), StartRemediationExecution is accepted with FailedItems empty and DescribeRemediationExecutionStatus settles on State `SUCCEEDED` for the submitted ResourceKey ({resourceType:"AWS::::Account", resourceId:<account id>}); the execution ids, timestamps and generated rule/document/role names are per-run values and are not part of the requirement.
Emulator: the check never finishes — replay reports only `Error: Check timed out after 60.0s`, so no assertion in the body is reached and neither refusal's status, code nor message is observable. Every bounded call in the setup (PutConfigRule x2, DescribeConfigRules, IAM CreateRole, SSM CreateDocument, PutRemediationConfigurations) is a normal request; the check's only unbounded work, in order, is (1) _poll_rule_active per rule until ConfigRuleState==ACTIVE, (2) _retry_until_no_failed_items around StartRemediationExecution for the sibling rule (36 attempts x 10 s = up to 360 s, retried while FailedItems is non-empty or InsufficientPermissionsException is returned), and (3) _poll_for_terminal_status_entry over DescribeRemediationExecutionStatus until State is SUCCEEDED/FAILED (120 s). One of those three answers 200 with a projection that never resolves instead of converging or refusing. Hypothesis: poll (2) — StartRemediationExecution keeps returning the submitted ResourceKey in FailedItems (or InsufficientPermissionsException) for a rule whose account-scoped resource has no NON_COMPLIANT evaluation yet, so the harness burns its whole retry ladder; the adjacent already-filed cause on this same path (open issue 20261111T121325Z-config-2-net-new-behavioral-causes-startremediationexecution-never.md, its cause 1: StartRemediationExecution reports SUCCEEDED without ever creating the SSM Automation execution) shows the acceptance/terminal legs can answer, which makes (2) the most likely blocker; a never-ACTIVE rule in (1) is the second candidate. That open issue does NOT cover this failure: it carries only the replay keys of config.concurrent-start-remediation-execution-dedup, config.e2e-remediation-execution-resolves-noncompliant-resource and config.conformance-pack-deploy-compliance-summary, which is why the report left this check unowned, and fixing the SSM hand-off alone will not make this check complete or exercise either refusal message.
Why: a client gets no answer at all on this path. A caller that starts a remediation and loops on FailedItems/DescribeRemediationExecutionStatus — exactly what the AWS Config remediation workflow prescribes — hangs forever instead of either seeing the key accepted or being refused, and a hung read is indistinguishable from a wedged service. Simultaneously the two NoSuchRemediationConfigurationException refusals are unverified in the emulator, so error-handling code that branches on that code and on the two distinct messages (StartRemediationExecution's without a trailing period, DescribeRemediationExecutionStatus's with one) cannot be trusted, and a caller that expects a 400 for a rule with no remediation configuration may instead be left waiting or handed a success.
Fix: Config's remediation execution path — the StartRemediationExecution handler (its FailedItems/acceptance decision for a resource key, and the InsufficientPermissionsException branch), the asynchronous executor that advances the RemediationExecutionStatus State to a terminal value, and the NoSuchRemediationConfigurationException refusal branch shared by StartRemediationExecution and DescribeRemediationExecutionStatus (including each operation's exact message text). Each of these must settle inside a normal poll budget: a key is either accepted (FailedItems empty, record advancing to SUCCEEDED/FAILED) or refused with a modeled 400 — never left in a state the caller must poll indefinitely. The ConfigRuleState=ACTIVE projection for a freshly created managed rule must likewise resolve promptly.
Traces: config.start-remediation-execution-missing-configuration-rejected.

Check: config.start-remediation-execution-missing-configuration-rejected, listed under `### config`, verdict [mismatch].
Replay output, in full: `Error: Check timed out after 60.0s` — the check body never returned, so no assertion inside it was reached.

What the check does (setup all through bounded calls): ensure a customer-managed configuration recorder (IAM role + S3 bucket + bucket policy + PutConfigurationRecorder + PutDeliveryChannel + StartConfigurationRecorder); PutConfigRule twice for two managed rules with Source {Owner: AWS, SourceIdentifier: CLOUD_TRAIL_ENABLED}, one intentionally WITHOUT a remediation configuration and one WITH; poll DescribeConfigRules until each ConfigRuleState is ACTIVE; create an IAM role assumable by ssm.amazonaws.com; create a customer SSM Automation document (schemaVersion 0.3, a single aws:sleep PT1S step, assumeRole from the AutomationAssumeRole parameter); PutRemediationConfigurations for the sibling rule with TargetType=SSM_DOCUMENT, TargetId=<that document>, Automatic=false, Parameters={AutomationAssumeRole: {StaticValue: {Values: [<role arn>]}}}.

Expected (AWS), resource_key = {resourceType: "AWS::::Account", resourceId: <account id>}:
1. StartRemediationExecution(ConfigRuleName=<rule-without-remediation>, ResourceKeys=[resource_key])
   -> HTTP 400, Error.Code = "NoSuchRemediationConfigurationException",
      Error.Message = "There is no applicable RemediationConfiguration setup for AWS Config rule " + <rule-without-remediation> (no trailing period; the rule name is the request value, the rest is fixed text).
2. DescribeRemediationExecutionStatus(ConfigRuleName=<rule-without-remediation>, ResourceKeys=[resource_key])

   i.e. the refusal leaves nothing behind — there is no execution record to describe.
3. StartRemediationExecution(ConfigRuleName=<rule-with-remediation>, ResourceKeys=[resource_key]) -> 200 with FailedItems == [].

Actual (emulator): none of 1-4 is observable. The check is killed at its 60 s budget while still inside its own unbounded polling, so the emulator produced no status code, no error code and no message for either refusal. The three candidate blockers, which are the check's only unbounded waits, are: DescribeConfigRules never reporting ConfigRuleState=ACTIVE (60 s), StartRemediationExecution never returning an empty FailedItems / repeatedly returning InsufficientPermissionsException (up to 360 s of retries), and DescribeRemediationExecutionStatus never reporting a terminal State (120 s). In every one of those cases the emulator answers HTTP 200 with a projection that never resolves rather than converging or issuing one of the operation's modeled 400s — the divergence is precisely that absence of a settling answer.
