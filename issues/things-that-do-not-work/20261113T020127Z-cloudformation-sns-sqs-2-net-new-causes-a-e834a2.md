# cloudformation__sns__sqs: 2 net-new causes — a sibling-nested-stack deploy wired by Fn::GetAtt <Child>.Outputs.<Key> never settles, and Fn::GetAtt on a Data key the custom-resource provider omitted never produces the CustomResource attribute error / ROLLBACK_COMPLETE

> _Note: this issue was identified against the code base at commit `f3c33bab928599ae9956c8a8be7ee7afed317dab`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Two net-new root causes in the CloudFormation side of the cloudformation__sns__sqs suite. Both failing checks are listed with no OWNED/ALREADY-FILED marker, so no open issue carries their replay keys; similar open issues are named per cause below but none of them covers these checks.

Cause 1 of 2: a parent stack whose three AWS::CloudFormation::Stack children are wired to each other with Fn::GetAtt <Child>.Outputs.<Key> never reaches a terminal StackStatus, so none of the sibling wiring or the SNS->SQS delivery that depends on it can be observed.
AWS: CreateStack on a parent template holding three AWS::CloudFormation::Stack resources (a Producer exporting Outputs.TopicArn for an AWS::SNS::Topic, and two consumer siblings each taking that ARN as a String Parameter via {"Fn::GetAtt": ["Producer", "Outputs.TopicArn"]}) drives the whole tree to completion: the root ends CREATE_COMPLETE (Smithy: StackStatus enum includes CREATE_IN_PROGRESS/CREATE_COMPLETE/ROLLBACK_COMPLETE — DescribeStacks has no modeled errors and is simply polled until the status leaves *_IN_PROGRESS), DescribeStackResource returns each child's PhysicalResourceId (the child stack id), DescribeStacks on each child returns Outputs rows carrying BOTH members of the modeled Output structure (OutputKey and OutputValue), and the child's AWS::SNS::Subscription is confirmed (SNS GetSubscriptionAttributes PendingConfirmation == "false"). Only the sibling that also declares an AWS::SQS::QueuePolicy allowing Principal {"Service": "sns.amazonaws.com"} on sqs:SendMessage receives the publishes; the policy-less sibling receives none, while a direct SQS SendMessage to that same queue still arrives. Recorded behavior: the recording completes this whole sequence inside the suite's 60s per-check budget.
Emulator: the check is cut off — 'Error: Check timed out after 60.0s'. Nothing past the first poll loop is reached, i.e. the root stack does not leave *_IN_PROGRESS (its own waiter allows 300s) or the first positive-control publish never arrives in the policy-bearing sibling's queue, so the emulator produced neither a terminal root status, nor the resolved sibling parameter, nor any delivery. Hypothesis: nested-stack children wired by Fn::GetAtt Producer.Outputs.TopicArn are left un-provisioned because the parent cannot resolve a child's output value, which is the same shape of defect open issues 20261110T124641Z-cloudformation-a-nested-stack-s-parent-returns-outputs.md and 20261111T111216Z-cloudformation-s3-ssm-fn-getatt-outputs-name-on-a-nested-aws.md describe for other services; neither carries this check.
Why: a client deploying the standard producer/consumer nested-stack layout (CDK and SAM emit exactly this) hangs forever on a stack that never becomes CREATE_COMPLETE, never learns its child resources' physical ids, and can never test the negative case that a missing SQS queue policy blocks SNS delivery — a permission gap would be indistinguishable from this hang.
Fix: the CloudFormation nested-stack provisioning path — the AWS::CloudFormation::Stack resource handler and the parent's intrinsic-function resolution for Fn::GetAtt <Child>.Outputs.<Key> (child outputs must be materialized with OutputValue before dependent siblings are created), plus the stack-status state machine that must always advance a stack out of *_IN_PROGRESS to a terminal StackStatus.
Traces: cloudformation__sns__sqs.cfn-nested-sibling-stacks-getatt-wiring-missing-queue-policy-blocks-delivery.

Cause 2 of 2: Fn::GetAtt on an attribute the custom-resource provider's Data does not contain neither fails the consuming resource with the CustomResource attribute error nor rolls the stack back.
AWS: for a Custom::<Type> resource whose ServiceToken is an SNS topic, the provider PUTs {Status, PhysicalResourceId, StackId, RequestId, LogicalResourceId, Data} to the presigned ResponseURL. A consumer referencing {"Fn::GetAtt": ["Provider", "<Attribute>"]} for an <Attribute> absent from that Data fails: DescribeStackEvents reports exactly one CREATE_FAILED StackEvent for the consumer's LogicalResourceId whose ResourceStatusReason is "CustomResource attribute error: Vendor response doesn't contain <Attribute> attribute in object <StackId>|<ProviderLogicalResourceId>|<ProviderRequestId>" — fixed text: "CustomResource attribute error: Vendor response doesn't contain " and " attribute in object "; variable parts: <Attribute> taken from the template's GetAtt, and <StackId>|<ProviderLogicalResourceId>|<ProviderRequestId> taken from the stack and the provider's own Create request (never the literal ids of one run). The stack then reaches ROLLBACK_COMPLETE, the provider is sent a Delete request, and the consumer is NEVER sent any provider request. The control case (GetAtt on a key the Data DOES contain) delivers the resolved value in the consumer's ResourceProperties and the stack reaches CREATE_COMPLETE. The model only states that StackEvent.ResourceStatusReason is the free-text "Success/failure message associated with the resource" (Smithy: StackEvent.ResourceStatusReason; DescribeStackEvents is paginated over StackEvents) — the wording above is recorded behavior only.
Emulator: the check is cut off — 'Error: Check timed out after 60.0s'. The flow does not get past waiting for the Provider's Create request on the SNS->SQS mailbox (its own waiter allows 240s), so the emulator delivers no custom-resource request, produces no CREATE_FAILED event with the attribute-error reason, and never reaches ROLLBACK_COMPLETE.
Why: a client whose provider forgets a Data key gets a stack that hangs in *_IN_PROGRESS instead of a named attribute error and a clean rollback, so the template bug is never surfaced and the stack cannot be retried; and because the consumer is not skipped, a provider could be invoked for a resource whose GetAtt never resolved.
Fix: the custom-resource provider protocol in the CloudFormation resource-provisioning path — dispatch of Create/Delete requests to the ServiceToken topic, resolution of Fn::GetAtt against the provider response Data (with the attribute-error reason recorded on the consumer's CREATE_FAILED event), and the rollback state machine that must take the stack to ROLLBACK_COMPLETE. Related open issues 20261101T212352Z-cloudformation-sns-sqs-a-custom-resource-whose-servicetoken.md and 20261105T141713Z-cloudformation-sns-sqs-4-net-new-root-causes.md describe neighbouring custom-resource defects but do not carry this check.
Traces: cloudformation__sns__sqs.custom-resource-getatt-missing-data-key-fails.

## Steps to Reproduce
Cause 1: create an S3 bucket and put three templates in it — producer.json (one AWS::SNS::Topic, Outputs.TopicArn = {"Ref": "Topic"}), good.json and bad.json (each: a String Parameter TopicArn, an AWS::SQS::Queue, an AWS::SNS::Subscription with Protocol=sqs, Endpoint={"Fn::GetAtt":["Queue","Arn"]}, RawMessageDelivery=true, Outputs.QueueUrl = {"Ref":"Queue"}; good.json additionally an AWS::SQS::QueuePolicy allowing Principal {"Service":"sns.amazonaws.com"} on sqs:SendMessage with Condition ArnEquals aws:SourceArn = the topic, and DependsOn QueuePolicy on the subscription). CreateStack a parent holding three AWS::CloudFormation::Stack resources (Producer/Good/Bad) where Good and Bad pass Parameters.TopicArn = {"Fn::GetAtt":["Producer","Outputs.TopicArn"]}. Poll DescribeStacks on the root: it must reach CREATE_COMPLETE. Then read each child's Outputs, SNS Publish a marker to the topic and ReceiveMessage on both child queues — only the good sibling's queue receives it, the bad one stays empty, and a direct SQS SendMessage to the bad queue still arrives. Replay: cloudformation__sns__sqs.cfn-nested-sibling-stacks-getatt-wiring-missing-queue-policy-blocks-delivery.

Cause 2: create an SNS topic and an SQS queue subscribed to it with RawMessageDelivery=true (and a queue policy admitting sns.amazonaws.com) to act as the custom-resource mailbox.
