# kms__stepfunctions: 3 net-new causes — UpdateStateMachine back to AWS_OWNED_KEY never clears the CMK, and a CMK that becomes unusable mid-execution (disabled key, or revoked kms:Decrypt) does not fail the running execution States.Runtime

> _Note: this issue was identified against the code base at commit `c43f13612f17253679972bb58b777ab0e011820f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateStateMachine

## Description
Three net-new root causes about customer-managed-key (CMK) encryption on Step Functions state machines, grounded in three failing behavioral checks the replay report left unmarked (no ALREADY-FILED marker, no OWNED marker). Smithy model used: services/service-com-amazonaws-sfn-awsstepfunctions/smithy-model/com-amazonaws-sfn-awsstepfunctions.json. None of these is covered by the open CMK issues for this service: 20261110T140310Z-kms-stepfunctions-2-net-new-causes-createactivity-with.md (CreateActivity under a disabled key; removed-trust redrive), 20261109T164957Z-kms-stepfunctions-2-net-new-causes-an-execution.md (trust-policy Conditions on StartExecution; the principal rendered in a relayed KMS denial) and 20261111T004529Z-kms-stepfunctions-startsyncexecution-on-a-cmk-encrypted-express.md (StartSyncExecution key-policy allow) all describe different causes.

Cause 1 of 3 — UpdateStateMachine with encryptionConfiguration={"type":"AWS_OWNED_KEY"} does not remove the customer managed key; DescribeStateMachine keeps reporting the previous CUSTOMER_MANAGED_KMS_KEY configuration.
Failing check id: kms__stepfunctions.update-state-machine-cmk-add-swap-remove-reflected-in-describe.
AWS: Smithy models UpdateStateMachine's input member encryptionConfiguration as EncryptionConfiguration{type (required, enum EncryptionType = AWS_OWNED_KEY | CUSTOMER_MANAGED_KMS_KEY), kmsKeyId (@length 1..2048), kmsDataKeyReusePeriodSeconds (@range 60..900)}, and DescribeStateMachine's output carries the same shape. encryptionConfiguration is a whole-value replacement: when the update sets type=AWS_OWNED_KEY, the state machine is no longer encrypted with a customer key, so the subsequent DescribeStateMachine must report exactly {"type": "AWS_OWNED_KEY"} — no kmsKeyId and no kmsDataKeyReusePeriodSeconds, since kmsDataKeyReusePeriodSeconds only applies to customer managed keys. The add and swap legs of the same sequence (AWS_OWNED_KEY -> CMK#1/300s -> CMK#2/600s) must likewise be reflected member-for-member, and each accepted update must advance revisionId.
Emulator: after the update to {"type": "AWS_OWNED_KEY"}, DescribeStateMachine still answers the previously configured customer key: {'kmsKeyId': '<key ARN of CMK#2>', 'kmsDataKeyReusePeriodSeconds': 600, 'type': 'CUSTOMER_MANAGED_KMS_KEY'}. The AWS_OWNED_KEY update is accepted (no error) but the stored encryption configuration is merged/ignored rather than replaced, so the CMK members are never cleared and type is never switched back.
Why: a client that de-provisions a CMK (to delete the key, to move the machine to AWS-owned encryption, or to stop paying for the key) is told the machine is still bound to a key it is about to schedule for deletion; conversely a client reading encryptionConfiguration to decide whether it must keep granting kms:Decrypt/kms:GenerateDataKey keeps the grant forever. Any audit that asserts "no customer key is attached" fails against a machine AWS would report as AWS_OWNED_KEY.
Fix: the UpdateStateMachine handler's encryption-configuration write path and the state it persists — encryptionConfiguration must be stored as a replacement of the whole structure, dropping kmsKeyId and kmsDataKeyReusePeriodSeconds when type is AWS_OWNED_KEY, and DescribeStateMachine must project exactly what was stored.
Traces: kms__stepfunctions.update-state-machine-cmk-add-swap-remove-reflected-in-describe.

Cause 2 of 3 — disabling a state machine's CMK while an execution is RUNNING has no effect: the execution still SUCCEEDS instead of failing States.Runtime.
Failing check id: kms__stepfunctions.xsvc-sfn-disabled-cmk-mid-execution-fails-states-runtime.
AWS: recorded behavior only for the end-to-end sequence (the Smithy model states the surface, not the runtime rule): DescribeExecution's output carries status, error and cause, and both DescribeStateMachine and DescribeExecution model KmsInvalidStateException / KmsAccessDeniedException / KmsThrottlingException as HTTP 400 errors, which is how a machine encrypted with CUSTOMER_MANAGED_KMS_KEY is defined to surface an unusable key. The recording shows: an execution of a CMK-encrypted STANDARD machine sits in a Wait state; kms:DisableKey is called (kms:DescribeKey then reports KeyState "Disabled"); once the Wait elapses and the cached data key's kmsDataKeyReusePeriodSeconds has expired, Step Functions can no longer obtain a data key to record the transition, so the execution leaves RUNNING as FAILED with error "States.Runtime" and a cause that is KMS's message relayed verbatim — fixed text "<key ARN> is disabled. (Service: Kms, Status Code: 400, Request ID: <request-id>) (SDK Attempt Count: <n>)", where <key ARN> is the key named by the state machine's encryptionConfiguration and <request-id>/<n> are the inner call's per-attempt values (the check masks exactly those two). While the key is disabled, an ALL_DATA DescribeExecution is itself refused KmsInvalidStateException; only METADATA_ONLY reads the elided status.
Emulator: after DisableKey the execution reaches status 'SUCCEEDED' (observed within the 195 s budget), so neither the FAILED status, the States.Runtime error, the relayed disabled-key cause, nor the KmsInvalidStateException on the ALL_DATA read is produced. The emulator never consults the key's live state after the execution starts — encryption is recorded as configuration rather than being exercised per data-key operation.
Why: disabling a key is the documented emergency control for a compromised or retiring CMK. A client that disables the key believes in-flight work has been cut off, while the emulator finishes and commits that work and reports success; conversely a client whose runbook branches on error=="States.Runtime" with a KMS cause sees no failure at all, and nothing distinguishes a healthy execution from one running on a key the account has revoked.
Fix: the execution runtime's data-key acquisition path for CMK-encrypted state machines (the per-transition GenerateDataKey/Decrypt against the configured key, honouring kmsDataKeyReusePeriodSeconds) — a key whose state is not Enabled must fail the execution with error States.Runtime and the relayed KMS message as the cause, and the sensitive-field projection of DescribeExecution must refuse ALL_DATA with KmsInvalidStateException while the key is unusable.
Traces: kms__stepfunctions.xsvc-sfn-disabled-cmk-mid-execution-fails-states-runtime.

Cause 3 of 3 — revoking the execution role's kms:Decrypt on the state machine's CMK while an execution is RUNNING has no effect: the execution still SUCCEEDS instead of failing States.Runtime.
Failing check id: kms__stepfunctions.xsvc-sfn-kms-access-denied-mid-execution-fails-states-runtime.
AWS: recorded behavior only, same surface as Cause 2. The recording shows: an execution of a CMK-encrypted STANDARD machine sits in a Wait state; the key policy is replaced with one that explicitly denies kms:Decrypt to the execution role; once the Wait elapses and the data-key reuse period has passed, the execution leaves RUNNING as FAILED with error "States.Runtime" and a cause whose fixed text is "User: <principal> is not authorized to perform: kms:Decrypt on resource: <key ARN> with an explicit deny in a resource-based policy (Service: Kms, Status Code: 400, Request ID: <request-id>) (SDK Attempt Count: <n>)" — <principal> is the STS assumed-role session ARN arn:aws:sts::<account>:assumed-role/<role-name>/<session>, <key ARN> is the key from the machine's encryptionConfiguration, and <session>/<request-id>/<n> are the only per-call values (the check masks exactly those three). While the deny is in force an ALL_DATA DescribeExecution is refused KmsAccessDeniedException.
Emulator: after the deny is installed the execution reaches status 'SUCCEEDED' (observed within the 360 s budget), so the FAILED status, the States.Runtime error, the relayed authorization cause and the KmsAccessDeniedException on the ALL_DATA read are all absent. Authorization against the key is not re-evaluated for the data-key operations an in-flight execution performs. (Distinct from Cause 2: here the key stays Enabled and it is the execution role's authorization on it that is withdrawn; note the principal-rendering defect already filed as 20261109T164957Z-kms-stepfunctions-2-net-new-causes-an-execution.md applies to the cause text once this cause produces one.)
Why: revoking a role's key access is how an operator contains a compromised execution role without touching the key's availability for everyone else. A client that does so is told the affected executions completed successfully, and data it believes was never committed has been committed.
Fix: the execution runtime's data-key acquisition path must authorize each KMS call as the execution role's assumed-role session against the key policy and the role's policies at the time of the call, and map a denial to a FAILED execution with error States.Runtime and the relayed KMS authorization message as the cause.
Traces: kms__stepfunctions.xsvc-sfn-kms-access-denied-mid-execution-fails-states-runtime.

## Evidence
Cause 1 — kms__stepfunctions.update-state-machine-cmk-add-swap-remove-reflected-in-describe, verdict mismatch.
Expected: after UpdateStateMachine(stateMachineArn=<sm>, definition=<same>, encryptionConfiguration={"type":"AWS_OWNED_KEY"}), DescribeStateMachine reports encryptionConfiguration == {"type": "AWS_OWNED_KEY"} (no kmsKeyId, no kmsDataKeyReusePeriodSeconds) and a revisionId advanced past the swap's.
Actual (AssertionError from the check): "after removing the CMK, DescribeStateMachine must report AWS_OWNED_KEY with no kmsKeyId; got {'kmsKeyId': 'arn:aws:kms:<region>:<account>:key/<key-id>', 'kmsDataKeyReusePeriodSeconds': 600, 'type': 'CUSTOMER_MANAGED_KMS_KEY'}" — i.e. the previously swapped-in CMK and its 600 s reuse period, unchanged. (The literal key id and account in the recorded text are per-run values; the requirement is that both CMK members are absent and type is AWS_OWNED_KEY.) The update call itself returned 200.

Cause 2 — kms__stepfunctions.xsvc-sfn-disabled-cmk-mid-execution-fails-states-runtime, verdict mismatch.
Expected: with the machine's CMK Disabled (kms:DescribeKey KeyState == "Disabled") while the execution is inside its Wait state, DescribeExecution(includedData=METADATA_ONLY) leaves RUNNING with status "FAILED"; after kms:EnableKey, DescribeExecution(includedData=ALL_DATA) reports status FAILED, error "States.Runtime" and cause "<key ARN> is disabled. (Service: Kms, Status Code: 400, Request ID: <request-id>) (SDK Attempt Count: <n>)".
Actual (AssertionError from the check): "an execution whose CMK is Disabled when its Wait state ends must FAIL; got 'SUCCEEDED' within 195s". The error/cause and the KmsInvalidStateException-while-disabled assertions were never reached.

Cause 3 — kms__stepfunctions.xsvc-sfn-kms-access-denied-mid-execution-fails-states-runtime, verdict mismatch.
Expected: with the key policy explicitly denying kms:Decrypt to the execution role while the execution is inside its Wait state, DescribeExecution(includedData=METADATA_ONLY) leaves RUNNING with status "FAILED"; after the grant is restored, ALL_DATA reports status FAILED, error "States.Runtime" and cause "User: arn:aws:sts::<account>:assumed-role/<role-name>/<session> is not authorized to perform: kms:Decrypt on resource: <key ARN> with an explicit deny in a resource-based policy (Service: Kms, Status Code: 400, Request ID: <request-id>) (SDK Attempt Count: <n>)".
Actual (AssertionError from the check): "an execution whose execution role has lost kms:Decrypt when its Wait state ends must FAIL; got 'SUCCEEDED' within 360s". The error/cause and the KmsAccessDeniedException-while-denied assertions were never reached.

In Causes 2 and 3 the state machine is created with encryptionConfiguration {type: CUSTOMER_MANAGED_KMS_KEY, kmsKeyId: <key ARN>, kmsDataKeyReusePeriodSeconds: 60} — the minimum reuse period — so no cached data key can explain the success.

2. sfn:CreateStateMachine(name=<n>, definition={"StartAt":"P","States":{"P":{"Type":"Pass","End":true}}}, roleArn=<role>, type=STANDARD) with NO encryptionConfiguration. sfn:DescribeStateMachine -> encryptionConfiguration == {"type":"AWS_OWNED_KEY"}.
