# ds: the LDAPS enable/disable and directory-data-access toggle flows reach no verdict — each is killed at the 60 s check budget because every clock-owed transition withholds its settled value past the poll that starts it

> _Note: this issue was identified against the code base at commit `34aa023e13a037c836015cae341f7a7e68727fe7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateMicrosoftAD

## Description
One net-new root cause in the Directory Service (ds) control plane, found by replaying suite simparity-behavioral-aws-v1 against the emulator built from this checkout. Two poll-and-wait server-side flows are killed at the suite's 60 s per-check budget having graded NOTHING: neither the LDAPS enable/disable status contract nor the directory-data-access gate contract (including its DirectoryInDesiredStateException refusal) is ever exercised. The service answers every call; the flows simply never reach their assertions. Neither check is stub-blocked — the suite marks stub-blocked checks separately.

Cause 1 of 1: every status transition this service owes is materialised only by a call that happens AFTER the transition's span has elapsed, and the span is deliberately set so that a client probing immediately after the call that starts the transition always reads the transient value. A client therefore pays one full poll interval per transition before it can learn the settled one, and a flow with three to five chained transitions exceeds any budget shorter than the sum of its intervals.
AWS: recorded behavior only — the ds model declares the transient and settled enum values (DirectoryStage Requested/Creating/Active; LDAPSStatus Enabling/Enabled/Disabled; DataAccessStatus Enabling/Enabled/Disabling/Disabled) but says nothing about timing. On real AWS a Managed Microsoft AD stays Requested/Creating for 20–45 minutes and LDAPS/data-access transitions take minutes, so a client polls at human intervals — 30 s for Stage Active, 10 s for the certificate poll, 20 s for the LDAPS enable poll, 15 s for the LDAPS disable poll, 10 s for the data-access polls in these two checks — and eventually reads the settled value. The behaviours these flows are asserting, once reachable, are: DescribeLDAPSSettings reporting no Client LDAPS Enabled on a fresh directory, EnableLDAPS driving LDAPSStatus to Enabled for a freshly Registered self-signed certificate and DisableLDAPS driving it to Disabled; and DescribeDirectoryDataAccess reporting Disabled on a fresh directory, EnableDirectoryDataAccess driving it to Enabled, a second EnableDirectoryDataAccess being refused with HTTP 400 DirectoryInDesiredStateException whose message is the fixed text "Directory " + the DirectoryId from the request + " is already in the desired state. : RequestId: " + the call's own request id (only the directory id and the request id are per-call values; the sentence is the requirement), the gate's state being left untouched by that refusal, and DisableDirectoryDataAccess then driving it back to Disabled and a further enable back to Enabled.
Emulator: a create's stage is a CHAIN held for TRANSITION_SPAN = 500 ms in Requested then DIRECTORY_BUILD_SPAN = 3 s in Creating before Active (services/.../src/state.rs:119, :146, :156 directory_active_at), and the same TRANSITION_SPAN governs the certificate Registering→Registered, LDAPS Enabling→Enabled and data-access Enabling/Disabling steps, each materialised lazily by advance_clock on the next handler call. Because the span is documented as chosen so "a caller acting immediately after the create still observes the transient state" (state.rs:106-118), the first read after each transition-starting call ALWAYS returns the transient value, and the settled value only becomes observable one poll interval later. Fixed sleeps alone: ds.ldaps-enable-disable-server-enforced pays 30 s (Stage Active) + 10 s (certificate) + 20 s (LDAPS enable) + 15 s (LDAPS disable) = 75 s; ds.directory-data-access-server-enforced-toggle pays 30 s (Stage Active) plus four 10 s data-access transitions = 70 s. Both exceed the 60 s ceiling before any request traffic, and the harness reports exactly "Check timed out after 60.0s" with no exception frame and no response divergence.
Why: a client cannot distinguish "still transitioning" from "settled" at its own polling cadence — it reads Enabling/Creating where AWS would already have settled, so a poll loop with a realistic interval and a realistic overall deadline gives up or mis-reports the resource as stuck. For this suite the consequence is that two whole server-side contracts are ungraded: the LDAPS Enabled/Disabled round trip and the data-access gate with its DirectoryInDesiredStateException, so any regression in either is invisible.
Fix: the ds service's clock-owed transition spans and the chain built on them — the per-feature spans advance_clock materialises, and TRANSITION_SPAN / DIRECTORY_BUILD_SPAN / directory_active_at which they derive from. A settled value must be reachable by a client polling at the intervals these flows use, within the suite's per-check budget; equivalently this is the transition-span contract decision that has to be settled rather than left failing, since zeroing the spans removes the modeled transient values (Requested/Creating/Enabling/Disabling) from the observable surface.
Traces: ds.ldaps-enable-disable-server-enforced, ds.directory-data-access-server-enforced-toggle.

## Steps to Reproduce
1. git_clone(), then run_behavioral_suite(). Both check ids in trace_ids reproduce the cause, each reported as "Check timed out after 60.0s" with nothing graded.
2. LDAPS flow by hand: create a VPC and two subnets in different AZs; POST ds:CreateMicrosoftAD(Name=<x>.example.com, Password=<pattern-compliant>, Edition=Standard, VpcSettings={VpcId,SubnetIds}); poll ds:DescribeDirectories every 30 s until Stage==Active. Observe that the read issued immediately after the create returns Requested and the next 30 s-spaced read returns Active — one full interval is spent on a transition the emulator settles in 3.5 s.
3. Continue: ds:DescribeLDAPSSettings(Type="Client") must report no Enabled entry; ds:RegisterCertificate(Type="ClientLDAPS", CertificateData=<self-signed PEM>) and poll every 10 s until the certificate is terminal — expect "Registered"; ds:EnableLDAPS(Type="Client") and poll every 20 s — expect LDAPSStatus "Enabled"; ds:DisableLDAPS(Type="Client") and poll every 15 s — expect "Disabled". Each poll's first read returns the transient value, so the flow costs 75 s of sleeps and is killed at 60 s.
4. Data-access flow by hand: same create and Active wait, then ds:DescribeDirectoryDataAccess — expect DataAccessStatus "Disabled"; ds:EnableDirectoryDataAccess and poll every 10 s — expect "Enabled"; call ds:EnableDirectoryDataAccess again — expect HTTP 400 DirectoryInDesiredStateException with message "Directory <the DirectoryId sent> is already in the desired state. : RequestId: <the response's request id>" and DataAccessStatus unchanged at "Enabled"; ds:DisableDirectoryDataAccess and poll every 10 s — expect "Disabled"; ds:EnableDirectoryDataAccess and poll every 10 s — expect "Enabled". The four 10 s transitions plus the 30 s Active wait exceed the 60 s budget, so none of these assertions is reached.
5. To localise only (do not keep): set TRANSITION_SPAN and DIRECTORY_BUILD_SPAN in services/service-com-amazonaws-directoryservice-directoryservice-20150416/src/state.rs to zero and replay both checks — they then run on to their assertions, which both confirms the cause and shows its cost (the modeled transient values Requested/Creating/Enabling/Disabling stop being observable).
