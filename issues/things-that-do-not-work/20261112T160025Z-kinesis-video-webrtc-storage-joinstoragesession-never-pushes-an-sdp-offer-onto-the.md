# JoinStorageSession never pushes an SDP_OFFER onto the joined channel's MASTER WSS signaling connection (WSS upgrade now succeeds, the offer does not follow)

> _Note: this issue was identified against the code base at commit `7394251eefd071b8c239bc91125495753c22c75a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
JoinStorageSession

## Description
This issue carries ONE net-new root cause. It is grounded in two failing behavioral checks whose failure point has MOVED since open issue 20261029T194201Z-kinesis-video-webrtc-storage-viewer-joins-always-404.md was filed. That issue's Cause 8 (and open issue 20261109T162245Z-kinesis-video-signaling-the-channel-s-wss-signaling.md) describe the WebSocket UPGRADE being answered HTTP 404, and the replay keys they carry for these two checks are 'run#11|InvalidStatus' / 'run#12|InvalidStatus' — the ws_connect() call itself. In this replay the upgrade is no longer refused: both checks get past ws_connect and now fail later, inside the signaling exchange, with no SDP_OFFER ever arriving. Neither open issue names or carries this failure, so it is filed here as its own root cause; the signaling-push half of Cause 8 is the part that remains unaddressed and the upgrade half appears to have progressed.

Cause 1 of 1: a MASTER peer attached to the channel's WSS signaling endpoint receives no SDP_OFFER after JoinStorageSession returns 200.

AWS: Smithy (services/service-com-amazonaws-kinesisvideowebrtcstorage-awsacuityroutingservicelambda, sdkId 'Kinesis Video WebRTC Storage', restJson1, sigv4): JoinStorageSession POST /joinStorageSession, input channelArn (ChannelArn, @required, @pattern ^arn:(aws[a-zA-Z-]*):kinesisvideo:[a-z0-9-]+:[0-9]+:[a-z]+/[a-zA-Z0-9_.-]+/[0-9]+$), output Unit with HTTP 200, errors AccessDeniedException(403), ClientLimitExceededException(400), InvalidArgumentException(400), ResourceNotFoundException(404). The operation's own model documentation states the contract that is violated here: 'Join the ongoing one way-video and/or multi-way audio WebRTC session as a video producing device for an input channel. If there's no existing session for the channel, a new streaming session needs to be created'; 'Idempotent - This API is not idempotent'; 'Retry behavior - This is counted as a new API call'; and decisively 'Concurrent calls - Concurrent calls are allowed. An offer is sent once per each call.' The offer itself travels on the native Kinesis Video WebRTC signaling protocol, which no Smithy model describes — for the wire shape this is recorded behavior only: the MASTER peer that holds a SigV4-presigned WebSocket (query parameter X-Amz-ChannelARN) to the ResourceEndpoint returned by kinesisvideo GetSignalingChannelEndpoint(SingleMasterChannelEndpointConfiguration={Protocols:['WSS'],Role:'MASTER'}) receives, within seconds of each JoinStorageSession call, a JSON signaling message with messageType='SDP_OFFER' and a non-empty base64 messagePayload. That payload base64-decodes to a JSON description envelope {"type":"offer","sdp":"..."} whose sdp is a real RFC 4566 session description: it begins with the 'v=0' version line and carries at least one 'm=' media line (for WebRTC ingestion, H.264 video and Opus audio tracks). Because the API is explicitly not idempotent and sends one offer per call, N successive JoinStorageSession calls on the same channel produce N distinct SDP_OFFER messages, each with its own payload (distinct session/SDP state), never one deduplicated copy.

Emulator: JoinStorageSession is answered HTTP 200 with an empty body (the call does not fail), and the WSS signaling connection is established, but nothing is ever pushed down it. In webrtc-signaling-sdp-offer-round-trip the check drains the socket for a bounded 30 seconds after the join and receives no SDP_OFFER at all — 'AssertionError: storage session never pushed an SDP_OFFER within 30s of JoinStorageSession' (message is None, i.e. not a wrong messageType, not an empty payload: no message of that type arrived). In join-storage-session-repeated-calls-not-deduplicated the first join likewise yields nothing — 'AssertionError: expected an SDP_OFFER pushed for the first join, got {}' — the empty dict being the check's initial value, meaning the 30-second recv window lapsed with no frame received at all, so the second-call/distinct-payload assertions are never even reached. The 200-with-empty-body response is therefore indistinguishable from a stub that records nothing.

Why: a client relying on AWS's behavior deadlocks. The WebRTC ingestion handshake is offer-driven: the video producing device joins, then waits on its signaling channel for the storage session's SDP offer so it can answer and start sending media. With no offer the device waits forever (or times out) and no media is ever ingested into the linked Kinesis video stream, while the control plane reports the channel ACTIVE and storage ENABLED and the join returns 200. Nothing in the API surface tells the caller the session is non-functional, so an integration cannot distinguish a working backend from this one until playback silently yields no fragments. The per-call non-idempotency is also unobservable, so a client cannot verify that a retried join opened a fresh negotiation rather than being coalesced.

Fix: the JoinStorageSession handler's session-establishment step together with the signaling fan-out in this crate's state — services/service-com-amazonaws-kinesisvideowebrtcstorage-awsacuityroutingservicelambda/src/ops/join_storage_session.rs and src/state.rs. On each call the handler must create (or add a producer to) the channel's storage session and emit exactly one SDP_OFFER signaling message, with a freshly generated offer per call, onto every MASTER signaling connection currently attached to that channel; the WSS signaling route must deliver it to the attached peer. The offer's messagePayload must be base64 of a {"type":"offer","sdp":...} envelope whose sdp is a well-formed RFC 4566 description ('v=0' session line plus media 'm=' lines), not a placeholder.

Traces: kinesis-video-webrtc-storage.webrtc-signaling-sdp-offer-round-trip (no SDP_OFFER within 30s), kinesis-video-webrtc-storage.join-storage-session-repeated-calls-not-deduplicated (no SDP_OFFER for the first join, so the two-independent-offers contract is untestable).

## Steps to Reproduce
Boot the emulator from this checkout. With a kinesisvideo client and a kinesis-video-webrtc-storage client:

1. kv.create_signaling_channel(ChannelName=C, ChannelType='SINGLE_MASTER') and kv.create_stream(StreamName=S, DataRetentionInHours=1); poll describe_signaling_channel / describe_stream until both report ACTIVE.
2. kv.update_media_storage_configuration(ChannelARN=<chan>, MediaStorageConfiguration={'StreamARN': <stream>, 'Status': 'ENABLED'}).
3. wss_endpoint = kv.get_signaling_channel_endpoint(ChannelARN=<chan>, SingleMasterChannelEndpointConfiguration={'Protocols': ['WSS'], 'Role': 'MASTER'})['ResourceEndpointList'][0]['ResourceEndpoint'].
4. SigV4-presign that URL (service name 'kinesisvideo', GET, query parameter X-Amz-ChannelARN=<chan>) and open a WebSocket to it. The upgrade now completes (HTTP 101).
5. webrtc_endpoint = kv.get_signaling_channel_endpoint(ChannelARN=<chan>, SingleMasterChannelEndpointConfiguration={'Protocols': ['WEBRTC'], 'Role': 'MASTER'})['ResourceEndpointList'][0]['ResourceEndpoint']; build a kinesis-video-webrtc-storage client against it.
6. With the socket still open, call join_storage_session(channelArn=<chan>) and drain the socket for up to 30 seconds looking for a frame with messageType='SDP_OFFER'.
   Observed: the join returns HTTP 200 with an empty body and NO frame is ever received. Expected on AWS: exactly one SDP_OFFER frame with a non-empty base64 messagePayload; base64-decoding it yields {'type': 'offer', 'sdp': ...} whose sdp starts with 'v=0' and contains an 'm=' line.
7. Call join_storage_session(channelArn=<chan>) a SECOND time on the same open socket and drain again. Expected on AWS: a second, independent SDP_OFFER whose messagePayload differs from the first (the API is documented not idempotent, one offer per call). Observed: again no frame at all.
