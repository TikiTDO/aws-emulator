=== Cause 1 of 4: the dead-letter event's ERROR_CODE reports the SDK exception shape name ('AccessDeniedException') instead of the target service's wire error code ('AccessDenied') ===
Failing check: scheduler.schedule-dead-letter-queue-receives-failed-invocation

AWS: Smithy (com.amazonaws.scheduler) — Target.RoleArn is required, @pattern ^arn:aws(-[a-z]+)?:iam::\d{12}:role\/[\w+=,.@\/-]+$, documented "The Amazon Resource Name (ARN) of the IAM role that EventBridge Scheduler will use for this target when the schedule is invoked"; Target.DeadLetterConfig -> DeadLetterConfig.Arn @pattern ^arn:aws(-[a-z]+)?:sqs:[a-z0-9\-]+:\d{12}:[a-zA-Z0-9\-_]+$ @length 1..1600, "EventBridge Scheduler delivers failed events that could not be successfully delivered to a target to the queue". The model does not describe the dead-letter envelope, so: recorded behavior only — the dead-letter message carries an SQS message attribute ERROR_CODE whose StringValue is the ERROR CODE THE TARGET API RETURNED on the wire, not the name of an SDK exception class. For an SQS SendMessage refused because the execution role has no sqs:SendMessage on the target queue, that code is the fixed string `AccessDenied`. The same rule is corroborated inside this corpus by the sibling case in Cause 2, where the recorded code for a SendMessage to a queue that does not exist is the fixed string `AWS.SimpleQueueService.NonExistentQueue`. ERROR_CODE's value is fixed text per failure class — nothing in it is taken from the request or from emulator state.
Emulator: the dead-letter event arrives, but ERROR_CODE.StringValue is 'AccessDeniedException' — the modelled exception SHAPE name, with the 'Exception' suffix appended. Replay: "AssertionError: expected the dead-letter event to record the role's missing sqs:SendMessage permission on the target queue as ERROR_CODE='AccessDenied', got 'AccessDeniedException'".
Why: ERROR_CODE is the machine-readable failure classification a client keys its DLQ consumers, alarms and redrive logic on. Code strings are matched exactly, so a consumer written against AWS ('AccessDenied', 'AWS.SimpleQueueService.NonExistentQueue') routes every emulator event to its unknown/default branch, and a consumer written against the emulator silently stops matching in AWS. It also mislabels the class: 'AccessDeniedException' is an SDK exception name, which is not a value AWS ever puts on this attribute.
Fix: the delivery-failure path of the dispatch component that builds the dead-letter message — the mapping from a failed target call to the ERROR_CODE message attribute. It must carry the target API's wire error code verbatim, not the Rust/SDK error variant or shape name (no 'Exception' suffix synthesis).

=== Cause 2 of 4: the dead-letter event Body is not the attempted target request — it has no MessageBody/QueueUrl members at all ===
Failing check: scheduler.server-side-dead-letter-queue-receives-failed-event-payload

AWS: recorded behavior only (the Smithy model describes Target.Input — @length min 1, "The text, or well-formed JSON, passed to the target" — but not the dead-letter envelope). For an SQS target, the dead-letter message Body is a JSON object describing the SendMessage request Scheduler attempted: its `MessageBody` member is the occurrence's Target.Input byte-for-byte, and its `QueueUrl` member names the target queue the call was aimed at. The recorded response for this case also carries message attributes ERROR_CODE = `AWS.SimpleQueueService.NonExistentQueue` (fixed text for the failure class) and RETRY_ATTEMPTS = `0` when Target.RetryPolicy.MaximumRetryAttempts is 0 (a value derived from the attempts actually made). The member NAMES and the ERROR_CODE string are the requirement; the queue name and the input string in any one run are values taken from the request.
Emulator: the dead-letter message arrives but its Body, parsed as JSON, has no 'MessageBody' key, so the check dies with "KeyError: 'MessageBody'" at the first assertion that reads the envelope (and therefore never reaches the 'QueueUrl', ERROR_CODE or RETRY_ATTEMPTS assertions). Hypothesis: the emulator writes the raw Target.Input as the Body, which is what the companion finding under the scheduler__sqs token reports for the same envelope.
Why: the dead-letter Body is the only record of WHAT work was lost and WHERE it was headed. A client's DLQ consumer parses MessageBody to replay the payload and QueueUrl to decide where to replay it; against the emulator both lookups raise, so no redrive tooling written for AWS can consume an emulator dead-letter event, and tooling written against the emulator breaks on AWS.
Fix: the dead-letter envelope serializer in the dispatch component — it must emit the attempted target request as the Body (for an SQS target: {"QueueUrl": <target queue url>, "MessageBody": <Target.Input unchanged>, plus the other SendMessage parameters it sent}) rather than the bare Target.Input.

=== Cause 3 of 4: the EXHAUSTED_RETRY_CONDITION message attribute is never emitted, so the bound that ended the retries is never reported ===
Failing checks: scheduler.server-side-retry-policy-exhaustion-triggers-dlq, scheduler.scheduler-retry-exhaustion-condition-reported-only-for-event-age-bound

AWS: Smithy (com.amazonaws.scheduler) — Target.RetryPolicy -> RetryPolicy{MaximumEventAgeInSeconds @range 60..86400 "The maximum amount of time, in seconds, to continue to make retry attempts", MaximumRetryAttempts @range 0..185 "The maximum number of retry attempts to make before the request fails. Retry attempts with exponential backoff continue until either the maximum number of attempts is made or until the duration of the MaximumEventAgeInSeconds is reached."}. Recorded behavior only for the envelope: when retrying actually ENDS because one of those two bounds was reached, the dead-letter message carries an EXHAUSTED_RETRY_CONDITION attribute naming WHICH bound ended it, as the fixed member name of the bound that was hit — `MaximumEventAgeInSeconds` or `MaximumRetryAttempts`. The attribute is CONDITIONAL: when the target fails permanently on its very first attempt nothing is ever retried, no bound is exhausted, and the attribute is ABSENT (that arm reports RETRY_ATTEMPTS = 0). The two checks pin both sides of that rule on identical failing wiring: the arm configured MaximumRetryAttempts=185 / MaximumEventAgeInSeconds=60 must report EXHAUSTED_RETRY_CONDITION='MaximumEventAgeInSeconds' with RETRY_ATTEMPTS strictly below 185, while the arm configured MaximumRetryAttempts=1 / MaximumEventAgeInSeconds=86400 must carry NO EXHAUSTED_RETRY_CONDITION at all.
Emulator: the attribute is never present on any dead-letter event. Both checks get past SCHEDULE_ARN, ERROR_CODE and RETRY_ATTEMPTS and then die with "KeyError: 'EXHAUSTED_RETRY_CONDITION'" — in server-side-retry-policy-exhaustion-triggers-dlq at attrs["EXHAUSTED_RETRY_CONDITION"]["StringValue"], and in scheduler-retry-exhaustion-condition-reported-only-for-event-age-bound at the age-capped arm's read of the same attribute. Because it is absent everywhere, the emulator also cannot be distinguished on the conditional half of the rule (an implementation that always emitted it would diverge on the attempt-capped arm instead).
Why: without this attribute a client cannot tell a target that was genuinely retried until a policy bound was reached from one that was abandoned on its first failure — which is exactly the difference between 'raise MaximumRetryAttempts' and 'fix the target or the role' as a remediation. Retry-exhaustion dashboards and alarms keyed on EXHAUSTED_RETRY_CONDITION never fire, and a client tuning RetryPolicy against the emulator gets no feedback on which bound is binding.
Fix: the retry/exhaustion bookkeeping in the dispatch component that builds the dead-letter envelope. It must track which bound terminated the retry loop and set EXHAUSTED_RETRY_CONDITION to that bound's member name, and must OMIT the attribute entirely when no retry was performed (a permanent first-attempt failure), consistently with the RETRY_ATTEMPTS it reports.

=== Cause 4 of 4: no AWS/Scheduler CloudWatch metric is ever published — InvocationAttemptCount, TargetErrorCount, InvocationDroppedCount and InvocationsSentToDeadLetterCount all read 0 after observed occurrences ===
Failing check: scheduler.scheduler-invocation-attempt-count-metric-counts-every-retry

AWS: recorded behavior only (these are CloudWatch series, not Smithy shapes) — EventBridge Scheduler publishes per-invocation metrics in the `AWS/Scheduler` namespace, dimensioned by ScheduleGroup: InvocationAttemptCount (one datapoint per delivery attempt), TargetErrorCount (a failed target call), InvocationDroppedCount (an occurrence given up on) and InvocationsSentToDeadLetterCount (an event written to the DLQ). On the wiring the check builds — one healthy one-time schedule in its own group and one permanently denied one-time schedule in another, both with MaximumRetryAttempts=2 and MaximumEventAgeInSeconds=900 — the recorded sums are: healthy group attempts=1, target errors=0, dropped=0; denied group attempts=1 (an AccessDenied-class failure is permanent and is NOT retried, so the configured cap of 2 does not raise it), target errors=1, dropped=1, dead-lettered=1. The counts follow from the occurrences, which the check has already independently confirmed at their destinations (the healthy target received the body, the denied arm's dead-letter event arrived) before reading CloudWatch.
Emulator: every series is empty. After 420 s of polling GetMetricStatistics the last observation is {'ok': {'InvocationAttemptCount': 0.0, 'TargetErrorCount': 0.0, 'InvocationDroppedCount': 0.0}, 'err': {'InvocationAttemptCount': 0.0, 'TargetErrorCount': 0.0, 'InvocationDroppedCount': 0.0, 'InvocationsSentToDeadLetterCount': 0.0}} — i.e. the dispatcher delivered and dead-lettered but published no datapoint for either outcome, so not even the attempt counter reaches 1.
Why: AWS/Scheduler metrics are the only aggregate, side-channel view of whether schedules are firing and failing; they are what operators alarm on (TargetErrorCount/InvocationsSentToDeadLetterCount > 0) and what capacity and retry budgets are sized from. With the namespace permanently empty, every such alarm evaluates as INSUFFICIENT_DATA/OK on the emulator and a failing fleet of schedules looks identical to a healthy one, so no monitoring configuration can be validated before it reaches AWS.
Fix: the dispatch/occurrence component of the scheduler crate must emit CloudWatch datapoints in the AWS/Scheduler namespace with the ScheduleGroup dimension as each occurrence is processed: one InvocationAttemptCount per attempt actually made, TargetErrorCount on a failed target call, InvocationDroppedCount when the occurrence is abandoned, and InvocationsSentToDeadLetterCount when it writes the dead-letter event (the counts must follow the attempts actually made, not the configured RetryPolicy cap).

Traces (examples, one run's names and ids are not requirements): scheduler.schedule-dead-letter-queue-receives-failed-invocation (Cause 1), scheduler.server-side-dead-letter-queue-receives-failed-event-payload (Cause 2), scheduler.server-side-retry-policy-exhaustion-triggers-dlq and scheduler.scheduler-retry-exhaustion-condition-reported-only-for-event-age-bound (Cause 3), scheduler.scheduler-invocation-attempt-count-metric-counts-every-retry (Cause 4).
