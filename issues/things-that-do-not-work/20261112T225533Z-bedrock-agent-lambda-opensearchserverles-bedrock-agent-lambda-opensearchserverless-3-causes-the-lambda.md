# bedrock-agent__lambda__opensearchserverless: 3 causes — the Lambda sandbox refuses the AOSS collectionEndpoint the emulator itself published ('addresses no service this emulator serves'), a collection with no network policy still serves its data plane, and the KB field-mapping end-to-end path never converges

## Operation
Invoke

## Description
THREE root causes grounded in four failing behavioral checks listed under the `bedrock-agent__lambda__opensearchserverless` suite heading. None of the four was marked ALREADY FILED or OWNED in this replay.

Shared model context: the AOSS collection data plane is not Smithy-modeled. Smithy (com.amazonaws.opensearchserverless) documents CollectionDetail.collectionEndpoint as the 'Collection-specific endpoint used to submit index, search, and data upload requests to an OpenSearch Serverless collection'; BatchGetCollection is the read that publishes it, and CreateSecurityPolicy(type: SecurityPolicyType, name, policy — required, @length 1..20480) is the modeled writer that configures network admission. Lambda's Invoke is modeled by com.amazonaws.lambda. The data plane's own wire behavior is recorded behavior only.

=== Cause 1 of 3: a Lambda function cannot reach the AOSS collectionEndpoint the emulator published — the sandbox's own egress resolver refuses that address ===
Failing checks: bedrock-agent__lambda__opensearchserverless.lambda-opensearchserverless-data-plane-search-positive, bedrock-agent__lambda__opensearchserverless.lambda-opensearchserverless-data-plane-access-denied-negative
AWS: recorded behavior only for the data plane; on AWS a Lambda function that holds aoss:APIAccessAll and is admitted by the collection's data access and network policies reaches the collectionEndpoint read from BatchGetCollection and gets an ordinary OpenSearch answer — a write receipt (`result: created`) for `PUT /<index>/_doc/<id>` and a hits document for `_search`, and a policy denial arrives as an HTTP 403 OpenSearch error document, never as a name-resolution failure. The requirement is that the host published in collectionEndpoint is reachable from inside the emulator's own Lambda sandbox and answers the collection's data plane.
Emulator: the handler's HTTPS request to the published endpoint dies in the sandbox's address resolver before any request is sent. The invocation returns an unhandled `gaierror` whose errorMessage is `<the published collectionEndpoint URL> addresses no service this emulator serves: sqs, events, eventbridge, dynamodb, logs, cloudwatchlogs, cloudwatch, apigateway, secretsmanager, ssm, opensearch, es, stepfunctions, sfn, sesv2, s3, xray, rds-data, appconfigdata, appconfig, config, configservice, codedeploy, cloudfront`, raised from `urllib.request.urlopen` -> `http/client.py getresponse` -> `socket.gaierror`. The emulator thus publishes a collection endpoint address it then refuses to route for its own in-sandbox clients: the served-service list has entries for `opensearch`/`es` but nothing that matches the aoss collection endpoint, so BOTH the positive search path and the negative access-denied path fail on the same wall — the denial under test is never reached because no request ever leaves the sandbox.
Why: every realistic AOSS consumer is server-side code (a Lambda indexer, an ingestion worker). Such code cannot talk to the collection at all, and the failure it sees is a DNS/`gaierror` rather than any AWS status — so a client cannot distinguish 'collection unreachable' from 'permission denied', retry logic keyed on 403 never runs, and no data-plane behavior behind the endpoint is testable from a function.
Related open issue (named, different symptom): 20261109T154357Z-bedrock-agent-lambda-opensearchserverles-bedrock-agent-lambda-opensearchserverless-the-published-aoss-collectionendpoint.md reports the published endpoint being the real AWS host `<id>.<region>.aoss.amazonaws.com`. Here the published endpoint is an emulator-local `https://127.0.0.1:<port>/...` address and it is the Lambda sandbox's egress resolver that refuses it, so the fix needed is in the sandbox's routing table, not only in endpoint publication.
Fix: the Lambda sandbox's outbound address resolution/routing component (the layer that maps a hostname or host:port a handler dials onto an emulated service) must route the AOSS collection data-plane endpoint published by BatchGetCollection to the opensearchserverless crate's data-plane listener, so a handler's HTTPS request to collectionEndpoint is served instead of refused.

=== Cause 2 of 3: an ACTIVE collection with NO network policy still serves every data-plane request ===
Failing check: bedrock-agent__lambda__opensearchserverless.bedrock-kb-opensearchserverless-network-policy-missing-negative
AWS: recorded behavior only (the data plane is unmodeled); network admission is configured by the modeled CreateSecurityPolicy(type='network'). Recorded: a collection that is ACTIVE with encryption and data access policies but NO matching network policy refuses every data-plane request at the proxy layer with HTTP 401, surfaced by opensearch-py as `AuthenticationException` with `status_code == 401` — not a socket timeout and not a connection refusal — and the index the refused create addressed does not exist afterwards. Creating ONLY the network policy, with everything else unchanged, then makes the identical index create succeed and a knowledge base on that collection and index reach ACTIVE. The 401 status and the fact that no state is created by the refused call are the requirement; collection, index and VPC-endpoint ids are request/state values.
Emulator: the request is served. `indices.create` against the published endpoint raises nothing at all although no network policy exists, so the check fails at `assert raised is not None, "expected the request to fail without a matching network policy"` — the emulator produced a successful index create under a configuration AWS refuses outright.
Why: the network policy is the collection's network boundary. A client or compliance control that has not yet created one (or that intentionally leaves one out to keep a collection unreachable) believes the data plane is closed while the emulator serves every signed request, and nothing in any response distinguishes the open configuration from the closed one.
Related open issue (named, different service token): 20261108T223024Z-opensearchserverless-3-net-new-causes-on-the-collection.md Cause 2 describes network policies not being enforced when a policy is NARROWED or DELETED; this cause is the never-created case and is grounded in a check the suite lists under a different service heading, so it is filed here.
Fix: the collection data-plane request handler in the opensearchserverless service crate — before authorization it must resolve the network security policies matching the target collection and refuse a request that matches NO network policy (and one arriving from outside every admitted SourceVPCE) with HTTP 401, driven by the policy state the control plane holds.

=== Cause 3 of 3: the knowledge-base field-mapping end-to-end path never converges, so the check is killed by its budget ===
Failing check: bedrock-agent__lambda__opensearchserverless.bedrock-kb-opensearchserverless-field-mapping-positive
AWS: recorded behavior only for the end-to-end sequence; each stage is a modeled operation that CONVERGES: BatchGetCollection reports the collection ACTIVE, BatchGetVpcEndpoint reports the endpoint ACTIVE, GetKnowledgeBase reports ACTIVE, GetIngestionJob reaches the terminal status COMPLETE, and a `match_all` search on the configured index then returns at least one hit whose `_source` carries the CONFIGURED field names — the vector field with exactly the configured dimension, the text field carrying the source document's content, and the metadata field referencing the source S3 object. The requirement is that the pipeline reaches those terminal states and that the honored field names are the ones configured in the knowledge base's vector field mapping (not hardcoded `vector`/`text`/`metadata`).
Emulator: no stage ever reaches its terminal state within the check's budget — the suite reports `Error: Check timed out after 60.0s`, i.e. the check was killed while polling and produced no observation of the field mapping at all. Every poll in this check is bounded and each has a terminal predicate, so a timeout means some stage stayed non-terminal indefinitely rather than answering wrongly.
Why: a client that waits on these statuses waits forever. An ingestion-to-search pipeline built on the emulator can never be exercised end to end, and the honoring of a custom vector/text/metadata field mapping — the whole contract between a knowledge base and the collection's index — is unobservable.
Related open issue (named, different grounding): 20261105T040349Z-bedrock-agent-lambda-opensearchserverles-bedrock-agent-lambda-opensearchserverless-the-retrieveandgenerate-end-to.md reports the RetrieveAndGenerate end-to-end path stalling on the AOSS collection; this check stalls on the ingestion-and-search path with a CUSTOM field mapping and was not marked owned.
Fix: whichever stage of the knowledge-base pipeline fails to settle — the bedrock-agent crate's knowledge-base/data-source/ingestion-job state progression (CreateKnowledgeBase -> ACTIVE, StartIngestionJob -> COMPLETE) and the write of the ingested document into the collection index under the configured field names — must advance to its terminal state and write the configured fields, instead of leaving pollers to exhaust their budgets.

Traces (examples): Cause 1 — lambda-opensearchserverless-data-plane-search-positive, lambda-opensearchserverless-data-plane-access-denied-negative. Cause 2 — bedrock-kb-opensearchserverless-network-policy-missing-negative. Cause 3 — bedrock-kb-opensearchserverless-field-mapping-positive.

## Steps to Reproduce
Cause 1 (Lambda cannot reach the published collectionEndpoint):
1. Create an AOSS encryption policy, a network policy admitting the caller, and a data access policy whose Principal is the Lambda function's execution role; create_collection(type='SEARCH'|'VECTORSEARCH') and poll batch_get_collection until ACTIVE; read collectionDetails[0].collectionEndpoint.
2. Create a Lambda function whose execution role holds aoss:APIAccessAll, passing that collectionEndpoint to the handler in its environment. The handler SigV4-signs (service name 'aoss') and issues `PUT <endpoint>/<index>/_doc/<id>` with urllib.
3. lambda.Invoke the function.
   -> EXPECTED: the response payload carries the OpenSearch write receipt (or a 403 OpenSearch error document when the policy denies it).
   -> ACTUAL: the payload is an unhandled `gaierror` whose message is '<endpoint URL> addresses no service this emulator serves: sqs, events, ... cloudfront' — the sandbox refuses the address the emulator itself published.

Cause 2 (no network policy still serves):
1. create_security_policy(type='encryption', ...) for collection/<name>; create_vpc_endpoint and wait ACTIVE; create_access_policy(type='data', ...) granting the caller and the KB role index/document permissions. Create NO network policy.
2. create_collection(name=<name>, type='VECTORSEARCH'); poll batch_get_collection until ACTIVE; read collectionEndpoint.
3. With an aoss-signed opensearch-py client, call indices.create(index=<ix>, body=<knn mapping>).
   -> EXPECTED: opensearchpy AuthenticationException with status_code 401, and the index does not exist (HEAD /<ix> is false).
   -> ACTUAL: the create succeeds.
4. Then create_security_policy(type='network', ..., AllowFromPublic=false, SourceVPCEs=[<vpce>]) and repeat: the create must now succeed and a knowledge base on that collection/index must reach ACTIVE.

Cause 3 (field-mapping end-to-end never converges):
1. Same AOSS setup as Cause 2 but WITH a network policy; create a vector index whose knn_vector/text/metadata fields use deliberately non-default names (e.g. a 1536-dim vector field, a text field and a metadata field) and wait until HEAD /<index> is true.
2. bedrock-agent.CreateKnowledgeBase with an OPENSEARCH_SERVERLESS storage configuration whose fieldMapping names exactly those three fields; poll GetKnowledgeBase for ACTIVE.
3. Put a text object in an S3 bucket, CreateDataSource(type=S3) on it, StartIngestionJob and poll GetIngestionJob for COMPLETE.
4. Search the index with {"query": {"match_all": {}}} and read hits[0]._source.
   -> EXPECTED: every stage reaches its terminal state and _source carries the configured vector (exactly the configured dimension, all numeric), text (the source content) and metadata (referencing the S3 object) field names.
   -> ACTUAL: the polls never terminate and the check is killed by its budget.
