# CodeCommit pull-request comment operations refuse a missing pull request as a missing repository, and GetBlobDifferences borrows GetBlob's blob-id message (3 causes)

> _Note: this issue was identified against the code base at commit `109a38b6a58a7a1a061f30f160f2510a3720b32a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetCommentsForPullRequest

## Description
THREE net-new causes on codecommit error paths, sharing one fault: the handler picks the WRONG error identity for the condition it met — twice because it resolves the repository before the pull request and reports the repository's absence instead of the pull request's, and once because it answers a sibling operation's message template. A fixer must close ALL THREE causes before submitting.

=== Cause 1 of 3: GetCommentsForPullRequest reports a nonexistent pull request as RepositoryDoesNotExistException ===
AWS: Smithy com.amazonaws.codecommit#GetCommentsForPullRequest takes pullRequestId as the only @required member (PullRequestId); repositoryName is OPTIONAL (RepositoryName, @length 1..100, @pattern ^[\w\.-]+$), because the pull request id is the operation's primary key and the repository is only a filter. The operation models both PullRequestDoesNotExistException and RepositoryDoesNotExistException (both errorKind client, httpError 400 [defaulted], single `message` member). The model does not state wire text (PullRequestDoesNotExistException's doc is only 'The pull request ID could not be found. Make sure that you have specified the correct repository name and pull request ID, and then try again.'), so recorded behavior supplies it: a request naming a pull request id that does not exist is refused 400 with $.__type 'PullRequestDoesNotExistException' and message 'The pull request ID does not exist. Verify that you provided a valid pull request ID, and then try your operation again. To get a list of pull request IDs, use ListPullRequests.' — that message is ENTIRELY fixed text; AWS interpolates neither the pull request id, the repository name nor the account id. The precedence is the requirement: the pull-request lookup happens FIRST, so an unknown pull request id is reported as such whatever the (optional) repositoryName names.
Emulator: the same status (400) but $.__type 'RepositoryDoesNotExistException' and the repository-absence message 'sim2real-probe-codecommit-prcmt-get-missing-repo-161bb20c for 000000000000' — i.e. the crate-shared repository_does_not_exist_message template '<repositoryName> for <accountId>' (fixed text ' for ' with the requested repository name and the caller's account id as its two variable parts). That template is AWS's wording for the repository error, so the message is not itself wrong — the handler simply resolved the repository first and reported that error instead of the pull-request one.
Why: the error CODE is what clients dispatch on. A caller polling a pull request's comments after a merge, or a tool that resolves pull request ids it was handed, must distinguish 'that pull request id is gone' (stop, or re-list with ListPullRequests, as AWS's message directs) from 'that repository is gone' (a different, account-level failure). Against the emulator the first condition is indistinguishable from the second, so retry/compensation logic keyed on PullRequestDoesNotExistException never fires, and a caller that omits repositoryName altogether can still be told a repository does not exist — an error about a member it never sent.
Fix: the existence-check ORDER in the GetCommentsForPullRequest handler's validation (services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/get_comments_for_pull_request.rs): resolve pullRequestId first and raise PullRequestDoesNotExistException with AWS's fixed three-sentence text; consult repositoryName only after the pull request resolved, and keep RepositoryDoesNotExistException (with the existing '<name> for <account>' wording) for the case where the pull request exists and the named repository does not.
Traces: codecommit-get-comments-for-pull-request-error-paths#task#5.

=== Cause 2 of 3: PostCommentForPullRequest has the same inverted precedence ===
AWS: Smithy PostCommentForPullRequest requires pullRequestId, repositoryName, beforeCommitId, afterCommitId and content, and models PullRequestDoesNotExistException and RepositoryDoesNotExistException alongside each other (both client, httpError 400 [defaulted]). Recorded behavior: a write aimed at a pull request id that does not exist is refused 400 with $.__type 'PullRequestDoesNotExistException' and the same entirely-fixed message 'The pull request ID does not exist. Verify that you provided a valid pull request ID, and then try your operation again. To get a list of pull request IDs, use ListPullRequests.' — the pull-request lookup precedes the repository lookup on the write path exactly as it does on the read path.
Emulator: 400 with $.__type 'RepositoryDoesNotExistException' and the repository template's output ('<repositoryName> for <accountId>'), the same substitution as Cause 1 — a separate handler, so fixing Cause 1 alone leaves this one diverging.
Why: this is the error a review bot meets when it tries to comment on a pull request that was deleted or never existed. Dispatching on RepositoryDoesNotExistException instead of PullRequestDoesNotExistException makes a transient-looking, account-level failure out of a permanent, per-pull-request one, so the bot abandons the whole repository rather than that one pull request.
Fix: the same ordering change in the PostCommentForPullRequest handler's validation (src/ops/post_comment_for_pull_request.rs) — pull-request resolution before repository resolution; ideally both handlers share one 'resolve the pull request, then the repository' helper so the two cannot drift apart again.
Traces: codecommit-post-comment-for-pull-request-error-paths#task#4.

=== Cause 3 of 3: GetBlobDifferences' BlobIdDoesNotExistException carries GetBlob's id-naming sentence instead of its own fixed one ===
AWS: Smithy GetBlobDifferences takes repositoryName and afterBlobId (@required, ObjectId) plus an optional beforeBlobId, and models BlobIdDoesNotExistException (client, httpError 400 [defaulted]); the shape's doc is only 'The specified blob does not exist.', so recorded behavior supplies the wire text. For a well-formed git object id that the repository does not hold, GetBlobDifferences answers 400 BlobIdDoesNotExistException with 'The specified blob does not exist in the repository.' — that sentence is ENTIRELY fixed text: this operation interpolates NO value, neither the rejected blob id nor the repository name.
Emulator: the same status (400) and the same error code, but the message 'AWS CodeCommit could not find the blob <blobId> in the repository.' — the template AWS uses for GetBlob ('AWS CodeCommit could not find the blob ' + the requested blob id + ' in the repository.'), applied here to a sibling operation that does not word the refusal that way.
Why: the two operations word one error code differently on AWS, and a client or test asserting the comparison path's sentence never matches. CRITICALLY, this is the mirror image of an already-open finding: behavioral issue 20261109T165809Z-codecommit-getblob-s-blobiddoesnotexistexception-message-is-an-emulator.md requires the id-NAMING template for GetBlob (where the emulator currently emits the fixed sentence). So the fix is not 'one message for both' in either direction — the two templates must COEXIST, keyed by operation: GetBlob names the blob id, GetBlobDifferences does not. No open issue carries this step's replay key.
Fix: the BlobIdDoesNotExistException construction on the blob-resolution path of the GetBlobDifferences handler (src/ops/get_blob_differences.rs) and the shared blob-absence message helper it calls — give this operation its own fixed sentence while leaving the id-naming template available to GetBlob.
Traces: codecommit-blob-differences-error-paths#task#5 (representative; the cluster also covers codecommit-get-blob-differences-errors#task#4).
