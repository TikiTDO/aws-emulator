# kafka: 4 net-new causes — CreateConfiguration's per-property refusal Message is compact JSON with a request-scoped version list, DescribeTopicPartitions' malformed-ARN AccessDenied message is reworded and un-encoded, and the Express-channel and Replicator sequences reach no verdict

## Description
Four net-new root causes in the kafka (MSK) service survive every ALREADY-FILED / OWNED filter in this replay. They are bundled here because they share one service; a fixer must close all four before submitting.

=== Cause 1 of 4: CreateConfiguration's per-property BadRequestException Message is serialized as compact JSON, and its "Key checked against versions" list is scoped to the request's KafkaVersions ===
AWS: Smithy (com.amazonaws.kafka#Kafka) CreateConfiguration POST /v1/configurations, 200; input Name (required), ServerProperties (required blob), KafkaVersions (list), Description; modeled errors BadRequestException 400, ConflictException 409, ForbiddenException 403, UnauthorizedException 401, TooManyRequestsException 429, InternalServerErrorException 500, ServiceUnavailableException 503. The model does not state the refusal text, so the message is recorded behavior only: MSK refuses a ServerProperties document containing a key it does not accept with 400 BadRequestException whose Message is a Jackson PRETTY-PRINTED JSON array of per-property objects. Its fixed text is the layout and the sentence:
  line 1: `[ {`
  line 2: `  "name" : "<key>",`
  line 3: `  "value" : "<value>",`
  line 4: `  "errorMessages" : [ "Key '<key>' is not supported by at least one Apache Kafka version. Key checked against versions: [<versions>]" ]`
  line 5: `} ]`
i.e. newline-separated, two-space indented, a SPACE on each side of every `:` and inside every `[`/`]`/`{`/`}` bracket pair. Its variable parts are <key> and <value>, taken from the offending line of the request's ServerProperties (for a line with no `=`, MSK reads the text up to the first space as the key and the remainder as the value), and <versions>, the comma-separated set of Kafka versions MSK itself checked the key against — a property of MSK's catalog, NOT of the request. No value-type, value-range or value-enum validation exists on this API at all: legal keys with ill-typed values (num.partitions=not-a-number, num.partitions=-5, auto.create.topics.enable=maybe, compression.type=bogus) are accepted and stored byte-identical in revision 1. Keys MSK reserves (broker.id) and keys unknown to Kafka are refused through the same envelope. In every refusal case nothing is created: the name must not appear in ListConfigurations, and an unrelated control configuration must stay ACTIVE at revision 1 and still advance to revision 2 on a later UpdateConfiguration.
Emulator: the code (BadRequestException) and the status (400) are right and the sentence is right, but the envelope is emitted with Python/serde COMPACT separators — one line, no indentation, no spaces around `:` or inside brackets, e.g. `[{"name":"broker.id","value":"7","errorMessages":["Key 'broker.id' is not supported by at least one Apache Kafka version. Key checked against versions: [3.6.0]"]}]` and `[{"name":"this","value":"line has no equals sign and is not valid java properties syntax","errorMessages":[...]}]`. Separately, the <versions> list is taken from the REQUEST: a request carrying KafkaVersions=["3.6.0"] yields `Key checked against versions: [3.6.0]` and KafkaVersions=["3.9.x"] yields `[3.9.x]`, while the request that omits KafkaVersions prints the whole catalog — so the emulator reports which versions the CALLER named, not which versions the service checked.
Why: a client that surfaces or parses this Message cannot reproduce AWS's output. Operators and tooling that diff MSK's refusal text, and any consumer that splits the envelope on its documented layout, see a differently shaped document; and because the version list is request-scoped, a caller who pins one KafkaVersion is told the key was checked against only that version, which misstates why the key was refused.
Fix: the CreateConfiguration handler's ServerProperties validation and the serializer that renders its per-property refusal envelope in the kafka service — render the array with AWS's pretty-printed Jackson layout and source the checked-version list from the service's own Kafka-version catalog rather than from the request's KafkaVersions. Related OPEN issue, which does not cover this (it covers the earlier state where these four inputs were accepted and minted rather than refused): 20261029T175822Z-kafka-createconfiguration-performs-no-serverproperties-or-name-validation-four.md. Also neighbouring but distinct (KafkaVersions value list, not ServerProperties): 20261103T090515Z-kafka-createconfiguration-s-unsupported-kafkaversion-refusal-renders-the-wrong.md.
Traces: kafka.configuration-invalid-server-properties-rejected, kafka.configuration-invalid-server-property-rejected, kafka.configuration-property-value-type-accepted, kafka.configuration-reserved-broker-property-rejected.

=== Cause 2 of 4: DescribeTopicPartitions' AccessDeniedException for a structurally invalid ClusterArn appends an extra clause and does not percent-encode the resource ARN ===
AWS: Smithy DescribeTopicPartitions GET /v1/clusters/{ClusterArn}/topics/{TopicName}/partitions, 200; ClusterArn and TopicName are httpLabel-bound and required; modeled errors BadRequestException 400, ForbiddenException 403, NotFoundException 404, UnauthorizedException 401, InternalServerErrorException 500. AccessDeniedException is not modeled on this operation, so its text is recorded behavior only: when the ClusterArn is a well-formed ARN prefix but the cluster resource segment is missing its required `/<uuid>` suffix, the ARN cannot be resolved for authorization and MSK answers AccessDeniedException whose Message is exactly `User: <callerArn> is not authorized to perform: kafka-cluster:Connect on resource: <percent-encoded ClusterArn>` and NOTHING after it. Fixed text: `User: `, ` is not authorized to perform: kafka-cluster:Connect on resource: `. Variable parts: <callerArn>, the caller's own identity ARN as GetCallerIdentity reports it, and the submitted ClusterArn, percent-encoded with NO safe characters (every `:` and `/` escaped). Once the ClusterArn is syntactically valid but names no cluster, the same call instead answers NotFoundException with Message `The requested resource doesn\u2019t exist.` (note the typographic apostrophe U+2019).
Emulator: the code AccessDeniedException is right, but the Message is `User: arn:aws:iam::<account>:user/emulator is not authorized to perform: kafka-cluster:Connect on resource: arn:aws:kafka:<region>:<account>:cluster/<name> because no identity-based policy allows the kafka-cluster:Connect action` — it (a) emits the ClusterArn verbatim instead of percent-encoded and (b) appends a trailing ` because no identity-based policy allows the kafka-cluster:Connect action` clause that AWS does not emit for this unresolvable-ARN case.
Why: a client that matches or displays this denial reads a different sentence than AWS's, and tooling that recovers the offending ARN by URL-decoding the resource clause gets a different string. The added reason clause also misattributes the refusal: the call was refused because the ARN is structurally unresolvable, not because an identity policy was missing a grant.
Fix: the DescribeTopicPartitions handler's ClusterArn resolution/authorization path and the AccessDeniedException message builder in the kafka service — emit AWS's two-clause sentence with the resource ARN percent-encoded and no trailing reason clause, and keep the valid-but-absent case on NotFoundException. Related OPEN issue that does not cover it: 20261029T175822Z-kafka-msk-arn-handling-malformed-and-cross-region-arns.md.
Traces: kafka.describe-topic-partitions-malformed-name-rejected.

=== Cause 3 of 4: the Express-cluster channel sequence never settles, so the unicode round-trip reaches no verdict ===
AWS: Smithy CreateChannel POST /v1/clusters/{ClusterArn}/channels (200, output channelArn + optional clusterOperationArn, echoing no channel state), DescribeChannel GET /v1/clusters/{ClusterArn}/channels/{ChannelArn} (200, required channelArn/channelName/status/destinationType/creationTime/topicConfigurationList, optional tags/s3DestinationConfiguration), UpdateChannel PUT .../channels/{ChannelArn} (200, output channelArn + clusterOperationArn only). ChannelStatus is CREATING|ACTIVE|UPDATING|DELETING|FAILED|SUSPENDING|SUSPENDED, so a new channel settles CREATING -> ACTIVE and an updated one UPDATING -> ACTIVE, with the update's cluster operation settling to a completed OperationState observable through DescribeClusterOperationV2. Because neither write echoes destination state, DescribeChannel is the ONLY confirmation path. Nothing in the model lets an unrelated update alter the channel's name, tags or Storage.OutputPrefix: non-ASCII strings submitted on create must come back byte-identical, and S3DestinationUpdate.DataFreshnessInSeconds must become visible on an independent read.
Emulator: the CreateClusterV2(Express) -> CreateTopic -> CreateChannel -> wait ACTIVE -> DescribeChannel -> UpdateChannel -> wait cluster operation -> wait ACTIVE -> DescribeChannel sequence never reaches a terminal observable state; the replay detail is the bare `Error: Check timed out after 60.0s` with no status, no error code and no frame, so no assertion was ever evaluated. Hypothesis (neither the model nor the replay output names the broken link): one of the Express cluster's CREATING -> ACTIVE, the topic's CREATING -> ACTIVE, the channel's CREATING -> ACTIVE, the UpdateChannel cluster operation reaching UPDATE_COMPLETE/COMPLETED, or the channel's UPDATING -> ACTIVE with the new DataFreshnessInSeconds applied never settles, so each poll burns its whole deadline.
Why: a client creating an MSK S3 delivery channel, or changing its buffering interval, hangs until its own timeout and can never distinguish 'applied' from 'silently dropped' — the write responses carry no state. The representation guarantee goes with it: nothing proves unicode channel names, tag values and S3 prefixes survive an unrelated update unchanged, which is exactly where a lossy encode would corrupt a client's object layout and tag inventory.
Fix: the channel state machine in the kafka service's state layer plus the CreateChannel / DescribeChannel / UpdateChannel handlers and the cluster-operation and Express-cluster/topic settling in front of them. === Cause 4 of 4: the two-cluster Replicator topic-sync and teardown sequence never settles, so it reaches no verdict ===
AWS: Smithy CreateReplicator POST /replication/v1/replicators, 200, output replicatorArn/replicatorName/replicatorState; ReplicatorName @pattern ^[0-9A-Za-z][0-9A-Za-z-]{0,}$ length 1..128; KafkaClusters, ReplicationInfoList and ServiceExecutionRoleArn required; modeled errors BadRequestException 400, ConflictException 409, ForbiddenException 403, NotFoundException 404, UnauthorizedException 401, TooManyRequestsException 429, and server 500/503. The replicator settles to ReplicatorState RUNNING (never FAILED for a valid 3-broker pair), after which a topic created on the source cluster becomes visible in the target cluster's ListTopics; DeleteTopic then resolves the source topic to NotFoundException with Message `The requested resource doesn\u2019t exist.` and DeleteReplicator resolves DescribeReplicator to NotFoundException with Message `Invalid parameter replicatorArn: The requested resource doesn\u2019t exist.` (both use the typographic apostrophe U+2019; the fixed text is those sentences, with no per-run value in them).
Emulator: the sequence produces no response the check can assert on — the replay detail is the bare `Error: Check timed out after 60.0s`, with no status, no error code and no frame. Hypothesis: one of the two clusters' CREATING -> ACTIVE, the replicator's CREATING -> RUNNING, the source topic's propagation into the target cluster's ListTopics, the source topic's CREATING -> ACTIVE before DeleteTopic, or either delete's convergence to its NotFoundException never happens, so every poll runs to its deadline.
Why: a client that provisions MSK Replicator and waits for RUNNING, or that tears a replicator down and confirms absence, never gets a terminal answer; cross-cluster replication cannot be observed at all, and the two documented not-found refusals that mark successful deletion are never reached.
Fix: the replicator state machine in the kafka service's state layer plus the CreateReplicator / DescribeReplicator / DeleteReplicator handlers, the cross-cluster topic propagation into ListTopics, and the cluster/topic settling in front of them — each state must reach its terminal value within one or two probes at an AWS-sized cadence.
