# Redshift: 3 net-new causes — ModifyClusterDbRevision answers 501 NotImplemented instead of ClusterOnLatestRevision / InvalidParameterValue, and a ModifyCluster resize is applied synchronously so no busy-state window exists

> _Note: this issue was identified against the code base at commit `ece6d2295e7fd7091ecbef4c65d6af7cf635653d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ModifyClusterDbRevision

## Description
Three net-new root causes in the redshift service, all grounded in the behavioral replay. The first two live in the ModifyClusterDbRevision handler (which is still the generated scaffold: services/service-com-amazonaws-redshift-redshiftserviceversion20121201/src/ops/modify_cluster_db_revision.rs returns crate::scaffolded::Scaffolded::not_implemented("ModifyClusterDbRevision") at line 163 and still carries the SCAFFOLDED marker at line 4); the third is in ModifyCluster's cluster state machine. The open issue 20261029T200555Z-redshift-control-operations-answer-notimplemented-instead-of-their.md names ModifyClusterDbRevision for one cause only — its ClusterNotFoundFault leg for a nonexistent ClusterIdentifier — and carries none of the replay keys below; the refusal contracts named here (ClusterOnLatestRevision and the non-offered-target refusal) are additional contracts the stood-up handler must satisfy. No open issue covers cause 3.

Cause 1 of 3: ModifyClusterDbRevision targeting the revision the cluster is already on is not refused with ClusterOnLatestRevision. AWS: for an available cluster whose RevisionTarget equals the CurrentDatabaseRevision DescribeClusterDbRevisions reports, the call is refused, not accepted as a no-op; Smithy (com.amazonaws.redshift#ModifyClusterDbRevision) models ClusterOnLatestRevisionFault, errorKind client, httpError 400, awsQueryError code `ClusterOnLatestRevision` (shape doc: "Cluster is already on the latest database revision."). The message is fixed text with no variable parts: "Modification of cluster-db-revision was skipped. The cluster is already on the requested db-revision." The cluster's ClusterRevisionNumber / CurrentDatabaseRevision must be unchanged afterwards, and DescribeClusterDbRevisions for the same cluster must keep working. Emulator: every call is refused with error code `NotImplemented` (HTTP 501, message "operation ModifyClusterDbRevision is scaffolded but not implemented in this emulator"), so neither the code, the status, the message nor the no-effect guarantee can be observed. Why: a client that upgrades a cluster's db revision only when it is not already current branches on ClusterOnLatestRevision; against the emulator it instead sees an unmodelled code that SDK retry classifiers treat as an unknown non-retryable failure, and no amount of state setup makes the modeled refusal appear. Fix: the ModifyClusterDbRevision handler and the cluster's db-revision state — resolve the cluster, then compare RevisionTarget with the cluster's current revision and raise ClusterOnLatestRevisionFault with that message before applying anything. Traces: redshift.cluster-db-revision-already-latest-blocked, redshift.cluster-db-revision-already-latest-fault, redshift.cluster-db-revision-modify-transition, redshift.modify-cluster-db-revision-already-latest-rejected, redshift.modify-cluster-db-revision-latest-blocked.

Cause 2 of 3: ModifyClusterDbRevision given a well-formed RevisionTarget the cluster does not offer is not refused with InvalidParameterValue, and the refusal-class precedence AWS guarantees is unobservable. AWS: a syntactically valid revision id that is not one of the cluster's offered RevisionTargets is refused with the query-protocol common error code `InvalidParameterValue`, HTTP 400, and the fixed message "The requested database revision requires an intermediate upgrade. Use DescribeClusterDbRevisions to get the next available revision target." (no variable parts). ClusterOnLatestRevision is reserved for a target the cluster is already on — the two classes must not be conflated. Smithy models ClusterNotFoundFault (404, `ClusterNotFound`), ClusterOnLatestRevisionFault (400), InvalidClusterStateFault (400) and UnsupportedOperationFault (400) for this operation and does NOT model InvalidParameterValue, so this class and its wording are recorded behavior only. The rejected call must leave CurrentDatabaseRevision unchanged and the cluster otherwise mutable (CreateTags on it still succeeds). Emulator: `NotImplemented` again. Why: a caller cannot tell "that revision id is not reachable from here, read DescribeClusterDbRevisions" from "the cluster is already current" from "the API is broken", so an upgrade driver has no way to pick a valid next target. Fix: the ModifyClusterDbRevision handler's RevisionTarget validation, ordered after cluster resolution and before the already-on-latest comparison. Traces: redshift.ordering-modify-cluster-db-revision-sequential.

Cause 3 of 3: a ModifyCluster that resizes a cluster is applied synchronously and the cluster never leaves the available state, so no in-flight-operation window exists and the busy-state refusal of a second mutation is unreachable. AWS: ModifyCluster(ClusterType="multi-node", NodeType=<same>, NumberOfNodes=2) on a single-node cluster starts a resize; the ModifyCluster response's Cluster.ClusterStatus is an in-progress status (a non-available value such as `modifying`/`resizing`) and DescribeClusters keeps reporting a non-available status until the resize completes, after which the cluster returns to `available`. While that operation is applying, another mutating call on the same cluster is refused with InvalidClusterState — Smithy: ModifyClusterDbRevision and ModifyCluster both model InvalidClusterStateFault, errorKind client, httpError 400, awsQueryError code `InvalidClusterState` (shape doc: "The specified cluster is not in the available state."); for ModifyClusterDbRevision the message's fixed text is "Cannot modify the cluster-db-revision right now because another operation is running. Check the cluster's status and retry when the cluster is available." (no variable parts), and the racing call must not change the cluster's revision. Emulator: the ModifyCluster resize call answers 200 with Cluster.ClusterStatus "available" — the modification is already complete when the response is written, so the cluster is never busy and the concurrency gate can never fire. Why: a client that polls for a resize to finish sees it finished before it ever started, and code written to back off on InvalidClusterState during a resize is never exercised; conversely an emulator that accepts concurrent mutations is overly permissive, since AWS serializes them. Fix: the ModifyCluster handler plus the cluster status/state machine in the redshift service state — a resize-class modification must park the cluster in a non-available status for an observable window, report that status in its own response, and make other mutating operations on the cluster refuse with InvalidClusterStateFault while it is in flight. Traces: redshift.cluster-concurrent-modify-state-conflict-blocked.

Generated cluster identifiers, subnet-group names, node types and revision ids in the replay are this run's environment; the requirements are the statuses, error codes, message templates and state transitions described above.
