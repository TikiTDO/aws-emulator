# Braket SearchSpendingLimits' createdAt is served as an epoch-seconds number, so a CloudFormation AWS::Braket::SpendingLimit's CreatedAt attribute never agrees with the limit the API reports (1 cause)

> _Note: this issue was identified against the code base at commit `d5058bf9472168e1295443ef351c1b19f1a4a885`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SearchSpendingLimits

## Description
One net-new behavioral cause, found by replaying the behavioral suite simparity-behavioral-aws-v1 against the emulator. It is NOT marked OWNED/ALREADY FILED by the suite report. The open wire issue 20261103T044954Z-braket-read-paths-serialize-response-bodies-wrongly-spending.md describes the same serializer fault from the WIRE corpus (its Issue-Key braket|SearchSpendingLimits|2xx->2xx|$.spendingLimits[*].createdAt) and is named here so a fixer can close both with one change; it does not carry this check's replay key, and this check additionally pins the CROSS-SERVICE consequence (the CloudFormation attribute must denote the instant the Braket API reports), so it is filed separately.

Cause 1 of 1: SpendingLimitSummary$createdAt (and $updatedAt) are put on the wire as epoch-seconds JSON numbers instead of the modelled date-time strings, so the instant a client reads from SearchSpendingLimits is not the instant the stack publishes as the resource's CreatedAt attribute. Failing check: braket__cloudformation.deploy-braket-spendinglimit-round-trip-and-delete.

AWS: Smithy (services/service-com-amazonaws-braket-braket/smithy-model/com-amazonaws-braket-braket.json) models SpendingLimitSummary$createdAt and $updatedAt as Timestamp with @timestampFormat("date-time"), both required. Under restJson1 a member carrying that trait is serialized as an RFC3339 date-time STRING (e.g. "<yyyy-mm-dd>T<hh:mm:ss>.<frac>Z"), never as the protocol's default epoch-seconds number; the recorded AWS response for this operation carries such a string. The CloudFormation resource AWS::Braket::SpendingLimit publishes CreatedAt as a return value, and AWS's CreatedAt is the same instant Braket records for the limit, so Fn::GetAtt CreatedAt and the createdAt SearchSpendingLimits reports for the same spendingLimitArn denote ONE instant: a client can parse the stack output and compare it with the API's value and they agree. Status/shape of the calls themselves is unchanged (SearchSpendingLimits 200, CreateSpendingLimit 201); no error is involved.
Emulator: the limit is created by the stack (CREATE_COMPLETE), Ref resolves to the ARN Braket minted and GetAtt SpendingLimitArn equals the listed spendingLimitArn — those assertions pass. The round-trip then fails on the value triple: botocore parsed createdAt into a datetime with tzlocal() and microsecond resolution (replay actual datetime.datetime(2026, 11, 11, 12, 23, 52, 786063, tzinfo=tzlocal())), which is what botocore produces from a JSON NUMBER, not from a date-time string (a date-time string parses to tzutc). The other two elements of the triple cannot diverge: the entry was selected by a deviceArn EQUAL filter on the templated DeviceArn and the amount compares equal as a Decimal. So the member-level @timestampFormat is dropped on the way out: crate::state::to_date_time builds the Timestamp from SystemTime as DateTime::from_secs_f64 (services/service-com-amazonaws-braket-braket/src/state.rs, to_date_time) and the SearchSpendingLimits output serializer emits it in the protocol's default epoch-seconds form (the summary is assembled in services/service-com-amazonaws-braket-braket/src/ops/search_spending_limits.rs, which hands created_at/updated_at to the serializer). CloudFormation then renders that number to the TEXT a GetAtt attribute carries (services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner/braket_spending_limits.rs, created_at_text/reported_attributes_of over the number SearchSpendingLimits answered), so the published CreatedAt and the API's createdAt are two different renderings of a sub-millisecond f64 and do not denote the same instant.
Why: a generated AWS SDK client deserializes createdAt/updatedAt per the model, as date-time; a bare number there is either a deserialization failure or a silently wrong instant, so SearchSpendingLimits is unusable from a typed client even though it answers 200. Across the two services it is worse: a client that reads the stack's CreatedAt output and correlates it with the limit Braket lists — the normal way to confirm a deployed cost control, and the way drift and reconciliation tooling matches a stack resource to the resource the owning service holds — finds two instants that never compare equal, so the correlation fails on a stack that deployed correctly.
Fix: the SearchSpendingLimits output serializer / the generated SpendingLimitSummary output schema in the braket crate must honour the member's @timestampFormat("date-time") instead of falling back to restJson1 epoch-seconds, and the instant Braket stores for a limit must be held at the resolution that form carries, so the one instant renders identically wherever it is read; CloudFormation's AWS::Braket::SpendingLimit provisioner then publishes CreatedAt as the text Braket reported rather than as its own rendering of a number. No change to statuses, error codes or messages is involved.
Traces: braket__cloudformation.deploy-braket-spendinglimit-round-trip-and-delete.

What the check had already confirmed before that line: the stack reached CREATE_COMPLETE, SearchSpendingLimits lists exactly ONE entry whose spendingLimitArn equals Ref Limit, and GetAtt SpendingLimitArn equals that entry's spendingLimitArn. The failing comparison is therefore (entry.deviceArn, Decimal(entry.spendingLimit), entry.createdAt) against (the templated DeviceArn, Decimal("5.00"), datetime.fromisoformat(GetAtt CreatedAt)). The entry was fetched with a deviceArn EQUAL filter on the templated DeviceArn and Decimal('5.00') == Decimal('5.00'), so the diverging element is createdAt.

Diagnosis of that element: tzinfo=tzlocal() with 786063 microseconds is what botocore's parse_timestamp returns for a JSON NUMBER (epoch seconds); a date-time string yields tzutc. Expected wire form (model): $.spendingLimits[*].createdAt as an RFC3339 date-time string. Actual wire form: an epoch-seconds number with an f64 fractional part. The literal instant, the ARN and the per-run stack/limit ids are per-run values and are not part of the requirement; the requirement is the date-time STRING form @timestampFormat("date-time") pins, and that GetAtt CreatedAt and the API's createdAt denote one instant.

Also observed in the same output, NOT the cause of the failing assertion and not claimed here as a cause: the braket client was pinned to us-east-1, and the first ONLINE QPU its SearchDevices listed was 'arn:aws:braket:eu-north-1::device/qpu/iqm/Garnet' — a device ARN of another Region served from a us-east-1 endpoint.

3.
