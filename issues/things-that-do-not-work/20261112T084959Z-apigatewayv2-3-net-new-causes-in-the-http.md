# apigatewayv2: 3 net-new causes in the HTTP API CORS layer and stage-variable integrations — gateway-answered OPTIONS preflight 404s, a non-allowlisted origin leaks the backend's Access-Control-Allow-Origin, and a ${stageVariables.*} integration never reaches a verdict

> _Note: this issue was identified against the code base at commit `a71435d592561fc10ca1c4dcda74d11758c7bd15`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateApi

## Description
Three net-new root causes in the apigatewayv2 HTTP API data plane, all on APIs whose CorsConfiguration (Smithy shape Cors, services/service-com-amazonaws-apigatewayv2-apigatewayv2/smithy-model/com-amazonaws-apigatewayv2-apigatewayv2.json: members AllowOrigins/AllowMethods/AllowHeaders/ExposeHeaders/AllowCredentials/MaxAge, MaxAge @range -1..86400, 'Supported only for HTTP APIs', doc link https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-cors.html) or whose IntegrationUri carries a stage variable. All three are reached through CreateApi/CreateIntegration/CreateRoute/CreateStage and then observed on the execute-api endpoint.

Cause 1 of 3: an HTTP API with a CorsConfiguration and NO OPTIONS route does not answer the CORS preflight itself — the request falls through to route matching and is refused 404.
AWS: for an HTTP API with CorsConfiguration, API Gateway answers an OPTIONS request carrying Origin + Access-Control-Request-Method (+ Access-Control-Request-Headers) itself, without invoking any integration and without needing an OPTIONS route. The response status is 204 (the check accepts 200 or 204) with Access-Control-Allow-Origin set to the request's Origin when that origin is in AllowOrigins, Access-Control-Allow-Methods containing the configured methods, Access-Control-Allow-Headers containing the configured headers and Access-Control-Max-Age equal to the configured MaxAge. Smithy models the configuration (Cors.AllowOrigins/AllowMethods/AllowHeaders/MaxAge, jsonNames allowOrigins/allowMethods/allowHeaders/maxAge) but not the data-plane response, so the preflight contract is recorded behavior plus the documented CORS rule above; the header NAMES, the 204 and the fact that the values are echoed are the fixed part, while the origin, the method/header lists and the max-age number are taken from the API's own CorsConfiguration (e.g. 600 in one check's template is a value, not a requirement). A preflight from an origin NOT in AllowOrigins must come back WITHOUT any Access-Control-Allow-Origin header.
Emulator: the preflight is routed like any other request and refused with HTTP 404 and body {"message":"Not Found"} — 'expected 200/204 for a CORS preflight, got 404: {"message":"Not Found"}' and 'a CORS preflight on a CORS-configured HTTP API must be 204, got 404: {"message":"Not Found"}'. No Access-Control-* header is emitted, so the allow-origin/allow-methods/max-age assertions are never reached.
Why: browsers refuse the real request whenever a preflight is required, so every cross-origin fetch, XHR or non-simple request against an emulated HTTP API fails even though the API is configured exactly as in AWS. Clients also cannot distinguish 'origin denied' (200/204 with no Access-Control-Allow-Origin) from 'route missing' (404), which is the signal CORS debugging relies on.
Fix: the execute-api HTTP data plane's request dispatch for apigatewayv2 — the CORS layer must intercept OPTIONS preflights ahead of route matching when the API has a CorsConfiguration and build the 204 preflight response from that configuration (including the deny case that omits Access-Control-Allow-Origin).
Traces: apigatewayv2.http-api-cors-preflight-origin-allowlist-and-delete; apigatewayv2.deploy-apigatewayv2-1-http-api-cors-removed-in-place-then-api-replaced. Note: open issue 20261106T180247Z-apigatewayv2-a-cfn-provisioned-http-api-with-corsconfiguration.md describes the second of those checks as a 60 s hang; the emulator now gets past that prefix and refuses the preflight 404 instead, and the suite did not attribute this failure to that issue, so the preflight cause is filed here.

Cause 2 of 3: with CorsConfiguration set, the backend's own Access-Control-* response headers are NOT replaced/stripped for a request whose Origin is not allowlisted — the integration's header leaks to the caller.
AWS: when an HTTP API has a CorsConfiguration, API Gateway owns the CORS response headers: it removes the Access-Control-* headers the integration returned and emits its own. For an allowed origin it emits Access-Control-Allow-Origin = that origin and Access-Control-Expose-Headers = the configured ExposeHeaders; for an origin that is not in AllowOrigins the response body and status are still delivered unchanged but NO Access-Control-Allow-Origin header is returned, and the backend's value must not be passed through. Non-CORS backend headers (e.g. a custom marker header) still pass through. Documented at https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-cors.html; Smithy models only the configuration, so the stripping rule is documented/recorded behavior.
Emulator: the allowed-origin leg is correct (it stamps the API's own Access-Control-Allow-Origin and Access-Control-Expose-Headers), but on the foreign-origin leg the response carries the backend's header verbatim: 'foreign origin: no access-control-allow-origin may be returned (the backend's must not leak through), got <the origin string the Lambda itself set>' — i.e. the emulator forwards the integration's Access-Control-Allow-Origin instead of dropping it.
Why: the API's allowlist stops being an allowlist. Any integration that sets a permissive Access-Control-Allow-Origin (or '*') silently re-enables cross-origin reads from origins the API explicitly does not allow, so a browser accepts a response AWS would make it discard — a security-relevant divergence, and code tested against the emulator ships an allowlist that does not hold in AWS.
Fix: the response path of the execute-api HTTP data plane's CORS layer — strip every Access-Control-* header produced by the integration before applying the API's CorsConfiguration, on both the allowed and the denied-origin branch, while leaving non-CORS headers untouched.
Traces: apigatewayv2.http-api-cors-configuration-overrides-backend-cors-headers.

Cause 3 of 3: an HTTP API whose integration's IntegrationUri names a Lambda through a stage variable ('...function:${stageVariables.fn}') reaches no terminal answer — the replay is killed at the harness budget with no status and no error.
AWS: an HTTP API integration may parameterise IntegrationUri with ${stageVariables.<name>}; each stage substitutes its own StageVariables value, so one integration plus one deployment on two stages is served by two different Lambdas, each stage's invoke URL answering 200 with that function's body. The 2.0 proxy event the function receives carries version '2.0', the matched routeKey, requestContext.stage equal to the stage that served the request and stageVariables equal to that stage's variable map. Documented at https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-stages.stage-variables.html; Smithy models StageVariables on CreateStage/UpdateStage and IntegrationUri on CreateIntegration but not the substitution, so this is documented plus recorded behavior.
Emulator: the replay never produces a status, an error code or a message on this path — 'Error: Check timed out after 60.0s'. Neither stage's invoke URL reaches an accepted status, so the emulator neither serves the stage-variable-selected backend nor refuses the integration; the stageVariables/requestContext.stage content of the delivered event is consequently unobservable.
Why: a client that uses one integration across stages (the standard dev/prod pattern) gets no answer at all instead of a response or a modelled refusal, and hangs until its own socket timeout. Handlers that branch on event.stageVariables or requestContext.stage cannot be exercised at all.
Fix: the execute-api HTTP data plane's integration-target resolution (expand ${stageVariables.*} in IntegrationUri against the serving stage's StageVariables, and fail the request with the modelled refusal rather than never answering when the variable is unset) plus stage-variable propagation into the 2.0 payload (stageVariables, requestContext.stage).
Traces: apigatewayv2.deep-apigatewayv2-3-stagesem-stage-variable-selects-lambda-backend.

## Evidence
Cause 1 — Expected (AWS): OPTIONS <stage-invoke-url>/<path> with Origin: <an origin in AllowOrigins>, Access-Control-Request-Method: GET, Access-Control-Request-Headers: content-type on an HTTP API that has a CorsConfiguration and no OPTIONS route -> HTTP 204 (200 also accepted), access-control-allow-origin == the request Origin, access-control-allow-methods containing 'GET', access-control-allow-headers containing the configured headers, access-control-max-age == the configured MaxAge; the same preflight from an origin NOT in AllowOrigins -> no access-control-allow-origin header at all. Actual (emulator): HTTP 404 with body {"message":"Not Found"} and no Access-Control-* headers. Replay assertions: 'expected 200/204 for a CORS preflight, got 404: {"message":"Not Found"}' (apigatewayv2.http-api-cors-preflight-origin-allowlist-and-delete) and 'a CORS preflight on a CORS-configured HTTP API must be 204, got 404: {"message":"Not Found"}' (apigatewayv2.deploy-apigatewayv2-1-http-api-cors-removed-in-place-then-api-replaced).

Cause 2 — Expected (AWS): GET <stage-invoke-url>/<path> with Origin: <origin NOT in AllowOrigins>, where the AWS_PROXY Lambda returns its own Access-Control-Allow-Origin and Access-Control-Expose-Headers -> HTTP 200 with the integration body unchanged, NO access-control-allow-origin header, and non-CORS backend headers (x-marker) still present. Actual (emulator): HTTP 200 with the backend's own access-control-allow-origin value forwarded to the caller — 'AssertionError: foreign origin: no access-control-allow-origin may be returned (the backend's must not leak through), got <backend-set origin>'. (The allowed-origin leg of the same check passes, so the defect is specifically the failure to strip integration-supplied Access-Control-* headers on the denied branch.)

Cause 3 — Expected (AWS): with one integration IntegrationUri 'arn:aws:lambda:<region>:<account>:function:${stageVariables.fn}' and two stages whose StageVariables.fn name different functions, each stage's invoke URL answers 200 with that stage's function body, and each function's 2.0 event carries version '2.0', the matched routeKey, requestContext.stage == its own stage and stageVariables == its own stage's map. Actual (emulator): no status, no error code and no message — the replay is aborted by the harness ('Error: Check timed out after 60.0s'), so no leg of the lifecycle is observable.
