# ds__ec2: a Managed Microsoft AD never materialises its network presence in EC2 — no controllers security group and no per-subnet directory ENI is created, so both directory-network flows hang to the budget

> _Note: this issue was identified against the code base at commit `7eb0bd3bda5e5fd14f4b01ea8dd2daf93fb4b55d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateMicrosoftAD

## Description
One net-new root cause spanning ds and ec2, found by replaying the behavioral suite against the emulator built from this checkout. Not a scaffold stub: ds answers CreateMicrosoftAD and DescribeDirectories and EC2 answers the describes — what is missing is the cross-service effect.

Cause 1 of 1: CreateMicrosoftAD places no EC2 resources for the directory it creates, so EC2's view of the directory is permanently empty and the directory reports no controllers security group.
AWS: recorded behavior only (the ds Smithy model describes the envelope, not the cross-service effect); the one modeled anchor is DirectoryVpcSettingsDescription$SecurityGroupId — target SecurityGroupId, @pattern ^(sg-[0-9a-f]{8}|sg-[0-9a-f]{17})$, documented "The domain controller security group identifier for the directory." Recorded behavior: Directory Service provisions into the caller's VPC on the caller's behalf, so once a Managed Microsoft AD created with VpcSettings has left Requested, (a) DescribeDirectories reports VpcSettings.SecurityGroupId naming a security group that EXISTS in EC2 in the subnets' VPC and whose GroupName carries the directory id, and (b) EC2 holds exactly one network interface per chosen subnet whose Description names the directory and whose Groups include that security group. DeleteDirectory then RELEASES both: the interfaces disappear and DescribeNetworkInterfaces on a released id answers InvalidNetworkInterfaceID.NotFound "The networkInterface ID '<eni-id>' does not exist", DescribeSecurityGroups on the released group answers InvalidGroup.NotFound "The security group '<sg-id>' does not exist" (fixed text; the id is taken from the request), which is what lets the caller then delete its own subnets and VPC. The ids differ per run and are not requirements; the existence, the placement and the release are.
Emulator: nothing in the ds service ever creates an EC2 security group or network interface. Its only hop into EC2 is READ-ONLY — src/state/ec2_subnets.rs is documented as "THE HOP: asking the service that OWNS subnets what the subnets a create names really are" and issues DescribeSubnets with a subnet-id filter — and src/state/directory_network.rs keeps only the resolved CIDR block and Availability Zone per subnet and counts server addresses out of the block ("this one GATES no create"), creating no resource and having no teardown counterpart. Both polls these two checks make are therefore unsatisfiable: the wait for a non-empty VpcSettings.SecurityGroupId and the wait for one directory ENI per subnet in EC2. Both checks make no progress and are killed at the 60 s budget with "Check timed out after 60.0s" and no exception frame — the signature of a poll loop waiting on a state the emulator never reaches.
Why: the directory's network is unreachable for any client. Anything that authorizes the directory's AD ports (a same-VPC trust between two directories must add an ingress rule naming the peer's controllers group), resolves the controllers' interfaces, or reconciles the directory against EC2 finds nothing — and a client that waits for the group id or the interfaces, as AWS callers must because they appear asynchronously during Creating, hangs instead of being served. The teardown half is equally invisible: a caller cannot tell whether the directory has released the interfaces that otherwise block DeleteSubnet/DeleteVpc with DependencyViolation.
Fix: the cross-service provisioning in the CreateMicrosoftAD/CreateDirectory handler plus the single rendering point for DirectoryVpcSettingsDescription in the ds service state — a create must mint a controllers security group and one network interface per requested subnet in the EC2 service state (the directory id in the group name and in each interface's description, each interface in its own subnet and carrying that group), report THAT group id in VpcSettings.SecurityGroupId, and the directory teardown (src/state/directory_deletion.rs) must release both so EC2 afterwards answers InvalidNetworkInterfaceID.NotFound / InvalidGroup.NotFound for them.
Traces: ds__ec2.microsoft-ad-creates-a-controllers-security-group-and-one-eni-per-subnet-in-the-vpc (dies in the SecurityGroupId / ENI poll), ds__ec2.delete-directory-releases-its-controllers-security-group-and-enis-from-the-vpc (dies in the same setup poll, so its release assertions are never reached). Related open issues that do NOT carry these replay keys: 20261024T081028Z-ds-directory-service-a-microsoft-ad-never-provisions-its.md describes the same mechanism but is keyed on an earlier corpus (simparity-behavioral-ga-prod-v1) and bundles it with the DnsIpAddrs cause, and this replay marks both checks unowned; 20261108T155909Z-ds-2-net-new-causes-describedirectories-omits-vpcsettings.md covers the ds-side VpcSettings.SecurityGroupId member being absent from the response, not the EC2-side group and interfaces. A fixer should land them together.

## Evidence
Replay of suite simparity-behavioral-aws-v1 against the emulator built from this checkout: service ds__ec2 14/21 (67%), 7 failed; five of those are marked OWNED by existing issues and are skipped. The two clustered here report exactly "Error: Check timed out after 60.0s" with no exception frame, having asserted nothing.

ds__ec2.microsoft-ad-creates-a-controllers-security-group-and-one-eni-per-subnet-in-the-vpc, from its own source: build a private VPC with one /24 subnet per available AZ, CreateMicrosoftAD (Standard) on two subnets in different AZs, then _poll(lambda: _describe(ds, directory_id), lambda x: bool(x["VpcSettings"].get("SecurityGroupId")), timeout_s=300, interval_s=5) — expects a SecurityGroupId matching ^(sg-[0-9a-f]{8}|sg-[0-9a-f]{17})$; then ec2.describe_security_groups(GroupIds=[sg_id]) must return exactly one group whose VpcId is the check's VPC and whose GroupName contains the directory id; then ec2.describe_network_interfaces(Filters=[{vpc-id}]) must, within 300 s at 10 s intervals, show at least two interfaces whose Description contains the directory id, sitting in the two chosen subnets and carrying that group. Neither state is ever reached, so the check is killed at 60 s.

ds__ec2.delete-directory-releases-its-controllers-security-group-and-enis-from-the-vpc: the same setup and the same two polls as CONTROL, then ds.delete_directory, then polls until the directory stops being listed, until the directory ENIs are gone, and finally asserts ec2.describe_network_interfaces on each released id answers ("InvalidNetworkInterfaceID.NotFound", "The networkInterface ID '<eni-id>' does not exist") and ec2.describe_security_groups on the released group answers ("InvalidGroup.NotFound", "The security group '<sg-id>' does not exist"). It never gets past the control polls, so the release half is ungraded.

Checkout evidence that nothing is provisioned: services/service-com-amazonaws-directoryservice-directoryservice-20150416/src/state/ec2_subnets.rs:1-70 — the only EC2 hop, an in-process DescribeSubnets by subnet-id filter, read-only; and src/state/directory_network.rs:1-83 — what a create KEEPS of that answer (subnet id, CIDR block, Availability Zone) plus the address arithmetic, explicitly "GATES no create". There is no CreateSecurityGroup, no CreateNetworkInterface and no release counterpart anywhere in the ds state modules (src/state/directory_deletion.rs:123-142 removes only ds-side records: snapshots, trusts, shares).

Both checks build their own VPC, so no account-specific or live-only value is involved. VPC, subnet, group and interface ids differ per run and are not requirements; the required facts are the group's existence in the subnets' VPC with the directory id in its name, one interface per chosen subnet naming the directory and carrying that group, the SecurityGroupId member being reported, and both being released by DeleteDirectory with the two EC2 not-found refusals above.

## Steps to Reproduce
1. git_clone(), then run_behavioral_suite(); both check ids in trace_ids reproduce the cause.
2. Create a VPC with two subnets in different AZs and call ds:CreateMicrosoftAD(Name=<x>, Password=<compliant>, Edition=Standard, VpcSettings={VpcId, SubnetIds:[a,b]}).
3. Poll ds:DescribeDirectories(DirectoryIds=[<id>]) for VpcSettings.SecurityGroupId: expect an id matching ^(sg-[0-9a-f]{8}|sg-[0-9a-f]{17})$ once the directory has left Requested; observe the poll never satisfying.
4. Call ec2:DescribeSecurityGroups on that id and ec2:DescribeNetworkInterfaces(Filters=[{Name:vpc-id,Values:[<vpc>]}]): expect one group in that VPC whose GroupName carries the directory id, and one interface per chosen subnet whose Description carries the directory id and whose Groups include that group; observe EC2 holds neither.
5. Call ds:DeleteDirectory, wait until the directory stops being listed, then re-describe: expect ec2:DescribeNetworkInterfaces on each released id to answer InvalidNetworkInterfaceID.NotFound "The networkInterface ID '<eni-id>' does not exist" and ec2:DescribeSecurityGroups on the group to answer InvalidGroup.NotFound "The security group '<sg-id>' does not exist"; this release half cannot be reached at all because nothing was created in step 2.
