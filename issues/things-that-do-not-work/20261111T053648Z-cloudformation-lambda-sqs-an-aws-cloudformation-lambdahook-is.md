# cloudformation__lambda__sqs: an AWS::CloudFormation::LambdaHook is created but never invoked — DescribeStackEvents carries no HOOK_IN_PROGRESS/HOOK_COMPLETE_* events for the targeted resource, so a FAIL-mode hook cannot veto anything

> _Note: this issue was identified against the code base at commit `950d97075a2dc28c97155d1939158688cbb186aa`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeStackEvents

## Description
One net-new root cause, grounded in the single failing check of this service that the replay report marks neither ALREADY FILED nor OWNED.

Cause 1 of 1: a CloudFormation Lambda hook that is created and ENABLED is not run as part of a targeted stack operation, and the stack's event stream carries no hook events at all.

AWS: Smithy (com.amazonaws.cloudformation) — DescribeStackEvents returns StackEvent, and StackEvent models the hook-invocation members HookType (length 1..255), HookStatus (enum com.amazonaws.cloudformation#HookStatus = HOOK_IN_PROGRESS | HOOK_COMPLETE_SUCCEEDED | HOOK_COMPLETE_FAILED | HOOK_FAILED), HookStatusReason (length 1..1024), HookInvocationPoint (enum com.amazonaws.cloudformation#HookInvocationPoint = PRE_PROVISION), HookInvocationId (36-char uuid) and HookFailureMode (enum com.amazonaws.cloudformation#HookFailureMode = FAIL | WARN). Beyond the model this is recorded behavior only: when an AWS::CloudFormation::LambdaHook with HookStatus ENABLED, TargetOperations [RESOURCE] and TargetFilters {Actions [CREATE], InvocationPoints [PRE_PROVISION], TargetNames [<resource type>]} matches a resource in a stack admitted by its StackFilters, CloudFormation invokes the hook's Lambda once per matching resource action at PRE_PROVISION and records, against that resource's LogicalResourceId, a pair of stack events carrying HookType = the hook's alias: first HookStatus HOOK_IN_PROGRESS, then HookStatus HOOK_COMPLETE_SUCCEEDED when the Lambda answers hookStatus SUCCESS. When the Lambda answers hookStatus FAILED, the second event is HOOK_COMPLETE_FAILED with HookFailureMode = the hook's FailureMode (FAIL), HookInvocationPoint = PRE_PROVISION and HookStatusReason = the message the Lambda returned; the targeted resource then records CREATE_FAILED with a ResourceStatusReason naming the hook alias, the stack reaches ROLLBACK_COMPLETE, and because the hook ran PRE_PROVISION the underlying resource is never created (here: SQS GetQueueUrl on the vetoed name must answer HTTP 400 with error code AWS.SimpleQueueService.NonExistentQueue and the fixed message "The specified queue does not exist."). The alias, the resource's logical id and the Lambda's refusal text are request/state-derived; the status enum values, the invocation point, the failure mode and the SQS error code/message are fixed.

Emulator: the hook estate itself deploys — the hook stack reaches CREATE_COMPLETE and GetAtt Hook.HookArn returns the expected arn:aws:cloudformation:<region>:<account>:type/hook/<alias-with-'::'-replaced-by-'-'> — and the targeted stack also reaches CREATE_COMPLETE, but DescribeStackEvents (paginated over the whole stack) returns NO event whose HookType equals the hook's alias for the targeted resource: the filtered list of (HookStatus, HookStatusReason) pairs is empty, so the replay reports `AssertionError: the allow- queue's hook events for 'Simreal::Sqs::Lh<token>' were []`. Because the run blocks there, everything the check asserts downstream of a hook that actually ran is unverified by this replay: the once-per-create invocation count, the HOOK_COMPLETE_FAILED/FAIL/PRE_PROVISION event trio on the vetoed stack, the CREATE_FAILED ResourceStatusReason naming the alias, the ROLLBACK_COMPLETE outcome, and the AWS.SimpleQueueService.NonExistentQueue refusal proving the queue was never provisioned. Hypothesis: the AWS::CloudFormation::LambdaHook resource is provisioned as inert state only — no hook registry is consulted during resource provisioning, so neither the Lambda invocation nor the hook stack events are ever produced.

Why: a client that enforces policy with a FAIL-mode hook gets no enforcement and no evidence. A non-compliant resource is created instead of vetoed, so a template the hook exists to refuse deploys successfully; the stack events a client (or the console) reads to see which hook ran and why it passed or failed contain nothing, so an auditing or compliance workflow built on HookType/HookStatus/HookStatusReason reports a hook-free deployment even though the hook is ENABLED.

Fix: the CloudFormation provisioning engine plus its stack-event recorder — evaluate registered/activated hooks (TargetOperations, TargetFilters.Actions/InvocationPoints/TargetNames, StackFilters) at PRE_PROVISION for each matching resource, invoke the hook's LambdaFunction under its ExecutionRole, map the returned hookStatus/message onto the resource's outcome per FailureMode, and emit the HOOK_IN_PROGRESS/HOOK_COMPLETE_* StackEvents (HookType, HookStatus, HookStatusReason, HookInvocationPoint, HookInvocationId, HookFailureMode) that DescribeStackEvents serializes.
