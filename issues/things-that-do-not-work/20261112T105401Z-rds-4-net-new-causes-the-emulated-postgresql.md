# rds: 4 net-new causes — the emulated PostgreSQL engine leaks a SQLite "string or blob too big" error from string_agg, never refuses ALTER ROLE rdsadmin, has no pg_read_file/pg_ls_dir (syntax error instead of 42501), and Endpoint.Port ignores the requested Port

> _Note: this issue was identified against the code base at commit `ca25ba25e081839cb5618fe742d51d98e2f97d2c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDBInstance

## Description
This issue bundles 4 net-new root causes in the rds service, each grounded in a failing behavioral check the suite report marked neither ALREADY FILED nor OWNED. A fixer must close ALL FOUR causes below before submitting.

=== Cause 1 of 4: the emulated PostgreSQL engine aborts a legitimate aggregate query with the backing store's "string or blob too big" error ===
AWS: recorded behavior only (the RDS Smithy model does not describe engine SQL). Real RDS for PostgreSQL executes `SELECT md5(string_agg(id::text || label || amount::text, ',' ORDER BY id)) FROM <table>` over a 50,000-row table and returns one row holding a 32-character lowercase hex md5; PostgreSQL's limit on a text value is 1 GB, so an aggregate string of this size is ordinary work and no error is produced. PostgreSQL never emits the message text seen here.
Emulator: the statement raises `psycopg.errors.SystemError: string or blob too big` — the SQLite backing store's SQLITE_TOOBIG message, surfaced verbatim as a backend error class rather than any PostgreSQL condition. Any query whose result or intermediate aggregate exceeds the emulator's store limit fails this way; the limit and the message are both artifacts of the backing store.
Why: a client doing content verification, bulk-load auditing or any large aggregate/string concatenation on an RDS PostgreSQL instance receives an internal error for a query AWS answers, and the error is not in PostgreSQL's vocabulary, so no SQLSTATE-driven handling can classify or retry it. It also makes the whole COPY-correctness path unexercisable: the check never reaches its COPY-refusal assertions (one malformed NUMERIC datum on line 25,000 must abort the whole COPY with SQLSTATE 22P02, context `COPY <table>, line <n>, column <col>: "<datum>"`, leaving zero rows), so those remain unverified behind this cause.
Fix: the emulated PostgreSQL engine's execution layer in the rds crate's SQL data plane — large text/aggregate results (string_agg, concatenation, md5 over them) must not be bounded by the backing store's value limit, and no backing-store error text may be surfaced to a client; any genuine limit must be reported as the PostgreSQL condition for that limit.
Traces: rds.copy-from-stdin-bulk-load-rejects-a-malformed-row.

=== Cause 2 of 4: ALTER ROLE on the RDS-owned rdsadmin role is accepted instead of refused ===
AWS: recorded behavior only; the rule is documented at https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Appendix.PostgreSQL.CommonDBATasks.Roles.rds_superuser.html — the master user is a member of rds_superuser and is NOT a superuser, so it cannot modify RDS-owned roles. `ALTER ROLE rdsadmin NOLOGIN` is refused with SQLSTATE 42501 and primary message `cannot alter "rdsadmin"` (fixed text `cannot alter "` + the role name from the statement + `"`), and rdsadmin is left unchanged (pg_roles.rolcanlogin stays true). The same gate refuses `DROP ROLE rds_superuser` with 42501 and `cannot drop "rds_superuser"`.
Emulator: the statement SUCCEEDS — no error is raised at all ("expected the engine to refuse 'ALTER ROLE rdsadmin NOLOGIN', but it succeeded"). The master session can therefore mutate the RDS-owned superuser role. The sibling assertions the check reached first (ALTER SYSTEM refused 42501 "ALTER SYSTEM command is not supported", server-side COPY TO a file refused 0A000 "COPY to a file is not supported") passed, so what is missing is specifically the RDS-owned-role gate; the DROP ROLE rds_superuser half of that gate was never reached and must be fixed with it.
Why: a client exercising the documented privilege boundary sees an over-permissive engine: it can disable or re-shape rdsadmin (and drop predefined roles), which on real RDS is impossible. Negative tests of least-privilege designs pass here and fail on AWS, and a tenant could render the managed role unusable.
Fix: the role-management privilege gate in the emulated PostgreSQL engine's ALTER ROLE / DROP ROLE path in the rds crate's SQL data plane — refuse statements targeting RDS-owned/predefined roles (rdsadmin, rds_superuser and the other rds_* roles) for a non-superuser master with 42501 and the messages above, leaving the target role unchanged.
Traces: rds.pg-master-user-not-superuser-alter-system-rejected.

=== Cause 3 of 4: pg_read_file/pg_ls_dir do not exist in the emulated engine, so a privilege refusal comes back as a parser error ===
AWS: recorded behavior only; the role boundary is documented at https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Appendix.PostgreSQL.CommonDBATasks.Roles.html — the RDS master user is NOT a member of pg_read_server_files, pg_write_server_files or pg_execute_server_program. The functions themselves exist in every PostgreSQL catalog, so `SELECT pg_read_file('<path>')` is planned and then refused at execution with SQLSTATE 42501 and primary message `permission denied for function pg_read_file`; `SELECT pg_ls_dir('<path>')` is refused with 42501 and `permission denied for function pg_ls_dir` (fixed text `permission denied for function ` + the function name). The session stays usable afterwards.
Emulator: the call is refused with SQLSTATE 42601 and message `syntax error at or near "pg_read_file"` — a parse-time rejection, i.e. the function is not in the emulated catalog at all. The pg_ls_dir assertion was never reached and fails for the same reason.
Why: the wrong SQLSTATE class makes a security boundary indistinguishable from a client-side typo: 42601 says "your SQL is malformed", 42501 says "you lack the privilege". A client (or a compliance check) asserting that server-side file access is denied cannot confirm it, and any legitimate query referencing these catalog functions is unparseable here while it parses on AWS.
Fix: the emulated PostgreSQL engine's catalog/function resolution plus its default-role privilege check in the rds crate's SQL data plane — register pg_read_file, pg_ls_dir (and the sibling server-file/program functions) so they resolve, and refuse their execution for a caller lacking pg_read_server_files/pg_write_server_files/pg_execute_server_program with 42501 and the message above.
Traces: rds.postgres-admin-user-lacks-pg-read-server-files-role.

=== Cause 4 of 4: Endpoint.Port reports an ephemeral local listener port instead of the Port the instance was created with ===
AWS: Smithy: CreateDBInstanceMessage$Port — "The port number on which the database accepts connections. Valid Values: 1150-65535. Default: ... RDS for PostgreSQL - 5432"; Endpoint$Port — "Specifies the port that the database engine is listening on." So CreateDBInstance(Engine=postgres, Port=P) with P in 1150-65535 must publish Endpoint.Port == P on the available instance, the engine must accept a session on P, and in that session `current_setting('port')` must be the string form of P and `inet_server_port()` must be P.
Emulator: Endpoint.Port is a value drawn from the host's dynamic port range — the requested port is discarded ("Endpoint.Port must be the requested 5439; got 42777"; the concrete number is per-run and environment-specific, the requirement is only that it equal the requested/defaulted port). This is the same defect class as Cause 1 of the open issue 20261108T051751Z-rds-7-net-new-causes-endpoint-port-is.md, whose replay keys cover two different checks (engine-default port on aurora-postgresql/postgres) and not this one, which supplies Port explicitly; the server-side `current_setting('port')`/`inet_server_port()` half is additionally unverified behind it.
Why: Endpoint.Port is the contract a client builds its connection string, security-group rule, proxy target or CNAME from; publishing the emulator's own socket placement means every such artifact is wrong, and "the instance listens on the port I asked for" — true of every real RDS instance — is false here.
Fix: the instance endpoint projection in the rds crate's CreateDBInstance/DescribeDBInstances serializers and the Port recorded in instance state — store the requested (or engine-default) port and publish it, decoupled from whatever local socket the data plane binds, and have the emulated engine report that port as its own configured/session port.
Traces: rds.postgres-custom-port-is-the-published-and-listening-port.

## Steps to Reproduce
Cause 1: CreateDBInstance(Engine=postgres, AllocatedStorage=20, DBName=simparitydb), wait available, connect with psycopg to Endpoint.Address:Endpoint.Port; CREATE TABLE t (id INT PRIMARY KEY, label TEXT NOT NULL, amount NUMERIC(12,4) NOT NULL, tag TEXT); drive `COPY t FROM STDIN WITH (FORMAT text)` with 50,000 tab-separated rows; then run `SELECT md5(string_agg(id::text || label || amount::text, ',' ORDER BY id)) FROM t` — it must return the md5, not an error. Then repeat the COPY into a fresh table with line 25,000's amount set to 'not-a-number': it must be refused with SQLSTATE 22P02, diag.context `COPY <table>, line 25000, column amount: "not-a-number"`, and that table must hold 0 rows.
Cause 2: on the same postgres instance, as the master user run `ALTER ROLE rdsadmin NOLOGIN` — expect SQLSTATE 42501, message `cannot alter "rdsadmin"`, and `SELECT rolcanlogin FROM pg_roles WHERE rolname='rdsadmin'` still true; then run `DROP ROLE rds_superuser` — expect 42501, `cannot drop "rds_superuser"`, with pg_has_role(current_user,'rds_superuser','MEMBER') still true. Positive controls: CREATE/GRANT/DROP of an ordinary role and `SET work_mem='64MB'` must succeed.
Cause 3: on the same instance, as the master user run `SELECT pg_read_file('/etc/hostname')` — expect SQLSTATE 42501 and `permission denied for function pg_read_file`; then `SELECT pg_ls_dir('/tmp')` — expect 42501 and `permission denied for function pg_ls_dir`; `SELECT pg_has_role(current_user,'pg_read_server_files','MEMBER')` must be false while `pg_has_role(current_user,'rds_superuser','MEMBER')` is true, and the session must stay usable (`SELECT current_user, current_database()`).
Cause 4: CreateDBInstance(Engine=postgres, Port=5439, …), poll to available, read Endpoint.Port (must be 5439), open a TLS-required psycopg session on that port, and read `SELECT current_setting('port'), inet_server_port()` (must be ('5439', 5439)).
