# ec2__ecs__servicediscovery: an EC2 launch-type task carries no containerInstanceArn — RunTask and DescribeTasks omit the placement entirely, so no caller can tell which container instance hosts a task

> _Note: this issue was identified against the code base at commit `9de0dc732b013e7abf09d4b752737b31a8a239ee`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeTasks

## Description
Cause 1 of 1: the emulator places EC2 launch-type tasks without ever recording (or serializing) the container instance that hosts them, so the `Task` structure returned by BOTH RunTask and DescribeTasks has no `containerInstanceArn` member at all. Both ECS-on-EC2 checks now get past container-instance registration (the capacity helper obtains an ACTIVE, agent-connected container instance ARN and its registeredResources MEMORY) and then fail on the very first read of the placement. Failing check ids: ec2__ecs__servicediscovery.ecs-on-ec2-places-a-task-that-ecs-auto-registers-in-cloud-map (DescribeTasks), ec2__ecs__servicediscovery.ecs-run-task-is-blocked-by-insufficient-memory-on-the-only-container-instance (RunTask).

  AWS: Smithy — ecs#Task declares the member `containerInstanceArn` (target String), documented "The ARN of the container instances that host the task."; `Task` is the element type of DescribeTasksResponse.tasks and RunTaskResponse.tasks alike. For a task whose `launchType` is `EC2` (or `EXTERNAL`), AWS populates it with the ARN of the container instance the scheduler chose — the same ARN ListContainerInstances returns for that cluster and DescribeContainerInstances describes, in the long `arn:aws:ecs:<region>:<account>:container-instance/<cluster>/<uuid>` form. It is present from the moment RunTask returns the task (RunTask's 200 body already names the placement) and stays present for the task's whole lifetime, including after it reaches STOPPED. The member is absent only for tasks with no host of their own, i.e. `launchType` FARGATE. Nothing in the model makes it optional for EC2 launch type; the pairing of an EC2 task with a container instance is recorded behavior, confirmed by the recordings in which the registered instance's ARN is exactly the value both checks compare against.

  Emulator: the key is simply not in the response map. Check 1 creates an ECS service with launchType=EC2 and desiredCount=1 on a cluster holding exactly one registered container instance, waits until DescribeServices reports runningCount >= desiredCount >= 1, confirms ListTasks returns exactly one taskArn and DescribeTasks reports lastStatus RUNNING — and then dies with `KeyError: 'containerInstanceArn'` at `assert task["containerInstanceArn"] == capacity["container_instance_arn"]` (check line 481). Check 2 calls RunTask(cluster, taskDefinition=<128 MiB family>, count=1, launchType="EC2"), gets `failures == []` and exactly one entry in `tasks` — so the emulator did accept and place the task — and then dies with `KeyError: 'containerInstanceArn'` at `assert placed["tasks"][0]["containerInstanceArn"] == capacity["container_instance_arn"]` (check line 317). Both are plain missing-member errors, not a wrong value: the response is a successful 200 whose Task object has no placement member to compare.

  Why: `containerInstanceArn` is the only link from a task back to the host that runs it, so a client that relies on AWS's behavior loses every EC2-launch-type placement decision. Schedulers and drain/replacement tooling cannot tell which instance to cordon before DeregisterContainerInstance, cannot verify a placement constraint such as distinctInstance or a memberOf attribute expression actually took effect, and cannot correlate a task with the EC2 instance id, availability zone or ENI it shares with its host. Observability and cost-attribution code that groups tasks per container instance sees every task as unplaced. In check 2 the omission also hides the subject of the scenario: with no way to attribute the control task to the only instance in the cluster, the contrast the check exists for — an oversized definition must come back HTTP 200 with `tasks: []` and exactly one `failures` entry whose `reason` is the structured code `RESOURCE:MEMORY` and whose `arn` is the SHORT container-instance ARN form (without the `/<cluster>/` segment DescribeContainerInstances returns) — is never reached, so a placement refusal cannot be distinguished from an empty cluster. Code doing `task["containerInstanceArn"]` (the normal, non-defensive idiom for an EC2 task) raises KeyError rather than reading a value.

  Fix: the ECS task-placement path and the Task serializer. Whatever chooses a host for an EC2/EXTERNAL launch-type task (the RunTask handler and the service scheduler that creates tasks for an ECS service) must record the selected container instance on the task's state record, and the Task serializer shared by RunTask, DescribeTasks, ListTasks-backed reads and the task-state-change surface must emit `containerInstanceArn` for every task that has a host, in the long container-instance ARN form, while continuing to omit it for FARGATE tasks. The placement must be chosen from the cluster's ACTIVE, agent-connected container instances and must respect their registeredResources, so the same record is what the memory-refusal path attributes its failure to.

  Related open issue, which does NOT cover this: 20261109T013300Z-ec2-ecs-servicediscovery-an-ec2-instance-launched-from.md filed the earlier stall in the same two checks — an EC2 instance with ECS_CLUSTER user data never auto-registering as a container instance, keyed on the ListContainerInstances poll timeout. That step now succeeds and both checks fail later, on this missing member, which that issue's keys and description do not name.

  Traces: ec2__ecs__servicediscovery.ecs-on-ec2-places-a-task-that-ecs-auto-registers-in-cloud-map (DescribeTasks on a service-placed task, check line 481), ec2__ecs__servicediscovery.ecs-run-task-is-blocked-by-insufficient-memory-on-the-only-container-instance (RunTask's own 200 body, check line 317).

## Evidence
Expected (AWS): with one ACTIVE agent-connected container instance in the cluster, `ecs run-task --cluster <cluster> --task-definition <family> --launch-type EC2 --count 1` returns HTTP 200 whose `tasks[0]` includes `containerInstanceArn` set to that instance's ARN (long form `arn:aws:ecs:<region>:<account>:container-instance/<cluster>/<uuid>`), and `ecs describe-tasks --cluster <cluster> --tasks <taskArn>` returns the same member for the running task. The ARN value is per-run; its PRESENCE and its equality with the ARN ListContainerInstances/DescribeContainerInstances report for the host are the requirement.

Actual (emulator):
- Check ec2__ecs__servicediscovery.ecs-run-task-is-blocked-by-insufficient-memory-on-the-only-container-instance — RunTask returns 200 with `failures == []` and exactly one entry in `tasks`, but that Task object has no `containerInstanceArn` member: `KeyError: 'containerInstanceArn'` raised at `assert placed["tasks"][0]["containerInstanceArn"] == capacity["container_instance_arn"]`, check line 317.
- Check ec2__ecs__servicediscovery.ecs-on-ec2-places-a-task-that-ecs-auto-registers-in-cloud-map — the EC2 launch-type service reaches runningCount 1, ListTasks returns exactly one taskArn, DescribeTasks reports `lastStatus == "RUNNING"`, and the same member is absent: `KeyError: 'containerInstanceArn'` raised at `assert task["containerInstanceArn"] == capacity["container_instance_arn"]`, check line 481.

Every preceding call in both checks succeeds (CreateVpc/subnet/IGW/route, IAM role+instance profile, SSM GetParameter for the ECS-optimized AMI, EC2 RunInstances, ECS CreateCluster, RegisterTaskDefinition, ListContainerInstances returning one ARN, DescribeContainerInstances reporting ACTIVE + agentConnected + registeredResources MEMORY, CreatePrivateDnsNamespace to SUCCESS, CreateService / RunTask), which isolates the divergence to the Task structure's placement member. Both failures are missing-member KeyErrors on a successful 200 response, not value mismatches and not per-run-value differences.

## Steps to Reproduce
1. `ecs create-cluster --cluster-name <cluster>` and bring up exactly one container instance in it (launch an instance from the ECS-optimized AMI with `ECS_CLUSTER=<cluster>` user data and an instance profile holding AmazonEC2ContainerServiceforEC2Role), then wait until `ecs list-container-instances --cluster <cluster>` returns one ARN and `ecs describe-container-instances` reports it `ACTIVE` with `agentConnected: true` and a `registeredResources` MEMORY above 128.
2. `ecs register-task-definition` with requiresCompatibilities EC2, bridge networking, memory 128, one container mapping containerPort 80 to hostPort 0.
3. `ecs run-task --cluster <cluster> --task-definition <family> --count 1 --launch-type EC2`. Inspect the response: on AWS `tasks[0].containerInstanceArn` is the ARN from step 1; on the emulator the member is absent from `tasks[0]`.
4. `ecs describe-tasks --cluster <cluster> --tasks <taskArn from step 3>`. On AWS `tasks[0].containerInstanceArn` is again that ARN; on the emulator it is absent.
5. Same via a service: `ecs create-service --cluster <cluster> --service-name <name> --task-definition <family> --desired-count 1 --launch-type EC2 --scheduling-strategy REPLICA`, wait for runningCount 1, `ecs list-tasks --cluster <cluster> --service-name <name>`, then `ecs describe-tasks` on that taskArn — the member is absent on the emulator.
6. Confirm the member is correctly omitted only for FARGATE: run the same task definition with `--launch-type FARGATE` and expect no `containerInstanceArn`.
