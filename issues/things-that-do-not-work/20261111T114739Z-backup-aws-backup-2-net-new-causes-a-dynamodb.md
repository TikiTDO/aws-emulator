# AWS Backup: 2 net-new causes — a DynamoDB restore drops the source table's secondary indexes (so CreateTable refuses the carried-over AttributeDefinitions and the restore job ends FAILED), and the restored table holds none of the backed-up items

> _Note: this issue was identified against the code base at commit `85d4e2e507e1d419cd5d78e6f9826baf71120c33`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartRestoreJob

## Description
Two net-new root causes in the AWS Backup emulator's DynamoDB restore arm. Both live in the restore-execution path that StartRestoreJob performs (services/service-com-amazonaws-backup-cryocontrollerusermanager/src/state/restore_execution.rs, restore_dynamodb_table). They are numbered below and each carries its own failing check ids; both must be closed before this work item is submitted. The check fails at Cause 1 first, so Cause 2's assertion is only reached once Cause 1 is fixed — fixing Cause 1 alone will leave the check failing.

=== Cause 1 of 2: the restore recreates the table with the source's AttributeDefinitions but WITHOUT its GlobalSecondaryIndexes/LocalSecondaryIndexes, so DynamoDB refuses the CreateTable and the restore job ends FAILED ===
AWS: Smithy (backup model, services/service-com-amazonaws-backup-cryocontrollerusermanager/smithy-model/com-amazonaws-backup-cryocontrollerusermanager.json): StartRestoreJob is PUT /restore-jobs, success 200, and "Recovers the saved resource identified by an Amazon Resource Name (ARN)" — the resource it recovers is the protected resource, i.e. the table with the shape it had when it was backed up. The DynamoDB model (services/service-com-amazonaws-dynamodb-dynamodb-20120810) types CreateTableInput with AttributeDefinitions, KeySchema, LocalSecondaryIndexes and GlobalSecondaryIndexes as separate members, and DynamoDB's own validation requires every AttributeDefinition to be used by some KeySchema — a table's own or one of its indexes'. Recorded behavior: an on-demand AWS Backup of a DynamoDB table that has a GSI restores to a table that carries the SAME index (same IndexName, same index KeySchema, same Projection.ProjectionType), that index reaching IndexStatus ACTIVE with the table ACTIVE, and the restore job reaching DescribeRestoreJob Status COMPLETED. (AWS documents this for restoring DynamoDB: https://docs.aws.amazon.com/aws-backup/latest/devguide/restoring-dynamodb.html .)
Emulator: restore_dynamodb_table reads the source table with DescribeTable and then builds CreateTable from only key_schema, attribute_definitions, billing mode / provisioned throughput and (optionally) tags — the source TableDescription's global_secondary_indexes and local_secondary_indexes are never carried over. For any source table with an index, the carried-over AttributeDefinitions therefore contain an attribute no KeySchema uses, and the emulator's own DynamoDB correctly refuses the CreateTable with HTTP 400, Error code "ValidationException" and message "Some AttributeDefinitions are not used in any KeySchema: <the index-only attribute names>" (in the replay: "Some AttributeDefinitions are not used in any KeySchema: owner", where "Some AttributeDefinitions are not used in any KeySchema: " is DynamoDB's fixed text and "owner" is the GSI hash-key attribute taken from the source table — it is a value from the request/state, not part of the template). perform_restore maps that refusal to RestoreOutcome::Failed, so the restore job moves to Status 'FAILED' with StatusMessage "the restored table could not be created: service error: unhandled error (ValidationException): ... Some AttributeDefinitions are not used in any KeySchema: owner ..." instead of ever reaching COMPLETED. The restore is thus not merely index-less: it produces NO table at all whenever the source table has any secondary index.
Why: a client that backs up any realistically-shaped DynamoDB table (practically every table with a GSI or LSI) can never restore it — the restore job terminates FAILED and no target table is created, so disaster-recovery rehearsals, restore-test tooling and any code that polls DescribeRestoreJob for COMPLETED all break, and the StatusMessage blames a DynamoDB validation error the caller never caused and cannot correct through the API. Even if the table were created, an index-less restore would silently lose the query paths the application depends on.
Fix: the DynamoDB arm of the restore execution — services/service-com-amazonaws-backup-cryocontrollerusermanager/src/state/restore_execution.rs, restore_dynamodb_table: carry the source TableDescription's GlobalSecondaryIndexes and LocalSecondaryIndexes (IndexName, KeySchema, Projection, and per-index throughput where the billing mode requires it) onto the CreateTable request alongside the AttributeDefinitions and KeySchema it already copies, so the AttributeDefinitions it forwards are all used and the restored table has the source's index shape.
Traces: backup.ondemand-dynamodb-backup-restore-keeps-global-secondary-index.

=== Cause 2 of 2: a completed DynamoDB restore produces an EMPTY table — none of the items the recovery point was taken of are restored ===
AWS: recorded behavior only (the Smithy model describes the job, not the data path). Recorded behavior: after the restore job reaches COMPLETED and the restored table and its index are ACTIVE, a Query against the restored table's index for the backed-up item's key returns exactly that item, with all of its attributes as they were at backup time — i.e. the recovery point carries the table's contents and the restore puts them back. AWS Backup's DynamoDB restore is a full-data restore, not a schema-only one.
Emulator: the restore arm performs a bare CreateTable and nothing else; the module's own documentation states "The ITEMS it held are not restored: a backup in this emulator copies no bytes ... so there is nothing captured to put back" (and RecoveryPoint::backup_size_in_bytes stays 0 on the backup side). So even once Cause 1 is fixed, the restored table is empty: the check's final Query on the restored index returns [] where it must return the backed-up item, and the assertion "a query on the restored GSI 'by-owner' must return the backed-up item" fails.
Why: a client uses a restore to get its DATA back. A restore that reports COMPLETED and hands back an empty table is worse than a failure: recovery tooling and any verification step that reads a known row after restore concludes the data is lost, while the job's own status says the recovery succeeded. Backup size reported as 0 bytes gives no hint either.
Fix: the backup/restore data path in the backup crate — capture the protected DynamoDB table's items into the recovery point when StartBackupJob stores it (state.rs / the backup-job execution, which today records no content and leaves backup_size_in_bytes at 0), and write them back into the target table from restore_execution.rs after the CreateTable in the DynamoDB restore arm, so a COMPLETED restore's table answers reads for the backed-up items.
Traces: backup.ondemand-dynamodb-backup-restore-keeps-global-secondary-index.

## Steps to Reproduce
1. dynamodb.CreateTable(TableName=<src>, AttributeDefinitions=[{pk,S},{owner,S}], KeySchema=[{pk,HASH}], GlobalSecondaryIndexes=[{IndexName:'by-owner', KeySchema:[{owner,HASH}], Projection:{ProjectionType:'ALL'}}], BillingMode='PAY_PER_REQUEST'); wait for the table_exists waiter.
2. dynamodb.PutItem(TableName=<src>, Item={'pk':{'S':'order-1'},'owner':{'S':'alice'},'total':{'N':'42'}}); dynamodb.DescribeTable(<src>) and confirm the GSI is reported.
3. iam.CreateRole trusted by backup.amazonaws.com with AWSBackupServiceRolePolicyForBackup and AWSBackupServiceRolePolicyForRestores attached; backup.CreateBackupVault(BackupVaultName=<vault>).
4. backup.StartBackupJob(BackupVaultName=<vault>, ResourceArn=<src table arn>, IamRoleArn=<role>); poll DescribeBackupJob to State COMPLETED and take its RecoveryPointArn.
5. backup.StartRestoreJob(RecoveryPointArn=<rp>, Metadata={'targetTableName': <restored>}, IamRoleArn=<role>, ResourceType='DynamoDB', IdempotencyToken=<token>).
6. Poll backup.DescribeRestoreJob(RestoreJobId=<id>) to a terminal Status. AWS reaches 'COMPLETED'; the emulator reaches 'FAILED' with StatusMessage 'the restored table could not be created: ... (ValidationException): Some AttributeDefinitions are not used in any KeySchema: owner' (Cause 1).
7. On AWS, dynamodb.DescribeTable(TableName=<restored>) reports TableStatus ACTIVE and the same GlobalSecondaryIndexes as the source with IndexStatus ACTIVE; on the emulator the table does not exist.
8. On AWS, dynamodb.Query(TableName=<restored>, IndexName='by-owner', KeyConditionExpression='#o = :o', ExpressionAttributeNames={'#o':'owner'}, ExpressionAttributeValues={':o':{'S':'alice'}}) returns the item from step 2; on the emulator (once step 6 is fixed) it returns [] because no items are restored (Cause 2).
