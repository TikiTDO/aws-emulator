# bedrock-agent-runtime: 2 net-new causes — the OpenSearch Serverless collection endpoint answers the AWS-JSON front door (SerializationException 'missing required header x-amz-target') so no vector index can be created, and CreateAgent is accepted where AWS refuses it

> _Note: this issue was identified against the code base at commit `d7c92a359e65b119da339df847b0735e9ef403e3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Retrieve

## Description
TWO net-new root causes reached through bedrock-agent-runtime checks. Note on overlap: the two knowledge-base checks below are listed in the Issue-Trace-Ids of the open issue 20261023T004328Z-bedrock-agent-runtime-retrieve-optimizeprompt-getagentmemory-deleteagentmemory-and.md, but that issue's cause for them was 'opensearchserverless CreateAccessPolicy is a scaffold stub'. CreateAccessPolicy now answers, and the checks fail one step LATER, on a different defect — so this is a net-new cause, not that one.

=== Cause 1 of 2: a VECTORSEARCH collection's published collectionEndpoint serves the AWS-JSON RPC front door instead of the OpenSearch REST data plane, so index creation is impossible ===
AWS: recorded behavior only (the opensearchserverless Smithy model describes the control plane; the collection data plane is the OpenSearch REST API and is not modeled in Smithy). Recorded behavior: after CreateCollection(type='VECTORSEARCH') reaches ACTIVE, BatchGetCollection reports a `collectionEndpoint`, and a SigV4-signed (service name `aoss`) HTTP PUT of an index body to `https://<collectionEndpoint>/<indexName>` — exactly what opensearch-py's `client.indices.create(index=..., body=...)` issues, with no `x-amz-target` header, because the OpenSearch REST API has no RPC target — is accepted and creates the knn_vector index that a Bedrock knowledge base's OPENSEARCH_SERVERLESS storageConfiguration requires.
Emulator: that same request is answered HTTP 400 with body `{"__type":"SerializationException","message":"missing required header `x-amz-target`"}`. The published collectionEndpoint is wired to the emulator's AWS-JSON protocol dispatcher, which demands an `X-Amz-Target` header, rather than to a REST data plane for the collection. No OpenSearch REST verb can therefore be served on a collection endpoint.
Why: every Bedrock knowledge base backed by OpenSearch Serverless — the standard vector store — is unbuildable, because its vector index can never be created. Retrieval scoring, RetrieveAndGenerate grounding and the Retrieve not-found contract are all unreachable behind this one wall. Downstream, the checks that retry the index create (opensearch-py loop, 12 attempts x 10s) burn their whole budget and are reported as 'Check timed out after 60.0s' rather than as this 400 — the retrieve-nonexistent-knowledge-base-not-found check is one of those, and its timeout is this failure (its setup calls the identical `_create_vector_index` helper against the same endpoint).
Fix: the opensearchserverless collection data plane — the published collectionEndpoint host must be routed to an OpenSearch REST handler (index create/get/delete, document index/search) that authorises SigV4 `aoss` requests against the collection's data-access policy, instead of falling through to the AWS-JSON `x-amz-target` dispatcher (services/service-com-amazonaws-opensearchserverless-opensearchserverless, plus the emulator's endpoint/host routing table that resolves the collection endpoint).
Traces: bedrock-agent-runtime.knowledge-base-retrieval-scoring-deterministic (surfaces the 400 directly, via opensearchpy.exceptions.RequestError), bedrock-agent-runtime.retrieve-nonexistent-knowledge-base-not-found (same endpoint, reported as a 60s timeout inside the index-create retry loop).

=== Cause 2 of 2: bedrock-agent CreateAgent is accepted, where AWS refuses it with AccessDeniedException ===
AWS: recorded behavior only (Smithy models CreateAgent's AccessDeniedException @httpError 403 but not the account condition). Recorded behavior, confirmed live on real AWS: Amazon Bedrock Agents Classic is in per-account maintenance mode — for any account with no prior Agents-Classic usage, CreateAgent is refused 403 AccessDeniedException whose message states the maintenance-mode condition ('... Maintenance Mode. New agent creation is not available for accounts without prior service usage ...'). The refusal is proven to be specific to CreateAgent, not a blanket authorization failure, by a ListAgents positive control in the same credentials that succeeds.
Emulator: CreateAgent SUCCEEDS for the same account and role whose ListAgents control is healthy — no refusal at all.
Why: this is an overly-permissive accept. A client developed against the emulator builds an agent-creation flow that cannot run on AWS, and the negative class (AccessDenied-vs-ResourceNotFound, the only way the sibling checks observe Bedrock's IAM boundary for agents) collapses because the resource can be created here.
Fix: the bedrock-agent CreateAgent handler (services/service-com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda/src/ops/create_agent.rs) — gate agent creation on the account's Agents-Classic eligibility and refuse an ineligible account with 403 AccessDeniedException carrying the maintenance-mode wording, leaving the agent list/read plane unaffected.
Traces: bedrock-agent-runtime.e2e-session-invoke-memory-teardown.

## Evidence
Cause 1 — expected: `PUT https://<collectionEndpoint>/<indexName>` (SigV4 `aoss`, opensearch-py indices.create) accepted and the knn_vector index created. actual: HTTP 400, `opensearchpy.exceptions.RequestError: RequestError(400, '{"__type":"SerializationException","message":"missing required header `x-amz-target`"}')` — raised from opensearchpy http_requests.py perform_request -> base.py _raise_error. The companion check that retries the same call 12x10s is reported as 'Error: Check timed out after 60.0s'.
Cause 2 — expected: bedrock-agent CreateAgent refused 403 AccessDeniedException (Agents-Classic maintenance mode) while ListAgents on the same credentials succeeds. actual: AssertionError 'CreateAgent unexpectedly succeeded -- this account may have gained Agents-Classic eligibility; this check needs re-auditing against a prepare/invoke/memory flow instead of the withdrawal' — i.e. the emulator returned a created agent.
