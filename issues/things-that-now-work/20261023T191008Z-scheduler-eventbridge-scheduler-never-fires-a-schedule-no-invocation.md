# EventBridge Scheduler never fires a schedule: no invocation/dispatch engine, so no target is ever invoked

> _Note: this issue was identified against the code base at commit `3dc196f76d19116b5d570e1dc438e2b93d0e0d47`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateSchedule

## Description
Single root cause (1 of 1): the scheduler emulator implements the control plane only. A schedule is persisted and read back faithfully, but nothing ever evaluates its ScheduleExpression and nothing ever invokes its Target, so no occurrence is ever delivered to any target type (SQS, SNS, Lambda, Step Functions, EventBridge bus, or a universal `aws-sdk` target), no DLQ entry is ever produced, and no retry is ever attempted.

AWS: EventBridge Scheduler is a data-plane service. A schedule in State=ENABLED fires at each occurrence of its ScheduleExpression (`at(...)` once, `rate(...)`/`cron(...)` recurring), interpreted in ScheduleExpressionTimezone, bounded by StartDate/EndDate and jittered inside FlexibleTimeWindow; at each occurrence it assumes Target.RoleArn and invokes Target.Arn with Target.Input verbatim (or with the Input template's `<aws.scheduler.scheduled-time>` / `<aws.scheduler.execution-id>` substitutions), applies Target.RetryPolicy on failure, and routes a terminally failed invocation to Target.DeadLetterConfig.Arn. ActionAfterCompletion=DELETE removes the schedule once it completes. Smithy (scheduler model, CreateSchedule input): `ScheduleExpression` (required) "The expression that defines when the schedule runs ... at expression - at(yyyy-mm-ddThh:mm:ss), rate expression - rate(value unit), cron expression - cron(fields)"; `State` (ENABLED|DISABLED) "Specifies whether the schedule is enabled or disabled"; `Target` (required) "The schedule's target"; `FlexibleTimeWindow` "Allows you to configure a time window during which EventBridge Scheduler invokes the schedule".

Emulator: CreateSchedule's handler (services/service-com-amazonaws-scheduler-awschronosservice/src/ops/create_schedule.rs) validates the flexible window and the execution role, then only inserts a `ScheduleRecord` into the in-memory store and returns the ARN; the state module (src/state.rs) documents nothing but storage, group lifecycle and paging — there is no timer, no occurrence computation, no target dispatcher, no retry/DLQ path. Every delivery-observing check in the suite exhausts its poll window and none ever observes a single invocation: 60+ checks across six target services end in `Check timed out after 60.0s` while polling the target (ReceiveMessage / log scan / ListExecutions / ListInvalidations), and NOT ONE delivery-observing check in the suite passes.

Why: every client that uses Scheduler for its actual purpose is broken against this emulator. A cron/rate/one-time schedule silently never runs, so a workload that enqueues work, starts a state machine, invalidates a CDN path, stops an RDS instance or publishes an event on a timer appears healthy at the control plane (CreateSchedule 200, GetSchedule ENABLED) and produces nothing. Negative expectations are equally unverifiable: 'disabled schedule does not fire', 'deleted group stops firing', 'denied role dead-letters' all look correct for the wrong reason.

Fix: this is a missing component, not a handler bug — the service needs an occurrence scheduler plus a target-invocation path in the scheduler crate (services/service-com-amazonaws-scheduler-awschronosservice/src/, alongside src/state.rs's `ScheduleRecord` and src/ops/create_schedule.rs | update_schedule.rs | delete_schedule.rs | delete_schedule_group.rs, which must arm/disarm it), covering expression evaluation + timezone, StartDate/EndDate bounds, FlexibleTimeWindow jitter, Input/Input-template rendering, role assumption, RetryPolicy, DeadLetterConfig and ActionAfterCompletion.

Note on the lambda-target checks listed below (`lambda__scheduler.scheduler-lambda-*`, `lambda__scheduler__sqs.*`, `dynamodb__lambda__scheduler.*`): those additionally require Lambda Invoke, which is already owned by 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md. Re-replay them after both land; the non-lambda targets in this list are sufficient to confirm this fix on their own.

Traces: every check id in trace_ids; representative bodies: scheduler.e2e-schedule-to-sqs-fire-and-receive (rate(1 minute) SQS target, polls 90s, 'schedule never delivered its first invocation to SQS'), scheduler.schedule-fire-delivers-to-target (240s poll, 'schedule never delivered a message to the target queue'), cloudfront__scheduler.xsvc-cloudfront-3-scheduler-one-time-invalidation-applies-exact-paths (universal aws-sdk target).

## Evidence
Expected: a schedule with State=ENABLED and ScheduleExpression rate(1 minute)/cron(...)/at(...) delivers Target.Input to Target.Arn at each occurrence, honouring StartDate/EndDate, FlexibleTimeWindow, RetryPolicy, DeadLetterConfig and ActionAfterCompletion.
Actual: CreateSchedule 200 and GetSchedule reports State=ENABLED with the submitted Target, but no target ever receives anything. 60+ delivery-observing checks exhaust their poll loops ('Check timed out after 60.0s'); zero delivery-observing checks pass. Source confirms the gap: src/ops/create_schedule.rs's handle() ends at `store.schedules.insert(...)` / `Ok(CreateScheduleOutput { schedule_arn: arn })` and src/state.rs holds only `ScheduleRecord` storage, group-deletion settling and paging — no timer or dispatcher exists anywhere in the crate.

## Steps to Reproduce
1. sqs.create_queue(QueueName=q) and read its QueueArn.
2. iam.create_role with a trust policy for scheduler.amazonaws.com and an inline sqs:SendMessage policy on that queue ARN.
3. scheduler.create_schedule(Name=n, ScheduleExpression='rate(1 minute)', FlexibleTimeWindow={'Mode':'OFF'}, State='ENABLED', Target={'Arn': queue_arn, 'RoleArn': role_arn, 'Input': '{"marker":"x"}'}).
4. scheduler.get_schedule(Name=n) -> State ENABLED, Target as submitted.
5. Poll sqs.receive_message(QueueUrl=q, WaitTimeSeconds=10) for several minutes: on AWS the marker arrives within about one minute; on the emulator the queue stays empty forever. Same result with an SNS, Step Functions, EventBridge or `arn:aws:scheduler:::aws-sdk:<service>:<operation>` target, and no DLQ message is ever produced for a denied role or a missing target.
