# bedrock-agent direct document ingestion and read-back surface diverges: ingest is refused and every document read reports NOT_FOUND or nothing (5 causes)

> _Note: this issue was identified against the code base at commit `d5d5092b5af2686a6a1d42f09a764e6dd1daf2a1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
IngestKnowledgeBaseDocuments

## Description
FIVE net-new root causes on bedrock-agent's direct knowledge-base document surface (IngestKnowledgeBaseDocuments / GetKnowledgeBaseDocuments / ListKnowledgeBaseDocuments), all reached by replaying the wire corpus. None of the seven divergence clusters behind them is marked stub-blocked or owned by an open issue. Causes 2-5 are read-back semantics that Cause 1 currently hides: a fixer must close each one separately and re-replay each named fixture step, because fixing Cause 1 alone does not establish that the read-backs then report what AWS reports.

=== Cause 1 of 5: IngestKnowledgeBaseDocuments refuses a CUSTOM document addressed at a managed-connector data source with 400 instead of accepting it 202 ===
AWS: Smithy (services/service-com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda/smithy-model/com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda.json): IngestKnowledgeBaseDocuments http {method: PUT, uri: /knowledgebases/{knowledgeBaseId}/datasources/{dataSourceId}/documents, code: 202}; input knowledgeBaseId/dataSourceId (@httpLabel, @pattern ^[0-9a-zA-Z]{10}$, required) and documents (KnowledgeBaseDocuments, @length 1..10, required); output documentDetails (KnowledgeBaseDocumentDetails); modeled errors AccessDeniedException 403, InternalServerException 500, ResourceNotFoundException 404, ServiceQuotaExceededException 402, ThrottlingException 429, ValidationException 400. Smithy: DocumentContent.dataSourceType targets ContentDataSourceType, whose complete value set is CUSTOM | S3; DataSourceConfiguration.type targets DataSourceType = S3 | WEB | CONFLUENCE | SALESFORCE | SHAREPOINT | CUSTOM | REDSHIFT_METADATA | MANAGED_KNOWLEDGE_BASE_CONNECTOR. Recorded behavior: a CUSTOM/IN_LINE document PUT at the data source of a MANAGED knowledge base is ACCEPTED with HTTP 202 and documentDetails carrying one entry per submitted document, with knowledgeBaseId, dataSourceId, identifier.dataSourceType=CUSTOM, identifier.custom.id echoing the submitted custom document id, status STARTING and an updatedAt timestamp.
Emulator: the request is refused with HTTP 400 and no documentDetails at all. Hypothesis (from the handler source, services/service-com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda/src/ops/ingest_knowledge_base_documents.rs:210 and :261-274): the per-document guard compares document.content.dataSourceType (only ever CUSTOM or S3) against the stored data source's dataSourceConfiguration.type by raw string equality, so a data source whose type is the connector enum MANAGED_KNOWLEDGE_BASE_CONNECTOR matches no document content and the ValidationException is unsatisfiable. The requirement is the status and the body: the content kind must be resolved against the data source's CONTENT kind (a managed connector whose connectorParameters.type is CUSTOM takes CUSTOM documents), and the ValidationException must be reserved for a content kind that really does not correspond to the addressed data source.
Why: direct ingestion into a managed knowledge base is impossible. No value of content.dataSourceType the model permits is accepted, so a client cannot load a single document, and every workflow built on it (ingest, poll to INDEXED, list, delete) dies at the first call with an error that blames the caller's input.
Fix: the IngestKnowledgeBaseDocuments handler's validation stage in the bedrock-agent crate (src/ops/ingest_knowledge_base_documents.rs, the content-kind/data-source-kind guard and its message helper crate::state::document_data_source_type_message). Not the serializer: the 202 output shape is correct, the request never reaches it.
Related open work that does NOT cover this (neither carries this fixture step's replay key): 20261106T140124Z-bedrock-agent-runtime-ingestknowledgebasedocuments-refuses-a-custom-document.md records the same refusal from the BEHAVIORAL corpus under the separate bedrock-agent-runtime service token, and 20261105T115813Z-bedrock-agent-deleteknowledgebasedocuments-stub.md owns only DeleteKnowledgeBaseDocuments.
Traces: bedrock-agent-knowledge-base-documents-delete-workflow#setup#5, bedrock-agent-knowledge-base-documents-ingest-and-list#task#5.

=== Cause 2 of 5: GetKnowledgeBaseDocuments never reports an ingested document as INDEXED and returns a placeholder detail with no updatedAt ===
AWS: Smithy: GetKnowledgeBaseDocuments http {method: POST, uri: /knowledgebases/{knowledgeBaseId}/datasources/{dataSourceId}/documents/getDocuments, code: 200}, input documentIdentifiers (@length 1..10, required), output documentDetails. KnowledgeBaseDocumentDetail requires knowledgeBaseId, dataSourceId, status (DocumentStatus = INDEXED | PARTIALLY_INDEXED | PENDING | FAILED | METADATA_PARTIALLY_INDEXED | METADATA_UPDATE_FAILED | IGNORED | NOT_FOUND | STARTING | IN_PROGRESS | DELETING | DELETE_IN_PROGRESS) and identifier, and carries updatedAt (DateTimestamp, @timestampFormat date-time), documented as "The date and time at which the document was last updated"; status is documented as the ingestion status, STARTING when the ingestion was submitted. Recorded behavior: after the document is ingested, a Get on its identifier reports status STARTING and then INDEXED within the fixture's polling window, with updatedAt present on every detail.
Emulator: the detail comes back with status NOT_FOUND and NO updatedAt member, and it stays NOT_FOUND for the whole 60s / 21-attempt poll window, so the document never reaches a terminal ingestion state. The store holds no record for the identifier (src/ops/get_knowledge_base_documents.rs:236-247 falls back to crate::state::not_found_document_detail, which omits updatedAt).
Why: the documented poll-to-INDEXED contract is unusable — a client waits out its timeout and then sees NOT_FOUND, which it must read as "this document was never submitted", so an ingestion pipeline cannot tell a lost document from one still indexing, and code that reads detail.updatedAt gets a missing member on a required-shape read.
Fix: the document state machine in the bedrock-agent crate's state (crate::state::DocumentRecord::starting / to_detail and state.materialise_due_transitions, read by src/ops/get_knowledge_base_documents.rs) — a document stored by an accepted ingestion must progress STARTING -> INDEXED on the clock, and every detail (including the not-found placeholder) must carry updatedAt.
Traces: bedrock-agent-knowledge-base-documents-ingest-and-list#task#6, bedrock-agent-knowledge-base-documents-ingest-and-list#task#7, bedrock-agent-knowledge-base-documents-delete-workflow#task#6.

=== Cause 3 of 5: ListKnowledgeBaseDocuments reports an empty page for a data source that holds ingested documents ===
AWS: Smithy: ListKnowledgeBaseDocuments http {method: POST, uri: /knowledgebases/{knowledgeBaseId}/datasources/{dataSourceId}/documents, code: 200}, output documentDetails (required, paginated with nextToken/maxResults). Recorded behavior: after two documents are ingested into the data source, the listing returns one detail per ingested document, each with status INDEXED, identifier.dataSourceType CUSTOM, its own custom id, and updatedAt.
Emulator: documentDetails is an empty list — the data source holds no document record, so state.page_of_documents (src/ops/list_knowledge_base_documents.rs:255) pages an empty collection.
Why: a client enumerating what a knowledge base holds concludes the data source is empty, so reconciliation loops re-ingest or report data loss, and pagination over documents can never be exercised.
Fix: the document store the listing pages (crate::state::page_of_documents and the records IngestKnowledgeBaseDocuments writes) — once an ingestion is accepted (Cause 1) its documents must be enumerable with their current status and updatedAt.
Traces: bedrock-agent-knowledge-base-documents-ingest-and-list#task#9.

=== Cause 4 of 5: after a document is deleted, ListKnowledgeBaseDocuments drops it instead of listing it with status NOT_FOUND ===
AWS: Smithy: DocumentStatus includes NOT_FOUND, DELETING and DELETE_IN_PROGRESS as document statuses, and KnowledgeBaseDocumentDetail.status is required — so a deleted document is reported as a document whose STATUS says it is gone, not as an absent list entry. Recorded behavior: after DeleteKnowledgeBaseDocuments removes the document, the listing still returns one detail for it with status NOT_FOUND, its identifier (dataSourceType CUSTOM, the same custom id) and updatedAt.
Emulator: documentDetails is empty — the deleted (in fact never-stored) document contributes no entry at all.
Why: a client that confirms a deletion by listing cannot distinguish "deleted" from "never existed" and cannot observe the NOT_FOUND terminal state the API documents, so a delete-and-verify workflow has no positive signal to key on.
Fix: the delete path and the listing's view of a deleted document in the bedrock-agent crate's document state — a deleted document must remain visible to ListKnowledgeBaseDocuments with status NOT_FOUND rather than being dropped from the page. Related open work that does NOT cover this: 20261105T115813Z-bedrock-agent-deleteknowledgebasedocuments-stub.md owns the unimplemented DeleteKnowledgeBaseDocuments operation itself; this cause is the LISTING semantics that must hold once that operation exists, and that issue does not carry this fixture step's replay key.
Traces: bedrock-agent-knowledge-base-documents-delete-workflow#task#8.

=== Cause 5 of 5: a multi-identifier GetKnowledgeBaseDocuments answers with placeholder details whose order does not match the recorded response ===
AWS: Smithy: GetKnowledgeBaseDocuments takes documentIdentifiers (@length 1..10) and returns documentDetails, one detail per identifier asked about. Recorded behavior: a Get naming two ingested custom documents returns both details with status INDEXED and updatedAt, in the recorded response's order (the guide document first, then the faq document).
Emulator: both details come back with status NOT_FOUND and no updatedAt, and the two entries appear in the opposite position from the recording, so the positional comparison reports both entries as mismatched. The handler emits one detail per identifier in request order (src/ops/get_knowledge_base_documents.rs:212-248). Hypothesis: the recorded service orders the details other than by request position; the requirement this cause carries is the detail CONTENT for a multi-document read — each requested identifier must come back with its own ingested document's status (INDEXED) and updatedAt — plus details ordered as AWS returns them for the same request.
Why: a client that zips its request list against documentDetails by position pairs each document with the wrong detail, and one that reads status sees NOT_FOUND for documents it just ingested.
Fix: the GetKnowledgeBaseDocuments handler's per-identifier resolution and detail ordering (src/ops/get_knowledge_base_documents.rs) together with the document records it reads.
Traces: bedrock-agent-knowledge-base-documents-ingest-and-list#task#8.
