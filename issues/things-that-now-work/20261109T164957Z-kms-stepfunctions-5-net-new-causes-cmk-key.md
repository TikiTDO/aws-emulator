# kms__stepfunctions: 5 net-new causes — CMK key state and KMS authorization are never evaluated for encrypted state machines, activities and executions, includedData=METADATA_ONLY is ignored, and kmsKeyId is echoed unresolved

> _Note: this issue was identified against the code base at commit `e7dbaf2595c70ec955bc42fbbc1eb5a5cb48abfe`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartExecution

## Description
Step Functions resources configured with a customer managed KMS key (encryptionConfiguration.type = CUSTOMER_MANAGED_KMS_KEY) are served as if the key were never consulted: no key-state check, no key-policy/identity authorization, no encryption-context scoping, no includedData semantics, and no resolution of the key reference. Five distinct causes, all grounded in failing behavioral checks of this service.

Cause 1 of 5: the CMK's key state is never consulted, so a Disabled key is accepted at write time and still delivers activity tasks.
AWS: Smithy (com.amazonaws.sfn) — CreateActivity declares InvalidEncryptionConfiguration (HTTP 400), documented as "Received when encryptionConfiguration is specified but various conditions exist which make the configuration invalid ... or the KMS key is not symmetric or inactive"; the recorded refusal for a Disabled CMK is HTTP 400, code InvalidEncryptionConfiguration, message exactly "kmsKeyId is not enabled" (that whole message is fixed text — it has no variable part), and nothing is created (the refused name does not appear in ListActivities). GetActivityTask declares KmsInvalidStateException (HTTP 400, member kmsKeyState, doc "The KMS key is not in valid state, for example: Disabled or Deleted"); while the activity's key is Disabled, AWS refuses delivery with that error and resumes delivering once the key is re-enabled.
Emulator: CreateActivity keeps returning 200 with an activityArn for a key whose DescribeKey KeyState is Disabled, for the full 60 s the check polls; GetActivityTask returns 200 with a taskToken and the task input while the key is Disabled.
Why: a client that relies on AWS refusing CMK work while a key is disabled (break-glass key disable as a kill switch, or a test asserting the InvalidEncryptionConfiguration path) sees the operation succeed, so a disabled key stops protecting anything and the negative path can never be exercised.
Fix: the key-state lookup in the CreateActivity handler's encryption-configuration validation and in the GetActivityTask delivery path (sfn ops/state for CMK-backed activities).
Traces: kms__stepfunctions.create-activity-disabled-cmk-invalid-encryption-config-rejected, kms__stepfunctions.xsvc-sfn-activity-cmk-disabled-denies-get-activity-task-until-reenabled.

Cause 2 of 5: KMS authorization (key-policy deny, or a caller/execution role with no kms:Decrypt/kms:GenerateDataKey) is never evaluated, so every CMK-gated call succeeds.
AWS: Smithy — StartExecution, StartSyncExecution, GetActivityTask, GetExecutionHistory, DescribeExecution, SendTaskSuccess and CreateStateMachine/CreateActivity all declare KmsAccessDeniedException (HTTP 400), documented as "Either your KMS key policy or API caller does not have the required permissions". Where the recordings show the relayed KMS text, its fixed form is "User: <principal> is not authorized to perform: <kms action> on resource: <key ARN> with an explicit deny in a resource-based policy (Service: Kms, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)" — the principal, action, key ARN come from the request and state, the request id and attempt count vary per call. An execution whose role loses kms:Decrypt must end FAILED, and a read that needs execution data must be refused even when the caller asks for no data.
Emulator: every such call is served 200. StartSyncExecution returns status SUCCEEDED with input/output included both when the caller lacks kms:Decrypt and when the key policy explicitly denies it (never refused within 180 s); GetExecutionHistory returns the events list under a key-policy deny; SendTaskSuccess returns 200 for a role without kms:Decrypt; a nested sync execution whose parent role lacks kms:Decrypt on the child's key reports SUCCEEDED; an execution whose key trust was removed reports SUCCEEDED instead of FAILED; GetActivityTask hands the task to a worker whose role is not granted decrypt on the activity's key; and the write-time caller-deny check never observes a refusal at all (it is killed at the 180 s cap).
Why: a client that depends on KMS as the authorization boundary for execution data — least-privilege workers, key-policy deny as an incident control, cross-account/nested-workflow isolation — is handed plaintext input/output and task tokens it must never see, and negative tests that assert KmsAccessDeniedException pass vacuously or hang.
Fix: the shared CMK authorization step (evaluate the key policy and the caller's/execution role's identity policy before each Decrypt/GenerateDataKey) invoked by the sfn handlers for StartExecution, StartSyncExecution, GetActivityTask, GetExecutionHistory, SendTaskSuccess and the execution runtime.
Traces: kms__stepfunctions.write-time-cmk-ops-caller-kms-deny-access-denied, kms__stepfunctions.xsvc-sfn-express-cmk-start-sync-execution-caller-decrypt-required-unless-metadata-only, kms__stepfunctions.xsvc-sfn-express-cmk-start-sync-execution-key-policy-deny-and-disabled-key, kms__stepfunctions.xsvc-sfn-get-execution-history-kms-deny-refuses-even-without-execution-data, kms__stepfunctions.send-task-success-cmk-role-without-decrypt-denied-sourcearn-trust-works, kms__stepfunctions.nested-sync-parent-role-without-child-key-decrypt-denied, kms__stepfunctions.cmk-trust-removed-then-restored-execution-redrive-succeeds, kms__stepfunctions.xsvc-sfn-activity-cmk-get-activity-task-worker-decrypt-scoped-to-activity-key.

Cause 3 of 5: the GenerateDataKey call Step Functions makes on the caller's behalf carries no encryption context, so a grant scoped by a kms:EncryptionContext condition is not honoured and a non-matching create is not denied.
AWS: Smithy — CreateStateMachine declares KmsAccessDeniedException (HTTP 400). Recorded behavior: a caller whose only KMS grant is conditioned on the Step Functions encryption context may create a state machine whose context matches, and an otherwise identical create whose context does not match is refused KmsAccessDeniedException relaying KMS's "User: <assumed-role session ARN> is not authorized to perform: kms:GenerateDataKey on resource: <key ARN> because no identity-based policy allows the kms:GenerateDataKey action (Service: Kms, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)" — fixed text apart from the principal, key ARN, request id and attempt count.
Emulator: the non-matching create returns 200 with a stateMachineArn; no KMS condition is evaluated because no encryption context is supplied to the data-key request.
Why: a client that scopes a key grant to one state machine (the standard way to stop one workflow from using another's key) finds the condition inert, so the grant is effectively unscoped.
Fix: the CreateStateMachine handler's data-key request construction (populate the Step Functions encryption context) and the key-policy condition evaluation it feeds.
Traces: kms__stepfunctions.caller-kms-generate-data-key-encryption-context-scopes-create-state-machine.

Cause 4 of 5: includedData is ignored — METADATA_ONLY reads still project the sensitive execution data and still take the KMS path, so they fail when the key is unusable.
AWS: Smithy — DescribeExecution.includedData targets the IncludedData enum (ALL_DATA, METADATA_ONLY); output members input, output, error, cause are @sensitive. With METADATA_ONLY the response omits input/inputDetails/output/outputDetails (and error/cause), needs no KMS call, and therefore keeps answering 200 while the CMK is Disabled or denied; only ALL_DATA is refused, with KmsInvalidStateException (key Disabled) or KmsAccessDeniedException (deny).
Emulator: DescribeExecution(includedData=METADATA_ONLY) returns the keys ['executionArn','input','inputDetails','name','output','outputDetails','redriveCount','redriveStatus','redriveStatusReason','startDate','stateMachineArn','status','stopDate'] — input and output are present while the key is healthy — and once the key is Disabled or denied the same METADATA_ONLY call is refused instead of served: "KmsInvalidStateException ... <key ARN> is disabled. (Service: Kms, Status Code: 400 ...)" and "KmsAccessDeniedException ... is not authorized to perform: kms:Decrypt on resource: <key ARN> with an explicit deny in a resource-based policy ...".
Why: METADATA_ONLY exists so an operator can still read status while a key is unavailable; a client polling for a terminal status during a key incident is locked out, and a client that chose METADATA_ONLY to avoid handling sensitive payloads receives them anyway.
Fix: the DescribeExecution (and StartSyncExecution) response projection — honour includedData by eliding the sensitive members and skipping the decrypt entirely for METADATA_ONLY.
Traces: kms__stepfunctions.xsvc-sfn-describe-execution-metadata-only-elides-despite-disabled-cmk, kms__stepfunctions.xsvc-sfn-disabled-cmk-mid-execution-fails-states-runtime, kms__stepfunctions.xsvc-sfn-kms-access-denied-mid-execution-fails-states-runtime.

Cause 5 of 5: encryptionConfiguration.kmsKeyId is echoed back exactly as supplied instead of as the key's ARN.
AWS: Smithy — EncryptionConfiguration.kmsKeyId accepts "An alias, alias ARN, key ID, or key ARN of a symmetric encryption KMS key". Recorded behavior: whichever reference form the create used, DescribeStateMachine reports the resolved key ARN (arn:<partition>:kms:<region>:<account>:key/<key-id>) in encryptionConfiguration.kmsKeyId.
Emulator: a CreateStateMachine that passed the bare key id gets {'kmsKeyId': '<bare key id>', 'kmsDataKeyReusePeriodSeconds': 300, 'type': 'CUSTOMER_MANAGED_KMS_KEY'} back from DescribeStateMachine — the reference is stored verbatim and never resolved.
Why: a client comparing the described key against a key ARN it holds (drift detection, policy checks, cross-account key identification, which AWS requires an ARN for) sees a mismatch for a correctly configured machine.
Fix: resolve the key reference to its ARN when the encryption configuration is stored, in the CreateStateMachine/CreateActivity handler, and serialize that ARN in the describe projections.
Traces: kms__stepfunctions.create-state-machine-kms-via-service-condition.
