# cloudtrail__sfn: a trail that reports IsLogging=true delivers no log file to its S3 bucket/prefix at all, so neither a states.amazonaws.com management event nor an added Data selector's StartSyncExecution event ever arrives

> _Note: this issue was identified against the code base at commit `004a13bc6b62a404600c0a09686b1d7dd87c7440`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartLogging

## Description
One net-new root cause. The failing check is not marked ALREADY FILED or OWNED in the replay report, so no existing issue carries its replay key. (Service token: the check id's leading token is `cloudtrail__sfn`, a cross-service check over cloudtrail and sfn; both underlying services are bootstrapped.)

Cause 1 of 1 — a logging trail never writes any log file object to its configured S3 bucket and key prefix.
AWS: after CreateTrail(S3BucketName=<bucket>, S3KeyPrefix=<prefix>) followed by StartLogging, GetTrailStatus reports IsLogging=true and the trail begins delivering gzipped JSON log files to s3://<bucket>/<prefix>/AWSLogs/<account-id>/CloudTrail/<region>/<yyyy>/<mm>/<dd>/, batched roughly every five minutes. With an advanced event selector whose FieldSelectors are eventCategory Equals ["Management"], every management call of the account — here sfn DescribeStateMachine on states.amazonaws.com — is delivered as a record whose requestID equals the SDK's ResponseMetadata.RequestId. Adding a second advanced selector with eventCategory Equals ["Data"], resources.type Equals ["AWS::StepFunctions::StateMachine"] and resources.ARN Equals [<state-machine-arn>] then delivers that machine's StartSyncExecution data events — only for calls made after the selector was stored, and never for a bystander machine. Model support for the configuration path: PutEventSelectors/GetEventSelectors carry AdvancedEventSelectors, and GetTrailStatus carries IsLogging (recorded behavior for delivery timing and the S3 key layout).
Emulator: the configuration path is accepted — CreateTrail returns a TrailARN, PutEventSelectors stores the Management selector, StartLogging returns and GetTrailStatus reports IsLogging=true — but phase 0 of the check never completes: repeated sfn DescribeStateMachine marker calls are made for the whole budget and NO object whose records carry those request ids is ever present under s3://<bucket>/<prefix>/. The check ends with `TimeoutError: the trail's first management event in s3://<bucket>/<prefix>/: the run budget ended first; not graded` (raise at line 106 of the check). Because not even a management record is delivered, the data-selector half of the contract (deliver the subject machine's StartSyncExecution only after the selector is added, never the bystander's) is unreachable.
Why: IsLogging=true is a promise of delivery. Any client that consumes CloudTrail through S3 — a log-ingestion pipeline, an S3 event notification on the trail prefix, an Athena/Lake query over delivered files, a retention or integrity check — sees an empty prefix forever while the control plane reports a healthy, logging trail. A test that asserts "the selector I just added starts capturing" passes vacuously, and a consumer cannot tell a mis-scoped selector from a trail that delivers nothing.
Fix: the trail delivery path in the cloudtrail service — the component that, for a trail whose status is logging, serializes recorded events matching its (advanced) event selectors into gzipped log-file objects and PUTs them under the trail's S3 bucket and key prefix, plus the state linking StartLogging/PutEventSelectors to that delivery. It must also honour eventCategory Management vs Data and the resources.type/resources.ARN scoping, and must only capture calls made after a selector change was stored.

## Evidence
Expected: with a trail created on s3://<bucket> with S3KeyPrefix=<prefix>, an AdvancedEventSelector of eventCategory=["Management"] stored, StartLogging called and GetTrailStatus reporting IsLogging=true, listing s3://<bucket>/<prefix>/ eventually yields gzipped log-file objects containing a record whose requestID equals the RequestId returned by sfn DescribeStateMachine; after also storing a Data selector scoped to resources.type AWS::StepFunctions::StateMachine / resources.ARN <subject-arn>, later StartSyncExecution calls on the subject machine are delivered and the bystander machine's are not. (The bucket/prefix/machine names in the recorded run are per-run values; the requirement is that a logging trail delivers its matching records to its configured prefix.)
