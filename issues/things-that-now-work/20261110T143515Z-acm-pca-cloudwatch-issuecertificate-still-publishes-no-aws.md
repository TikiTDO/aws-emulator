# acm-pca__cloudwatch: IssueCertificate still publishes no AWS/ACMPrivateCA metrics — the Success series never appears, so the metrics check now burns its whole run budget polling ListMetrics

> _Note: this issue was identified against the code base at commit `a86c3493c3f63ce00344d068ccb26649087a2439`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
IssueCertificate

## Description
Cause 1 of 1: ACM Private CA never publishes its per-CA CloudWatch metric series, so the AWS/ACMPrivateCA namespace stays empty no matter how many certificates a certificate authority issues or refuses. Failing check: acm-pca__cloudwatch.issue-certificate-success-and-failure-counted-in-acmprivateca-namespace.

Relationship to an already-open issue: the open issue 20261109T132558Z-acm-pca-cloudwatch-issuecertificate-publishes-no-aws-acmprivateca.md describes this same root cause, but it is keyed on the check's AssertionError exit from _poll_until (the 600 s cap elapsing with `Last result: []`). This replay exits the SAME poll through its other branch — a TimeoutError raised because the runner's overall budget expired before the 600 s cap — so this run's failure does not carry that issue's replay key and the suite did not mark it OWNED. It is filed here so the surviving replay key is carried by an issue; a fixer closing the metric-emission gap closes both, and should re-replay the check id listed below to confirm.

AWS: metric emission is not expressed in either service's Smithy model — acm-pca's IssueCertificate (input ApiPassthrough/CertificateAuthorityArn/Csr/SigningAlgorithm/TemplateArn/Validity/ValidityNotBefore/IdempotencyToken, output CertificateArn, errors InvalidArgsException, InvalidArnException, InvalidStateException, LimitExceededException, MalformedCSRException, ResourceNotFoundException) says nothing about CloudWatch, because these are CloudWatch-side series. This is documented and recorded behavior only: per the privateca userguide (PcaCloudWatch.html), ACM Private CA emits into the AWS/ACMPrivateCA namespace the metrics Success (the number of certificates ACM Private CA issued, applying only to IssueCertificate), Failure (failed issuance attempts) and Time (the time in milliseconds between an issuance request and the completion or failure of issuance). Each series is dimensioned on the certificate authority it belongs to, so cloudwatch:ListMetrics(Namespace='AWS/ACMPrivateCA', MetricName='Success') reports at least one dimension set whose value identifies the CA under test, and GetMetricStatistics over that dimension set sums to the number of issuances that actually succeeded against that CA. A synchronous validation refusal emits no Failure series at all — the recording shows Failure absent (None, not 0.0) for the refused call.

Emulator: every ACM PCA call in the scenario behaved. The CA was created, driven to PENDING_CERTIFICATE, its CSR fetched, its own root certificate issued and imported, and DescribeCertificateAuthority reported Status='ACTIVE'. A 1-day end-entity leaf was issued and signed; a 7-day leaf was correctly refused with ValidationException and the message 'The certificate validity specified exceeds the certificate authority validity.' (fixed text, no variable part); a second 1-day leaf was issued and signed. Only the metric delivery is missing: the poll over cloudwatch ListMetrics(Namespace='AWS/ACMPrivateCA', MetricName='Success') never once observed a dimension set naming the CA, and the check ended with `TimeoutError: ListMetrics reporting a AWS/ACMPrivateCA Success series dimensioned on this run's CA <ca-id>: the run budget ended first; not graded`. The CA id in that message is a per-run server-minted value and is no part of the requirement; the requirement is that SOME dimension set identifying the CA under test exists. Because the Success series never appears, the dependent assertions were never reached at all: Success == 2 over the run's own window, the absence of a Failure series for the synchronous refusal, and Time being a positive latency bounded above by the measured elapsed time. Note the grading caveat honestly: the check labels this exit 'not graded' because the runner's budget, not the 600 s cap, ended the wait — but the wait is only reached because the series is absent, and the earlier replay recorded in the open issue above shows the same poll exhausting the full 600 s cap with an empty Metrics list, so the absence is the emulator's and not a harness artifact.

Why: a client that monitors private-CA issuance — an alarm on AWS/ACMPrivateCA Failure, a per-CA dashboard of Success volume, or an SLO over issuance Time — reads an empty metric list and zero datapoints against the emulator however many certificates are issued or refused. Alarms built on these series sit in INSUFFICIENT_DATA forever, and the documented way to distinguish a synchronous refusal (no Failure datapoint) from an asynchronous signing failure (a Failure datapoint) cannot be exercised. Worse, a client or test that polls for the series consumes its entire time budget waiting for a datapoint that will never arrive, turning a missing metric into a hang rather than a readable zero.

Fix: belongs in the ACM PCA IssueCertificate handler's metric-emission path and the CloudWatch metric store it must write into. The handler should publish, per certificate authority, a Success datapoint on each completed issuance, a Failure datapoint on an issuance that fails during signing (and NOT for a synchronous validation refusal), and a Time datapoint carrying the issuance latency in milliseconds, each dimensioned so the CA is identifiable, so that cloudwatch ListMetrics and GetMetricStatistics can read them back.

## Evidence
Expected (AWS, per privateca userguide PcaCloudWatch.html; metric emission is unmodeled in the Smithy model of either service): after two successful and one refused IssueCertificate against one CA, cloudwatch.list_metrics(Namespace='AWS/ACMPrivateCA', MetricName='Success') reports a dimension set identifying that CA; get_metric_statistics(Namespace='AWS/ACMPrivateCA', MetricName='Success', Dimensions=<that set>, Period=60, Statistics=['Sum']) sums to exactly 2 over the run's own window; MetricName='Failure' has no series naming the CA (None, not 0.0), because the over-long leaf was refused synchronously; MetricName='Time' reports a positive Average bounded above by the wall-clock time the run spent on the issuances.

Actual (emulator): no AWS/ACMPrivateCA series is ever published. The ListMetrics poll never observed a Success dimension set naming the CA and the check terminated in that poll:
  TimeoutError: ListMetrics reporting a AWS/ACMPrivateCA Success series dimensioned on this run's CA d018b8be-42af-4a00-950b-5d5171af0810: the run budget ended first; not graded
(the CA id is a per-run minted value, not a requirement). The same poll in the earlier replay captured by open issue 20261109T132558Z-...-publishes-no-aws-acmprivateca.md exhausted the full cap instead: 'AssertionError: ... not met within 600.0s. Last result: []'.

Everything the emulator was asked before the metrics read behaved: CreateCertificateAuthority (ROOT, UsageMode=SHORT_LIVED_CERTIFICATE, RSA_2048, SHA256WITHRSA) -> CertificateAuthorityArn; DescribeCertificateAuthority -> 'PENDING_CERTIFICATE'; GetCertificateAuthorityCsr -> CSR PEM; IssueCertificate (RootCACertificate/V1, Validity {Value:2,Type:DAYS}) -> CertificateArn; GetCertificate -> signed; ImportCertificateAuthorityCertificate -> accepted; DescribeCertificateAuthority -> 'ACTIVE'; IssueCertificate (EndEntityCertificate/V1, 1 DAY) -> signed; IssueCertificate (EndEntityCertificate/V1, 7 DAYS) -> refused ValidationException 'The certificate validity specified exceeds the certificate authority validity.'; IssueCertificate (1 DAY) -> signed. Only the AWS/ACMPrivateCA Success/Failure/Time delivery is absent.

## Steps to Reproduce
1. acm-pca CreateCertificateAuthority with CertificateAuthorityType=ROOT, UsageMode=SHORT_LIVED_CERTIFICATE, CertificateAuthorityConfiguration {KeyAlgorithm=RSA_2048, SigningAlgorithm=SHA256WITHRSA, Subject.CommonName=<any>}.
2. Poll DescribeCertificateAuthority until Status=PENDING_CERTIFICATE; GetCertificateAuthorityCsr; IssueCertificate against the CA with TemplateArn=arn:aws:acm-pca:::template/RootCACertificate/V1 and Validity={Value:2,Type:DAYS}; GetCertificate until signed; ImportCertificateAuthorityCertificate with that PEM; poll until Status=ACTIVE.
3. Generate a local RSA-2048 CSR. IssueCertificate it with TemplateArn=arn:aws:acm-pca:::template/EndEntityCertificate/V1 and Validity={Value:1,Type:DAYS}; GetCertificate until signed.
4. IssueCertificate the same CSR with Validity={Value:7,Type:DAYS} — observe the (correct) ValidationException 'The certificate validity specified exceeds the certificate authority validity.'
5. IssueCertificate again with Validity={Value:1,Type:DAYS}; GetCertificate until signed.
6. cloudwatch list_metrics(Namespace='AWS/ACMPrivateCA', MetricName='Success') and poll for a dimension set whose value contains the CA id. Observe an empty Metrics list on every poll until the budget/cap ends; repeat for MetricName='Failure' and MetricName='Time'. No AWS/ACMPrivateCA series is ever published for the CA, so the Success==2 / Failure-absent / Time-positive assertions can never be reached.
