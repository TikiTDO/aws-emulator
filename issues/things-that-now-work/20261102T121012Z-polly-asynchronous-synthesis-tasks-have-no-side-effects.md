# Polly asynchronous synthesis tasks have no side effects: no object is written to the output bucket, no SNS completion notification is published, and ListSpeechSynthesisTasks orders oldest-first (3 causes)

> _Note: this issue was identified against the code base at commit `8a15654a3e32a09451431e59a712f0f10794d652`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartSpeechSynthesisTask

## Description
StartSpeechSynthesisTask is now implemented (it mints a task, records it and moves it to `completed` on the clock), so the open issue 20261022T175007Z-polly-startspeechsynthesistask-stub.md (keyed `polly|StartSpeechSynthesisTask|NotImplemented`) no longer reproduces and does not cover any of the failures below — none of these checks is refused any more; each gets a 200 and then observes a missing side effect or a wrong order. Likewise, the open 20261022T232910Z-polly-startspeechsynthesistask-performs-no-request-validation-lexicon-speech.md carries polly.start-speech-synthesis-task-marks-rejected-for-mp3-format under the key `assert code == "MarksNotSupportedForFormatException"`; that assertion now PASSES and the check fails later, on the missing output object, which is Cause 1 here. 3 causes, all in the asynchronous-task path.

Cause 1 of 3: a completed task writes NOTHING to the destination S3 bucket, although it reports an OutputUri.
AWS: Smithy (services/service-com-amazonaws-polly-parrot-v1/smithy-model/com-amazonaws-polly-parrot-v1.json) models StartSpeechSynthesisTask as POST /v1/synthesisTasks -> 200, with OutputS3BucketName (@required, pattern ^[a-z0-9][\.\-a-z0-9]{1,61}[a-z0-9]$), OutputS3KeyPrefix and OutputFormat (@required: alaw|json|mp3|mulaw|ogg_opus|ogg_vorbis|pcm); the operation doc says the caller supplies "the name of an Amazon S3 bucket for the service to store the output of the synthesis task", and SynthesisTask$OutputUri is documented "Pathway for the output speech file". Recorded behavior: once the task reaches TaskStatus=completed, exactly ONE object exists in the destination bucket under the requested OutputS3KeyPrefix; its key is the key named by OutputUri, its size is greater than 0, its S3 ContentType is the content type of the requested OutputFormat (mp3 -> audio/mpeg), and for OutputFormat=json with SpeechMarkTypes the object body is a newline-delimited JSON speech-marks stream whose records carry the requested mark types (e.g. type "sentence" and type "word").
Emulator: the task completes and reports an OutputUri whose key does carry the requested prefix, but no object is ever uploaded: ListObjectsV2 on the bucket (with and without Prefix) returns an empty Contents, and GetObject on the key taken from OutputUri answers 404 NoSuchKey ("The specified key does not exist."). The handler states this outright — services/service-com-amazonaws-polly-parrot-v1/src/ops/start_speech_synthesis_task.rs lines 23-33: "THE EMULATOR PERFORMS NO TEXT-TO-SPEECH, and no object is written to the output bucket" — and only computes output_uri() (same file, lines 279-289) without ever writing the object.
Why: the whole point of the async API is that the rendered output lands in the caller's bucket; a client that polls to `completed` and then reads OutputUri (or lists the prefix) gets NoSuchKey / an empty listing and concludes its own bucket or IAM configuration is broken, while the task reports success. Pipelines that hand the OutputUri to a downstream consumer propagate a dangling reference.
Fix: the StartSpeechSynthesisTask completion path (src/ops/start_speech_synthesis_task.rs and the task-completion materialisation in src/state.rs that flips pending_status to `completed`) must, when the task completes, write the output object into the named bucket at exactly the key OutputUri reports — audio bytes for the audio formats, carrying the format's content type (reuse content_type_for() from src/ops/synthesize_speech.rs), and the newline-delimited speech-marks stream for OutputFormat=json with SpeechMarkTypes — so the object is non-empty and present before the task is reported terminal.
Traces: polly.speech-synthesis-task-completes-and-uploads-to-s3 (expected exactly 1 uploaded object, found 0), polly.start-speech-synthesis-task-output-s3-key-prefix-applied (listing under the prefix is set()), polly.start-speech-synthesis-task-json-speech-marks-to-s3 (GetObject on the OutputUri key -> NoSuchKey), polly.start-speech-synthesis-task-marks-rejected-for-mp3-format (the accepted OutputFormat=json task completes and writes nothing).

Cause 2 of 3: ListSpeechSynthesisTasks returns tasks oldest-first; AWS returns them newest-first.
AWS: Smithy models ListSpeechSynthesisTasks as GET /v1/synthesisTasks -> 200 with SynthesisTasks + NextToken, @paginated (MaxResults 1..100, Status filter); the model's prose only says the list is "ordered by their creation date" and does not state the direction, so: recorded behavior only — of two tasks created in sequence, the MORE RECENTLY created task appears EARLIER in the unfiltered listing, and the listed order agrees with the CreationTime each task itself reports (descending CreationTime).
Emulator: the listing is ascending by creation time: for tasks a (older) then b (newer) the listing is [a, b], i.e. positions a=0, b=1. The order is deliberate in src/ops/list_speech_synthesis_tasks.rs (order_key(), lines 204-218: "oldest first, with the TaskId breaking a tie"), and the page cursor resumes in that same direction.
Why: a client that reads the first page (or the first element) to find its most recent task gets the OLDEST task instead, and with more tasks than one page the recent ones are not on the first page at all — so dashboards and "latest task" lookups silently report stale tasks.
Fix: the listing's total order in src/ops/list_speech_synthesis_tasks.rs — sort descending by creation time (keeping a deterministic TaskId tie-break so the order stays total) and keep encode_task_cursor/decode_task_cursor resuming in the same direction, so paging still neither skips nor repeats a task.
Traces: polly.list-speech-synthesis-tasks-ordered-by-creation-time-descending.

Cause 3 of 3: a task started with SnsTopicArn publishes no completion notification.
AWS: Smithy models StartSpeechSynthesisTaskInput$SnsTopicArn (pattern ^arn:aws(-(cn|iso(-b)?|us-gov|eusc))?:sns:[a-z0-9_-]{1,50}:\d{12}:[a-zA-Z0-9_-]{1,251}([a-zA-Z0-9_-]{0,5}|\.fifo)$), documented "ARN for the SNS topic optionally used for providing status notification for a speech synthesis task". Recorded behavior only: when the task reaches a terminal status, Polly publishes one notification to that topic; an SQS queue subscribed to the topic receives exactly one message whose body is a raw SNS Notification envelope (Type="Notification", TopicArn equal to the requested topic ARN) whose Message payload contains the task's TaskId and its terminal status ("completed") — the TopicArn, TaskId and status are the variable parts taken from the request and the task's state; the envelope's Type value is fixed text.
Emulator: nothing is ever published. The task record stores sns_topic_arn (src/ops/start_speech_synthesis_task.rs line 481) and no code path publishes to SNS when the pending completion is materialised, so the subscribed queue stays empty and the check exhausts its wait ("Check timed out after 60.0s" while polling ReceiveMessage on the subscribed queue).
Why: event-driven consumers never learn the task finished; a client that waits on the notification instead of polling GetSpeechSynthesisTask hangs forever, which is indistinguishable from a lost task.
Fix: the task-completion materialisation (src/state.rs, where pending_status is applied) plus StartSpeechSynthesisTask's handler must publish one SNS notification to the recorded SnsTopicArn when the task reaches a terminal status, with a Message payload carrying the task's TaskId and terminal TaskStatus, so SNS fan-out to a subscribed SQS queue delivers it.
Traces: polly.speech-synthesis-task-sns-notification-on-completion.
