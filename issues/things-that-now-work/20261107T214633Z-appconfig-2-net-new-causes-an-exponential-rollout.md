# appconfig: 2 net-new causes — an EXPONENTIAL rollout never advances through an observable G*(2^N) progression, and a mid-rollout StopDeployment can never be exercised because no partial rollout state is ever reachable

> _Note: this issue was identified against the code base at commit `7f27151474f220c715589d81820913dcd4b7b62b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartDeployment

## Description
Two net-new root causes in the AppConfig deployment rollout engine. Both are grounded in behavioral checks that run to the harness ceiling ("Check timed out after 180.0s") because the emulator never produces the intermediate rollout state the operations are specified to produce: the deployment neither advances through the strategy's growth grid nor ever settles on a terminal DeploymentState, so every poll loop spins against an unchanging deployment. Related open issues describe the data-plane half of the rollout (20261029T233120Z-appconfig-rollout-percentage-never-gates-what-the-data.md, 20261101T232607Z-appconfig-exponential-rollout-is-never-partial-at-the.md, 20261103T021132Z-appconfig-deployment-lifecycle-advances-instantly-through-deploy-bake.md); neither of the two checks below is owned by any of them and both are still failing, so they are filed here as net-new causes.

Cause 1 of 2: a deployment started with GrowthType=EXPONENTIAL never advances through the documented G*(2^N) percentage grid and never reaches a terminal state, so neither PercentageComplete nor the PERCENTAGE_UPDATED EventLog records the exponential schedule.
  AWS: Smithy: CreateDeploymentStrategy.GrowthType is an enum of LINEAR|EXPONENTIAL, GrowthFactor is a float in [1.0,100.0], DeploymentDurationInMinutes an integer in [0,1440]. The modeled documentation for GrowthType states for Exponential: "AppConfig processes the deployment exponentially using the following formula: G*(2^N). In this formula, G is the growth factor specified by the user and N is the number of steps until the configuration is deployed to all targets", continuing "until the configuration has been deployed to all targets". So for GrowthFactor=G the rollout passes through G*(2^0), G*(2^1), ... capped at 100 — for G=10 that is 10, 20, 40, 80, 100: five steps, half the ten a LINEAR strategy with the same GrowthFactor would take. StartDeployment/GetDeployment/StopDeployment all return the Deployment shape, which carries GrowthType, GrowthFactor, PercentageComplete (Percentage, range 1.0-100.0), State (DeploymentState: BAKING|VALIDATING|DEPLOYING|COMPLETE|ROLLING_BACK|ROLLED_BACK|REVERTED) and EventLog (DeploymentEventType includes DEPLOYMENT_STARTED, PERCENTAGE_UPDATED, BAKE_TIME_STARTED, DEPLOYMENT_COMPLETED). AWS therefore emits one PERCENTAGE_UPDATED entry per grid step, reports PercentageComplete monotonically non-decreasing on that grid, and ends at State=COMPLETE with PercentageComplete=100.0.
  Emulator: the check starts an EXPONENTIAL deployment (GrowthFactor=10, DeploymentDurationInMinutes=4, FinalBakeTimeInMinutes=0) and then polls GetDeployment every 4s, breaking as soon as State is terminal. It never breaks: the deployment is never reported in COMPLETE/ROLLED_BACK/REVERTED and no step grid is observable, so the loop runs against its declared 900s budget and the check is killed at the suite ceiling with "Check timed out after 180.0s". The grid, step-count and convergence assertions are never reached, which means the emulator supplied no terminating rollout at all for the whole window — not merely a wrong step count.
  Why: a client that starts a rollout and waits for it, as the console and every deployment pipeline does, waits forever: GetDeployment never reports a terminal State, so a deploy step blocks until its own timeout and is indistinguishable from a stuck AppConfig. A client that reads PercentageComplete or the PERCENTAGE_UPDATED EventLog to report rollout progress, or that discriminates EXPONENTIAL from LINEAR by step count, sees nothing to read, so GrowthType is effectively ignored.
  Fix: the deployment rollout scheduler in the appconfig service state — the component that advances a deployment's PercentageComplete over DeploymentDurationInMinutes, appends one PERCENTAGE_UPDATED EventLog entry per step, and drives the DeploymentState machine (DEPLOYING -> BAKING -> COMPLETE) — must compute its step grid from the deployment's copied GrowthType/GrowthFactor as G*(2^N) capped at 100 for EXPONENTIAL, and must reach a terminal state. The Deployment serializer must carry that progression on GetDeployment.
  Traces: appconfig.exponential-growth-type-advances-in-powers-of-the-growth-factor.

Cause 2 of 2: a linear deployment never presents a partial rollout, so StopDeployment's mid-rollout withdrawal path is unreachable and the deployment never settles terminally.
  AWS: Smithy: StopDeployment is DELETE /applications/{ApplicationId}/environments/{EnvironmentId}/deployments/{DeploymentNumber}, HTTP 202, output shape Deployment, errors BadRequestException (400), ResourceNotFoundException (404), InternalServerException (500). There is no STOPPED member in DeploymentState; a user-requested stop of an in-flight deployment is a withdrawal that answers State=ROLLED_BACK with PercentageComplete reset, records ROLLBACK_COMPLETED in the EventLog (DeploymentEventType includes ROLLBACK_STARTED and ROLLBACK_COMPLETED), and leaves the environment in EnvironmentState ROLLED_BACK (served on the wire as CamelCase 'RolledBack'). A second StopDeployment on the now-terminal deployment is refused with BadRequestException (400); the recorded message's fixed text is "Deployment <n> for App <applicationId> and Environment <environmentId> cannot be stopped, it has a status of <STATE>.", whose variable parts are the DeploymentNumber from the request path, the ApplicationId and EnvironmentId from the request path, and the deployment's current State from emulator state — the digits and ids of any one run only fill that template.
  Emulator: the check deploys v1 instantly, then starts a LINEAR deployment (GrowthFactor=20, DeploymentDurationInMinutes=5) of v2 and polls GetDeployment, sampling AppConfigData sessions whenever 0.0 < PercentageComplete < 100.0, until both versions are demonstrably in service at once. That precondition is never met and the deployment is never reported terminal either (the loop's own assertion that the state is non-terminal never trips), so the check exhausts its declared 600s budget and is killed with "Check timed out after 180.0s". The StopDeployment call, its 202/ROLLED_BACK answer, PercentageComplete 0.0, the ROLLBACK_COMPLETED EventLog entry, the environment's 'RolledBack' State and the second-stop BadRequestException are all never reached — the emulator offers no mid-rollout state in which a stop could be issued.
  Why: a client that aborts a bad rollout — the primary reason StopDeployment exists — has no reachable state in which to do so, and a client that polls for the rollout to finish is left blocked. Nothing about the stop/rollback contract (the synchronous ROLLED_BACK answer, the rollback EventLog, the environment state, or the refusal of a second stop) can be exercised against the emulator at all.
  Fix: the same deployment rollout scheduler plus StopDeployment's handler and state transition in the appconfig service: a deployment must occupy an observable in-flight window with 0 < PercentageComplete < 100 for the duration its strategy declares, StopDeployment must transition that in-flight deployment to ROLLED_BACK synchronously (202) with PercentageComplete reset and a ROLLBACK_COMPLETED EventLog entry, set the environment to ROLLED_BACK, and refuse a subsequent stop of a terminal deployment with BadRequestException carrying AWS's message template above.
  Traces: appconfig.stop-deployment-mid-rollout-reverts-every-session.

## Evidence
Cause 1 — check appconfig.exponential-growth-type-advances-in-powers-of-the-growth-factor
  Expected (AWS): after StartDeployment of an EXPONENTIAL strategy (GrowthFactor=10, DeploymentDurationInMinutes=4, FinalBakeTimeInMinutes=0), GetDeployment eventually reports State='COMPLETE' with PercentageComplete=100.0, every observed PercentageComplete lies on the grid [10.0, 20.0, 40.0, 80.0, 100.0] and is non-decreasing, and EventLog carries exactly 5 PERCENTAGE_UPDATED entries (not the 10 a LINEAR strategy with GrowthFactor=10 would log).
  Actual (emulator): no terminal State is ever observed. The poll loop (GetDeployment every 4s, breaking on State in COMPLETE/ROLLED_BACK/REVERTED) never breaks and the check is killed by the suite: "Error: Check timed out after 180.0s". The grid/step-count/convergence assertions are never reached, so the emulator produced neither a completed rollout nor an exponential step sequence within the window.

Cause 2 — check appconfig.stop-deployment-mid-rollout-reverts-every-session
  Expected (AWS): after StartDeployment of a LINEAR strategy (GrowthFactor=20, DeploymentDurationInMinutes=5), there is a window in which GetDeployment reports 0.0 < PercentageComplete < 100.0 and fresh AppConfigData sessions are served both the old and the new bytes; StopDeployment in that window answers HTTP 202 with State='ROLLED_BACK' and PercentageComplete=0.0, GetDeployment settles on 'ROLLED_BACK' with a ROLLBACK_COMPLETED EventLog entry, GetEnvironment reports State='RolledBack', and a second StopDeployment is refused with HTTP 400 BadRequestException whose message follows "Deployment <n> for App <applicationId> and Environment <environmentId> cannot be stopped, it has a status of ROLLED_BACK."
  Actual (emulator): a genuinely partial rollout is never observed and the deployment is never reported terminal; the precondition loop (GetDeployment every 3s plus 20 AppConfigData sessions per sample) exhausts its 600s budget and the check is killed: "Error: Check timed out after 180.0s". StopDeployment is therefore never issued and none of its contract is observable.

Both failures are listed by the suite under '### appconfig' and neither is marked ALREADY FILED or OWNED by an open issue.

## Steps to Reproduce
Cause 1:
1. CreateApplication, CreateEnvironment, CreateConfigurationProfile(LocationUri='hosted'); CreateHostedConfigurationVersion twice (v1 bytes {"tier":"one"}, v2 bytes {"tier":"two"}).
2. CreateDeploymentStrategy(DeploymentDurationInMinutes=0, GrowthFactor=100, FinalBakeTimeInMinutes=0, ReplicateTo='NONE') and deploy v1 with it; wait for COMPLETE.
3. CreateDeploymentStrategy(DeploymentDurationInMinutes=4, GrowthFactor=10, GrowthType='EXPONENTIAL', FinalBakeTimeInMinutes=0, ReplicateTo='NONE').
4. StartDeployment of v2 with that strategy, then poll GetDeployment every 4s, recording each distinct PercentageComplete, until State is COMPLETE/ROLLED_BACK/REVERTED.
5. Observe no terminal State is ever reached, and that EventLog never accumulates the 5 PERCENTAGE_UPDATED entries G*(2^N) with G=10 predicts (10, 20, 40, 80, 100).
   Replay: run the behavioral suite and re-run check appconfig.exponential-growth-type-advances-in-powers-of-the-growth-factor.

3. StartDeployment of v2 with that strategy; poll GetDeployment every 3s and, whenever 0.0 < PercentageComplete < 100.0, open 20 fresh AppConfigData sessions (StartConfigurationSession + GetLatestConfiguration) and collect the payloads.

Intended continuation, currently unreachable: StopDeployment -> 202 State='ROLLED_BACK', PercentageComplete=0.0; GetDeployment -> 'ROLLED_BACK' with ROLLBACK_COMPLETED in EventLog; GetEnvironment -> State='RolledBack'; a second StopDeployment -> 400 BadRequestException with AWS's cannot-be-stopped message.
