# sns: 4 net-new causes — identity-policy explicit Deny is ignored on GetSMSSandboxAccountStatus, a removed TopicInlinePolicy keeps authorizing Publish, a numeric MessageStructure=json branch is not delivered, and no FAILURE delivery-status record is ever written

> _Note: this issue was identified against the code base at commit `73a8baeac3f8a94bf357d3a10d4553d70859ebf3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Publish

## Description
This issue carries 4 root causes, grounded in 4 failing behavioral checks of the sns service. All four must be closed before submitting.

Cause 1 of 4: an identity-based policy's explicit Deny does not refuse an SNS control-plane call. Operation: GetSMSSandboxAccountStatus. Failing check id: sns.authorization-error-explicit-deny-returns-correct-code.
AWS: Smithy (com.amazonaws.sns) models GetSMSSandboxAccountStatus with error AuthorizationErrorException, errorKind client, httpError 403, awsQueryError code "AuthorizationError" (HTTP 403). IAM evaluation is deny-overrides: a policy carrying both an explicit Allow and an explicit Deny for sns:GetSMSSandboxAccountStatus refuses the signed call, never serves it. The message's fixed text is "User: <principal-arn> is not authorized to perform: SNS:GetSMSSandboxAccountStatus on resource: arn:<partition>:sns:<region>:<account>:* with an explicit deny in an identity-based policy" — fixed outside the substitutions; the variable parts are the caller's user ARN (from the signing credentials) and the partition/region/account of the account-wide SNS resource, with the region taken from the endpoint being called.
Emulator: the call succeeds. The check polls for any non-success for 60 s, three times over, and records 'UNEXPECTED_SUCCESS' with HTTPStatusCode 200 and body {"IsInSandbox": true} on every attempt — while the same user's sts:GetCallerIdentity Allow is honoured, so the credential is live and propagated. No AuthorizationError is ever produced.
Why: a client relying on AWS's behavior loses IAM enforcement on the SNS control plane: a Deny written to fence off SMS-sandbox (and by the same path other) operations has no effect, and negative tests that assert a 403 AuthorizationError pass vacuously.
Fix: the request-authorization step shared by the SNS operation handlers (it must evaluate the caller's identity-based policies with explicit Deny overriding any Allow and refuse with 403 AuthorizationErrorException / awsQueryError AuthorizationError and the message above), reached from the GetSMSSandboxAccountStatus handler.
Traces: sns.authorization-error-explicit-deny-returns-correct-code.

Cause 2 of 4: removing an AWS::SNS::TopicInlinePolicy by stack update does not revoke the grant — the role it named keeps publishing. Operations: Publish / GetTopicAttributes. Failing check id: sns.deploy-cfn-removing-a-topic-inline-policy-restores-the-default-policy.
AWS: Smithy models Publish -> AuthorizationErrorException (client, httpError 403, awsQueryError "AuthorizationError"). Deleting the AWS::SNS::TopicInlinePolicy resource drops the inline policy, so GetTopicAttributes Attributes["Policy"] goes back to a single statement whose Sid is the default statement id ("__default_statement_ID", recorded behavior), and a principal the removed statement had allowed is then refused with the fixed text "User: <principal-arn> is not authorized to perform: SNS:Publish on resource: <topic-arn> because no identity-based policy allows the SNS:Publish action" — the variable parts being the caller's assumed-role ARN (arn:<partition>:sts::<account>:assumed-role/<role-name>/<session-name>, from the credentials) and the request's TopicArn.
Emulator: after UpdateStack removes the resource, the assumed role's Publish keeps returning 200 with a MessageId for the whole 120 s revocation window; the check fails with "the revoked role kept publishing after the stack update". (This replay gets past the policy poll, so the topic policy does read back as the default statement; the authorization decision on Publish simply never consults it — consistent with cause 1 of the companion iam__sns issue filed in this sweep.)
Why: a client that manages topic access through CloudFormation cannot revoke a grant. An infrastructure change whose purpose is to close access completes successfully while the principal it removed keeps publishing, and nothing observable distinguishes a successful revocation from none.
Fix: the Publish handler's topic-policy authorization (and the state that serves the topic's access-policy document to it) in the SNS service; the CFN TopicInlinePolicy delete path appears to clear the policy already.
Related OPEN issue that names this scenario but does NOT carry this replay key (it was filed for the earlier failure mode, a 60 s timeout before the policy ever reverted): 20261104T022807Z-sns-removing-an-aws-sns-topicinlinepolicy-by-stack.md.
Traces: sns.deploy-cfn-removing-a-topic-inline-policy-restores-the-default-policy.

Cause 3 of 4: with MessageStructure=json, a non-string scalar protocol branch is not delivered as its JSON text. Operation: Publish. Failing check id: sns.message-structure-json-stringifies-scalar-branches-and-ignores-object-branches.
AWS: Smithy PublishInput$MessageStructure documents that with MessageStructure=json the Message must be a syntactically valid JSON object containing at least a top-level "default" key whose value is a string, and that other top-level keys select the body for a specific transport protocol. Recorded behavior: the selected branch is delivered as its JSON text — a number branch arrives as its decimal text, true as "true", null as "null", an empty string as "" — while an object/null-valued protocol branch falls back to "default" and a non-scalar "default" is refused 400 InvalidParameter "Invalid parameter: Message Structure - No default entry in JSON message body". Exactly one notification per accepted publish.
Emulator: the publishes are all accepted (the earlier over-strict refusal filed as the now-fixed 20261025T025317Z-sns-refuses-four-calls-aws-accepts-deliverypolicy-on.md is gone — this is not that refusal), but the notification whose Message is the stringified number branch never arrives at the subscribed SQS queue inside 90 s: the check reports the wanted body (the branch's decimal text) as never received while other envelopes were delivered. The object/null fallback cases and the No-default-entry refusals passed, so the divergence is confined to selecting and stringifying a non-string scalar branch.
Why: a client using per-protocol payload shaping silently loses the message for any protocol branch it expresses as a JSON number (or other non-string scalar) — Publish reports success with a MessageId and the subscriber receives nothing for that publish.
Fix: the MessageStructure=json branch selection/stringification in the Publish handler's message rules (serialize the selected scalar branch with its JSON text form rather than requiring/keeping a string), and the per-subscription delivery path that carries it.
Traces: sns.message-structure-json-stringifies-scalar-branches-and-ignores-object-branches.

Cause 4 of 4: a denied SQS delivery produces no FAILURE delivery-status record. Operation: Publish (SQSFailureFeedbackRoleArn). Failing check id: sns.sqs-failure-feedback-role-logs-the-denied-delivery-while-the-message-never-reaches-the-queue.
AWS: Smithy SetTopicAttributes.Attributes documents SQSFailureFeedbackRoleArn / SQSSuccessFeedbackRoleArn / SQSSuccessFeedbackSampleRate, with "After you configure the <ENDPOINT>FailureFeedbackRoleArn attribute, then all failed message deliveries generate CloudWatch Logs." Recorded behavior: each failed delivery attempt writes one JSON record into the log group sns/<region>/<account-id>/<topic-name>/Failure (region, account and topic name taken from the topic's own ARN) carrying notification.messageId (the MessageId Publish returned), status "FAILURE", delivery.destination = the subscribed queue ARN, delivery.statusCode = 403, and providerResponse whose ErrorCode is "AccessDenied" and whose ErrorMessage has the fixed text "User: sns.amazonaws.com is not authorized to perform: sqs:sendmessage on resource: <queue-arn> because no resource-based policy allows the sqs:sendmessage action" (only <queue-arn> is substituted, from the subscription).
Emulator: nothing is written. The check publishes a probe message every 10 s for 120 s and polls logs:FilterLogEvents on the Failure group; no record for any of the 13 probe messages ever appears, and the check fails with "no delivery status record for 13 probe message(s) reached sns/<region>/<account>/<topic>/Failure" (the region/account/topic in that string are this run's values; the group-name template is the requirement).
Why: a client relying on AWS's behavior loses the only audit trail SNS gives for deliveries it cannot otherwise observe. A delivery a queue policy denies is completely silent: no FAILURE record, no 403/AccessDenied provider response, so alarms and operational tooling built on the feedback log group never fire and any workflow waiting for a delivery-status record hangs instead of failing.
Related OPEN issues in the same area that do NOT carry this replay key: 20261104T075451Z-sns-delivery-status-logging-is-entirely-inert-no.md and 20261107T090707Z-sns-delivery-status-log-records-omit-delivery-statuscode.md (this check's failure mode has changed from a harness timeout to an explicit no-record assertion, so neither carries it).
Fix: the per-subscription delivery path of the Publish handler plus the topic record holding the feedback attributes — each failed attempt must emit a FAILURE delivery-status record (creating the sns/<region>/<account>/<topic>/Failure group and stream on first write, always logging failures regardless of the success sample rate) through the CloudWatch Logs write path.
Traces: sns.sqs-failure-feedback-role-logs-the-denied-delivery-while-the-message-never-reaches-the-queue.
