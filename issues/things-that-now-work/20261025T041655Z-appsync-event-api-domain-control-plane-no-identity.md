# AppSync Event-API/domain control plane: no identity-based IAM deny gate, and UpdateApi / AssociateApi-GetApiAssociation-DisassociateApi / CreateChannelNamespace answer NotImplemented where AWS answers a modeled rejection

> _Note: this issue was identified against the code base at commit `8b3fb3b9641f9f0b47110ea9811423e23ffd107b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListApis

## Description
Four distinct root causes on the AppSync Event-API (v2 /apis) and domain-association control plane. 4 causes in this issue; all four must be closed before submitting. None of the four checks below is marked ALREADY FILED or OWNED in the replay report, and no open issue carries their replay keys; the open issues named per cause are related but do not record these contracts.

=== Cause 1 of 4: there is no identity-based IAM authorization gate in front of the Event-API/domain operations, so an authenticated-but-unauthorized principal is never denied ===
AWS: a principal whose IAM user has NO attached policy is refused by implicit default deny BEFORE any resource lookup or operation dispatch. Smithy (appsync) models AccessDeniedException with httpError 403 on GetApi (GET /v2/apis/{apiId}), UpdateApi (POST /v2/apis/{apiId}), DeleteApi, AssociateApi (POST /v1/domainnames/{domainName}/apiassociation), GetApiAssociation and DisassociateApi; ListApis (GET /v2/apis) models BadRequestException(400)/UnauthorizedException(401)/InternalFailureException(500) and, per the recorded behavior this check was measured against, answers AccessDeniedException/403 for a zero-policy principal. `NotImplemented` is in none of those error sets. The denial message is rule-derived, not a recorded literal: `User: <principal-arn> is not authorized to perform: appsync:<Action> on resource: <resource-arn> because no identity-based policy allows the appsync:<Action> action`, where the resource is `arn:aws:appsync:<region>:<account>:*` for ListApis, the Api's apiArn for GetApi/UpdateApi/DeleteApi, and `arn:aws:appsync:<region>:<account>:domainnames/<domain>` for the three association operations. The same calls with permissioned credentials must reach the service layer (that is what distinguishes a real gate from a blanket 403).
Emulator: the zero-policy principal's ListApis answers error code `NotImplemented` (HTTP 501, "operation ListApis is scaffolded but not implemented in this emulator") instead of AccessDeniedException/403, and the check aborts there. The emulator applies no identity-based authorization decision to AppSync requests at all — operation dispatch (and therefore the scaffold stub) happens first, so no principal can ever be denied on any of these operations.
Why: this is an overly-permissive boundary. A client built against AWS catches AccessDeniedException to distinguish "you lack permission" from "the service is broken"; here it gets an unmodeled 501 that is in no SDK error set, so least-privilege regressions cannot be detected against the emulator and denial-path code is never exercised.
Fix: the request authorization layer in front of AppSync operation dispatch (sigv4 principal -> IAM policy evaluation -> AccessDeniedException/403 carrying the implicit-deny message shape), which must fire before the op handler is selected. Open issue 20261024T032443Z-appsync-control-plane-fidelity-domain-name-operations-unimplemented.md describes the same missing gate for the sandbox ops (EvaluateCode) in its Cause 4, but carries only appsync.access-denied-sandbox-eval; it does not record the Event-API/domain-association operations or this check.
Traces: appsync.access-denied-event-api-mgmt.

=== Cause 2 of 4: CreateChannelNamespace never rejects an auth mode absent from the parent Event API's authProviders ===
AWS: Smithy CreateChannelNamespace (POST /v2/apis/{apiId}/channelNamespaces) takes publishAuthModes/subscribeAuthModes (AuthModes) and models BadRequestException httpError 400, ConflictException 409, NotFoundException 404, ServiceQuotaExceededException 402, UnauthorizedException 401, InternalFailureException 500. A namespace whose requested auth mode is not one of the parent Api's eventConfig.authProviders (recorded: parent authProviders=[API_KEY], namespace requests AWS_IAM) is refused with 400 BadRequestException and no partially-usable namespace is created; the identical call with an auth mode that DOES match a provider succeeds with 200. `NotImplemented` is not a modeled error.
Emulator: the call answers error code `NotImplemented` (HTTP 501) instead of `BadRequestException`, so neither the rejection nor the no-leftover-resource invariant exists.
Why: a client (or CDK/CFN) misconfiguring a channel namespace's auth modes gets an unmodeled server error instead of a 400 it can correct, so an input error is mis-classified as an outage; and because nothing is validated, an auth mode the parent API does not offer would be accepted once the stub is replaced by a naive implementation.
Fix: the CreateChannelNamespace handler and its cross-validation against the parent Api's eventConfig.authProviders in the appsync service crate (ops/create_channel_namespace.rs), plus the ChannelNamespace state it writes. The scaffold-stub issue filed for CreateChannelNamespace asks only that the operation exist; it does not record this rejection contract — close this cause only when the mismatched-auth-mode call is refused with BadRequestException/400 and leaves no namespace.
Traces: appsync.create-channel-namespace-invalid-auth-mode-rejected.

=== Cause 3 of 4: AssociateApi / GetApiAssociation / DisassociateApi against a domain that was never created answer NotImplemented instead of NotFoundException ===
AWS: Smithy models all three domain-association operations on /v1/domainnames/{domainName}/apiassociation (POST/GET/DELETE) with the error set AccessDeniedException(403), BadRequestException(400), NotFoundException(404), InternalFailureException(500) (DisassociateApi additionally ConcurrentModificationException(409)). A syntactically valid domainName (DomainName @length 1..253, pattern ^(\*[\w\d-]*\.)?([\w\d-]+\.)+[\w\d-]+$) that was never created with CreateDomainName can never have been associated, so every one of the three is refused with 404 NotFoundException rather than ever silently succeeding (recorded message examples: "Domain name not found." for AssociateApi/DisassociateApi, "Domain name not found" for GetApiAssociation).
Emulator: AssociateApi answers error code `NotImplemented` (HTTP 501) for the never-created domain instead of `NotFoundException`, and the same holds for the sibling association operations.
Why: a client cannot distinguish "this domain does not exist" from "the service is down", so the state-mismatch boundary that keeps an Api/DomainName association consistent is simply absent; code branching on NotFoundException to create the domain first takes the wrong branch.
Fix: the AssociateApi / GetApiAssociation / DisassociateApi handlers in the appsync service crate (ops/associate_api.rs, ops/get_api_association.rs, ops/disassociate_api.rs) and the DomainName/ApiAssociation state they read. Open issue 20261024T032443Z-appsync-control-plane-fidelity-domain-name-operations-unimplemented.md covers Get/List/Create/Update/DeleteDomainName only — the three association operations are not named there.
Traces: appsync.reject-api-domain-association-mismatched-state.

=== Cause 4 of 4: UpdateApi answers NotImplemented for every call, so no Event-API update ever applies and racing updates have no winner ===
AWS: Smithy UpdateApi (POST /v2/apis/{apiId}) requires apiId, name (ApiName @length 1..50, pattern ^[A-Za-z0-9_\-\ ]+$) and eventConfig, and returns HTTP 200 with the updated `api`; its modeled errors are AccessDeniedException(403), BadRequestException(400), ConcurrentModificationException(409), NotFoundException(404), UnauthorizedException(401), InternalFailureException(500). When several UpdateApi calls race on one Api, at least one succeeds (200) and the state converges to that winner's name; any loser is refused specifically with ConcurrentModificationException/409 — never some other code. `NotImplemented` is not modeled.
Emulator: all six concurrent UpdateApi calls return error code `NotImplemented` (HTTP 501) — zero successes — so an Event API can never be renamed or reconfigured and the last-writer-wins/409 concurrency contract does not exist.
Why: Event APIs are immutable in practice against this emulator; a client that updates an Api's name or eventConfig gets an unmodeled 501, and a client written to retry on ConcurrentModificationException sees an error code it does not model and gives up.
Fix: the UpdateApi handler in the appsync service crate (ops/update_api.rs) plus the Api state's update path and its concurrent-modification guard (losers -> ConcurrentModificationException/409). No open issue names UpdateApi.
Traces: appsync.update-api-concurrent-modification-converges.
