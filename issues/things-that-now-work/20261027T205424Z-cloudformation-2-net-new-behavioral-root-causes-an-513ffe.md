# cloudformation: 2 net-new behavioral root causes — an UpdateStack that changes an exported Output value while another stack imports it is accepted and reaches UPDATE_COMPLETE, and ExecuteChangeSet's InvalidChangeSetStatus refusal reports the change set's creation Status instead of its ExecutionStatus

## Description

=== Cause 1 of 2: UpdateStack changes an exported Output value that another live stack imports, instead of refusing the update ===
Failing check: cloudformation.export-value-update-refused-while-imported

AWS: Smithy (services/service-com-amazonaws-cloudformation-cloudformation/smithy-model/com-amazonaws-cloudformation-cloudformation.json): UpdateStack(StackName required; TemplateBody/TemplateURL/UsePreviousTemplate, Parameters, Capabilities, StackPolicy*, RollbackConfiguration, Tags, DisableRollback, ClientRequestToken, …) -> 200 {StackId, OperationId}; its only operation-specific modeled errors are InsufficientCapabilitiesException (client, httpError 400, awsQueryError InsufficientCapabilitiesException) and TokenAlreadyExistsException (client, 400), so the remaining refusal channel for this class is the service-common ValidationError at HTTP 400. ListImports is modeled as the read that tells a caller which stacks consume an export (ExportName required, output Imports, paginated on NextToken, NO modeled errors) — it exists precisely because an exported output value may not be changed or removed while it is in use. AWS's rule: an Outputs entry carrying Export.Name is immutable in VALUE while any other live stack resolves it with Fn::ImportValue. The attempted change does not succeed: the caller either gets a synchronous 400 ValidationError, or the stack settles in a terminal UPDATE_ROLLBACK_COMPLETE / UPDATE_FAILED whose StackStatusReason (and the failing resource's ResourceStatusReason) names the refusal. Message: the fixed text for this class is "Export " … " cannot be updated as it is in use by " … ; its variable parts are the export name (taken from the exporting stack's Outputs[*].Export.Name in the request's template) and the name of the importing stack (taken from the emulator's own cross-stack import index) — never values literal to one run. Whichever shape is chosen, the pre-update export value must survive: ListExports must still report the old value and the importing stack's consuming resource property must still hold it.

Emulator: the update is simply applied. Replaying the check, the exporter stack is created with Outputs.Exported = {"Value": {"Ref": "Shared"}, "Export": {"Name": <export>}}, an importer stack whose AWS::SNS::Topic DisplayName is {"Fn::ImportValue": <export>} reaches CREATE_COMPLETE, ListImports correctly names the importer (so the in-use condition IS detectable from the emulator's own state), and a positive-control update that changes only the NON-exported parameter correctly reaches UPDATE_COMPLETE. The update that changes the EXPORTED parameter's value then also reaches UPDATE_COMPLETE with the generic StackStatusReason "User Initiated": no 400 ValidationError is returned, no terminal failed/rollback status is published, and no reason naming the export or the importer appears anywhere. Assertion: "changing export '<export>' while '<importer>' imports it must be refused, but the update reached UPDATE_COMPLETE (evidence='User Initiated')". Note this is NOT the already-filed DeleteStack case: 20261027T083129Z-cloudformation-deletestack-on-a-stack-whose-export-is.md and Cause 2 of 20261026T000642Z-cloudformation-3-net-new-root-causes-the-stackset.md both cover DELETING an exporting stack whose export is in use (the emulator has an export_in_use guard on that path); neither covers UpdateStack changing the VALUE of an in-use export, and that guard is absent from the update path. 20261025T133035Z-cloudformation-7-net-new-root-causes-cli-deploy.md covers export-NAME collision, not value mutation while imported.

Why: a client relying on AWS's behavior believes its cross-stack contract is enforced. Against this emulator an export silently changes under every stack that imports it, so an importing stack's already-provisioned resources keep the stale value while ListExports reports the new one — the two are permanently inconsistent and nothing ever reports an error. Change-management tooling that depends on this refusal (any pipeline that relies on CloudFormation to block a breaking change to a shared VPC id, bucket name, queue URL, or role ARN) proceeds as if the change were safe, and an operator who deliberately tests the guard sees a green UPDATE_COMPLETE where AWS fails the update.

Fix: the UpdateStack handler's pre-flight validation and the cross-stack export/import state in the cloudformation crate — the same export/import index the DeleteStack handler already consults must be consulted when an update's reconciled Outputs change the VALUE of an export that index reports as in use, and the update must be refused (service-common ValidationError, 400) or driven to a terminal failed/rolled-back status with the reason recorded on the stack event, in AWS's wording for the class, with the export name and importing stack name taken from the request and from state. The pre-update export value and the importer's consuming resource property must be left untouched, and the identical update must succeed once the importer is gone.

=== Cause 2 of 2: re-executing an already-executed change set is refused with the wrong message — the creation Status, not the ExecutionStatus ===
Failing check: cloudformation.changeset-not-found-and-invalid-status-errors

AWS: Smithy: ExecuteChangeSet(ChangeSetName required, StackName, ClientRequestToken, DisableRollback, RetainExceptOnCreate) -> empty output; modeled errors ChangeSetNotFoundException (client, httpError 404, awsQueryError ChangeSetNotFound), InsufficientCapabilitiesException (400), InvalidChangeSetStatusException (client, httpError 400, awsQueryError code InvalidChangeSetStatus) and TokenAlreadyExistsException (400). The model documents InvalidChangeSetStatusException as "The specified change set can't be used to update the stack. For example, the change set status might be CREATE_IN_PROGRESS, or the stack status might be UPDATE_IN_PROGRESS." A change set has TWO independent status fields that DescribeChangeSet returns separately — Status (the creation lifecycle: CREATE_PENDING/CREATE_IN_PROGRESS/CREATE_COMPLETE/FAILED) and ExecutionStatus (AVAILABLE/EXECUTE_IN_PROGRESS/EXECUTE_COMPLETE/EXECUTE_FAILED/UNAVAILABLE/OBSOLETE) — and AWS words the two refusals differently accordingly. For a change set refused because it has ALREADY BEEN EXECUTED, the status in question is the EXECUTION status, and the message's fixed text is "ChangeSet [" … "] cannot be executed in its current execution status of [" … "]", with the variable parts being the change set's ARN (from state, as returned by CreateChangeSet's Id) and its ExecutionStatus value (here EXECUTE_COMPLETE). The "in its current status of [<Status>]" form is AWS's wording for the OTHER case — a change set whose CREATION has not completed. Status and error code are correct in the emulator; the message is not.

Emulator: services/service-com-amazonaws-cloudformation-cloudformation/src/ops/execute_change_set.rs refuses a non-executable change set from a single branch (`if !change_set.is_executable()`) that formats one message for both cases: "ChangeSet [{}] cannot be executed in its current status of [{}]" interpolating `change_set.change_set_id` and `change_set.status`. Replaying the check against an executed change set, the emulator answers InvalidChangeSetStatus (correct code, 400) with the message "ChangeSet [<cs-arn>] cannot be executed in its current status of [CREATE_COMPLETE]" where AWS says "ChangeSet [<cs-arn>] cannot be executed in its current execution status of [EXECUTE_COMPLETE]". Two things are wrong at once: the phrase omits "execution", and the interpolated value is the creation Status (CREATE_COMPLETE — which is the SUCCESSFUL creation state, so the sentence claims the change set cannot be executed because its creation completed) rather than the ExecutionStatus (EXECUTE_COMPLETE). Everything else in this check passes, including DescribeChangeSet/GetTemplate answering ChangeSetNotFound "ChangeSet [<name>] does not exist", DeleteChangeSet's no-op success, the execution itself reaching UPDATE_COMPLETE, and the change set and stack being left untouched by the rejected re-execute. No open issue names ExecuteChangeSet or InvalidChangeSetStatus; the sibling 20261025T015306Z-cloudformation-refusal-taxonomy-diverges-wrong-not-found-validation.md covers not-found/validation taxonomy on other operations and does not cover this message.

Why: a client that classifies refusals by message text — the AWS CLI's error output, error-matching layers, runbooks and tests that distinguish "this change set was already executed, drop it and create a new one" from "this change set is still being created, wait" — cannot tell the two cases apart, because the emulator reports the already-executed case using the still-being-created wording and reports a creation status that is the success value. The message actively misinforms: CREATE_COMPLETE is the state in which a change set IS executable, so the refusal reads as self-contradictory.

Fix: the refusal branch in the ExecuteChangeSet handler (services/service-com-amazonaws-cloudformation-cloudformation/src/ops/execute_change_set.rs, the `!change_set.is_executable()` arm) must split into the two cases AWS distinguishes and build the message from the matching field of the change set's state — the already-executed/unavailable case from the change set's ExecutionStatus using the "current execution status" wording, and the creation-not-complete case from its Status using the "current status" wording. The error code (InvalidChangeSetStatus) and HTTP 400 are already right and must not change.

Traces: cloudformation.changeset-not-found-and-invalid-status-errors ([mismatch]).
