# Neptune parameter and engine-version catalogs serve RDS reference data and misjudge engine/family names

> _Note: this issue was identified against the code base at commit `c27f8675843924c63f0ee6aedd1be01f08149ed1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeEngineDefaultClusterParameters

## Description
The Neptune front door's read-only reference surfaces (parameter catalogs, engine-default parameter catalogs, engine-version and orderable-option catalogs) are answered from an RDS-wide catalog and from an RDS-wide engine/family validator rather than from the graph engine's own. Ten distinct causes fall out of that: five where the parameter data served is not Neptune's, and five where the engine name or the DB-parameter-group family in the request is judged by RDS rules instead of Neptune's, inverting the verdict or the wording. The related open issue 20261030T024450Z-neptune-3-net-new-catalog-causes-engine-version.md covers only the DescribeDBEngineVersions/DescribeEventCategories/DescribeOrderableDBInstanceOptions catalog CONTENT clusters under the neptune-catalog-* fixtures; every cluster below is reported by replay with owned_by=[] and stub_path="", so none of them is carried by it or by any other open issue. THIS ISSUE HAS 10 CAUSES — all ten must be closed before submitting.

Cause 1 of 10: DescribeDBClusterParameters reports an RDS-worded Description for a Neptune cluster parameter. AWS: the operation's output carries Parameters, a list of com.amazonaws.neptune#Parameter whose Description member is documented as 'Provides a description of the parameter' (Smithy: neptune#Parameter.Description, target String). Recorded behavior only for the text: for the Neptune cluster parameter neptune_enable_audit_log the service's catalog describes it as 'Toggle audit logging for Neptune'. The whole string is fixed text belonging to that parameter in that engine's catalog; nothing in it comes from the request. Emulator: the same parameter is described as 'Enables the auditing of cluster activity.' — the RDS-generic wording. Why: a client that renders the parameter catalog to an operator, or that keys a configuration-drift check on the catalog description, shows and compares text the service never emits for this engine. Fix: the Neptune cluster-parameter reference catalog read by the DescribeDBClusterParameters handler. Traces: neptune-cluster-parameter-group-lifecycle#task#6.

Cause 2 of 10: DescribeDBParameters drops the terminating period from the Neptune instance-parameter Description. AWS: same Parameter.Description member (Smithy: neptune#Parameter.Description). Recorded behavior only for the text: the service describes neptune_query_timeout as 'Graph query timeout (ms).' — entirely fixed text, including the final period. Emulator: 'Graph query timeout (ms)', without it. Why: the description is a byte-for-byte catalog value; a client that compares a fetched catalog against a stored or documented one sees a spurious difference on every parameter whose text is truncated this way. Fix: the Neptune instance-parameter reference catalog read by the DescribeDBParameters handler. Traces: neptune-db-parameter-group-copy-and-lifecycle#task#4.

Cause 3 of 10: DescribeEngineDefaultClusterParameters serves a different engine-default cluster-parameter set, in a different order, with RDS-worded descriptions. AWS: the operation returns EngineDefaults carrying Parameters, a list of neptune#Parameter (Smithy: DescribeEngineDefaultClusterParameters, input DBParameterGroupFamily required, output shape DescribeEngineDefaultClusterParametersResult). Recorded behavior only for the catalog itself: for the Neptune cluster family the service reports, in its own order, neptune_enable_audit_log (Description 'Toggle audit logging for Neptune', ApplyType static, DataType boolean, AllowedValues '0,1', ParameterValue '0', Source engine-default), then neptune_enable_slow_query_log (Description 'Enable Slow query logs for Neptune', ApplyType dynamic, DataType string, AllowedValues 'disabled,info,debug', ParameterValue 'disabled'), then neptune_streams (Description 'Enable or disable Neptune Streams feature', ApplyType static, DataType boolean, AllowedValues '0,1', ParameterValue '0'). Emulator: no recorded element is present at its index — position 0 carries neptune_enable_audit_log with the RDS wording 'Enables the auditing of cluster activity.', position 1 carries neptune_enforce_ssl ('Requires client connections to the cluster to use TLS.') where the service reports neptune_enable_slow_query_log, and position 2 likewise diverges. Why: a client that discovers which cluster parameters it may set, and with what allowed values, before calling ModifyDBClusterParameterGroup reads a set that is not the engine's — it will offer parameters the engine does not publish and miss the ones it does (slow-query logging, Streams). Fix: the engine-default cluster-parameter reference catalog read by the DescribeEngineDefaultClusterParameters handler, including the published order of its entries. Traces: neptune-npt-traj-engine-default-parameter-levels#task#1.

Cause 4 of 10: DescribeEngineDefaultParameters serialises a single-entry Parameters list as a bare structure instead of a list member, and carries the RDS-worded description. AWS: EngineDefaults.Parameters is a LIST of neptune#Parameter and the operation is paginated over it (Smithy: DescribeEngineDefaultParameters paginated items=EngineDefaults.Parameters, pageSize=MaxRecords); the awsQuery response therefore wraps each element in a repeated Parameter member even when there is exactly one. The recording shows Parameters.Parameter as a one-element list whose element describes neptune_query_timeout with Description 'Graph query timeout (ms).'. Emulator: Parameters.Parameter is emitted as a single structure (type_mismatch: expected a list, got an object) and its Description is 'Graph query timeout (ms)' without the terminating period. Why: a generated SDK deserialising a list member that arrives as a scalar structure either fails or yields a one-element list by accident; any client that pages or indexes EngineDefaults.Parameters is reading a shape the model does not permit. Fix: the awsQuery serializer's list handling for EngineDefaults.Parameters in the DescribeEngineDefaultParameters response, plus the engine-default instance-parameter catalog for the description. Traces: neptune-npt-traj-engine-default-parameter-levels#task#2.

Cause 5 of 10: DescribeDBClusterParameters omits every descriptive member of a parameter when the parameter group's family is not one the Neptune catalog recognises. AWS: neptune#Parameter models AllowedValues, ApplyType, DataType, Description and IsModifiable alongside ParameterName/ParameterValue, and the service populates them for every parameter it reports, whatever family the group was created with — the family selects WHICH catalog is used, never whether the metadata is emitted. Recorded behavior only for the values: the recorded element reports ApplyType 'dynamic', DataType 'string', IsModifiable 'true', Description "The server's default character set." and the full AllowedValues character-set list for that family's parameter. Emulator: ParameterName/ParameterValue are emitted but AllowedValues, ApplyType, DataType, Description and IsModifiable are all absent (reported 'missing ... got None'). Why: a client cannot tell whether a parameter is modifiable, static or dynamic, or what values it accepts, so it cannot validate a ModifyDBClusterParameterGroup call before making it. Fix: the DescribeDBClusterParameters handler's projection of Parameter — the metadata members must be resolved from the group's family catalog rather than dropped when the family is unknown to it. Traces: neptune-parameter-group-family-not-engine-scoped#task#4.

Cause 6 of 10: DescribeEngineDefaultClusterParameters accepts a DB-parameter-group family that does not exist and answers 200. AWS: DBParameterGroupFamily is a required input member (Smithy: DescribeEngineDefaultClusterParametersMessage.DBParameterGroupFamily required) and a family the service does not publish is refused. The recording shows HTTP 400 with awsQuery ErrorResponse Error Type 'Sender', Code 'InvalidParameterValue', Message 'ParameterGroupFamily neptune9 is not a valid parameter group family' — fixed text 'ParameterGroupFamily ' + the family name taken verbatim from the request + ' is not a valid parameter group family'. Emulator: answers HTTP 200 with an engine-defaults body and no ErrorResponse at all. Why: a client that probes a family name before creating a parameter group concludes the bogus family is valid and goes on to create a group against it, so the error surfaces later (or never) instead of at the call that was wrong. Fix: the DescribeEngineDefaultClusterParameters handler's input validation — the family must be resolved against the published family catalog before any defaults are returned. Traces: neptune-npt-traj-engine-default-parameter-levels#task#3.

Cause 7 of 10: DescribeEngineDefaultParameters refuses an engine-name-only family with its own generic explanation instead of AWS's family message. AWS: for a DBParameterGroupFamily that is a bare engine name rather than an engine+version family, the service answers HTTP 400 InvalidParameterValue with Message 'ParameterGroupFamily <family> is not a valid parameter group family' — the same fixed template as cause 6, the family name taken from the request (here the bare engine name). Emulator: answers HTTP 400 but with the message "Invalid value '<family>' for DBParameterGroupFamily: a DB parameter group family names an engine this service serves followed by that engine's version (mysql8.0, aurora-postgresql16, sqlserver-ee-15.0)" — a different template, and one whose examples name RDS engines that the Neptune front door does not serve. Why: the status and code are right but a client matching on the message (log assertions, user-facing error surfacing, retry classification keyed on text) sees wording the service never produces, and an operator is pointed at MySQL/SQL Server families by a Neptune endpoint. Fix: the message template used by the DescribeEngineDefaultParameters family validation. Traces: neptune-npt-traj-engine-default-parameter-levels#task#4.

Cause 8 of 10: DescribeDBEngineVersions refuses a Neptune engine-version query outright, so the engine catalog cannot be read before a create. AWS: DescribeDBEngineVersions models NO errors at all (Smithy: DescribeDBEngineVersions errors=[]) and returns DBEngineVersionMessage.DBEngineVersions; querying the Neptune front door for its engine and a published version answers HTTP 200 with that release's DBEngineVersion element — Engine 'neptune', the requested EngineVersion, its MajorEngineVersion/MinorEngineVersion, its DBParameterGroupFamily, DBEngineVersionDescription, ExportableLogTypes [audit, slowquery], SupportsLogExportsToCloudwatchLogs true, SupportsGlobalDatabases true and the ServerlessV2FeaturesSupport capacity range. Emulator: answers HTTP 400 with no DescribeDBEngineVersionsResponse body. Why: this is the discovery call a client makes before CreateDBCluster/CreateDBInstance to pick a version; refusing it makes the whole create path undiscoverable and breaks any client that validates its configured engine version first. Fix: the DescribeDBEngineVersions handler's engine/version resolution for the Neptune front door — the graph engine and its releases must be present in the engine catalog it queries. Traces: neptune-npt-traj-engine-version-catalog-to-create#task#1.

Cause 9 of 10: DescribeDBEngineVersions misclassifies an unknown engine name as InvalidParameterCombination with an RDS default-version message. AWS: for an engine name the service does not serve, the recorded refusal is HTTP 400 with Error Type 'Sender', Code 'InvalidParameterValue' and Message 'Unrecognized engine name: <engine>' — fixed text 'Unrecognized engine name: ' plus the Engine value from the request. Emulator: HTTP 400 with Code 'InvalidParameterCombination' and Message "RDS can't find a default engine version." — a different error class and a message that does not mention the engine the caller asked for. Why: the code is what a client branches on; InvalidParameterCombination tells it the combination of inputs was wrong rather than that the Engine value was, and the message names no offending value, so the caller cannot correct the request. Fix: the DescribeDBEngineVersions handler's engine validation — unknown engine names must raise InvalidParameterValue with the engine named. Traces: neptune-npt-traj-engine-version-catalog-to-create#task#2.

Cause 10 of 10: DescribeOrderableDBInstanceOptions words an invalid-engine refusal as an 'Unrecognized engine name' listing instead of AWS's 'Invalid DB engine'. AWS: Engine is a required input member (Smithy: DescribeOrderableDBInstanceOptionsMessage.Engine required) and the operation models no errors; the recorded refusal for an engine this front door does not serve is HTTP 400 InvalidParameterValue with Message 'Invalid DB engine' — the message is entirely fixed text and names no value. Emulator: HTTP 400 with Message 'Unrecognized engine name: <engine>', a different template that also echoes the request value. Why: identical class and status, different wording; a client or test that matches the service's refusal text does not match. Fix: the message used by the DescribeOrderableDBInstanceOptions engine validation (note that this is the inverse of cause 9 — the two operations use each other's template). Traces: neptune-npt-traj-engine-version-catalog-to-create#task#6.
