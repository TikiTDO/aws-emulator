# ses: 7 net-new behavioral root causes in the receipt-rule plane — CreateReceiptRule/UpdateReceiptRule pre-flight nothing (header charset, S3 bucket existence and grant, Lambda invoke permission, SNS topic), DescribeReceiptRule drops TlsPolicy and the SNSAction.Encoding default, and v1 GetIdentityVerificationAttributes cannot see a SESv2-created identity

> _Note: this issue was identified against the code base at commit `65fd8797851bb5c5937d1ea0792f5c718c73df47`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateReceiptRule

## Description
Seven net-new behavioral root causes on the SES v1 (awsQuery) receipt-rule surface, plus one cross-API identity read. None is marked ALREADY FILED or OWNED in the replay report. Open issues that touch the same crate but do NOT carry these causes: 20261025T171011Z-ses-v1-awsquery-createreceiptruleset-is-refused-pre-dispatch.md (router-level AmbiguousService on CreateReceiptRuleSet — requests are now dispatched, so the defects below are behind the dispatcher), 20261025T214303Z-ses-describereceiptruleset-stub.md and 20261027T215946Z-ses-deletereceiptrule-stub.md (scaffold stubs for other operations).

Cause 1 of 7: CreateReceiptRule accepts an AddHeaderAction HeaderName outside the documented charset.
AWS: Smithy (com.amazonaws.ses#SimpleEmailService, awsQuery) AddHeaderAction.HeaderName is required and targets HeaderName with NO pattern in the model; its documentation states the rule — "The name must contain at least one character, and can contain up to 50 characters. It consists of alphanumeric (a-z, A-Z, 0-9) characters and dashes." The refusal itself is recorded behavior only: HTTP 400 with awsQuery Error.Code InvalidParameterValue and Error.Message "Invalid header name: <HeaderName>" — the fixed text is "Invalid header name: " and the variable part is the submitted HeaderName echoed verbatim from the request. The rejected rule is not persisted, and a well-formed name (letters, digits, dashes) is accepted.
Emulator: the call with HeaderName containing spaces and '!' answers HTTP 200 with an empty CreateReceiptRuleResponse and persists the rule — replay: "real AWS rejects this call, but it SUCCEEDED and returned {... 'HTTPStatusCode': 200 ...}".
Why: a client that relies on SES to reject a malformed inbound header name ships a receipt rule AWS would never have created; the fault surfaces only in production, and the negative-test class (bad charset -> InvalidParameterValue) cannot be exercised at all.
Fix: input validation in the CreateReceiptRule handler of the ses v1 crate (the AddHeaderAction branch of its action validation), before anything is written to the rule-set state.
Traces: ses.create-receipt-rule-invalid-header-name-rejected.

Cause 2 of 7: CreateReceiptRule never pre-flights an S3Action's bucket — neither a missing bucket nor an existing bucket that grants SES nothing is refused, and the two faults are not distinguished.
AWS: Smithy CreateReceiptRule declares InvalidS3ConfigurationException (awsQueryError code InvalidS3Configuration, httpResponseCode 400). SES pre-flights the bucket when the rule is created (it also drops a permission-check object into it). Recorded behavior for the two distinct faults: a bucket that does not exist -> InvalidS3Configuration with message "No such bucket: <BucketName>"; a bucket that exists in the caller's account but carries no policy granting ses.amazonaws.com s3:PutObject -> InvalidS3Configuration with message "Could not write to bucket: <BucketName>". In both the fixed text is the sentence prefix and the variable part is the BucketName taken from the request's S3Action; the refusals must not collapse into one byte-identical Error dict, the refusal must not name any bucket other than the one in the request, nothing is persisted, and the identical call succeeds once the bucket exists and the AllowSESPuts policy is published.
Emulator: both calls answer HTTP 200 and persist the rule — replay: "expected this call to be rejected, but it SUCCEEDED and returned {... 'HTTPStatusCode': 200 ...}" (ghost bucket) and "real AWS refuses this call, but it SUCCEEDED and returned {... 'HTTPStatusCode': 200 ...}" (existing bucket, no grant).
Why: the whole S3-destination misconfiguration class disappears. A client that depends on SES to tell it at rule-creation time that the bucket is absent or unwritable instead gets a rule that silently drops every received message, and it can never tell the two causes apart because neither is reported.
Fix: the S3Action branch of the CreateReceiptRule handler's pre-flight in the ses v1 crate — resolve the bucket in the emulator's S3 state and evaluate its bucket policy for ses.amazonaws.com s3:PutObject, emitting the two distinct InvalidS3Configuration messages above and persisting nothing on refusal.
Traces: ses.create-receipt-rule-invalid-s3-bucket-fails, ses.receipt-rule-s3-action-requires-a-live-bucket-policy-grant.

Cause 3 of 7: CreateReceiptRule never pre-flights a LambdaAction's invoke permission.
AWS: Smithy CreateReceiptRule declares InvalidLambdaFunctionException (awsQueryError code InvalidLambdaFunction, httpResponseCode 400); LambdaAction.FunctionArn is required. SES checks, at rule-creation time, that the named function grants ses.amazonaws.com lambda:InvokeFunction with a SourceArn scoped to THIS receipt rule (arn:aws:ses:<region>:<account>:receipt-rule-set/<set-name>:receipt-rule/<rule-name>). Recorded behavior: when the function exists but carries no resource policy, and also when it carries a grant scoped to a DIFFERENT receipt rule, the call is refused with InvalidLambdaFunction and the message "Could not invoke Lambda function: <FunctionArn>" — fixed sentence prefix plus the FunctionArn from the request. Once a grant scoped to this rule exists, the identical call succeeds.
Emulator: the call answers HTTP 200 with no permission check at all — replay: "real AWS refuses this call, but it SUCCEEDED and returned {... 'HTTPStatusCode': 200 ...}" for the no-policy leg (the check first proves the function is readable and that lambda:GetPolicy answers ResourceNotFoundException, so the only thing missing is the grant).
Why: an over-permissive accept hides the single most common SES-receiving misconfiguration; a caller gets a rule whose Lambda action can never fire, and a mis-scoped grant (another rule's SourceArn) is indistinguishable from a correct one.
Fix: the LambdaAction branch of the CreateReceiptRule handler's pre-flight in the ses v1 crate — read the function's resource policy from the emulator's lambda state and require a lambda:InvokeFunction statement for principal ses.amazonaws.com whose SourceArn names the rule being created.
Traces: ses.receipt-rule-lambda-action-requires-a-rule-scoped-invoke-permission.

Cause 4 of 7: UpdateReceiptRule performs no action pre-flight of any kind, so a rule can be mutated into an unusable state.
AWS: Smithy UpdateReceiptRule declares exactly the same destination errors as CreateReceiptRule — InvalidLambdaFunctionException (InvalidLambdaFunction/400), InvalidS3ConfigurationException (InvalidS3Configuration/400), InvalidSnsTopicException (InvalidSnsTopic/400) — and the same pre-flight applies on update. Recorded messages: "Could not invoke Lambda function: <FunctionArn>" for a LambdaAction naming a function SES cannot invoke; "No such bucket: <BucketName>" for an S3Action naming a bucket that does not exist; "Could not publish to SNS topic: <TopicArn>" for an SNSAction naming a topic SES cannot publish to (each a fixed sentence prefix plus the ARN/name taken from the request), and the stored rule is left exactly at its last-good state.
Emulator: every one of the three updates answers HTTP 200 — replay: "expected rejection, but the call SUCCEEDED and returned {... 'HTTPStatusCode': 200 ...}" (lambda), "expected the call to be rejected, but it SUCCEEDED: {... 'HTTPStatusCode': 200 ...}" (s3), "expected a rejection, but the call SUCCEEDED and returned {... 'HTTPStatusCode': 200 ...}" (sns).
Why: a client that validates its receiving configuration by attempting the update, and treats success as proof the destination is reachable, is told its broken configuration is good — and the previously working rule is overwritten by it instead of being preserved.
Fix: the UpdateReceiptRule handler in the ses v1 crate must run the same destination pre-flight as CreateReceiptRule (shared validation for the LambdaAction/S3Action/SNSAction branches) and leave the stored rule untouched when it refuses.
Traces: ses.update-receipt-rule-invalid-lambda-function-rejected, ses.update-receipt-rule-invalid-s3-configuration-rejected, ses.update-receipt-rule-invalid-sns-topic-rejected.

Cause 5 of 7: DescribeReceiptRule omits the Rule's TlsPolicy member entirely, so the rule's default (and post-update) TLS policy is unreadable.
AWS: Smithy ReceiptRule.TlsPolicy targets the TlsPolicy enum (values Require, Optional) and is documented "The default is Optional"; Enabled and ScanEnabled are booleans with modelled default false. DescribeReceiptRule output Rule therefore always carries TlsPolicy — Optional for a rule created without one, and the value last written otherwise. UpdateReceiptRule is a full replace, so a rule updated with only Name reads back TlsPolicy Optional, Enabled false, ScanEnabled false, no Recipients and no Actions.
Emulator: the serialized Rule has no TlsPolicy member at all — replay: KeyError: 'TlsPolicy' on rule["TlsPolicy"] both for a freshly created rule (ses.receipt-rule-describe-update-and-position) and after the full-replace update (ses.update-receipt-rule-full-replace-resets-unspecified-fields).
Why: an SDK client reading a receipt rule cannot tell whether inbound mail is required to arrive over TLS; the member is modelled, so typed clients and any round-trip-then-rewrite workflow either KeyError or silently rewrite the rule without a TlsPolicy.
Fix: the receipt-rule record and its awsQuery serializer in the ses v1 crate — persist TlsPolicy (defaulting to Optional when the request omits it) and emit it on DescribeReceiptRule/DescribeReceiptRuleSet, together with the Enabled/ScanEnabled defaults.
Traces: ses.receipt-rule-describe-update-and-position, ses.update-receipt-rule-full-replace-resets-unspecified-fields.

Cause 6 of 7: an SNSAction created without Encoding reads back with no Encoding instead of the default UTF-8.
AWS: Smithy SNSAction.Encoding targets the SNSActionEncoding enum and is documented "The default value is UTF-8." A rule created with an SNSAction that omits Encoding therefore reads back Encoding "UTF-8" from DescribeReceiptRule.
Emulator: the member is absent — replay: "expected the omitted SNSAction.Encoding to default to 'UTF-8', got None".
Why: a client that round-trips a rule (read, modify one field, write back) loses the encoding semantics, and code that branches on the notification encoding has no value to branch on where AWS always supplies one.
Fix: default materialisation in the ses v1 crate's receipt-action model/serializer — apply the documented UTF-8 default to SNSAction.Encoding when the request omits it, the same way the other action defaults are applied.
Traces: ses.create-receipt-rule-rich-actions-round-trip.

Cause 7 of 7: v1 GetIdentityVerificationAttributes returns no entry for an identity created through SESv2 CreateEmailIdentity. This is the same defect as Cause 3 of the open issue 20261025T214303Z-ses-identity-verification-is-auto-completed-and-the.md (the v1/v2 identity store is not shared); it is filed here because that issue does not carry this check's replay key, and this check reaches the divergence through a different path (the send-refusal path, whose earlier assertions all PASS).
AWS: SESv2 CreateEmailIdentity and SES v1 are two APIs over one set of account identities. Smithy (v1) GetIdentityVerificationAttributes: input Identities (required list), output VerificationAttributes (required map) of IdentityVerificationAttributes{VerificationStatus required, enum [Pending, Success, Failed, TemporaryFailure, NotStarted]}. An email identity created a moment earlier through SESv2 and never confirmed is therefore reported by v1 as VerificationStatus "Pending" (v1's TitleCase spelling of v2's PENDING).
Emulator: the v1 map comes back without the identity at all — replay: KeyError: 'sim2real-behav-sender@sim2real-behav-unverif-<id>.example.com' on v1_attrs[created]. Everything the check asserts before that point passes, including both MessageRejected refusals with the "Email address is not verified. The following identities failed the check in region <REGION>: <identity>" message and the unchanged 24-hour send counters, so the single divergence is the cross-API read.
Why: a workflow that creates identities with the modern API and polls the legacy one for the Pending->Success transition sees an empty account and can never converge; 'not verified' and 'does not exist' become indistinguishable through v1.
Fix: the identity state shared by the two crates — SESv2 CreateEmailIdentity must write into the same per-account/region identity store that the ses v1 GetIdentityVerificationAttributes handler reads, with the v1<->v2 status spelling mapped on read.
Traces: ses.send-unverified-identity-rejected-quota-unchanged.
