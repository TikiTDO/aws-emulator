# appconfig__iam__lambda: a Lambda handler's in-process AppConfig data-plane read never converges on a decidable answer, so all three handler-level AppConfig scenarios are killed at the harness cap

> _Note: this issue was identified against the code base at commit `ef4505bfafb91e46a48884457977c8eb48b81782`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
One net-new root cause, grounded in three behavioral checks that are each killed at the harness 60 s cap without reaching any assertion.

NOTE ON PRIOR WORK: 20261105T085348Z-appconfig-iam-lambda-the-in-process-lambda-python.md is open and names these same three check ids, but it was filed against a DIFFERENT failure signature (its Issue-Keys are AssertionError on `assert "FunctionError" not in resp` — the handler faulting Runtime.ImportModuleError / No module named 'boto3' at import). In this replay none of the three checks is marked OWNED or ALREADY FILED and none of them reaches that assertion any more: they now hang instead of failing fast, i.e. the handler no longer reports FunctionError but still never produces the answer AWS produces. That issue therefore does not cover this run's failure; close this one on the in-function AppConfig read converging.

Cause 1 of 1: a python Lambda whose handler opens an appconfigdata session and reads the deployed configuration never returns an answer that satisfies the scenario, so every loop built on it exhausts its budget and the check is killed.
Failing check ids: appconfig__iam__lambda.execution-role-without-appconfig-actions-denied-in-handler, appconfig__iam__lambda.handler-with-logical-id-identifiers-falls-back-to-default, appconfig__iam__lambda.in-place-identifier-fix-reaches-appconfig-only-once-all-three-are-real.
AWS: Smithy (services/service-com-amazonaws-appconfigdata-appconfigdata/smithy-model/com-amazonaws-appconfigdata-appconfigdata.json) models StartConfigurationSession as POST /configurationsessions (success 201, output InitialConfigurationToken, errors BadRequestException 400 / ResourceNotFoundException 404 / ThrottlingException 429 / InternalServerException 500) and GetLatestConfiguration as GET /configuration?configuration_token=... (success 200, Configuration as the @httpPayload blob, errors BadRequestException 400 / ResourceNotFoundException 404 / ThrottlingException 429 / InternalServerException 500); lambda Invoke answers StatusCode 200 with the handler's own payload and no X-Amz-Function-Error when the handler returns normally. On AWS the three legs these checks need are each reachable within seconds of the deployment reaching COMPLETE: (a) POSITIVE — a handler under a role granting appconfig:StartConfigurationSession/GetLatestConfiguration/GetConfiguration, given the REAL application/environment/profile ids, gets the deployed bytes, so its answer reports source 'appconfig' and the exact deployed document; (b) IDENTIFIER NEGATIVE — the same handler given CloudFormation-logical-id-shaped identifiers (names that match no application/environment/profile) is refused ResourceNotFoundException/404 by StartConfigurationSession and falls back to its own default; (c) IDENTITY NEGATIVE — the same handler under an execution role that grants NO appconfig: action is refused AccessDeniedException (not ResourceNotFoundException: the resources exist and are deployed) and falls back to its default, while an authorized caller is still served the same bytes.
Emulator: all three checks report exactly 'Error: Check timed out after 60.0s' with verdict [mismatch] — no assertion in any of them is reached. Each blocks in an invoke-until loop (_INVOKE_TIMEOUT_S = 240, 5 s between invocations) whose predicate is the handler's self-reported source: the positive leg waits for a.get('source') == 'appconfig' and the negative legs wait for a.get('source') == 'default' with a specific Error.Code. Because the loop never returns, none of the deployed-bytes, ResourceNotFoundException and AccessDeniedException outcomes above is observable. Hypothesis: the handler's in-process appconfigdata call never yields the deployed configuration (so the positive-control predicate never holds and the loop runs to its budget), which is consistent with the data-plane gap already filed as 20261024T112615Z-appconfigdata-data-plane-deployed-configuration-never-served-sessions.md; the emulator's own replay output shows only the timeout, so the specific leg that stalls must be re-observed with the steps below.
Why: this is the whole point of AppConfig for a serverless client. A function's feature flags silently stay at its hard-coded default, and the two faults an operator must be able to tell apart — a wrong identifier (ResourceNotFoundException) and a missing appconfig: grant (AccessDeniedException) — are indistinguishable and unobservable, so a caller debugging a stale value against this emulator gets no signal at all and any caller polling for the real value never returns.
Fix: the lambda Invoke execution path's in-process AWS SDK environment together with the appconfigdata data-plane handlers it calls — a handler's StartConfigurationSession/GetLatestConfiguration against the emulator must return the deployed bytes for real ids, 404 ResourceNotFoundException for identifiers that resolve to nothing, and AccessDeniedException when the function's execution role grants no appconfig: action, each promptly enough for a synchronous invoke to answer.
Traces: the three failing check ids above. Generated role, function, application, environment and profile names/ids in those runs are per-run values that only fill the templates; the requirements are the served bytes and the two error codes.
