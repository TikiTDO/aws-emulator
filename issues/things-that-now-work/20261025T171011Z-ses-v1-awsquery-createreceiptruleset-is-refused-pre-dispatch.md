# SES v1 (awsQuery) CreateReceiptRuleSet is refused pre-dispatch with AmbiguousService framed as awsJson, so the LambdaAction invoke-permission pre-flight is unreachable

> _Note: this issue was identified against the code base at commit `e730bd97e23027ce38421dab7cedb53db537ccde`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateReceiptRuleSet

## Description
One root cause, in the pre-dispatch request router / service registry and the gateway's pre-dispatch error serializer — not in any SES operation handler.

Related open issues that do NOT carry this check's replay key (so this is filed separately and must be re-replayed with the id in trace_ids before any of them is closed): 20261023T120410Z-ses-v1-and-v2-is-entirely-unreachable-the.md (reports the signing-name route collision for the other 137 checks; its Issue-Trace-Ids do not list this check), 20261024T184456Z-ses-v1-awsquery-createreceiptruleset-is-never-dispatched-the.md (same operation, but keyed to ses.receipt-rule-s3-action-kms-key-policy-is-evaluated-apart-from-the-bucket-grant), and 20261025T114929Z-ses-the-pre-dispatch-ambiguousservice-refusal-is-served.md (the retryable-status facet, keyed to ses.contact-list-and-contacts-paginators-walk-every-item-once). None of them lists ses.receipt-rule-lambda-action-requires-a-rule-scoped-invoke-permission.

Cause 1 of 1: route resolution by sigv4 signing name alone makes the entire SES v1 surface unreachable, and the resulting refusal is serialized with awsJson framing on an awsQuery (XML) service, so the SDK cannot classify it at all.
AWS: SES v1 is an ordinary sigv4-signed service reached at its own endpoint and answers with its modeled output or a modeled client error. Smithy (services/service-com-amazonaws-ses-simpleemailservice/smithy-model/com-amazonaws-ses-simpleemailservice.json): service SimpleEmailService, version 2010-12-01, protocols [awsQuery], sigv4Name 'ses', awsService.endpointPrefix 'email', xmlNamespace http://ses.amazonaws.com/doc/2010-12-01/. Smithy: CreateReceiptRuleSet(RuleSetName required) -> empty output, HTTP 200 XML CreateReceiptRuleSetResponse; its only modeled errors are AlreadyExistsException (awsQueryError code 'AlreadyExists', 400) and LimitExceededException ('LimitExceeded', 400). Because the protocol is awsQuery, EVERY response — success or failure — is XML: an error is an <ErrorResponse><Error><Code>/<Message></Error></ErrorResponse> envelope that botocore surfaces as a ClientError carrying that Code. On AWS a client sees exactly one service behind the endpoint it addressed; a signing name is not an identity (SimpleEmailService, SimpleEmailService_v2, AmazonPinpointEmailService and MailManagerSvc all sign as 'ses'). 'AmbiguousService' is a code in no AWS model, and no AWS service answers a correctly addressed request by refusing to decide which service owns it.
Emulator: the call never reaches a handler. The check's first SES call, ses.create_receipt_rule_set(RuleSetName=...), is answered with the non-AWS body b'{"__type":"AmbiguousService","message":"4 emulated services all claim requests for \'ses\': ses, ses, ses, ses; the request is rejected rather than served by an arbitrary one"}'. Two things are wrong at once: (a) the request is refused instead of dispatched, and (b) the refusal is framed as awsJson for a service the model fixes as awsQuery/XML, so botocore cannot parse it and raises botocore.parsers.ResponseParserError 'Unable to parse response (not well-formed (invalid token): line 1, column 0), invalid XML received. Further retries may succeed' instead of any status/code pair. In that message the fixed text is 'emulated services all claim requests for' / 'the request is rejected rather than served by an arbitrary one'; the variable parts (the count '4' and the repeated registration names) come from the emulator's own service registry, not from the request — nothing in the request or in AWS's model produces either.
Why: a client gets neither the operation's behavior nor a classifiable failure. No receipt rule set can be created, so nothing that depends on one is configurable or observable — in particular CreateReceiptRule's LambdaAction pre-flight, which on AWS must refuse a LambdaAction whose target function grants ses.amazonaws.com nothing (and whose grant is scoped by SourceArn to a different receipt rule) with awsQuery code InvalidLambdaFunction, HTTP 400, message 'Could not invoke Lambda function: <FunctionArn>' (fixed text 'Could not invoke Lambda function: ' plus the FunctionArn taken verbatim from the request's Rule.Actions[].LambdaAction.FunctionArn; Smithy: CreateReceiptRule errors InvalidLambdaFunctionException awsQueryError code InvalidLambdaFunction httpError 400, alongside InvalidS3Configuration, InvalidSnsTopic, RuleSetDoesNotExist, RuleDoesNotExist, AlreadyExists, LimitExceeded). Because the error body is not in the addressed service's protocol framing, even generic error handling, error-code branching and retry classification break: the SDK sees a parse error with no code.
Fix: the pre-dispatch route-resolution layer (service selection before operation dispatch) must disambiguate the four registrations sharing sigv4 name 'ses' to exactly one target per request, using protocol + endpoint prefix + request shape (awsQuery POST / with an Action= body for SES v1, restJson1 /v2/email/... for SESv2, /v1/email/... for Pinpoint Email, awsJson1_0 X-Amz-Target for Mail Manager); and the gateway's pre-dispatch error serializer must emit the addressed service's protocol framing (an XML <ErrorResponse> envelope for awsQuery) rather than always awsJson. Once dispatch works, CreateReceiptRule's LambdaAction validation belongs in that operation's handler pre-flight.
Traces: ses.receipt-rule-lambda-action-requires-a-rule-scoped-invoke-permission (the STS/IAM/Lambda setup calls succeed; the failure is on the first SES v1 call, ses.create_receipt_rule_set).
