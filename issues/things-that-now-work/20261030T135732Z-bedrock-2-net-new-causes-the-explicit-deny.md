# bedrock: 2 net-new causes — the explicit-deny AccessDeniedException message names a wildcard resource ARN instead of the resource the request names, and CreateModelInvocationJob never accepts a well-formed batch-inference submission

> _Note: this issue was identified against the code base at commit `07e872c7593558b582731e73c173338530c40226`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetGuardrail, CreateModelInvocationJob

## Description
TWO net-new root causes on the bedrock control plane, both grounded in failing behavioral checks that no open issue carries a replay key for. A fixer must close BOTH before submitting.

=== Cause 1 of 2: the explicit-deny AccessDeniedException message names a wildcard resource ARN ("guardrail/*") instead of the ARN of the resource the request names ===

AWS: Smithy (com.amazonaws.bedrock) models GetGuardrail as GET /guardrails/{guardrailIdentifier} (success 200) with errors AccessDeniedException (httpError 403), ValidationException (400), ResourceNotFoundException (404), ThrottlingException (429), InternalServerException (500); AccessDeniedException carries a single `message` member, and the model does not state its text — recorded behavior only for the wording. The recorded refusal is the standard IAM explicit-deny message for this error class. Its FIXED text is: "User: " … " is not authorized to perform: " … " on resource: " … " with an explicit deny in an identity-based policy". Its VARIABLE parts are taken from the request and from state: (a) the caller's assumed-role session ARN, from the request's signing identity (arn:aws:sts::<account-id>:assumed-role/<role-name>/<role-session-name>); (b) the action, `bedrock:<OperationName>` — here `bedrock:GetGuardrail`; and (c) THE ARN OF THE RESOURCE THE REQUEST NAMES — for GetGuardrail the guardrail ARN resolved from the `guardrailIdentifier` httpLabel, i.e. arn:aws:bedrock:<region>:<account-id>:guardrail/<guardrailId> (GetGuardrail's own output member guardrailArn is modelled @pattern ^arn:aws(-[^:]+)?:bedrock:[a-z0-9-]{1,20}:[0-9]{12}:guardrail/[a-z0-9]+$, which admits no wildcard). AWS reports the resource the CALL targeted, never the policy statement's Resource element and never a wildcard.

Emulator: the status (403) and the error code (AccessDeniedException) are right, and the session-ARN and action segments are right, but the resource segment is a wildcard ARN. Replayed message: 'User: arn:aws:sts::<account-id>:assumed-role/<role-name>/<role-session-name> is not authorized to perform: bedrock:GetGuardrail on resource: arn:aws:bedrock:<region>:<account-id>:guardrail/* with an explicit deny in an identity-based policy' — the trailing element is the literal `*` rather than the guardrailId the request supplied. Everything else in the message matched the recording character for character, so this is a single wrong substitution, not a reworded message.

Why: a client relying on AWS's behavior parses the resource ARN out of the denial to learn WHICH resource was refused — least-privilege CI gates, access-analyzer style tooling, audit log scrapers and operator runbooks all key on it. With a wildcard there, a caller that was denied one guardrail out of many cannot tell which, and automated remediation reads the `*` as the policy's Resource and widens a grant to every guardrail in the account instead of the one that was needed. Any assertion on the exact denial text (the recorded contract for this error class) fails.

Fix: the shared request-authorization layer the control-plane handlers are served behind — `services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/service/authorization.rs`, reached from `src/service.rs` (named as the home of this decision in the Resolution of the fixed issue 20261029T172312Z-bedrock-control-plane-applies-no-authorization-gate-an.md). The message renderer there must substitute the ARN of the resource the request names, resolved from the operation's own resource identifier (for GetGuardrail the `guardrailIdentifier` httpLabel, expanded to the full guardrail ARN when a bare id is supplied), rather than a wildcard/resource-type ARN. GetGuardrail's handler itself takes no authorization decision (its `handle` opens with `let _ = ctx;`), so no change belongs there.

Traces: bedrock.resource-policy-cross-account-access-enforced-denied. Related open issue that does NOT cover this (it carries no replay key for this assertion, and describes the gate as ABSENT rather than mis-worded): 20261024T025841Z-bedrock-control-plane-no-iam-authorization-gate-guardrail.md. The gate now exists and fires; only the resource substitution in its message diverges.

=== Cause 2 of 2: CreateModelInvocationJob never accepts a well-formed batch-inference submission, so the operation's success path is unreachable ===

AWS: Smithy CreateModelInvocationJob = POST /model-invocation-job, success 200, required members jobName, roleArn (@pattern ^arn:aws(-[^:]+)?:iam::([0-9]{12})?:role/.+$), modelId (ModelId, length 1..2048, pattern admitting a bare model id OR an arn:aws:bedrock:<region>::foundation-model/<model-id> ARN OR a custom-model/inference-profile ARN), inputDataConfig and outputDataConfig; required output member jobArn; errors AccessDeniedException (403), ValidationException (400), ResourceNotFoundException (404), ConflictException (400), ServiceQuotaExceededException (400), ThrottlingException (429), InternalServerException (500). Recorded behavior: a submission that names an existing foundation model by its foundation-model ARN, a same-account service role whose trust policy grants bedrock.amazonaws.com sts:AssumeRole and whose inline policy grants s3:GetObject/s3:ListBucket/s3:PutObject on the staged bucket, and inputDataConfig/outputDataConfig s3Uri values matching S3Uri's pattern, is ACCEPTED on the FIRST attempt: HTTP 200 carrying a jobArn, after which GetModelInvocationJob reports a status in {Submitted, Validating, Scheduled, InProgress, Completed, PartiallyCompleted}. None of the modelled 4xx errors is a correct answer to such a request.

Emulator: no jobArn is ever returned. The check stages 100 JSONL records in S3, creates the batch role, confirms the malformed-s3Uri refusal (that half now matches AWS: 400 ValidationException with the "1 validation error detected: Value at 'inputDataConfig.s3InputDataConfig.s3Uri' failed to satisfy constraint: Member must satisfy regular expression pattern: …" wording) and that no job was created, and then submits the identically-shaped WELL-FORMED request in a loop that retries whenever the answer is AccessDeniedException, ResourceNotFoundException or ValidationException. That loop never obtains a jobArn: the check is killed with "Check timed out after 60.0s" having never reached its post-submission assertions, so the emulator answered one of those three refusals to every attempt over the whole window instead of 200. Hypothesis for which refusal: `services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/create_model_invocation_job.rs` resolves `modelId` against the store's own catalogue (lines 291-311: `store.foundation_models.qualified_model(base_model_id_of(&input.model_id))` OR `custom_model(...)` OR `inference_profile_arn_of(...)`) and, on a miss, returns ResourceNotFoundException "modelId <id> does not name a model in this account in <region>" — a model id that AWS's catalogue carries but this emulator's does not therefore makes every attempt fail with a code the caller's retry loop treats as transient. AWS answers 200 for the same request, and for a genuinely unresolvable identifier answers 400 ValidationException, not 404.

Why: the whole batch-inference surface is unusable against the emulator — a caller cannot submit a job at all, so nothing downstream (GetModelInvocationJob, ListModelInvocationJobs, StopModelInvocationJob, the output objects in S3) can be exercised. Worse, the refusal class is one SDKs and hand-rolled submitters treat as retryable-or-terminal-IAM, so instead of one failed round trip the client spends its entire timeout budget retrying a request that will never be accepted, and a CI pipeline reports a hang rather than a diagnosable error.

Fix: CreateModelInvocationJob's handler and the model-resolution state it reads — `services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/create_model_invocation_job.rs` plus the foundation-model catalogue in `src/state.rs` that `names_a_model` consults: a foundation-model ARN for a model AWS's catalogue carries must resolve and the submission must be accepted with 200 + jobArn; and an identifier that truly resolves to nothing must be refused 400 ValidationException rather than 404 ResourceNotFoundException.

Traces: bedrock.create-model-invocation-job-malformed-s3-uri-rejected. Related open issues that do NOT cover this (none carries this check's current replay key): 20261024T025841Z-bedrock-control-plane-no-iam-authorization-gate-guardrail.md lists this check id, but its key for it is the validation-MESSAGE assertion `assert bad_message == expected_message`, which now passes — the check fails later and differently; 20261030T063647Z-bedrock-batch-job-creation-runs-its-pass-role.md is a WIRE issue whose keys are CreateModelInvocationJob|4xx->4xx for an INVALID model identifier and says nothing about a well-formed submission being refused; and 20261029T172312Z-bedrock-reopens-bedrock-getfoundationmodel-the-catalogue-does-not-resolve.md covers GetFoundationModel/provisioned-throughput catalogue misses, not CreateModelInvocationJob's own modelId resolution. The fixed issue 20261029T172312Z-bedrock-control-plane-applies-no-authorization-gate-an.md installed the pass-role gate for this operation; per its own Resolution that gate GRANTS a same-account role trusted for bedrock.amazonaws.com, which is the role this check passes, so it is not the refusal here.
