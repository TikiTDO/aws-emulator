# signer GetRevocationStatus refuses a well-formed profileVersionArn whose profile-name segment is shorter than 2 characters, so every revocation read on such an ARN is a 400 instead of a 200

> _Note: this issue was identified against the code base at commit `5b2a9eedb8fa287cac2318fd09ae07f52de03ab6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetRevocationStatus

## Description
Cause 1 of 1: GetRevocationStatus answers 400 ValidationException "Invalid profileVersionArn: <value>" for a syntactically well-formed signing-profile version ARN, because the ARN parser the handler gates on applies ProfileName's @length(2,64) rule to the name segment it reads out of the ARN. Every request whose profileVersionArn carries a one-character profile name (the behavioral corpus uses arn:aws:signer:<region>:<account>:/signing-profiles/n/<10-char version>) is refused before any revocation record is consulted, so 11 separate checks never reach the behavior they exercise.

AWS: HTTP 200 with {"revokedEntities": []}. Smithy (services/service-com-amazonaws-signer-wallabyservice/smithy-model/com-amazonaws-signer-wallabyservice.json, com.amazonaws.signer#GetRevocationStatus, GET /revocations, hostPrefix data-): profileVersionArn targets Arn, a string with @length(min 20, max 2048) and NO @pattern; jobArn is the same shape; the operation models ValidationException (client, httpError 400), AccessDeniedException (403), TooManyRequestsException (429), InternalServiceErrorException (500). The model does not constrain the ARN's internal segments at all, and the operation models no not-found: recorded behavior is that an ARN naming a profile version this endpoint holds nothing for is answered as an entity that is simply not revoked (empty revokedEntities), while a value that is not ARN-shaped at all is refused 400 ValidationException with message "Invalid profileVersionArn: <value>" — fixed text "Invalid profileVersionArn: " followed by the request's profileVersionArn query value, echoed as supplied. Both halves are recorded by signer.profile-version-arn-format-rejected, which asserts the valid-ARN positive control succeeds and only the non-ARN string of the same length is refused. Nothing in the model or the recording makes the ARN's name segment subject to ProfileName's 2-character minimum: that constraint belongs to the ProfileName MEMBER of the profile-management operations, not to a name read out of an Arn-typed value.

Emulator: HTTP 400 ValidationException, message "Invalid profileVersionArn: arn:aws:signer:us-west-2:111122223333:/signing-profiles/n/aaaaaaaaaa" (the version segment varies per check: aaaaaaaaaa, cccccccccc, hhhhhhhhhh, iiiiiiiiii, jjjjjjjjjj, 1111111111 — all 10 alphanumeric characters, i.e. valid). The status, the error class and the message TEMPLATE are right; what is wrong is that the gate fires for an ARN AWS accepts. ops/get_revocation_status.rs resolves the member through crate::state::profile_version_in_arn (src/state.rs:1164-1170) and refuses with crate::state::invalid_arn_message when it answers None; that parser requires is_profile_name(name) (src/state.rs:2097-2102), which enforces (2..=64).contains(&value.len()), so the name segment "n" fails and the whole ARN is declared malformed. is_profile_version (src/state.rs:2110-2112) accepts the 10-character versions, so the name length is the sole trigger.

Why: a client doing a revocation check on a profile version it was handed (by another account, another region, or any ARN whose name segment is one character) is told its request is invalid instead of being told whether the signature is revoked. The operation is a trust decision with no not-found channel, so the caller has no way to distinguish "this emulator will not parse my ARN" from "my ARN is wrong", and the refusal blocks every downstream behavior of the operation: certificateHashes validation, signatureTimestamp validation, platformId validation, authorization and read consistency are all unreachable while this gate fires, which is exactly what the 11 failing checks show (each fails on its first, positive-control call).

Fix: the profileVersionArn (and, symmetrically, the jobArn) shape gate of GetRevocationStatus in the signer crate — ops/get_revocation_status.rs must judge the ARN's SHAPE only (partition/service/region/account plus the /signing-profiles/<name>/<version> resource form), and the ARN parser in src/state.rs (profile_version_in_arn / profile_region_and_name_in_arn) must stop applying the ProfileName member's length floor to a name segment read out of an Arn-typed request value; keep the "Invalid profileVersionArn: <value>" wording for values that genuinely are not ARN-shaped. Any state lookup done with the parsed name must tolerate names the profile-management operations would not accept and answer "not revoked" rather than refuse.
