# CodeBuild/CodePipeline/ECR: a CloudFormation-deployed CI topology never yields a Succeeded pipeline execution, so the deployed service-role trust can never be exercised (both trust-policy checks burn the whole replay budget)

> _Note: this issue was identified against the code base at commit `5c0f2e9076960c0c5ec367c612fbea7052ab391b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartPipelineExecution

## Description
ONE net-new root cause, reported by the suite as unowned. Open issue 20261029T174654Z-codebuild-codepipeline-ecr-build-actions-are-never-executed.md lists these two check ids in its trace list, but the replay keys it carries for them (`_run_pipeline_with_retry#15|Timeout|time.sleep(15.0 * (attempt + 1))`) are no longer the keys these checks produce, so the suite does not report them as OWNED and they are not covered by it; the neighbouring issues 20261023T080113Z-codebuild-codepipeline-ecr-cloudformation-stack-reports-completion-but-provisions-no-codepipeline.md, 20261024T014332Z-codebuild-codepipeline-ecr-codepipeline-build-stages-fail-and-record-no-action.md and 20261022T172625Z-codebuild-codepipeline-ecr-ci-chain-pipeline-executions-never.md describe adjacent symptoms only. Filing it here so the surviving failure is not dropped.

Cause 1 of 1 — a CI topology provisioned by CloudFormation (versioned source bucket + artifact bucket + an IAM role trusting codebuild.amazonaws.com + an IAM role trusting codepipeline.amazonaws.com + an AWS::CodeBuild::Project with CODEPIPELINE source/artifacts + an AWS::CodePipeline::Pipeline with an S3 Source stage and a CodeBuild Build stage) never produces a pipeline execution that reaches the terminal status `Succeeded`, so the IAM trust the stack declares is never functionally exercised and both checks are killed at the 60 s replay cap with no verdict.

AWS: recorded behavior only for the end-to-end sequence. StartPipelineExecution returns `pipelineExecutionId` (Smithy codepipeline: StartPipelineExecution.output.pipelineExecutionId, pattern ^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$; modeled errors ConcurrentPipelineExecutionsLimitExceededException, ConflictException(409), PipelineNotFoundException, ValidationException). GetPipelineExecution (Smithy codepipeline: input pipelineName+pipelineExecutionId required; output pipelineExecution: PipelineExecution; errors PipelineExecutionNotFoundException, PipelineNotFoundException, ValidationException) then reports `pipelineExecution.status`, and in the recording that status advances from a non-terminal value to the terminal value `Succeeded` for this topology: the S3 Source action fetches the versioned source zip, the Build action runs the project's buildspec and the stage succeeds. Before that, CreateStack/DescribeStacks reaches `CREATE_COMPLETE` and the stack's Outputs carry `PipelineName` and `CodeBuildRoleArn`, and IAM GetRole returns the declared AssumeRolePolicyDocument (one Allow statement with Action sts:AssumeRole and Principal.Service codebuild.amazonaws.com, resp. codepipeline.amazonaws.com).

Emulator: the sequence never converges. Both checks end with the harness verdict `Check timed out after 60.0s` — they are still polling when the cap hits, having never obtained a terminal `Succeeded` status from GetPipelineExecution (the checks allow up to 3 StartPipelineExecution attempts with 15 s/30 s/45 s backoff and a 300 s per-execution poll budget, so nothing short of an immediate Succeeded can finish inside the cap). The replay key for these checks has moved relative to the key recorded in the open issue above, i.e. the point at which the flow stalls is no longer the one previously recorded; the suite therefore treats them as unowned. Hypothesis: the stall is the Build stage — the same emulator-authored refusal reported elsewhere in this chain (a Build action of provider CodeBuild resolved with errorDetails.code `ConfigurationError` and the self-describing message `this emulator does not run Build actions provided by CodeBuild, so the action cannot be performed`) makes every execution of this pipeline terminate non-Succeeded, so the retry loop consumes the whole budget; the alternative is that the stack itself never reaches a terminal DescribeStacks status for this template shape. Either way the emulator never serves a Succeeded execution for a CFN-provisioned pipeline.

Why: a client that provisions this standard CI topology by template cannot verify it end to end. Nothing it can observe distinguishes "the declared IAM trust is wrong" from "the emulator does not run the stage": GetPipelineExecution never leaves its non-terminal status, no Succeeded execution exists, and any test asserting the deployed role is usable hangs instead of failing with an AWS-shaped result. Negative permission tests built on the same topology also pass vacuously.

Fix: the CodePipeline execution engine's Build-action executor and its CodeBuild provider integration (it must actually invoke codebuild StartBuild under the pipeline role and drive the stage to Succeeded, and must never answer with an emulator self-description in errorDetails/externalExecutionSummary), together with the CloudFormation provisioners for AWS::CodeBuild::Project / AWS::CodePipeline::Pipeline / AWS::IAM::Role in this template shape and the stack's terminal-status reporting, so that DescribeStacks settles on CREATE_COMPLETE with the declared Outputs and the provisioned pipeline is executable.

Traces: codebuild__codepipeline__ecr.deploy-stack-codebuild-role-trust-policy-allows-codebuild-service, codebuild__codepipeline__ecr.deploy-stack-pipeline-role-trust-policy-allows-codepipeline-service.

## Evidence
Expected (AWS, from the checks' recording): CreateStack on the CI template settles at DescribeStacks StackStatus `CREATE_COMPLETE` with Outputs {PipelineName, CodeBuildRoleArn / PipelineRoleArn}; IAM GetRole on the declared role returns an AssumeRolePolicyDocument containing a statement {Effect: Allow, Action: sts:AssumeRole, Principal: {Service: codebuild.amazonaws.com}} (resp. codepipeline.amazonaws.com); StartPipelineExecution returns a uuid pipelineExecutionId and GetPipelineExecution(pipelineName, pipelineExecutionId).pipelineExecution.status subsequently reports the terminal value `Succeeded`.

Actual (emulator, this replay):
- [mismatch] codebuild__codepipeline__ecr.deploy-stack-codebuild-role-trust-policy-allows-codebuild-service — `Error: Check timed out after 60.0s`.
- [mismatch] codebuild__codepipeline__ecr.deploy-stack-pipeline-role-trust-policy-allows-codepipeline-service — `Error: Check timed out after 60.0s`.
Neither check reached its final assertion (`assert final_status == "Succeeded", f"pipeline execution ended in {final_status}: {detail}"`), so no terminal Succeeded execution was ever served; both were still inside the deploy/poll flow when the cap hit. The suite marked neither OWNED nor ALREADY FILED, i.e. the replay key differs from the one open issue 20261029T174654Z-codebuild-codepipeline-ecr-build-actions-are-never-executed.md records for these same check ids.

Note on wording that is part of the requirement: where the emulator answers a Build action at all in this chain it emits errorDetails.code `ConfigurationError` with the message `this emulator does not run Build actions provided by CodeBuild, so the action cannot be performed`. That whole string is emulator self-description and is not AWS text for any error class — AWS's Build-action failure reports errorDetails.code `JobFailed` with a message whose variable parts are the build id / project name taken from the request and state. Fixed text that must not be invented by the emulator; values (build id, project name, execution id, role ARN, stack name, timestamps) come from the request and the emulator's own state and are never part of the requirement.

## Steps to Reproduce
1. s3 CreateBucket a source bucket, PutBucketVersioning Status=Enabled, PutObject a zip containing one file (e.g. readme.txt) at key source.zip.
2. cloudformation CreateStack with Capabilities [CAPABILITY_IAM, CAPABILITY_NAMED_IAM] and a template declaring: AWS::S3::Bucket (ArtifactBucket); AWS::IAM::Role CodeBuildRole whose AssumeRolePolicyDocument allows sts:AssumeRole for Principal.Service codebuild.amazonaws.com (inline policy: logs:CreateLogGroup/CreateLogStream/PutLogEvents on *, s3:GetObject/GetObjectVersion/PutObject on the artifact and source buckets); AWS::CodeBuild::Project with Artifacts.Type=CODEPIPELINE, Source.Type=CODEPIPELINE and an inline buildspec writing output.txt, Environment LINUX_CONTAINER/BUILD_GENERAL1_SMALL/aws/codebuild/amazonlinux2-x86_64-standard:5.0, ServiceRole=!GetAtt CodeBuildRole.Arn; AWS::IAM::Role PipelineRole trusting codepipeline.amazonaws.com with s3:Get*/PutObject on the buckets and codebuild:StartBuild/BatchGetBuilds on the project ARN; AWS::CodePipeline::Pipeline with RoleArn=PipelineRole, ArtifactStore S3=ArtifactBucket, stage Source (Owner AWS, Provider S3, S3Bucket/S3ObjectKey parameters, PollForSourceChanges false, OutputArtifacts SourceOutput) and stage Build (Owner AWS, Provider CodeBuild, Configuration.ProjectName=!Ref CodeBuildProject, InputArtifacts SourceOutput); Outputs PipelineName and CodeBuildRoleArn (resp. PipelineRoleArn). Poll DescribeStacks until a terminal status.
3. iam GetRole on the role named by the stack output and confirm the AssumeRolePolicyDocument statement {Effect: Allow, Action: sts:AssumeRole, Principal: {Service: codebuild.amazonaws.com}} (resp. codepipeline.amazonaws.com) round-trips.
4. codepipeline StartPipelineExecution(name=<PipelineName output>), then poll GetPipelineExecution(pipelineName, pipelineExecutionId) until pipelineExecution.status is one of Succeeded/Failed/Superseded/Stopped/Cancelled.
Observed: step 4 never reports `Succeeded`, so the flow is still polling when the 60 s replay cap kills it. On AWS the execution reaches `Succeeded` and ListActionExecutions shows the Build action with an externalExecutionId. Also run ListActionExecutions(filter={pipelineExecutionId}) on any non-Succeeded execution to see the ConfigurationError/"this emulator does not run Build actions…" result quoted above.
