# apigatewaymanagementapi: 2 net-new causes — a @connections call on a DEPLOYED stage is now answered by closing the connection with no HTTP response (no 410 GoneException), and the deployed WEBSOCKET stage still mints no connection (13 checks)

> _Note: this issue was identified against the code base at commit `692bdbd743c675f7ea04b289b05ae1316dab417a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetConnection

## Description
TWO net-new root causes on the apigatewaymanagementapi service token, taken from the 15 failures in this replay that are marked neither ALREADY FILED nor OWNED. They are numbered below and each carries its own failing check ids; BOTH must be closed before this issue is submitted.

=== Cause 1 of 2: a @connections request addressed to a DEPLOYED stage of a WEBSOCKET API is answered by aborting the TCP/TLS connection with no HTTP response at all, instead of HTTP 410 GoneException for a well-formed but unknown ConnectionId ===
AWS: Smithy model com.amazonaws.apigatewaymanagementapi#ApiGatewayManagementApi (sdk_id ApiGatewayManagementApi, protocols [restJson1], authSchemes [sigv4], 3 operations). GetConnection GET /@connections/{ConnectionId} code 200 with output ConnectedAt (jsonName connectedAt, timestampFormat date-time), LastActiveAt (jsonName lastActiveAt, date-time) and Identity; PostToConnection POST /@connections/{ConnectionId} code 200 with Data @httpPayload blob @length{min 0, max 131072}; DeleteConnection DELETE /@connections/{ConnectionId} code 204. All three declare errors ForbiddenException (@httpError 403), GoneException (@httpError 410, memberless) and LimitExceededException (@httpError 429); PostToConnection additionally declares PayloadTooLargeException (@httpError 413). Recorded behavior: against a DEPLOYED stage of the API, a connection id that is well formed (the shape API Gateway mints — base64 of 11 bytes, e.g. a 16-character padded token) but owned by no live socket reaches the connection store and is refused HTTP 410 with error code GoneException and an EMPTY message (the recordings assert exactly ('GoneException', '') — the code is fixed text, the message is empty, nothing in it is derived from the request). Whatever the verdict, AWS always ANSWERS a @connections request with a complete HTTP response; it never drops the connection.
Emulator: the request produces no HTTP response whatsoever. botocore raises `ConnectionClosedError: Connection was closed before we received a valid response from endpoint URL: "https://<host>:<port>/<stage>/@connections/<connection-id>"` on GetConnection against the stage that was just created by create_api(ProtocolType=WEBSOCKET) + create_integration(MOCK) + create_route($connect) + create_deployment + create_stage('dev'). Host, port and the id are per-run values; the requirement is that an HTTP response arrives at all. Both affected checks die in their readiness probe (`_wait_management_ready`, which polls GetConnection with a well-formed unknown id until it answers GoneException), so neither reaches its graded assertions.
This is net-new and a change of failure mode: the open issue 20261109T160349Z-apigatewaymanagementapi-2-net-new-causes-a-connections-call.md reports the same no-response behavior only for an UNDEPLOYED stage name and carries only that check's replay key; the DEPLOYED stage used to ANSWER (incorrectly — see 20261104T221013Z-apigatewaymanagementapi-connections-splits-400-410-on-did-this.md, which records a 400 BadRequestException for a well-formed unknown id, and 20261029T214905Z-apigatewaymanagementapi-connections-error-layer-every-failure-answers-410.md, which records a 410 with a __type body). None of those issues covers these two checks; the replay reports no owner for them.
Two further requirements sit BEHIND this refusal and are currently unobservable, so they must be satisfied once a response is served again: (a) a MALFORMED connection id is refused HTTP 400 with error code BadRequestException and the message `Invalid connectionId: <the ConnectionId exactly as sent>` — 'Invalid connectionId: ' is fixed text, the suffix is the value taken verbatim from the request path — on GetConnection, PostToConnection and DeleteConnection alike, decided by the id's shape and before the connection store is consulted (a single character, non-base64 text, an unpadded token and a 200-character token are all malformed); and (b) PostToConnection enforces its 131072-byte Data ceiling BEFORE resolving the connection and before validating the id, answering a bare HTTP 413 with NO x-amzn-errortype header (botocore therefore surfaces the error Code as the string '413', never the modelled PayloadTooLargeException), while exactly 131072 bytes is accepted and falls through to the 410 GoneException.
Why: a client gets a transport-level reset in place of a modelled refusal. Every SDK classifies an aborted connection as retryable, so addressing a connection that has gone away — the single most common @connections outcome in real applications — becomes a retry storm and a hang instead of an immediate, catchable GoneException; application code that prunes stale connection ids on GoneException never runs, and nothing in the client can distinguish 'this connection is gone' from 'the emulator crashed'. Because the refusal arrives before any status line, the whole @connections surface is unusable even for negative paths.
Fix: the @connections data-plane front door / endpoint-and-stage resolution that sits in front of the three handlers, plus those handlers' error serialization — resolve {api-id, stage} from the request path, dispatch to the connection store, and always emit a complete HTTP response (410/GoneException with an empty message for a well-formed unknown id) rather than terminating the connection. The ordering of the connection-id shape check and the payload-size check belongs in PostToConnection's/GetConnection's/DeleteConnection's input validation, ahead of the store lookup.
Traces: apigatewaymanagementapi.agwmgmt-malformed-connection-id-rejected, apigatewaymanagementapi.agwmgmt-post-oversize-payload-rejected-before-lookup.

=== Cause 2 of 2: a deployed apigatewayv2 WEBSOCKET stage still never yields a usable WebSocket connection, so 13 more live-connection @connections checks reach no verdict at all ===
AWS: the RFC 6455 opening handshake is the execute-api data plane and is not a modelled operation, so this is recorded behavior only. Recorded: a GET on the deployed stage path carrying `Connection: Upgrade`, `Upgrade: websocket`, `Sec-WebSocket-Key: <base64 of 16 bytes>` and `Sec-WebSocket-Version: 13` is answered `HTTP/1.1 101 Switching Protocols` with `Upgrade: websocket`, `Connection: Upgrade` and `Sec-WebSocket-Accept: base64(SHA1(Sec-WebSocket-Key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))`. $connect then runs, the service mints the connection id, and that id is what the modelled @connections surface addresses: GetConnection returns ConnectedAt/LastActiveAt as ISO8601 date-times and a non-empty Identity.SourceIp (and Identity.UserAgent recorded verbatim from the handshake's User-Agent header, omitted when none was sent); PostToConnection delivers the exact bytes as a TEXT frame on that socket (zero-length Data delivers an empty frame; non-UTF8 bytes are sanitized per `bytes.decode("utf-8", errors="replace")` rather than relayed as a binary frame) and is scoped to the one target connection; DeleteConnection closes the socket with WebSocket code 1000, fires $disconnect, and makes every subsequent Get/PostTo/DeleteConnection on that id answer 410 GoneException; a live id from API A is 410 GoneException on API B's endpoint.
Emulator: no connection is ever established on a deployed WEBSOCKET stage, so every one of the 13 checks is killed by the harness — `Check timed out after 60.0s` — inside the step that opens the socket to the stage's wss URL and waits for the $connect record to learn the minted connection id. No 101 status line and no Sec-WebSocket-Accept is ever produced; the harness's handshake helper only retries a status line containing 500/502/503/504 and otherwise raises at once, so the full-budget hang means the upgrade is being answered with a 5xx (or not answered at all) rather than with a terminal 4xx. No connection id is minted, so none of the graded assertions is reached.
Why: with no connection id in existence the entire server-push surface is unobservable and unusable — delivery of text/binary/empty payloads, per-connection isolation, message ordering under sequential and concurrent PostToConnection, the 131072-byte boundary on a live socket, GetConnection's identity and timestamp reporting, DeleteConnection's forced close and its $disconnect fan-out, post-delete and cross-API GoneException. A developer pointing a WebSocket client at a stage the control plane reports as deployed cannot tell a missing data plane from a misconfigured stage, and no server-push application code can be exercised at all.
Fix: the execute-api data-plane front door / request router plus the apigatewayv2 WebSocket session layer — claim an upgrade request addressed to a deployed WEBSOCKET-protocol API's stage path, complete the handshake (101 + correct Sec-WebSocket-Accept) instead of falling through to a 5xx, mint a connection id, dispatch $connect/$disconnect/route selection, and register the connection in the store the three @connections handlers read. An upgrade that cannot be served must still be answered immediately with a terminal HTTP status rather than a retryable 5xx. This is a capability gap, not an error-shape bug.
