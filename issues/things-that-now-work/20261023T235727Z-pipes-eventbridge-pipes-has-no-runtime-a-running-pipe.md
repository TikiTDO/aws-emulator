# EventBridge Pipes has no runtime: a RUNNING pipe never polls its source or delivers to its target, bad sources/roles never fail, transitions never conflict, CFN pipes are never created and no pipe metrics are published (5 causes)

> _Note: this issue was identified against the code base at commit `cfd0674e2ddfe499cbab1f11b70f1bc18d331a71`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreatePipe

## Description
This bundle has 5 causes; all five must be closed before submitting. All five are grounded in failing checks of this run and all of them share one theme: the pipes emulator stores a pipe record and answers reads from it, but nothing ever *runs* a pipe.

Cause 1 of 5: a pipe in CurrentState RUNNING never polls its SQS source and never delivers anything to any target, so every end-to-end check hangs until the harness cap.
AWS: recorded behavior only for the data plane (the Smithy model describes only the control plane). Smithy (com.amazonaws.pipes): CreatePipe accepts SourceParameters -> PipeSourceParameters (for SQS, PipeSourceSqsQueueParameters with BatchSize @range 1..10000 and MaximumBatchingWindowInSeconds @range 0..300), FilterCriteria, Enrichment/EnrichmentParameters and TargetParameters (InputTemplate, SqsQueueParameters.MessageGroupId, EventBridge event-bus DetailType/Source, Step Functions target, ...); DescribePipe reports CurrentState from PipeState, whose values include RUNNING. The documented contract of EventBridge Pipes is that once a pipe is RUNNING the SERVICE polls the source with no client action, applies FilterCriteria, optionally invokes the enrichment, renders InputTemplate and invokes the target, deleting the source message only after a successful target invocation (and letting it reappear after the visibility timeout, or go to the source DLQ, when the target invocation is refused). The checks in Traces below each wait on exactly one of those observables.
Emulator: every such check reaches the harness cap ("Check timed out after 60.0s") while polling the target queue / event bus / state machine for the record the pipe should have moved; pipes.pipe-server-side-polling-without-client-action, which asserts only that the service polls at all, times out identically. The handler confirms why: services/service-com-amazonaws-pipes-pipes/src/ops/create_pipe.rs builds a crate::state::PipeRecord, inserts it into state.pipes and returns; the only asynchronous machinery in the crate is state.settle_due_transitions(), which flips CurrentState after a delay. No source poller, filter evaluator, enrichment invoker, input-template renderer or target dispatcher exists, so source messages are never received, never deleted, and nothing is ever sent to a target.
Why: a client that wires a queue, a stream or a FIFO queue through a pipe sees the pipe report RUNNING and then observes nothing: no record at the target, no message consumed at the source, no filtering, no enrichment, no batching-window latency, no redelivery and no DLQ redrive. Every integration test and every application that depends on a pipe moving data silently hangs or asserts on an empty target, and the pipe's own state says everything is healthy.
Fix: a pipes data-plane/dispatch engine in services/service-com-amazonaws-pipes-pipes (a per-pipe poller driven by the stored SourceParameters, plus filter, enrichment and target-invocation stages that call the sqs / events / sfn / lambda surfaces of the same emulator) and the state that tracks in-flight batches.

Cause 2 of 5: a pipe whose source does not exist, or whose execution role cannot be assumed or cannot read the source, settles in a healthy state with no StateReason instead of a terminal failure state.
AWS: Smithy: PipeState includes CREATE_FAILED, CREATE_ROLLBACK_FAILED, START_FAILED and UPDATE_FAILED, and DescribePipe returns StateReason (PipeStateReason, @length 0..512) alongside CurrentState — those members exist precisely because pipe creation/start validates the source and the role asynchronously and reports the failure as a terminal CurrentState plus a human-readable reason. CreatePipe is accepted synchronously (CurrentState CREATING) and the failure surfaces later; the recorded expectation is CREATE_FAILED (or CREATE_ROLLBACK_FAILED) with a non-empty StateReason that attributes the failure to role assumption / source access.
Emulator: a pipe created against a deleted source queue settles in STOPPED ("a pipe on a missing source queue settled in 'STOPPED', expected 'CREATE_FAILED'"); a pipe whose role trust policy names lambda.amazonaws.com instead of pipes.amazonaws.com never leaves the requested state, so the check polling for CREATE_FAILED times out at the harness cap; StartPipe on a pipe whose role has no source-read permission reports CurrentState RUNNING with StateReason None, and a second check reads back STOPPED where CREATE_FAILED was required. create_pipe.rs performs no source resolution and no role/trust check at all — it stores RoleArn and Source verbatim.
Why: the single most common misconfiguration in a pipe (a role that pipes cannot assume, or a role missing sqs:ReceiveMessage on the source) is reported as success. A client has no signal to act on: no terminal state, no StateReason, and — because of Cause 1 — no data movement either, so a permission bug is indistinguishable from an idle source.
Fix: asynchronous create/start validation in the pipes state machine (services/service-com-amazonaws-pipes-pipes: resolve Source and Target against the emulator's sqs/other surfaces, check the role's trust policy and the required source/target actions against iam), and set CurrentState to the modeled terminal failure value with a populated StateReason instead of settling into DesiredState.

Cause 3 of 5: StartPipe/StopPipe never refuse a conflicting or concurrent state transition — every caller wins.
AWS: Smithy: StartPipe and StopPipe both model ConflictException (HTTP 409) with required members message, resourceId and resourceType; ConflictException is documented as "An action you attempted resulted in an exception" and is the error AWS returns when the requested transition is not legal for the pipe's CurrentState (e.g. a StartPipe while the pipe is STARTING/RUNNING, or a StopPipe on an already STOPPED/STOPPING pipe), so exactly one of two simultaneous StartPipe calls on a STOPPED pipe succeeds and the loser gets 409 ConflictException.
Emulator: both concurrent StartPipe calls return success — "expected exactly one StartPipe success, got [('ok', None, None), ('ok', None, None)]", "expected exactly one winner, got ['ok', 'ok']", "expected exactly one success under the race, got [('ok', None), ('ok', None)]" — and a StartPipe/StopPipe issued mid-transition is accepted too ("expected at least one mid-transition StartPipe call to be rejected with ConflictException", same for StopPipe).
Why: a client cannot use ConflictException to serialize control-plane actions, and nothing tells it that a transition it requested was already in flight; two racing deploys both believe they drove the transition, and the 409-retry path that SDK users write is dead code.
Fix: the StartPipe and StopPipe handlers plus the pipe state machine in services/service-com-amazonaws-pipes-pipes — gate the transition on CurrentState under the state lock and return the modeled ConflictException (409) with resourceId = pipe name and resourceType = the pipe resource type for an illegal or already-in-flight transition.
Traces: pipes.concurrent-start-pipe-single-winner, pipes.concurrent-start-requests-single-transition, pipes.concurrent-start-stop-race-resolves-deterministically, pipes.start-running-pipe-conflict-rejected, pipes.stop-stopped-pipe-conflict-rejected.

Cause 4 of 5: a CloudFormation stack containing an AWS::Pipes::Pipe reaches CREATE_COMPLETE but no pipe exists, and a stack whose pipe role cannot read its source is not rolled back.
AWS: recorded behavior only (CloudFormation resource provider). A stack that reports CREATE_COMPLETE has created every declared resource, so pipes DescribePipe on the template's pipe must answer 200 with that pipe; Smithy (com.amazonaws.pipes#DescribePipe) models NotFoundException (404) only for an entity that does not exist. Why: every pipe deployed as infrastructure-as-code (CDK, SAM, plain CFN) appears to deploy and then does not exist, and a template with a broken pipe role is reported as a successful deployment. A client that reads the stack status as its gate proceeds against a resource that is absent.
Fix: the CloudFormation AWS::Pipes::Pipe resource provider — create/update/delete the pipe through the pipes state on stack events, propagate the pipe's terminal failure state into the resource's status, and roll the stack back when the pipe cannot be created.

AWS: recorded behavior only, and the grading check is explicitly an unblessed draft: it states as hypotheses (from the EventBridge Pipes monitoring documentation) that the namespace is AWS/EventBridge/Pipes with dimension PipeName, that counters such as TargetStageFailed carry Unit "None" rather than "Count", that delivery is best-effort (so it asserts only Sum >= 1 and strictly greater than the healthy twin), and that a healthy pipe publishes an explicit 0 series.
