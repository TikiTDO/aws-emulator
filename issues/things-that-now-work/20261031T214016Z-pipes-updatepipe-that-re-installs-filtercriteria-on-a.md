# pipes: UpdatePipe that re-installs FilterCriteria on a RUNNING pipe never converges — the pipe does not demonstrably apply the replaced pattern (tightened v2 then restored v1)

> _Note: this issue was identified against the code base at commit `8b6650a5c8878c43d4882ca4e4593dd0d1d3dff8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdatePipe

## Description
This issue has 1 cause; it must be closed before submitting.

Cause 1 of 1: UpdatePipe on a pipe whose CurrentState is RUNNING replaces the pipe's FilterCriteria, but the pipe never demonstrably moves onto the replaced pattern — the check that drives tighten-then-revert never reaches either of its two absence assertions, so the emulator cannot be shown to apply a filter re-installed on a live pipe, in either direction.

AWS: Smithy (com.amazonaws.pipes#UpdatePipe, PUT /v1/pipes/{Name}, 200; errors ConflictException 409, NotFoundException 404, ValidationException 400, ThrottlingException 429, InternalException 500). Its input member SourceParameters targets UpdatePipeSourceParameters, whose FilterCriteria member is documented as "The collection of event patterns used to filter events. To remove a filter, specify a FilterCriteria object with an empty array of Filter objects" (FilterCriteria.Filters is a FilterList with @length 0..5). The operation's own documentation states that the Amazon-Web-Services-service-specific objects inside SourceParameters are updated "atomically as one" and that existing values are overridden — so a SourceParameters block carrying a new FilterCriteria REPLACES the stored one rather than adding to it. UpdatePipe's output and DescribePipe both report CurrentState from PipeState (values include UPDATING and RUNNING), which is how a client observes the update landing. The data-plane consequence is recorded behavior only (the model describes the control plane): a RUNNING pipe polls its source with no client action and admits only records matching its CURRENT patterns, so after the update the newly admitted shape must start being delivered and the newly excluded shape must stop — and reverting the patterns must swap those two back, because the revert is a replacement and not an addition.

Emulator: the check never completes. Replay reports `Check timed out after 60.0s` for pipes.update-pipe-filter-criteria-takes-effect-on-a-running-pipe-and-reverts, with no frame captured, so neither of its two decisive assertions is ever evaluated: (a) after UpdatePipe installs the tightened pattern, that the shape only the OLD pattern admitted is no longer delivered while the twin shape admitted by BOTH patterns keeps arriving, and (b) after UpdatePipe restores the original pattern, that the previously withheld shape is delivered again and the shape only the tightened pattern admitted is now withheld. Every other observable this check needs on the way there is a pipes behaviour the suite exercises elsewhere, and UpdatePipe itself does store the replacement: services/service-com-amazonaws-pipes-pipes/src/ops/update_pipe.rs computes `updated_source_parameters(...)` (which sets `filter_criteria: update.filter_criteria.clone()`, i.e. the atomic override the model documents), writes `pipe.source_parameters`, and then starts a poller only "if the pipe has none" — an ALREADY-running poller is not restarted. Hypothesis (not confirmed by this replay, because no stage of the check was reached): the pipe's running poller does not converge onto the re-installed FilterCriteria promptly enough for a client to observe the swap, and/or the UPDATING->RUNNING settle plus the first post-update poll is slow enough that the newly admitted shape never arrives; services/service-com-amazonaws-pipes-pipes/src/state/data_plane.rs documents that configuration is read as "what the record says NOW", so the behaviour must be verified against a live update rather than assumed from that comment. Note also that this check's own protocol spends two unconditional idle-drain windows of at least 60 s each after each update before it asserts, so part of the elapsed time is the check's budget and not emulator latency — a fixer should first confirm, with the harness cap raised or by driving the sequence by hand, whether the swap is applied at all.

Why: a client that re-targets a live pipe by replacing its FilterCriteria (the normal way to change which records a pipe admits without tearing it down) has no way to tell whether the change took effect. The stored configuration reads back as the new pattern while the records that reach the target are not demonstrably governed by it, so a tightening that is supposed to stop a record class may keep delivering it, and a revert may either fail to bring the old class back or stop filtering altogether (the two failure modes the unreached assertions exist to separate). Filter changes are a security- and cost-relevant control, so "stored but not applied" is indistinguishable from "applied" to every client.

Fix: the UpdatePipe handler's hand-off to the data plane plus the poller's configuration re-read — services/service-com-amazonaws-pipes-pipes/src/ops/update_pipe.rs (the branch that starts a poller only when the pipe has none, and the UPDATING->RUNNING settle it leaves behind) and services/service-com-amazonaws-pipes-pipes/src/state/data_plane.rs (the filter stage must evaluate the FilterCriteria the pipe record holds at the moment of each poll, so an in-flight poller picks up a replaced pattern, and a replacement must not be merged with the pattern it replaced).
