# Kinesis Video Archived Media data plane: streams never resolve (all calls 404), GetClip range validation missing, two refusal messages reworded, and GetImages ignores an explicit IAM Deny (5 causes)

> _Note: this issue was identified against the code base at commit `221dd3602e5d0e66d71e70da1fb8509b07c948c5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetClip

## Description
Five distinct net-new root causes found by the behavioral suite against the kinesis-video-archived-media (KVAM) data plane. A fixer must close all 5 before submitting. Related open issues exist for the WIRE corpus and describe overlapping symptoms from a different corpus — 20261029T173921Z-kinesis-video-archived-media-reads-do-not-resolve.md and 20261029T173921Z-kinesis-video-archived-media-client-error-messages-are.md — neither owns any of the behavioral checks listed below, and causes 2 and 5 are not described in either.

Cause 1 of 5: KVAM stream resolution never consults Kinesis Video Streams state, so every stream-addressed read short-circuits to 404 ResourceNotFoundException instead of reaching the per-operation retention/fragment logic.
AWS: Smithy GetClip (POST /getClip) and GetHLSStreamingSessionURL (POST /getHLSStreamingSessionURL) each model NoDataRetentionException (errorKind client, httpError 400) and ResourceNotFoundException (errorKind client, httpError 404). A stream that EXISTS in the kinesisvideo control plane with DataRetentionInHours == 0 resolves successfully and is then refused by the retention gate: HTTP 400, code NoDataRetentionException, message 'The stream data retention is set to 0 hours.' — entirely fixed text, no variable part. The same stream, once retention is positive and no media has ever been ingested, is refused HTTP 404 ResourceNotFoundException with message 'No fragments found in the stream for the clip request.' (GetClip) / 'No fragments found in the stream for the streaming request.' (GetHLSStreamingSessionURL) — also entirely fixed text. UpdateDataRetention is a real state transition and the data plane must re-read retention per call, so decreasing retention back to 0 flips the refusal back to NoDataRetentionException.
Emulator: every one of these calls answers HTTP 404 with code ResourceNotFoundException and message 'No such stream: StreamName <streamName>' — fixed prefix 'No such stream: StreamName ' plus the StreamName copied from the request — for a stream the check just created through kinesisvideo CreateStream and waited to ACTIVE. The retention gate, the fragment-index lookup and the retention transition are never reached at all.
Why: a client that distinguishes 'stream exists but retains nothing' (fix retention, retry) from 'no media in the requested window yet' (keep polling) from 'stream absent' (create it) takes the wrong branch on every archived-media read, and sees a 404 for a stream it just created and observed ACTIVE; a client waiting on an UpdateDataRetention transition never observes it.
Fix: the KVAM stream-resolution step shared by the GetClip and GetHLSStreamingSessionURL handlers — resolve the stream against the shared Kinesis Video Streams registry before raising ResourceNotFoundException, then apply the retention gate from current stream state, then the fragment-index path with AWS's no-fragments wording.
Traces: kinesis-video-archived-media.data-retention-update-changes-error-class, kinesis-video-archived-media.get-clip-no-data-retention-rejected, kinesis-video-archived-media.get-hls-streaming-session-url-no-data-retention-rejected.

Cause 2 of 5: GetClip does not reject a reversed ClipTimestampRange.
AWS: Smithy GetClip input member ClipFragmentSelector is required and carries a TimestampRange; GetClip models InvalidArgumentException (errorKind client, httpError 400). A ClipTimestampRange whose StartTimestamp is AFTER its EndTimestamp is refused HTTP 400, code InvalidArgumentException, message 'StartTimestamp must be before EndTimestamp.' — entirely fixed text with no variable part; it is an input-validation refusal, independent of whether the stream holds any media.
Emulator: answers code ResourceNotFoundException (HTTP 404) for the reversed-range request, i.e. no range-ordering validation is performed at all on GetClip input; the request is instead refused by the stream-resolution defect of cause 1. Fixing cause 1 alone leaves this call wrongly accepted or refused for the wrong reason, so this ordering check is its own cause.
Why: a client that sent an inverted window gets a 'resource missing' signal instead of a 'bad argument' signal, so it provisions or polls instead of correcting the request; worse, once resolution is fixed the reversed range may be silently accepted and produce an empty/undefined clip.
Fix: GetClip's input validation — compare ClipFragmentSelector.TimestampRange.StartTimestamp against EndTimestamp and raise InvalidArgumentException with AWS's fixed sentence before any state lookup.
Traces: kinesis-video-archived-media.get-clip-reversed-timestamp-range-rejected.

Cause 3 of 5: GetMediaForFragmentList reports a list-member constraint violation per element instead of per member, and echoes the rejected value.
AWS: Smithy GetMediaForFragmentList input member Fragments is required, targets FragmentNumberList with @length min 1 max 1000, whose member FragmentNumberString has @length min 1 max 128 and @pattern ^[0-9]+$. A non-numeric fragment number is refused HTTP 400 ValidationException whose message aggregates the member's whole constraint set and does NOT echo the offending value or its index: '<n> validation error detected: Value at \'fragments\' failed to satisfy constraint: Member must satisfy constraint: [Member must have length less than or equal to 128, Member must have length greater than or equal to 1, Member must satisfy regular expression pattern: ^[0-9]+$]'. Fixed text apart from the leading error count and the member path 'fragments', which is the request member's wire name.
Emulator: right status and right code, but message '1 validation error detected: Value \'not-a-fragment-number\' at \'fragments.1.member\' failed to satisfy constraint: Member must satisfy regular expression pattern: ^[0-9]+$' — it echoes the rejected value, addresses an indexed element path and lists only the single constraint that failed. ('not-a-fragment-number' is this check's request value, not part of the requirement; the bracketed constraint list and the 'fragments' member path are.)
Why: clients and test suites matching AWS's constraint sentence do not match, and the echoed value leaks request content into a message AWS keeps value-free.
Fix: GetMediaForFragmentList's input validation / constraint-message serializer — collapse list-member constraint failures onto the member path and emit the full bracketed constraint set without the value or index.
Traces: kinesis-video-archived-media.get-media-for-fragment-list-malformed-fragment-number-rejected.

Cause 4 of 5: ListFragments' stream-addressing refusal message is emulator-authored.
AWS: Smithy ListFragments takes StreamName and StreamARN, both optional, and exactly one must be supplied; ListFragments models InvalidArgumentException (errorKind client, httpError 400). Supplying both — or neither — is refused HTTP 400 InvalidArgumentException with message 'One of StreamName or StreamARN must be provided, but not both.', entirely fixed text with no variable part.
Emulator: correct status and correct code, message 'StreamName and StreamARN are mutually exclusive: specify exactly one'.
Why: the text is not AWS's wording, so clients and operators keying on or logging the message see something no AWS region produces, and it fails to state the 'neither supplied' half of the rule.
Fix: ListFragments' input validation — emit AWS's fixed addressing sentence for both the both-supplied and neither-supplied cases.
Traces: kinesis-video-archived-media.list-fragments-stream-identifier-mutual-exclusivity-rejected.

Cause 5 of 5: GetImages ignores an explicit IAM Deny — the call is never refused with AccessDeniedException.
AWS: Smithy GetImages (POST /getImages) models NotAuthorizedException (errorKind client, httpError 401) and the KVAM data plane is authorized against the caller's IAM policy before the operation body runs. An IAM user whose inline policy carries an explicit Deny on kinesisvideo:GetImages for one stream's ARN is refused with code AccessDeniedException and message 'User: arn:aws:iam::<account>:user/<userName> is not authorized to perform: kinesisvideo:GetImages on resource: <streamName>' — fixed text 'User: ' / ' is not authorized to perform: ' / ' on resource: ' with the caller's user ARN (account id and user name from the signing identity) and the action and resource from the request. The deny is scoped: the SAME identity's ListFragments (not denied) still succeeds 200 with an empty Fragments list, and the account's own credentials still reach GetImages' own refusal path.
Emulator: GetImages never returns AccessDeniedException for the explicitly-denied identity — the check polls it for 60s and the denial code never appears, so the check fails with 'Check timed out after 60.0s'. The data-plane call is not authorization-checked at all; it answers whatever the operation path answers regardless of the policy. (GetImages being an unimplemented scaffold stub is filed separately; the authorization gate is a distinct defect, because it must refuse the denied identity BEFORE the operation body regardless of that operation's implementation status.)
Why: this is an overly-permissive failure — a caller an IAM policy explicitly denies is not refused, so emulated IAM policy tests pass against a configuration real AWS rejects, and callers never see the 'fix the policy' signal.
Fix: the KVAM data-plane request pipeline's authorization step for GetImages (and the other stream-addressed reads) — evaluate the signing identity's IAM policy against kinesisvideo:<action> and the stream ARN and raise AccessDeniedException with AWS's wording before dispatching the operation.
Traces: kinesis-video-archived-media.get-images-not-authorized-without-permission.
