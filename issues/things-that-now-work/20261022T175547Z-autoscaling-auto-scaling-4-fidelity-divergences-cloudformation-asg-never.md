# Auto Scaling: 4 fidelity divergences — CloudFormation ASG never provisioned into Auto Scaling, DescribeMetricCollectionTypes catalog short 5 metrics, 'elasticloadbalancing' claimed by two services, ASG SNS notifications never delivered

> _Note: this issue was identified against the code base at commit `242e2a822ca6eb3fec2aad3ba89160f0a6f40669`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

DescribeAutoScalingGroups

## Description
FOUR distinct net-new root causes on Auto Scaling paths that the emulator answers (it is up and serving), each grounded in a failing behavioral check. A fixer must close ALL FOUR before submitting. None of these failures was marked ALREADY FILED or OWNED by the replay report. Open issues that do NOT cover them: 20261022T112459Z-autoscaling-group-round-trip-create-skips-min-max.md (CreateAutoScalingGroup validation/describe defaults) and 20261022T093447Z-fis-4-fidelity-divergences-cloudformation-aws-fis-experimenttemplate.md (same CloudFormation-does-not-provision PATTERN, but for AWS::FIS::ExperimentTemplate and keyed to fis checks only).

Cause 1 of 4: a CloudFormation/CDK-deployed AWS::AutoScaling::AutoScalingGroup is never created in the Auto Scaling service, and the stack publishes a fabricated CloudFormation physical id instead of the group name.
AWS: CloudFormation provisions AWS::AutoScaling::AutoScalingGroup by calling autoscaling CreateAutoScalingGroup; the resource's physical id — the value of !Ref, which both checks read back from a stack Output — is the Auto Scaling group NAME, and autoscaling DescribeAutoScalingGroups(AutoScalingGroupNames=[that name]) then returns exactly one group carrying the declared MinSize/MaxSize/launch template (Smithy: DescribeAutoScalingGroups input AutoScalingGroupNamesType, output AutoScalingGroupsType, errors InvalidNextToken/ResourceContentionFault; a name that does not exist is simply absent from the answer, not an error). Recorded behavior only for the id text; the requirement is that the id a CREATE_COMPLETE stack publishes for that resource resolves in Auto Scaling.
Emulator: the stack reaches CREATE_COMPLETE and the output is present, but its value is a CloudFormation-fabricated '<stackName>-<logicalId>-<hex>' name (observed 'sim2real-xsvc-cdkasg-f474867e4d62-AsgASGD1D7B4E2-7F5DC5C28138' and 'sim2real-asgssh-e2e-b50975f7e71f-AutoScalingGroup-3796E99B23E3') and DescribeAutoScalingGroups for it returns 0 groups — no group exists in autoscaling state at all; the resource is accounted for in the stack only.
Why: the stack reports success while nothing was provisioned, so every deploy-then-use workflow breaks immediately after CREATE_COMPLETE — the client cannot scale, describe, tag or delete the group it just deployed, and infrastructure-as-code tests (CDK L2 ASG, rolling updates, drift) pass vacuously against a stack that created no Auto Scaling resource.
Fix: the CloudFormation resource provider for AWS::AutoScaling::AutoScalingGroup — create the group through the autoscaling CreateAutoScalingGroup path at stack-create time, use the group name as the resource's physical id (hence the !Ref/GetAtt value), and delete it on stack delete.

AWS: DescribeMetricCollectionTypes returns the fixed, account-independent catalog of group metrics plus the single granularity '1Minute'. The current catalog has 25 entries: the 20 the emulator returns PLUS GroupTerminatingRetainedInstances, GroupTerminatingRetainedCapacity, WarmPoolMinSize, WarmPoolPendingRetainedCapacity and WarmPoolTerminatingRetainedCapacity (recorded behavior only — the on-disk Smithy model's EnableMetricsCollectionQuery$Metrics documentation still enumerates only the legacy 20, so the model is behind the service here; the recording is the requirement, and the operation has no error path for this).

Cause 3 of 4: two emulated services both claim the 'elasticloadbalancing' endpoint prefix, so every ELB/ELBv2 request in a mixed-service workflow is rejected — and rejected with a JSON body to a query-protocol client.
AWS: elasticloadbalancing (classic, Query 2012-06-01) and elasticloadbalancing v2 (Query 2015-12-01) share the endpoint prefix 'elasticloadbalancing' and are disambiguated by the request's Version/Action, so an elbv2 CreateTargetGroup/DescribeTargetHealth call returns its normal 200 XML envelope. On any error these services answer with an XML ErrorResponse document, which is what the client's Query parser expects.
Emulator: the request is refused with the body {"__type":"AmbiguousService","message":"2 emulated services all claim requests for 'elasticloadbalancing': elasticloadbalancing, elasticloadbalancing; the request is rejected rather than served by an arbitrary one"} — a JSON error for a Query-protocol client, which cannot parse it (botocore raises ResponseParserError: 'invalid XML received'), and 'AmbiguousService' is not a modeled error code of either service.
Why: no client can use the load-balancing APIs through the emulator when both crates are registered: the failure is unrecoverable (not even a retry-classifiable modeled error), it hides itself as a parser crash rather than an API error, and it takes down every cross-service workflow (ASG/ECS + ALB) that touches a target group.
Fix: request routing / service registration — key the two load-balancing crates by their distinct wire identity (protocol Version plus Action) instead of the shared endpoint prefix so a request resolves to exactly one service; and whatever the dispatcher cannot resolve must be serialized in the protocol of the addressed service (XML ErrorResponse for awsQuery), never as a JSON __type body.

Cause 4 of 4: Auto Scaling never publishes its SNS notifications, so a configured notification target receives nothing.
AWS: PutNotificationConfiguration (Smithy: PutNotificationConfigurationType, errors LimitExceededFault/ResourceContentionFault/ServiceLinkedRoleFailure) makes Auto Scaling publish an 'autoscaling:TEST_NOTIFICATION' message to the configured topic immediately, and thereafter publish 'autoscaling:EC2_INSTANCE_LAUNCH'/'autoscaling:EC2_INSTANCE_TERMINATE' messages naming the exact instance the group moved, with an ActivityId that appears in the group's scaling history; a topic nobody configured receives nothing (recorded behavior only for the message body — the requirement is that a message with the configured Event type and the moved instance id reaches a subscriber of the configured topic and only that topic).
Emulator: neither check ever completes — both are reported as 'Check timed out after 60.0s'. Both prove their SNS->SQS pipes live with a direct canary publish BEFORE asserting anything, so SNS and SQS deliver; the only unbounded waits left are the polls for the TEST_NOTIFICATION and for the launch/terminate notifications. Hypothesis: the autoscaling notification configuration is stored but never drives a Publish, so the polls cannot terminate.
Why: notification-driven automation (an operator queue, a Lambda reacting to launches, a scale-event audit trail) sees no traffic at all against the emulator, so its event handling is never exercised and an eventing test passes vacuously.
Fix: the PutNotificationConfiguration handler plus the group's scaling-activity path in the autoscaling crate — publish a TEST_NOTIFICATION to the configured topic when a configuration is created, and publish EC2_INSTANCE_LAUNCH/EC2_INSTANCE_TERMINATE (naming the instance id and the activity id) through the emulated SNS publish path as instances enter and leave the group.
