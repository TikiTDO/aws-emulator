# lambda__mq: a CloudFormation stack declaring AWS::AmazonMQ::Broker with a Lambda consumer and a RabbitMQ event source mapping never reaches CREATE_COMPLETE — it rolls back (1 cause)

> _Note: this issue was identified against the code base at commit `8323f4d349418e3a01a6cea3a48f7209706d6844`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
One net-new root cause. A fixer must close it before submitting.

=== Cause 1 of 1: provisioning the RabbitMQ broker estate fails, so the stack transitions to ROLLBACK_IN_PROGRESS instead of CREATE_COMPLETE ===
Failing check: lambda__mq.e2e-rabbitmq-esm-absent-queue-delivers-nothing-lifecycle

AWS: CreateStack on this template provisions five resources and the stack reaches CREATE_COMPLETE with every one of them CREATE_COMPLETE — BrokerSecret (AWS::SecretsManager::Secret, GenerateSecretString minting the `password` key), RabbitMqBroker (AWS::AmazonMQ::Broker, EngineType RABBITMQ / EngineVersion 3.13 / HostInstanceType mq.m5.large / DeploymentMode SINGLE_INSTANCE / PubliclyAccessible true, whose Users[0].Password is the dynamic reference `{{resolve:secretsmanager:${BrokerSecret}:SecretString:password}}`, Logs.General true), ConsumerRole (AWS::IAM::Role, created under CAPABILITY_NAMED_IAM), RabbitMqConsumer (AWS::Lambda::Function, nodejs20.x, inline Code.ZipFile) and RabbitMQEventSource (AWS::Lambda::EventSourceMapping, DependsOn the broker and the role, EventSourceArn = Fn::GetAtt RabbitMqBroker.Arn, Queues=['testQueue'], SourceAccessConfigurations BASIC_AUTH -> the secret and VIRTUAL_HOST -> '/', BatchSize 1). The stack then exports Outputs BrokerArn/BrokerId/BrokerName/SecretArn/FunctionName/FunctionArn/EventSourceMappingId, and the EventSourceMapping's PhysicalResourceId is the mapping UUID the EventSourceMappingId output reports. Notably AWS creates this estate even though the broker has no `testQueue` declared on it — the mapping is created and stays Enabled while recording a connect failure; nothing about the absent queue makes CREATE fail. Recorded behavior only for the status sequence (the Smithy model does not describe resource providers): the measured transition is CREATE_IN_PROGRESS -> CREATE_COMPLETE, with the broker the long pole at roughly 556s.
Emulator: CreateStack is ACCEPTED (no ValidationError, so the resource types are recognized), but provisioning fails and the stack is rolled back: DescribeStacks reports StackStatus `ROLLBACK_IN_PROGRESS`. Replay: `AssertionError: [phase 1/4 deploy] stack sim2real-refmq-<id> reached 'ROLLBACK_IN_PROGRESS', not CREATE_COMPLETE -- read its stack events for the resource that failed`. The check dies in its first phase, so nothing downstream is reachable: no Outputs, no BrokerId, and therefore none of mq:DescribeBroker, lambda:ListEventSourceMappings, the mapping's LastProcessingResult, or the queue-declaration positive control. Hypothesis (neither modelled nor recorded — the replay reports only the stack status): the failure is in the AmazonMQ broker resource provider and/or the `{{resolve:secretsmanager:...:SecretString:password}}` dynamic reference it depends on, since those are the only parts of this estate not already exercised by passing checks; the stack events for the run name the exact resource.
Why: every AmazonMQ-backed architecture is undeployable, and it fails in the most expensive way — the create is accepted, a rollback is started, and the caller must read stack events to learn anything. A client validating a RabbitMQ consumer against the emulator cannot get past deployment, so the entire Lambda-on-RabbitMQ event-source surface (mapping state, LastProcessingResult, SourceAccessConfigurations, delivery once the queue exists) is unreachable even though those operations may themselves be implemented.
Fix: the CloudFormation resource provider for AWS::AmazonMQ::Broker (it must create the broker in the mq service state, drive it to RUNNING and answer Ref with the BrokerId and Fn::GetAtt Arn), together with the template dynamic-reference resolver for `{{resolve:secretsmanager:<secret>:SecretString:<key>}}` used in Users[].Password; the provisioning engine must then let the stack reach CREATE_COMPLETE with all five resources CREATE_COMPLETE and populate the declared Outputs. Whatever resource the stack events blame must also report a real failure reason rather than only a stack-level rollback.
Related but not covering: the open issue 20261025T015306Z-cloudformation-cannot-deploy-large-parts-of-the-resource.md enumerates unrecognized/never-provisioned resource types (Hooks, AWS::IoT::Authorizer, DynamoDB, Glue, Logs) and does not mention AWS::AmazonMQ::Broker, the secretsmanager dynamic reference, or this check id; its symptom is also different (a 400 ValidationError at CreateStack, not an accepted create that rolls back).

Traces: lambda__mq.e2e-rabbitmq-esm-absent-queue-delivers-nothing-lifecycle (Cause 1).
