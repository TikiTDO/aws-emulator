# GetEffectiveRecommendationPreferences omits enhancedInfrastructureMetrics instead of reporting the effective default Inactive

> _Note: this issue was identified against the code base at commit `142ab0a7d17cfa52d1be6cb25774352167d2b4a7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetEffectiveRecommendationPreferences

## Description
ONE cause, on compute-optimizer.

Cause 1 of 1: GetEffectiveRecommendationPreferences leaves `enhancedInfrastructureMetrics` out of the response body entirely when no recommendation-preference record sets it, instead of reporting the effective value, which is the documented default `Inactive` when neither the resource, the account nor the organization has set the preference. Failing check: compute-optimizer.effective-recommendation-preferences-for-real-ec2-instance.

  AWS: Smithy (services/service-com-amazonaws-computeoptimizer-computeoptimizerservice/smithy-model/com-amazonaws-computeoptimizer-computeoptimizerservice.json): GetEffectiveRecommendationPreferences input = {resourceArn (ResourceArn, REQUIRED)}; output = {enhancedInfrastructureMetrics (EnhancedInfrastructureMetrics enum = Active|Inactive), externalMetricsPreference, lookBackPeriod (LookBackPeriodPreference = DAYS_14|DAYS_32|DAYS_93), utilizationPreferences, preferredResources}; errors = [AccessDeniedException 403, InternalServerException 500, InvalidParameterValueException 400, MissingAuthenticationToken 403, OptInRequiredException 403, ResourceNotFoundException 404, ServiceUnavailableException 503, ThrottlingException 429]. The operation is documented as reporting the preferences that are IN EFFECT for the resource, considering all applicable preferences set at the resource, account and organization level, and `enhancedInfrastructureMetrics` documents both of its states as an answer: "A status of Active confirms that the preference is applied in the latest recommendation refresh, and a status of Inactive confirms that it's not yet applied to recommendations." Recorded behavior for an EC2 instance in an opted-in account with no resource-level override: HTTP 200 whose body carries enhancedInfrastructureMetrics — the value of the account-scope preference on record, or `Inactive` when no record sets it — alongside lookBackPeriod (the account-scope value, or `DAYS_14` when none is on record). The member is an effective-state report, not an echo of what was written, so it is present whether or not a preference exists.
  Emulator: HTTP 200, but the body has no `enhancedInfrastructureMetrics` key at all for a resource with no preference record, so the client sees the member as absent. botocore surfaces this as KeyError: 'enhancedInfrastructureMetrics' when the check reads resp["enhancedInfrastructureMetrics"]. The rest of the body is served (lookBackPeriod, utilizationPreferences, preferredResources are all emitted with their defaults), so only this member is dropped. The omission is by construction: crate::state::EffectivePreferences.enhanced_infrastructure_metrics is an Option<String> documented "reported only where a record sets it", and the handler assigns it straight through, unlike look_back_period/utilization_preferences/preferred_resources which are wrapped in Some(..) with a resolved default.
  Why: a client reading the effective enhanced-infrastructure-metrics state — a console preference page, a drift/compliance check, or any code that asserts the preference is NOT active before enabling it — gets a missing member rather than the documented `Inactive`. Strongly-typed SDKs read it as null/unset and cannot distinguish "preference off" from "service did not answer"; dynamic clients (botocore, boto3) raise KeyError and the call site fails outright. The member being absent exactly in the no-preference case means the common path (a fresh account that has never written a preference) is the broken one, and code that branches on Active vs Inactive never takes its Inactive branch. The same Option is threaded into the EffectiveRecommendationPreferences block that the recommendation readers embed (crate::state::EffectivePreferences::to_wire, and the RDS recommendation path), so the same member disappears from those recommendations' effectiveRecommendationPreferences for an account with no preference on record.
  Fix: the preference resolution in the compute-optimizer service crate's state (the EffectivePreferences resolution that GetEffectiveRecommendationPreferences and the recommendation readers share) plus the GetEffectiveRecommendationPreferences handler — resolve enhancedInfrastructureMetrics to the most specific scope that sets it and to the service's documented default `Inactive` when none does, and emit it unconditionally, the way lookBackPeriod already defaults to DAYS_14. It must not become an echo of a stored record: when an account-scope record sets the preference, the effective report must be that record's value.

Code: services/service-com-amazonaws-computeoptimizer-computeoptimizerservice/src/ops/get_effective_recommendation_preferences.rs:278-293 (enhanced_infrastructure_metrics passed through un-defaulted while look_back_period is Some(..)); services/service-com-amazonaws-computeoptimizer-computeoptimizerservice/src/state.rs:2186-2196 (EffectivePreferences.enhanced_infrastructure_metrics: Option<String>, "reported only where a record sets it") and src/state.rs:2232-2240 (same Option re-exported into EffectiveRecommendationPreferences).
