# cloudwatch__s3: S3 request-metrics configurations publish no AWS/S3 datapoints, and DescribeAlarmHistory's ConfigurationUpdate summaries are not AWS's text (2 causes)

> _Note: this issue was identified against the code base at commit `cfbb9a1e24eec7d8c98af7d6e9e62a0e8013f018`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetMetricStatistics

## Description
Two net-new root causes in the cloudwatch__s3 pair. Both were reached after the control-plane calls the checks make (CreateBucket, PutBucketTagging, PutBucketMetricsConfiguration, GetBucketMetricsConfiguration, PutMetricAlarm) all succeeded, so this is not a bootstrap gap.

Cause 1 of 2 — a bucket's metrics configuration never produces AWS/S3 request metrics in CloudWatch.
AWS: recorded behavior only (neither the CloudWatch nor the S3 Smithy model describes metric emission; CloudWatch's model only gives the read surface: ListMetrics(Namespace @length 1..255, Dimensions @length 0..10) and GetMetricStatistics(Namespace/MetricName/StartTime/EndTime/Period required, Dimensions @length 0..30) -> Datapoints). The recording for `s3-request-metrics-filter-partitions-traffic-into-cloudwatch` was blessed against real AWS (PASS in 606s, us-west-2): after PutBucketMetricsConfiguration with Filter.Prefix, real S3 data-plane traffic under that prefix is accounted into the AWS/S3 namespace under the dimension pair [BucketName, FilterId] (FilterId value == the configuration's Id), those series are readable with GetMetricStatistics and are separately indexed by ListMetrics, per-verb (GetRequests Unit=Count, BytesDownloaded Unit=Bytes, 4xxErrors, AllRequests), and an ACTIVE filter publishes a zero-valued 4xxErrors datapoint while a filter with no traffic at all publishes none.
Emulator: no AWS/S3 datapoint is ever produced for any filter. Both checks poll with `_poll_until(..., interval_s=60.0)` whose predicate is evaluated IMMEDIATELY on entry and then once per pass — a target that publishes request metrics promptly (an emulator has no 15-minute enablement lag) satisfies it on the first pass — yet GetMetricStatistics returns no datapoints for the busy or the quiet FilterId and ListMetrics reports no AWS/S3 metric dimensioned on the bucket, so the poll never becomes ready and the check is killed at the harness's 60s cap ('Error: Check timed out after 60.0s').
Why: a client that enables request metrics to partition traffic per prefix/tag, or that alarms or dashboards on AWS/S3 GetRequests/4xxErrors/BytesDownloaded, sees permanently empty series; code that waits for its own FilterId to appear in ListMetrics before proceeding blocks forever, and nothing distinguishes 'no traffic' from 'metrics not implemented'.
Fix: the S3 request path's metrics-configuration accounting must publish into the CloudWatch metric store (services/service-com-amazonaws-s3-amazons3 request handling + the AWS/S3 namespace writer), and those series must be registered in CloudWatch's metric-discovery index served by ListMetrics (services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801). Caveat for the fixer: of the two checks here, `obs-s3-1-request-metrics-filter-counts-each-verb-exactly` additionally opens a measured window 120s after its barrier stops and `s3-request-metrics-filter-partitions-traffic-into-cloudwatch` declares timeout_s=1500, so after the fix the first will still exceed a 60s cap; `s3-request-metrics-filter-partitions-traffic-into-cloudwatch` is the one that can complete quickly once the first poll pass is satisfiable.
Traces: cloudwatch__s3.s3-request-metrics-filter-partitions-traffic-into-cloudwatch, cloudwatch__s3.obs-s3-1-request-metrics-filter-counts-each-verb-exactly.

Cause 2 of 2 — DescribeAlarmHistory ConfigurationUpdate items carry summaries that are not AWS's and omit the alarm name.
AWS: Smithy models AlarmHistoryItem.HistorySummary only as 'A summary of the alarm history, in text format' (@length 1..255) with HistoryItemType in {ConfigurationUpdate, StateUpdate, Action, ...}, so the text is recorded behavior; the recording shows that a PutMetricAlarm that creates an alarm records the summary `Alarm "<AlarmName>" created` and a PutMetricAlarm that re-puts an existing alarm records `Alarm "<AlarmName>" updated` — i.e. the summary interpolates the request's own AlarmName in double quotes. That interpolation rule, not one recording's literal name, is the requirement.
Emulator: the two ConfigurationUpdate items exist and the counts are right, but their summaries are `Alarm created` and `Alarm updated from configuration` — the alarm name is absent and the update wording differs. Replay: AssertionError: the history must hold one 'created' and one 'updated' item; got ['Alarm updated from configuration', 'Alarm created'].
Why: DescribeAlarmHistory is the audit view clients use to attribute a change to an alarm; when several alarms are returned in one history page (DescribeAlarmHistory can be called without AlarmName) a summary that never names the alarm cannot be attributed at all, and tooling that matches AWS's documented wording to classify create-vs-update misclassifies every re-put.
Fix: the alarm-history record writer behind PutMetricAlarm / DescribeAlarmHistory in the CloudWatch crate (services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801) must build HistorySummary by interpolating the alarm's name, using AWS's created/updated wording.
Traces: cloudwatch__s3.s3-tagfilter-alarm-reput-with-another-filter-id-moves-the-alarm.
