# outposts catalog reads publish a synthesized hardware catalog instead of the catalog AWS serves

> _Note: this issue was identified against the code base at commit `8f194cc1fc794f910c53fc884e414c1833919c6c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListCatalogItems

## Description
The two READ-ONLY reference catalogs this service publishes - the orderable hardware configurations (ListCatalogItems, GET /catalog/items) and the orderable instance types (ListOrderableInstanceTypes, GET /instanceTypes) - are served from a dataset the emulator invented for itself rather than the catalog AWS answers with. Membership, ordering and the per-item hardware attributes all diverge, so every index of a recorded catalog page differs, and a filtered read reports an item the recorded AWS page does not contain at all. This is ONE fault (the seeded catalog data) with THREE causes below.

This is distinct from the two open outposts wire issues: 20261029T191039Z-outposts-success-responses-omit-server-set-fields-and.md (server-set fields missing on Create*/Update*/TagResource) and 20261029T191039Z-outposts-lifecycle-and-precondition-gates-diverge-across-capacity.md (precondition/lifecycle gates). Neither one touches the published catalogs, and neither carries the replay keys below.

=== Cause 1 of 3: ListCatalogItems publishes a different set of catalog items (fixture outposts-catalog-list-catalog-items, step task#1) ===
AWS: recorded behavior only - the Smithy model describes ListCatalogItems as "Lists the items in the catalog" and types CatalogItems as CatalogItemListDefinition with no enumerated contents (Smithy: ListCatalogItems -> ListCatalogItemsOutput$CatalogItems; http GET /catalog/items, success 200), so the catalog's contents are reference data the recording is the only authority for. The recorded unfiltered first page is 200 with 37 CatalogItems entries, each a fixed AWS catalog SKU with its own hardware figures - e.g. the first entry is CatalogItemId OR-FWTFFXJ, ItemClass RACK, Dimensions OUTPOST_RACK, PowerKva 6.39, WeightLbs 1328, RackScalingType MULTI_RACK, SupportedUplinkGbps [10,40,100], SupportedStorage [EBS,S3], EC2Capacities a single entry {Family c5, MaxSize 24xlarge, Quantity 1}; the second is OR-G4Q39QN with PowerKva 13.3, WeightLbs 1432, SupportedStorage [EBS] and two GENERATION_2 EC2Capacities (m7i/48xlarge and r7i/48xlarge).
Emulator: answers 200 but with its own catalog. Every one of the 37 recorded entries is reported missing and the emulator's own entries appear instead: at index 0 it serves CatalogItemId OR-7Q7BLB6 with PowerKva 15.0, WeightLbs 1800 and eight EC2Capacities each of Quantity 15 (c5, c5d, g4dn, i3en, m5, m5d, r5, r5d at 24xlarge/16xlarge). The dataset is a hand-assigned table of 8 CatalogConfiguration rows whose CatalogItemId is derived by hashing the row (sku_seed/sku_code), and the file's own comment states "WHICH configurations are offered ... is this emulator's own catalog assignment" - so neither the SKU ids, the count, the power/weight figures nor the per-family capacity quantities can match AWS.
Why: a client cannot use this catalog. CatalogItemId values are stable AWS reference identifiers (they are not per-run generated), so a caller that lists the catalog and then orders - CreateOrder / CreateQuote carry a CatalogItemId - receives SKUs no real account knows, and anything that sizes a deployment off PowerKva, WeightLbs, SupportedUplinkGbps or EC2Capacities.Quantity reads invented hardware.
Fix: the seeded catalog data behind the ListCatalogItems read - the catalog item table in the outposts service state (services/service-com-amazonaws-outposts-outpostsolafservice/src/state/catalog.rs, CATALOG_ITEMS and the sku_code id derivation it feeds), not the handler's paging/filter logic, which is structurally correct. It must publish AWS's catalog entries, with their own ids and hardware figures, in AWS's order.
Traces: outposts-catalog-list-catalog-items#task#1.

=== Cause 2 of 3: a FILTERED ListCatalogItems read reports an item past the end of the recorded page (fixture outposts-catalog-and-instance-types-browsing, step task#1) ===
AWS: recorded behavior only - the model documents that "If you specify multiple filters, the results include only the resources that match all of the specified filters" and that within one filter the results include items matching any value (Smithy: ListCatalogItems input ItemClassFilter/SupportedStorageFilter/EC2FamilyFilter, all @httpQuery). The recorded filtered read is 200 with exactly 3 CatalogItems and no 4th element.
Emulator: answers 200 with a 4th element the recording does not have: {CatalogItemId OR-GB94EOS, ItemClass SERVER, Dimensions OUTPOST_SERVER_2U, RackUnitHeight HEIGHT_2U, PowerKva 1.0, WeightLbs 70, EC2Capacities c6gd/16xlarge and c6id/32xlarge, SupportedStorage [EBS]} - i.e. one of its own synthesized SERVER rows. The first three entries match, so the selection rule itself behaves; what is selected from is the wrong catalog.
Why: a client that narrows the catalog by class, storage or EC2 family gets a page with an item AWS would not have returned, so filter-driven SKU pickers select hardware that does not exist and the page size a paginating client sees is wrong.
Fix: same component as Cause 1 - the seeded catalog dataset the filtered read selects over (src/state/catalog.rs); once the published rows are AWS's, the filtered page is AWS's page. Re-verify the filter predicates (CatalogItemRecord::is_class / supports_storage / offers_family) against AWS's rows after reseeding.
Traces: outposts-catalog-and-instance-types-browsing#task#1.

=== Cause 3 of 3: ListOrderableInstanceTypes publishes the wrong instance-type catalog (fixture outposts-catalog-list-orderable-instance-types, step task#1) ===
AWS: recorded behavior only - the model types InstanceTypes as DetailedInstanceTypeListDefinition and enumerates nothing (Smithy: ListOrderableInstanceTypes -> ListOrderableInstanceTypesOutput$InstanceTypes, input OutpostGenerationFilter/MaxResults/NextToken as @httpQuery; http GET /instanceTypes, success 200). The recorded page is 200 and includes GENERATION_2 rack types the emulator has no row for at all - m8i.96xlarge (VCPUs 384, MemoryInMib 1572864, NetworkPerformance "100 Gigabit"), r8i.96xlarge (VCPUs 384, MemoryInMib 3145728), c8i.96xlarge (VCPUs 384, MemoryInMib 786432), each with FormFactorConfigs [{FormFactor RACK, OutpostGeneration GENERATION_2}] - and for GENERATION_1 it lists a narrower set of sizes per family (c5.24xlarge, c5d.24xlarge at VCPUs 96 / MemoryInMib 196608).
Emulator: answers 200 with a list built by expanding its own ORDERABLE_FAMILIES table to EVERY size of every family it knows, so ~105 of the recorded entries diverge: the GENERATION_2 entries are reported missing (the emulator's second generation is c7i/m7i/r7i, not c8i/m8i/r8i), and entries AWS does not publish are reported extra (c5.12xlarge, c5.18xlarge, c5.2xlarge, c5d.12xlarge, c5d.4xlarge ...). Ordering therefore diverges from the recorded index onwards as well.
Why: this is the list a caller consults to decide what an Outpost can run. A client reading it cannot find the instance types AWS actually offers (so a GENERATION_2 order is rejected as unorderable), while offerings that do not exist are advertised; any index- or page-based consumption of the list lands on the wrong element.
Fix: the seeded instance-type catalog behind this read - ORDERABLE_FAMILIES and its per-size expansion in services/service-com-amazonaws-outposts-outpostsolafservice/src/state/catalog.rs (orderable_instance_type_catalog) - must publish the instance types AWS publishes, with their generation/form-factor pairs, in AWS's order; the handler's filter and paging need no change.
Traces: outposts-catalog-list-orderable-instance-types#task#1.
