# Listed association summaries advertise an id their own ARN does not name

> _Note: this issue was identified against the code base at commit `4c5ed4b9d036a2e1417b0b3c05fbe59e6fe27101`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
This issue bundles 4 distinct net-new replay clusters. All 4 are in the guardduty service, all are on ListCustomDetectionRuleAssociations, and all are on the SAME member of the SAME shape: the `associationId` the emulator serializes into each AssociationSummary of the `ruleAssociations` listing, for the entry the replay locates by that entry's own `arn`. Fix ALL FOUR causes and re-replay every fixture#step named under Traces (the representative in Issue-Trace/Issue-Step plus the three in Issue-Trace-Ids) before submitting; closing fewer than four leaves this issue's remaining causes unexercised. None of the 4 clusters is blocked by a stub (stub_path="") and none is marked owned by an open issue (owned_by=[]).

SHARED FAULT: the identity an association advertises in the list projection is not interchangeable with the identity that same entry's ARN names and that the recording establishes for the association, so a list-then-act client receives a handle the service does not accept. In all 4 clusters the HTTP status is correct (200) and every other member of the summary matches; ONLY `associationId` is reported as a value_mismatch, and the deterministic comparator renders expected and actual with the SAME visible characters. The diverging dimension is therefore NOT the visible digits: it is one the report's rendering collapses (the serialized member's JSON type - e.g. a number or a quoted-twice string rather than a plain JSON string - its case, or surrounding whitespace), or it is the identity the record is bound to rather than how it prints. A fixer MUST compare the serialized `associationId` byte-for-byte, JSON type included, against the trailing `/association/<id>` segment of the `arn` in the SAME entry and against the id a following GetCustomDetectionRuleAssociation accepts as its path label. Do not compare by eye against the replay report.
