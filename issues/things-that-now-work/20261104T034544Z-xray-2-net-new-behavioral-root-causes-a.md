## Description
TWO distinct net-new root causes in the X-Ray service. Both failing checks carry SERVICES = ["xray"], and xray is bootstrapped and answering (131/159 xray checks pass in this run), so these are fidelity defects, not a bootstrap gap. Cause 1 of 2: a service whose root segment PutTraceSegments has just accepted is not readable as a GetServiceGraph node over a window containing that segment.
AWS: Smithy (services/service-com-amazonaws-xray-awsxray/smithy-model/com-amazonaws-xray-awsxray.json) models GetServiceGraph as POST /ServiceGraph (success 200, paginated inputToken/outputToken NextToken, items Services) with required StartTime/EndTime and output Services -> ServiceList of Service{Name, Names, Type, State, Edges, SummaryStatistics}; errors InvalidRequestException (400) and ThrottledException (429). PutTraceSegments is POST /TraceSegments (200) whose only negative signal is UnprocessedTraceSegments. Recorded behavior: a segment accepted by PutTraceSegments (UnprocessedTraceSegments == []) makes its `name` reachable in the service graph for a window containing the segment — as a node Name or as an entry of a node's Names alias list — within tens of seconds, and a host that only called PutTelemetryRecords (POST /TelemetryRecords, empty output) never becomes a node, because the telemetry and trace pipelines are separate.
Emulator: PutTraceSegments accepted the probe segment (the check asserts UnprocessedTraceSegments == [] before polling, and that assertion passed) and PutTelemetryRecords answered 200, but a fully paginated GetServiceGraph walk over [now-600 s, now+300 s] never contains the traced service name; the check is cut off inside that poll. The contrast assertion the check exists for (the telemetry-only hostname must never be a node) is therefore never even reachable, so the emulator's telemetry/trace separation is unverified. Hypothesis: the node exists but is unreachable through pagination — the handler pages the graph at an emulator-chosen SERVICE_GRAPH_PAGE_SIZE of 5 Services per page (services/service-com-amazonaws-xray-awsxray/src/ops/get_service_graph.rs:258) over a node map ordered by node name, so with a shared store holding every other check's services in the same 15-minute window, a node sorting late is beyond the pages a client walks; AWS does not page the service map five nodes at a time. The alternative is that the window selection in the graph derivation (crate::state::service_graph, segment.start_time >= start && < end) drops the segment.
Why: the service map is X-Ray's primary aggregate read. A client that submits segments and then reads GetServiceGraph to discover topology, latency and fault statistics sees a graph without its own service, so dependency discovery, console views and anything alarmed off the map are blind, and the client cannot distinguish 'no traffic' from 'not readable'.
Fix: the GetServiceGraph handler and the graph projection/paging it reads (services/service-com-amazonaws-xray-awsxray/src/ops/get_service_graph.rs and crate::state::service_graph / page_service_graph in src/state.rs) — make a just-ingested root segment's service appear in the window that contains it and keep it reachable within a client-sized page walk.
Traces: xray.telemetry-only-host-absent-from-service-graph.

Cause 2 of 2: with the account's trace-segment destination settled on CloudWatchLogs, an accepted segment is never delivered to the aws/spans CloudWatch Logs log group — PutTraceSegments only acknowledges it.
AWS: recorded behavior only for the delivery itself (Smithy models UpdateTraceSegmentDestination/GetTraceSegmentDestination returning {Destination -> TraceSegmentDestination [XRay|CloudWatchLogs], Status -> TraceSegmentDestinationStatus [PENDING|ACTIVE]}, and PutTraceSegments POST /TraceSegments 200; no operation models the delivery). Per the Transaction Search prerequisites (https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/Enable-TransactionSearch.html), once the destination is CloudWatchLogs and ACTIVE and a CloudWatch Logs resource policy grants xray.amazonaws.com logs:PutLogEvents on arn:aws:logs:<region>:<account>:log-group:aws/spans:*, X-Ray writes each ingested span into the aws/spans log group, so a FilterLogEvents on that group with a filterPattern naming an annotation value carried by the submitted segment returns at least one event whose message contains that value. The log group name aws/spans is fixed; the only variable part is the marker value, which comes from the submitted segment document.
Emulator: the destination switch is accepted and reads back Destination=CloudWatchLogs/Status=ACTIVE, and PutTraceSegments answers 200 with UnprocessedTraceSegments == [] (both asserted before the poll, both passed), but logs.filter_log_events(logGroupName='aws/spans', filterPattern='"<marker>"') never returns an event for the submitted segment for the whole poll; the aws/spans log group is not even created (the check treats ResourceNotFoundException as 'no events'). PutTraceSegments stores the document in the X-Ray trace store unconditionally and writes nothing to CloudWatch Logs (services/service-com-amazonaws-xray-awsxray/src/ops/put_trace_segments.rs never reads the destination singleton).
Why: Transaction Search is exactly the feature that makes spans queryable as logs. A client that enables it, verifies Destination=CloudWatchLogs/ACTIVE and then queries aws/spans — the documented consumption path for CloudWatch Logs Insights queries, metric filters and subscription filters over spans — gets an empty or missing log group forever, while the emulator reports the feature as enabled. The destination setting is thereby cosmetic: it changes a reported value and nothing about where data goes.
Fix: the PutTraceSegments handler and the trace-segment-destination state it must consult (services/service-com-amazonaws-xray-awsxray/src/ops/put_trace_segments.rs and the trace_segment_destination record in src/state.rs) — when the settled destination is CloudWatchLogs, deliver each accepted segment document to the aws/spans log group (creating it as X-Ray does) through the emulator's CloudWatch Logs state.
Traces: xray.trace-segment-destination-cloudwatch-logs-delivery-enforced.
