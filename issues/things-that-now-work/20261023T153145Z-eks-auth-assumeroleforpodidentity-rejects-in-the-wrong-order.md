# eks-auth AssumeRoleForPodIdentity rejects in the wrong order and with unmodeled/wrong error shapes (3 causes)

> _Note: this issue was identified against the code base at commit `6d7833292dd9d4a45d8e52e2aa7ee7e5a822f7f5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssumeRoleForPodIdentity

## Description
EKS Auth's only operation, AssumeRoleForPodIdentity (POST /clusters/{clusterName}/assume-role-for-pod-identity, restJson1), fails every behavioral check in this suite that reaches it (11 mismatches). The failures cluster into 3 distinct root causes, all on the operation's rejection path. All 3 are in service eks-auth.

NOTE ON OVERLAP: the open wire issue 20261023T055957Z-eks-auth-assumeroleforpodidentity-returns-wrong-rejection-errors-for-invalid-token.md describes the same two surfaces as Causes 1 and 2 below from the WIRE corpus; the behavioral replay did not mark these checks as OWNED by it (its Issue-Keys are wire replay keys, not behavioral check ids), so they are filed here with their behavioral check ids so a fixer can re-replay them. Cause 3 is NOT covered by that issue or any other open issue.

Cause 1 of 3: clusterName is resolved BEFORE the token is parsed, so a bad token is reported as a missing cluster (ResourceNotFoundException/404 instead of InvalidTokenException/400).
AWS: Smithy (services/service-com-amazonaws-eksauth-eksauthfrontend/smithy-model/com-amazonaws-eksauth-eksauthfrontend.json): AssumeRoleForPodIdentity models InvalidTokenException (httpError 400, doc "The specified Kubernetes service account token is invalid.") and ResourceNotFoundException (httpError 404); input clusterName is an @httpLabel with @length 1..100 and @pattern ^[0-9A-Za-z][A-Za-z0-9\-_]*$, token is @required, @sensitive, @pattern ^[A-Za-z0-9-_=]+\.[A-Za-z0-9-_=]+\.[A-Za-z0-9-_=]+$. Recorded behavior (us-west-2, per the checks): AWS validates and parses the presented token first and answers HTTP 400 InvalidTokenException for any token that is not genuine cluster-issued key material, regardless of whether the named cluster exists; the modeled 404 ResourceNotFoundException is effectively unreachable without real key material. Example messages: "The token included in the request has missing header - kid." / "The token included in the request has invalid header - kid." (messages are examples; the requirements are status 400 and code InvalidTokenException).
Emulator: answers HTTP 404 ResourceNotFoundException with message "The cluster <name> does not exist." for every such request. This holds for an absent-but-pattern-valid name, for the shortest legal name ('a'), for every token-claims variant (valid window, expired, wrong audience, etc.), and consistently across 10 concurrent requests (all 10 returned ResourceNotFoundException). It also makes eks-auth agree with EKS proper on cluster existence, where real AWS deliberately diverges: EKS DescribeCluster/ListPodIdentityAssociations 404 on the absent name while eks-auth reports the token error, so the emulator invents a cluster-existence oracle for a caller holding no valid token.
Why: the EKS Pod Identity Agent / SDK credential provider keys on the error code and status. A 404 ResourceNotFoundException sends it down the "cluster is misconfigured" path instead of refreshing/reporting a bad service-account token, and 404 vs 400 also changes SDK retry classification. It additionally leaks cluster existence to an unauthenticated-by-token caller.
Fix: the operation's handler ordering in services/service-com-amazonaws-eksauth-eksauthfrontend/src/ops/assume_role_for_pod_identity.rs — the cluster lookup runs at the top of `handle` (the `guard.cluster(&input.cluster_name).ok_or_else(... ResourceNotFoundException ...)` step) before `verify_service_account_token`; token parsing/header validation must run first and raise InvalidTokenException there.
Traces: eks-auth.assume-role-unknown-cluster-not-found, eks-auth.assume-role-error-response-no-credentials-leak, eks-auth.assume-role-concurrent-invalid-requests-consistent-error, eks-auth.pod-identity-clustername-constraint-boundaries-rejected, eks-auth.pod-identity-token-claims-are-never-evaluated, eks__eks-auth.pod-identity-absent-cluster-rejected-on-token-not-existence.

Cause 2 of 3: input-constraint rejections surface as the unmodeled generic ValidationException instead of InvalidParameterException.
AWS: Smithy: this service models InvalidParameterException (httpError 400, doc "The specified parameter is invalid. Review the available parameters for the API request.") and models NO ValidationException at all (the operation's error list is AccessDenied, ExpiredToken, InternalServer, InvalidParameter, InvalidRequest, InvalidToken, ResourceNotFound, ServiceUnavailable, Throttling). Recorded behavior: a token violating the JwtToken @pattern and a clusterName violating the ClusterName @pattern are both refused with HTTP 400 and code InvalidParameterException. The message here has a known rule — it is built from the request, naming the member and the violated constraint, with the @sensitive token's value omitted — e.g. "1 validation error detected: Value at 'token' failed to satisfy constraint: Member must satisfy regular expression pattern: [A-Za-z0-9-_=]+\.[A-Za-z0-9-_=]+\.[A-Za-z0-9-_=]+" and "1 validation error detected: Value '-sim2realbehav' at 'clusterName' failed to satisfy constraint: Member must satisfy regular expression pattern: [0-9A-Za-z][A-Za-z0-9\-_]*" (note the pattern is rendered unanchored).
Emulator: status 400 is right, but the error code is ValidationException (produced by the generic constraint-trait validator, an error shape this service does not model). Observed for the clusterName leading-hyphen case, for a token with no dot separators at all, and for a request that violates both at once; the emulator's rendering of the constraint also carries the ^...$ anchors.
Why: an SDK cannot catch the modeled InvalidParameterException — an unmodeled error type deserializes to a generic service exception — so client error handling keyed on InvalidParameterException never fires.
Fix: the operation's input validation / error serializer for this service — map constraint failures on clusterName and token to InvalidParameterException (400) with the eksauth error type, and keep the @sensitive token value out of the composed message.
Traces: eks-auth.assume-role-malformed-token-pattern-rejected, eks-auth.assume-role-malformed-cluster-name-rejected, eks-auth.assume-role-invalid-token-value-not-leaked-in-error, eks-auth.pod-identity-header-rejection-layers-are-ordered.

Cause 3 of 3: the caller's IAM authorization is never evaluated, so an explicitly-denied principal is never answered AccessDeniedException.
AWS: Smithy: AssumeRoleForPodIdentity models AccessDeniedException (httpError 400, doc "You don't have permissions to perform the requested operation. The IAM principal making the request must have at least one IAM permissions policy attached that grants the required permissions..."). Recorded behavior only: a principal carrying an explicit Deny on eks-auth:AssumeRoleForPodIdentity is refused with AccessDeniedException BEFORE request-body validation, so even a request with a bogus clusterName and a garbage token surfaces the permission failure; the same request from an unrestricted principal gets a different, more specific error.
Emulator: no IAM policy evaluation happens on this path at all. The check polled for AccessDeniedException for 60s (12 attempts) and never observed it, exhausting the harness timeout; the IAM/STS scaffolding itself succeeded (its failure path raises immediately instead of timing out). Corroborated by the handler, which uses AccessDeniedException only for "the cluster holds no pod identity association for this service account" and never consults the caller's identity/policies, and by Cause 1, where every request from any principal is answered ResourceNotFoundException. Hypothesis: the authorization layer is simply absent for this operation, so the request falls straight through to cluster resolution.
Why: a client or test asserting that an IAM deny boundary is enforced sees the request accepted into business-logic validation instead of refused, so an emulator-backed policy test passes where real AWS refuses — an over-permissive divergence.
Fix: the operation's authorization step (request authorization middleware / the handler's entry in services/service-com-amazonaws-eksauth-eksauthfrontend/src/ops/assume_role_for_pod_identity.rs) — evaluate the caller's IAM permissions for eks-auth:AssumeRoleForPodIdentity ahead of input validation and raise AccessDeniedException (400) on an explicit deny.
Traces: eks-auth.assume-role-access-denied-explicit-deny.
