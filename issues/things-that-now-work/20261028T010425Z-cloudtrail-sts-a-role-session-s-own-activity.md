# cloudtrail__sts: a role session's own activity is never audited with its session identity — no AssumeRole record carrying requestParameters.sourceIdentity and no session-attributed GetCallerIdentity record with userIdentity.sessionContext

> _Note: this issue was identified against the code base at commit `90e278c71dc0064b33db461e7a7ee5696876a066`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
LookupEvents

## Description
ONE net-new root cause (Cause 1 of 1): CloudTrail's event history carries no record that attributes a call to the STS role session that made it, and no AssumeRole record that carries the session's provenance, so SourceIdentity is unobservable anywhere in the audit path.

Related open issues, none of which covers this check: 20261027T001707Z-sts-3-net-new-behavioral-root-causes-assumerolewithwebidentity.md (its Cause 3 is the same family — SourceIdentity not visible on a session's later GetCallerIdentity record — but its replay set names only sts.assume-role-source-identity-echoed, and it says nothing about the AssumeRole record's own requestParameters.sourceIdentity / responseElements.assumedRoleUser.arn, the chained-session inheritance, or the twin control that must record NO sourceIdentity) and 20261024T114720Z-cloudtrail-event-history-is-empty-for-everything-but.md (its Cause 1 is the absence of management events for non-CloudTrail services generally; its replay set does not name this check and it does not describe session attribution or sourceIdentity at all). A fixer must make the behavior below hold for this check's replay key regardless of those two.

Cause 1 of 1 — session provenance is absent from the delivered records.
AWS: Smithy binds sts AssumeRole with input member SourceIdentity (sourceIdentityType, @length 2..64, @pattern ^[\w+=,.@-]*$) and echoes it in AssumeRoleResponse.SourceIdentity; cloudtrail LookupEvents (input LookupAttributes/StartTime/EndTime/EventCategory/MaxResults, output Events whose CloudTrailEvent is the record as a JSON STRING) is the index those records are read from. Beyond the model, the documented record contract is: (a) the AssumeRole event records requestParameters.roleArn, requestParameters.roleSessionName and requestParameters.sourceIdentity (IAM User Guide, "Viewing source identity in CloudTrail"), responseElements.assumedRoleUser.arn equal to the ARN STS returned, eventSource "sts.amazonaws.com", no errorCode on success, and userIdentity.arn naming the principal that CALLED AssumeRole (not the role minted); (b) every later call made with that session's credentials is recorded with userIdentity.type "AssumedRole", sessionContext.sessionIssuer.arn equal to the ROLE ARN (not the session ARN), and sessionContext.sourceIdentity equal to the value passed to AssumeRole (CloudTrail User Guide, "CloudTrail userIdentity element" -> "AWS STS source identity": in service API events sourceIdentity is found in the sessionContext block); (c) the value persists into a CHAINED session that supplies none of its own (sts AssumeRole model doc for SourceIdentity: "The source identity value persists across chained role sessions."); (d) a session assumed WITHOUT SourceIdentity records no sourceIdentity key at all, while still being audited with its own sessionIssuer. All of those values are taken from the request and from the emulator's own state (role ARN, session name, assumed-role ARN, the SourceIdentity string); none of them is a per-run constant of a particular recording.
Emulator: no such record is ever delivered. The check mints three roles, assumes one WITH SourceIdentity, chains from it into a second, assumes a third WITHOUT SourceIdentity, makes one GetCallerIdentity marker call with each set of session credentials, and then polls cloudtrail LookupEvents (EventName=AssumeRole, then EventName=GetCallerIdentity, 10 s interval, 255 s internal budget, paging to exhaustion) for a record pinned to its own run-unique session names. Nothing matching ever arrives, so the check is still polling when the harness's 60 s cap kills it: verdict [mismatch], detail "Error: Check timed out after 60.0s", and it never reaches any of its field assertions. Hypothesis: the shared management-event log is written only by CloudTrail's own mutating handlers, and the record builder has no notion of the calling principal's assumed-role session, so neither the STS AssumeRole call nor the session-credential GetCallerIdentity calls produce a record and no sessionContext is ever rendered.
Why: a client gets no answer to "who did this". SourceIdentity exists precisely so a session's activity can be attributed to the human or workload behind it, and it cannot be changed for the session's life; an emulator that accepts the field, echoes it, and then records nothing tells a developer their attribution and compliance control works when in AWS the audit record is the only thing that control reads. Equally, because the twin control leg is also unrecorded, the emulator cannot be distinguished from one that stamps a constant source identity on every session — both look identical (empty) to the consumer.
Fix: the management-event recording seam plus session state — persist SourceIdentity (and the chained-session inheritance) on the assumed-role session in the STS service crate, drive the shared management-event recorder from STS's served operations (AssumeRole and read-only calls such as GetCallerIdentity, not just CloudTrail's own mutating handlers), and render the caller's session into the record: userIdentity.type/arn, sessionContext.sessionIssuer.arn (role ARN), sessionContext.sourceIdentity, requestParameters.roleArn/roleSessionName/sourceIdentity and responseElements.assumedRoleUser.arn in the CloudTrail record builder. Relevant components per the checkout cited by the related CloudTrail issue: services/service-com-amazonaws-cloudtrail-cloudtrail-20131101/src/ops/lookup_events.rs reading service_common::management_events via crate::state::management_event_log, whose writer is documented as "reached from each mutating handler" of that service only.

## Evidence
Replay of suite simparity-behavioral-ga-prod-v1 against the booted emulator.

cloudtrail__sts.source-identity-propagates-from-assume-role-into-the-sessions-own-audit-records — verdict [mismatch], detail "Error: Check timed out after 60.0s". The check is not marked ALREADY FILED and is not OWNED by any open issue in this report.

The stall is an absence of records, not a refusal or a sleep: the check's setup legs (CreateRole/PutRolePolicy/GetRole, three AssumeRole calls including one chained AssumeRole and one with SourceIdentity, three GetCallerIdentity marker calls) all have to have been SERVED for execution to reach the terminal reads, and its retry helpers raise immediately on any non-AccessDenied / non-"Invalid principal" error. Its only unbounded waits are the three _await_record() polls over cloudtrail LookupEvents (_INDEX_BUDGET_S=255.0, _POLL_INTERVAL_S=10.0, _lookup_all pages to exhaustion up to 40 pages), each of which looks for a record pinned to a run-unique session name:
  - EventName=AssumeRole with requestParameters.roleSessionName == 'first<nonce>', then asserts requestParameters.sourceIdentity == the SourceIdentity sent, requestParameters.roleArn == the role ARN, responseElements.assumedRoleUser.arn == the ARN STS returned, eventSource == 'sts.amazonaws.com', errorCode is None, and userIdentity.arn == the CALLER's assumed-role ARN;
  - EventName=GetCallerIdentity whose userIdentity.arn names 'first<nonce>', then asserts userIdentity.type == 'AssumedRole', sessionContext.sessionIssuer.arn == the ROLE ARN, and sessionContext['sourceIdentity'] == the SourceIdentity;
  - the same for the CHAINED session 'chain<nonce>' (must INHERIT the source identity) and for the control session 'bare<nonce>' (must carry NO sourceIdentity key yet still be audited with its own sessionIssuer).
None of the three polls is ever satisfied, so none of the above assertions is reached. The check also carries the suite's DATAPLANE_UNIMPLEMENTED marker for exactly the case of a target that audits no session identity.

Corroboration that this is attributable to the emulator and not to a slow runner: the emulator has no IAM propagation delay, so the check's setup completes fast and the whole 60 s window is spent in LookupEvents polling; cloudtrail__cognito-identity__sts checks in the same run pass (2/2), so the CloudTrail client path and LookupEvents itself answer; and the open issue 20261027T001707Z (Cause 3) records the same non-arriving GetCallerIdentity record for a SourceIdentity session from an STS-only check.

1. Boot the emulator from this checkout and replay the behavioral suite (run_behavioral_suite); re-replay exactly the check id in trace_ids.
2. Minimal repro: iam.create_role R_launch trusting arn:aws:iam::<account>:root for sts:AssumeRole with an inline Allow on sts:AssumeRole + sts:SetSourceIdentity; iam.create_role R_first trusting the account root for sts:AssumeRole + sts:SetSourceIdentity; iam.create_role R_chain trusting R_first's ARN for sts:AssumeRole + sts:SetSourceIdentity; iam.create_role R_bare trusting the account root for sts:AssumeRole.

4. cloudtrail.lookup_events(StartTime=<just before step 3>, EndTime=now+5min, LookupAttributes=[{'AttributeKey':'EventName','AttributeValue':'AssumeRole'}]), paging NextToken to exhaustion. 5. cloudtrail.lookup_events(... LookupAttributes=[{'AttributeKey':'EventName','AttributeValue':'GetCallerIdentity'}]) over the same window. Observe: no record names any of the three sessions, so none of these fields exists to be read.
