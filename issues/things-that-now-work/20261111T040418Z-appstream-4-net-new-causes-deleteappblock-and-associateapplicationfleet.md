# appstream: 4 net-new causes — DeleteAppBlock and AssociateApplicationFleet answer 501 so their refusals are unreachable, a duplicate CreateUser succeeds, and an issued StreamingURL resolves to no fleet-referencing session endpoint

> _Note: this issue was identified against the code base at commit `6f5959473f4f355ac18f705f826bb321fb68622e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteAppBlock

## Description
Four net-new root causes in the appstream (PhotonAdminProxyService, 2016-12-01, awsJson1_1) emulator, found by the behavioral suite. Each cause is numbered with its own failing check ids; all four must be closed before this issue is submitted. Hosts, ports, per-run unique resource names, account ids, timestamps and signature values quoted below come from one replay and are NOT part of any requirement — only statuses, error codes and message templates are.

=== Cause 1 of 4: DeleteAppBlock is an unimplemented scaffold stub, so AppStream's in-use refusal and its delete/not-found lifecycle are all unreachable. Failing check: appstream.appblock-deletion-blocked-while-associated-rejected ===
AWS: Smithy (services/service-com-amazonaws-appstream-photonadminproxyservice/smithy-model/com-amazonaws-appstream-photonadminproxyservice.json) models DeleteAppBlock with input {Name (required, Name, pattern ^[a-zA-Z0-9][a-zA-Z0-9_.-]{0,100}$)}, an EMPTY output (DeleteAppBlockResult has no members) and errors {ConcurrentModificationException (httpError 400), ResourceInUseException (httpError 400, doc "The specified resource is in use."), ResourceNotFoundException (httpError 404)}. The model does not state when each applies, so the sequencing is recorded behavior only: (a) DeleteAppBlock on an app block whose ARN is still the AppBlockArn of an existing Application is refused HTTP 400 ResourceInUseException with message "The app-block <Name> is currently in use." — fixed text "The app-block " ... " is currently in use.", with <Name> the app-block name taken from the request; (b) the refusal has no effect: DescribeAppBlocks(Arns=[arn]) still returns exactly one entry; (c) once the referencing Application is deleted, DeleteAppBlock returns HTTP 200 with the empty result; (d) DescribeAppBlocks on the deleted ARN is then refused HTTP 404 ResourceNotFoundException with message "The App block <Arn> for account <accountId> does not exist." — fixed text "The App block " ... " for account " ... " does not exist.", with <Arn> from the request and <accountId> the caller's account; (e) a repeat DeleteAppBlock on the already-deleted name is refused with that same 404 ResourceNotFoundException and message (gone means unusable, not merely unlisted).
Emulator: every DeleteAppBlock answers HTTP 501 with error code 'NotImplemented'. services/service-com-amazonaws-appstream-photonadminproxyservice/src/ops/delete_app_block.rs still carries the `//! SCAFFOLDED, NOT IMPLEMENTED:` marker and its handle() body is `Err(crate::scaffolded::Scaffolded::not_implemented("DeleteAppBlock"))`, so no app block can be deleted and neither refusal class can ever be produced.
Why: a client cannot delete app blocks at all, and the one guard that protects a deployed Application from losing its package (ResourceInUseException) is silently absent — code that relies on AWS refusing the delete sees a 501 it has no handler for, and code that deletes app blocks in teardown cannot clean up. A caller distinguishing "in use" from "not found" gets neither.
Fix: implement the handler services/service-com-amazonaws-appstream-photonadminproxyservice/src/ops/delete_app_block.rs against the service's app-block/application state (reference lookup from Application.AppBlockArn, removal, and the not-found path shared with DescribeAppBlocks), and delete the SCAFFOLDED marker line.
Traces: appstream.appblock-deletion-blocked-while-associated-rejected.

=== Cause 2 of 4: AssociateApplicationFleet is an unimplemented scaffold stub, so the platform-compatibility refusal and the successful association are both unreachable. Failing check: appstream.associate-application-fleet-platform-mismatch-rejected ===
AWS: Smithy models AssociateApplicationFleet with input {FleetName (required, Name), ApplicationArn (required, Arn)}, output {ApplicationFleetAssociation} and errors {ConcurrentModificationException 400, InvalidParameterCombinationException 400, LimitExceededException 400, OperationNotPermittedException 400, ResourceNotFoundException 404}; its doc is "Associates the specified application with the specified fleet. This is only supported for Elastic fleets." The model does NOT declare the error this case uses, so that part is recorded behavior only: associating an Application whose Platforms do not contain the fleet's Platform is refused HTTP 400 with error code InvalidParameterValueException and message "Application '<ApplicationArn>' may not be associated with fleet '<FleetName>' because fleet Platform '<fleet Platform>' is not supported by application Platforms: [<the application's Platforms, comma-separated>]" — the quoted sentence fragments are fixed text, and the ARN, fleet name, fleet Platform and the application's Platforms list are all values from the request and from stored state. The refusal leaves no association (DescribeApplicationFleetAssociations(FleetName=...) does not list the ApplicationArn), and a platform-compatible application associates successfully (HTTP 200 with ApplicationFleetAssociation).
Emulator: AssociateApplicationFleet answers HTTP 501 'NotImplemented'; services/service-com-amazonaws-appstream-photonadminproxyservice/src/ops/associate_application_fleet.rs is still the generated stub returning `Scaffolded::not_implemented("AssociateApplicationFleet")`. Replay detail: "expected InvalidParameterValueException for a platform-mismatched association, got 'NotImplemented'".
Related, not duplicate: the suite auto-filed a bare "unimplemented scaffold stub" issue for AssociateApplicationFleet from the checkout (it blocks appstream.application-fleet-association-lifecycle). This cause records the behavior that implementation owes beyond existing: the platform-compatibility check, its exact error code/message, and the no-effect guarantee. Close it against this check as well.
Why: an Elastic-fleet client can neither attach applications to a fleet nor rely on AppStream rejecting a Linux-only application on a Windows fleet. On AWS a mismatched association is refused up front; here the caller gets a 501 it cannot classify, and an orchestrator that treats non-4xx as retryable spins.
Fix: implement services/service-com-amazonaws-appstream-photonadminproxyservice/src/ops/associate_application_fleet.rs — validate fleet and application existence (ResourceNotFoundException), intersect Application.Platforms with Fleet.Platform and refuse the mismatch with the message above before mutating state, persist the association for DescribeApplicationFleetAssociations, and remove the SCAFFOLDED marker.
Traces: appstream.associate-application-fleet-platform-mismatch-rejected.

=== Cause 3 of 4: a repeat CreateUser for an already-established identity SUCCEEDS instead of being refused ResourceAlreadyExistsException. Failing check: appstream.user-enable-disable-state-transition ===
AWS: Smithy models CreateUser with input {UserName (required, Username, @length 1..128, sensitive), AuthenticationType (required enum), MessageAction (enum), FirstName, LastName}, an EMPTY output and errors {InvalidAccountStatusException 400, InvalidParameterCombinationException 400, LimitExceededException 400, OperationNotPermittedException 400, ResourceAlreadyExistsException (httpError 400)}. Recorded behavior: after a user has been created and is observable via DescribeUsers(AuthenticationType=...), a second CreateUser with the same UserName and AuthenticationType is refused HTTP 400 ResourceAlreadyExistsException with message "A user with that username already exists." — that whole sentence is fixed text with no variable part (notably it does NOT echo the user name).
Emulator: the duplicate CreateUser(UserName=<same>, AuthenticationType='USERPOOL', MessageAction='SUPPRESS') returns HTTP 200 with an empty JSON body (content-type application/x-amz-json-1.1, content-length 2). Replay detail: "expected the call to be rejected, but it SUCCEEDED and returned {'ResponseMetadata': {'HTTPStatusCode': 200, ...}}". The settled-duplicate path is therefore unguarded; the check stops there, so the DisableUser/EnableUser Enabled flip and the post-delete ResourceNotFoundException path after it are untested, not proven.
Related, not duplicate: open issue 20261102T120557Z-appstream-createuser-is-not-idempotent-a-repeat-create.md records the opposite-looking recording — N CONCURRENT identical CreateUser calls all return 200. Both recordings must hold: concurrent identical creates in flight all succeed and allocate the identity once, while a create issued after the identity is established and observable is refused ResourceAlreadyExistsException. Whatever change made the concurrent case pass must not blanket-accept the settled duplicate.
Why: a client that provisions users treats success as "I created this user". Accepting a duplicate hides a genuine identity collision between two different onboarding flows (different FirstName/LastName or a different owner reusing the name), so a caller that on AWS would stop and reconcile instead proceeds against someone else's user.
Fix: the CreateUser handler and the user-pool state in services/service-com-amazonaws-appstream-photonadminproxyservice — keyed on (UserName, AuthenticationType), refuse an established duplicate with ResourceAlreadyExistsException and AWS's sentence, keeping the existence-check/insert atomic so in-flight identical creates still collapse to one success.
Traces: appstream.user-enable-disable-state-transition.

=== Cause 4 of 4: the StreamingURL CreateStreamingURL issues resolves to nothing — fetching it yields no session endpoint referencing the fleet the session was issued for. Failing check: appstream.streaming-url-rejected-until-fleet-running ===
AWS: Smithy models CreateStreamingURL with input {StackName (required), FleetName (required), UserId (required, @length 2..32, pattern ^[\w+=,.@-]*$), ApplicationId, Validity, SessionContext}, output {StreamingURL, Expires} and errors {InvalidParameterCombinationException 400, OperationNotPermittedException 400, ResourceNotAvailableException 400, ResourceNotFoundException 404}. The model says nothing about what the URL resolves to, so this is recorded behavior only: the signed URL returned for a RUNNING fleet is a real reservation — fetching it (as a browser would) is authenticated by the backend and redirects to a session-specific endpoint whose final URL carries the fleet reference `fleet%2F<FleetName>` (URL-encoded `fleet/<FleetName>`), naming the exact fleet the session was allocated against. The earlier, now-passing parts of this check (OperationNotPermittedException "The fleet <FleetName> is not running. The stack must have a running fleet to get a streaming URL" while STOPPED, no session at DescribeSessions, non-empty StreamingURL with a future Expires after StartFleet) are satisfied; only the resolution of the issued URL diverges.
Emulator: fetching the issued StreamingURL performs no redirect to any session endpoint — the final URL is byte-for-byte the signed URL that was handed out, of the form `/streaming-sessions/<StackName>/<FleetName>/<UserId>?X-Amz-Algorithm=AWS4-HMAC-SHA256&X-Amz-Credential=...&X-Amz-Date=...&X-Amz-Expires=60&X-Amz-SignedHeaders=host&X-Amz-Signature=...`, which contains no `fleet%2F<FleetName>` reference. So the URL is a formatted string, not a session allocated at the destination. (The host, port, credential, date and signature in the replay are per-run values and not requirements; the absent redirect and absent `fleet%2F<FleetName>` reference are.)
Why: the StreamingURL is the only artifact a client hands to an end user or embeds in a portal. On AWS following it lands in a session bound to that fleet; here it dead-ends at the same signed URL, so a browser never reaches a session and tooling that reads the redirect target to confirm which fleet served the session finds no fleet reference — a client cannot tell a real reservation from a fabricated URL.
Related, not duplicate: open issue 20261109T145337Z-appstream-2-net-new-causes-createstreamingurl-is-a.md covers CreateStreamingURL having been a 501 stub and the not-RUNNING-fleet refusal being unreachable; that refusal now answers correctly, and what remains is the issued URL resolving to no fleet-referencing session endpoint.
Fix: the CreateStreamingURL handler in services/service-com-amazonaws-appstream-photonadminproxyservice plus the route that serves the `/streaming-sessions/...` endpoint it points at — allocate a session for (StackName, FleetName, UserId) at issue time and have a GET of the signed URL redirect to that session's endpoint carrying the `fleet%2F<FleetName>` reference for the fleet the session was allocated against.
Traces: appstream.streaming-url-rejected-until-fleet-running.
