# s3: 10 more net-new root causes — bucket sub-resource configuration validation (analytics, intelligent-tiering, inventory, metrics, lifecycle, website) accepts invalid documents or refuses with non-AWS codes and messages

> _Note: this issue was identified against the code base at commit `56c3e2d5db4619f120a986f75a3622f8f9af8979`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutBucketLifecycleConfiguration

## Description
Ten further distinct net-new root causes under `### s3`, all in the bucket sub-resource configuration surface and the listing/batch plane. Close all ten before submitting.

Cause 1 of 10: DeleteObjects does not report a delete-marker removal as such, and its over-limit refusal message carries extra prose.
AWS: Smithy — DeleteObjects POST /{Bucket}?delete; `DeletedObject` carries `Key`, `VersionId`, `DeleteMarker` and `DeleteMarkerVersionId`. When the deleted version WAS a delete marker, the `<Deleted>` entry sets `DeleteMarker` true and `DeleteMarkerVersionId` to that marker's id. A `Delete` element carrying more than 1000 `Object` entries is refused HTTP 400 `<Code>MalformedXML</Code>` with the fixed schema-failure sentence "The XML you provided was not well-formed or did not validate against our published schema" and nothing appended.
Emulator: the marker removal comes back as `{'Key': ..., 'VersionId': ..., 'DeleteMarker': True}` with no `DeleteMarkerVersionId`, so the caller cannot tell which marker was removed; and the 1001-entry refusal message is "The XML you provided was not well-formed or did not validate against our published schema: a Delete request carries from 1 to 1000 Object elements, and this one carries 1001" — AWS's fixed text plus an emulator-authored suffix.
Why: an undelete routine that reads DeleteMarkerVersionId to confirm which marker it removed gets nothing, and exact-message matching on MalformedXML fails.
Fix: the DeleteObjects handler's result serializer and its batch-size validation message.
Traces: s3.mbes-deleting-a-delete-marker-restores-the-previous-version, s3.mbes-delete-objects-caps-a-batch-at-one-thousand-keys.

Cause 2 of 10: ListObjectsV2 delimiter/StartAfter semantics are wrong.
AWS: recorded behavior. With `Delimiter="/"`, a zero-byte "folder marker" object whose key ends in `/` is folded into its OWN CommonPrefix, so `empty/` appears in CommonPrefixes even though it is the only key under that prefix. `StartAfter` is a plain lexicographic start token applied to keys, so `StartAfter="b/"` with `Delimiter="/"` resumes AFTER the whole `b/` group and the response's CommonPrefixes start at `c/`.
Emulator: the folder marker is dropped from CommonPrefixes (expected `['documents/', 'empty/']`, got `['documents/']`), and `StartAfter='b/'` still returns the `b/` prefix (expected `['c/']`, got `['b/', 'c/']`).
Why: directory-browser UIs lose empty folders and paginate the same page twice.
Fix: the ListObjectsV2 handler's delimiter/common-prefix grouping and its StartAfter comparison.
Traces: s3.folder-marker-object-folds-into-its-own-common-prefix, s3.start-after-a-common-prefix-skips-the-whole-subdirectory.

Cause 3 of 10: PutBucketAnalyticsConfiguration performs almost no validation, and the validation it does perform answers the wrong code.
AWS: Smithy — PutBucketAnalyticsConfiguration PUT /{Bucket}?analytics, `Id` is @required on the `?id=` query and `AnalyticsConfiguration` is the @required @httpPayload; `AnalyticsFilter` is a UNION whose doc states "A filter must have exactly one prefix, one tag, or one conjunction (AnalyticsAndOperator)". AWS refuses: an Id outside the allowed character set and an Id longer than 64 characters with HTTP 400 `<Code>InvalidConfigId</Code>`; a destination `S3BucketDestination.Bucket` that is not an ARN, an ARN carrying a region, and an empty `BucketAccountId` with HTTP 400 `<Code>InvalidArgument</Code>`; a Filter setting both Prefix and Tag at the top level with HTTP 400 `<Code>MalformedXML</Code>` and the fixed sentence "The XML you provided was not well-formed or did not validate against our published schema"; a document whose `Id` element differs from the `?id=` parameter with HTTP 400 `<Code>MalformedXML</Code>`; and a NEW configuration id past the 1000-per-bucket cap with `<Code>TooManyConfigurations</Code>` and AWS's limit sentence.
Emulator: the id-pattern, non-ARN destination, region-qualified ARN and empty-account-id documents are all ACCEPTED with 200; the over-64-character id is refused `InvalidArgument` instead of `InvalidConfigId`; the both-Prefix-and-Tag filter is refused `ValidationException` "union 'AnalyticsFilter' had more than one member set" (a Smithy union artefact, not an S3 code); the id-mismatch document is refused `InvalidArgument` instead of MalformedXML; and the limit refusal's wording does not match AWS's.
Why: a caller cannot trust that the analytics configuration it just stored is the one AWS would have accepted, and clients branching on InvalidConfigId / MalformedXML never see those codes.
Fix: PutBucketAnalyticsConfiguration validation and its error mapping (the union-arity failure must be mapped to MalformedXML, not surfaced as ValidationException).
Traces: s3.s3-analytics-xacct-only-put-validates-the-config-id-pattern, s3.s3-analytics-xacct-put-rejected-for-a-config-id-over-64-characters, s3.s3-analytics-xacct-put-rejected-for-a-destination-that-is-not-an-arn, s3.s3-analytics-xacct-put-rejected-for-a-filter-with-both-prefix-and-tag, s3.s3-analytics-xacct-put-rejected-for-a-region-qualified-destination-arn, s3.s3-analytics-xacct-put-rejected-for-an-empty-bucket-account-id, s3.s3-analytics-xacct-put-rejected-past-one-thousand-configurations, s3.s3-analytics-xacct-put-rejected-when-the-document-id-differs.

Cause 4 of 10: forged or foreign continuation tokens are not refused MalformedContinuationToken.
AWS: recorded behavior. The `continuation-token` on the bucket-configuration listings (ListBucketAnalyticsConfigurations, ListBucketIntelligentTieringConfigurations, ListBucketInventoryConfigurations) is opaque and bucket-scoped; a token S3 never issued, or a token issued for a different bucket, is refused HTTP 400 `<Code>MalformedContinuationToken</Code>` with the fixed message "The continuation-token you provided invalid."
Emulator: a forged token is refused `('InvalidArgument', 'The continuation token provided is incorrect')` — wrong code and wrong message — and a token from another bucket is accepted outright ("the call succeeded; real AWS rejects it, so there is no error code").
Why: a paginating client that replays a stale token silently gets a page from the wrong bucket instead of a retryable error.
Fix: the continuation-token decoder shared by the bucket-configuration list handlers.
Traces: s3.s3-analytics-xacct-list-rejected-for-a-malformed-continuation-token, s3.s3-itc-list-rejected-for-a-malformed-continuation-token, s3.s3-inventory-list-errors-for-a-continuation-token-from-another-bucket.

Cause 5 of 10: PutBucketIntelligentTieringConfiguration performs no document validation and mis-words the refusals it does emit.
AWS: Smithy — PutBucketIntelligentTieringConfiguration PUT /{Bucket}?intelligent-tiering; `IntelligentTieringConfiguration` requires `Id`, `Status` and `Tierings`. AWS refuses with HTTP 400 `<Code>InvalidArgument</Code>`: two Tierings naming the same AccessTier; an `And` filter carrying a single predicate; an empty Filter `Prefix`; duplicate Tag keys inside `And`; and a DEEP_ARCHIVE_ACCESS `Days` that does not exceed the ARCHIVE_ACCESS `Days`. A document whose `Id` differs from the `?id=` parameter is refused HTTP 400 `<Code>MalformedXML</Code>` with the fixed schema-validation sentence. A new id past the 1000-per-bucket cap is `<Code>TooManyConfigurations</Code>` with AWS's limit sentence.
Emulator: five of those documents are accepted with 200 ("the call succeeded; real AWS rejects it, so there is no error code"); the id-mismatch is refused `('InvalidArgument', 'IntelligentTieringConfiguration.Id must be the id the request identifies ("query-id"), got "body-id"')` — emulator-authored prose under the wrong code; the cap refusal message is 'The bucket already carries the 1000 S3 Intelligent-Tiering configurations a bucket may have', not AWS's.
Why: invalid tiering plans are stored and read back as valid, so a caller believes objects are being tiered on a schedule AWS would never have accepted.
Fix: PutBucketIntelligentTieringConfiguration validation and its error mapping/messages.
Traces: s3.s3-itc-put-rejected-for-a-duplicate-access-tier, s3.s3-itc-put-rejected-for-an-and-filter-with-a-single-element, s3.s3-itc-put-rejected-for-an-empty-filter-prefix, s3.s3-itc-put-rejected-for-duplicate-tag-keys-in-an-and-filter, s3.s3-itc-put-rejected-past-one-thousand-configurations, s3.s3-itc-put-rejected-when-deep-archive-days-do-not-exceed-archive-days, s3.s3-itc-put-rejected-when-the-document-id-differs-from-the-query-id.

Cause 6 of 10: inventory and metrics configuration validation uses the wrong codes, and the metrics filter arity is not checked.
AWS: recorded behavior. PutBucketInventoryConfiguration with a document `Id` that differs from the `?id=` parameter is refused HTTP 400 `<Code>IdMismatch</Code>`. Emulator: the inventory id mismatch is refused `InvalidArgument`, not IdMismatch; the metrics multi-member and empty filters are refused `ValidationException` (the Smithy union/structure artefact) instead of MalformedXML; the metrics id mismatch is refused `InvalidArgument`; and the cap message is not AWS's.
Why: accepting a `Filter: {}` or a multi-member filter stores a configuration whose scope is undefined — downstream tag-filter predicates then count a whole-bucket configuration as filtered — and IdMismatch-aware clients never see that code, storing a configuration under an id they cannot predict.
Fix: PutBucketInventoryConfiguration / PutBucketMetricsConfiguration validation and error mapping.

Cause 8 of 10: the lifecycle refusals the emulator DOES emit are its own prose under partly wrong codes.
AWS: recorded behavior — each lifecycle refusal has fixed text whose only variable parts are the storage class, the filter description, the rule id and the day counts taken from the submitted document:
  • duplicate rule ids → `InvalidArgument` "Rule ID must be unique. Found same ID for more than one rule"
  • a transition to a colder class scheduled before a warmer one → `InvalidArgument` "'Days' in the 'Transition' action for StorageClass '<COLDER>' for filter '<filter>' must be greater than 'Days' in the 'Transition' action for StorageClass '<WARMER>' for filter '<filter>'"
  • a NoncurrentVersionTransition within the minimum duration → `InvalidArgument` "'NoncurrentDays' in the 'NoncurrentVersionTransition' action for StorageClass '<CLASS>' for filter '<filter>' must be 30 days more than ... for StorageClass '<CLASS>'"
  • STANDARD as a NoncurrentVersionTransition target → `InvalidArgument` "Invalid target Storage class for NoncurrentVersionTransition action"
  • a rule id over 255 characters → "ID length should not exceed allowed limit of 255"
  • a rule with no action → `InvalidRequest` "At least one action needs to be specified in a rule"
  • a Transition/Expiration `Date` not at midnight → `InvalidArgument` "'Date' must be at midnight GMT"
  • an undefined `x-amz-transition-default-minimum-object-size` → `InvalidRequest` "Invalid TransitionDefaultMinimumObjectSize found: <the value sent>"
  • a short transition (STANDARD_IA after 1 day) is ACCEPTED and round-trips — there is no 30-day floor on the Transition action itself.
Emulator: every message is replaced with emulator prose prefixed by a rule ordinal — e.g. 'Rule 3: ID "a-transition" identifies an earlier rule as well; a rule identifier is unique within a lifecycle configuration', 'Rule 1: transitions to "GLACIER" and then to the warmer class "ONEZONE_IA"; transitions follow the order STANDARD_IA -> ...', 'Rule 1: Transition.Date must be at midnight UTC', 'Rule 1: names no action; a lifecycle rule carries at least one expiration or transition action'; the STANDARD-target case is answered `MalformedXML` instead of InvalidArgument; TransitionDefaultMinimumObjectSize is answered with a Smithy enum-constraint message under `InvalidArgument`; and the short transition is REFUSED with an invented 30-day floor ('Rule 1: transitions to "STANDARD_IA" after 1 days, before the 30 days an object is stored in its current class first').
Why: every client that matches on AWS's lifecycle error text mis-reports the problem, and the invented 30-day floor rejects a configuration AWS accepts, so a valid lifecycle policy cannot be deployed at all.
Fix: the lifecycle validator's error codes and message templates in the PutBucketLifecycleConfiguration handler.

Cause 9 of 10: PutBucketWebsite refusals use the wrong codes and emulator-authored messages.
AWS: Smithy — PutBucketWebsite PUT /{Bucket}?website; `WebsiteConfiguration` holds ErrorDocument, IndexDocument, RedirectAllRequestsTo and RoutingRules, and RedirectAllRequestsTo's doc states "If you specify this property, you can't specify any other property." AWS's refusals carry fixed text:

Cause 10 of 10: the S3 website endpoint does not serve.
AWS: recorded behavior. The website endpoint serves the IndexDocument for `/` and for a directory-style path, serves the ErrorDocument with HTTP 404 for a missing key, honours `x-amz-website-redirect-location` on an object by answering HTTP 301 with that `Location` while the REST endpoint still serves the object's body, applies RoutingRules on a 404 (redirecting missing keys), refuses write methods, and answers `NoSuchWebsiteConfiguration` on GetBucketWebsite for a bucket that was never configured.

Why: the whole static-website hosting feature is unreachable, so nothing that fronts S3 with a website endpoint can be exercised.
Fix: the S3 website-endpoint request path (index/error document resolution, redirect-location handling, routing rules, method gating) and the website-configuration state it reads.
