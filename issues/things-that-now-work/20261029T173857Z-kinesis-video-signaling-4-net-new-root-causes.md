# kinesis-video-signaling: 4 net-new root causes — the signaling data plane keeps its own channel registry nothing ever seeds (every GetIceServerConfig on a real channel is 404), both channel-resolution refusal messages are invented, the modeled-ARN-pattern refusal leaks the generic constraint-validation text, and the WSS signaling data plane is not served at all

> _Note: this issue was identified against the code base at commit `42eb24959c6a4eb33ac3ba3d48b702ee83f6032d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetIceServerConfig

## Description
The Kinesis Video Signaling data plane diverges from AWS in four independent ways. All 12 failing behavioral checks of this service are accounted for by these causes. Related but NOT covering: open issue 20261022T180000Z-kinesis-video-media-getmedia-cannot-see-a-stream-createstream-made.md reports the same class of defect for kinesis-video-media streams; this issue is the signaling-channel registry and is a different service and different state.

=== Cause 1 of 4: the signaling channel registry is never populated by the control plane, so GetIceServerConfig answers 404 for every channel that actually exists ===
AWS: recorded behavior only — the Smithy model binds GetIceServerConfig (restJson1, POST /v1/get-ice-server-config) with a required `ChannelARN` (target ResourceARN, @length 1..1024, @pattern ^arn:aws:kinesisvideo:[a-z0-9-]+:[0-9]+:[a-z]+/[a-zA-Z0-9_.-]+/[0-9]+$) and returns `IceServerList` (IceServer: Uris, Username, Password, Ttl with @range 30..86400); errors modeled are ClientLimitExceededException(400), InvalidArgumentException(400), InvalidClientException(400), NotAuthorizedException(401), ResourceNotFoundException(404), SessionExpiredException(400). The model does not describe resource lifetime, but every recording shows the same contract: a channel created through the control plane (kinesisvideo CreateSignalingChannel, waited to ChannelStatus ACTIVE) and whose HTTPS data-plane endpoint came from kinesisvideo GetSignalingChannelEndpoint resolves on the signaling data plane, and GetIceServerConfig against that ARN returns HTTP 200 with a non-empty IceServerList (Ttl 300, at least one turn:/turns: URI, Username of the form <unix-expiry>:<opaque token>).
Emulator: every one of the nine GetIceServerConfig checks fails on its FIRST, positive-control call — the one made against the freshly created, ACTIVE channel — with HTTP 404 ResourceNotFoundException and message "No signaling channel exists with ARN arn:aws:kinesisvideo:<region>:<account>:channel/<channelName>/<creationId>". The channel demonstrably exists: the same check's DescribeSignalingChannel returned ACTIVE and GetSignalingChannelEndpoint returned the endpoint the call was addressed to. The signaling crate owns a private `channels: HashMap<String, SignalingChannel>` registry that only its own `register_channel` writes, and nothing on the control-plane path calls it, so the registry is permanently empty and `resolve_channel_mut` always reports NotFound.
Why: the service's only ICE/TURN operation is unusable. A WebRTC client cannot obtain relay credentials for any channel it created, so no viewer can ever fall back to TURN; worse, the emulator reports "this channel does not exist" for a channel the control plane says is ACTIVE, which sends a client down a resource-recreation path instead of a retry.
Fix: the signaling data plane's channel state and its seeding seam — services/service-com-amazonaws-kinesisvideosignaling-awsacuitysignalingservice/src/state.rs (register_channel, resolve_channel/resolve_channel_mut, lines 89-119) must be fed by, or share one store with, the kinesisvideo control plane's CreateSignalingChannel/DeleteSignalingChannel, so that channel create/delete is visible to GetIceServerConfig (handler lookup at src/ops/get_ice_server_config.rs:412-428) and SendAlexaOfferToMaster (src/ops/send_alexa_offer_to_master.rs:242-245).
Traces: kinesis-video-signaling.get-ice-server-config-returns-valid-turn-credentials, .get-ice-server-config-minimal-required-params-succeeds, .get-ice-server-config-client-id-pattern-not-enforced, .get-ice-server-config-concurrent-clients-share-time-bucketed-credential, .get-ice-server-config-ice-ttl-independent-of-channel-message-ttl, .get-ice-server-config-denied-without-iam-permission, .get-ice-server-config-deleted-channel-not-found, .get-ice-server-config-nonexistent-channel-not-found, .get-ice-server-config-malformed-channel-arn-rejected

=== Cause 2 of 4: the ResourceNotFoundException message for an unresolved channel ARN is invented ===
AWS: recorded behavior only — for a well-formed ChannelARN naming a channel that does not exist (never created, or deleted), the signaling data plane answers HTTP 404 ResourceNotFoundException (modeled, httpError 404, member Message) whose message is "<channelName> channel does not exist !". Fixed text: " channel does not exist !" (single space before `channel`, space before the trailing `!`); the only variable part is <channelName>, the channel-name segment taken from the request's ChannelARN — not the whole ARN.
Emulator: answers the right code and status but the message "No signaling channel exists with ARN <full ARN>" (src/ops/get_ice_server_config.rs:360-365 and src/ops/send_alexa_offer_to_master.rs:178-181), which is neither AWS's fixed text nor AWS's variable part. This is observable today on every GetIceServerConfig call because of Cause 1, and the two not-found checks assert the message verbatim.
Why: clients and test suites that match on the refusal message (or scrape the channel name out of it) misclassify a missing channel, and a human reading the emulator's log sees wording no AWS runbook contains.
Fix: the channel-resolution refusal mapping of both operations' handlers — `unresolved_channel` in src/ops/get_ice_server_config.rs:355-367 and src/ops/send_alexa_offer_to_master.rs:173-182 — must render the AWS message template from the ARN's parsed channel name.
Traces: kinesis-video-signaling.get-ice-server-config-nonexistent-channel-not-found, .get-ice-server-config-deleted-channel-not-found

=== Cause 3 of 4: a ChannelARN that violates the modeled @pattern is refused with the generic constraint-validation message instead of the service's "Invalid Channel ARN !" ===
AWS: recorded behavior only (the model supplies the constraint, not the text) — ChannelARN carries @pattern ^arn:aws:kinesisvideo:[a-z0-9-]+:[0-9]+:[a-z]+/[a-zA-Z0-9_.-]+/[0-9]+$ on both GetIceServerConfig and SendAlexaOfferToMaster, and a value failing it (e.g. a valid ARN with one trailing non-digit appended, still inside @length 1..1024) is refused with HTTP 400 InvalidArgumentException whose message is exactly "Invalid Channel ARN !" — entirely fixed text, with NO request value interpolated, and specifically not a not-found lookup.
Emulator: SendAlexaOfferToMaster returns InvalidArgumentException (code correct) with the framework's generic constraint report: "1 validation error detected: Value 'arn:aws:kinesisvideo:<region>:<account>:channel/<name>/<creationId>x' at 'channelARN' failed to satisfy constraint: Member must satisfy regular expression pattern: ^arn:aws:kinesisvideo:[a-z0-9-]+:[0-9]+:[a-z]+/[a-zA-Z0-9_.-]+/[0-9]+$" — it echoes the caller's value and the raw regex. The same divergence is baked into the handlers' own fallback for a malformed ARN, which reads "ChannelARN is not a Kinesis Video signaling channel ARN: <arn>" (src/ops/get_ice_server_config.rs:357-359, src/ops/send_alexa_offer_to_master.rs:175-177).
Why: an AWS-faithful client distinguishes a malformed-ARN refusal by its message; the emulator's text leaks the model's regex and the caller's input, so message-based assertions and error-presentation layers diverge, and the two code paths (boundary validator vs handler) can disagree with each other.
Fix: the ChannelARN validation/refusal path for these two operations — the request-boundary pattern validator's message for `channelARN` must be the service's "Invalid Channel ARN !" InvalidArgumentException, and the handlers' MalformedArn branch must render the identical text.
Traces: kinesis-video-signaling.send-alexa-offer-to-master-malformed-arn-and-no-master-error-semantics, kinesis-video-signaling.get-ice-server-config-malformed-channel-arn-rejected

=== Cause 4 of 4: the channel's WSS signaling data plane is not served, and SendAlexaOfferToMaster refuses instead of returning an answer-less 200 ===
AWS: recorded behavior only — the signaling channel's real data plane is a SigV4(query)-authenticated secure WebSocket. The WSS endpoint returned by kinesisvideo GetSignalingChannelEndpoint (Protocols [WSS], Role MASTER/VIEWER) accepts a WebSocket upgrade carrying X-Amz-ChannelARN (and X-Amz-ClientId for a viewer) and brokers JSON signaling frames: a viewer's {action: SDP_OFFER} is delivered to the connected master as {messageType: SDP_OFFER, senderClientId: <viewer client id>, messagePayload: <base64 offer>}, and the master's {action: SDP_ANSWER, recipientClientId: <that id>} is delivered back to the viewer as {messageType: SDP_ANSWER, messagePayload: <base64 answer>}. SendAlexaOfferToMaster (POST /v1/send-alexa-offer-to-master, output member `Answer` @length 1..10000) delivers the offer over the master's live WSS connection and returns that master's answer; with NO master connected the recordings show the call is still ACCEPTED — it blocks for the channel's redelivery window (bounded by SingleMasterConfiguration.MessageTtlSeconds) and then returns HTTP 200 with no `Answer` member at all. ResourceNotFoundException is reserved for a channel that does not exist, never for "no master connected".
Emulator: the WebSocket upgrade to the channel's WSS endpoint is rejected outright — websockets.exceptions.InvalidStatus: server rejected WebSocket connection: HTTP 404 — for both the MASTER and VIEWER roles, so no signaling frame can ever be exchanged and no master can ever attach to a channel. Consequently the only source of an answer (the crate's SignalingChannel.master_answer, src/state.rs:146-147) is never set, and SendAlexaOfferToMaster's handler takes its no-master branch and REFUSES with 404 ResourceNotFoundException "No master is connected to signaling channel <arn>, so the offer from <senderClientId> cannot be delivered" (src/ops/send_alexa_offer_to_master.rs:253-258) where AWS answers 200 with no Answer.
Why: WebRTC peering is the entire purpose of a signaling channel. A client can create a channel and read endpoints but can never connect, offer or answer, so no session is ever established; and the Alexa REST path converts AWS's "accepted, nothing to deliver" (a verdict inside a 200) into a hard not-found error, which tells a caller its channel is gone rather than that no master is listening.
Fix: the signaling data plane's WSS route must be served (a WebSocket upgrade handler on the endpoint kinesisvideo GetSignalingChannelEndpoint advertises for WSS, authenticating the presigned SigV4 query, registering the connecting peer as MASTER/VIEWER on the channel, and routing SDP_OFFER/SDP_ANSWER/ICE_CANDIDATE frames between them), and SendAlexaOfferToMaster's delivery path (src/ops/send_alexa_offer_to_master.rs:242-272) must wait on the live master and return a 200 with `Answer` omitted when none answers, instead of raising ResourceNotFoundException.
Traces: kinesis-video-signaling.kvs-signaling-wss-offer-answer-roundtrip, kinesis-video-signaling.send-alexa-offer-to-master-master-connectivity-gates-delivery
