# cloudfront: 3 causes — a distribution's DomainName is published as <id>.cloudfront.net (34 edge checks unreachable), CreateWebACL refuses Scope=CLOUDFRONT, and AssociateDistributionWebACL accepts a REGIONAL-scope web ACL

> _Note: this issue was identified against the code base at commit `17c4643c966c9683f16ddaee3534ae6f6497ef31`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDistribution

## Description
Three distinct root causes. A fixer must close all three before submitting.

Cause 1 of 3: a distribution's DomainName names an address the emulator does not serve, so the CloudFront edge data plane is unreachable.
AWS: CreateDistribution/GetDistribution return Distribution.DomainName, and a viewer request to https://<DomainName>/<path> is answered by the CloudFront edge — that is the whole contract behind cache behaviors, cache-key policies, compression, custom error responses, invalidations, origin groups, edge functions, signed cookies/URLs, response-headers policies, OAC origin signing, web-ACL enforcement and the Requests metric (recorded behavior only; the Smithy model types DomainName as a string and says nothing about reachability).
Emulator: DomainName is published as "<lowercased-id>.cloudfront.net" — a host the emulator does not serve and does not resolve to it. Every check that then sends a viewer request is refused before any byte reaches the emulator: "endpoint_url was given https://<id>.cloudfront.net (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener". The announced address, not the caller's choice, is the defect: the emulator advertises an address other than one it is reached on.
Why: no client can fetch anything through a distribution. Every edge-observable behavior is silently untestable and unusable: a customer who follows the API's own DomainName gets a connection to AWS's production CloudFront (or nothing), never the emulator.
Fix: the CloudFront distribution serializer must publish a DomainName on a host:port the emulator actually serves (its own host, or a per-distribution listener), and an edge request router must answer viewer requests on that host by applying the distribution's cache behaviors and fetching from the configured origin. Cause 2 of 3: CreateWebACL refuses Scope=CLOUDFRONT outright, so no CloudFront-scope web ACL can exist.
AWS: Smithy (wafv2) com.amazonaws.wafv2#Scope is an enum with values [CLOUDFRONT, REGIONAL]; CreateWebACL with Scope=CLOUDFRONT is accepted and returns Summary with Id/ARN of a global web ACL (arn:aws:wafv2:<region>:<account>:global/webacl/<name>/<id>). WAFInvalidParameterException is modeled for parameters WAF does not recognize (client error, HTTP 400).
Emulator: CreateWebACL(Scope="CLOUDFRONT") is refused 400 WAFInvalidParameterException "Error reason: The scope is not valid., field: SCOPE_VALUE, parameter: CLOUDFRONT" — the fixed text is "Error reason: <Reason>, field: <Field>, parameter: <Parameter>" and here Reason="The scope is not valid.", Field=SCOPE_VALUE, Parameter=the requested scope. A modeled enum value is thus rejected as invalid.
Why: every CloudFront web-ACL workflow is blocked at its first setup call. A client cannot create the only kind of web ACL a distribution or distribution tenant accepts, so association, disassociation and their refusal contracts cannot be reached at all.
Fix: the wafv2 CreateWebACL handler's scope validation must accept both modeled Scope values and store a CLOUDFRONT-scope (global) web ACL, minting a global/webacl ARN. Related open wafv2 issues touch CLOUDFRONT-scope refusal routing on other operations (20261105T153125Z-wafv2-refusal-routing-3-net-new-causes-generic.md, 20261102T094456Z-wafv2-scope-and-identifier-validation-refusals-carry-the.md) but none reports CreateWebACL refusing the scope itself.

Cause 3 of 3: AssociateDistributionWebACL accepts a REGIONAL-scope web ACL ARN.
AWS: only a CLOUDFRONT-scope web ACL may be associated with a distribution. A REGIONAL ARN (arn:aws:wafv2:<region>:<account>:regional/webacl/<name>/<id>) is refused 400 InvalidArgument with the fixed message "The specified web ACL isn't valid. Specify a web ACL that was previously validated and try again." and nothing is mutated — a follow-up GetDistributionConfig still shows WebACLId empty (recorded behavior; Smithy models InvalidArgument as a client error for this operation).
Emulator: the call succeeds with HTTP 200, echoing Id, ETag and the REGIONAL WebACLArn, and the association is persisted.
Why: a client that mis-scopes its web ACL is told the distribution is protected when, on AWS, the association would have been refused; the distribution carries an ARN WAF will never enforce, and the mistake is discovered only in production traffic.
Fix: AssociateDistributionWebACL's validation must check the web ACL ARN's scope (and its existence) before mutating distribution state and refuse a non-CLOUDFRONT ARN with 400 InvalidArgument and AWS's sentence. The open issue 20261029T175823Z-cloudfront-10-more-divergences-the-edge-data-plane.md owns a neighbouring check (a malformed WebACLArn) but not this scope case.
