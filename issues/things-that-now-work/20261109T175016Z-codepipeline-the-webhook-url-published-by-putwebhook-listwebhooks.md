# codepipeline: the webhook URL published by PutWebhook/ListWebhooks is on an AWS webhooks.aws host the emulator does not serve, so a signed POST can never start the pipeline

> _Note: this issue was identified against the code base at commit `4cb124a92bc472448f3b420460157b630c09e49d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutWebhook

## Description
Cause 1 of 1: the webhook URL CodePipeline publishes for a GITHUB_HMAC webhook points at an AWS-shaped host instead of the emulator's own endpoint.

AWS: Smithy (codepipeline) ListWebhookItem.url is a required member of type WebhookUrl with @length min 1 / max 1000, documented as "A unique URL generated by CodePipeline. When a POST request is made to this URL, the defined pipeline is started as long as the body of the post request satisfies the defined authentication and filtering." The URL is therefore not decorative: it is the data-plane endpoint a client POSTs the provider payload and its signature to, and on real AWS it resolves to a host AWS serves. The requirement an emulator inherits is that the published host/port is one the emulator itself answers on, so the documented POST semantics (correctly signed payload starts an execution; wrong-secret payload is acked 2xx and starts none) are reachable.

Emulator: PutWebhook/ListWebhooks publish `https://<region>.webhooks.aws/trigger?t=<uuid>&v=1` — a host that is not one of the emulator's own hosts. A customer of the emulator needs `http(s)://127.0.0.1:<port>/<resource path>` or `http(s)://<own host>:<port>/<path>` on a per-resource listener. The replay reports the published URL as off-host before any POST is attempted.

Why: a client that does exactly what the API documents — POST the provider payload to the URL the service handed it — never reaches the emulator at all. The request leaves for a name the emulator does not serve, so no pipeline execution is ever started by a webhook, and the whole HMAC authentication path (accept a correct signature, ack-but-ignore a wrong one) is unreachable. Any CI integration driven through a CodePipeline webhook is dead on arrival.

Fix: the URL construction in the PutWebhook handler (and whatever ListWebhooks reads it back from) must build the webhook URL from the emulator's own published endpoint host and port — the same resolution the other per-resource listeners use — and must serve the webhook trigger path on it. The host must never be synthesized from the region as a *.webhooks.aws name.

  AssertionError: the emulator published https://us-west-2.webhooks.aws/trigger?t=8848b8f5-454f-4e85-a585-48a5485da184&v=1: its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:37915/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener

Expected: ListWebhookItem.url is a URL on a host:port the emulator serves, and a POST to it with a correct GITHUB_HMAC signature starts a pipeline execution while a wrong-secret POST is acked 2xx and starts none.
Actual: url host is `<region>.webhooks.aws`, which the emulator does not serve; the POST cannot be delivered. (The uuid in the query string and the 127.0.0.1:37915 address are per-run values, not requirements — the requirement is that the host/port is the emulator's own.)

## Steps to Reproduce
1. Build and boot the emulator from this checkout.
2. Create an S3 artifact bucket, an IAM pipeline role and a pipeline with an S3 source action.
3. Call PutWebhook with authentication GITHUB_HMAC, AuthenticationConfiguration.SecretToken=<secret>, a filter on $.ref, and targetPipeline/targetAction of that pipeline.
4. Read the returned webhook.url (and the same item from ListWebhooks) and compare its host and port with the address the emulator is being reached on.
5. POST the provider payload to that URL with the correct X-Hub-Signature HMAC and observe whether an execution starts.
