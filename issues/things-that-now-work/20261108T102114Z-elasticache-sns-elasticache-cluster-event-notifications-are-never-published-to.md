# ElastiCache cluster event notifications are never published to the configured SNS topic, and NotificationTopicStatus=inactive deletes the topic binding instead of deactivating it (2 causes)

> _Note: this issue was identified against the code base at commit `582ed21b383f102b650a2b551c0e79525419c00c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateCacheCluster

## Description
Two independent root causes on the IMPLEMENTED ElastiCache cache-cluster surface, both exercised by the one failing check elasticache__sns.cache-cluster-event-notification-reaches-the-sns-subscriber. Together they mean the documented ElastiCache -> SNS event integration does not exist in this emulator: a cluster accepts a NotificationTopicArn, reports it as active, and publishes nothing; and asking for notifications to be paused throws the binding away instead of deactivating it. Each cause is separate and must be closed separately.

Note on an existing issue: open issue 20261023T155010Z-elasticache-control-plane-is-unusable-end-to-end.md lists this same check id under its Cause 1, but that cause is CreateCacheSubnetGroup refusing real EC2 subnet ids — a different defect on a different operation, and the replay no longer dies there (the check now gets as far as a provisioned, available cluster). Neither cause below is covered by that issue or by any other open issue; the suite did not mark this check OWNED.

Cause 1 of 2: a cache cluster that carries a NotificationTopicArn never publishes any event to that SNS topic; the event is only written to the local event log.
AWS: Smithy (com.amazonaws.elasticache#AmazonElastiCacheV9): CreateCacheCluster$NotificationTopicArn — "The Amazon Resource Name (ARN) of the Amazon Simple Notification Service (SNS) topic to which notifications are sent. The Amazon SNS topic owner must be the same as the cluster owner"; ModifyCacheCluster$NotificationTopicStatus — "The status of the Amazon SNS notification topic ... Notifications are sent only if the status is active. Valid values: active | inactive"; DescribeCacheClusters reports CacheCluster$NotificationConfiguration as {TopicArn, TopicStatus}. Recorded behavior (the model does not describe the publish itself, so this is recorded behavior only): while NotificationConfiguration.TopicStatus is 'active', every cluster event ElastiCache records for that cluster is ALSO published to the named topic, so an SQS subscriber of that topic receives an SNS Notification envelope (Type='Notification', TopicArn = the configured topic) whose Message names the event in the documented `ElastiCache:<Event>` form together with the cluster id (reboot of a node produces the ElastiCache:CacheNodeReboot* events). The event names and the cluster id are variable parts taken from the operation and the request; the `ElastiCache:` prefix and the envelope shape are fixed.
Emulator: the ARN is STORED and nothing else happens. CreateCacheCluster copies input.notification_topic_arn onto the cluster record and calls store.record_event(..); RebootCacheCluster only sets the node/cluster transition and comments that "the cluster event the reboot's completion creates belongs to DescribeEvents"; there is no SNS Publish anywhere on the elasticache event path, and state.rs says so explicitly next to the hardcoded topic status ("The emulator models no SNS subscription lifecycle"). DescribeEvents does record the event, so the producer side is observable while the delivery side is permanently silent, and a subscriber's queue stays at ApproximateNumberOfMessages=0 forever.
Why: a client that wires cluster events to SNS (the documented ElastiCache ECEvents.SNS pattern, usually SNS -> SQS or SNS -> Lambda for alerting) gets a configuration the service reports as active and a notification stream that never produces a single message. Nothing fails loudly: the client simply never learns a node was replaced, rebooted, or that provisioning completed.
Fix: the elasticache cluster event path — the place a cluster event becomes real (crate::state record_event / CacheClusterRecord::settle, and the create / modify / reboot / delete handlers that drive it) must publish the event to the cluster's configured topic whenever that topic's status is active, instead of only appending to the event log.
Traces: elasticache__sns.cache-cluster-event-notification-reaches-the-sns-subscriber (arm A: after RebootCacheCluster the check waits for a matching notification through its own topic while DescribeEvents already shows the reboot). Code: services/service-com-amazonaws-elasticache-amazonelasticachev9/src/ops/create_cache_cluster.rs (notification_topic_arn stored, event recorded), .../src/ops/reboot_cache_cluster.rs lines 213-238, .../src/state.rs lines 856-859.

Cause 2 of 2: ModifyCacheCluster with NotificationTopicStatus='inactive' CLEARS the stored topic ARN, and NotificationConfiguration.TopicStatus is a hardcoded constant 'active', so an inactive notification configuration is unrepresentable and the binding is destroyed.
AWS: Smithy: ModifyCacheCluster$NotificationTopicStatus — "Notifications are sent only if the status is active. Valid values: active | inactive"; CacheCluster$NotificationConfiguration carries both TopicArn and TopicStatus. Recorded behavior: after ModifyCacheCluster(NotificationTopicStatus='inactive', ApplyImmediately=true) the cluster STILL reports NotificationConfiguration.TopicArn = the same topic with TopicStatus='inactive' (deactivated, not detached); events keep being recorded and are not delivered; a later ModifyCacheCluster(NotificationTopicStatus='active') flips the same configuration back to TopicStatus='active' and delivery resumes without the caller re-supplying the ARN.
Emulator: services/service-com-amazonaws-elasticache-amazonelasticachev9/src/ops/modify_cache_cluster.rs lines 626-633 does `if input.notification_topic_status.as_deref() == Some("inactive") { cluster.notification_topic_arn = None; }` — the topic binding is deleted. And services/.../src/state.rs line 859 defines `NOTIFICATION_TOPIC_STATUS: &str = "active"` as the only status a configured topic is ever reported in, so TopicStatus can never read back 'inactive'. A client polling DescribeCacheClusters for TopicStatus='inactive' therefore never converges (it sees either 'active' or no NotificationConfiguration at all), and re-activating is impossible because the ARN is gone.
Why: pausing notifications is the documented way to silence a cluster temporarily; here it silently unbinds the topic and loses the configuration, so the state a client is told to wait for never appears and the 'resume' step has nothing to resume. Two distinct observable requirements are broken: the readback of TopicStatus, and the persistence of TopicArn across a deactivate/reactivate cycle.
Fix: the cache-cluster record and its projection — store the notification topic STATUS beside the ARN on CacheClusterRecord and project it into NotificationConfiguration.TopicStatus (replacing the fixed NOTIFICATION_TOPIC_STATUS constant), and make the ModifyCacheCluster handler set that status instead of clearing notification_topic_arn; the publish gate of Cause 1 then reads this status.
Traces: elasticache__sns.cache-cluster-event-notification-reaches-the-sns-subscriber (arm B sets NotificationTopicStatus='inactive' and polls NotificationConfiguration.TopicStatus for 'inactive'; arm C sets it back to 'active' and demands delivery resume on the same topic). Code: modify_cache_cluster.rs lines 626-633, state.rs lines 856-868.

2. sns CreateTopic; sqs CreateQueue; set a queue policy allowing sns.amazonaws.com for that topic; sns Subscribe(Protocol='sqs', Endpoint=<queue arn>).
3. ec2 CreateVpc + CreateSubnet (one per AZ) + CreateSecurityGroup; elasticache CreateCacheSubnetGroup over those subnets.
4. elasticache CreateCacheCluster(CacheClusterId=<id>, Engine='redis', CacheNodeType='cache.t3.micro', NumCacheNodes=1, CacheSubnetGroupName=<group>, SecurityGroupIds=[<sg>], NotificationTopicArn=<topic>) and poll DescribeCacheClusters until CacheClusterStatus='available'; observe NotificationConfiguration={TopicArn:<topic>, TopicStatus:'active'}.
5.
