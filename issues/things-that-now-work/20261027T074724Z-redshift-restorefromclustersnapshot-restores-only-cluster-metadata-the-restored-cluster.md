# RestoreFromClusterSnapshot restores only cluster metadata: the restored cluster's database is empty and SELECT on a snapshotted table fails with 'no such table'

## Description

NOTE on an adjacent open issue: 20261024T115115Z-redshift-zero-etl-integration-error-semantics-unreachable-dynamodb.md lists redshift.snapshot-restore-preserves-table-data under its Issue-Trace-Ids, but it carries that check under the replay key `redshift.snapshot-restore-preserves-table-data|_wait_until#30|Timeout|time.sleep(interval_s)` — a 60 s harness timeout in which the restore was never reached and no verdict about snapshot contents was produced. === Cause 1 of 1: a snapshot captures cluster metadata only, so RestoreFromClusterSnapshot produces a cluster with an empty database ===
Failing check: redshift.snapshot-restore-preserves-table-data

AWS: a manual snapshot is a point-in-time copy of the cluster's DATA, not only of its configuration. CreateClusterSnapshot (Smithy: CreateClusterSnapshotMessage{SnapshotIdentifier @required, ClusterIdentifier @required} -> CreateClusterSnapshotResult{Snapshot}; errors ClusterNotFoundFault 404/ClusterNotFound, ClusterSnapshotAlreadyExistsFault 400, InvalidClusterStateFault 400) captures the cluster's databases and their tables and rows; RestoreFromClusterSnapshot (Smithy: RestoreFromClusterSnapshotMessage{ClusterIdentifier @required, SnapshotIdentifier, ...} -> RestoreFromClusterSnapshotResult{Cluster}; errors ClusterSnapshotNotFoundFault 404/ClusterSnapshotNotFound, ClusterAlreadyExistsFault 400/ClusterAlreadyExists, InvalidRestoreFault 406/InvalidRestore) then creates a new cluster with the same configuration as the source AND the snapshot's data, so once the restored cluster is `available` a SELECT over redshift-data against it returns exactly the rows that existed when the snapshot was taken — not rows written to the source afterwards — and both clusters are thereafter independently writable. Documented at https://docs.aws.amazon.com/redshift/latest/mgmt/working-with-snapshots.html. The Smithy model describes the control-plane shapes only, so the data-carrying requirement is documentation plus the recorded behavior of the reference run; neither the model nor the recording models any error for it, because in AWS the restore simply succeeds with data.

Emulator: the control plane is faithful end to end — CreateCluster reaches `available`, CREATE TABLE / INSERT / SELECT on the source cluster FINISH and return the three seeded rows, CreateClusterSnapshot returns SnapshotType 'manual' for the right ClusterIdentifier and the snapshot reaches `available`, and RestoreFromClusterSnapshot returns a Cluster carrying the snapshot's DBName and MasterUsername which then reaches `available`. But the restored cluster's database is EMPTY: the first statement against it fails instead of returning rows. redshift-data DescribeStatement reports Status='FAILED' with Error='no such table: <table>' (fixed text of the engine's refusal is "no such table: " and the variable part is the table name taken from the submitted SQL — here the check's `sim2real_behav_snapshot_rows`), so GetStatementResult is never reached and the check fails with: "SQL 'SELECT id, val FROM <table> ORDER BY id' on <restored-cluster-id> did not FINISH: status='FAILED' error='no such table: <table>'". The cause is visible in the handlers themselves: CreateClusterSnapshot "Copies the identifying attributes off the stored cluster into a new manual snapshot record", and RestoreFromClusterSnapshot builds the new cluster purely from the snapshot's captured CONFIGURATION (node type/count, admin user, db name, port, retention, maintenance window, identity-derived endpoint/ARN); neither touches the data-plane store that backs redshift-data statements.

Why: the single invariant a snapshot exists for is unobservable, and it fails silently rather than loudly. A client that snapshots a cluster, restores it and then queries gets a FAILED statement whose error claims the table does not exist, so backup/restore, clone-for-test and restore-into-a-new-cluster flows all appear to succeed at the control plane (snapshot 'available', cluster 'available') and then lose every row. Point-in-time semantics are equally untestable: a caller cannot distinguish "the restore correctly excluded a post-snapshot row" from "the restore contains nothing at all", and the leaked SQLite-style message 'no such table: X' is not a Redshift error string a client can match on.

Fix: the redshift snapshot state and the restore path — CreateClusterSnapshot's handler (services/service-com-amazonaws-redshift-redshiftserviceversion20121201/src/ops/create_cluster_snapshot.rs) must capture the source cluster's data-plane database contents alongside the identifying attributes it already copies, and RestoreFromClusterSnapshot's handler (services/service-com-amazonaws-redshift-redshiftserviceversion20121201/src/ops/restore_from_cluster_snapshot.rs, the branch that assembles the new cluster record) must materialize that captured data into the new cluster's own database so the redshift-data engine serves it, as an independent copy that later writes to either cluster do not share.

## Evidence

WHERE val=\'after-snapshot\'' on the restored cluster returns 0; the source still returns its four rows.

Actual (emulator): every control-plane step matches — the source statements FINISH and return the three rows, the snapshot is created as SnapshotType 'manual' and reaches 'available', RestoreFromClusterSnapshot returns a Cluster with the snapshot's DBName/MasterUsername and the new cluster reaches 'available'. The first statement against the RESTORED cluster then terminates as Status='FAILED' with Error='no such table: sim2real_behav_snapshot_rows' (table name is the request's, the rest is fixed engine text), so the check aborts in _run_sql with:
  AssertionError: SQL 'SELECT id, val FROM sim2real_behav_snapshot_rows ORDER BY id' on sim2real-behav-rs-snapdst-<id> did not FINISH: status='FAILED' error='no such table: sim2real_behav_snapshot_rows'
The restored cluster's database contains no objects at all; no 2xx/4xx status diverges, the divergence is entirely in the restored cluster's data-plane contents. Handler evidence: create_cluster_snapshot.rs records only "the identifying attributes" of the cluster, and restore_from_cluster_snapshot.rs derives the new cluster solely from the snapshot's captured configuration.
