# connect-contact-lens: 4 net-new root causes in ListRealtimeContactAnalysisSegments refusals — framework ValidationException replaces InvalidRequestException/UnauthorizedException, no instance-resolution stage, and IAM authorization never evaluated

> _Note: this issue was identified against the code base at commit `b2028dd6393016a9896c0e35ff905bdd884f0327`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListRealtimeContactAnalysisSegments

## Description
Four distinct root causes in how ListRealtimeContactAnalysisSegments refuses a request. All four live in the same crate (services/service-com-amazonaws-connectcontactlens-amazonconnectcontactlens) and all four must be closed before this issue is submitted.

=== Cause 1 of 4: a whitespace-only InstanceId is refused with the framework's synthetic ValidationException instead of UnauthorizedException ===
AWS: recorded behavior only. The Smithy model (ListRealtimeContactAnalysisSegments.InstanceId: @required, @length min 1 max 256, @pattern "\\S") models NO error for this case other than the operation's five modeled errors (AccessDeniedException 403, InternalServiceException 500, InvalidRequestException 400, ResourceNotFoundException 404, ThrottlingException 429) — ValidationException is not among them and is not declared anywhere in this service's model. The recording shows AWS resolves InstanceId to a Connect instance BEFORE the request body's pattern constraint is applied to it: an InstanceId made only of whitespace resolves to no instance and the call is refused with error code "UnauthorizedException" and message "Unauthorized". That message is entirely fixed text — it interpolates nothing from the request or from state.
Emulator: the centralized request walk (deserialize -> validate -> handle) refuses the request during validation, so the handler is never entered, and the client sees Code 'ValidationException' with the framework-authored message "1 validation error detected: Value '<the rejected InstanceId>' at 'instanceId' failed to satisfy constraint: Member must satisfy regular expression pattern: \\S". Both the code and the message are emulator/framework artifacts: AWS never emits a smithy.framework#ValidationException for this service, and the AWS text for this class of refusal never echoes the rejected value back for InstanceId.
Why: a client that branches on UnauthorizedException (a retry-never, re-authorize/re-resolve-the-instance path) sees an unmodeled code its SDK cannot map, so error handling falls through to a generic failure. Worse, SDKs and tooling treat ValidationException as a 400 client-input fault local to one member, while the AWS answer is an authorization-stage refusal about the instance, which means operators debug the wrong layer.
Fix: ListRealtimeContactAnalysisSegments's handler and its validation ordering, in services/service-com-amazonaws-connectcontactlens-amazonconnectcontactlens/src/ops/list_realtime_contact_analysis_segments.rs — InstanceId resolution must run ahead of body-constraint validation for that member and must produce the service's own UnauthorizedException (code "UnauthorizedException", message "Unauthorized") rather than letting the framework's synthetic ValidationException escape to the wire.

=== Cause 2 of 4: an InstanceId that satisfies the pattern but resolves to no instance is refused with ResourceNotFoundException instead of UnauthorizedException ===
AWS: recorded behavior only (the model gives InstanceId @length 1..256 and @pattern "\\S" and declares no code for an unresolvable instance). The recording shows a 256-character, non-GUID-shaped InstanceId is NOT rejected for length — it reaches instance resolution, fails to resolve, and is refused with code "UnauthorizedException", message "Unauthorized" (fixed text). A canonical GUID-shaped but still nonexistent InstanceId clears that stage and reaches the contact lookup, which refuses with ResourceNotFoundException, message "Real-time contact analysis not found." So AWS has two distinct stages, and the id's shape decides which one answers.
Emulator: there is no instance-resolution stage at all. list_realtime_contact_analysis_segments.rs builds a SessionKey from (instance_id, contact_id) and, when no session is stored, returns ResourceNotFoundException for every unresolvable InstanceId. The replay shows a 256-char non-GUID InstanceId producing Code 'ResourceNotFoundException' where AWS produces 'UnauthorizedException'.
Why: the two refusals mean different things to a caller — Unauthorized says the instance/principal pairing is wrong (stop and fix configuration), NotFound says the instance is fine but this contact has no live analysis session (a 24-hour-retention timing condition, often retried). Collapsing both into 404 makes a misconfigured instance look like an expired session, so clients retry forever instead of failing fast.
Fix: ListRealtimeContactAnalysisSegments's handler in the same file — add the instance-resolution step the real service performs before the session lookup, and emit UnauthorizedException/"Unauthorized" when the InstanceId resolves to no Connect instance, reserving ResourceNotFoundException/"Real-time contact analysis not found." for a resolvable instance with no stored session.

=== Cause 3 of 4: a ContactId violating @pattern is refused with the framework's ValidationException instead of the modeled InvalidRequestException (HTTP 400) ===
AWS: Smithy: ListRealtimeContactAnalysisSegments.ContactId is @required with @length min 1 max 256 and @pattern "\\S"; the operation models InvalidRequestException with httpError 400 ("The request is not valid."). The recording shows a whitespace-only ContactId against a real ACTIVE instance refused with HTTP 400, code "InvalidRequestException", and message of the form:
  Invalid request body: [ECMA 262 regex ".*\\S.*" does not match input string "<the rejected ContactId>"]
Fixed text: 'Invalid request body: [ECMA 262 regex ".*\\S.*" does not match input string "' ... '"]'. The only variable part is the rejected ContactId value, taken verbatim from the request. When the request ALSO carries MaxResults, the bracketed list gains a second entry and the message becomes:
  Invalid request body: [ECMA 262 regex ".*\\S.*" does not match input string "<the rejected ContactId>", format attribute "int32" not supported]
i.e. the bracketed body is a comma-separated list of findings, not a single fixed sentence. The response body carries no Segments key.
Emulator: the request is refused by centralized validation with Code 'ValidationException' and the framework message "1 validation error detected: Value '<value>' at 'contactId' failed to satisfy constraint: Member must satisfy regular expression pattern: \\S". The modeled InvalidRequestException variant exists in ListRealtimeContactAnalysisSegmentsErrorModeled but is only ever constructed for an unrecognised NextToken, never for a constraint violation.
Why: InvalidRequestException is the code this operation documents for a bad request and the one SDK error-handling branches on; a synthetic ValidationException is not in the model, so a client's `except InvalidRequestException` branch never fires and a deterministic 400 is surfaced as an unknown error. The message text is also part of the contract — clients and support tooling parse the bracketed finding list.
Fix: ListRealtimeContactAnalysisSegments's validation/serialization path in services/service-com-amazonaws-connectcontactlens-amazonconnectcontactlens/src/ops/list_realtime_contact_analysis_segments.rs (and the crate's binding of the framework validation layer) — body-constraint failures for this service must be rendered as the modeled InvalidRequestException on HTTP 400 with the "Invalid request body: [...]" finding-list message, accumulating one finding per violating member, and never as smithy.framework#ValidationException.

=== Cause 4 of 4: identity-based authorization is never evaluated, so a caller explicitly denied connect:ListRealtimeContactAnalysisSegments is served the resource verdict instead of AccessDeniedException (HTTP 403) ===
AWS: Smithy: the operation models AccessDeniedException with httpError 403, documented "You do not have sufficient access to perform this action." Per the recording, authorization runs BEFORE and independently of resource existence: a caller assuming a role with an explicit Deny on connect:ListRealtimeContactAnalysisSegments gets HTTP 403, code "AccessDeniedException", and the standard IAM denial sentence — fixed text "User: " / " is not authorized to perform: " / " on resource: " / " with an explicit deny in an identity-based policy", with the assumed-role principal ARN, the action name connect:ListRealtimeContactAnalysisSegments, and the resource ARN arn:aws:connect:<region>:<account>:instance/<InstanceId>/contact/<ContactId> filled in from the caller's identity and the request. No Segments key appears in the body. A fully privileged caller issuing the identical request clears authorization and reaches the lookup (ResourceNotFoundException, "Real-time contact analysis not found.").
Emulator: no authorization decision is made at all. The handler's own module doc states it deliberately: "The emulator verifies every request signature at the framework boundary and models no IAM principal or policy ... the modeled AccessDeniedException is intentionally unreachable rather than overlooked." The denied caller therefore gets the resource verdict — the replay shows Code 'ResourceNotFoundException' where AWS returns 'AccessDeniedException'.
Why: this is over-permissive. Code written and tested against the emulator never exercises its 403 path, so least-privilege policy regressions and denial handling are invisible until production; and a denied principal is told the resource does not exist, which inverts the ordering AWS guarantees (authorize, then look up) and leaks existence information in the opposite direction.
Fix: the authorization stage for this operation — either the crate's request walk in services/service-com-amazonaws-connectcontactlens-amazonconnectcontactlens/src/ops/list_realtime_contact_analysis_segments.rs or the shared identity/policy evaluation seam it would call — must evaluate the caller's identity-based policy before the instance/session lookup and return the modeled AccessDeniedException on HTTP 403 with the standard denial message when the action is denied.
