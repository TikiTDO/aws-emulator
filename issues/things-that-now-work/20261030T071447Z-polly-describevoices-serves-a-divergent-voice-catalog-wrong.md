# Polly DescribeVoices serves a divergent voice catalog: wrong SupportedEngines, ASCII-folded voice names, wrong LanguageCode/LanguageName and wrong order (4 causes)

> _Note: this issue was identified against the code base at commit `533efece7fa11c0e537273065624bf5d01aa80f8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeVoices

## Description
The seeded voice catalog DescribeVoices reads from does not match the catalog AWS reports. Four replayed DescribeVoices steps (unfiltered and filtered) each diverge in the catalog payload; they are grouped here because they share one root cause — the seed data and the order it is emitted in — but each step is its own cause a fixer must close.

Cause 1 of 4 (fixture polly-catalog-describe-voices, step task#1): the unfiltered catalog diverges in three independent ways at once. (a) SupportedEngines is wrong in content and order for most voices. (b) Voices whose AWS Name/LanguageName carries non-ASCII characters are absent and an ASCII-folded spelling appears in their place. (c) LanguageCode / LanguageName are wrong for individual voices.
AWS: Smithy (services/service-com-amazonaws-polly-parrot-v1/smithy-model/com-amazonaws-polly-parrot-v1.json) models DescribeVoices as GET /v1/voices -> 200 with Voices: list<Voice>, where Voice = {Gender, Id (VoiceId enum), LanguageCode (LanguageCode enum), LanguageName ("Human readable name of the language in English"), Name (VoiceName — "Name of the voice (for example, Salli, Kendra, etc.)"), AdditionalLanguageCodes, SupportedEngines: list<Engine>} and Engine = [standard, neural, long-form, generative]. The model fixes the value SET of SupportedEngines but not which engines a given voice has, nor the catalog's order, so for the per-voice values this is recorded behavior only: the recording shows each voice's engine list in a fixed order with generative first where the voice has it, voice Name/Id spelled with the voice's own diacritics where AWS uses them (Name carries the diacritic form, Id the ASCII form — e.g. the Portuguese and French voices), and a specific LanguageCode/LanguageName pairing per voice (e.g. the Swiss German voice's LanguageName is "Swiss Standard German").
Emulator: for the same request it returns, per voice, engine lists in a different order and with different members (a generative-capable voice reports neural first and generative later or not at all; long-form appears on voices the recording does not give it; standard is dropped from or added to others); it omits every diacritic-spelled voice entirely while serving an ASCII-folded entry under the same Id; and it pairs some voices with the wrong LanguageCode and the wrong LanguageName ("Swiss German" for the voice AWS reports as "Swiss Standard German").
Why: DescribeVoices is the discovery call a client uses to pick a voice and an engine before calling SynthesizeSpeech. A client that filters the catalog for a generative- or long-form-capable voice gets the wrong set, so it either skips a usable voice or calls SynthesizeSpeech with an engine the voice does not support; a client that matches on the voice's displayed Name never finds the diacritic-spelled voices; a client that groups voices by language mis-labels or mis-buckets them.
Fix: the seeded catalog in this service's state (ComAmazonawsPollyParrotV1State::voices, seeded in services/service-com-amazonaws-polly-parrot-v1/src/state.rs) — the per-voice SupportedEngines order and membership, the Name/LanguageName strings including their non-ASCII spellings, and the LanguageCode/LanguageName pairing.
Traces: polly-catalog-describe-voices#task#1.

Cause 2 of 4 (fixture polly-describe-voices-catalog, step task#1): the catalog's ORDER diverges — the first element of Voices is a different voice than the recording's first element.
AWS: recorded behavior only; the model declares no sort for Voices, and the recording returns the catalog in a stable order whose head is a specific voice. A client that takes Voices[0], or that compares the list positionally, depends on that order.
Emulator: Voices[0] is a different voice entirely (the whole list is ordered differently), so every positional comparison after index 0 is offset.
Why: callers that treat the catalog as an ordered listing (taking the first match, paging through it positionally, or snapshotting it) see a different catalog than AWS returns for the same request.
Fix: the ordering the DescribeVoices handler emits the filtered catalog in (services/service-com-amazonaws-polly-parrot-v1/src/ops/describe_voices.rs) together with the seed order in src/state.rs.
Traces: polly-describe-voices-catalog#task#1.

Cause 3 of 4 (fixture polly-describe-voices-catalog, step task#2): a FILTERED DescribeVoices request returns the wrong membership — voices the recording includes are missing and voices it does not include are present, on top of the same SupportedEngines content/order divergence as cause 1.
AWS: Smithy models Engine and LanguageCode as httpQuery filters and IncludeAdditionalLanguageCodes (default false) as the switch that admits a bilingual voice on its AdditionalLanguageCodes; the filtered result is exactly the voices that carry the requested engine/language. Recorded behavior: the filtered list contains a set of voices including ones the emulator omits, and excludes voices the emulator adds.
Emulator: for the same filtered request a modeled voice is absent (missing) while extra voices appear (extra), and the surviving voices' SupportedEngines are reordered/altered as in cause 1 — i.e. the filter is applied over wrong seed data, so its output set is wrong.
Why: a client that asks "which voices support this engine/language" is told a voice it can use does not exist, or offered one that will fail at synthesis time.
Fix: same component as cause 1 — the per-voice SupportedEngines / language seed in src/state.rs, which is what the filter in describe_voices.rs selects on.
Traces: polly-describe-voices-catalog#task#2.

Cause 4 of 4 (fixture polly-describe-voices-catalog, step task#3): a second DescribeVoices variant in the same fixture repeats the engine-list, missing-diacritic-voice and LanguageName divergences, and additionally reports the wrong AdditionalLanguageCodes / LanguageCode for bilingual voices.
AWS: Smithy documents AdditionalLanguageCodes as "Additional codes for languages available for the specified voice in addition to its default language", with the default language being the one LanguageCode reports. Recorded behavior: the bilingual voices carry a specific default LanguageCode plus the additional code(s) for their other language, and a monolingual voice omits the key.
Emulator: for bilingual voices it reports a different default LanguageCode / LanguageName and a different additional-code list than the recording, and the same diacritic-spelled voices are still missing.
Why: the bilingual-voice contract (default language vs additional languages) is the rule a client uses to decide whether to pass LanguageCode to SynthesizeSpeech at all; with the pairing inverted the client omits a LanguageCode it needs or sends one the voice does not accept.
Fix: the bilingual entries of the voice seed in src/state.rs (LanguageCode + AdditionalLanguageCodes) and crate::state::reported_list's omit-when-empty behavior for the key.
Traces: polly-describe-voices-catalog#task#3.

No open issue covers the voice catalog's contents; the open polly issues concern SynthesizeSpeech, StartSpeechSynthesisTask and GetSpeechSynthesisTask.

## Evidence
All four steps answer HTTP 200 where the recording answers HTTP 200, so the divergence is entirely in the body.
Cause 1 (polly-catalog-describe-voices#task#1): per-voice diffs reported by the replay include SupportedEngines[0] value_mismatch (expected 'generative', got 'neural') on many voices; SupportedEngines[1] missing (expected 'neural', got None); SupportedEngines[2] extra (expected None, got 'long-form'); LanguageName value_mismatch (expected 'Swiss Standard German', got 'Swiss German'); whole-voice missing for the diacritic-spelled entries (e.g. $.Voices[Name="In\u00eas"] missing, with an ASCII $.Voices[Name="Ines"] present instead — likewise for the Andrés/Céline/Léa/Rémi/Vitória/Dóra/Penélope entries); whole-voice extra for voices the recording has no entry for; LanguageCode/LanguageName value_mismatch on individual voices.
Cause 2 (polly-describe-voices-catalog#task#1): $.Voices[0] value_mismatch — expected the Belgian-French voice record, got a US-English voice record, i.e. a different head of list.
Cause 3 (polly-describe-voices-catalog#task#2): $.Voices[Name="Tiffany"] missing (expected a full Voice record with SupportedEngines ['generative'], got None) alongside extra voices ($.Voices[Name="Kenneth"], $.Voices[Name="Tina"] present with no recorded counterpart), plus the same SupportedEngines reorderings.
Cause 4 (polly-describe-voices-catalog#task#3): the cause-1 engine/name/LanguageName diffs again, plus AdditionalLanguageCodes[0] and LanguageCode/LanguageName mismatches on bilingual voices and AdditionalLanguageCodes present where the recording has none.
Model facts used: smithy_query(operation="DescribeVoices") -> GET /v1/voices, 200, output Voices: VoiceList, errors InvalidNextTokenException(400)/ServiceFailureException(500); smithy_query(shape="Voice,Engine") -> Voice members Gender/Id/LanguageCode/LanguageName/Name/AdditionalLanguageCodes/SupportedEngines, Engine enum = [standard, neural, long-form, generative].
