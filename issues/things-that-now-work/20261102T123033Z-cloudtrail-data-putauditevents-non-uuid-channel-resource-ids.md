# cloudtrail-data PutAuditEvents: non-UUID channel resource ids resolve as valid ARNs (encoding changes the error class), and the operation is never authorized against the caller's IAM policy (2 causes)

Neither cause is a runner artifact: both verdicts come from the emulator's own responses.

=== Cause 1 of 2: a channel ARN whose resource suffix is not a channel id is treated as well-formed, so the SAME logical reference changes error class with its encoding ===
AWS: the resource segment of a channel ARN must be a channel id (the ARN suffix CloudTrail issued, a UUID). An arn:aws:cloudtrail:<region>:<account>:channel/<arbitrary-string> is refused by the service with error code InvalidChannelARN, HTTP 400, and the fixed message AWS words for that class — "The specified channel ARN is not a valid channel ARN." (the whole sentence is fixed text; nothing in it is request-derived). Crucially the classification does not depend on the ENCODING of that string: the multi-byte form (channel/café-<emoji>-not-real) and its plain-ASCII analogue of the same shape (channel/cafe-rocket-not-real) both take the invalid-ARN path. Smithy (services/service-com-amazonaws-cloudtraildata-cloudtraildataservice/smithy-model/com-amazonaws-cloudtraildata-cloudtraildataservice.json): PutAuditEventsRequest$channelArn is @required, httpQuery 'channelArn', constrained only to @pattern ^arn:.*$, so the model does not state the resource-id rule; InvalidChannelARN is a modelled error of the operation, errorKind client, httpError 400 (defaulted), and its shape doc is "The specified channel ARN is not a valid channel ARN." The same-class-for-both-encodings requirement is recorded behavior only (the check asserts the unicode form and its ASCII analogue must classify identically, with the unicode form InvalidChannelARN).
Emulator: the two encodings take DIFFERENT paths. The unicode form is refused InvalidChannelARN (correct code and message — those assertions passed), because state.rs::is_channel_id (lines 68-74) rejects any non-ASCII char; the ASCII analogue 'cafe-rocket-not-real' satisfies is_channel_id (any non-empty string of [-_A-Za-z0-9] up to 128 chars), so parse_channel_arn (lines 94-117) accepts it as a well-formed channel ARN and the request falls through to resolution, which answers ChannelNotFound/400. Observed: code 'InvalidChannelARN' for the unicode ARN vs code 'ChannelNotFound' for the ASCII ARN, for the same nonexistent resource id written two ways.
Why: a client's error handling flips purely with the character encoding of a value it passed through unchanged — the same reference is 'malformed ARN' in one encoding and 'absent channel' in the other, so a caller cannot tell a syntax error from a missing resource, and any arbitrary non-id string is reported as an absent channel (making the emulator answer resolution questions for references AWS never accepts). It also means a client that encodes the id differently gets a different retry/repair decision.
Fix: the resource-suffix check in services/service-com-amazonaws-cloudtraildata-cloudtraildataservice/src/state.rs (is_channel_id / parse_channel_arn) must be tightened to the channel-id form CloudTrail actually issues, so both encodings of a non-id suffix take the single InvalidChannelARN path in the handler's parse_channel_ref miss branch.
Traces: cloudtrail-data.channel-arn-unicode-characters-rejected.

=== Cause 2 of 2: PutAuditEvents is never authorized against the caller's IAM policy, so an unentitled principal is answered the resolution verdict instead of AccessDeniedException/403 ===
AWS: PutAuditEvents is authorized under the `cloudtrail-data:` IAM action prefix, which is disjoint from `cloudtrail:`. A principal that does not hold cloudtrail-data:PutAuditEvents is refused by the authorization layer ahead of the service with error code AccessDeniedException and HTTP 403, BEFORE channel resolution, so the response says nothing about whether the channel exists and carries neither `successful` nor `failed`. A principal that does hold it passes authorization and is refused by resolution instead: ChannelNotFound, HTTP 400, message "The channel <channelArn> could not be found." (fixed text around one request-derived slot, the channelArn the caller sent). The denial message for the 403 class is AWS's standard identity-based template, whose fixed text is "User: <principal-arn> is not authorized to perform: cloudtrail-data:PutAuditEvents on resource: <resource-arn> because no identity-based policy allows the cloudtrail-data:PutAuditEvents action" — the principal ARN (the assumed-role session ARN from the request's credentials) and the resource ARN (the channelArn from the request) are the only variable parts; the action string is fixed and MUST carry the cloudtrail-data: prefix, not cloudtrail:. Smithy: PutAuditEvents declares errors ChannelInsufficientPermission, ChannelNotFound, ChannelUnsupportedSchema, DuplicatedAuditEventId, InvalidChannelARN, UnsupportedOperationException — and no AccessDeniedException, confirming the denial belongs to the authorization layer in front of the operation; the 403/AccessDeniedException pairing itself is recorded behavior only.
Emulator: the verdict does not depend on the caller at all. The check holds the channel ARN (in the caller's own account), the region, the account and the single-event batch byte-identical across five arms and varies ONLY the assumed role's inline policy; after replacing the policy with one that grants only cloudtrail:* on * (arm 2), and then only cloudtrail:PutAuditEvents on * (arm 4), it polls PutAuditEvents for AccessDeniedException and the emulator keeps answering the resolution-layer verdict (ChannelNotFound/400, as every other cloudtrail-data check in this replay shows for a same-account absent channel), so the expected 403 never arrives and the check is killed — reported verdict 'Check timed out after 60.0s'. Hypothesis: the non-converging arm is arm 2, the first arm that needs an authorization verdict (arms 0 and 1 only need ChannelNotFound/400, which the handler already produces); the only alternative stall point, sts:AssumeRole on the freshly created role never succeeding inside the check's bounded retry, would equally be an emulator-side gap. Either way no 403 is produced for a principal lacking the action.
Why: a client cannot distinguish 'you may not call this' from 'the channel is not there' — it gets a 400 request-shape class where AWS gives a 403 authorization class, so permission handling, credential-vs-policy triage and retry classification are all wrong. Least-privilege policies cannot be validated against the emulator: a role holding only cloudtrail:*, or the right action name under the wrong cloudtrail: prefix, is silently treated as entitled, and the emulator stays an existence oracle for callers AWS would refuse before resolution.
Fix: an authorization gate in the PutAuditEvents handler (services/service-com-amazonaws-cloudtraildata-cloudtraildataservice/src/ops/put_audit_events.rs) that evaluates the signing principal's effective policy for the action cloudtrail-data:PutAuditEvents on the parsed channel ARN and returns AccessDeniedException/403 with no `successful`/`failed` member, running BEFORE ARN resolution and before the existing post-resolution owner-account check. The action namespace must be matched on the full cloudtrail-data: prefix, never on the operation name alone.
Traces: cloudtrail-data.put-audit-events-requires-the-cloudtrail-data-action-not-cloudtrail-wildcard.
