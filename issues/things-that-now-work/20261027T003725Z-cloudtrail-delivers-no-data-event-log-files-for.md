# CloudTrail delivers no data-event log files for Cognito identity-pool data operations: an accepted eventCategory=Data / resources.type=AWS::Cognito::IdentityPool advanced selector produces nothing in the trail bucket (1 cause)

> _Note: this issue was identified against the code base at commit `64e3d31da0f219acb3f0523749fc49dddb7bfb57`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutEventSelectors

## Description
ONE net-new root cause in this issue; it must be closed before submitting.

Cause 1 of 1: a trail whose advanced event selector names the Cognito identity-pool data-event class accepts and echoes the selector, reports IsLogging=true, and then never delivers a single log file, so the five identity-pool DATA operations are unauditable.

AWS: PutEventSelectors accepts AdvancedEventSelectors and echoes them back (Smithy: PutEventSelectors, input TrailName (required) + EventSelectors/AdvancedEventSelectors, output TrailARN/EventSelectors/AdvancedEventSelectors; errors InvalidEventSelectorsException 400 / InvalidTrailNameException 400 / TrailNotFoundException 404 / UnsupportedOperationException 400). StartLogging has an empty output and GetTrailStatus then reports IsLogging=true (Smithy: GetTrailStatus output IsLogging plus the LatestDelivery*/LatestDigestDelivery* members that describe delivery). What the selector then CAUSES is recorded behavior only (measured by the check against real AWS, us-west-2, 2026-10-01, and quoted in the check header): with a selector of {Field: eventCategory, Equals: ["Data"]} and {Field: resources.type, Equals: ["AWS::Cognito::IdentityPool"]}, CloudTrail writes gzipped objects (gzip magic 0x1f 0x8b, body a JSON object with a Records list) under the documented key layout AWSLogs/<account>/CloudTrail/<region>/YYYY/MM/DD/, and each of GetId, GetOpenIdToken, GetCredentialsForIdentity, UnlinkIdentity and GetOpenIdTokenForDeveloperIdentity appears there as exactly ONE record joined to its caller by requestID == that call's ResponseMetadata.RequestId, with eventSource "cognito-identity.amazonaws.com", managementEvent false, eventCategory "Data", resources[0] of type AWS::Cognito::IdentityPool whose ARN is the pool, requestParameters.logins keyed by the presented provider with every value the fixed literal HIDDEN_DUE_TO_SECURITY_REASONS, userIdentity exactly {"type": "Unknown"} for the four unsigned calls and an AssumedRole identity with sessionContext.sessionIssuer {type: "Role", arn: <the assumed role>} for the signed one. Delivery was measured at about 5 minutes (the documented "average of about 5 minutes"), with a selector activation lag between 10 s and 11 min; the recording states no bound.

Emulator: the setup legs are accepted — the bucket, the trail, PutEventSelectors (its echo assertion is before the wait and did not fire), StartLogging and GetTrailStatus(IsLogging=true) all pass — and then nothing is ever delivered. The check issues a fresh round of all five operations every 60 s and re-lists the trail prefix every 20 s under a 1260 s delivery budget; it is still inside that loop when the harness's 60 s cap kills it, so the verdict is "mismatch", detail "Check timed out after 60.0s", and it never reaches a single per-record assertion. The check carries the suite's DATAPLANE_UNIMPLEMENTED marker for exactly this case ("no round of the five identity-pool data operations was delivered in full"). Hypothesis (neither the model nor the replay says which): the refusal could instead be inside one of the bounded retry loops of a round — GetCredentialsForIdentity retried on InvalidIdentityPoolConfigurationException (90 s) or GetOpenIdTokenForDeveloperIdentity retried on AccessDeniedException/NotAuthorizedException (90 s) — both of which also exceed the cap; the delivery gap is certain regardless, because no trail in this emulator writes any S3 object at all.

Neighbouring OPEN issues, named because they do not cover this check: 20261024T114720Z-cloudtrail-event-history-is-empty-for-everything-but.md has a Cause 2 for "a logging trail never delivers a log file to its S3 bucket", but its replay set names only cloudtrail.trail-delivers-a-gzipped-log-file-to-the-documented-s3-key-layout (management events, basic event selectors) and nothing about the DATA class or advanced selectors; 20261026T234020Z-cognito-identity-4-net-new-root-causes-web.md Cause 2 covers the opposite error on the other half of the split (identity data calls wrongly INDEXED as management events in LookupEvents) and owns cognito-identity.* checks, not this one. Neither carries this check's key, and this check's absence leg (none of the five in LookupEvents) can only be graded once delivery proves they are data events.

Why: a client that configures the advanced event selector AWS publishes for identity pools gets a trail that looks healthy — the selector round-trips byte-identically and GetTrailStatus says it is logging — while the entire data-event audit trail is empty. Every detective control over identity-pool data access (who exchanged a token, which identity got credentials, proof that the live ID token / minted OpenID token / vended secret key were redacted and never persisted, SIEM or Athena ingestion over the log prefix) reads an empty prefix and cannot tell "nothing happened" from "nothing is recorded". The management/data split is also unobservable: without delivery there is no evidence these calls are data events at all.

Fix: CloudTrail trail log-file delivery and its event-selector evaluation — the trail's logging state must evaluate stored AdvancedEventSelectors against each served call (including the DATA class, matching on eventCategory and resources.type) and write the matching records as gzipped objects into the configured S3 bucket under AWSLogs/<account>/CloudTrail/<region>/YYYY/MM/DD/, with each record populated per operation (eventSource, eventName, requestID equal to the caller's request id, managementEvent false, eventCategory "Data", resources[0] type/ARN, the HIDDEN_DUE_TO_SECURITY_REASONS redaction of sensitive request/response members, and userIdentity derived from the signing principal or {"type": "Unknown"} when the request is unsigned); the cognito-identity operation handlers must feed that seam for the five identity-pool data operations.
