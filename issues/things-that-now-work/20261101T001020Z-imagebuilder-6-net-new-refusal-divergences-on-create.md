# imagebuilder: 6 net-new refusal divergences on create paths — wrong error class, emulator-authored messages, and an instance profile that is never validated

> _Note: this issue was identified against the code base at commit `e3579db6a1835cfcd1e7033eb2fb9f64dc458cca`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateComponent

## Description
SIX independent root causes in the imagebuilder emulator's create/refusal paths. All six must be closed before this issue is submitted; each is numbered with its own failing check ids.

Cause 1 of 6: a semanticVersion node outside the documented bound is refused InvalidVersionNumberException instead of InvalidParameterValueException.
AWS: Smithy: CreateComponentRequest.semanticVersion is required with @pattern ^[0-9]+\.[0-9]+\.[0-9]+$ and CreateImageRecipeRequest.semanticVersion with ^(?:[0-9]+|x)\.(?:[0-9]+|x)\.(?:[0-9]+|x)$, so a value like 9999999999.0.0 satisfies the model and the refusal is a service-side bound (each node must be <= 2^30-1). InvalidParameterValueException is a client error with @httpError 400 ("The value that you provided for the specified parameter is invalid."); InvalidVersionNumberException (also 400, "Your version number is out of bounds or does not follow the required syntax.") is modeled for both operations but is NOT what AWS returns here — recorded behavior is InvalidParameterValueException. Recorded message for CreateComponent: "The value supplied for parameter 'semanticVersion' is not valid. The supplied semantic version does not follow the required format."; for CreateImageRecipe the same sentence plus " Only one 'x' wildcard is allowed per version.". Fixed text: "The value supplied for parameter '", "' is not valid. The supplied semantic version does not follow the required format." (+ the wildcard sentence on the recipe path); the only variable part is the member name (semanticVersion).
Emulator: both handlers answer Code 'InvalidVersionNumberException' (create_component.rs lines 291-302 and the equivalent branch in create_image_recipe.rs call crate::state::invalid_version_number_message(..)), so the error class a client branches on is wrong.
Why: a client that catches InvalidParameterValueException to report "bad parameter" to its user, or that treats InvalidVersionNumberException as a distinct retriable/version-bump condition, takes the wrong branch; the message text does not match AWS either.
Traces: imagebuilder.create-component-invalid-semantic-version-rejected, imagebuilder.create-image-recipe-invalid-semantic-version-rejected.

Cause 2 of 6: CreateComponent's already-exists refusal under contention uses ResourceInUseException where AWS uses ResourceAlreadyExistsException.
AWS: Smithy: ResourceAlreadyExistsException is a client error with @httpError 400 ("The resource that you are trying to create already exists."); CreateComponent's modeled error list does not include it (it lists ResourceInUseException 400 instead), so the class AWS actually returns for a losing racer is recorded behavior only: N concurrent CreateComponent calls for the SAME name+semanticVersion with identical content and distinct clientTokens leave at least one winner, and every loser is refused ResourceAlreadyExistsException.
Emulator: the already-exists branch in services/service-com-amazonaws-imagebuilder-imagebuilder/src/ops/create_component.rs lines 378-389 deliberately returns ResourceInUseException (its comment states it does so because the operation declares no ResourceAlreadyExistsException). With 6 racers, 5 were refused 'ResourceInUseException' and 1 succeeded.
Why: client code (and Terraform/CDK-style convergence loops) treats ResourceAlreadyExistsException as "already there, adopt it" and ResourceInUseException as "busy, retry later"; the emulator's class turns a settled race into an endless retry.
Traces: imagebuilder.concurrent-create-component-same-name-version-contention.

Cause 3 of 6: the idempotent-parameter-mismatch message is emulator-authored.
AWS: Smithy: IdempotentParameterMismatchException is a client error with @httpError 400, documented "You have specified a client token for an operation using parameter values that differ from a previous request that used the same client token." The recorded message for replaying CreateComponent with the same clientToken and different parameters is the fixed sentence "The request parameters do not match those in the original idempotent request." — it has no variable parts.
Emulator: the correct class is returned, but with the invented sentence "The clientToken was already used for a request with different parameter values." (crate::state::idempotent_parameter_mismatch_message(), used by create_component.rs lines 352-361 and by create_infrastructure_configuration.rs lines 328-337, so every create path carries it).
Why: the error message is part of the contract a caller logs, matches on and shows to a user; a reworded sentence breaks text assertions and user-facing output.
Traces: imagebuilder.create-component-idempotent-mismatch-rejected.

Cause 4 of 6: CreateInfrastructureConfiguration's duplicate-name message is emulator-authored.
AWS: Smithy: CreateInfrastructureConfiguration models ResourceAlreadyExistsException (client, @httpError 400, "The resource that you are trying to create already exists."). The recorded message for a name that already exists in the Region is the fixed sentence "The resource already exists." — no variable parts; AWS does not name the resource in it.
Emulator: the right class with the invented, name-interpolated sentence "An infrastructure configuration named <name> already exists in this Amazon Web Services Region." (crate::state::infrastructure_configuration_exists_message(&input.name) at create_infrastructure_configuration.rs lines 349-360).
Why: callers that assert on or display AWS's refusal text get a sentence AWS never emits, and the leaked resource name changes the message shape.
Traces: imagebuilder.create-infrastructure-configuration-duplicate-name-rejected.

Cause 5 of 6: CreateInfrastructureConfiguration ACCEPTS an instanceProfileName that does not exist.
AWS: Smithy: instanceProfileName is required, length 1..256, @pattern ^[\w+=,.@-]+$ — a well-formed but absent profile satisfies the model, so the existence check is service-side. AWS refuses it 400 InvalidParameterValueException with the message "Invalid parameter value for instanceProfileName: The provided instance profile does not exist. Please specify a different instance profile and try again." — fixed text apart from the member name (instanceProfileName) taken from the request. Nothing is created: a subsequent ListInfrastructureConfigurations filtered by that name returns an empty summary list.
Emulator: the call succeeds with HTTP 200 and mints an infrastructureConfigurationArn for the configuration; create_infrastructure_configuration.rs never consults IAM for the profile, so the refusal does not exist at all.
Why: an emulator that accepts a configuration referencing a nonexistent instance profile lets a broken pipeline be built and only fails much later (at image build time, or never), so tests that assert their IAM wiring is correct pass against the emulator and fail against AWS.
Traces: imagebuilder.create-infrastructure-configuration-invalid-instance-profile-rejected.

Cause 6 of 6: SendWorkflowStepAction's stepExecutionId refusal comes out of the generic constraint validator as ValidationException instead of Image Builder's InvalidParameterValueException.
AWS: Smithy: SendWorkflowStepActionRequest.stepExecutionId is required with @pattern ^step-[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$, and the operation models InvalidParameterValueException (client, @httpError 400). The recorded refusal is 400 InvalidParameterValueException with "The value supplied for parameter 'stepExecutionId' is not valid. stepExecutionId must match pattern ^step-[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$" — fixed text "The value supplied for parameter '", "' is not valid. ", " must match pattern "; variable parts are the member name (twice) and the service-side pattern for that member.
Emulator: the centralized request walk refuses the pattern before the handler runs and answers the unmodeled, generic Code 'ValidationException', so the Image Builder error the operation models is never emitted. This is the same mechanism as the open issue 20261031T221631Z-ec2-iam-imagebuilder-image-builder-createimagepipeline-refuses-imagetestsconfiguration-timeoutminutes-above-the.md, which is bound to CreateImagePipeline.imageTestsConfiguration.timeoutMinutes and does not cover this operation/member.
Why: clients branch on the modeled error shape and on x-amzn-errortype; a generic ValidationException is in no SDK's imagebuilder error union, so handlers keyed on InvalidParameterValueException are dead code and the message text diverges too.
Fix (all causes): the imagebuilder operation handlers and their pre-handler validation — services/service-com-amazonaws-imagebuilder-imagebuilder/src/ops/create_component.rs (version bound, already-exists class, idempotency message), create_image_recipe.rs (version bound), create_infrastructure_configuration.rs (duplicate-name message, missing instance-profile check against IAM state), send_workflow_step_action.rs plus the per-member refusal path that currently defers to the generic constraint validator — and the shared message builders in src/state.rs.
Traces: imagebuilder.send-workflow-step-action-nonexistent-step-rejected.
