# kinesis: 3 net-new root causes — UpdateStreamRecordDistributionStrategy is an unimplemented 501 scaffold, DescribeStreamSummary never reports RecordDistributionStrategy, and AUTO distribution is not honoured by the PutRecord shard-routing path

> _Note: this issue was identified against the code base at commit `58d3cdd8a54717975c7a5e45d2c60ee5b89f816e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateStreamRecordDistributionStrategy

## Description
The record-distribution-strategy feature of Kinesis Data Streams is entirely absent from the emulator: the control operation that sets it is still a scaffold, the setting is not part of stream state so it never appears in DescribeStreamSummary, and the write path has no AUTO mode. Three behavioral checks cover it and none of them can get past the first call. Three distinct causes, each needing its own fix; a fixer that closes only the first will leave the other two checks failing.

NOTE ON THE REPLAY SIGNAL (read before re-replaying): all three checks die in the harness's own SDK client, not on an emulator response — `AttributeError: 'Kinesis' object has no attribute 'update_stream_record_distribution_strategy'` raised in botocore `client.py` line 973. The request is therefore never sent, which is why the suite's unimplemented-stub detector did NOT auto-file this operation the way it did for PutResourcePolicy/GetResourcePolicy/UntagResource. The emulator-side gap is nevertheless real and is visible directly in the checkout (see Cause 1). Sibling checks in this suite that exercise equally new kinesis operations reach the emulator by going through the harness's raw client (`_raw_client(ctx, "kinesis")`, e.g. kinesis.update-max-record-size-out-of-range-fails calling `raw.update_max_record_size`), so re-replay of these three checks may continue to raise the AttributeError until they are routed through the raw client too; verify the fix against the raw client / a hand-signed request.

=== Cause 1 of 3: UpdateStreamRecordDistributionStrategy answers 501 NotImplemented ===
AWS: Smithy (services/service-com-amazonaws-kinesis-kinesis-20131202/smithy-model/com-amazonaws-kinesis-kinesis-20131202.json) binds UpdateStreamRecordDistributionStrategy. Input: `StreamARN` required, @length 1..2048, @pattern ^arn:aws.*:kinesis:.*:\d{12}:stream/\S+$; `RecordDistributionStrategy` required, enum RecordDistributionStrategy = AUTO | USER_PARTITION_KEY; `StreamId` optional (@length 1..24, @pattern ^[a-z0-9]{20}-[a-z0-9]{3}$, modelled "Not Implemented. Reserved for future use."). Output shape is `Unit` — a success is HTTP 200 with an empty body. Modelled errors, all HTTP 400: AccessDeniedException, InvalidArgumentException, LimitExceededException, ResourceInUseException, ResourceNotFoundException, ValidationException. The operation doc states the setting is a stream-level setting switchable at any time with immediate effect, supported ONLY on on-demand streams.
  Not-found refusal: recorded behavior — the ResourceNotFoundException for a never-created stream ARN carries code `ResourceNotFoundException` at HTTP 400 and message `Stream <streamName> under account <accountId> not found.` The fixed text is `Stream `, ` under account `, ` not found.`; `<streamName>` is the stream name taken from the request's StreamARN (the segment after `stream/`) and `<accountId>` is the 12-digit account from the request's credentials/ARN. Never emit one run's literal name or account.
Emulator: services/service-com-amazonaws-kinesis-kinesis-20131202/src/ops/update_stream_record_distribution_strategy.rs still carries the `//! SCAFFOLDED, NOT IMPLEMENTED` marker and its `handle` body is `Err(crate::scaffolded::Scaffolded::not_implemented("UpdateStreamRecordDistributionStrategy"))`, i.e. HTTP 501 `NotImplemented` for every request — a status and code the model does not declare for this operation. Nothing in the handler reads or writes stream state.
Why: a client cannot set or change the distribution strategy at all. A caller gets a 501 with an unmodelled error code, which no SDK retry/error-handling path classifies: it is neither a throttle, nor a validation failure, nor a not-found, so application code that branches on the modelled errors mis-handles it, and the documented "switch strategy with no downtime" workflow is impossible.
Fix: the operation's handler (and its validation) in services/service-com-amazonaws-kinesis-kinesis-20131202/src/ops/update_stream_record_distribution_strategy.rs — resolve StreamARN against stream state, refuse an unknown stream with ResourceNotFoundException and the message template above, and on success return the empty 200 Unit output and persist the new strategy; then delete the SCAFFOLDED marker line.
Traces: kinesis.update-stream-record-distribution-strategy-nonexistent-stream-rejected (asserts the ResourceNotFoundException code and message, plus a 200 positive control on a real on-demand stream); all three checks below also stop here.

=== Cause 2 of 3: the strategy is not stream state — DescribeStreamSummary never reports RecordDistributionStrategy, and the provisioned-mode refusal does not exist ===
AWS: recorded behavior — DescribeStreamSummary's StreamDescriptionSummary reports `RecordDistributionStrategy` with the value `USER_PARTITION_KEY` on a freshly created ON_DEMAND stream (the documented default), reports the new value after a successful UpdateStreamRecordDistributionStrategy (both AUTO and back to USER_PARTITION_KEY round-trip), and OMITS the member entirely for a provisioned stream, which does not support the setting. Setting AUTO on a provisioned stream is refused and leaves the member still absent; the refusal recorded is code `ValidationException` at HTTP 400 with message `Request is invalid. Stream <streamName> under account <accountId> is in Provisioned mode.` — fixed text `Request is invalid. Stream `, ` under account `, ` is in Provisioned mode.`, with `<streamName>` from the request's StreamARN and `<accountId>` the request's 12-digit account. Model-vs-recording discrepancy to preserve as recorded: the operation's own prose says "Attempting to set AUTO on a provisioned stream results in an InvalidArgumentException", and the model's ValidationException doc is inverted ("you tried to invoke this API for a data stream with the on-demand capacity mode"), but the recorded refusal is ValidationException with the message above — implement the recording.
Emulator: the setting is absent from the service's stream state, so DescribeStreamSummary emits no RecordDistributionStrategy member for on-demand streams (the same state/serializer gap this suite already shows for MaxRecordSizeInKiB, which raises KeyError: 'MaxRecordSizeInKiB' in kinesis.update-max-record-size-out-of-range-fails), and there is no capacity-mode guard to produce the Provisioned-mode refusal — the 501 of Cause 1 is returned for a provisioned stream exactly as for an on-demand one.
Why: a client cannot read back which strategy a stream is using, so it cannot confirm a switch took effect or discover the default, and it cannot distinguish "this stream does not support the setting" (provisioned) from "the setting is at its default". Code that polls DescribeStreamSummary for the new value hangs or KeyErrors instead of converging.
Fix: the stream state (services/service-com-amazonaws-kinesis-kinesis-20131202/src/state.rs) must carry the per-stream strategy, defaulted to USER_PARTITION_KEY for ON_DEMAND streams and unset for provisioned ones; DescribeStreamSummary's handler/serializer must emit the member only when set; the capacity-mode check and its ValidationException message belong in the UpdateStreamRecordDistributionStrategy handler's validation.
Traces: kinesis.update-stream-record-distribution-strategy-requires-on-demand; kinesis.update-stream-record-distribution-strategy-nonexistent-stream-rejected.

=== Cause 3 of 3: the PutRecord/PutRecords shard-routing path has no AUTO mode ===
AWS: Smithy doc for UpdateStreamRecordDistributionStrategy — under AUTO, "Amazon Kinesis Data Streams distributes records evenly across shards using service-managed algorithms, and ignores any partition key and ExplicitHashKey that a producer provides"; under USER_PARTITION_KEY, "Amazon Kinesis Data Streams uses the partition key to determine shard placement. Records that share a partition key are sent to the same shard" (the default). "New records that arrive after the change are distributed according to the new strategy. Records already in the stream keep their original shard assignments and are not redistributed." Recorded behavior: under USER_PARTITION_KEY every PutRecord for one partition key returns the ShardId of the single open shard whose HashKeyRange contains the 128-bit MD5 of that key; after switching to AUTO, repeated PutRecord calls carrying that same key return at least two distinct ShardIds; records written before the switch are still read back from, and only from, the shard PutRecord assigned them; after switching back, a run of consecutive PutRecord calls for the key again all return the MD5-owning shard.
Emulator: the strategy does not exist in state (Cause 2), so the write path can only ever do MD5-of-partition-key routing — AUTO is unreachable and a producer's PartitionKey/ExplicitHashKey is always honoured.
Why: a stateless producer that opts into AUTO to spread a hot partition key across shards silently keeps hot-spotting onto one shard, so throughput and per-shard quota behavior observed against the emulator do not match AWS, and a consumer written against AUTO's "no per-key ordering" contract is validated by the emulator under the wrong distribution.
Fix: the shard-selection step of the PutRecord/PutRecords handlers must branch on the stream's stored strategy — AUTO ignores PartitionKey and ExplicitHashKey and spreads across open shards; the switch must affect new writes only and must not relocate already-stored records.
Traces: kinesis.update-stream-record-distribution-strategy-auto-ignores-partition-key.
