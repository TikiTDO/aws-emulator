# CloudTrail records no iam.amazonaws.com GetUser event (nor its own DescribeTrails) in any region, so a failed IAM read is never audited with errorCode NoSuchEntityException

> _Note: this issue was identified against the code base at commit `87a15e696e25e083bfb6cdeb9d5ca1a3533a6381`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
LookupEvents

## Description
Cause 1 of 1: CloudTrail event history contains no management record for IAM read calls (iam:GetUser) in the partition leader region, and no record for CloudTrail's own read (cloudtrail:DescribeTrails) in a non-leader region, so none of the audit-record fields that distinguish a failed call from a successful one can ever be observed. Failing check id: cloudtrail__iam.obs-iam-1-absent-user-get-is-audited-as-no-such-entity-exception.

AWS: iam:GetUser for a name that does not exist is ACCEPTED and then fails. Smithy (service-com-amazonaws-iam-awsidentitymanagementv20100508): GetUser errors = NoSuchEntityException, errorKind client, httpError 404, awsQueryError {code: NoSuchEntity, httpResponseCode: 404}; so the SDK/wire error code is `NoSuchEntity` while the exception SHAPE name is `NoSuchEntityException`. Recorded behavior (measured on real AWS, us-west-2 caller reading the us-east-1 record): within ~140s CloudTrail LookupEvents in the partition leader region us-east-1 returns an event with EventName=GetUser whose CloudTrailEvent JSON carries eventSource "iam.amazonaws.com", awsRegion "us-east-1", readOnly true, requestID equal to the SDK request id of that call, requestParameters {"userName": <the name from the request>} (populated, because the call was accepted and failed rather than refused by authorization), responseElements null, errorCode exactly "NoSuchEntityException" (the shape name, NOT the wire code `NoSuchEntity`) and errorMessage exactly the SDK's message. That message's fixed text is "The user with name " ... " cannot be found." with the single variable part being the UserName taken from the request; it must be byte-identical in the audit record and in the SDK error. The SAME operation on a user that DOES exist is audited with no errorCode and no errorMessage key at all and requestParameters {"userName": <existing name>}. A read in a non-leader region (cloudtrail:DescribeTrails in the caller's own region) is filed under that region: awsRegion is the caller's region and requestParameters is {"trailNameList": [<the token from the request>]}.

Emulator: nothing is ever indexed. The check creates a user, issues one GetUser that fails and one that succeeds, issues one DescribeTrails in a second region, then pages LookupEvents to exhaustion in a loop (EventName=GetUser in us-east-1, EventName=DescribeTrails in the second region) over a window that starts 2 minutes before the calls and ends 5 minutes after. Every page comes back with an empty Events list; failed_rec, control_rec and regional_rec all stay None and the poll loop runs until the harness cuts it off — replay verdict `mismatch`, detail `Error: Check timed out after 60.0s`. Because no record is ever produced, the assertions on errorCode/errorMessage/requestParameters/responseElements/readOnly/requestID are never even reached.

Why: a client that relies on CloudTrail to audit IAM activity sees an empty history. Failed IAM reads are invisible, so the documented distinction between the wire error code (`NoSuchEntity`) and the audited errorCode (`NoSuchEntityException`) cannot be honoured; nothing joins an SDK request id back to an audit record; and a read in a non-leader region is not filed under its own region. Compliance tooling, incident forensics and any automation that polls LookupEvents to confirm an action happened will hang or conclude the call never occurred. Note this is a target that "audits only successes" — it in fact audits nothing: even the successful GetUser control and CloudTrail's own DescribeTrails are missing.

Fix: CloudTrail's event-recording/ingestion path and its LookupEvents query state (the emulator's CloudTrail service state plus the cross-service hook that emits a management event for every served operation). It needs to (a) emit a management event for every served call, including read-only ones and ones that fail after acceptance, (b) file global IAM (iam.amazonaws.com) events in the partition leader region us-east-1 and all other services' events in the region that served them, (c) populate the record from the request and the served response: readOnly from the operation's classification, requestParameters from the request members (lowerCamelCase member names), responseElements null on failure, requestID from the response's request id, and (d) set errorCode to the modeled exception SHAPE name while the wire keeps the awsQueryError code, with errorMessage copied verbatim from the error the caller received. Related open issues cover adjacent symptoms of the same missing recorder but not this check: 20261024T114720Z-cloudtrail-event-history-is-empty-for-everything-but.md, 20261025T121312Z-cloudtrail-lookupevents-records-no-iam-management-event-so.md (CreateAccessKey/CreateLoginProfile secret omission) and 20261029T173328Z-cloudtrail-records-and-delivers-no-audit-record-for.md.

## Evidence
Expected (real AWS, measured): LookupEvents in us-east-1 with LookupAttributes=[{AttributeKey: EventName, AttributeValue: GetUser}] over a window around the call returns, within ~140s, two events — one for the failed GetUser with CloudTrailEvent fields {eventSource: "iam.amazonaws.com", awsRegion: "us-east-1", readOnly: true, requestID: <SDK request id>, requestParameters: {"userName": <absent name>}, responseElements: null, errorCode: "NoSuchEntityException", errorMessage: "The user with name <absent name> cannot be found."} and one for the successful GetUser with no errorCode/errorMessage key and requestParameters {"userName": <existing name>}; plus, in the caller's own (non-leader) region, a DescribeTrails event with awsRegion = that region and requestParameters {"trailNameList": [<token>]}. The wire error for the failed call is code `NoSuchEntity` / HTTP 404 (Smithy GetUser -> NoSuchEntityException, awsQueryError code NoSuchEntity, httpResponseCode 404) — i.e. the audited errorCode is deliberately NOT the wire code.

Actual (emulator): every LookupEvents page returns an empty Events list for both EventName=GetUser in us-east-1 and EventName=DescribeTrails in the second region. No record is produced for the failed call, for the successful control, or for CloudTrail's own read. The check's bounded poll loop never satisfies its three preconditions and the replay ends as `mismatch` with `Error: Check timed out after 60.0s`; the first assertion it would have reached is the DATAPLANE_UNIMPLEMENTED guard "CloudTrail in us-east-1 produced no audit record for the FAILED iam:GetUser".
