# CodeBuild: ListSharedReportGroups leaks the owner's own report group, and a CFN-deployed AWS::CodeBuild::ReportGroup is unaddressable by PutResourcePolicy (2 causes)

> _Note: this issue was identified against the code base at commit `3b8e580b43dad03fd4ed613a27e30f57a2ae4b6e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListSharedReportGroups

## Description
TWO distinct net-new root causes in the CodeBuild service crate services/service-com-amazonaws-codebuild-codebuild-20161006 (plus its CloudFormation resource provider for Cause 2). Both must be closed before this issue is resolved. Every check the replay report marked ALREADY FILED or OWNED is excluded from this issue; the two checks below carry no replay key on any open issue.

Cause 1 of 2: ListSharedReportGroups reports a report group merely because it has a resource policy attached, so the OWNING account sees its own report group in its own shared listing.
AWS: Smithy ListSharedReportGroups() -> { reportGroups: ReportGroupArns (@length 1..100), nextToken }, sole modeled error InvalidInputException (client, httpError 400). The model documents the output member as "The list of ARNs for the report groups shared WITH the current Amazon Web Services account or user", and sortBy as "The criterion to be used to list report groups shared with the current Amazon Web Services account or user". Report-group sharing is one-directional: an account must own a report group to share it, and a report group shared with you cannot be re-shared, so the consumer side is what this listing reports. An owner that attaches a resource policy to its OWN report group (even one naming its own root principal) therefore gets that ARN back from GetResourcePolicy but must NOT see it in its own ListSharedReportGroups result; with nothing shared with the caller the response carries an empty reportGroups list.
Emulator: ListSharedReportGroups returns the account's own report groups filtered only by "a resource policy exists for this ARN" — services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/list_shared_report_groups.rs builds its candidate set from guard.report_groups filtered by guard.resource_policies.contains_key(arn), with no notion of which account owns the group or which principal it is shared with. The replay shows the ARN the test account created and policied coming straight back in reportGroups.
Why: a client uses ListSharedReportGroups to enumerate resources it has been GRANTED access to by other accounts. The emulator turns it into "every report group I own that has any policy", so consumer-side inventory, cross-account onboarding flows and any "is this resource foreign?" branch are all wrong, and simply calling PutResourcePolicy on an owned group corrupts the listing. The direction of the sharing relationship is unobservable.
Fix: the ownership/direction predicate in the ListSharedReportGroups handler (services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/list_shared_report_groups.rs, the filter_map at the top of handle), which must report only report groups owned by another account and shared with the caller — i.e. exclude every group the calling account owns, instead of equating "has a resource policy" with "is shared with me". The sibling listing it cites, src/ops/list_shared_projects.rs, is built the same way and should be checked for the same defect while this is fixed. Related open issue 20261025T014438Z-codebuild-8-further-divergences-getresourcepolicy-updatewebhook-deletebuildbatch-stubs.md lists this check only against its Cause 2 (GetResourcePolicy answering NotImplemented); that part now works — the baseline ResourceNotFoundException and the PutResourcePolicy/GetResourcePolicy round trip both pass — and the check now fails further on, at the sharing listing, which that issue does not describe.
Traces: codebuild.resource-policy-sharing-not-listed-for-owner.

Cause 2 of 2: a report group provisioned by CloudFormation does not exist in CodeBuild, so PutResourcePolicy against it is refused instead of validating the policy document.
AWS: Smithy PutResourcePolicy(policy @required NonEmptyString @length min 1, resourceArn @required NonEmptyString @length min 1) -> { resourceArn }; modeled errors InvalidInputException and ResourceNotFoundException (both client, httpError 400). Once a stack containing AWS::CodeBuild::ReportGroup reaches CREATE_COMPLETE the report group exists in CodeBuild and arn:aws:codebuild:<region>:<account>:report-group/<name> is addressable: PutResourcePolicy with a syntactically malformed policy body is then refused with 400 InvalidInputException and message "Problem parsing given policy" (fixed text; no request values interpolated), nothing is attached (GetResourcePolicy answers 400 ResourceNotFoundException, message "Resource ARN resource policy does not exist"), and a well-formed policy on the same ARN succeeds and round-trips.
Emulator: the stack reaches CREATE_COMPLETE, but PutResourcePolicy on the stack's declared report-group ARN answers ResourceNotFoundException with message "Report group does not exist" — the existence check fails because the CFN-declared report group was never materialized in CodeBuild state, so the policy-parsing branch (InvalidInputException / "Problem parsing given policy") is never reached and the whole malformed-vs-well-formed distinction is unobservable.
Why: a caller is told provisioning succeeded and then cannot address what it provisioned; CFN-managed report groups and every resource policy or report hung off them are unusable, and a client that distinguishes "bad policy document" from "resource absent" misclassifies the failure and retries creation instead of fixing its policy.
Fix: the CloudFormation resource provider for AWS::CodeBuild::ReportGroup must create the record in the CodeBuild service state (the same seam the already-filed project/fleet causes identify) so that services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/put_resource_policy.rs resolves the ARN; the policy-document parse/validation branch of that handler then needs to be reachable and to classify a non-JSON body as InvalidInputException. Related open issue 20261025T014438Z-codebuild-8-further-divergences-getresourcepolicy-updatewebhook-deletebuildbatch-stubs.md describes the same non-materialization as its Cause 8 but carries only the replay key for codebuild.deploy-codebuild-report-group-cfn-policy-applies, not for this check's PutResourcePolicy classification path, so this check must be replayed too before that fix is confirmed.
Traces: codebuild.deploy-codebuild-report-group-put-resource-policy-malformed-rejected.
