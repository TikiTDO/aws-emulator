# arc-zonal-shift: AccessDenied message on unknown shift id, wrong enum-set order in ValidationException, and NLB never becomes an ARC managed resource

> _Note: this issue was identified against the code base at commit `2216fbd2f00c4c2b6b2036585ad12df5e43cbdbf`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetManagedResource

## Description
Three net-new root causes in the arc-zonal-shift emulator, found by replaying the behavioral suite (simparity-behavioral-aws-v1). This bundle has 3 causes; all three must be closed before submitting.

RELATED (not the same cause, and neither covers these checks): open issue 20261029T170702Z-arc-zonal-shift-accessdeniedexception-403-body-does-not.md describes the 403 BODY SHAPE on the wire corpus (member casing / extra __type / empty-body steps); open issue 20261029T170702Z-arc-zonal-shift-validationexception-messages-omit-the-rejected.md describes the missing quoted value in ValidationException messages. Cause 1 below is about the presence of message TEXT on a well-formed-but-unknown zonalShiftId, and cause 2 is about the ORDER of the enum value set — neither is claimed by those issues' keys.

Cause 1 of 3 — CancelZonalShift answers AccessDeniedException with a message body where AWS sends none (check arc-zonal-shift.cancel-zonal-shift-malformed-id-rejected).
AWS: Smithy: CancelZonalShift (DELETE /zonalshifts/{zonalShiftId}) models AccessDeniedException (errorKind client, httpError 403) with a single optional member `message`; input member zonalShiftId targets ZonalShiftId (@length 6..36, @pattern ^[A-Za-z0-9-]+$). For a zonalShiftId that is well formed (satisfies both length and pattern) but names no shift this account owns, the recorded service answers 403 AccessDeniedException with an EMPTY message — the error class is carried by the status and the error-type discriminator, and there is no reason text at all. Recorded behavior only for the empty message (the model marks `message` optional and documents no text). This is the service's ownership check firing before any lookup, so it is the same shape for every unknown-but-well-formed id; nothing in the message varies with the request.
Emulator: returns the correct code (AccessDeniedException) but populates a reason: the message is the fixed string "Requested resource is not available." The check asserts an empty message and fails with: expected an empty AccessDeniedException message, got 'Requested resource is not available.'
Why: a client that branches on whether an access-denied response carries a reason (logging it, surfacing it to a user, or treating a non-empty reason as an IAM/policy denial rather than an unknown resource) is told a reason exists where AWS supplies none, and the text it is given is not text AWS ever emits for this path. Error-text assertions and contract tests written against the real service's empty message fail against the emulator even though the status and code are right.
Fix: the CancelZonalShift handler's ownership/denial path in services/service-com-amazonaws-arczonalshift-percdataplane/src/ops/cancel_zonal_shift.rs and the shared helper it uses to construct the denial (crate::state::identifier_not_attributable(), referenced from ops/get_managed_resource.rs:181) — the AccessDeniedException it builds for an unknown well-formed shift id must carry no message. Hypothesis: one shared helper supplies that fixed text to every denial path in the service, so the fix must not silently change the paths where a message IS recorded.
Traces: arc-zonal-shift.cancel-zonal-shift-malformed-id-rejected (the earlier assertion in the same check — the ValidationException for a pattern-violating id — passes, so the pattern-rejection path is NOT part of this cause).

Cause 2 of 3 — ValidationException for an out-of-enum ListZonalShifts status filter reports the enum value set in the wrong order (check arc-zonal-shift.list-zonal-shifts-invalid-status-filter-rejected).
AWS: Smithy: ListZonalShifts (GET /zonalshifts) binds input member `status` to ZonalShiftStatus via @httpQuery("status"); ZonalShiftStatus is an enum whose MODEL declaration order is [ACTIVE, EXPIRED, CANCELED]; the operation models ValidationException (errorKind client, httpError 400, required member `message`). The recorded service rejects a value outside the enum with 400 ValidationException and the message "1 validation error detected: Value at 'status' failed to satisfy constraint: Member must satisfy enum value set: [EXPIRED, ACTIVE, CANCELED]" — i.e. the value set it advertises is EXPIRED, ACTIVE, CANCELED, which is NOT the model's declaration order. Fixed text of the class: "1 validation error detected: Value at '", "' failed to satisfy constraint: Member must satisfy enum value set: [", "]"; variable parts: the member path taken from the request and the service's value list for that enum. Recorded behavior only for the ordering (the model does not state it).
Emulator: returns the right status (400) and code (ValidationException) and the right fixed text, but renders the set in model declaration order: "1 validation error detected: Value at 'status' failed to satisfy constraint: Member must satisfy enum value set: [ACTIVE, EXPIRED, CANCELED]".
Why: a client or operator that reads the accepted values out of the error message — or any test pinning AWS's message byte-for-byte to prove the enum boundary is enforced — sees a different value set than production returns, so the only machine-readable part of the rejection does not match the service.
Fix: the arc-zonal-shift input-validation / ValidationException message builder for enum-constrained members (shared across the service's operations, used by the ListZonalShifts handler in services/service-com-amazonaws-arczonalshift-percdataplane/src/ops/list_zonal_shifts.rs) — the value list printed for ZonalShiftStatus must be the service's order, EXPIRED then ACTIVE then CANCELED, rather than the model's declaration order.
COORDINATION NOTE for the fixer: the recorded message for THIS operation/member contains no quoted rejected value ("Value at 'status'"), while the open wire issue 20261029T170702Z-arc-zonal-shift-validationexception-messages-omit-the-rejected.md requires the value to be interpolated on other operations/members. Do not generalise either shape across the whole service in a way that breaks the other; this check asserts the message above exactly.
Traces: arc-zonal-shift.list-zonal-shifts-invalid-status-filter-rejected (the positive control, ListZonalShifts(status=ACTIVE) returning items, is unreached because the assertion fails first).

Cause 3 of 3 — a Network Load Balancer with zonal-shift integration enabled never becomes an ARC managed resource, so GetManagedResource never reports it and every managed-resource-backed flow hangs (check arc-zonal-shift.update-zonal-shift-extends-expiry).
AWS: Smithy: GetManagedResource (GET /managedresources/{resourceIdentifier}) returns required members `appliedWeights` (map of AZ -> 1|0) and `zonalShifts`, and models ResourceNotFoundException (404) and AccessDeniedException (403). AWS documents that an ALB/NLB becomes an ARC managed resource once zonal-shift integration is turned on for it (elbv2 ModifyLoadBalancerAttributes with zonal_shift.config.enabled=true); recorded behavior: after that call, GetManagedResource on the load balancer ARN answers 200 with a non-empty appliedWeights within well under a minute, and UpdateZonalShift's effect on an ACTIVE shift is then visible in that resource's `zonalShifts`.
Emulator: the registration never happens. GetManagedResource resolves only out of its own store (services/service-com-amazonaws-arczonalshift-percdataplane/src/ops/get_managed_resource.rs:200, `store.managed_resources.get(...)`), and nothing populates that map from the ELBv2 side, so the ARN is answered as unregistered indefinitely. The check provisions the VPC/subnets/NLB, enables zonal_shift.config.enabled, then polls GetManagedResource until appliedWeights is non-empty; the poll never terminates and the check dies with "Check timed out after 60.0s" without ever reaching its UpdateZonalShift assertions. Hypothesis: there is no cross-service hook from elbv2 ModifyLoadBalancerAttributes (or from load-balancer creation) into the arc-zonal-shift store's managed_resources.
Why: every ARC flow that needs a real managed resource is unreachable on the emulator — StartZonalShift/UpdateZonalShift/CancelZonalShift against an actual load balancer, practice runs, and zonal autoshift. A client that follows AWS's documented sequence (create NLB, enable zonal-shift integration, read GetManagedResource) blocks forever instead of getting a registered resource, and the emulator answers a resource the service considers managed as unknown.
Fix: the arc-zonal-shift managed-resource registration path — the service's state (services/service-com-amazonaws-arczonalshift-percdataplane/src/state.rs, the `managed_resources` map read at ops/get_managed_resource.rs:200) must gain an entry, with appliedWeights seeded to 1 for each AZ the load balancer spans, when zonal-shift integration is enabled for an ELBv2 load balancer; i.e. the elbv2 ModifyLoadBalancerAttributes handler (or an equivalent cross-service registration seam) must publish that resource to ARC.
Traces: arc-zonal-shift.update-zonal-shift-extends-expiry. Note the sibling check arc-zonal-shift.cancel-practice-run-wrong-shift-type-rejected exercises the same provisioning and is separately blocked by the unimplemented EC2 CreateInternetGateway stub (already filed) — that is a different cause and is not part of this bundle.
