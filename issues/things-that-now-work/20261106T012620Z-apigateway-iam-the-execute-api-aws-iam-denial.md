## Description
Two net-new root causes in the execute-api data-plane AWS_IAM denial serializer. === Cause 1 of 2: the implicit-deny Message stops at the method ARN and omits AWS's ' because no identity-based policy allows the execute-api:Invoke action' clause ===
AWS: recorded behavior only — the on-disk Smithy model for this service (services/service-com-amazonaws-apigateway-backplanecontrolservice) models only the API Gateway control plane and says nothing about the execute-api data plane, so the oracle is the recorded response. For a SigV4-signed request to a method whose authorizationType is AWS_IAM where nothing in the signer's effective identity policy allows execute-api:Invoke on the method ARN, AWS answers HTTP 403 with header x-amzn-ErrorType: AccessDeniedException and a JSON body whose Message is, as a template: "User: <caller-arn> is not authorized to perform: execute-api:Invoke on resource: <method-arn> because no identity-based policy allows the execute-api:Invoke action". The fixed text, exactly as AWS words it, is "User: ", " is not authorized to perform: ", " on resource: " and the trailing " because no identity-based policy allows the execute-api:Invoke action". The variable parts come from the request and from state: <caller-arn> is the signing principal (for an assumed role, arn:aws:sts::<account>:assumed-role/<role-name>/<session-name>), <method-arn> is assembled from the request's region, account, rest-api-id, stage, HTTP verb and resource path, and the action named in the trailing clause is the same action named earlier in the message. (For a session-policy denial the trailing clause is ' because no session policy allows the execute-api:Invoke action'; for a resource-policy explicit deny it is ' with an explicit deny in a resource-based policy'.)
Emulator: the status and the error-type header are right and the message prefix is right, but the Message ENDS at the method ARN — the trailing reason clause is absent in every denial the eleven checks below produce, both on the /data-agreements/{agreementId} API and on the /widgets API.
Why: the reason clause is the only thing in the response that tells a client WHY it was denied — whether no policy granted the action (add a grant), a session policy narrowed the credential (re-vend it), or an explicit Deny matched (adding a grant will not help). Diagnostic tooling, runbooks and alarm rules that classify denials by AWS's wording misclassify every execute-api refusal, and an operator is told the call was denied but never told that nothing allowed it.
Fix: the execute-api data-plane authorization-refusal serializer in the apigateway service crate — the component that formats the AccessDeniedException body for an AWS_IAM-authorized method must append the reason clause for the denial class it decided (implicit deny / session policy / resource-based explicit deny), naming the same action it names earlier in the message.

=== Cause 2 of 2: the method ARN in the denial names the API Gateway resource's path TEMPLATE, not the path the request actually asked for ===
AWS: recorded behavior only (same reason as Cause 1). The method ARN IAM evaluates — and therefore the ARN AWS names in the denial — is arn:aws:execute-api:<region>:<account>:<rest-api-id>/<stage>/<HTTP-VERB>/<request-resource-path>, where <request-resource-path> is the path the client requested after the stage, with path parameters SUBSTITUTED by their request values and any duplicate slashes collapsed. For a resource declared as /data-agreements/{agreementId} and a GET of /<stage>/data-agreements/<id>, the evaluated and reported path segment is /data-agreements/<id> — that is what makes a grant on one concrete agreement id admit it and deny a sibling id, and what makes a doubled '//' spelling authorize identically to the single-slash one.
Emulator: the method ARN carries the resource definition's literal pathPart template instead: the recorded Message ends '...:<api-id>/beta/GET/data-agreements/{agreementId}' for every request, whatever id was asked for. The braces are emitted verbatim, so no two distinct requests on that resource can be told apart from the refusal.
Why: the ARN in the message is the resource IAM says it evaluated. A client cannot verify which object was denied, per-object grants cannot be audited from the refusal, and tooling that re-reads the ARN out of the message to retry or to narrow a grant builds a grant on the literal string '{agreementId}', which matches nothing. It also hides whether the authorizer evaluated the concrete path at all, which is the whole subject of the per-object and path-normalization contracts.
Fix: the execute-api data-plane authorizer's method-ARN builder in the apigateway service crate — it must build the ARN from the normalized REQUEST path (path parameters substituted, duplicate slashes collapsed) rather than from the matched resource's path template, and the denial serializer must report that same ARN.
