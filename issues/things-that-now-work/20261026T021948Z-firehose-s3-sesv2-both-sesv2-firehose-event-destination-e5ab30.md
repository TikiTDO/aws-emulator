# firehose__s3__sesv2: both SESv2→Firehose event-destination checks now abort one call later — CreateConfigurationSetEventDestination is an unimplemented scaffold stub answering 501 NotImplemented

## Description
One net-new root cause (Cause 1 of 1).

Context on the neighbouring issue (it does NOT cover this): the open issue 20261025T214423Z-firehose-s3-sesv2-both-sesv2-firehose-event-destination.md reports these same two checks aborting on sesv2 CreateConfigurationSet answering 501 NotImplemented. That is a different operation with a different handler file and a different fix site, so it is a distinct cause; it is not that issue's replay key, and because that issue is still OPEN (not fixed) this is not a REOPENS of anything.

Cause 1 of 1: sesv2 CreateConfigurationSetEventDestination is still a scaffold stub, so a configuration set can never be given a Kinesis Firehose event destination and the entire SESv2 → Firehose → S3 event-publication path is unreachable.
Failing check ids for this cause: firehose__s3__sesv2.firehose-destination-delivers-two-send-events-within-the-buffering-interval, firehose__s3__sesv2.firehose-destination-rejects-a-role-the-stream-cannot-be-assumed-by.

AWS: CreateConfigurationSetEventDestination is SESv2 restJson1, POST /v2/email/configuration-sets/{ConfigurationSetName}/event-destinations, success HTTP 200 with an EMPTY body. Smithy (services/service-com-amazonaws-sesv2-simpleemailservice-v2/smithy-model/com-amazonaws-sesv2-simpleemailservice-v2.json): input CreateConfigurationSetEventDestinationRequest {ConfigurationSetName required, @httpLabel; EventDestinationName required; EventDestination (EventDestinationDefinition) required}, output CreateConfigurationSetEventDestinationResponse {} (no members), http POST /v2/email/configuration-sets/{ConfigurationSetName}/event-destinations code 200. EventDestinationDefinition carries {Enabled (boolean, default false), MatchingEventTypes (EventTypes list), KinesisFirehoseDestination, CloudWatchDestination, SnsDestination, EventBridgeDestination, PinpointDestination}; KinesisFirehoseDestination requires IamRoleArn and DeliveryStreamArn (both AmazonResourceName, @length min 1). The ONLY modeled errors are AlreadyExistsException (400, "The resource specified in your request already exists."), BadRequestException (400, "The input you provided is invalid."), LimitExceededException (400, "There are too many instances of the specified resource type."), NotFoundException (404, "The resource you attempted to access doesn't exist.") and TooManyRequestsException (429, "Too many requests have been made to the operation."). There is no condition under which AWS answers this operation HTTP 501, and neither the code 'NotImplemented' nor status 501 appears anywhere in the model for it. The behavioural requirements that follow from the model plus the recorded runs: a ConfigurationSetName that was never created is refused NotFoundException 404; an EventDestinationName already present in that set is refused AlreadyExistsException 400; after a 200 the destination is visible to GetConfigurationSetEventDestinations and SendEmail against that configuration set publishes the matching event types (here SEND) to the named Firehose delivery stream, which the positive check then observes as objects under the stream's S3 prefix. The negative sibling's requirement is also model-grounded: when the referenced IamRoleArn's trust policy never allows ses.amazonaws.com to assume it, SES refuses the event destination PERMANENTLY with BadRequestException 400 (the message's fixed text is SES's own could-not-assume-role wording; its only variable part is the role ARN taken from the request's KinesisFirehoseDestination.IamRoleArn), while a correctly-trusted role against the same stream succeeds with 200 — so the rejection cannot be a blanket refusal of every role.

Emulator: every call is answered HTTP 501 with code 'NotImplemented' and the message "operation CreateConfigurationSetEventDestination is scaffolded but not implemented in this emulator". In that message, "operation ... is scaffolded but not implemented in this emulator" is the emulator's own fixed scaffold text and 'CreateConfigurationSetEventDestination' is the operation name interpolated from the stub — no part of it comes from the request or from state. The refusal is unconditional: it is returned for the correctly-trusted role exactly as for the untrustable one, which is why the negative check fails on its POSITIVE CONTROL rather than on its negative assertion.

Why: a client configuring SES event publication — the normal way send/delivery/bounce events are streamed to Firehose and on to S3 — cannot attach any event destination to a configuration set at all. It gets a 501 with a code that appears in no AWS model, so SDK error handling cannot classify it: it is neither a modeled client error it can branch on (NotFoundException for a missing set, AlreadyExistsException for a duplicate destination name, BadRequestException for an unassumable role) nor a retryable throttle (TooManyRequestsException 429). Worse for fidelity, the blanket refusal is indistinguishable from the legitimate BadRequestException path, so a client cannot tell a genuinely bad IAM trust policy from an operation that does not exist, and the emulator's whole SESv2→Firehose→S3 event path stays ungraded.

Fix: the operation's handler, services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/create_configuration_set_event_destination.rs — implement `handle` against the sesv2 service state (look the ConfigurationSetName up in the state the now-working CreateConfigurationSet registers and refuse NotFoundException when absent; refuse AlreadyExistsException when EventDestinationName is already present in that set; store the EventDestinationDefinition including KinesisFirehoseDestination {IamRoleArn, DeliveryStreamArn}, MatchingEventTypes and Enabled; validate the referenced role's trust policy and refuse BadRequestException when ses.amazonaws.com cannot assume it; return the empty 200 output) and delete the `//! SCAFFOLDED, NOT IMPLEMENTED:` marker line. The stored destination must then be visible to GetConfigurationSetEventDestinations/UpdateConfigurationSetEventDestination/DeleteConfigurationSetEventDestination and must drive SendEmail's event publication into the Firehose delivery stream.

Traces: firehose__s3__sesv2.firehose-destination-delivers-two-send-events-within-the-buffering-interval ([error], aborts on the CreateConfigurationSetEventDestination call) and firehose__s3__sesv2.firehose-destination-rejects-a-role-the-stream-cannot-be-assumed-by ([mismatch], its positive control fails on the same call). ## Steps to Reproduce
1. Boot the emulator and point boto3 at it: sesv2 = boto3.client('sesv2', endpoint_url=<emulator>, region_name=<region>); firehose = boto3.client('firehose', ...); iam = boto3.client('iam', ...); s3 = boto3.client('s3', ...).
2. Create an S3 bucket, an IAM role trusted by firehose.amazonaws.com with write access to it, and a Firehose delivery stream with an ExtendedS3DestinationConfiguration pointing at that bucket.
3. Create an IAM role whose trust policy DOES allow ses.amazonaws.com to assume it, with firehose:PutRecord/PutRecordBatch on the stream.
4. Call sesv2.create_configuration_set(ConfigurationSetName='sim2real-xsvc-sesfh-1') — this now returns 200.
5. Call sesv2.create_configuration_set_event_destination(ConfigurationSetName='sim2real-xsvc-sesfh-1', EventDestinationName='fh', EventDestination={'Enabled': True, 'MatchingEventTypes': ['SEND'], 'KinesisFirehoseDestination': {'IamRoleArn': <the ses-trusted role arn>, 'DeliveryStreamArn': <the stream arn>}}). Observe HTTP 501 with code 'NotImplemented' and the message 'operation CreateConfigurationSetEventDestination is scaffolded but not implemented in this emulator', instead of a 200 with an empty body.
