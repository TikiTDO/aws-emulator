# AppConfig rollout percentage never gates what the data plane serves: an in-flight deployment is served to 100% of sessions from StartDeployment onward

> _Note: this issue was identified against the code base at commit `54073c01592ce4e56a3cca58cb5387afed010108`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartDeployment

## Description
One net-new root cause. Cause 1 of 1: a deployment's rollout percentage is reported but never enforced, so a partial rollout is never partial in what consumers are served.

AWS: a deployment strategy's GrowthFactor is, per the model, "The percentage of targets that received a deployed configuration during each interval" (Smithy: DeploymentStrategy.GrowthFactor, CreateDeploymentStrategy.GrowthFactor -> Percentage), GrowthType is the enum [LINEAR, EXPONENTIAL], and Deployment.PercentageComplete is "The percentage of targets for which the deployment is available" (Smithy: Deployment.PercentageComplete; Deployment.State -> DeploymentState [BAKING, VALIDATING, DEPLOYING, COMPLETE, ROLLING_BACK, ROLLED_BACK, REVERTED]). That percentage is a serving decision, not a label: while a deployment is DEPLOYING at a percentage strictly between 0 and 100, independently-opened AppConfigData configuration sessions for the same application/environment/profile are split — some are served the PREVIOUS configuration version's exact bytes and some the new version's, bucketed per session and independently, with no session ever served a blend — and the fleet converges on the new version only once the rollout reaches 100%. Recorded behavior (the checks' MEASURED notes, us-west-2): with GrowthFactor=25 over DeploymentDurationInMinutes=4, PercentageComplete advanced 0 -> 25 -> 50 -> 75 -> 100 and 20-session samples at each step were split (5-8 of 20 on the new version at 25%, 8-13 at 50%, 12-19 at 75%); with GrowthFactor=20 at 20% rolled out, 6 of 20 fresh sessions were on the new version, and after StopDeployment all 20 of 20 were back on the previous version.

Emulator: the serving decision ignores the rollout entirely. services/service-com-amazonaws-appconfig-amazonappconfig/src/state.rs decides which deployment is in force with Deployment::serves_the_configuration(), which is `self.is_in_flight() || self.state == DEPLOYMENT_COMPLETE` — true from the instant StartDeployment is answered (DEPLOYING) — and Environment::in_force_deployment() then picks the highest-numbered such deployment for the profile. Deployment::percentage_complete is advanced by the clock in Deployment::materialize()/rollout_schedule() for reporting (and for the PERCENTAGE_UPDATED event log) only; nothing consults it when answering a configuration poll, and there is no per-session bucketing anywhere. So every session opened after StartDeployment — at 0%, at 20%, at 99% — is served the NEW version's bytes, and no session is ever served the previous version while the rollout is in flight. The three checks that observe this each poll until both versions have been served into the same environment; that condition can never become true, so each burns its declared rollout budget (_ROLLOUT_TIMEOUT_S 900 / _PARTIAL_ROLLOUT_TIMEOUT_S 600) and is killed by the harness at 60.0s. For appconfig.stop-deployment-mid-rollout-reverts-every-session the never-satisfiable condition is the check's PRECONDITION loop ("poll until the same environment is demonstrably serving BOTH versions"), so the stop is never even reached.

Why: a client relying on AWS's behavior believes a canary is a canary. GrowthFactor/GrowthType/DeploymentDurationInMinutes are the entire safety mechanism of AppConfig deployments: a 10%-canary rollout is supposed to expose one tenth of the fleet while the operator watches, and a stop mid-rollout is supposed to withdraw that exposure from the fraction that got it. Against this emulator every rollout is an instant 100% flip at StartDeployment while PercentageComplete cosmetically reports 0/20/40/..., so any safe-deployment logic, canary verification or blast-radius test is validated against a target that cannot reproduce the failure mode it exists to catch. It is also the over-permissive direction: the new configuration reaches every consumer earlier than AWS would ever serve it.

Fix: the configuration-serving decision in the appconfig service's state — Deployment::serves_the_configuration / Environment::in_force_deployment must take the materialized PercentageComplete into account and bucket per configuration session (a session opened while the rollout is at P% is served the new version with probability P%, independently per session, and the previous in-force version otherwise), and the AppConfigData poll that reads through it must answer from that decision. A rolling-back / rolled-back / reverted deployment already correctly falls back to the preceding version; the gap is the partial, in-flight case. Related open issues that do NOT cover this cause: 20261024T112615Z-appconfigdata-data-plane-deployed-configuration-never-served-sessions.md (data-plane session/serving defects, not percentage gating) and 20261025T020208Z-appconfig-cloudwatch-appconfig-deployments-with-cloudwatch-alarm-monitors-never-reach.md (monitored deployments never reaching a terminal state).

Traces: appconfig.linear-rollout-serves-both-versions-across-sessions, appconfig.stop-deployment-mid-rollout-reverts-every-session, appconfig.exponential-growth-type-advances-in-powers-of-the-growth-factor.

## Evidence
All three checks report "Error: Check timed out after 60.0s" with no assertion having fired, because the condition each polls for is unreachable on this emulator:

1) appconfig.linear-rollout-serves-both-versions-across-sessions — deploys v1 (b'{"tier":"one"}') with a 0-minute strategy, confirms 5/5 sessions are served v1, then starts a LINEAR GrowthFactor=25 / DeploymentDurationInMinutes=4 rollout of v2 (b'{"tier":"two"}') and samples 4 fresh sessions on every tick where 0.0 < PercentageComplete < 100.0, accumulating mid_payloads until both versions have been seen or _ROLLOUT_TIMEOUT_S=900 elapses. Expected: mid_payloads contains BOTH v1's and v2's exact bytes (assertion message "the rollout was not partial — across N mid-rollout sessions only [...] was ever served, so the new version reached either none or all of the fleet instead of a percentage of it"). Observed: every mid-rollout session is served v2 from the first tick, so the loop never short-circuits and the check is killed at the 60s cap.

2) appconfig.stop-deployment-mid-rollout-reverts-every-session — same setup with GrowthFactor=20 / DeploymentDurationInMinutes=5; its precondition is "poll until the same environment is demonstrably serving BOTH versions" before calling StopDeployment. Observed: both versions are never concurrently served (all sessions are on v2 immediately), so the precondition loop runs out its _PARTIAL_ROLLOUT_TIMEOUT_S=600 budget and the stop/revert legs are never exercised.

3) appconfig.exponential-growth-type-advances-in-powers-of-the-growth-factor — EXPONENTIAL GrowthFactor=10 / DeploymentDurationInMinutes=4; it asserts the G*(2^N) grid (10/20/40/80/100, 5 PERCENTAGE_UPDATED entries) AND the same partial-serving leg ("the rollout was genuinely PARTIAL: both versions were in service at the same time", asserting v1_bytes in mid_payloads and v2_bytes in mid_payloads). Observed: the same all-new-version serving; the check is killed at the 60s cap. Note for the fixer: the step grid itself IS implemented (state.rs Deployment::rollout_schedule computes GrowthFactor*2^step for GROWTH_EXPONENTIAL and GrowthFactor*(step+1) for LINEAR, capped at 100), so only the serving leg of this check is attributed to this cause; its remaining legs were never graded because the check never got past the rollout loop.

Source of the cause (services/service-com-amazonaws-appconfig-amazonappconfig/src/state.rs): `pub fn serves_the_configuration(&self) -> bool { self.is_in_flight() || self.state == DEPLOYMENT_COMPLETE }`, used by `Environment::in_force_deployment` as the single place "this service decides ... which deployment is in force" for both GetConfiguration and the appconfigdata poll; `percentage_complete` is written only by `materialize()` and read only by the Deployment serializer and the PERCENTAGE_UPDATED event text `format!("Configuration available to {reached}% of clients")`.

Smithy support: DeploymentStrategy.GrowthFactor / CreateDeploymentStrategy.GrowthFactor — "The percentage of targets that received a deployed configuration during each interval"; Deployment.PercentageComplete — "The percentage of targets for which the deployment is available"; GrowthType enum [LINEAR, EXPONENTIAL]; DeploymentState enum [BAKING, VALIDATING, DEPLOYING, COMPLETE, ROLLING_BACK, ROLLED_BACK, REVERTED].

2. CreateHostedConfigurationVersion twice with distinguishable bytes (v1, v2).
3. CreateDeploymentStrategy(DeploymentDurationInMinutes=0, GrowthFactor=100, FinalBakeTimeInMinutes=0, ReplicateTo='NONE') and StartDeployment of v1; wait for State 'COMPLETE'.
4. Sample the data plane: appconfigdata StartConfigurationSession + GetLatestConfiguration from several independent sessions — all return v1's bytes (correct today).
5. CreateDeploymentStrategy(DeploymentDurationInMinutes=4, GrowthType='LINEAR', GrowthFactor=25, FinalBakeTimeInMinutes=0) and StartDeployment of v2.
6. While GetDeployment reports 0.0 < PercentageComplete < 100.0, repeatedly open fresh configuration sessions and record what each is served. Expected: a mix of v1's and v2's exact bytes across sessions (per-session bucketing, no blended payload), with the proportion on v2 tracking PercentageComplete; observed: every session is served v2, already at the first tick and even before PercentageComplete leaves 0.
7. Variant for the stop leg: with GrowthFactor=20 / DeploymentDurationInMinutes=5, wait until both versions are observably in service (never happens today), call StopDeployment, and re-sample — every session must then be served v1's bytes again.
8. Re-replay the three check ids in trace_ids to confirm the fix (each needs a wall-clock budget larger than the current 60s cap: their declared budgets are 900s/600s).
