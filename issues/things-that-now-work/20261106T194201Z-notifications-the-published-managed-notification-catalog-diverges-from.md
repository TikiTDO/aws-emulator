# notifications: the published managed-notification catalog diverges from AWS — entries absent and entry text not AWS's prose

> _Note: this issue was identified against the code base at commit `07e9367022a66882e4e3c540bf6dceaeefec3f72`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListManagedNotificationConfigurations

## Description
Cause 1 of 1: the seeded managed-notification catalog this service publishes is not the catalog AWS publishes — it is MISSING whole categories and sub-categories AWS lists, and the entries it does publish carry display text that is not AWS's published prose (fixture notifications-catalog-list-managed-notification-configurations, step task#1).

AWS: Smithy: ListManagedNotificationConfigurations is GET /managed-notification-configurations, readonly, paginated (inputToken/outputToken nextToken, pageSize maxResults range 1..100, items managedNotificationConfigurations), output member managedNotificationConfigurations @required. Each item is ManagedNotificationConfigurationStructure with arn (@required, ManagedNotificationConfigurationOsArn, pattern ^arn:[a-z-]{3,10}:notifications::[0-9]{12}:managed-notification-configuration/category/[a-zA-Z0-9\-]{3,64}/sub-category/[a-zA-Z0-9\-]{3,64}$), name (@required, @length 1..64, pattern ^[A-Za-z0-9\-]+$) and description (@required, @length 0..256). The model enumerates NO entry, so WHICH entries exist and what their name/description say is recorded behavior only. Because no caller operation creates, edits or deletes a managed notification configuration, the catalog is the same fixed, service-published set for every account — it is a requirement of the response, not a per-account or per-run value. The recording publishes, among others, an AWS-BCM category (sub-categories Billing-and-Invoices, Financing, Fraud-Prevention, Payment, Subscriptions) that the emulator does not publish at all, and an AWS-Health category whose sub-categories include Security ('Security' / 'Health events with Security implications that are sent through email. By default, these are sent to the root email address, operations alternate contact, and the security alternate contact.') and Operations ('Health Operations' / 'Health events with Operational implications that are sent through email. By default, these are sent to the root email address and the operations alternate contact.'), neither of which the emulator publishes. For the entries that do exist, the recorded text differs: AWS-MP-Buyer/MPBuyerAgreements is named 'Agreements and subscriptions' and described as 'Notifications about your agreements and subscriptions, including new agreements, amendments, cancellations, expirations, renewals, free trial reminders, payment requests, and billing adjustments.', and AWS-Health/Issue's recorded name and description both differ from the published ones (the recorded description begins 'All a...'; the replay withholds the remainder). In every one of these the sentence template is AWS's fixed text — the variable parts of an entry are only its category and sub-category segments, which appear in the arn and in the display name.

Emulator: MANAGED_NOTIFICATION_CATALOG (services/service-com-amazonaws-notifications-notifications/src/state.rs, around lines 666-740) seeds exactly 12 entries — AWS-Health/{Issue, AccountNotification, ScheduledChange, Investigation}, four AWS-Partner-Central entries and AWS-MP-Buyer/{MPBuyerProducts, MPBuyerPrivateOffers, MPBuyerPricing, MPBuyerAgreements} — and seeded_managed_configurations() publishes that set verbatim. Replay of the unpaged listing answers HTTP 200 (200 expected, so the status and envelope are right) and diverges on 15 keys of $.managedNotificationConfigurations: ELEVEN expected entries are reported at whole-entry granularity — category/AWS-BCM/sub-category/{Billing-and-Invoices, Financing, Fraud-Prevention, Payment, Subscriptions} and category/AWS-Health/sub-category/{AccountNotification, Billing, Investigation, Operations, ScheduledChange, Security} — with the detail stating 'missing (expected {...}, got None)' for the ones it spells out (AWS-Health/Security, AWS-Health/Operations); and FOUR member keys mismatch on text — AWS-Health/Issue .name and .description, and AWS-MP-Buyer/MPBuyerAgreements .name (published 'Agreements', recorded 'Agreements and subscriptions') and .description (published 'Notifications about your agreements and subscriptions, including new agreements.', recorded text continues through 'amendments, cancellations, expirations, renewals, free trial reminders, payment requests, and billing adjustments.'). The seeded AWS-Health prose is of the emulator's own composition ('AWS Health events reporting an issue that affects resources, services or regions you use, ...') rather than AWS's 'Health events with <X> implications that are sent through email. By default, these are sent to ...' template.

Why: a client that enumerates managed notifications sees a catalog short by most of its membership. Every absent arn is unreachable: GetManagedNotificationConfiguration on it cannot resolve, no managed channel association exists for it, and a channelIdentifier-filtered managed listing can never return it — so a workflow that subscribes an account to AWS-BCM billing/payment/fraud notifications or to the AWS-Health Security or Operations sub-categories cannot be exercised at all, while against AWS it runs. For the entries that do exist, a console or client that renders the catalog shows a display name and a sentence that are not the ones AWS publishes, so text-matching and display assertions fail even though the request succeeded.

Fix: the operation's state — the catalog seed. Complete MANAGED_NOTIFICATION_CATALOG from the fixture recording itself (add the whole AWS-BCM category and the absent AWS-Health sub-categories, and correct the name/description of AWS-Health/Issue and AWS-MP-Buyer/MPBuyerAgreements) so the listing, GetManagedNotificationConfiguration, the channel-association reads and SEEDED_CHANNEL_ASSOCIATIONS all derive from one complete published set. Do NOT invent prose for an entry whose recorded text is not fully available — read it off the recording; publishing invented wording substitutes one fidelity defect for another, which is how the current AWS-Health text came to diverge. The already-open issue 20261102T020000Z-notifications-mp-buyer-agreements-text-and-the-two-204-content-length-keys-remain-open.md owns only the MPBuyerAgreements description tail and the two 204 content-length keys; it does NOT cover the absent AWS-BCM and AWS-Health entries or the AWS-Health/Issue text, which is why this is filed separately.
