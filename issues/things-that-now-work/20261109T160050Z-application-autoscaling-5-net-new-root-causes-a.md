=== Cause 1 of 5: a scheduled action's firing records ONE merged activity with a Cause AWS never emits, and no dispatch activity at all ===
AWS: Smithy — DescribeScalingActivities (paginated on NextToken, items ScalingActivities, input flag IncludeNotScaledActivities); ScalingActivity.Cause is REQUIRED ("A simple description of what caused the scaling activity to happen"), Description is REQUIRED ("A simple description of what action the scaling activity intends to accomplish"), StatusCode targets ScalingActivityStatusCode (Pending|InProgress|Successful|Overridden|Unfulfilled|Failed), StatusMessage is optional. The exact wording is recorded behavior only. When a scheduled action fires on a scalable target, AWS records TWO activities, both settling StatusCode Successful and returned newest-first:
  (a) the DISPATCH — Cause is the fixed text `scheduled action name ` + the ScheduledActionName + ` was triggered`; Description is `Setting min capacity to <N>` or `Setting max capacity to <N>` (no trailing period) naming the ScalableTargetAction member the action set and its value; StatusMessage is `Successfully set min capacity to <N>` / `Successfully set max capacity to <N>`.
  (b) the ENFORCEMENT the dispatch causes — Cause is the fixed text `minimum capacity was set to ` / `maximum capacity was set to ` + the new bound; Description names the scaled property per namespace (`Setting read capacity units to <N>.` for dynamodb and cassandra reads, `Setting desired count to <N>.` for ecs, `Setting desired capacity to <N>.` for custom-resource); StatusMessage is `Successfully set <property> to <N>. Change successfully fulfilled by <namespace>.`
The only variable parts are the scheduled action's name, the bound it set, the scaled property and the fulfilling namespace — every other word is fixed.
Emulator: exactly ONE activity is recorded per firing, and it is a hybrid of the two: its Cause is `scheduled action <name> set the minimum capacity to <N>` (or `... set the maximum capacity to <N>`) — a sentence AWS never emits, which welds the action name onto the enforcement value — while its Description and StatusMessage are the ENFORCEMENT activity's (`Setting read capacity units to <N>.` / `Successfully set read capacity units to <N>. Change successfully fulfilled by dynamodb.`). No activity carrying the documented dispatch Cause `scheduled action name <name> was triggered` is ever produced, for any schedule form (at(), cron(), rate()) or namespace (dynamodb, ecs, cassandra).
Why: the dispatch Cause is the documented join key between a scheduled action and the activity history it produced; a client that lists DescribeScalingActivities and filters for `scheduled action name <name> was triggered` (to audit which actions fired, in what order, in which timezone, before/after a StartTime or EndTime, or whether a suspended or deleted action fired) finds nothing, and a client that counts the two activities of a firing sees one. The emulator's single record also contradicts itself: a Cause that claims to be the dispatch carried on an activity whose Description/StatusMessage describe the downstream capacity change.
Emulator: note that the capacity effect itself does reach the resource in these runs, so this is purely the activity recording, not the enforcement.
Fix: the scheduled-action dispatcher and the scaling-activity recorder of this service (the dispatch path behind ops/put_scheduled_action.rs and the activity recorder in this service's state module): emit a dispatch activity for the firing AND a separate enforcement activity for the capacity change, each with AWS's own Cause/Description/StatusMessage template for its namespace.

=== Cause 2 of 5: a scheduled minimum above the registered maximum is applied successfully instead of failing the dispatch ===
AWS: Smithy — PutScheduledAction (ScalableTargetAction; errors ValidationException and ObjectNotFoundException, both errorKind client httpError 400) accepts and persists an out-of-range ScalableTargetAction verbatim; ScalingActivityStatusCode includes `Failed`. The dispatch outcome is recorded behavior only. A stored action whose ScalableTargetAction.MinCapacity is ABOVE the target's registered MaxCapacity is kept verbatim by DescribeScheduledActions, and at its instant it produces EXACTLY ONE activity that settles StatusCode `Failed`, with Cause `scheduled action name <name> was triggered`, Description `Setting min capacity to <N>`, and StatusMessage of fixed text `Failed to set min capacity to ` + <N> + `. Reason: Maximum capacity cannot be less than minimum capacity` — the same inverted-bounds reason PutScheduledAction would have returned inline. The registered bounds are left exactly as they were and the downstream resource's capacity is wholly unchanged.
Emulator: the dispatch activity resolves to StatusCode `Successful` — the out-of-range floor is applied (or silently clamped) instead of being refused, and no Failed activity with that StatusMessage exists.
Why: a client's scalable-target bounds are the guard rail; the emulator lets a scheduled action drive capacity past the registered maximum and reports success, so the violation is invisible in activity history and the target's effective bounds no longer match the ones it reports.
Fix: the scheduled-action dispatch path's bound validation plus the activity recorder — compare the action's ScalableTargetAction against the target's registered bounds at dispatch time, record the Failed activity with AWS's StatusMessage, and apply nothing.
Traces: application-autoscaling.scheduled-action-above-registered-maximum-rejected-at-dispatch

=== Cause 3 of 5: a target-tracking policy never acts on a breaching alarm — no scaling activity and no capacity change ===
AWS: Smithy — PutScalingPolicy.TargetTrackingScalingPolicyConfiguration; DescribeScalingActivities returns ScalingActivities whose StatusCode settles Successful. The wording and the metric linkage are recorded behavior only. A target-tracking policy on `dynamodb:table:ReadCapacityUnits` / `WriteCapacityUnits` mints its `TargetTracking-<resource-id>-AlarmHigh-<uuid>` alarm; under sustained real load above the policy's TargetValue that alarm breaches and Application Auto Scaling scales the table OUT: an activity is recorded for the target (Description `Setting read capacity units to <N>.`, StatusMessage `Successfully set read capacity units to <N>. Change successfully fulfilled by dynamodb.`) and the table's provisioned capacity rises above its pre-breach value, bounded by MaxCapacity.
Emulator: the minted alarms exist (the checks enumerate them at CloudWatch by name) but nothing ever executes: DescribeScalingActivities for the target stays EMPTY for the whole poll window and the provisioned capacity never moves (write capacity never increased past its registered floor of 5 under minutes of sustained write load; the read-load arm observed no AlarmHigh-driven activity at all; the unsuspended control target of the suspension check never completed a scale-out either, so that check's barrier is never reached). Hypothesis: either the DynamoDB consumed-capacity metric never reaches CloudWatch so the minted alarm never breaches, or the alarm breaches and the policy-execution path is not wired to it; the observable in both cases is no activity and no capacity change.
Why: target tracking is the primary scaling mode of this service. A client configures it and gets neither scaling nor any record that a decision was made, so a workload that outgrows its provisioned capacity silently stays throttled and the suspension semantics built on top of it (DynamicScalingOutSuspended withholding and then delivering on resume) cannot be exercised at all.
Fix: the target-tracking execution path of this service — evaluate the minted alarms (and the namespace metric feed they depend on) and drive the capacity-enforcement path and the activity recorder when one breaches.
Traces: application-autoscaling.target-tracking-policy-scales-out-table-capacity, application-autoscaling.target-tracking-alarm-breach-triggers-scaling-activity, application-autoscaling.dynamic-scaling-out-suspended-withholds-then-resume-delivers

=== Cause 4 of 5: custom-resource scalable targets are never enforced by any trigger — the endpoint is never PATCHed and no activity is recorded ===
AWS: recorded behavior only (Smithy models the namespace value `custom-resource` on ServiceNamespace and the dimension `custom-resource:ResourceType:Property`, but not the endpoint contract). In the `custom-resource` namespace Application Auto Scaling reads and writes the caller's own endpoint — GET and PATCH on `/scalableTargetDimensions/{id}`. Whenever a scaling decision is taken for such a target — a scheduled action firing, a CloudWatch alarm invoking a StepScaling policy, or a target-tracking policy's high alarm breaching — AWS PATCHes that endpoint with a body of exactly `{"desiredCapacity": <N>}`, the endpoint's capacity moves to <N>, and the activity pair of cause 1 is recorded with the custom-resource enforcement Description `Setting desired capacity to <N>.`
Emulator: nothing reaches the endpoint and nothing is recorded, for all three triggers. DescribeScalingActivities for the custom-resource target stays EMPTY (not even the single merged activity the dynamodb namespace produces), the endpoint's recorded PATCH count stays 0 and its desiredCapacity stays at its pre-decision value (observed `(1.0, 0, None)` = capacity 1.0, zero PATCHes, no body) across a 300s scheduled-action window, a 420s step-policy window and a 600s target-tracking window.
Why: the whole custom-resource contract — the documented way to scale anything AWS does not model natively — is inert on the trigger side: registration succeeds, policies and scheduled actions are stored and listed, and then no decision ever reaches the resource and no activity says so.
Fix: the custom-resource namespace branch of this service's capacity-enforcement path — issue the endpoint PATCH (and record the activities) from the scheduled-action dispatcher and from the policy-execution path, not only (per open issue 20261029T232940Z cause 7) from registration.
Traces: application-autoscaling.custom-resource-scheduled-action-patches-the-endpoint-when-it-fires, application-autoscaling.custom-resource-step-policy-alarm-patches-the-endpoint-up-to-the-ceiling, application-autoscaling.custom-resource-target-tracking-with-scale-in-disabled-still-scales-out

=== Cause 5 of 5: a scale-out blocked by MaxCapacity records no not-scaled activity ===
AWS: Smithy — DescribeScalingActivities.IncludeNotScaledActivities (boolean); ScalingActivity.NotScaledReasons is documented "Machine-readable data that describes the reason for a not scaled activity. Only available when IncludeNotScaledActivities..."; NotScaledReason.Code is REQUIRED with valid values AutoScalingAnticipatedFlapping, TargetServicePutResourceAsUnscalable, AlreadyAtMaxCapacity, AlreadyAtMinCapacity, AlreadyAtDesiredCapacity, alongside MaxCapacity, MinCapacity and CurrentCapacity. Wording is recorded behavior only. When a scale-out alarm breaches while the registered MaxCapacity equals the live capacity, AWS records EXACTLY ONE not-scaled activity: StatusCode `Failed`, Description the fixed text `Attempting to scale due to alarm triggered`, and NotScaledReasons = [{Code: `AlreadyAtMaxCapacity`, MaxCapacity: <the registered maximum>, CurrentCapacity: <the live capacity>}]. It is visible ONLY with IncludeNotScaledActivities=true (the default view hides it), a continuing breach does NOT add further entries unless the reason changes, and raising MaxCapacity then delivers the withheld scale-out as a normal Successful activity.
Emulator: no such record exists — DescribeScalingActivities with IncludeNotScaledActivities=true stays empty for the target while the AlarmHigh breaches against a ceiling equal to the live capacity.
Why: the not-scaled record is the only place AWS tells a client WHY a breach produced no scaling; without it, a target pinned at its ceiling is indistinguishable from a broken policy, and the documented machine-readable reason codes clients branch on are never emitted.
Fix: the scaling-decision path and the activity recorder — when a decision is withheld, record a not-scaled activity with the reason code and the Max/Current capacities, and gate it behind the IncludeNotScaledActivities flag in DescribeScalingActivities.
Traces: application-autoscaling.not-scaled-activity-records-already-at-max-capacity
