# iot: the HTTP topic-rule-destination confirm/enable/deliver trajectory never settles, so the unconfirmed-destination delivery gate reaches no verdict (1 cause)

> _Note: this issue was identified against the code base at commit `e0a2d0a80506ccb9fa0602d2975b19e44a09de79`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateTopicRuleDestination

## Description
Cause 1 of 1: the IoT HTTP topic-rule-destination lifecycle (create -> outbound DestinationConfirmation POST -> ConfirmTopicRuleDestination -> DISABLED -> ENABLED -> delivery) produces nothing a client can act on, so the check that asserts an enabled rule delivers NOTHING to an unconfirmed destination and DOES deliver once it is confirmed and enabled never reaches a verdict. Failing check: iot.topic-rule-with-unconfirmed-destination-blocks-delivery.

AWS: Smithy (service-com-amazonaws-iot-awsiotservice) models CreateTopicRuleDestination POST /destinations, success 200, output topicRuleDestination: TopicRuleDestination, required input destinationConfiguration: TopicRuleDestinationConfiguration; errors InvalidRequestException 400, ConflictingResourceUpdateException 409, ResourceAlreadyExistsException 409, UnauthorizedException 401, InternalException 500, ServiceUnavailableException 503. An httpUrlConfiguration destination is registered in status IN_PROGRESS and AWS sends a single HTTPS DestinationConfirmation POST to the supplied confirmationUrl carrying a confirmationToken query parameter. UpdateTopicRuleDestination PATCH /destinations (required arn: AwsArn, required status: enum TopicRuleDestinationStatus, success 200, empty output) with status=IN_PROGRESS re-sends that confirmation request. ConfirmTopicRuleDestination GET /confirmdestination/{confirmationToken+} (confirmationToken @length 1..2048, success 200, empty output) accepts the token; the destination then leaves IN_PROGRESS asynchronously and rests at DISABLED, and only UpdateTopicRuleDestination status=ENABLED moves it to ENABLED. GetTopicRuleDestination GET /destinations/{arn+} (200) reports that status. While the destination is not ENABLED an enabled topic rule's `http` action delivers nothing to that URL; once ENABLED the published payload is POSTed to it. Every one of these calls is bounded and answered promptly, with either a 200 or one of the modeled errors.

Emulator: the replay yields no response at all for this trajectory — the only output the suite reports for the check is `Error: Check timed out after 60.0s`. Each step of the check is a bounded poll whose own budget exceeds the harness cap (endpoint self-test 60 s, confirmation-token poll 240 s including UpdateTopicRuleDestination status=IN_PROGRESS resends, two 60 s destination-status polls, 180 s post-enable delivery poll), so the cap fires because a step that AWS answers never produces its value. No status, no error code, no delivered or suppressed payload, and no modeled refusal (400 InvalidRequestException, 409 ConflictingResourceUpdateException, 401 UnauthorizedException, 503 ServiceUnavailableException) is served in its place. Consistent with this, no outbound DestinationConfirmation POST and no destination-status gate on the `http` rule action is observable anywhere in this suite.

Why: a client that follows AWS — create the destination, receive the confirmation POST, call ConfirmTopicRuleDestination with the token, set ENABLED, then publish — never progresses and never learns why: it gets neither the confirmation request nor a prompt modeled refusal, so it blocks until its own timeout instead of failing fast. The security-relevant guarantee this check exists to assert, that an enabled rule delivers NOTHING to a destination that has not been confirmed and enabled, is unobservable, so neither the block nor the post-enable delivery can be relied on.

Fix: the iot topic-rule-destination component — the CreateTopicRuleDestination, ConfirmTopicRuleDestination, UpdateTopicRuleDestination and GetTopicRuleDestination handlers plus the destination state machine they share (IN_PROGRESS on create, DISABLED after confirmation, ENABLED only on an explicit update), the outbound HTTPS DestinationConfirmation POST that carries the confirmationToken to the configured confirmationUrl and is re-sent when the status is set back to IN_PROGRESS, and the topic-rule `http` action's delivery path, which must consult the destination's status and suppress delivery unless it is ENABLED. Each must either do the work or answer one of the modeled errors promptly rather than leaving the caller waiting.

## Evidence
Expected (AWS): CreateTopicRuleDestination returns 200 with topicRuleDestination.status=IN_PROGRESS, and a DestinationConfirmation POST carrying a confirmationToken query parameter arrives at the configured confirmationUrl. A message published to the rule's topic while the destination is unconfirmed is NOT delivered to that URL. ConfirmTopicRuleDestination(confirmationToken) returns 200 and GetTopicRuleDestination then reports status DISABLED. UpdateTopicRuleDestination(arn, status="ENABLED") returns 200 and GetTopicRuleDestination reports ENABLED. A message published after that IS POSTed to the URL. All calls are answered promptly with 200 or a modeled error.

Actual (emulator): the suite reports exactly `Error: Check timed out after 60.0s` for iot.topic-rule-with-unconfirmed-destination-blocks-delivery — no HTTP status, no error code, no error message, no delivered or suppressed marker. The check's own waits (240 s confirmation-token poll with IN_PROGRESS resends, 2x60 s status polls, 180 s delivery poll) all exceed the 60 s harness cap, so the cap is reached because the trajectory never produces a value AWS would have produced. The check never reaches the confirm/enable or post-enable delivery steps. Hypothesis: with CreateTopicRuleDestination still an unimplemented scaffold stub in this checkout there is no destination record, no outbound confirmation POST and no status gate for the `http` action to consult.

## Steps to Reproduce
1. Stand up an HTTPS endpoint that logs what it receives (the check uses an API Gateway v2 HTTP API with a $default route fronting a python3.12 Lambda that prints the request's confirmationToken query parameter and the body's `marker`), and self-test it by POSTing a probe and finding it in the function's CloudWatch Logs.
2. iot.create_topic_rule_destination(destinationConfiguration={"httpUrlConfiguration": {"confirmationUrl": <endpoint url>}}) and keep topicRuleDestination.arn; expect status IN_PROGRESS.
3. Wait for the DestinationConfirmation POST at the endpoint and read its confirmationToken; if it does not arrive, call iot.update_topic_rule_destination(arn=<arn>, status="IN_PROGRESS") to request a resend. Observe that no confirmation request ever arrives.
4. iot.create_topic_rule(ruleName=<name>, topicRulePayload={"sql": "SELECT * FROM '<topic>'", "actions": [{"http": {"url": <endpoint url>}}], "ruleDisabled": False}).
5. Publish a unique marker to <topic> through the iot-data plane and assert it never reaches the endpoint (the unconfirmed-destination block).
6. iot.confirm_topic_rule_destination(confirmationToken=<token>), poll iot.get_topic_rule_destination(arn=<arn>) until DISABLED, then iot.update_topic_rule_destination(arn=<arn>, status="ENABLED") and poll until ENABLED.
7. Publish a second marker and assert it now reaches the endpoint. Against the emulator the run never gets past step 3 and is killed at the harness's 60 s cap with no verdict.
