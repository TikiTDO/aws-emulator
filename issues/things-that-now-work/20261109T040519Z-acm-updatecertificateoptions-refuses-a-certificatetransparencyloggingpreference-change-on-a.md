Cause 1 of 1: the non-ISSUED precondition of UpdateCertificateOptions is decided with one class and one sentence for every Options member, so a CertificateTransparencyLoggingPreference change on a certificate that is not ISSUED is refused as a request-constraint violation instead of as the certificate's processing state.

AWS: Smithy UpdateCertificateOptions(CertificateArn required Arn @length 20..2048 @pattern ^arn:[\w+=/,.@-]+:acm:[\w+=/,.@-]*:[0-9]+:[\w+=,.@-]+(/[\w+=,.@-]+)*$, Options required CertificateOptions) -> Unit models ConflictException, InvalidArnException, InvalidStateException, LimitExceededException, ResourceNotFoundException and ValidationException, all errorKind client at HTTP 400 (services/service-com-amazonaws-acm-certificatemanager/smithy-model/com-amazonaws-acm-certificatemanager.json). CertificateOptions has exactly three members: CertificateTransparencyLoggingPreference (@deprecated "Certificate transparency logging opt-out is no longer available.", since 12th June 2026), Export and ValidationMethod. InvalidStateException is documented "Processing has reached an invalid state"; ValidationException "The supplied input failed to satisfy constraints of an Amazon Web Services service". Recorded behavior for the member at issue: a request whose Options names only CertificateTransparencyLoggingPreference, against a certificate whose Status is PENDING_VALIDATION, is refused HTTP 400 with Error.Code InvalidStateException and Error.Message "The selected certificate is not Issued and/or Valid." — wholly FIXED text (no ARN, domain, status, member name or option value is interpolated; the terminating period is part of it), and the refusal writes nothing: Status, Options.CertificateTransparencyLoggingPreference and each DomainValidationOptions[*].ValidationMethod are unchanged afterwards. The same recordings also show the neighbouring legs of this gate, which the emulator already answers correctly and which must not regress: an ISSUED IMPORTED certificate is refused InvalidStateException "The UpdateCertificateOptions command is not permitted for imported certificates." (fixed text), a new public certificate defaults to Options.CertificateTransparencyLoggingPreference ENABLED, and a certificate requested with DISABLED keeps DISABLED. The WIRE corpus records the OTHER member of the same gate differently: Options={'ValidationMethod':'DNS'} on a PENDING_VALIDATION certificate is refused ValidationException "Certificate is not issued" (also fixed text). Hypothesis (neither the model nor either recording states the rule): the non-ISSUED verdict is per-member — a ValidationMethod migration (and the Export leg) fails the operation's request constraints and draws ValidationException "Certificate is not issued", while a CertificateTransparencyLoggingPreference change reaches the certificate's state gate and draws InvalidStateException "The selected certificate is not Issued and/or Valid." — which is the only reading under which both corpora hold, since nothing else in the two requests differs.

Emulator: one branch answers both members. services/service-com-amazonaws-acm-certificatemanager/src/ops/update_certificate_options.rs:286-293 returns UpdateCertificateOptionsErrorModeled::ValidationException { message: crate::state::CERTIFICATE_NOT_ISSUED_MESSAGE } whenever certificate.status != crate::state::STATUS_ISSUED, whatever Options names; the module doc at lines 16-31 states that choice deliberately. So a CT-logging change on a PENDING_VALIDATION certificate comes back HTTP 400 Error.Code "ValidationException" / Error.Message "Certificate is not issued" where AWS answers Error.Code "InvalidStateException" / Error.Message "The selected certificate is not Issued and/or Valid.".

Why: the code is the branch a client takes. A client written to AWS catches InvalidStateException around the deprecated CT-logging opt-out — the refusal that says "this certificate has not been issued yet, so there is nothing to reconfigure; wait or stop" — and the emulator hands it an unhandled ValidationException, which a client reads as "my request is malformed" and never retries, aborting the whole options path. Because ACM reports several distinct conditions per class, the sentence is the only discriminator available, and "Certificate is not issued" matches nothing a client greps for in this class; a client that branches on the message to tell the not-yet-issued gate apart from the imported-certificate gate (which the emulator does answer with InvalidStateException) now sees the two refusals of one operation split across two classes inconsistently.

Fix: the status precondition in the UpdateCertificateOptions handler — the non-ISSUED branch in services/service-com-amazonaws-acm-certificatemanager/src/ops/update_certificate_options.rs and the message constants in crate::state it draws on. Deserialization and serialization are correct; the imported-certificate and Export branches already match their recordings and must be left as they are. Resolving this means deciding the conflict between the two corpora (per-member verdict, as hypothesised above), not flipping the single branch back and breaking the WIRE cause 6 again.
